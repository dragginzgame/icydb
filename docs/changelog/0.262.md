# 0.262 — Entity Creation

## 0.262.1 — 2026-09-30

This is the first release candidate containing entity creation. The completed
implementation originally lived in an isolated worktree; the published
`v0.262.0` tag did not include it. The candidate is now integrated into the main
checkout on that tagged baseline, preserving its maintenance changes and Cargo
resolver version 3. Cargo versions remain 0.262.0 until user-owned release tooling
bumps them. Earlier slice evidence below describes the isolated implementation;
qualification of the integrated source is recorded separately.

### ➕ Added

Ordinary and generated schema proposals can add empty source-version-1 entities
to existing accepted stores, including initial indexes, checks and restrictive
relations. Populated existing entities retain their accepted identities, rows
and index entries. Placeholder declarations are unnecessary for these additions.
Added entities may use new or already accepted named value types. New enum,
record, wrapper and collection definitions use the existing accepted value
catalogs, including supported recursive and shared definitions. Their IDs are
allocated above current accepted IDs within each store. Existing definitions,
type IDs, record-member IDs and enum-variant IDs remain unchanged; redeclarations
require an exact match. Missing references, orphan definitions, occupied paths
and identity exhaustion reject the whole proposal. Creation may accompany
explicit adjacent migrations of existing entities. Metadata migrations publish
both together; physical migrations keep additions unpublished until their
existing final publication phase. Renamed predecessors retain their identity,
including when a new declaration reuses the former source name. New stores and
SQL CREATE TABLE are outside this line's scope.

### 🧭 Migration Notes

With the migration feature, existing entities must have adopted source lineage
before creation. A database created without the feature first needs the unchanged
schema deployed with that feature and adopted. New entity lineage, accepted
catalogs and exact application receipts use the existing compound publication
and interruption-recovery boundary. No format discriminator, endpoint or durable
phase is added; internal encodings remain version 1. Cargo version selection is
left to release tooling.

Mixed proposals retain version 1 for new entities and supply migration
transitions only for existing entities. Existing lineage still requires prior
adoption. Physical admission proves fresh row/index/reverse domains empty before
preparing the migration. Metadata publication and physical final publication
combine fresh lineage with transitioned lineage. Aborting before rewriting
leaves additions unpublished; ordinary operations retain the existing migration
gate during physical work.

### 🧪 Testing

Focused native coverage protects populated preservation, ordinary/generated
application, indexed writes, checks, relation enforcement, deterministic
allocation, version and stale-head rejection, occupied physical domains,
adoption, exact receipt replay and interrupted compound-publication recovery.
Named-type coverage includes recursive enum/record closure, shared definitions,
accepted IDs without source bindings, store-local allocation and atomic rejection
of attempts to edit existing types. Type catalogs and bindings recover with the
added entities and receipt, including interruption after receipt publication.
Mixed-migration coverage protects metadata renames with predecessor-name reuse,
physical fill transforms and new indexes, nested types in added entities,
version/stale-head rejection, occupied fresh domains, abort, rewrite recovery,
compound publication before controls or after the receipt, exact command replay
and unchanged generated reconciliation after recovery.
Existing initial/named-type lowering and migration/publication checks qualify
reuse of the maintained constructors. Generated PocketIC coverage uses populated
current-format source and successor actors for ordinary creation, metadata rename
with creation, and physical field migration with creation. It exercises accepted
identity preservation, indexed old/new reads and writes, enum/record decoding,
relation enforcement, pending and applied restarts, and exact migration replay.
The retained build pipeline reports raw Wasm bytes; local request instruction
intervals and host delivery/lifecycle cycle envelopes are recorded separately.
Full repository and workspace suites remain user-owned.
