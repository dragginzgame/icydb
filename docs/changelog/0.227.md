# 0.227 Framework-Neutral Lifecycle Participation

## 0.227.0 - 2026-08-15

### ➕ Added

- `icydb::start!(participant)` generates the normal database actor without
  exporting `canister_init` or `canister_post_upgrade`. Instead, it exposes one
  hidden crate-local `init` function and one hidden crate-local `post_upgrade`
  function for an application-owned lifecycle root.
- Both participant functions share one volatile `Idle`/`Running`/`Completed`
  latch. A completed duplicate is inert, a running re-entry traps, and message
  rollback permits a clean retry without adding persisted lifecycle state.
- Framework-neutral guidance now shows the required synchronous order:
  restore application authority, invoke IcyDB, reconcile other framework
  state, and only then schedule deferred database work.

```rust
icydb::start!(participant);

#[ic_cdk::init]
fn application_init() {
    restore_application_authority();
    crate::__icydb_lifecycle_participant::init();
    reconcile_application_state();
    schedule_deferred_work();
}
```

### 🔧 Changed

- Generated recovery uses exact `ic-timers 0.3.8` claim-scoped wake-up
  observation while preserving unconditional scheduling whenever durable
  recovery remains actionable.
- Lifecycle registration has one timer-runtime initialization owner instead of
  repeating initialization before the same reconciliation call.
- Startup observation still reads the fixed journal watermark and continuation
  cursor, but constructs the wider journal proof only when an existing durable
  journal-failure receipt can consume it.

### 🧪 Testing

- Compile coverage proves root participant use and rejects malformed, nested,
  duplicate, mixed standalone/participant, and namespace-collision forms.
- Native protocol coverage proves exact function-pointer types, completed
  duplicates, running re-entry traps, rollback, retry, and cross-phase
  duplicate handling.
- PocketIC coverage proves empty and populated same-release upgrades, exact
  synchronous lifecycle ordering while the application remains Prepared,
  E280 admission until Ready, one later database-session opening, row
  preservation, and stable-memory-extent preservation.
- The exact `ic-timers 0.3.8` candidate retains watchdog recovery after a trap,
  40-billion-instruction exhaustion, upgrade reconstruction, overdue timer
  coalescing, and rejection of external timer execution.

### 📊 Audit

- Final participant measurements are 3,146,874 instructions for init,
  7,846,749 for empty post-upgrade, 10,175,810 for populated recovery
  post-upgrade, and 10,593,291 for fully converged populated post-upgrade. The
  reviewed broader-fixture ceiling is 10,750,000 instructions.
- The production evidence artifact is 2,037,038 raw Wasm bytes and 775,954
  deterministic gzip bytes. Its 2,009-byte Candid contains only three
  application audit queries; participant functions, lifecycle controls,
  readiness drivers, and local population seeding are absent.
- Participant mode adds no persisted format, stable allocation, public Candid
  method, executor, timer provider, callback registry, or framework dependency.
  Product structure remains one build-time form and one three-state volatile
  latch, while the closeout removes redundant startup work.
- Fully ready accepted-schema observation has only 1.46% instruction headroom.
  Reducing that cost is an explicit post-0.227 optimization carry-forward;
  future work should optimize it rather than silently raise the ceiling.

### 🧭 Migration Notes

- Existing `icydb::start!()` applications are unchanged. Applications selecting
  participant mode must own the single IC init/post-upgrade export pair and
  invoke the matching generated participant synchronously before scheduling
  deferred database work.
- Choose exactly one start form per canister. There is no alias, compatibility
  spelling, dynamic callback registry, or dual lifecycle dispatch.
- No public database Candid shape, persisted database format, stable-memory
  allocation, readiness state, or recovery protocol changes. Downstream
  lockfiles must resolve the exact `ic-timers 0.3.8` dependency.
