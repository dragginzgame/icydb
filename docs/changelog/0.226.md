# 0.226 Application-Scoped SQL And Schema Read Authority

## 0.226.0 - 2026-08-14

### ➕ Added

- Generated `icydb_query` and `icydb_schema` declarations can select
  `authorization = guard(path)`. The synchronous Rust function receives the
  caller and exact SQL-or-schema surface and returns only `Allow` or `Deny`.
- `icydb::guards::allowlist` provides allocation-free matching for at most 64
  application-owned reader principals and fails closed for anonymous callers
  or oversized lists.
- Guarded SQL and schema denials return distinct typed E281 and E282
  diagnostics, preserving reliable client-side classification.

### 🔧 Changed

- A configured guard replaces controller authority for that read surface; it
  never adds an implicit controller fallback. Applications can grant data-read
  access without giving the reader upgrade, settings, stop, or status powers.
- Authorization runs once after Candid decoding and before request metrics,
  startup admission, parsing, schema observation, or database work. An allowed
  caller must still pass normal readiness and read-only SQL checks.
- SQL and schema remain independent policy surfaces. IcyDB stores and caches no
  authorization decision, makes no remote policy call, and adds no persisted
  format, stable-memory allocation, or Candid field.

### 🧪 Testing

- A framework-neutral PocketIC canister proves initial denial, independent
  allow and immediate revoke, a separate canister controller, reader lifecycle
  denial, stable-memory neutrality, and exact SQL/schema recovery after a
  same-release upgrade.
- Matched controller and guarded builds retain identical Candid and exported
  query modes. Enabling both guards adds 250 raw Wasm bytes, well below the
  frozen 128-KiB ceiling.

### ⚠️ Breaking

- The new public Rust guard types and diagnostic enum variants are additive,
  but downstream exhaustive matches over those enums must handle the new
  cases. No compatibility aliases or fallback authorization paths are kept
  before 1.0.
