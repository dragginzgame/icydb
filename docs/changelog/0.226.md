# 0.226 Application-Scoped SQL And Schema Read Authority

## 0.226.1 - 2026-08-14

### 🩹 Fixed

- Generated lifecycle hooks now reserve the fixed startup-watchdog identity as
  an inactive retained declaration while the database is ready or terminally
  failed, and schedule that same declaration only while recovery is pending.
  This keeps lifecycle reconstruction and later application timer registration
  deterministic without creating an unnecessary wake-up.
- The authorization compile contract now routes every accepted Rust guard-path
  form through the production endpoint grammar as well as exact
  function-pointer coercion.
- Combined PocketIC evidence now proves that the non-human canister controller
  receives E281/E282 unless the application guard grants it, and that denial,
  allow, query, and revoke activity changes no stable bytes.
- The deliberate allocation-free scalar route representation is warning-clean
  under both native and Wasm32 Clippy without adding indirection.

### 🔧 Changed

- Generated recovery and maintained application timers hard-cut to exact
  `ic-timers 0.3.4`. The shared lifecycle helper owns retained declaration
  lifetime; IcyDB keeps no direct timer-provider path, lifetime selector,
  compatibility mode, or second registry.
- Maintained read-admission and session documentation now distinguish caller
  authorization from query-shape admission and describe guarded generated SQL
  as an alternative to the unchanged controller default.

### 🧪 Testing

- The final closeout reran the focused guard, diagnostic, parser, Candid,
  PocketIC, native/Wasm32 lint, Wasm build, repository-invariant, formatting,
  and diff-hygiene gates. The 0.226 verdict remains `ACCEPTED`.
- The updated SQL-performance lifecycle subject is 4,164,071 final raw Wasm
  bytes, remaining within its frozen owner ceiling. Candid remains
  byte-identical at 60,348 bytes, and the combined guarded/controller read
  subject still differs by only 250 raw Wasm bytes.

### 🧭 Migration Notes

- No public Candid, persisted database format, stable-memory allocation, or
  authorization result changes. Downstream lockfiles must resolve the exact
  `ic-timers 0.3.4` dependency; no older timer compatibility path is retained.

## 0.226.0 - 2026-08-14

### ➕ Added

- Generated `icydb_query` and `icydb_schema` declarations can select
  `authorization = guard(path)`. The synchronous Rust function receives the
  caller and exact SQL-or-schema surface and returns only `Allow` or `Deny`.
- `icydb::guards::allowlist` provides allocation-free matching for at most 64
  application-owned reader principals and fails closed for anonymous callers
  or oversized lists.
- Guarded SQL and schema denials return distinct typed E281 and E282
  diagnostics, preserving reliable client-side classification.

### 🔧 Changed

- A configured guard replaces controller authority for that read surface; it
  never adds an implicit controller fallback. Applications can grant data-read
  access without giving the reader upgrade, settings, stop, or status powers.
- Authorization runs once after Candid decoding and before request metrics,
  startup admission, parsing, schema observation, or database work. An allowed
  caller must still pass normal readiness and read-only SQL checks.
- SQL and schema remain independent policy surfaces. IcyDB stores and caches no
  authorization decision, makes no remote policy call, and adds no persisted
  format, stable-memory allocation, or Candid field.

### 🧪 Testing

- A framework-neutral PocketIC canister proves initial denial, independent
  allow and immediate revoke, a separate canister controller, reader lifecycle
  denial, stable-memory neutrality, and exact SQL/schema recovery after a
  same-release upgrade.
- Matched controller and guarded builds retain identical Candid and exported
  query modes. Enabling both guards adds 250 raw Wasm bytes, well below the
  frozen 128-KiB ceiling.

### ⚠️ Breaking

- The new public Rust guard types and diagnostic enum variants are additive,
  but downstream exhaustive matches over those enums must handle the new
  cases. No compatibility aliases or fallback authorization paths are kept
  before 1.0.
