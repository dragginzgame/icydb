# IcyDB 0.261

## 0.261.18 — Recovery, Record Renames And Internal Cleanup

### 🩹 Fixed

- Recompute structural not-null names when field removal renumbers their owners,
  so a later non-null SQL column can reuse the field number without a name
  collision. Retained constraint IDs, ownership, allocator state and authored
  check names are preserved; current encodings and publication paths are unchanged.

- Preserve retained row values and primary keys when physical migration removes
  an earlier field. Bind generated fields through accepted source lineage and
  explicit renames, and SQL-owned fields through their retained catalog names.
  Dense numeric IDs no longer select unrelated predecessor slots.
- Permit source migration after SQL-owned catalog edits by checking freshness
  against the live accepted head at the command boundary. Lineage retains its
  publication head as provenance; source versions/digests remain authoritative.
  Proposal and command heads must agree, stale requests still reject, and later
  SQL edits do not make an applied source plan pending again. Full rewrites
  clear historical absence fills for SQL-owned fields as well as generated
  fields, preserving future insertion defaults and materialized values.
  Current persisted encodings and the existing publication/recovery flow are
  unchanged.
- Decimal checked division returns `None` for signed integer division overflow;
  division operators use their existing saturation result, and database numeric
  evaluation reports typed overflow instead of panicking.

- Preserve generated Identity high-water, exhaustion and replay identity when
  removing another field renumbers the retained primary key. Accepted source
  bindings prove the move; schema publication relocates the state and removes
  its old key through live replay and canonical folding without adding a retired
  owner. Unknown lineage and occupied destinations reject before publication.
  Existing removal admission rules remain; previously published allocator resets
  are not repaired. Public APIs and persisted encodings are unchanged.
- Route retained row journals through the stable accepted entity tag encoded in
  their primary keys. Same-store entity renames can now fold earlier writes and
  recover later commit markers after volatile catalog state is lost. Row names,
  schema fingerprints and keys remain checked during preparation; journal
  encodings and public APIs are unchanged. Replay binds relation targets from
  the same canonical catalog state as source rows, so retained self/inbound
  relations also fold across a rename without first draining pending writes.
  Ordinary writes keep live target authority and exact identity/key-kind checks.
- Reject a journaled store's changed registered Rust path before replay when it
  disagrees with the verified accepted catalog. The existing unsupported
  configuration error leaves no terminal failure receipt, so restoring the
  original path can resume recovery. Genuine persisted corruption retains its
  durable failure classification. Transparent store renames remain unsupported;
  this prevents new erroneous receipts and does not clear previously recorded
  failures.
- Rewrite stored record-member names before publishing their renamed catalog.
  Stable accepted member IDs map predecessor values to current names through
  records, lists, sets, maps, tuples, newtypes and enum payloads; ordered
  containers are canonicalized after rewriting. Transitions declaring a
  record-member rename use the existing bounded physical migration. The proposal
  contract requires every entity sharing that record to declare the rename.
  This prevents unsafe publication; it does not repair previously published
  invalid renames.
- Apply accepted index predicates when rechecking unique ownership against a
  batch's final rows. Transferring a unique value by changing filter membership
  now preserves the same result in preflight, journal folding and restart
  recovery, for field-path and expression indexes. Genuine final-row collisions
  remain rejected. Reuse the mutation planner's compiled predicate and existing
  membership-aware key builders; public APIs and stored formats are unchanged.

### ⚠️ Breaking

- Record-member renames no longer publish in a single metadata-only `Advance`.
  Continue the normal physical migration through `Applied`; validation/rewrite
  gating and the pre-rewrite abort boundary apply. Public command shapes and
  current version-1 encodings are unchanged; no database recreation is required.

## 0.261.17 — Query And Migration Correctness, State Cleanup

### 🩹 Fixed

- Preserve excluded primary-key endpoints in reads, counts, updates and deletes.
  A two-sided range such as `id >= 2 AND id < 5` retains its endpoint predicate
  over the inclusive physical scan, so the row at `id = 5` is excluded.
  Remove the unsound planner range proof; exact key and key-list proofs remain.
- Keep migration validation and abort isolated from ordinary retained journal
  writes. Candidate staging and cleanup update only their exact canonical keys,
  preserving accepted index entries, live overlays, journal positions, fold
  watermarks and prefix-count deltas. This prevents incorrect indexed reads and
  later fold failures caused by moving ordinary index effects ahead of rows.
- Remove whole-store migration folding and its snapshot/cardinality rebuild
  helpers. Journal folding and candidate staging share the existing per-key
  canonical index writer; no public API or stored format changes. This prevents
  new corruption from this path; it does not repair previously corrupted stores.

### 🧪 Testing

- Add executed row-set and mutation-count coverage for primary-key endpoints,
  including inclusive/exclusive combinations, equal endpoints and `BETWEEN`.
  Numeric and ULID page coverage includes both directions, total limits,
  full-row and key-only projections, and continuation exhaustion.
- Cover retained inserts, updates and deletes before preparation and during
  Prepared, validation staging, abort, online folding and restart recovery.
  Assert indexed row sets and exact counts, canonical-key and watermark
  preservation, and successful folding of a subsequent delete. Existing bounded
  cleanup and idempotent staging coverage uses the same canonical write owner.
