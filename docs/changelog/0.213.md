# IcyDB 0.213: Schema Authority And Application Separation

## 0.213.6

### 📝 Summary

- Connects the first public schema-application path end to end for initial
  scalar database proposals.
- Keeps accepted candidates, source identity, marker publication, and durable
  receipt replay under their existing canonical owners.

### ➕ Added

- Added `DbSession::apply_schema` to the core and public facade.
- Added one catalog-native initial-proposal lowerer for exact scalar fields,
  row layouts, insert defaults, generated and managed write policy, secondary
  indexes, restrictive relations, accepted checks, and immutable entity,
  field, index, relation, and check source bindings.
- Added immutable-source-key check-expression binding through the maintained
  accepted check language and canonical renderer.

### 🔧 Changed

- Application now revalidates the proposal digest, target database, target
  stores, and optimistic accepted head before constructing candidates.
- Exact retries return the durable receipt. Reusing the same submission
  identity with another digest or prior head returns a typed conflict.
- All store-local candidates and the terminal application receipt publish
  through one commit marker. Receipt-only no-ops use the same durable boundary.
- Initial publication requires empty row and index stores and a ready index
  lifecycle. A dirty or incomplete derived store rejects before schema or
  receipt mutation.

### ⚠️ Breaking

- Named types, removals, and structural transitions over an existing accepted
  head remain unsupported and fail before mutation.
- No generated-model reconstruction, compatibility adapter, partial
  publication, or alternate activation path is retained.

### 🧭 Persistence

- This patch introduces no new persisted format beyond the current-form
  accepted source bindings, commit-marker effect, and application record
  established earlier in 0.213.
- Accepted schema, rows, indexes, relations, journals, cursors, and receipt
  records retain their 0.213.5 formats.

### 📊 Audit

- The maintained `sql_perf` subject is 5,333,126 raw non-gzipped Wasm bytes,
  840 bytes (+0.0158%) above 0.213.5 and 175,644 bytes (+3.4056%) above the
  0.213 opening baseline.
- Its raw SHA-256 is
  `acccdc28af3196a72487fe8f39133a8cb4895c8668b9c4f61fdeee714aa954e3`.
- The slice touches 17 Rust source/test files at approximately `+1,850/-27`
  lines before documentation. Runtime structure grows through one real
  lowerer and ingress, while proposal lowering, accepted publication, and
  receipt replay each retain one authority.

### 🧪 Testing

- Focused tests cover scalar defaults, indexes, accepted checks, source
  bindings, named-type rejection, exact replay, conflicting reuse, real
  journaled initial application, dirty-derived-state rejection, and atomic
  candidate-plus-receipt publication.
- Core and facade warnings-denied lint, no-default compilation, formatting,
  diff hygiene, and schema/model, layer-authority, mutation-atomicity,
  dependency, and durability guards pass.
- Full repository validation remains part of the human-owned push workflow.

### 🧭 Follow-up

- Existing-head and named-type lowering, pending receipts, and reuse of the
  0.211 activation jobs remain the unfinished Patch 2B work.

## 0.213.5

### 📝 Summary

- Establishes the durable idempotency and result protocol required by
  database-scoped schema application.
- Keeps receipts subordinate to the existing commit marker and 0.211
  activation architecture rather than creating a second publication or job
  engine.

### ➕ Added

- Added public opaque schema-change job identity, terminal/pending outcome,
  compact typed failure, and durable receipt projections.
- Added guarded receipt lookup by exact database identity and immutable
  submission key.
- Added one bounded database-wide record owner for canonical receipt and
  pending-activation state. Records are limited to 64 KiB, pending records to
  512 canonically ordered activation identities, and the store to 64 retained
  submissions.

### 🔧 Changed

- A commit marker may now own one exact schema-application record
  compare-and-replace effect.
- Marker admission preflights capacity and the expected prior record before
  opening the durable commit window.
- Normal apply and recovery accept only the expected prior bytes or the
  already-applied final bytes. Recovery verifies the final record before
  marker clearance.
- Pending receipts can transition only to `Applied` with their exact reserved
  candidate head or to a typed `Failed` state. Terminal receipts are
  immutable, no-op receipts retain the prior head exactly, and all persisted
  diagnostic identities must be registered current-form values.

### 🧭 Persistence

- Added the first current-form schema-application record format: one
  checksummed stable map in a restricted region after the existing bounded
  commit-control frame.
- The existing stable allocation identity is reused without overlapping the
  marker frame; no new canister memory ID is introduced.
- The transient commit-marker payload gains the optional exact record effect.
  Superseded in-flight development marker bytes fail current-form decoding;
  no compatibility decoder or translation path is retained.
- Accepted schema, row, index, relation, journal, cursor, database-control
  envelope, and 0.211 validation-job formats are unchanged.

### 📊 Audit

- The maintained `sql_perf` subject is 5,332,286 raw non-gzipped Wasm bytes,
  90,712 bytes (+1.7307%) above 0.213.4 and 174,804 bytes (+3.3897%) above the
  0.213 opening baseline.
- Its raw SHA-256 is
  `25b861c1fb3d8d93fbdcdc0ee3519165a9418d5a8a4501a26e419f05eaaf069c`;
  the canonical shrunk artifact is 4,966,388 bytes and deterministic raw gzip
  is 1,679,676 bytes.
- The raw artifact is 71,655 bytes above the original +2.00% review line. The
  overage is retained as the reviewed cost of the planned durable receipt,
  codec, marker/recovery, and public projection capability rather than hidden
  behind shrunk or gzip measurements.
- The implementation touches 15 Rust source/test files at approximately
  1,580 net lines before documentation, including roughly 550 focused
  test/accessor lines. Runtime structure becomes materially more complex
  through one bounded durable owner and one marker effect, but adds no second
  application protocol, publication owner, or activation runner.

### 🧪 Testing

- Focused coverage exercises canonical encoding and checksum failure,
  idempotent insert/replacement, compare conflicts, terminal immutability,
  candidate-head binding, bounded capacity, reopen, marker round-trip, and
  interrupted recovery.
- All-target, all-feature warnings-denied Clippy for `icydb-core` and `icydb`,
  native and Wasm no-default compilation, formatting, diff hygiene, and the
  dependency, generated-build, schema/model, layer-authority,
  mutation-atomicity, and durability-documentation guards pass.
- Full repository validation remains part of the human-owned push workflow.

### 🧭 Follow-up

- Catalog-native proposal lowering must construct these exact record effects.
  The later application-wiring slice will publish them atomically with
  multi-store candidates and resume the existing 0.211 activation owners.

## 0.213.4

### 📝 Summary

- Makes SQL DDL participate in the same immutable source-identity model that
  catalog-native schema proposals will consume.
- Keeps editable SQL names separate from store-local accepted identity without
  adding a second schema catalog or a compatibility backfill.

### 🔧 Changed

- A newly accepted SQL-owned field, secondary index, or `CHECK` constraint now
  receives an immutable source key derived from its entity and monotonic
  accepted publication revision.
- Existing keys follow their structural owner through field rename, dense
  field-ID reassignment, check and index activation, and final promotion.
- Drop and activation-abort transitions remove the corresponding binding in
  the same accepted-schema publication as the structural owner.
- Dense field compaction resolves unchanged-name lineage before considering a
  same-ID rename, preventing a removed field's key from transferring to the
  different field that inherits its physical ID.
- Objects accepted before their maintained admission path supplied immutable
  authorship remain unbound. The release does not infer identity from an
  editable name or reconstruct historical bindings.

### 🧭 Persistence

- The source-binding codec and accepted revision-bundle envelope remain
  unchanged.
- Entity snapshots, rows, indexes, relations, journals, cursors, and commit
  markers retain their existing formats.
- New SQL-DDL bindings participate in the accepted semantic fingerprint as
  part of the same candidate revision that creates their structural owner.

### 📊 Audit

- The maintained `sql_perf` subject is 5,241,574 raw non-gzipped Wasm bytes,
  24,324 bytes (+0.4662%) above 0.213.3 and 84,092 bytes (+1.6305%) above the
  0.213 opening baseline. It remains below the frozen +2.00% review budget.
- Its raw SHA-256 is
  `f9e9fd1ebf50e864a07357d1ba5ba24b87f20fd9e766ee301d06c186ab967636`;
  the canonical shrunk artifact is 4,882,816 bytes.
- The implementation changes six production, test, and structural-guard files
  at approximately 429 net lines before documentation. Runtime structure
  becomes moderately more complex inside the existing source-binding owner
  but adds no second catalog, proposal lowerer, receipt type, or application
  entry point.

### 🧪 Testing

- Focused all-feature coverage exercises field creation, non-trailing dense
  field removal, field rename, direct and activating checks, check abort,
  index creation and drop, and marker-authorized recovery.
- All-target, all-feature warnings-denied `icydb-core` Clippy, native
  no-default compilation, formatting, diff hygiene, schema/model authority,
  layer authority, mutation atomicity, and durability-documentation guards
  passed for the release slice.
- Full repository validation remains part of the human-owned push workflow.

### 🧭 Follow-up

- Catalog-native proposal lowering, durable idempotent receipts, the public
  application caller, and reuse of 0.211 activation jobs remain the coupled
  Patch 2B implementation boundary.

## 0.213.3

### 📝 Summary

- Completes immutable proposal identity for accepted enum variants before
  catalog-native proposal lowering begins.
- Keeps editable enum and variant names separate from their accepted
  store-local identities.

### 🩹 Fixed

- Added the missing enum-type-scoped variant namespace to the existing accepted
  source-binding catalog.
- A bound enum type must now bind every accepted variant exactly once.
  Variant bindings without their bound enum type, missing accepted variants,
  duplicate accepted identities, malformed source keys, and absent structural
  owners fail closed.
- Proposal application can therefore preserve a variant across an editable
  rename instead of reconstructing identity from its name or treating the
  rename as delete-plus-add.

### ⚠️ Breaking

- The accepted source-binding envelope and enclosing accepted revision bundle
  gain the enum-variant binding table. Development stores written by 0.213.0,
  0.213.1, or 0.213.2 must be recreated.
- The current format remains version 1 under the pre-1.0 hard cut. No
  compatibility decoder, translation path, name-based reconstruction, alias,
  or fallback reader is retained.

### 🧭 Persistence

- Accepted revision-bundle bytes and their semantic fingerprints change.
- Entity snapshots, enum definitions, rows, indexes, relations, journals,
  cursors, commit markers, and public response formats do not change.

### 📊 Audit

## 0.213.2

### 📝 Summary

- Adds the durable atomic publication foundation required by database-scoped
  schema proposals without exposing a partial application API.
- Consolidates accepted-schema binary envelopes behind one bounded primitive
  codec while preserving their current bytes and format ownership.

### 🔧 Changed

- Plain accepted-schema candidates for multiple journaled stores now preflight
  completely and publish through one canonically ordered commit marker.
- All marker-owned journal batches append before any candidate becomes the
  live accepted root. Recovery completes every store after an interruption
  leaves only a prefix of those batches appended.
- Equal journal sequence numbers from different stores are now treated
  correctly as tail-local identities. Additional batches receive distinct
  marker-local IDs, while established single-store batch bytes remain
  unchanged.
- Enum catalogs, composite catalogs, accepted revision bundles, and source
  bindings now share one checked primitive wire reader/writer. Each envelope
  continues to own its own magic, current version, byte ceiling, canonical
  ordering, and semantic validation.

### 🩹 Fixed

- Fixed the durable commit-marker representation that previously made a
  legitimate commit spanning two journaled stores fail when their next
  tail-local sequences matched or their batches reused the marker ID.
- Mixed already-current and new candidate sets fail closed instead of
  permitting a partially replayed database-scoped publication.
- Multi-store publication involving volatile stores rejects before mutation
  because no durable recovery authority can complete it atomically.

### 🧭 Persistence

- No accepted-bundle, commit-marker, journal, row, index, relation, cursor, or
  public response encoding changes in this patch.
- The current version-1 codecs remain hard-cut. No compatibility decoder,
  alias, translation path, or legacy fallback was added.

### 📊 Audit

- The maintained `sql_perf` subject is 5,207,037 raw non-gzipped Wasm bytes,
  334 bytes (-0.0064%) below 0.213.1 and 46,189 bytes (+0.8950%) above the
  0.213 opening baseline. Its raw SHA-256 is
  `1c006a2047cf8cd54dcca438e5fac330493ce655bdbc8fa249effe1183c6e8ae`.
- The canonical shrunk artifact is 4,850,206 bytes, 263 bytes below 0.213.1.
- The complete release-prep worktree changes 15 files at approximately
  `+803/-448` lines,
  including focused recovery tests and release evidence. Production code is
  approximately 15 lines smaller overall: the shared codec removes more code
  than the atomic publication owner adds.

### 🧪 Testing

- Focused tests cover equal sequence numbers across journal tails, successful
  two-store publication, interruption after a journal prefix, recovery
  completion, and retained single-store activation behavior.
- All-feature warnings-denied Clippy, native no-default compilation,
  formatting, diff hygiene, schema/model layering, mutation atomicity, and
  durability guards pass.
- Full repository validation remains part of the human-owned push workflow.

### 🧭 Follow-up

- Catalog-native proposal lowering, durable idempotent receipts, the public
  application caller, and reuse of 0.211 activation jobs remain the next
  coupled Patch 2B work.

## 0.213.0

### 📝 Summary

- Opens the 0.213 architecture line by separating the pure public schema
  contract from generated application-model metadata and database runtime
  authority.
- Adds bounded exact proposal composition and a read-only target context for
  future optimistic catalog-native application.
- Does not yet add schema mutation through `SchemaProposal`, durable receipts,
  or multi-store schema publication.

### ➕ Added

- Reclaimed `icydb-schema` as the standalone public proposal and canonical
  scalar leaf. It has no dependency on the database runtime, generated model
  graph, storage, recovery, clocks, generators, or application callbacks.
- Added bounded immutable source identities for entities, fields, named types,
  constraints, indexes, and relations.
- Added a current version-1 proposal envelope with explicit capability
  requirements, database/store routing tokens, an immutable submission key,
  an exact expected accepted head, explicit removals, and deterministic
  canonical encoding and digesting.
- Added exact scalar field contracts, source-keyed enum literals, bounded
  accepted-check source expressions, structural record fields, database insert
  policy, generated-value intent, and managed timestamp declarations.
- Added deterministic database-scoped composition with duplicate-definition,
  name, routing, removal, type-graph, enum-literal, relation-closure, and
  capability validation.
- Added `DbSession::schema_application_target`, which issues an opaque database
  identity, canonically ordered store-routing identities, and one exact
  multi-store accepted head from recovered runtime authority.

### 🔧 Changed

- Moved the previous `icydb-schema` authoring graph intact to the unpublished
  temporary `icydb-model-legacy` package so the reclaimed package cannot mix
  the retired graph with the new proposal contract.
- Made `icydb-schema` the single Rust representation owner for canonical
  scalar atoms. `icydb-core` retains runtime operations and re-exports those
  same representations rather than defining parallel scalar types.
- Split exact proposal composition from durable catalog application.
  Composition validates untrusted source-keyed intent but allocates no accepted
  identities, publishes no schema, and owns no marker or recovery behavior.
- Database identities are bound to the durable database incarnation and the
  complete registered store topology. Store identities additionally cover
  their path, capabilities, and stable allocations.
- The optimistic accepted head covers every store-local accepted root in
  canonical path order, including explicit absence, so a topology or accepted
  root change invalidates stale proposal context.
- Kept ULID generation as an engine-owned operation through `GenerateKey`;
  maintained fixtures import that runtime capability explicitly while the
  standalone schema leaf remains free of randomness and clocks.

### ⚠️ Breaking

- Removed the separate `icydb-primitives` package without an alias or
  compatibility wrapper.
- Reclaimed the `icydb-schema` package name for the new proposal/scalar
  contract. The old authoring API is not preserved under that public path.
- Removed permissive and alias `Date` constructors. Strict construction uses
  `Date::try_new`, while textual input uses `Date::parse`.
- The proposal codec accepts only its current version-1 form. No compatibility
  decoder or translation path exists for superseded development shapes.

### 📊 Audit

- The 0.213 opening `sql_perf` subject was 5,157,482 raw non-gzipped Wasm
  bytes. The closing 0.213.0 subject is 5,160,848 bytes, an increase of 3,366
  bytes (+0.0653%) and well below the frozen +2.00% review budget.
- The canonical shrunk artifact is 4,806,575 bytes.
- The affected source seam grew from 176 Rust files and 33,212 lines to
  approximately 194 files and 37,000 lines. Most growth is the bounded public
  contract, exact composition validation, tests, and the temporary package
  bridge. It remains below the frozen +15% source review tripwire.
- The target-authority slice adds no retained bytes to the measured
  `sql_perf` Wasm subject compared with the preceding exact-composition slice.
- No accepted-schema, row, index, relation, cursor, journal, commit-marker, or
  recovery persisted format changes in 0.213.0.

### 🧪 Testing

- Focused proposal tests cover malformed versions and capabilities, collection
  and byte bounds, source-key identity, canonical ordering and digest vectors,
  exact scalar/default compatibility, enum literals, named-type cycles and
  depth, explicit removals, and cross-fragment relation closure.
- Focused runtime tests prove stable target issuance, canonical multi-store
  ordering, distinct store identities, topology-bound database identity, and
  exact accepted-root coverage.
- The schema leaf, core, facade, moved legacy package, build package, and
  derive seams pass their focused compilation and warnings-denied checks.
- No-default-feature checks, documentation tests, formatting, diff hygiene,
  package-boundary guards, memory-allocation guards, and publication guards
  pass.
- Full repository validation remains part of the human-owned push workflow.

### 🧭 Follow-up

- Catalog-native source-to-accepted bindings, proposal lowering, durable
  idempotent receipts, atomic multi-store publication, and reuse of the 0.211
  activation machinery remain subsequent 0.213 work.
- The temporary unpublished model package deliberately blocks workspace
  publication until the final model-package and consumer cutover removes that
  bridge.
