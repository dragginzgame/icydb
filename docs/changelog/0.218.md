# IcyDB 0.218 — Explicit Versioned Schema Migrations

## 0.218.0

### 📝 Summary

- Adds one explicit, durable migration path between adjacent per-entity source
  versions. Accepted schema remains runtime authority; generated declarations
  propose the successor and one canister-owned plan accounts for every rename
  or physical rewrite.
- Runs physical work as a database-wide offline operation with bounded durable
  phases, exact plan identity, marker-bound publication, and deterministic
  recovery after traps or upgrades.
- Adds controller-operated migration status and command endpoints plus CLI
  `status`, `adopt`, `advance`, `run`, and pre-rewrite `abort` operations.
- Makes engine-neutral typed and dynamic reads part of base IcyDB, leaving SQL
  as an optional frontend over the same planner and executor.

### ➕ Added

- `#[entity(version = N)]` now carries an effective positive per-entity source
  version. `#[canister(migrations(...))]` owns one coordinated plan containing
  explicit immediate-predecessor transitions.
- The closed initial transform language supports literal fill, exact copy,
  checked fixed-integer or fixed-scale Decimal cast, and nullable coalesce.
  Unsupported conversions fail at proposal admission rather than invoking
  application code during execution.
- Exact catalog-native renames cover entities, fields, named types, enum
  variants, record members, relations, constraints, and durable rules while
  preserving accepted IDs and removing predecessor names immediately at
  publication.
- Existing pre-0.218 databases can explicitly adopt an exact version-1
  generated schema before their first migration. Fresh databases record
  current source lineage when first created.
- Bounded validation stages candidate constraints, unique-index generations,
  and reverse-relation generations without changing accepted rows. Bounded
  rewriting then publishes current row envelopes and candidate derived keys
  through the ordinary journal and commit-marker owners.
- Public guidance now documents the required adoption deployment, adjacent
  successor deployment, offline run/resume window, abort boundary, and final
  verification sequence.

### 🔧 Changed

- Proposal transport is now sole current contract version 2 and includes
  effective entity versions plus an optional canonical plan and digest.
- The commit-marker envelope is now sole current version 2 and atomically
  carries up to four canonical database-control compare-and-replace effects.
- Ordinary reads, writes, DDL, relation work, and schema mutation are gated
  from migration validation through final publication. `Prepared` remains
  available until advancement begins; terminal `Applied` and `Aborted` records
  do not block later same-version startup.
- Journal batch version 1 gains exact plan-bound migration row and candidate
  index records. Existing row, primary-key, index-key, reverse-key, cursor, and
  accepted-snapshot encodings remain otherwise unchanged.
- The optional `query` feature is removed. Base IcyDB now owns structural,
  typed, and dynamic reads without a compatibility feature alias, while `sql`
  includes the complete SQL frontend and its EXPLAIN capability.
- Compact and extended metrics types remain available from base IcyDB. Source
  declarations or direct API use select extended metrics instead of a separate
  `metrics-extended` Cargo feature.
- SQL-only scalar aggregate terminals remain excluded from base builds. COUNT,
  SUM, and AVG now share one reducer across scalar, grouped, and
  grouped-DISTINCT execution.
- Canonical schema construction, source digests, proposal application,
  accepted-catalog transitions, migration staging, publication, recovery,
  integrity proof, and deterministic diagnostic paths use unstable sorting
  where duplicate keys already reject or the sort key is total. Canonical
  bytes, diagnostic order, and executor response order are unchanged.

### 🩹 Fixed

- Rename rekeying now enforces local accepted-ID uniqueness within its owning
  entity or named type, so equal local field IDs in unrelated entities do not
  conflict while same-owner aliases still reject.
- A same-field checked cast retains that field's original introduction-layout
  identity; only genuinely new target fields are introduced by the successor
  layout.
- A terminal migration receipt is recognized before active-plan validation,
  allowing generated schema startup after final publication rebases the
  accepted head.
- Release invariants now recognize the accepted commit-marker version-2 hard
  cut without requiring PCRE2, and track the canonical unstable-sort spelling
  used by schema application.

### 🗑️ Removed

- Removed SQL-DDL predicate relabeling and complete user-index staging from
  base builds while retaining shared predicate execution and accepted
  uniqueness enforcement below the SQL frontend.
- Removed two unused direct dependencies and the obsolete endpoint-compiler
  dead-code suppression left from the pre-0.217 authority cut.
- Removed the retired `query` and `metrics-extended` feature names without
  aliases, dual feature paths, or compatibility behavior.

### ⚠️ Breaking

- Proposal version 1 and commit-marker version 1 have no compatibility
  decoder. This is a pre-1.0 hard cut; incompatible development state must be
  recreated rather than translated.
- Accepted source names are not aliases. After an applied rename, the old name
  is absent from accepted bindings and callers must use the successor name.
- There is no inferred rename, global source-schema version, SQL migration
  language, online rolling-schema mode, or generated-model runtime fallback.

### 🧭 Migration Notes

- Enable the optional `migration` Cargo capability only in migration-capable
  Wasm artifacts and explicitly declare `icydb_schema_migration` and
  `icydb_schema_migrate`; compiling the capability alone exports nothing.
- Adopt an existing version-1 database in a separate deployment, then deploy
  exactly one adjacent successor plan. Keep that exact successor Wasm
  available until the deployed status reaches `Applied`.
- `run` repeatedly performs bounded advances and fails if database, accepted
  head, deployment, or plan identity changes. Before rewriting, `abort --yes`
  cleans candidate state in bounded pages; after rewriting starts, the exact
  plan must resume to completion.

### 📊 Audit

- Added matched exact-key typed, dynamic, and SQL audit canisters plus a
  symbol-bearing attribution profile. These fixtures separate query-engine
  Wasm cost from typed adapters, SQL frontend code, and entity-count effects;
  production decisions continue to use raw non-gzipped `wasm-release` bytes.
- A maintained journaled SQL fixture upgrades from version 1 to version 2,
  renames `rank` to `score`, casts `age` from `Int32` to `Nat16`, survives an
  intervening same-plan Wasm upgrade, observes the database gate, completes
  all persisted phases, and rejects the predecessor field name afterward.
- The production-shaped SQL fixture is 5,209,288 raw Wasm bytes without the
  migration capability, 5,526,795 bytes with migration operations but no
  active plan, and 5,594,418 bytes with the maintained version-2 plan. The
  capability-and-endpoint delta is 317,507 bytes (6.095%); the concrete plan
  adds a further 67,623 bytes (1.224%).
- On the no-active-plan artifact, 32 warm SQL calls average 704,990
  instructions versus 704,094 without migration: 896 instructions or 0.127%
  per call. This is a focused hot-path observation, not a general scaling
  guarantee.
- Raw export inspection shows that enabling migration adds only query
  `icydb_schema_migration` and update `icydb_schema_migrate`. No existing
  Candid method or persisted row/key/cursor shape changes.
