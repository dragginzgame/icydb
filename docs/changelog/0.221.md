# IcyDB 0.221 — Request-Bounded Query Reliability And Resumable Reads

## 0.221.9

This release removes redundant payload work from primary-key scans and adds an
opt-in way to see when one endpoint is issuing the same kind of query over and
over. It completes the repository-owned 0.221 reliability work without
changing persisted rows, schemas, journals, or cursor formats.

### 📝 Summary

- Primary-key scans enumerate candidate keys without loading their payloads.
  A row that survives index filtering is fetched at most once, and unrelated
  large fields remain lazily decoded unless the filter or result needs them.
- Applications built with the `diagnostics` feature can enable one bounded
  diagnostic summary on the active request root. Every nested session and
  `db!()` call contributes to that same summary and aggregate work budget.
- The summary groups literal-free query shapes and reports cache activity,
  rows and bytes processed, hashed repeated-key counts, residual predicates,
  bounded overflow, and useful compound-index candidates.
- Repeated point lookups produce an actionable `get_many` warning. A scan that
  selects `collection_id` while filtering `stage` can suggest the ordered
  `collection_id, stage` prefix; diagnostics never create the index
  automatically.

### ➕ Added

- `DbSession::enable_request_diagnostics` enables collection for the current
  request, while `DbSession::request_diagnostics` returns its bounded snapshot.
  The public DTOs are available only when the `diagnostics` feature is enabled.
- Diagnostics retain at most 32 normalized query shapes and 128 hashed key
  identities. Labels, field lists, warnings, and output size have independent
  caps, with suppressed observations and capacity overflow reported explicitly.
- Exact-key observations preserve original input positions, so duplicate
  logical requests remain visible even when `get_many` performs only one
  physical read per distinct key.

### 🔧 Changed

- Heap and journaled primary-range traversal now use a key-only store boundary.
  Journal overrides and tombstones keep their existing forward and reverse
  ordering, while candidate enumeration no longer clones a stored payload.
- Residual filtering, ordering, grouping, and projection share the terminal
  row runtime's one fetched payload and its existing per-row structural-slot
  cache. Index-covered rejection still avoids the fetch entirely.
- Query-plan observations are recorded at the shared cache boundary, and
  physical work comes from the authoritative hard-budget tracker. Diagnostic
  work consumes the same request's diagnostic, temporary-byte, and result-byte
  allowances.
- Exhausting a diagnostic allowance suppresses detail instead of changing a
  successful query result. Failed queries and later sessions cannot refund or
  reset either the diagnostic evidence or aggregate database work.

### 🧭 Migration Notes

- Existing applications require no data migration and pay no diagnostic
  collection cost unless compiled with `diagnostics` and enabled for a request.
- Treat compound-index output as evidence for schema design, not an automatic
  migration. Confirm the proposed order against real canister instruction and
  byte measurements before accepting a new index.
- reference application still needs to reuse its preloaded provenance, snapshot, and token-type
  maps inside the per-token validation loop. IcyDB makes that N+1 pattern
  visible and bounded; it does not rewrite application control flow.

### 🧪 Testing

- Focused heap and journaled tests prove key-only primary enumeration, one
  payload fetch for accepted rows, index-covered rejection, tombstone ordering,
  and lazy access to a 300 KiB unrelated field.
- Diagnostic coverage proves bounded shapes and keys, raw-value redaction,
  fail-soft accounting, shared-root behavior, repeated-key warnings, cache and
  physical totals, and compound-index suggestions without duplicate advice.
- PocketIC exercises 200 repeated lookups, 200 distinct lookups, and 1,000
  distinct requested lookups. The last case executes 256 queries before the
  shared request budget returns typed failures for the remaining 744 while
  preserving one literal-free query shape.
- A deterministic 10,001-unit selective scan proves that 10,000 nonmatches can
  return an empty page with continuation, after which the final unit is
  examined and exhaustion is proven without skipped progress.
- Focused warning-denied core, facade, fixture, and Wasm-canister lint,
  feature-off compilation, formatting, and diff hygiene pass. Repository-wide
  suites remain push-owned.

### 📊 Audit

- Against `v0.221.8`, decode-once controls remain neutral: 200 repeated points
  stay at 54,479,158 instructions, 200 distinct-literal points stay at
  88,995,601, and 200 ordered empty scans fall from 50,874,535 to 50,872,735
  (`-0.0035%`). A populated primary range reduces required-row payload reads
  from two to one and candidate-enumeration payload reads from one to zero.
- On the diagnostic endpoint, enabling collection for 200 repeated point
  lookups changes local canister instructions from 52,583,327 to 54,998,945
  (`+4.5939%`). The disabled 200-distinct control uses 84,992,749 instructions;
  the bounded 1,000-request run uses 326,986,144 and stops after 256 executions.
- With diagnostics disabled, raw non-gzipped fixture Wasm is 2,479,797 bytes,
  1,131 bytes below `v0.221.8`. The maintained diagnostic-enabled fixture is
  2,523,035 bytes, `+42,107` bytes (`+1.6972%`) over `v0.221.8`; gzip is
  secondary at 989,201 bytes. The diagnostic audit endpoint expands that
  fixture's Candid from 612 to 4,670 bytes; applications expose no new endpoint
  automatically.
- The combined release spans approximately 28 implementation, test, contract,
  and documentation files at `+2,018/-98` lines before these release notes.
  Feature-off production complexity stays close to neutral. Opting in adds one
  bounded request accumulator and observation hooks without changing plans or
  successful query semantics.

## 0.221.8

This release makes large exhaustive validation complete, bounded, and safe to
resume across calls. Each page carries proof of the exact source revisions it
read, while durable jobs retain progress and replay receipts outside those
protected source stores.

### 📝 Summary

- Typed and dynamic exhaustive pages return
  `{ rows, continuation, work, proof }`. The proof binds the database,
  accepted schema, participating physical stores, row data, and access/index
  readiness.
- Every resumed page compares the complete proof before and after execution.
  A source change returns a typed invalidation instead of mixing revisions or
  silently treating a capped read as complete.
- Durable application jobs retain bounded accumulator state, continuation,
  sequence, idempotency key, and one replayable receipt. Repeating a request
  after a lost response returns the stored receipt without applying that page
  twice.
- Progress writes live outside the protected source revision domain, so saving
  a job cannot invalidate the proof that job is validating.

### ➕ Added

- `ReadSetRevisionProof` is a canonical, capped source authority containing
  the database incarnation, accepted runtime-root identity, and sorted
  revisions for at most 64 participating physical stores.
- `Query::execute_exhaustive_page` and the dynamic session equivalents add the
  revision-strict counterpart to revision-tolerant live pagination. Heap
  stores support one-call exhaustive reads; durable cross-call jobs require
  journaled sources.
- `start_resumable_job`, `resumable_job_state`,
  `compare_proof_and_advance`, and `acknowledge_resumable_job` provide one
  bounded progress protocol. Completed or invalidated jobs can be
  sequence-checked and removed to release their progress slot.
- Job state is capped at 256 KiB, receipts at 64 KiB, continuations at 16 KiB,
  idempotency keys at 256 bytes, and the shared progress allocation at 64
  records of at most 512 KiB each.

### 🔧 Changed

- Physical stores now track row-data revisions separately from access-state
  revisions. Real index `Building` and `Ready` transitions advance access
  authority without pretending source rows changed.
- Exhaustive cursor authentication includes the canonical proof. Missing,
  stale, malformed, oversized, differently ordered, or cross-database proofs
  fail before resumed results are admitted.
- Proof capture and every progress-control operation charge the same
  request-wide execution counter as ordinary database calls. Opening another
  session cannot reset the aggregate allowance.
- The excluded progress allocation admits the new bounded version-1
  `ICYRJOB1` record family alongside integrity jobs. Existing source rows,
  accepted schemas, journals, and live-page behavior are unchanged.

### 🧭 Migration Notes

- Use live pages for ordinary UI pagination that may tolerate concurrent
  changes. Use exhaustive pages when the caller must prove that one complete
  validation observed one stable source revision.
- Persist the proof and continuation together. If resume reports source
  invalidation, discard the old accumulator and restart from a newly captured
  proof; do not retry the stale continuation indefinitely.
- Applications still own authorization, accumulator meaning, and restart
  policy. IcyDB supplies revision comparison, bounded durable progress,
  sequence enforcement, and lost-response replay.
- The new access/progress control records are additive and created as needed.
  Existing databases require no source-row, accepted-schema, or journal-data
  migration.

### 🧪 Testing

- Focused coverage proves canonical proof bounds, required-proof resume,
  complete traversal, same-store row drift, unrelated-store stability,
  shared-store deduplication, index-access drift, and durable revision reopen.
- Durable-job coverage exercises progress self-exclusion, proof changes before
  and after a page, stale sequence rejection, lost-response replay, duplicate
  accumulator prevention, completion, invalidation, terminal cleanup, and
  heap-store rejection.
- Warning-denied core/facade lint, public facade compilation with and without
  SQL, read-admission, durability, mutation-atomicity and layer-authority
  invariants, focused PocketIC controls, formatting, and diff hygiene pass.
  Repository-wide suites remain push-owned.

### 📊 Audit

- Against `v0.221.7`, 200 repeated identical live point pages change from
  54,342,357 to 54,479,158 instructions (`+0.2517%`), distinct-literal points
  from 88,858,800 to 88,995,601 (`+0.1540%`), and ordered empty scans from
  50,739,334 to 50,874,535 (`+0.2665%`). New proof and progress work is entered
  only through the explicit exhaustive and job surfaces.
- Representative raw non-gzipped `one_entity_dynamic_query` Wasm changes from
  2,476,766 to 2,480,928 bytes (`+4,162`, `+0.1680%`). Deterministic gzip
  changes from 972,066 to 971,997 bytes (`-69`, secondary context). The
  612-byte fixture Candid remains byte-identical; the additive exhaustive DTOs
  have separate frozen-shape coverage.
- The patch spans 38 implementation, test, contract, and documentation files
  at approximately `+3,193/-210` lines before these release notes. Engine
  complexity increases because revision authority and replay-safe progress are
  explicit state machines; application validation becomes simpler because it
  no longer rebuilds those rules itself.

## 0.221.7

This release makes incomplete scalar reads impossible to mistake for complete
results. Typed and dynamic enumeration now returns a bounded live page with an
authenticated continuation and an explicit work receipt.

### 📝 Summary

- Scalar enumeration returns `{ rows, continuation, work }`. A non-null
  continuation means traversal has not yet been proven exhausted; it does not
  promise that another matching row exists.
- Cursor authentication binds the complete query, ordering, accepted-schema
  authority, database incarnation, total window, page envelope, and resume
  boundary. Modified, stale, oversized, or wrong-database cursors fail closed.
- The database-control layout now persists one nonzero cursor key generated by
  the same process-local randomness authority used for ULIDs. Publication,
  clear, recovery, and reopen preserve that key.
- Canister builds use `ic-testkit` 0.7.6, report long quiet build phases without
  forwarding noisy Cargo output, and treat scheduled target maintenance as
  best effort without discarding an otherwise valid Wasm result.
- Release workspace cleanup runs only after the release commit and tags push
  successfully. Failed validation or publication retains build artifacts for
  diagnosis and retry.

### 🔧 Changed

- Typed `Query::execute_live_page` and dynamic
  `DbSession::execute_live_page` replace scalar rows-only enumeration. Public
  pages return at most 100 rows and trusted pages at most 1,024 rows.
- A query `LIMIT` is one total traversal window across every page rather than
  a fresh per-page allowance. Changing the window on resume is rejected.
- Deterministic resume ordering covers mixed ascending and descending terms,
  canonical null comparison, duplicate secondary values, explicit primary-key
  directions, and hidden order fields that are not projected to the caller.
- Planner-proven exact primary-key sets that fit in one page retain their
  direct path and finish without constructing continuation state. Finite key
  callers should still prefer `get` or `get_many`.
- Scalar tokens are bounded to 8 KiB, 32 order terms, and 4 KiB of encoded
  logical-boundary state. Their MAC is checked before semantic payload decode
  and compared in constant time. Tokens are authenticated, not encrypted, and
  are not a field-level secrecy boundary.
- Read-admission and durability guards now protect the live-page entry points,
  current scalar-token wire, and current database-control layout instead of
  preserving removed scalar API names or retired formats.

### ⚠️ Breaking

- Typed `execute_rows`, `execute_public_dynamic_query`, and
  `execute_trusted_dynamic_query` are removed without aliases. Callers must
  consume the page result and return or persist its continuation.
- The commit control slot hard-cuts from version 1 to the sole current version
  2 layout containing the cursor key. Version-1 control state, zero authority,
  malformed state, and unknown versions fail closed without reconstruction.
- Scalar cursor bytes hard-cut to the sole current authenticated version-2
  form. Older or unsigned scalar tokens cannot resume.

### 🧭 Migration Notes

- Replace rows-only typed enumeration with an explicit page loop or return the
  continuation to the client:

  ```rust,ignore
  let page = db!()?
      .query::<Token>()?
      .order_by(asc("id"))
      .execute_live_page(previous_continuation.as_deref())?;

  return Ok((page.rows, page.continuation));
  ```

- Dynamic callers use `DbSession::execute_live_page(&query, continuation)`;
  trusted maintenance callers use `execute_trusted_live_page` and still own
  authorization.
- Development canisters containing the retired version-1 commit control slot
  must be recreated before using this release. Do not retain or translate old
  cursor tokens.
- Exhaustive validation is not represented by the live-page contract.
  Revision-bound exhaustive pages and atomic job advancement remain assigned
  to the next 0.221 landing.

### 🧪 Testing

- Focused coverage exercises mixed directions and nulls, duplicate and hidden
  order values, total limits spanning pages, modified cursors and wrong keys,
  token/tuple/term bounds, current control-state preservation and corruption,
  parameterized-plan reuse, and the frozen page Candid shape.
- Warning-denied core/facade lint, focused facade and control-state tests,
  read-admission and durability invariants, matched Wasm construction, and the
  maintained instruction benchmark pass. Repository-wide suites remain
  push-owned.
- Build-cache coverage freezes quiet-phase heartbeats, suppressed Cargo output,
  and best-effort shared-target maintenance. Release invariants require cleanup
  to occur only after a successful tag push.

### 📊 Audit

- Against `v0.221.6`, 200 repeated identical point pages change from
  50,634,074 to 54,342,357 instructions (`+7.3237%`), distinct-literal points
  from 84,857,468 to 88,858,800 (`+4.7154%`), and ordered empty scans from
  45,017,949 to 50,739,334 (`+12.7091%`). This is the bounded authenticated
  general-page cost; exact finite reads retain the cheaper key APIs.
- Representative raw non-gzipped `one_entity_dynamic_query` Wasm changes from
  2,459,632 to 2,476,766 bytes (`+17,134`, `+0.6966%`). Deterministic gzip
  changes from 962,337 to 972,066 bytes (`+9,729`, secondary context). The
  612-byte Candid remains byte-identical with SHA-256
  `6b0b35b9498df3dd69731bf3883160ab6a61258546274d8c04bbda1c17e4c12a`.
- The patch spans approximately 66 implementation, test, fixture, invariant,
  and documentation files at `+2,200/-370` lines before these release notes.
  Engine complexity increases because authenticated resumable state is now
  explicit; application pagination becomes simpler and safer because
  incompleteness is a structural result.

## 0.221.6

This release completes the request-budget developer experience introduced in
0.221.4. Manual sync and async entry points can keep ordinary zero-argument
`db!()` calls while IcyDB preserves one cumulative database allowance for the
whole invocation.

### 📝 Summary

- `#[icydb::request_execution]` establishes the normal request boundary for
  manual IC-CDK, Canic, lifecycle, timer, and background-task entry functions.
  `#[icydb::test]` gives synchronous unit tests the same boundary.
- Async entry points retain one request root across `.await`, but install it
  only while their future is actively being polled. Suspended requests cannot
  leak their scope into another interleaved message.
- Nested wrappers reuse the active counters. Unwrapped access and conflicting
  explicit roots fail with dedicated diagnostics instead of silently creating
  or replacing a budget.
- Query plans, physical read routes, successful results, Candid, accepted
  schema, rows, indexes, journals, and persisted formats are unchanged.

### ➕ Added

- `with_request_execution_async` owns one request root for the lifetime of an
  async invocation. It restores the previous ambient state after every
  `Pending`, successful completion, cancellation, and panic.
- The framework-neutral request attribute is a thin wrapper over the same sync
  and async helpers used by manual integration. Put it outside the endpoint
  framework attribute:

  ```rust,ignore
  #[icydb::request_execution]
  #[canic_query(requires(auth::authenticated()))]
  async fn refresh() -> Result<Receipt, Error> {
      authorize().await?;
      refresh_with(db!()?).await
  }
  ```

- E275 `RequestExecutionScopeRequired` identifies a `db!()` call made without
  an approved request boundary. E276 `RequestExecutionRootMismatch` identifies
  an explicit root that conflicts with the root already active for the
  invocation. CLI rendering explains how to correct both cases.

### 🔧 Changed

- The async request future is intentionally poll-local and non-`Send`. This
  prevents the thread-local ambient handle from migrating between executors;
  the root's counters remain owned by the future across suspension.
- A nested wrapper created before its first poll lazily adopts the active root.
  A future that has already started under one root cannot later move beneath a
  different request root.
- Generated IcyDB endpoints continue to establish their request boundary
  automatically. Manual endpoints no longer need an explicit root merely
  because they contain `.await`.
- `db!(&root)` remains the low-level integration form for frameworks that
  deliberately own and pass a root. It reuses the existing counters and is
  not an authorization capability.

### ⚠️ Breaking

- Missing request scope now reports E275 instead of the former generic runtime
  internal error. Code that exhaustively matches public runtime-boundary codes
  must handle E275 and E276.
- An explicit root can no longer replace a different active root. Integrations
  that created one root per database call must move root ownership to the
  endpoint boundary and reuse it for the full invocation.

### 🧭 Migration Notes

- Generated IcyDB endpoints require no source change.
- Manual IC-CDK or Canic endpoints should add
  `#[icydb::request_execution]` outside their framework attribute and keep
  using `db!()` in nested helpers. The same pattern applies to lifecycle hooks
  and timer callbacks that access IcyDB.
- Keep `with_request_execution_root` and `db!(&root)` only in low-level
  integration code that intentionally passes scope ownership itself.
- Replace ordinary synchronous `#[test]` with `#[icydb::test]` when the test
  accesses generated database helpers.

### 🧪 Testing

- Focused coverage proves shared root identity before and after `.await`,
  preconstructed nested-wrapper reuse, isolation between manually interleaved
  futures, and cleanup after cancellation, completion, and panic.
- Separate coverage rejects cross-request future migration and conflicting
  explicit roots, verifies the typed E275/E276 details and CLI text, checks
  generated-session enforcement, and exercises IC-CDK plus direct attribute
  composition.
- Warning-denied changed-package linting, focused core/facade/model/diagnostic
  tests, read-admission, mutation-atomicity, post-link invariants, formatting,
  and diff hygiene pass. Repository-wide suites remain push-owned.

### 📊 Audit

- No query execution route changed, so this release does not claim an
  instruction improvement. The added proc-macro work is host-side; the runtime
  artifact retains only reachable request-boundary code and diagnostics.
- Representative raw non-gzipped `one_entity_dynamic_query` Wasm changes from
  2,457,082 to 2,459,632 bytes (`+2,550`, `+0.1038%`). Deterministic gzip
  changes from 962,953 to 962,337 bytes (`-616`, secondary context), and the
  612-byte Candid remains byte-identical with SHA-256
  `6b0b35b9498df3dd69731bf3883160ab6a61258546274d8c04bbda1c17e4c12a`.
- The release delta spans 24 code, test, diagnostic, and documentation files
  at approximately `+645/-131` lines before these release notes. Runtime
  integration is more explicit because poll-local ownership and misuse
  diagnostics are enforced; ordinary application code is simpler because
  sync and async helpers keep using zero-argument `db!()`.

## 0.221.5

This release stages the bounded progress model needed by the upcoming public
cursor API. It also makes accepted entity names friendlier in interactive SQL
and removes repeated host-side compilation, artifact, and disk-retention work
from maintained CI, release, and publish flows.

### 📝 Summary

- One internal scalar-page coordinator now distinguishes successful bounded
  progress from absolute hard-budget failure. Selective traversal may return
  an empty page with a continuation after making physical progress.
- Accepted SQL/display entity names resolve through one allocation-free ASCII
  case-insensitive runtime-root index. `DESCRIBE customer`, schema-qualified
  introspection, and lowercase row queries resolve an entity authored as
  `Customer` while preserving its canonical spelling.
- CI and release flows reuse compiler and already-verified post-link artifacts,
  positive compile fixtures avoid unnecessary trybuild isolation, and exact
  release receipts prevent redundant package verification after the same
  tagged release gate.
- Local version-bump gates clean repository-owned Cargo output, release
  temporary files, SQLite comparison state, and stale PocketIC port markers on
  both success and failure without sweeping shared `/tmp`.
- Public page and cursor DTOs remain unchanged. Candid, accepted schemas, rows,
  indexes, journals, and persisted formats are unchanged.

### ➕ Added

- `PageWorkEnvelope` applies finite per-page limits to the 17 physically
  resumable resources within the enclosing 21-resource hard budget. Query
  execution, planning, compilation, and the instruction watermark remain
  owned by the hard request/execution scope.
- Successful internal pages carry rows, an exact work receipt, and progress
  containing the last emitted logical boundary, last consumed physical
  anchor, optional unconsumed lookahead match, consumed offset, total emitted
  rows, page-envelope identity, and immutable query window.
- E274 `PageUnitTooLarge` reports the resource, envelope limit, and attempted
  amount when one indivisible inspection or emission cannot fit in an empty
  page. This prevents callers from receiving an unchanged continuation
  forever. E273 hard-budget exhaustion still returns an error without a
  partial page.
- Release tooling records a receipt only when an annotated version tag points
  at the current `HEAD`. Workspace publishing may skip Cargo package rebuilds
  only when that exact tag, commit, and receipt agree; stale and standalone
  publishing retains normal verification, and verification can be forced.

### 🔧 Changed

- Page-envelope exhaustion returns completed rows plus continuation state.
  Residual-only work can therefore return no rows while still advancing the
  physical anchor. A non-null continuation means exhaustion is not yet proven;
  it does not promise that another matching row exists.
- Exact-full pages may inspect a nonmatching tail to prove exhaustion. A
  discovered lookahead match remains unconsumed and is re-read on resume, so
  the physical anchor never skips an unreturned row. Initial offset and total
  query limit are bound once and cannot be reinterpreted per page.
- The accepted runtime root keys editable SQL/display entity names by their
  bounded ASCII-folded `EntityName`. Case-only duplicates fail closed, while
  immutable source-key and persisted entity identity remain exact and
  case-preserving.
- GitHub Actions uses shared compiler caching and isolates concurrency by pull
  request or commit. The release job consumes the canonical Wasm and Candid
  already produced by the required size-report job instead of rebuilding the
  same canister with a second toolchain setup.
- Host canister builds use `ic-testkit` 0.7.2. Exact artifact-cache and shared
  incremental-target maintenance runs at most once per 24 hours; the exact
  artifact cache remains bounded to 1 GiB and 14 days, while the reusable Cargo
  target is bounded to 6 GiB and 14 days.
- Patch, minor, and major version-bump workflows route temporary work through a
  repository-owned directory and run the same bounded cleanup after successful
  completion or any failed formatting, validation, or bump step. The cleanup
  targets only known workspace paths and never recursively removes shared
  system temporary storage.
- Positive facade compile fixtures are ordinary Cargo integration-test targets
  with explicit feature requirements. Trybuild remains responsible for
  compile-fail contracts and the maintained link-time collision case, avoiding
  isolated recompilation of every successful fixture.

### 🧪 Testing

- Coordinator coverage exercises empty progress pages, exact-full pages with
  nonmatching tails, unconsumed lookahead replay, page versus hard exhaustion,
  oversized indivisible units, resume-contract mismatch, one-time offset and
  total-limit handling, and envelope headroom below every hard limit.
- Accepted-runtime coverage executes lowercase and mixed-case direct lookup,
  ordinary SQL selection, and schema-qualified `DESCRIBE`, verifies canonical
  metadata spelling, and confirms immutable source-key lookup remains exact.
  Existing model validation continues to reject case-insensitive duplicate
  entity names within one canister.
- Diagnostic registry, fact-schema, and CLI rendering coverage includes E274.
  Compile coverage remains feature-partitioned after moving positive fixtures
  out of trybuild, and post-link invariants require release packaging to consume
  the verified canonical artifact.

### 📊 Audit

- The page coordinator is not reachable from a current production query
  surface and is removed by production linking. The matched dynamic-query
  artifact changes from 2,457,335 to 2,457,082 raw non-gzipped Wasm bytes
  (`-253`, `-0.0103%`); deterministic gzip changes by `-593` bytes, and the
  612-byte Candid remains byte-identical with SHA-256
  `6b0b35b9498df3dd69731bf3883160ab6a61258546274d8c04bbda1c17e4c12a`.
- Host-only cache, release, publish, and compile-fixture changes do not enter
  canister Wasm. No instruction improvement is claimed until the authenticated
  page route integrates the coordinator.
- The release delta spans approximately 36 implementation, test, tooling, and
  documentation files at roughly `+1,460/-145` lines before these release
  notes. The executor is more complex because resumable progress is now an
  explicit state machine; accepted-name lookup and host delivery become
  simpler by using one canonical index and reusing authoritative artifacts.

## 0.221.4

This release gives every database-using endpoint one aggregate work
allowance. It also removes ambiguous operational defaults from environment
selection, accepted relation inspection, and maintained-canister artifact
builds.

### 📝 Summary

- One endpoint-owned request root now carries database work across sessions,
  nested helpers, failed operations, and retries. Hundreds of individually
  valid queries can no longer obtain a fresh budget for every call.
- The CLI defaults an omitted ICP environment to `local`, accepted-schema
  inspection reports relations from current catalog authority, and host Wasm
  validation uses `ic-testkit` 0.6.0's shared incremental build support.
- Successful database results, Candid, accepted schemas, rows, indexes,
  journals, and persisted formats are unchanged.

### 🔧 Changed

- Generated endpoints create one root and install it for their synchronous
  database call tree. Manual endpoints do the same with
  `with_request_execution`; nested helpers retain the established
  zero-argument `db!()` API.
- Every derived session retains one private monotonic counter set. Dropping a
  session, constructing another session, nesting a helper, retrying work, or
  returning an error does not refund or reset earlier usage.
- The production request profile permits at most 256 query executions, 1,024
  planning operations, and 256 plan compilations, alongside finite aggregate
  limits for the physical resources introduced in `0.221.3`. Exceeding one of
  these limits returns E273 with request-scope resource, limit, and observed
  usage facts.
- Shared-plan cache lookups charge planning work. A reusable parameterized
  template hit does not charge another compilation, while a real miss charges
  compilation before building the plan.
- Trusted admission remains execution policy rather than authorization.
  Application caller authentication and role checks are still owned by the
  endpoint.
- Omitting both `--environment` and `ICP_ENVIRONMENT` now selects `local`
  instead of `demo`. Scripts that intentionally target `demo` must select it
  explicitly. Missing-canister and stale-schema guidance now asks callers to
  verify the selected target before suggesting any destructive refresh.
- `SHOW ENTITIES` and `DESCRIBE` obtain accepted relation edges and target
  identities from the same captured database-wide runtime root used by
  relation constraints. Composite relation edges are no longer inferred from
  field wrappers alone.
- Host integration uses `ic-testkit` 0.6.0 to cache shared incremental Cargo
  Wasm builds separately from the canonical post-link artifact. Whole-fleet
  artifact validation builds each local or production package set together,
  then performs post-link work in bounded batches.

### ⚠️ Breaking

## 0.221.3

This release applies the hard-budget model to maintained physical read routes.
Expensive database work is now counted where it happens instead of only on the
planner-free exact-key reference path.

### 📝 Summary

- Scalar, grouped, aggregate, covering, hybrid, fallback, sorting, cursor,
  diagnostic, SQL, dynamic, public, trusted, and mutation-owned read paths now
  execute with finite physical-work allowances.
- When charged work exceeds an allowance, IcyDB returns the existing typed
  `ExecutionBudgetExceeded` diagnostic (E273). Successful result shapes and
  storage formats are unchanged.
- Host integration moves to `ic-testkit` 0.5.0, retaining the existing fixture
  API while adopting structured pool outcomes, lifecycle diagnostics, and a
  transactional cross-process Wasm artifact cache.

### 🔧 Changed

- Physical key and index visits, row fetches, stored bytes, decoded and
  materialized bytes, predicate/projection work, nested values, sorting,
  grouping and distinct state, cursors, diagnostics, and result rows/bytes now
  use one shared accounting contract.
- Covering reads charge only the index-backed work they perform. Hybrid and
  fallback reads additionally charge fetched payloads. Current primary scans
  charge both backend reads when the existing storage path reads a payload
  twice; a later decode-once patch owns removing that duplicate work.
- Full sorts and grouped top-k heaps precharge their known entry, comparison,
  and temporary-storage work before performing the expensive operation.
- Maintained Wasm loops sample an instruction watermark after bounded charge
  intervals or large work units and retain enough instruction and output
  headroom to construct a typed database failure. Small bounded executions use
  their physical counters without paying a performance-counter call on every
  query.
- Optional diagnostic collection fails soft after its own allowance is used.
  It does not change plan selection or turn an otherwise successful query into
  an error.
- The production budget profile is immutable and borrowed, avoiding a copy of
  all 21 resource limits for every query execution.
- The SQL performance audit uses four independently snapshot-restored fixture
  slots. Tests retain isolated post-install canister state without paying for
  a fresh PocketIC instance and canister installation on every case; fixtures
  whose topology or lifecycle is itself under test remain fresh.
- Host canister builds hash their complete maintained source/configuration,
  Cargo and Rust toolchain identities, relevant build environment, exact
  feature/profile request, and pinned post-link optimizer. A cache miss keeps
  using the shared incremental Cargo target, then atomically publishes the
  compiler-emitted and final deployable Wasm as one verified transaction.
- The cache is bounded to 1 GiB and entries older than 14 days. Different
  packages, features, profiles, toolchains, environments, and optimizer
  recipes cannot share an entry; incomplete or changed builds do not publish.
- This is still a per-execution boundary. It prevents one maintained database
  execution from running without limits, but it does not yet combine hundreds
  of individually small calls into one endpoint-wide allowance. The next
  request-scope patch owns that aggregate protection.
- IcyDB does not claim to bound arbitrary application code, external calls, or
  application response encoding outside the charged database boundary.

### 🧪 Testing

- Existing scalar, grouped, heap-backed, and journaled successful-result

## 0.221.2

This release combines bounded parameterized plan reuse and complete typed
filter-literal rehydration with the first charged hard-budget execution route.

### Hard execution budgets

#### 📝 Summary

- IcyDB now has one reusable hard-budget model for database work. It counts a
  finite set of resources monotonically and returns a typed
  `ExecutionBudgetExceeded` diagnostic instead of relying on a canister trap
  after too much charged work.
- The planner-free typed `get_many` path is the first real execution route to
  use the model. This is the reference integration for the broader executor
  instrumentation planned next.

#### ➕ Added

- The budget vocabulary covers 21 resource families: query executions,
  planning steps and compilations, key/index entries, visited rows, stored
  bytes, predicate/expression and nested-value work, decoded/materialized
  bytes, sorting, grouping/distinct state, cursors, temporary bytes,
  diagnostics, result rows/bytes, and instruction units.
- E273 reports the exhausted resource, its limit, attempted cumulative usage,
  counter scope, execution lane, and a literal-free normalized query-shape
  fingerprint prefix. The CLI turns those numeric facts into stable labels.
- Each budget profile declares instruction and response headroom reserved for
  constructing a typed failure. Actual canister instruction-watermark wiring
  is part of the next physical-route patch, so this release does not overclaim
  endpoint-wide trap prevention.

#### 🔧 Changed

- A junior-level example of the original reference application problem is this loop:

  ~~~rust
  for token_id in token_ids {
      load_provenance(token_id); // one database query
      load_snapshot(token_id);   // another query and a large decode
  }
  ~~~

  With 100 tokens, those two lines alone mean 200 query executions. The real
  reference application loop performed six queries and two shared-snapshot decodes per token,
  so 100 tokens meant about 600 extra queries and 200 large decodes. IcyDB
  cannot make that application loop disappear: reference application should still preload the
  known IDs with one bounded `get_many` call and reuse the returned maps.
- The database-side improvement is that work now has named counters and one
  typed failure contract. For example, `get_many([A, B, A])` charges three
  logical result positions because the caller expects three answers, but only
  two physical key visits because the repeated `A` is deduplicated. Found rows
  additionally charge their stored, decoded, materialized, projection, and
  returned bytes.
- Counters never roll backward. If an attempt fails or arithmetic overflows,
  the attempted usage remains charged. The model intentionally has no refund
  operation, which prevents retries from making already-spent database work
  look free once Patch 6 attaches the counters to a request root.
- The exact-key route retains its more specific item-count, input-byte,
  stored-byte, and result-byte errors when those limits fail first. The generic
  E273 boundary is for the shared hard-resource contract, not a replacement
  for useful route-specific admission errors.
- This patch creates per-execution ownership only. Patch 5 will charge every
  maintained physical route and Patch 6 will make one aggregate request scope
  non-resettable across sessions, nested calls, failures, and retries. A reference application
  endpoint making hundreds of individually small calls is therefore not fully
  stopped by the hard-budget slice in `0.221.2` alone.
- Public successful query results, accepted schema, rows, indexes, journals,
  cursors, Candid, and persisted formats are unchanged.

#### 🧭 Migration Notes

- `RuntimeBoundaryCode` adds `ExecutionBudgetExceeded`, and the diagnostic
  facade adds compact resource, scope, lane, and fact-tag registries.
  Downstream exhaustive matches must handle the new boundary and fact tags.

#### 🧪 Testing

- Focused coverage exercises all 21 counters, both precharge and periodic
  charging, retained failed usage, overflow saturation, failure headroom,
  exact fact schemas, CLI rendering, a real heap-backed exact-key rejection,
  and unchanged heap/journal duplicate and ordering semantics.
- Warning-denied diagnostic-code, all-feature core, and CLI lint pass, as does
  no-default-feature core checking. Repository-wide suites remain user-owned
  push validation.

#### 📊 Audit

- Against the matched pre-budget Patch 3 handoff, a 1,000-distinct-key
  missing-row batch grows from 37,314,077 to 37,488,673 local instructions
  (`+0.4679%`). A batch containing one repeated missing key falls from
  6,497,620 to 6,479,398 (`-0.2804%`). The unchanged dynamic-query controls
  isolate the difference to exact-key accounting.
- Final raw non-gzipped one-entity typed-query Wasm grows from 1,784,867 to
  1,786,868 bytes (`+2,001`, `+0.1121%`). The 64-byte Candid contract is
  byte-identical. Gzip grows by 999 bytes as secondary context.
- The implementation touches 10 code/test files at approximately
  `+1,016/-72` lines before documentation. It is moderately more complex because
  resource ownership is now explicit; later executor routes gain one shared
  charging and exhaustion contract instead of inventing separate limits.

### Parameterized query templates and typed filter values

#### 📝 Summary

- Dynamic and SQL equality, ordered-range, and non-empty `IN` filters now
  share value-independent planning templates when their complete structural
  contracts match. Different literal values no longer force full schema and
  access planning for every execution.
- Accepted-schema filter handling now rehydrates `Blob`, `Date`, `Duration`,
  `Subaccount`, and `Timestamp` literals into their exact runtime types across
  comparisons, membership, collection containment, and relation keys.
- Host SQL integration tests use bounded restorable fixtures, reducing
  repeated PocketIC installation without changing canister behavior.

#### 🔧 Changed

- A query plan is IcyDB's recipe for doing the work: which index to use, which
  filters to apply, what to sort, and which fields to return. Previously, the
  literal value was part of the plan-cache key. These simplified-ID examples
  therefore compiled as three unrelated plans even though they ask IcyDB to do
  the same kind of indexed lookup:

  ~~~sql
  SELECT id, stage FROM Token WHERE id = 'token-a';
  SELECT id, stage FROM Token WHERE id = 'token-b';
  SELECT id, stage FROM Token WHERE id IN ('token-a', 'token-b', 'token-c');
  ~~~

  IcyDB now compiles a reusable exact-set template and supplies the current IDs
  when each query runs. Fluent `DynamicQuery` filters lower to the same
  template, so SQL and Rust callers share this work.
- Range queries work the same way. For example, `score >= 10` and
  `score >= 50` share the `score >= ?` template, while `score < ?` remains a
  different template because it has different behavior.
- A template still records everything that can change how a query works: the
  field and value type, operators and boolean structure, selected columns,
  ordering, limit/window, accepted schema generation, store visibility, and
  chosen indexes. Only the current literal values are left out.
- On every execution, IcyDB validates the current values and creates fresh
  lookup keys or range bounds. It never reuses `token-a`'s stored bound while
  executing the `token-b` query. One replaceable same-value memo keeps the
  already-fast repeated-identical-query case cheap without storing one plan
  for every ID.
- Template admission is limited to 64 scalar/list slots, 1,024 items in one
  list parameter, and 256 KiB of estimated parameter payload. Unsupported or
  oversized shapes continue through the existing literal-specific planner.
- The unified shared plan/template cache uses deterministic FIFO eviction with
  a 1,024-entry ceiling and 4 MiB retained-template allowance. SQL attribution
  now exposes shared-plan insertions, evictions, and rejected oversize
  residents in addition to hits and misses.
- Cursor signatures continue to bind the current normalized predicate, so
  executions sharing a template cannot exchange continuations or retain the
  first execution's literal bounds.
- Blob filter text uses bounded hexadecimal decoding, durations use exact
  millisecond text, and malformed, wrong-width, or oversized string-backed
  atoms fail closed through accepted-schema authority.
- This reduces IcyDB's cost for any same-shaped calls that remain, but it does
  not turn an N+1 workload into a batch. Reference application code should
  still load many known IDs with `get_many` and reuse preloaded provenance or
  snapshot data instead of issuing one database call per token.
- Public query result shapes, Candid, accepted schema, rows, indexes, journals,
  and cursor formats remain unchanged. No removed prepared-session API or
  compatibility route returns.

#### 🧭 Migration Notes

- `SqlQueryCacheAttribution` adds counters for shared-plan insertions,
  evictions, and rejected oversize entries. Downstream exhaustive struct
  construction must initialize the new fields.

#### 🧪 Testing

- Host integration moves to `ic-testkit` 0.3.4. SQL canister tests acquire
  bounded cached fixtures and restore each lease to its post-install baseline,
  keeping test isolation while reducing repeated setup.
- Focused coverage includes equality/range/list-template reuse, wrong-type and
  oversize fallback, dynamic/SQL convergence, stale-bound rejection,
  projection/order separation, cursor binding, deterministic cache eviction,
  weighted resident limits, and typed filter-atom rehydration.

#### 📊 Audit

- Across 1,000 matched PocketIC 15 executions, distinct-literal point queries
  fall from 850,779,546 to 416,400,274 local instructions (`-51.0566%`). The
  repeated-identical point control grows by `+0.3851%`, and the ordered empty
  scan control grows by `+0.2958%`, both within the `+1%` gate.
- Put simply, the old distinct-value benchmark compiled nearly the same plan
  1,000 times. The new path compiles the reusable shape once and binds 1,000
  sets of values. The identical-query control was already cached before this
  patch, which is why it is used to prove that parameter binding did not make
  the existing fast case meaningfully slower.
- Final raw non-gzipped Wasm grows from 2,435,362 to 2,441,943 bytes
  (`+6,581`, `+0.2702%`), within the `+8,192`-byte gate. The 612-byte Candid
  contract remains byte-identical.
- Warning-denied all-feature core and audit-canister lint, no-default-feature
  core checking, focused unit tests, PocketIC measurement, formatting, and
  matched Wasm/Candid reporting pass. Repository-wide suites remain
  user-owned push validation.

## 0.221.0

### 📝 Summary

- Publishes one immutable accepted-schema runtime root for the complete
  database instead of rebuilding schema-derived query state for each call.
- Binds dynamic-query and SQL plan caches to the database incarnation and the
  complete accepted root, preventing reuse across mixed schema generations.
- Removes repeated accepted-schema serialization, hashing, schema metadata
  construction, and row-layout construction from the warm query path.

### 🔧 Changed

- Acceptance and recovery compile every participating entity runtime before
  atomically publishing the new root. Existing operations retain their exact
  captured generation; newly derived contexts observe the replacement root.
- The root identity includes the durable database incarnation and a canonical
  ordered record for every registered store, including stores without an
  accepted root. Reused entity versions or fingerprints therefore cannot
  cross a database replacement or an unrelated accepted-store change.
- Entity runtimes share immutable schema lookup tables, row-decode layouts,
  fingerprints, inspection plans, and executor authority. Query and SQL paths
  borrow those structures instead of deriving private copies.
- Warm root validation compares compact persisted root records before doing
  any cryptographic work. A changed root is compiled and revalidated before
  replacing the published handle.
- SQL DDL invalidates the complete runtime root rather than one entity-local
  cache entry. Accepted schema snapshots remain the only runtime authority;
  no generated-model fallback or compatibility path was added.
- Public APIs, Candid, successful query results, ordering, accepted schema and
  persisted formats remain unchanged.

### 📊 Audit

  cost from 374,226,936 to 243,649,156 local instructions (`-34.8927%`) and
  ordered empty-scan cost from 348,175,956 to 216,398,832 (`-37.8479%`).

- Focused all-feature checks, warning-denied lint, runtime-root tests,
