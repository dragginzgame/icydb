# IcyDB 0.225 — Explicit Startup Readiness And Replicated Recovery Driving

## 0.225.3

This release closes two startup-liveness gaps found by the final implementation
audit. Persisted corruption now becomes a durable terminal failure under its
exact owner, and generated schema validation that needs multiple bounded pages
continues through the lifecycle watchdog instead of leaving ordinary work
permanently gated.

### 🩹 Fixed

- Recovery retains whether a terminal error belongs to database-control state
  or one exact journal store. Heap-only malformed markers and live-schema
  checkpoint corruption can therefore publish a correctly bound failure
  receipt instead of retrying forever.
- The startup driver resumes an exact pending generated-schema application
  through the existing bounded continuation executor. Clean progress reaches
  readiness, retained constraint findings become durable typed failures, and
  aborted applications become replayably terminal.
- Generated actor wiring no longer memoizes a pending schema handoff in
  process-local state; each watchdog tick follows the durable application
  receipt while preserving the single driver and timer route.
- Trusted SQL queries reuse the entity name from their canonical compile parse
  when building the public result, removing a duplicate full-statement parse
  and restoring the frozen warmed `LIMIT 1` instruction ceiling.
- Test-only startup canisters use distinct stable-memory identifiers, removing
  order-dependent collisions in combined feature validation without changing
  production allocations.

### 🔧 Changed

- The maintained atomicity and durability contracts now describe state-only
  ordinary admission, lifecycle-owned replicated recovery, and the existing
  explicit migration-control exception.
- Accepted-index chunk decoding has direct zero and maximum-plus-one count
  coverage, proving rejection occurs before key-vector allocation.

### 🧪 Testing

- Focused no-feature and all-feature core suites cover heap-only corruption,
  exact failure replay, clean multi-page generated activation, a retained
  finding after the first 256-row page, and abort recovery across upgrade.
- Real-canister evidence covers watchdog trap and instruction-exhaustion
  survival, 10,001-row upgrade recovery, and CREATE/DROP INDEX recovery with
  durable rows and physical index entries preserved.
- Warning-denied lint, Wasm compilation, Candid and exported-mode checks,
  repository invariants, formatting, and diff hygiene pass.

### 📊 Audit

- Pending ordinary admission costs 114,578 instructions. Startup observation
  costs 112,372 while fresh, 452,378 while ready, and 61,849 immediately after
  upgrade, all below the frozen ceilings.
- Warm total-only heap and journaled `LIMIT 1` name projections cost 970,189
  and 975,265 instructions respectively, below the unchanged one-million
  ceiling.
- Raw final Wasm is 2,699,878 bytes for dynamic query, 1,887,128 for typed
  query, 3,014,960 for SQL query, and 4,125,495 for SQL lifecycle/performance.
  Every delta from 0.225.2 remains below the 65,536-byte owner ceiling.
- Candid remains byte-identical at 4,670, 64, 57, and 60,348 bytes. The startup
  receipt remains format version 1 with a 960-byte maximum valid encoding in
  its existing 2,048-byte cell.
- The correction adds no public endpoint, method mode, stable allocation,
  persisted format, cursor, executor, timer route, compatibility path, or
  caller-tunable behavior.

## 0.225.2

This release corrects journaled SQL DDL recovery. Accepted index metadata and
its exact physical deletion/insertion domain now cross one durable marker and
recover together, so startup cannot advertise a ready index whose canonical
entries were lost with the predecessor Wasm's volatile overlay.

### 🩹 Fixed

- Accepted DDL index additions and drops serialize their complete preflighted
  physical effects after the leading accepted-schema record in the same
  journal batch.
- Recovery folds 64-key ordered chunks into the canonical index before
  readiness, preserving indexed results and preventing stale dropped keys.
- Chunk decoding is bounded and fallible, binds inserted generations to the
  accepted-after entity fingerprint, and rejects malformed or mixed batches.
- DDL transitions that cannot fit the existing 16-MiB durable marker limit now
  fail before target mutation instead of publishing metadata with volatile
  physical state.

### ⚠️ Breaking

- The current journal vocabulary gains accepted-schema index delete/put tags.
  Downgrading to a predecessor binary while an unconverged 0.225.2 DDL batch
  remains in the tail is unsupported under the pre-1.0 hard-cut policy.

### 🧪 Testing

- A real generated PocketIC canister creates an index, upgrades through typed
  pending admission, recovers it, and proves the original three durable rows
  through the indexed route.
- The same fixture drops the index, upgrades again, recovers the deletion, and
  recreates the same index to prove no stale physical domain survived.
- The complete SQL-canister target passes 88 tests with two explicit release
  probes ignored; focused journal, domain-staging, recovery, Wasm, post-link,
  formatting, and warning-denied lint checks pass.

### 📊 Audit

- Raw final Wasm is 2,678,427 bytes for dynamic query, 1,865,726 for typed
  query, 2,981,931 for SQL query, and 4,120,547 for SQL performance/lifecycle;
  every correction/dependency-refresh delta remains below 65,536 bytes.
- Candid remains byte-identical at 4,670, 64, 57, and 60,348 bytes.
- The deterministic SQL-performance post-link artifact is 4,783,531 compiler
  bytes and 4,173,107 final bytes. Exact schema instruction samples remain
  12,995,958 / 12,541,134 / 12,624,656.

### 🧭 Migration Notes

- No public API or endpoint changes. Applications continue to retry typed E280
  while the lifecycle-owned watchdog folds pending startup work.
- Allow 0.225.2 to reach `Ready` after DDL before attempting a downgrade; no
  compatibility decoder or alternate recovery path is provided.

## 0.225.1

This release activates the startup coordinator introduced by 0.225.0. Generated
canisters now drive recovery from lifecycle-owned replicated callbacks, reject
ordinary database work with one typed pending result while recovery is active,
and give applications an explicit engine-first lifecycle composition contract.
The completed line has populated upgrade evidence and no second recovery
executor, timer policy, persistence log, cursor, or compatibility route.

### ➕ Added

- `icydb::start!` accepts one composed declaration for typed application
  install and post-upgrade callbacks. The generated wrapper registers IcyDB's
  watchdog first, then runs the application hook in its own request-execution
  scope.
- Application guidance defines polling `startup_state()`, restoring schedulers
  and caches exactly once after `Ready`, stopping blind retries on typed
  `StartupFailure`, and sequencing controller-driven schema migration.
- Populated real-canister evidence retains 10,001 target rows, 17 unrelated
  rows, exact canonical samples, ten accepted entity descriptions, accepted
  indexes, and both durable application phases across same-schema and
  mid-recovery upgrades.

### 🔧 Changed

- Generated `init` and `post_upgrade` lifecycle wiring now registers the fixed
  one-second serial watchdog. Ordinary typed, dynamic, SQL, integrity,
  diagnostics, and catalog entrypoints observe readiness without driving a
  recovery page themselves.
- While startup recovery is active, ordinary database construction fails with
  raw code 280,
  `RUNTIME_BOUNDARY_DATABASE_STARTUP_RECOVERY_PENDING`. Only the bounded state
  observer, private replicated driver, and existing authorized migration lane
  bypass ordinary admission.
- Normally returned post-`Ready` commit failures that leave actionable durable
  recovery controls atomically ensure a future watchdog wake-up. Trap and
  instruction-limit exits retain IC rollback semantics.
- Generated actor code no longer owns independent IC lifecycle attributes;
  the public start macro is the single export owner for both zero-hook and
  application-hook canisters.

### 🩹 Fixed

- Recovery observation is state-only after activation, preventing ordinary or
  diagnostic calls from decoding retained journal pages or mutating startup
  progress.
- Exceptional commit-window, schema-publication, and migration exits now
  preserve the post-`Ready` liveness invariant without adding a second WAL or
  recovery route.
- Warning-denied generated startup builds use the direct `RefCell::take`
  method, and the synchronous IC-update source guard no longer reports a
  generated callback declaration as an asynchronous production path.
- Prefix-family performance evidence reuses exact covering-cardinality
  authority, restoring the inherited instruction ceiling without weakening
  the fixture or changing query semantics.
- Generated native libtests explicitly drive fresh thread-local startup through
  the maintained coordinator, preserving production readiness admission while
  restoring the test-only initialization contract.
- A terminal generated submission remains reconciled after compatible
  catalog-native SQL DDL advances the accepted head. Database incarnation and
  the content-derived fragment-and-migration submission key remain exact;
  missing, changed, pending, and aborted submissions still fail readiness.
- Warm heap and journaled `LIMIT 1` evidence now primes each exact SQL cache
  identity through the existing update warmup before enforcing the unchanged
  one-million-instruction ceiling.

### ⚠️ Breaking

- Installation and upgrade readiness is now asynchronous when bounded startup
  work remains. Callers must treat code 280 as retryable and must not assume
  the first ordinary database call will perform recovery.
- Applications that need lifecycle hooks must use the composed `icydb::start!`
  form. Handwritten IC-CDK lifecycle exports alongside generated startup
  wiring are removed rather than retained through aliases or dual dispatch.
- This is a source and timing hard cut only. Persisted journal, recovery
  cursor, startup receipt, public Candid, and generated endpoint method modes
  do not change.

### 🧪 Testing

- Empty-canister PocketIC evidence proves engine-first registration,
  application deferral, exactly-once restoration after readiness, typed-failure
  retention, and independent watchdog continuity.
- The populated fixture reaches readiness through eleven bounded observations
  and survives an upgrade after the first incomplete page. Both application
  phases, accepted schema/index authority, canonical first/last/unrelated rows,
  and unrelated-row counts remain exact.
- Dedicated real-canister timer evidence reproduces explicit trap recovery,
  40-billion-instruction exhaustion, upgrade re-registration, rejected
  external executor ingress, independent same-time application delivery, and
  the pinned 250-message overdue dispatch burst.
- Canonical compiler-to-post-link upgrade evidence remains deterministic and
  retains rows and readiness with exact schema work below the frozen ceilings.
- The complete SQL-canister target passes after accepted DDL publication, and
  all 24 SQL-performance audit tests pass with exact warm samples between
  868,772 and 997,807 instructions.

### 📊 Audit

- Patch-closeout production artifacts are byte-identical to the preceding
  owner slice: raw final Wasm is 2,672,879 bytes for dynamic query, 1,860,287
  for typed query, 2,976,590 for SQL query, and 4,108,124 for the SQL
  performance/lifecycle subject.
- Candid sizes and hashes remain unchanged at 4,670, 64, 57, and 60,348 bytes.
  Every subject exports exactly one `canister_init` and one
  `canister_post_upgrade`, with no automatic readiness or recovery-driver
  endpoint.
- The startup receipt remains bounded to a 2,048-byte cell with a 960-byte
  maximum valid encoding and at most one 65,536-byte virtual-memory page.
- The complete line closes with one startup observer, one coordinator, one
  existing recovery engine, one lifecycle-owned watchdog, and application-owned
  restoration policy. Continuous retained-journal convergence remains 0.227
  work.

### 🧭 Migration Notes

- Keep the `startup_memory_id` allocation introduced by 0.225.0 unchanged.
- Replace handwritten application `init` or `post_upgrade` exports with the
  composed `icydb::start!` declaration and move restoration behind an explicit
  `startup_state()` readiness check.
- Retry ordinary calls that return code 280 after the watchdog has had time to
  advance; surface typed terminal failures instead of matching generic conflict
  text or guessing a fixed startup delay.
- No Candid client, persisted data, journal, cursor, or stable-memory migration
  is required.

## 0.225.0

This release establishes bounded startup observation and durable terminal
failure authority before lifecycle activation. It also adds the complete
recovery coordinator and serial watchdog in a deliberately dormant form, so
ordinary database admission and generated lifecycle behavior remain unchanged
until the next planned 0.225 hard-cut patch.

### ➕ Added

- Generated canisters expose a root-level, non-endpoint `startup_state()` Rust
  control that returns the closed `Ready` or `Recovering` state, or a typed
  terminal `StartupFailure`. Observation reads only fixed deployment-bounded
  controls and performs no recovery, scanning, scheduling, or stable writes.
- One current-only startup receipt format durably retains a binding-checked
  database-control, journal-recovery, or schema-reconciliation failure. Its
  encoding is bounded to 2,048 bytes, uses at most one 65,536-byte virtual
  memory page, and rejects corrupt, future, oversized, noncanonical, and
  impossible states with typed failures.
- One coordinator now composes pure observation, at most one page from the
  existing bounded recovery engine, and the existing generated-schema
  reconciliation boundary. It introduces no second executor, journal format,
  cursor, WAL, or generated-model fallback.
- Generated wiring includes one dormant fixed one-second serial watchdog with
  idempotent registration, re-entry protection, and a same-IC-time cadence
  guard. Terminal completion retires the logical timer immediately and clears
  it through a zero-delay cleanup after the serial callback returns.
- Runtime diagnostic code 280,
  `RUNTIME_BOUNDARY_DATABASE_STARTUP_RECOVERY_PENDING`, is reserved for the
  later ordinary-admission cut. It is retryable and is not persisted as a
  terminal failure receipt.

### 🔧 Changed

- Every generated canister declaration now requires one distinct
  `startup_memory_id`. Its stable key is derived from the existing memory
  namespace, and generation rejects application-range, reserved-range,
  stable-key, or allocation collisions.
- Terminal failure visibility follows one deterministic priority: directly
  readable corruption or an exactly binding-matched receipt wins over pending
  recovery state. Stale receipts are ignored, retryable failures are never
  published, exact replay performs no write, and authoritative success clears
  obsolete failure state.
- The watchdog reuses the existing recovery and schema engines and remains
  unregistered by production `init` and `post_upgrade`. The predecessor
  one-shot ordinary-admission path remains authoritative in this patch.

### ⚠️ Breaking

- Generated canister declarations must assign a non-colliding
  `startup_memory_id`; there is no inferred default, alias, compatibility
  allocation, or old-format decoder in this pre-1.0 hard cut.
- Rust consumers with exhaustive diagnostic-code matches must handle the new
  raw code 280 variant. Maintained public Candid bytes, exported methods, and
  method modes are unchanged, and no automatic startup endpoint is added.

### 🧪 Testing

- Focused native evidence covers bounded and fallible receipt decoding, stale
  and exact binding behavior, failure priority, zero-write observation,
  retryable non-publication, authoritative clearing, and 129 retained journal
  batches converging over multiple durable recovery pages without row loss.
- Real PocketIC evidence covers explicit watchdog registration, duplicate and
  external-call rejection, fresh-install and post-upgrade convergence, timer
  retirement, the pinned 250-call dispatch cap, and one driver attempt during
  a 300-second same-time callback burst.
- The pinned serial-timer probe demonstrates recovery after both a trapping
  callback and a 40-billion-instruction exhaustion while an independent
  application timer continues to run.
- Pure startup observation measured 4,520,968 instructions while fresh,
  453,734 while ready, and 10,991,045 after upgrade, all below the frozen
  25-million-instruction ceiling. Generated-schema creation and exact-match
  reconciliation remain below their 110-million and 20-million ceilings.

### 📊 Audit

- Relative to the preceding startup-observation slice, dormant coordinator
  reachability adds zero raw final-Wasm bytes across all four frozen subjects.
  Production Candid bytes and method modes remain byte-identical; deterministic
  gzip changes only for secondary build-context reasons.
- The implementation adds one bounded durable failure-receipt axis and the
  design-authorized volatile watchdog state. It does not add an endpoint,
  request mode, caller-selected policy, compatibility route, second recovery
  engine, or second persistence log.

### 🧭 Migration Notes

- Assign `startup_memory_id` to a stable-memory allocation unused by every
  application and generated IcyDB store, then rebuild the generated canister.
- No Candid client migration is required. This patch does not autonomously
  register the watchdog or gate ordinary operations; that activation remains
  a later planned 0.225 release step.
