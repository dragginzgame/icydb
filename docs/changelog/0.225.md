# IcyDB 0.225 — Explicit Startup Readiness And Replicated Recovery Driving

## 0.225.0

This release establishes bounded startup observation and durable terminal
failure authority before lifecycle activation. It also adds the complete
recovery coordinator and serial watchdog in a deliberately dormant form, so
ordinary database admission and generated lifecycle behavior remain unchanged
until the next planned 0.225 hard-cut patch.

### ➕ Added

- Generated canisters expose a root-level, non-endpoint `startup_state()` Rust
  control that returns the closed `Ready` or `Recovering` state, or a typed
  terminal `StartupFailure`. Observation reads only fixed deployment-bounded
  controls and performs no recovery, scanning, scheduling, or stable writes.
- One current-only startup receipt format durably retains a binding-checked
  database-control, journal-recovery, or schema-reconciliation failure. Its
  encoding is bounded to 2,048 bytes, uses at most one 65,536-byte virtual
  memory page, and rejects corrupt, future, oversized, noncanonical, and
  impossible states with typed failures.
- One coordinator now composes pure observation, at most one page from the
  existing bounded recovery engine, and the existing generated-schema
  reconciliation boundary. It introduces no second executor, journal format,
  cursor, WAL, or generated-model fallback.
- Generated wiring includes one dormant fixed one-second serial watchdog with
  idempotent registration, re-entry protection, and a same-IC-time cadence
  guard. Terminal completion retires the logical timer immediately and clears
  it through a zero-delay cleanup after the serial callback returns.
- Runtime diagnostic code 280,
  `RUNTIME_BOUNDARY_DATABASE_STARTUP_RECOVERY_PENDING`, is reserved for the
  later ordinary-admission cut. It is retryable and is not persisted as a
  terminal failure receipt.

### 🔧 Changed

- Every generated canister declaration now requires one distinct
  `startup_memory_id`. Its stable key is derived from the existing memory
  namespace, and generation rejects application-range, reserved-range,
  stable-key, or allocation collisions.
- Terminal failure visibility follows one deterministic priority: directly
  readable corruption or an exactly binding-matched receipt wins over pending
  recovery state. Stale receipts are ignored, retryable failures are never
  published, exact replay performs no write, and authoritative success clears
  obsolete failure state.
- The watchdog reuses the existing recovery and schema engines and remains
  unregistered by production `init` and `post_upgrade`. The predecessor
  one-shot ordinary-admission path remains authoritative in this patch.

### ⚠️ Breaking

- Generated canister declarations must assign a non-colliding
  `startup_memory_id`; there is no inferred default, alias, compatibility
  allocation, or old-format decoder in this pre-1.0 hard cut.
- Rust consumers with exhaustive diagnostic-code matches must handle the new
  raw code 280 variant. Maintained public Candid bytes, exported methods, and
  method modes are unchanged, and no automatic startup endpoint is added.

### 🧪 Testing

- Focused native evidence covers bounded and fallible receipt decoding, stale
  and exact binding behavior, failure priority, zero-write observation,
  retryable non-publication, authoritative clearing, and 129 retained journal
  batches converging over multiple durable recovery pages without row loss.
- Real PocketIC evidence covers explicit watchdog registration, duplicate and
  external-call rejection, fresh-install and post-upgrade convergence, timer
  retirement, the pinned 250-call dispatch cap, and one driver attempt during
  a 300-second same-time callback burst.
- The pinned serial-timer probe demonstrates recovery after both a trapping
  callback and a 40-billion-instruction exhaustion while an independent
  application timer continues to run.
- Pure startup observation measured 4,520,968 instructions while fresh,
  453,734 while ready, and 10,991,045 after upgrade, all below the frozen
  25-million-instruction ceiling. Generated-schema creation and exact-match
  reconciliation remain below their 110-million and 20-million ceilings.

### 📊 Audit

- Relative to the preceding startup-observation slice, dormant coordinator
  reachability adds zero raw final-Wasm bytes across all four frozen subjects.
  Production Candid bytes and method modes remain byte-identical; deterministic
  gzip changes only for secondary build-context reasons.
- The implementation adds one bounded durable failure-receipt axis and the
  design-authorized volatile watchdog state. It does not add an endpoint,
  request mode, caller-selected policy, compatibility route, second recovery
  engine, or second persistence log.

### 🧭 Migration Notes

- Assign `startup_memory_id` to a stable-memory allocation unused by every
  application and generated IcyDB store, then rebuild the generated canister.
- No Candid client migration is required. This patch does not autonomously
  register the watchdog or gate ordinary operations; that activation remains
  a later planned 0.225 release step.
