# 0.235 Bounded Same-Store Multi-Entity Mutations

## 0.235.0 - 2026-08-20

### ➕ Added

- `execute_trusted_structural_mutation_batch` now admits up to 64 distinct
  accepted entities from one captured runtime root and one registered store.
  It returns one single-row `DynamicMutationResult` per request in input order.
- Runtime diagnostics distinguish the 65th distinct entity from a cross-store
  item using bounded counts, ordinals, and entity tags only.
- Generated authored scalar primary keys and direct scalar relations now keep
  their entity identity as `Id<E>` until the generated adapter lowers the
  declared raw key. Optional/many direct relations retain null/list intent,
  while composite relation components and ordinary key fields stay primitive.
- `trusted_typed_write_batch` resolves heterogeneous generated inputs and
  returns sealed entity-typed handles for ordered dynamic-result or generated-
  row lookup over the existing canonical batch.

### 🔧 Changed

- The existing constraint scheduler now validates each final row under its own
  accepted entity context while retaining one entity-qualified target set and
  complete final overlay for uniqueness and referential integrity.
- Normal commit preflight now caches exact contexts by entity path and schema
  fingerprint, matching recovery rather than applying the first row's context
  to the whole batch. Delete protection runs once per affected target entity.
- Each Identity owner keeps its own tentative statement cursor and exact range;
  all row changes, range advances, journal records, entity revisions, and
  progress replacement remain under the existing marker-atomic commit flow.
- Index and reverse-index deltas remain attributed to their source entities.
  The marker-level commit observation records only bounded entity count and
  storage class, avoiding first-entity misattribution.
- The typed batch now accepts exact current bindings from one captured accepted
  root and store, then delegates once to the same structural executor. Stale
  and cross-store bindings fail before mutation execution.

### ⚠️ Breaking

- The general Rust structural-batch return hard-cuts from one homogeneous
  `DynamicMutationResult` to `Vec<DynamicMutationResult>`. No compatibility
  wrapper or same-entity-only alternate route is retained before 1.0.
- The obsolete `MutationBatchEntityMismatch` diagnostic is replaced by
  `MutationBatchStoreMismatch`; `MutationBatchTooManyEntities` is added for
  the independent 64-entity policy.
- Generated Rust write inputs for an authored scalar primary key or direct
  scalar relation hard-cut from the raw primitive to `Id<E>`. Raw row storage,
  output, and Candid key encoding do not change; schema-generated insert keys
  remain omitted and non-authorable.

### 📚 Documentation

- Transaction, atomicity, write-admission, relation, Identity, SQL, durability,
  and public-facade guidance now describe one-root/one-store admission, the
  64-entity limit, one operation timestamp, entity-qualified final-overlay
  semantics, ordered per-request results, and multiple marker-bound Identity
  owners.
- The public facade guide includes a maintained no-SQL User/membership/Robot
  example with fallible `Id::<User>::generate().map_err(Error::from)`, automatic
  binding resolution, and handle-selected results.

### 🧪 Testing

- Focused native regressions cover the exact 64/65 boundary, one timestamp,
  equal primitive keys in different entities, mixed inserts/updates/replaces/
  deletes, late-failure atomicity, unique release/swap, cross-entity relation
  creation and deletion, and cross-store rejection without a first-item effect.
- Journaled tests interrupt after marker persistence, journal publication, a
  row prefix, all rows, and state materialization. Recovery restores all three
  entities, ordinary indexes, one cross-entity reverse relation, ordered
  journal paths, all Identity ranges, and all exact entity revisions.
- Generated and compile-fail fixtures cover ordinary/generated and non-ULID
  scalar keys, direct relation cardinalities, raw non-relation ULIDs, composite
  relation components, byte-identical Candid keys, and rejection of raw or
  wrong-entity identity substitutions.
- A real Toko-shaped PocketIC flow proves User/membership/Robot atomicity,
  retained membership indexes, non-authorable generated Robot IDs, sealed
  handle ownership, and no staged User or Robot after a late conflict.

### 📊 Audit

- The final line retains one structural mutation state machine, one commit marker,
  current version-1 marker/journal formats, and the existing global operation,
  staged-byte, result-byte, marker-byte, and commit-work policies. It adds no
  transaction state, rollback, continuation, cross-store write route, caller-
  selected budget, stable allocation, Candid method, or generated-model
  reconstruction.
- The retained three-entity marker is exactly 770 bytes with one 740-byte
  journal batch. The stable-memory extent remains exactly 511,770,624 bytes
  before and after the PocketIC probe; no stable allocation or format is added.
- The Toko-shaped typed batch measures 18,146,812 instructions versus
  18,786,254 for three commits, a 3.4% reduction. The exact 64-distinct-entity
  boundary is 59,134,225 instructions with more than 99.85% headroom below 40
  billion; the independent 4,095-row work boundary is 1,564,725,324
  instructions.
- Final representative artifacts are 2,418,071 compiler Wasm bytes, 2,117,677
  raw deployable bytes, and 811,539 deterministic gzip bytes. Against
  `v0.234.0`, raw Wasm is +93 bytes (0.0044%) and compiler Wasm is -62 bytes;
  Candid remains 64 bytes with six unchanged exports.
- The line touches 45 files at approximately +3,040/-424 lines including tests
  and documentation. Runtime complexity rises only for bounded per-entity
  context ownership and the typed facade; it retains one converged executor,
  result vector, marker, journal, and accepted-schema authority with no new
  persisted state or behavior mode.
