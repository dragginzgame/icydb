# IcyDB 0.223 — Durable Resumable Mutation Jobs

## 0.223.2

This release makes durable mutation jobs execute bounded Forward work. IcyDB,
not application code, now retains canonical SQL meaning and continuation state;
each call advances one replayable sequence and never treats Forward exhaustion
as completed validation.

### ➕ Added - Durable Forward Advancement

- `advance_trusted_mutation_job` accepts only a job id, expected sequence, and
  bounded idempotency key. It loads the retained accepted intent and private
  checkpoint, validates database/schema/store authority, and scans at most 256
  authoritative keys while staging at most 64 updates.
- Mutating pages commit target journal work and the next progress record and
  receipt through one marker-owned transition. A lost response can therefore
  replay the exact receipt without repeating planning, scanning, or mutation.
- Already converged pages may return zero updates while still advancing their
  physical checkpoint and sequence. Aggregate request-budget exhaustion before
  commitment leaves target rows and durable progress unchanged.

### 🔧 Changed - Accepted Mutation Ownership

- Retained fixed patches rebuild an existing-row update from canonical field
  payloads only after current accepted authority is revalidated. Generated and
  managed fields stay excluded, full row constraints still run, and every page
  uses the operation timestamp frozen at start.
- Forward exhaustion persists an active Verify phase, null Forward checkpoint,
  and the target revision after the job's own final target commit. It does not
  claim completion; stable Verify/restart behavior remains the next 0.223
  landing patch.
- The obsolete variable-prefix commit sizing route is removed. One admitted
  64-row page either commits with its exact progress successor or fails without
  advancing that successor.

### ⚠️ Breaking And Migration Notes

- The public Rust `prepare_trusted_sql_resumable_update` and
  `resume_trusted_sql_resumable_update` methods and their caller-custodied
  continuation/receipt types are removed without aliases or importers. Start a
  durable job, retain its public sequence, and advance it with an idempotency
  key instead.
- This changes no automatic IcyDB Candid endpoint, exported method mode, row
  format, accepted schema, or mutation-job record format. Applications expose
  and authorize trusted job operations explicitly if required.

### 📊 Audit

- The fixed 512-row canister fixture converges through eight 64-row Forward
  commits at 27.22M-29.05M instructions per call, below the frozen 30M ceiling.
  Exact replay costs 122,882 instructions. A separate converged page scans 256
  keys, updates zero rows, advances once, and rejects a stale request without
  changing progress; all eight mutating pages share one operation timestamp.
- Final maintained raw Wasm is 2,630,963 bytes for the dynamic-query subject
  and 1,818,176 bytes for the typed-query subject, moving -116/+139 bytes from
  0.223.1 and remaining far below the 64 KiB patch review gate. Candid remains
  byte-identical at 4,670/64 bytes.

### 📊 Complexity

The patch removes more code than it adds by deleting the public continuation
protocol and variable-prefix commit flow. The new durable coordinator reuses
the existing canonical intent, bounded scan, request root, accepted mutation
pipeline, marker, and excluded progress store, so implementation complexity is
neutral to slightly lower despite the new atomic Forward behavior.

## 0.223.1

This release gives bounded mutation jobs durable identity, accepted SQL
custody, replayable state, and crash-atomic progress replacement. Starting a
job still changes no target rows: bounded Forward execution and stable Verify
completion remain later 0.223 work.

### ➕ Added - Durable Mutation Custody

- Mutation jobs have their own bounded identity, lifecycle, Forward/Verify
  phase, public state, replay receipt, restart reason, and typed error family.
  Generic revision-strict read jobs remain a separate contract.
- State load and sequence-checked terminal acknowledgement are available
  through core and facade sessions. Exact replay is checked before stale
  sequence or terminal-state rejection, and acknowledgement is idempotent
  after a lost response.
- Trusted fixed-update SQL can be lowered once through accepted runtime
  authority and stored as a canonical sequence-zero intent. The record binds
  database and schema authority, target identity, predicate, fixed patch,
  timestamp, continuation, and the fixed 256-key/64-update policy; it retains
  no raw SQL.
- Repeating a start with equivalent SQL returns the original retained state.
  Changed semantics, authority drift, unsupported shapes, and heap-store
  targets return typed errors before any target-row read or mutation.

### 🔧 Changed - Atomic Progress Recovery

- Commit-marker format version 3 can bind one exact mutation-progress
  replacement to the same recovery authority as its bounded journal work.
  Target rows and their next progress sequence therefore recover together
  after interruption rather than exposing either half independently.
- Replacement is valid only from the complete expected before-record to the
  complete next-sequence record. Replaying the already-applied after-record is
  idempotent; any third state is typed corruption and keeps recovery gating in
  place.
- The progress family reuses the existing excluded stable allocation,
  64-record shared capacity, commit marker, and mechanical commit window. It
  does not add a second write-ahead log, allocator, or transaction engine.

### 🩹 Fixed

- Empty journaled stores retain exact zero-row and index-prefix cardinality
  without startup scans. Empty-domain schema edits no longer report false
  corruption, and indexes populated later retain bounded prefix pruning.
- Artifact validation recognizes reserved IC-CDK self-call exports in raw Wasm
  evidence without treating them as missing public Candid endpoints.

### ⚠️ Breaking And Migration Notes

- Commit-marker payloads hard-cut from version 2 to version 3. There is no
  legacy decoder or dual dispatch; upgrades must begin without a pending
  version-2 marker. Completed stores require no row, schema, index, or mutation
  progress migration.
- The mutation-job APIs are additive Rust surfaces and do not add automatic
  canister endpoints. Maintained public Candid and exported method modes remain
  unchanged.
- Durable Forward and Verify execution are intentionally not part of this
  patch. A successfully started job is active custody, not evidence that any
  target row changed or that the intended set has been exhausted.

### 📊 Audit

- Current mutation records measure 97 bytes initially, 167 bytes for the
  replay fixture, and at most 18,842 bytes for an active record. The maximum
  retained replay receipt is 319 bytes, within the 8 KiB receipt limit.
- A maximum current before/after progress replacement contributes 37,797
  bytes to the existing 16 MiB marker ceiling. Interruption coverage recovers
  exact state after marker persistence, journal publication, target
  publication, and progress replacement.
- Durable start measures 1,051,601 instructions and equivalent replay
  1,161,322 instructions, below the frozen 5 million and 2 million review
  ceilings respectively. The existing 512-row application-custodied control
  remains behaviorally and instructionally stable.
- Final maintained raw Wasm is 2,631,079 bytes for the dynamic-query subject
  and 1,818,037 bytes for the typed-query subject: 0.91% and 1.42% above the
  published 0.223.0 baseline. Both per-patch deltas remain below the frozen
  64 KiB review gate.

### 📊 Complexity

The three landing patches add one bounded mutation lifecycle and one marker
control effect while reusing current schema authority, SQL lowering, progress
storage, request budgets, journal publication, and recovery. Most growth is in
bounded codecs, canonical validation, and interruption/corruption coverage.
The implementation is moderately more explicit, but it avoids a parallel job
framework or transaction path.

## 0.223.0

This release makes unchanged-schema startup safe for populated databases,
corrects accepted-enum projection without weakening corruption detection, and
establishes the measured authority for the later durable mutation-job runtime.
The mutation-job lifecycle itself is not exposed in 0.223.0.

### 🩹 Fixed - Accepted Enum Projection

- Direct projection decodes accepted enum fields through their catalog enum
  wire instead of the generic scalar wire. Ordinary valid enum rows therefore
  no longer produce error 18, `RUNTIME_CORRUPTION`.
- Invalid enum payloads, inconsistent accepted-schema state, malformed journal
  records, and mismatched derived-index evidence still fail with typed
  corruption. The correction removes a false positive rather than weakening
  integrity enforcement.
- The regression is covered at the smallest persisted-row projection boundary
  and through Toko Feed's canonical `ItemVariant` snapshot restore.

### 🔧 Changed - Bounded Startup Recovery

- Startup no longer folds the complete journal, scans every row and index for
  cardinality, rebuilds all secondary indexes, and folds those rebuilt indexes
  before schema acceptance can finish. That work made an unchanged-schema
  upgrade proportional to historical journal and database size.
- Journal recovery now persists an exact record-level cursor and advances in
  bounded pages. A production page admits at most 2,048 batches, 4,096 records,
  8 MiB of encoded batch data, and approximately 20 billion Wasm instructions;
  it still makes progress when one logical batch is larger than a page.
- Generated initialization schedules zero-delay continuation pages outside the
  upgrade message. The database remains recovery-gated until the current
  logical batch and all committed tails are complete, so a partially folded
  transaction never becomes query-visible.
- Row folding derives each accepted index transition from the canonical
  predecessor and current accepted schema. Constraint-validation candidate
  index writes are explicit journal effects, so resumability does not trade
  away unique-index or activation correctness.
- Empty-marker, empty-tail startup performs constant work independent of row,
  index, and historical journal counts. Startup cardinality is optional when
  it is not already available; query planning retains its conservative
  fallback rather than rebuilding it during upgrade.
- Whole-store inspection remains an explicit bounded integrity workflow. It is
  no longer an implicit side effect of ordinary schema acceptance.

### ➕ Added - Durable Mutation-Job Contract

- A machine-readable release contract freezes the published 0.222.4
  predecessor, current semantic owners, exact collection-scale SQL intents,
  step limits, record bounds, failure points, instruction ceilings, and raw
  Wasm review gates before runtime implementation begins.
- The fixed scale authority contains 10,001 matching rows for both tier reset
  and scoring invalidation. At the maintained 64-update and 256-key limits, an
  all-stale operation requires at least 157 Forward calls and clean Verify
  requires at least 40 calls; a bounded page can never masquerade as complete.
- The future current-format record is capped at 64 KiB, its canonical intent at
  16 KiB, its continuation at 2 KiB, and its replay receipt at 8 KiB. The
  retained progress allocation remains capped at 64 records.
- Review ceilings are fixed before implementation at 5 million instructions
  for start, 30 million for a 64-update Forward step, 8 million for a 256-key
  Verify step, and 2 million each for state, exact replay, and acknowledgement.
- Generic revision-strict read jobs remain unchanged. Durable mutations will
  use a separate record and coordinator instead of adding a switch that
  weakens protected-store proof comparison.

### ⚠️ Breaking And Migration Notes

- Generated `db!()` initialization may return while a committed journal tail
  is still recovering. Calls that reach IcyDB before the scheduled continuation
  completes receive a typed recovery-pending conflict; applications must not
  perform dependent row work synchronously after `db!()` in the same
  `post_upgrade` message.
- The current journal adds constraint-validation index effects and a durable
  fold cursor. Migration-enabled development builds also hard-cut the two
  schema-migration record tags to their new current values. An older build with
  an unfinished schema-migration journal tail must finish recovery before
  upgrading or recreate that development state; no legacy decoder is retained.
- Ordinary completed stores require no row, primary-key, accepted-schema, or
  secondary-index migration. The populated integration upgrade preserves its
  existing canonical identities and counts.
- No mutation-job API, Candid endpoint, marker replacement effect, or mutation
  progress record is published yet. Those remain later 0.223 landing patches.

### 🧹 Cleanup

- Maintained SQL evidence, source commentary, and ignored measurement tooling
  describe current authority directly instead of retaining historical
  design-slice plans and provisional owner inventories.
- Seven overlapping crosscutting structural audit definitions are archived and
  replaced by two current recurring methods: flow convergence and duplication,
  plus complexity and technical debt. Historical methods remain available as
  immutable reference material rather than compatibility aliases.
- Complexity and velocity governance now requires a demonstrated need,
  canonical owner, simplest alternative, and explicit state-space delta before
  adding an independent behavior axis.

### 📊 Audit

- Before the recovery change, a populated same-schema Toko Feed upgrade
  exceeded the IC's 300-billion-instruction message limit while folding 16,715
  historical journal batches and never reached the former index rebuild.
- After the change, the same retained canister deploys in approximately four to
  seven seconds. Recovery pages measured about 20.01-20.04 billion instructions
  at their ceiling, with the final partial page at 13.04 billion.
- The verified pre/post population contains 294 Items, 119 ItemVariants, 175
  PokemonCardMetadata rows, 1,139 normalized Magic extension rows, 1,381 unique
  ProviderRecords, and 1,381 observations. Sampled first and last canonical IDs
  are byte-identical across the upgrade. The application's 1,382 provider
  replay inputs converge to 1,381 stored identities through deterministic
  upsert.
- The rebuilt Toko Feed candidate is 12,524,737 raw Wasm bytes, 121,140 bytes
  (`0.98%`) above its checked-out artifact. This comparison includes the whole
  current IcyDB dependency-family delta, not only startup recovery.
- The frozen 512-row mutation control remains bounded at 0.43 million prepare
  instructions, 25.55-27.19 million per 64-update Forward call, and
  6.43-6.44 million per 256-key Verify call. These values are comparison
  evidence, not a public durable-job implementation.

### 🧪 Testing

- The isolated Toko Feed snapshot restore and all 28 store tests pass against
  the local 0.223.0 candidate without changing their expected semantics.
- Focused IcyDB coverage passes for accepted-enum projection, journal codecs,
  interruption recovery, paged recovery, store reopen, derived-index handling,
  generated startup continuation, and the mutation-job contract baseline.
- Formatting, diff hygiene, warning-denied focused Clippy, default/SQL/
  diagnostics feature checks, and focused compatibility checks pass.
  Repository-wide suites remain push-owned.

### 📊 Complexity

The runtime correction changes approximately `+1,390/-670` lines across 26
workspace, facade, recovery, journal, data, index, session, test, and changelog
files. Persisted record-level progress and automatic continuation add one
necessary recovery state axis, while the complete secondary-index rebuild and
startup row/index cardinality scans are removed. The implementation is
moderately more explicit but changes startup from database-size-owned work to
one constant fast path or a sequence of bounded recovery pages.

The wider release also adds the mutation authority contract and consolidates
historical SQL evidence and audit methods. Most apparent documentation deletion
is relocation into the structural archive rather than discarded history.
