# 0.230 Durable Exact Cardinality Generations

## 0.230.2 - 2026-08-17

### 📝 Summary

- Activates one bounded store-local builder that publishes exact entity and
  accepted user-index-prefix counts only after a complete source-stable pass.
- Maintains a matching `Ready` generation at complete canonical fold
  boundaries and lets exact consumers combine that base with bounded live
  deltas. Missing, Building, stale, or malformed evidence keeps the existing
  deterministic conservative route.

### 🔧 Changed

- The existing replicated startup watchdog now advances at most one optional
  clear, scan, restart, or publication page after required recovery work. It
  adds no timer, scheduler, persisted work flag, public mode, or configurable
  budget, and optional construction does not gate ordinary readiness.
- Canonical rows and accepted physical user-index entries are scanned in
  exclusive bounded pages into the inactive count slot. Source drift rotates
  to the other slot; complete publication retires the build cursor without
  retaining generation history.
- Complete-batch convergence preflights checked count deltas and the next
  watermark before canonical mutation. The existing row and index overlays
  retain only signed count deltas needed for exact live-before-canonical
  visibility.
- One proof-bound store-handle route now supplies exact entity counts, prefix
  counts, direct `COUNT`, pruning, SQL DDL emptiness, and accepted-schema
  historical-row checks. The duplicate streaming-only pruning helper is gone.
- Generated watchdog reconciliation now expresses behavior-identical `Ready`
  and `Recovering` registration through one match arm.

### 📊 Audit

- A populated real-canister fixture proved build continuation across upgrade,
  conservative reads while Building, exact publication, live-delta
  maintenance, accepted-index drop/recreate, and fixed stable-memory
  high-water at 796,983,296 bytes after both slots were established.
- Repeated 4,096-key construction reached 1,703,936 physical schema bytes
  after both count slots and did not grow when slot A was reused.
- The real-canister complete-batch trap probe still restores byte-identical
  stable state and retries canonically; its audit trigger now distinguishes
  required startup `Ready` from optional cardinality work still sharing the
  watchdog.
- Repeated SQL performance samples now drain against the watchdog's actual
  scheduled state instead of inferring quiescence from one unchanged
  performance-counter sample, so retained journal debt cannot leak into the
  next fixture reset and cause valid E284 pressure.
- Maintained fold maxima remain below 30 billion instructions: 2.330 billion
  for 4,096 zero-index rows, 3.737 billion for 2,048 rows with three indexes,
  10.576 billion for 240 rows with 64 secondary indexes, and 20.905 billion
  for the 65,536-key accepted-index shape.
- The final production SQL audit artifact is 4,975,617 compiler-emitted Wasm
  bytes and 4,346,191 final raw Wasm bytes, 76,508 raw bytes above 0.229.1 and
  54,564 bytes inside the line allowance. Deterministic gzip is 1,682,219
  bytes; raw non-gzipped Wasm remains authoritative.
- Candid remains 60,428 bytes with SHA-256
  `5bc8b2c65e8e57ec1bee7db4677d7fff3bcab686159128fc2604fe40c00882d1`,
  and the final artifact retains 70 exports.

### 🧭 Migration Notes

- The current version-1 cardinality records defined in 0.230.1 are now active.
  Existing 0.230.1 stores without a generation begin bounded optional
  construction; there is no startup scan, compatibility decoder, public API
  change, or additional stable-memory ID.

## 0.230.1 - 2026-08-17

### 📝 Summary

- Adds the sole current version-1 durable identity and record codecs for one
  store-local exact-cardinality generation.
- Reserves the accepted `0x05` control and `0x06`/`0x07` count namespaces in
  the existing 16-byte schema key space. No additional stable-memory ID is
  introduced.

### 🔧 Changed

- The fixed 192-byte generation header binds database incarnation, the active
  data/index/schema/journal allocation quartet, accepted-root identity,
  canonical sorted accepted-index identity, fold sequence and epoch,
  generation ID, slot, and `Building`/`Ready` state.
- The bounded build cursor binds the same source identity and persists only a
  `Rows` or `Indexes` phase, exclusive physical checkpoint, and cumulative work
  totals. Its maximum encoded form is 16,897 bytes, below the frozen 20-KiB
  limit.
- Entity and accepted user-index-prefix logical keys use the frozen
  domain-separated SHA-256 preimage. Count values retain the full digest,
  generation ID, and exact nonzero `u64` count in 57 bytes; zero remains
  represented by absence.
- All current decoders reject unknown versions, malformed bounds, fingerprint
  corruption, source-identity drift, generation mismatch, and truncated-key
  digest collisions without a predecessor or fallback decoder.

### 📊 Audit

- Twenty-nine focused cardinality, codec, stable-reopen, and maintained
  volatile-owner tests pass. Warning-denied all-feature core Clippy and the
  durability-format and memory-ID invariant guards also pass.
- The production SQL audit artifact remains 4,888,976 compiler-emitted Wasm
  bytes and 4,269,683 final raw Wasm bytes, a zero-byte authoritative delta.
  Candid remains 60,428 bytes with SHA-256
  `5bc8b2c65e8e57ec1bee7db4677d7fff3bcab686159128fc2604fe40c00882d1`,
  and the final artifact retains 70 exports.
- The deterministic gzip is 1,648,180 bytes in the current tool environment;
  raw non-gzipped Wasm remains authoritative.

### 🧭 Migration Notes

- Existing databases require no action because this patch defines the current
  durable form but does not yet publish a generation. Patch 3 owns bounded
  populated construction; no compatibility decoder or startup scan was added.

## 0.230.0 - 2026-08-17

### 📝 Summary

- The accepted 0.229.1 baseline confirms that entity and accepted user-index
  prefix cardinality is exact during the current process but deliberately
  unavailable after reopening a populated journaled store.
- The 0.230 line is promoted through a six-patch tracker. This first patch
  freezes the durable generation, bounded build, planner fallback, storage,
  and measurement contracts without changing runtime behavior.

### 🔧 Changed

- One future store-local generation will own entity and accepted user-index
  prefix counts together. It binds the database incarnation, store allocation,
  accepted schema and physical index set, and complete-batch fold watermark.
- Durable records will use three reserved namespaces in the existing schema
  allocation: one control namespace and two isolated count slots. This adds no
  fifth store allocation, public memory-ID setting, or reduction to the
  38-store deployment bound.
- Populated construction is frozen as a bounded `Rows` then `Indexes` build
  outside startup. Source drift discards the isolated candidate; only a
  complete unchanged candidate can become `Ready`.
- Exact planning will consume only a matching `Ready` base plus exact bounded
  post-watermark overlay deltas. Missing, Building, stale, malformed, or
  mismatched evidence retains the existing deterministic conservative route.
- Optional build work will reuse the existing replicated driver. The line
  adds no convergence cursor, timer, scheduler, persisted work flag, mode, or
  caller configuration.
- Validation now provides grouped timing and complete failure summaries, a
  fast preflight, an exact-test-to-binary loop, and a focused durability
  matrix. CI runs the same static, core, workspace, and SQL evidence in
  parallel behind the unchanged required `check` gate.
- CI exposes reporting tools installed in its repository-local Cargo home to
  later Wasm evidence steps.
- Tag cleanup verifies both selected local and remote refs. Release publication
  atomically pushes only the current branch and exact release tag so deleted
  historical annotated tags cannot be republished implicitly.

### 📊 Audit

- Focused baseline validation passed 23 cardinality, reopen, schema,
  production-shaped planning, startup, and collection-scale upgrade tests.
- The maintained 10,001-row recovery fixture completed 179 Forward and 49
  Verify advances and preserved stable-memory length exactly at 1,124,139,008
  bytes across upgrade recovery.
- Production startup observation measured 160,897 instructions while freshly
  Recovering, 378,507 while Ready, and 250,821 immediately after upgrade, all
  below the unchanged 25-million ceiling and without a cardinality scan.
- The production SQL audit artifact remains 4,888,976 compiler-emitted Wasm
  bytes and 4,269,683 final raw Wasm bytes. Its Candid remains 60,428 bytes
  with SHA-256
  `5bc8b2c65e8e57ec1bee7db4677d7fff3bcab686159128fc2604fe40c00882d1`,
  and it retains 70 exports.
- The current tool environment produced a 1,648,186-byte deterministic gzip.
  Raw non-gzipped Wasm remains the authoritative footprint measure.

### 🧭 Migration Notes

- This release changes no persisted bytes or runtime behavior and
  requires no migration. Later 0.230 implementation patches remain governed
  by the pre-1.0 version-1 hard-cut policy.
