# Startup and Schema-Application Owner Audit

## Decision

The shared startup closure is large because it retains genuine recovery,
proposal-admission, schema-evolution and publication behavior. It is not one
accidentally duplicated runtime. No production rewrite is justified from the
retained-size result alone.

One bounded experiment is credible for a future authorized slice: determine
whether the generated proposal path can prove its existing no-removal contract
at the singular core admission boundary and thereby avoid retaining the
general removal-lowering family in minimum actors. This is a measurement
candidate, not an implementation recommendation.

## Observed Ownership Chain

| Owner | Role | May select or publish accepted schema? |
| --- | --- | --- |
| Generated actor wiring | Supplies sealed fragment bytes, submission key and entity-to-store paths; drives the startup lifecycle | No |
| Public `DbSession` facade | Decodes generated bytes, obtains opaque runtime target identities and composes one ordinary `SchemaProposal` | No |
| Core schema application | Proves recovery admission, idempotency, database identity and accepted-head freshness | Yes; singular admission owner |
| Application lowering | Derives catalog-native initial or existing-head candidates from the admitted proposal | No |
| Schema publication | Commits candidates and the durable application record atomically | Yes; only after core admission |

The generated path ends in the same core `apply_schema` authority as an
explicit source-keyed proposal. It does not reconstruct authority from
generated models. This convergence must remain intact.

## Measured Retention

The symbol-bearing builds are diagnostic and cannot predict final Binaryen
bytes directly. They do show that the same owner family is retained across all
four query actors:

| Actor | Startup retained | `lower_application_candidates` retained | `lower_existing_store_candidate` retained | Direct removal-family shallow bytes |
| --- | ---: | ---: | ---: | ---: |
| One-entity typed | 1,066,322 | 271,360 | 124,104 | 31,466 |
| One-entity SQL | 1,009,362 | 247,799 | 124,118 | 31,466 |
| One-entity dynamic | 1,019,444 | 255,071 | 124,120 | 31,466 |
| Ten-entity typed | 1,009,956 | 252,443 | 124,106 | 31,466 |

Within the 31,466-byte direct family, 13,833 bytes are separate generic sort
bodies for resolved removal representations. The exact equality across actors
confirms that this is shared schema-application reachability, not SQL-specific
duplication.

The 31,466 bytes are a diagnostic lower bound for the directly named removal
surface. The roughly 124 KB retained by `lower_existing_store_candidate` is an
upper bound only: generated upgrades still require existing-entity lowering,
so most of that closure cannot simply disappear.

## Reachability Reconciliation

Generated proposal composition always passes an empty removal vector. Initial
installation nevertheless needs initial proposal lowering, and later generated
schema reconciliation needs existing-head lowering. Therefore:

- deleting existing-head lowering is invalid;
- specializing only fresh installation is not lifecycle-complete;
- bypassing `SchemaProposal::try_compose` would duplicate canonical proposal
  validation and is invalid;
- bypassing core `apply_schema` would create a parallel admission authority and
  is invalid;
- merely extracting helpers or adding `inline(never)` has no credible saving
  ceiling because there is one retained caller and no demonstrated duplicated
  body.

The public facade contains similar setup in
`ensure_generated_schema_fragment` and `apply_generated_schema_fragment`, but
the actors select only one generated caller and unused generic methods are
dead-stripped. Consolidating that source may remove some Rust lines, but there
is no evidence it reduces final Wasm.

## Candidate Assessment

| Candidate | Expected reach | Complexity/state delta | Verdict |
| --- | --- | --- | --- |
| Keep the converged general application route | Every actor | None | Current reference |
| DRY the two public facade setup bodies | Source hygiene only; final Wasm likely neutral | Fewer source lines, no new state | Accept only as independent hygiene work |
| One private generated no-removal lowering contract beneath the existing core authority | Potentially every generated actor | One compile-time contract and a second lowering specialization; no new mutable owner | Measure in isolation before design |
| Merge removal representations solely to share sort monomorphs | At most the 13,833-byte named sort family before final optimization | New enum/dispatch and more coupled removal handlers | Reject as disproportionate |
| Skip generated fragment decode or proposal canonicalization | Superficially broad | Duplicated validation/admission semantics | Reject |
| Split initial install from existing-head reconciliation | Initial install only | Incomplete upgrade lifecycle | Reject |

## Required Experiment Contract

A future experiment may proceed only after a new minor is explicitly
authorized. It should be temporary and reverted unless it passes all gates:

1. The core application module remains the only authority that validates the
   target database, accepted head, idempotency identity and publication.
2. The generated contract checks an empty removal set fail-closed; it cannot
   accept a broader proposal or infer accepted state.
3. Initial install, exact replay, no-op restart and existing-head generated
   evolution produce identical receipts and accepted bundles.
4. Explicit public proposals retain all removal behavior unchanged.
5. Final raw Wasm is measured on at least `default_empty`, one-entity typed,
   one-entity SQL and ten-entity typed actors with the same `WASM-3.0` pipeline.
6. Startup instruction cost is non-regressing for fresh install, exact replay
   and one representative existing-head evolution.
7. The experiment is rejected if it adds a mutable owner, cache, persisted
   state, fallback authority, generated-model reconstruction or more than one
   private admitted-contract type.
8. A useful outcome should remove at least 32 KiB final raw Wasm from each
   minimum actor. A smaller result does not justify a second compiler-visible
   lowering specialization.

## Recommendation

Do not optimize the whole startup driver or split schema authority. If a future
minor prioritizes footprint, first run the no-removal specialization as a
throwaway paired build against the gates above. If it misses 32 KiB final raw
per minimum actor, retain the current converged route and move to the separate
SQL-ingress owner audit.
