## Problem

The maintained atomic mutation batch accepts inserts, updates, replacements,
and deletes for one entity. A synchronous application workflow that must
publish related rows from several entities therefore either:

1. performs several immediately committed IcyDB calls and owns partial-state
   repair; or
2. collapses independent entities into one row merely to obtain atomicity.

Toko Miner's local enrollment demonstrates the gap. `User`, its first
`UserPrincipal`, and its `Robot` are separate accepted entities in one store.
Publishing only a prefix leaves a valid but incomplete account that every read
and retry path must classify and repair.

This is narrower than a general transaction system. All requested rows live in
one registered store, execution is synchronous in one canister update message,
and the existing commit marker already binds ordered row records, multiple
entity paths, multiple Identity range owners, and recovery replay contexts.
The missing authority is the normal-write coordinator and preflight contract,
which currently specialize one batch to one catalog and row layout.

## No-Build Gate

The no-build alternative is an application-owned enrollment saga. It remains
required for cross-canister effects and lost-response idempotency, but it is
disproportionate for three local rows when the database already owns one
complete final-row overlay and one marker-atomic commit window.

The smallest typed-facade alternative is to document three manual binding
lookups, raw-key conversions, and result indexes. That executes correctly, but
it discards the entity distinction already represented by `Id<E>` and repeats
the same binding/ordinal plumbing in every mixed workflow. The generated
input-to-entity association, ephemeral builder, and sealed handles remove only
that demonstrated plumbing; they do not own database semantics.

The smallest engine outcome is therefore:

- widen the existing structural mutation batch from one entity to multiple
  current accepted entities in one registered store;
- preserve the existing writer, constraint, marker, journal, and recovery
  authorities;
- expose the same widening through the existing generated typed-write adapter;
  and
- reject every wider scope rather than add transaction modes.

The line does not introduce begin/commit commands, an interactive transaction,
a durable transaction record, rollback, or a second mutation executor.

## Decision Summary

`execute_trusted_structural_mutation_batch` becomes the one bounded same-store
multi-entity batch surface. A batch may contain one or more entities, provided
that every requested entity:

- resolves from one captured database-wide accepted runtime root;
- resolves to the same registered primary-row store path;
- is current and accepted before any generated value is evaluated; and
- participates within the fixed operation, entity-count, staged-byte,
  result-byte, marker-byte, and commit-work policies.

The generated `execute_trusted_typed_write_batch` remains an adapter over that
same owner. Its inputs may carry different exact current entity bindings when
those bindings resolve to the same store and runtime root.

The generated facade retains entity identity through `Id<E>` in authored
write inputs. An authored scalar primary-key slot for `E` uses `Id<E>`. A
direct relation field declared with `item(rel = T, ...)` uses `Id<T>` for one
or optional cardinality and `Vec<Id<T>>` for many, inside the existing
`WriteCell`. This applies to every supported scalar key, not only ULID. Raw key
scalars remain the storage and dynamic-write representation; the generated
adapter performs the one explicit lowering. A mixed-entity typed batch builder
resolves those bindings and returns sealed item handles so callers do not
coordinate heterogeneous result ordinals themselves.

One operation timestamp, one complete final-row overlay, one ordered row-op
set, one commit marker, and one recovery outcome cover the whole batch.

## Public API Hard Cut

The general structural and typed batch methods keep their current names and
accept mixed entities. They return one result per input mutation in input
order:

```text
execute_trusted_structural_mutation_batch(...)
    -> Result<Vec<DynamicMutationResult>, Error>

execute_trusted_typed_write_batch(...)
    -> Result<Vec<DynamicMutationResult>, TypedWriteError>
```

Each returned `DynamicMutationResult` describes exactly one input item:

- `entity` and `columns` identify that item's accepted row shape;
- `rows` contains exactly one final after-image or removed before-image; and
- `affected_rows` is zero or one.

This deliberately reuses the current result type. It avoids a second grouped
result schema and keeps heterogeneous rows unambiguous. Repeating entity and
column metadata consumes the existing result-byte budget; the engine does not
add an alternate compact result mode.

The maintained typed convenience is a facade view over that exact result
vector:

```text
let mut batch = session.trusted_typed_write_batch();
let user = batch.push(UserInsert { ... })?;
let membership = batch.push(UserPrincipalInsert { ... })?;
let robot = batch.push(RobotInsert { ... })?;
let results = batch.execute()?;

results.row(&robot)?
```

`TypedWriteAdapter` associates each generated input with its generated entity.
`push` uses that association to issue the current opaque binding and encode the
input; the caller cannot supply or substitute a binding. It returns a sealed
`TypedWriteHandle<E>` carrying only ephemeral facade identity and the item
position. `execute` consumes the builder, invokes the existing
`execute_trusted_typed_write_batch` exactly once, and returns
`TypedWriteBatchResults`, which owns the same ordered
`Vec<DynamicMutationResult>` plus the already issued bindings needed by the
existing row-projection helper.

A result accessor accepts only a handle issued by that exact builder, validates
its entity and position, and fails closed on an impossible mismatch. The
dynamic accessor returns the corresponding existing result item; the row
accessor projects its single row through the retained binding. It does not run
generated row decoding inside the mutation call. Thus the convenience removes
manual binding and ordinal bookkeeping without adding a core result schema,
wire encoding, output budget, or post-commit mutation failure.

The single-mutation method and same-entity insert convenience method retain
their current homogeneous `DynamicMutationResult` behavior. They converge on
the same staging and commit owner and are not compatibility execution paths.

Before 1.0 this is a direct public Rust hard cut. No legacy same-entity batch
alias, output wrapper, dual dispatch, or feature flag remains. No generated
IcyDB Candid endpoint or canister export is added.

## Admission And Bounds

The coordinator rejects before row staging when any structural condition is
invalid. The fixed policy is:

| Resource | Limit and owner |
| --- | --- |
| Input mutations | 4,096, existing structural batch owner |
| Distinct requested entities | 64, new fixed coordinator bound |
| Canonical stored row | 4 MiB, existing row boundary |
| Staged canonical keys and before/after rows | 16 MiB cumulative, existing writer-owned exact charge |
| Encoded public result vector | 1 MiB, completed before marker publication |
| Encoded commit marker | 16 MiB, existing commit-marker boundary |
| Commit work | Existing 16,384-unit prepared-row/index/Identity preflight ledger, unchanged; distinct context construction is independently bounded by 64 entities |

There is no caller-selected budget. The entity count is measured by distinct
accepted entity tag after resolution, not by display-name spelling or item
count. The 64-entity bound is intentionally much larger than the demonstrated
three-entity workflow while preventing an accepted 1,024-entity schema from
turning one request into unmeasured context construction.

The staged-byte charge remains exact and global across the batch. It counts
each admitted raw primary key plus canonical before and after row exactly as
the current writer does. Splitting items by entity must not reset the ledger or
clone a separately budgeted page. Marker encoding, derived index work, and
public result encoding retain their independent bounds and may reject a batch
before publication even when staged rows fit.

The synchronous API has no checkpoint or retry state. A deterministic policy
failure returns before a marker and retains no capacity, continuation, or
Active record. Retrying the same invalid request may repeat the error, but it
cannot wedge a durable job.

## Accepted Authority Capture

The coordinator captures one `AcceptedSchemaRuntimeRoot` and resolves every
dynamic entity name or typed source binding against that immutable root. It
does not repeatedly discover current schema and then compare loosely related
revision numbers.

For every item it retains the exact accepted catalog identity needed by row
lowering and commit preparation. Admission rejects:

- an unknown entity;
- a stale or incompatible typed binding;
- more than 64 distinct entity tags;
- a requested entity whose primary-row `store_path` differs from the first
  item; or
- any catalog/root inconsistency as a typed internal failure.

All of this happens before `Timestamp::now`, `Ulid::generate`,
`Identity::next`, row decoding, or result materialization. A rejected mixed-
store batch therefore cannot consume a generated value or Identity range.

"Same-store" applies to caller-requested primary-row mutations. Existing
schema-declared relation maintenance may touch a target index store owned by
another registered store, just as a current single-entity write can. Those
derived effects remain marker-bound and do not authorize direct row mutations
in the other store.

## Time And Generated Values

After complete structural admission, the coordinator reads one current
operation timestamp and passes it to every entity stager. Database-managed
timestamp fields across all items therefore receive the same value. There is
no item-local or entity-local call to `Timestamp::now`.

Other accepted insert generators retain their current semantics. Generation
is fallible pre-commit work, and the marker stores only canonical resolved row
bytes. Recovery never reruns a clock, ULID generator, default, normalizer, or
application callback.

### No symbolic cross-item references

One batch item cannot refer to a value that another item will generate. The
line adds no aliases, temporary IDs, expression language, generated-value
substitution, or caller-custodied continuation.

Relations between newly inserted rows therefore require caller-known primary
keys. A canister may generate a ULID before constructing the batch and submit
it only to an ordinary required ULID primary-key field. A field declared with
`generated(insert = "Ulid::generate")` remains GENERATED ALWAYS: generated
typed inserts omit it and structural admission rejects an explicit value.
0.235 does not weaken or bypass that accepted write policy. Independently
generated fields remain valid when no other batch item needs their value.

For the motivating enrollment shape, Toko's 0.235 adoption fixture must declare
`User.id` as an ordinary required ULID primary key, with no insert-generation
policy. Generated write inputs expose that scalar identity as `Id<User>` and
expose scalar relations targeting User as `Id<User>`, even though accepted row
storage remains raw ULID. Application code generates that `UserId` once before
constructing the three real generated inputs. The generated User insert
therefore contains `WriteCell<Id<User>>`, while the UserPrincipal and Robot
inserts carry the same typed `user_id` relation value. An unrelated raw ULID or
`Id<Robot>` cannot be substituted accidentally at this facade boundary.

This typing applies only to authored generated write inputs. Generated entity
rows retain their accepted schema field types, non-relation ULID fields remain
raw ULIDs, and the dynamic structural API continues to accept public scalar key
values. Insert uses `WriteCell<Id<E>>` for an ordinary authored scalar primary
key; patch and replace selectors use `Id<E>` directly. A schema-generated
insert key remains absent from the insert input, while its later patch/replace
selector is still `Id<E>`. Multi-component relation declarations retain their
component input types; they do not pretend that one component is a complete
`Id<Target>`.

The maintained adoption guide must show the generation boundary as fallible
and map the core generation failure into the public IcyDB error rather than
trapping or assuming generation cannot fail:

```rust
use icydb::{Error, prelude::*};

fn allocate_user_id() -> Result<Id<User>, Error> {
    Id::<User>::generate().map_err(Error::from)
}
```

The public prelude supplies `Id`, and `Id::<User>::generate()` is available when
the generated entity key implements `GenerateKey`. Toko calls this boundary
once per logical enrollment before constructing the batch, retains the
resulting key according to its application-owned lost-response retry contract,
and reuses it in all three typed inputs. This is documentation and compile-
proof of the existing public generation surface, not a new generator mode or
IcyDB idempotency mechanism.

The upstream proof does not simplify Toko's accepted membership invariants.
`UserPrincipal.authentication_principal` may remain its primary key, and the
fixture also retains Toko's deliberate unique
`(user_id, authentication_principal)` index plus its indexed `user_id`
relation. A generated Robot ID remains possible because no other enrollment
item needs it, but lost-response retry still requires an application-owned
stable operation/key strategy.

## Writer And Constraint Ownership

There remains one accepted structural writer. The current entity-specialized
constraint scheduler is generalized rather than copied.

The batch-wide scheduler owns:

- one global target-key set, where raw keys already include entity tag;
- ordered `CommitRowOp` values in input order;
- deleted target keys grouped by accepted target entity path; and
- the complete accepted constraint proof required by commit preflight.

Row-local save scheduling receives an explicit accepted item context containing
entity path/tag, decode contract, fingerprint method and value, and compiled
row constraints. The scheduler does not retain a second schema catalog or
reconstruct one from generated models.

Per-entity mutable staging state is limited to accepted authority, store/row
contracts, generated Identity ownership, and entity-local allocation ordinal.
The coordinator retains a map keyed by accepted entity tag. It does not group
and execute entity batches independently, publish subcommits, or reset bounds.

### Identity ranges

`Identity::next` remains entity- and field-owned. The coordinator may open one
tentative `IdentityStatementCursor` per participating Identity owner and emits
at most one contiguous range advance per owner. Candidate ordinals are
entity-local and follow that entity's request order.

Immediately before marker publication, every expected high-water is
revalidated. The marker binds all admitted ranges to the same commit identity.
Failure of any owner publishes no range or row. Recovery materializes the exact
marker-bound ranges and never reallocates values.

## Complete Multi-Entity Final Overlay

Commit preflight builds one `PreflightStoreOverlay` from every ordered row op
before it checks storage-backed constraints. Reads use this view:

```text
batch final row, including deletion
    -> committed accepted row
```

The preflight context cache is keyed by exact accepted entity path and schema
fingerprint. Each row is prepared with its own accepted commit context, while
the data and index overlays remain batch-wide.

This gives the required semantics:

- a source may reference a target inserted anywhere in the same batch;
- a source may not reference a target deleted by the batch;
- deleting a target succeeds when every referencing source is deleted or
  changed away in the same batch;
- deleting a target fails when any final source row still references it;
- uniqueness observes all final rows and all released old memberships;
- the same primitive key may appear for different entity tags; and
- two operations targeting the same entity-qualified key are rejected before
  commit.

Request order does not control constraint visibility: constraints see the
complete final overlay. Request order still controls row-op application,
results, generated ordinals within an entity, and deterministic first-error
evaluation where final-state semantics do not require canonical grouping.

Delete protection runs once for each target entity path that has deleted keys.
Target groups follow first request appearance; accepted relation sources keep
their existing canonical store/tag/path traversal. The source reader is the
same complete overlay for every group.

## Commit, Journal, Revisions, And Recovery

The current commit marker and journal version-1 formats remain authoritative.
No persisted field or decoder changes are required:

- `CommitRowOp` already carries entity path, raw entity-qualified key, before
  and after bytes, and accepted schema fingerprint;
- one marker already carries multiple ordered journal records and Identity
  range owners;
- one journal batch already derives all affected entity tags and advances each
  physically changed entity's mutation revision;
- one database commit sequence already binds every marker-local journal batch;
  and
- recovery already caches exact replay contexts by entity path and fingerprint
  and reads one complete canonical row overlay.

Normal preflight must use the same per-entity context rule as replay. The old
"first row supplies the context for every row" assumption is removed, not kept
as a single-entity fast path.

For a journaled same-store batch, all direct row records remain in one ordered
journal batch. Existing derived cross-store effects may cause the established
additional marker-local batches. Marker publication, journal append, row/index
application, entity-revision materialization, Identity range application, and
marker clearing retain the existing apply order.

Interruption at marker persistence, journal publication, a row prefix, all
rows, or state materialization must recover to the exact complete batch. No
guarded read or write can observe a mixed entity prefix while startup recovery
is incomplete.

Entities with at least one physical row transition advance their exact journal
revision once for the commit. Untouched entities and entities represented only
by logical no-op results do not advance. This preserves entity-scoped Verify:
an unrelated entity outside the batch does not restart Verify, while every
physically changed target entity does.

## Result Preparation

Every output row is converted through its own accepted enum/value catalog
before the marker opens. The complete `Vec<DynamicMutationResult>` is then
Candid-encoded only for the existing 1 MiB size proof. The encoded bytes are
not retained in stable state.

Typed execution validates every binding and lowers every typed patch before
staging. The returned dynamic result items can be projected through the
existing binding-owned `typed_mutation_row` helper at row index zero. The
mutation call itself does not perform a new fallible typed decode after commit.

The builder does not become another admission owner. It may reject binding or
input-encoding failures before dispatch, but operation/entity/byte/work
policy, accepted-root currency, same-store admission, result construction, and
commit remain exclusively owned by the canonical batch. Its item handle is
opaque, non-authoritative, non-serializable, and non-durable. It cannot select
an entity, key, budget, binding, result ordinal, or retry identity.

## Diagnostics, Metrics, And Privacy

New bounded rejection facts are limited to:

- actual and maximum distinct entity count; and
- failing batch ordinal plus expected and actual accepted entity tags for a
  same-store mismatch.

The facade adds one payload-free `BatchHandleMismatch` adapter reason for a
handle not issued by the exact result owner. It reports no builder identity,
entity, position, binding, or result value.

Errors do not retain entity names, store paths, keys, field values, row bytes,
Principals, ULIDs, result values, or generated/idempotency material. Existing
row, relation, uniqueness, staged-byte, result-byte, marker-byte, and commit-
work errors remain authoritative.

Save mutation metrics remain attributed to each item's accepted entity path.
Index and reverse-index deltas are accumulated per source entity rather than
attributed to the first item. The internal commit-plan observation remains one
event per marker; for a multi-entity marker it records only bounded entity
count and commit storage class instead of misattributing the commit to the
first entity. It contains no row or schema payload, creates no per-batch label,
and does not change the public metrics response.

The existing single-entity mismatch diagnostic is removed from the general
batch surface when same-entity admission is removed. It is not retained as a
legacy alias.

## Compatibility And Persisted Format

0.235 changes the current Rust batch return type in place and widens accepted
input semantics. Before 1.0:

- the maintained source surface moves directly to the new form;
- no old-return wrapper or same-entity-only mode remains;
- no generated-model runtime reconstruction is introduced;
- marker, journal, row, index, schema, revision, and Identity formats remain
  current version 1; and
- no predecessor decoder, translator, repair shim, or fallback authority is
  added.

The line is an additive execution capability but a source-breaking Rust API
hard cut. Generated write fields that represent scalar entity identities move
from raw keys to `Id<E>` with no raw-key alias. `Id<E>` retains the exact
`E::Key` Candid representation, so the intended wire shape is unchanged even
when an application independently exposes a generated input struct; Patch 2
must verify that claim rather than infer it. No maintained generated-canister
Candid method or export is added.

## State-Space And Complexity Delta

One independent behavior axis is widened: the general batch's distinct entity
count changes from exactly one to `1..=64`. It combines with the existing four
mutation intents and current heap/journal store modes, but only inside one
captured accepted root and one requested primary-row store.

Invalid combinations are rejected before generation or row staging:
cross-store direct rows, stale bindings, excessive entity count, async work,
and unsupported generated cross-item dependencies.

No persisted state, phase, continuation, cursor, transaction identity,
rollback outcome, configuration, or executor is added. The specialized one-
entity scheduler/preflight assumption is removed. Implementation structure
becomes moderately more complex in the coordinator and simpler in authority
shape because normal execution and recovery both use the same per-entity
context rule. The typed facade adds one generated input-to-entity association,
one ephemeral builder, and one sealed handle/result view; these erase repeated
caller binding/index plumbing and all converge on the existing typed-write
vector and structural executor.

## Explicit Non-Goals

0.235 does not add:

- cross-store caller-requested row batches;
- cross-canister or distributed transactions;
- multi-message, awaited, interactive, or nested transactions;
- SQL `BEGIN`, `COMMIT`, savepoints, isolation levels, or rollback;
- atomicity across separate IcyDB calls or unrelated application state;
- durable request idempotency, lost-response receipts, or automatic retry;
- compensation, partial abandonment, or cascading relations;
- batch-local aliases or references to generated values;
- preallocation, BY DEFAULT override, or explicit authorship of a schema-
  generated field;
- caller-selected operation, entity, byte, work, or result budgets;
- a second structural or typed mutation executor;
- automatic authorization, domain-error mapping, operation-ID retention, or
  lost-response classification in the typed builder;
- generated-schema runtime authority; or
- legacy output or same-entity compatibility paths.

## Downstream Retry Boundary

One successful batch is atomic, but a lost response still leaves the caller
uncertain whether the complete batch committed. Applications must use known
keys, operation identity, exact re-read, or idempotent replacement semantics
appropriate to their domain. 0.235 reduces the possible database states from
every committed prefix to only `before` or `complete`; it does not turn the
public method into an exactly-once protocol.

Toko's enrollment design should therefore retain a bounded retry contract even
after adopting this feature. It no longer needs to repair a User/membership/
Robot prefix created by this one call, but it must classify a lost successful
response and avoid generating a different logical account on retry.

## Validation And Evidence Requirements

### Owner-local correctness

- Same primitive key under different entity tags is admitted; the same full
  raw key twice is rejected.
- Row-local constraints use each item's own accepted catalog.
- Unique swaps/releases and relation target/source changes see the complete
  final overlay across entity boundaries.
- A late failure in any entity leaves every participating entity unchanged.
- Dynamic entity names and typed bindings resolve from one captured root.
- Cross-store rejection occurs before timestamps or generators run.
- Exactly 64 distinct entities admit when all other limits fit; 65 reject.
- Global operation, staged-byte, result-byte, marker-byte, and commit-work
  boundaries retain exact at-limit and over-limit proofs.

### Time, identity, and results

- Managed timestamps are identical across participating entities.
- Multiple numeric Identity owners commit exact contiguous ranges together;
  rejection consumes none.
- Results are one item per request in request order, with one row and zero/one
  affected count.
- Result-size rejection occurs before marker persistence.
- A caller-known target key supports source-before-target request order.
- The real generated Toko User insert exposes its ordinary required `id` as
  `WriteCell<Id<User>>`, and its scalar UserPrincipal and Robot relations reuse
  that exact `Id<User>` without a raw-ULID boundary conversion.
- Compile fixtures reject a raw `Ulid` or `Id<Robot>` in those User identity
  positions while non-relation ULID fields retain their raw type.
- Macro compile fixtures cover authored and generated scalar primary keys plus
  required, optional, and many direct relations, including one non-ULID key;
  composite relation components remain component-typed.
- A maintained no-SQL example compiles
  `Id::<User>::generate().map_err(Error::from)` through the public prelude and
  uses the successful value in the real Toko typed batch rather than trapping
  on generation failure.
- The mixed builder resolves and encodes each generated input without caller-
  supplied bindings. Its sealed handles retrieve the exact ordered dynamic
  result and binding-owned row projection without caller-authored indexes;
  handles from another builder or entity fail closed.
- A separate generated-ULID fixture omits `id` from its typed insert and
  rejects an explicitly authored structural value, proving that 0.235 did not
  add a generated-field bypass or hidden substitution.
- Toko's compound `(user_id, authentication_principal)` uniqueness is
  exercised beside the Principal primary key and `user_id` index rather than
  removed from the proof fixture.

### Durability and recovery

- Journal records preserve request order and exact entity path/fingerprint.
- Every physically touched journaled entity revision advances once; unrelated
  entity revisions remain unchanged.
- Recovery uses one complete canonical multi-entity overlay and an exact
  context per entity path/fingerprint.
- Interruption after marker, journal, first row, all rows, and state effects
  converges to the complete batch with correct indexes, reverse indexes,
  Identity ranges, and revisions.
- Corrupt path/tag/fingerprint combinations fail closed; replay never falls
  back to generated models or another schema revision.

### IC and artifact evidence

- Measure a Toko-shaped three-entity journaled batch against equivalent three
  sequential writes, reporting instructions and the eliminated partial-state
  window without claiming distributed transaction behavior.
- Measure the 64-entity policy boundary or a mechanically equivalent worst-
  case context-construction harness and retain explicit execution headroom.
- Report stable marker/journal bytes for the three-entity case and prove no new
  stable allocation or format.
- Report compiler and final raw Wasm bytes as primary artifact measures;
  deterministic gzip is secondary context.
- Compare Candid and exports and explain any difference. The intended result is
  no maintained generated-canister surface change.
- Report files touched, approximate line delta, delivery domains, duplicated
  flows removed/retained, and whether the final implementation became simpler,
  neutral, or more complex.

Agents run only the focused package, target, named recovery, compile, and
PocketIC selections for the active patch. The user owns complete repository
validation and release publication.

## Completion Criteria

0.235 is complete only when:

- the maintained general structural and typed batch surfaces accept current
  same-store entities and reject cross-store direct rows;
- all items share one captured accepted root and operation timestamp;
- every applicable constraint reads one complete multi-entity final overlay;
- all canonical dynamic output conversion and byte/work admission finish
  before the marker;
- multiple entity contexts, Identity ranges, entity revisions, and journal
  records remain marker-atomic through every recovery boundary;
- the old first-entity context assumption and same-entity rejection path are
  removed rather than retained beside the new flow;
- the real Toko-shaped typed proof uses one application-generated ordinary
  `Id<User>` across User, UserPrincipal, and Robot while retaining compound
  membership uniqueness;
- generated scalar primary-key and direct scalar-relation write inputs retain
  entity identity through `Id<E>` and reject cross-entity key substitution;
- the binding-resolving builder and sealed item handles remain a facade over
  the one canonical typed-write vector, ordered dynamic result vector, and
  structural executor;
- the maintained fallible `Id::<User>::generate()` example is compile-checked
  against the public facade and maps generation failure without a panic;
- schema-generated ULID fields still omit their typed insert member and reject
