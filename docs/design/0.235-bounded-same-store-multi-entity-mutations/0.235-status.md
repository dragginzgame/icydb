## Demonstrated Need

Toko Miner `ICYDB-009` requires one synchronous local enrollment operation for
`User`, `UserPrincipal`, and `Robot` rows in one registered IcyDB store. The
current same-entity batch otherwise leaves the application responsible for
every partial committed prefix.

The design passes the no-build gate narrowly because the current marker,
journal, final overlay, multiple Identity range, entity-revision, and recovery
owners already carry most of the required atomic shape. 0.235 generalizes the
normal writer and preflight; it does not introduce transaction state.

## Frozen Decisions

- Requested primary rows must all resolve from one captured accepted runtime
  root and one registered store path.
- The existing structural batch method becomes multi-entity; the typed batch
  remains an adapter over it.
- Both general batch methods return `Vec<DynamicMutationResult>`, exactly one
  result per request in request order.
- Fixed limits are 4,096 operations, 64 distinct entities, 4 MiB per row,
  16 MiB staged keys/rows, 1 MiB encoded result, 16 MiB marker, and the existing
  16,384-unit prepared-row/index/Identity commit-work policy. Distinct context
  construction is independently bounded by the 64-entity limit.
- One current operation timestamp covers every item.
- The complete final overlay is visible to every entity's uniqueness and
  relation validation.
- Multiple Identity owners retain one tentative cursor/range per owner and
  commit under the same marker.
- Current marker and journal version-1 formats are unchanged.
- Batch-local references to generated values are unsupported. Newly related
  rows require caller-known keys.
- Toko's adoption fixture uses an ordinary required `User.id: Ulid` generated
  once as `Id<User>` by application code before constructing real generated
  typed writes. Generated scalar primary-key and direct scalar-relation inputs
  preserve `Id<E>` even though accepted row storage remains raw key material.
  0.235 adds no preallocation or explicit-value bypass for a schema-generated
  field.
- A facade-only mixed typed builder resolves each generated input's binding and
  produces sealed entity-typed item handles over the canonical ordered dynamic
  result vector. It adds no executor, core result schema, wire encoding, or
  durable state.
- Toko's Principal primary key, indexed `user_id` relation, and unique
  `(user_id, authentication_principal)` membership index all remain in the
  proof fixture.
- Lost-response idempotency remains application-owned.
- There is no cross-store direct row batch, cross-canister transaction,
  rollback, continuation, caller-selected budget, or second executor.

## Patch 1 Boundary

Patch 1 owns:

- one-root/same-store structural admission;
- the 64-entity bound and privacy-safe rejection facts;
- global exact staged/result/marker/work policy;
- batch-wide constraint scheduling and deleted-target grouping;
- per-entity accepted commit contexts and Identity cursors;
- ordered heterogeneous results;
- multi-entity journal/revision/recovery proof; and
- direct transaction, atomicity, relation, identity, and facade documentation.

Patch 1 may not add typed-only execution, generated-value aliases,
idempotency receipts, cross-store direct mutations, rollback, transaction
state, or compatibility wrappers.

## Patch 2 Boundary

Patch 2 owns:

- current mixed-binding typed-write admission over Patch 1;
- generated scalar primary-key and direct scalar-relation write inputs typed as
  `Id<E>` (or `Vec<Id<E>>` for a many relation), with raw key lowering retained
  inside the generated adapter and composite relation components unchanged;
- a binding-resolving mixed typed builder and sealed item handles over Patch
  1's canonical result vector;
- one Toko-shaped User/membership/Robot proof using real generated adapters and
  an ordinary application-generated `UserId`;
- one maintained no-SQL example that compile-checks fallible
  `Id::<User>::generate().map_err(Error::from)` through the public facade;
- retained compound membership uniqueness plus a negative generated-ULID
  authorship/bypass proof;
- stale and mixed-store typed rejection;
- result projection/order proof without post-commit mutation failure;
- representative PocketIC instructions and stable-state evidence;
- final Candid/export and raw-Wasm comparison; and
- final complexity and closeout reconciliation.

Patch 2 may not add another core/executor or wire batch result shape,
typed-specific budgets, a generated-model runtime route, generated-key
preallocation/override, or any deferred transaction machinery. Its typed
result view may only retain Patch 1's ordered dynamic vector and already issued
opaque bindings. A wrong-owner handle uses one payload-free
`BatchHandleMismatch` adapter reason. The `Id<E>` Rust input hard cut retains
the exact raw key Candid representation and must be verified as wire-
equivalent rather than assumed.

## Downstream Review Resolution

The first external review found one implementation blocker: the design's
caller-known User key did not distinguish an ordinary required ULID from
Toko's then-proposed `generated(insert = "Ulid::generate")` field. Generated
typed inserts omit that field and the structural writer correctly rejects an
explicit value.

The smaller resolution is frozen here. Toko's 0.235 adoption shape changes
`User.id` to an ordinary required ULID and generates it once in application
code as `Id<User>` before batch construction. IcyDB does not add a new
generator mode or write-policy exception. The same review confirmed that Toko
intentionally retains unique `(user_id, authentication_principal)` membership
authority; the Patch 2 proof must retain and exercise it.

The next downstream review found no atomic-execution blocker but identified a
typed-facade gap: generated write inputs erase entity identity to raw `Ulid`,
and callers must resolve three bindings and coordinate heterogeneous result
indexes manually. Patch 2 now closes that gap without widening the executor.
Generated scalar User identity positions use `Id<User>`, each generated write
associates its entity for automatic binding, and sealed builder-issued handles
map back to the existing ordered dynamic results. Miner still owns key
retention, authenticated Principal resolution, value construction,
authorization, retry operation IDs, lost-response classification, and domain
errors.

The maintained public-facade example uses
`Id::<User>::generate().map_err(Error::from)`, followed by construction of the
real three-item typed batch from the successful typed key. This documents the
existing `Id<E>` generation and public `Error` conversion surfaces; it adds no
new generator mode, error class, persistence, or execution path.

## Current Implementation Facts

- Normal structural staging owns one catalog, descriptor, scheduler, store,
  operation timestamp, and optional Identity cursor.
- Commit preflight currently derives one context from the first row and applies
  it to every row.
- The preflight row overlay itself is already entity-qualified and resolves
  fallback rows by entity tag.
- Recovery already caches contexts by entity path/fingerprint and reads one
  canonical final-row overlay for a retained row-op batch.
- Commit payload construction already supports ordered records from multiple
  entity paths, multiple Identity owners, one database commit sequence, and
  multiple marker-local journal batches.
- Journal append already derives the affected entity-tag set and advances
  entity-scoped mutation revisions.
- The public prelude re-exports `Id`, `Id::<E>::generate()` delegates to the
  entity key's `GenerateKey`, and public `Error` converts its `InternalError`.
- Generated write structs currently expose scalar primary-key and relation
  positions as raw schema types, and callers currently resolve bindings and
  heterogeneous result indexes manually; Patch 2 owns those facade hard cuts.
- Delete relation validation must change from one target path plus one key set
  to bounded target-path groups over the same complete overlay.
- The current homogeneous `DynamicMutationResult` cannot describe several row
  layouts, so the general batch return becomes an ordered vector of one-row
  results.
