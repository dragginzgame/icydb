# Query normalization boundary allowance — feasibility checkpoint

Date: 2026-09-15. Baseline: published 0.257.13; no runtime changes.

## Verdict

The later reduced-parser finding at the end of this document is a separate
representation decision. The user subsequently approved its narrow identity
exception while preserving input limits; this does not revive the rejected
allowance estimates or relax unrelated canonical-identity requirements.

Do not enable a blanket node-count × payload-size allowance. It conflates cheap
field/operator checks with expensive value comparison and can reject useful
inputs despite modest actual work. A shape-aware, query-boundary allowance is
still a candidate, not a proven bound or completed R1 admission.

The initial shape-aware prototype below also fails the usefulness gate. Do not
land it or turn the preflight into a simplifier simulator. This does not prove
every boundary estimate impossible; it rejects this candidate before investing
in a full scratch/sorting bound. Next, admit actual expression-to-predicate
construction through its existing request owner and distinguish resource failure
from unsupported extraction. Boolean normalization itself remains unqualified.

## Source findings

| Owner | What an upfront allowance must cover |
| --- | --- |
| `predicate/normalize.rs`: `normalize_not`, `normalize_and`, `normalize_or` | Box/Vec construction and cumulative growth; nested associative flattening can move leaves through several ancestors. A leaf is returned without construction. |
| `predicate/simplify.rs`: `simplify_and_compare_constraints` | Pair traversal, field/coercion equality and vector removal shifts. Replacement restarts traversal; pure removal does not. Value comparison occurs only after field/coercion and operator eligibility. |
| `predicate/normalize.rs`: `canonicalize_predicate_children_for_eval` | Stable sorting and deduplication. Two reusable key buffers do not eliminate per-comparison encoding or encoder-owned scratch. Different evaluation ranks skip key construction. |
| `predicate/encoding.rs`: raw sort-key encoding | Text casefolding, temporary membership views, map-reference ordering, nested payload encoding and buffer growth. A small final key is not a cumulative allocation bound. |
| `predicate/encoding/admission.rs` | Existing capacity walkers admit one encoding's output/work and scratch, not repeated normalization comparisons. They charge while walking; they are not pure reusable size getters. |
| `value/canonical.rs` | OR-to-IN canonicalization has its own canonicality scan, value sort and deduplication. An explicit membership leaf is not sorted by boolean normalization itself. |

Authored input limits are depth 128, 4,096 nodes and 2 MiB of input bytes
(`query/admission/input.rs`). These are not a derived-work proof. The current
read budget has 16,000,000 predicate/expression steps and 128 MiB temporary
construction bytes (`executor/budget.rs`); temporary bytes are cumulative, not
peak live heap. Neither limit is changed by this assessment.

## Structural arithmetic check

For one flattened conjunction with `n` children, a deliberately loose pair-visit
bound is `sum(C(m, 2), m=2..n) = n(n²-1)/6`: every mutation removes a child,
and a fixed-size pass visits each pair at most once. This bounds pair dispatch
only, not field bytes, value comparison, shifts, sorting or nested conjunctions.

The table is an analytical operation-count exercise, cross-checked with a local
JavaScript model of the maintained scan/restart control flow. It is **not** a
Rust execution measurement, IC instruction/cycle result or timing benchmark.
The equal-bound case is a flat sequence of `f_i >= 0, f_i <= 0` pairs, each
on its own field; each pair becomes an equality and restarts the scan.

| Children | Disjoint fields, no reductions | Independent equal-bound pairs | Loose pair-visit bound |
| --- | ---: | ---: | ---: |
| 16 | 120 | 260 | 680 |
| 64 | 2,016 | 16,400 | 43,680 |
| 128 | 8,128 | 131,104 | 349,504 |
| 512 | 130,816 | 8,388,736 | 22,369,536 |

Multiplying the 64-child bound by two 1-KiB operands gives 89,456,640 byte-visits,
already above the 16,000,000 expression-step limit under a byte-per-step policy.
For distinct fields, none of those payload comparisons runs. This disproves the
usefulness of that particular blanket estimate, not all conservative estimates.
It does not establish a cycles-per-step conversion or a safe sort bound.

## Placement and error contracts

- `normalize_query_predicate` in `query/plan/access_planner.rs` already owns
  current preparation work. Preflight must inspect the schema-normalized
  predicate, since accepted conversion may change value representation.
- `hash_predicate` in `predicate/fingerprint.rs` already receives a
  `ConstructionBudget`. A failure must return before publishing a digest;
  successful bytes must stay identical. Do not create a fresh request here.
- Expression-derived predicates normalize inside
  `query/plan/expr/predicate/compile.rs`, whose extraction result is currently
  `Option<Predicate>`. A check only in access normalization misses this earlier
  work. Before enabling admission, separate resource failure from unsupported
  extraction at its existing callers; do not turn exhaustion into `None`.
- Accepted-index, schema and recovery callers remain separate operation owners.
  Query-boundary admission must not silently change their accepted formats,
  rejection contracts or replay behavior. No optional/no-op budget adapter or
  second semantic normalizer is authorized.

## Initial experiment acceptance gate

Prototype a shape-aware allowance before wiring new rejection into runtime.
Use structural counts for pair dispatch and separate conservative payload/key
allowances; evaluate whether these can be derived without simulating reductions
or introducing a domain-grouping data structure solely for accounting.

Qualification must include single leaves, explicit large `IN`, eligible OR-to-IN,
wide distinct-field ANDs, repeated same-field bounds, nested AND/OR, casefolded
text and nested membership/map payloads. Include 16/64/128/512-child shapes where
otherwise admitted. Check cumulative repeated calls and long common field-name
prefixes as well as literal sizes. Estimates must cover work after flattening,
OR collapse and equality replacement, not only the authored tree.

Prove encoder and sorting scratch bounds against the maintained owners, including
growth and nested sorting. Preserve stable equal-key order, canonical bytes,
cursor identity and schema validation before simplification. Ordinary useful
queries need room for subsequent planning/execution, not merely a normalization
allowance just below the whole request ceiling.

If a cheap, defensible estimate cannot pass that matrix, report the concrete
failure and choose scoped owner-level admission explicitly. Do not silently add
a general cost simulator, new limits or broader write/replay accounting.

No performance gain is claimed. Matched raw Wasm and IC instruction/cycle
qualification belongs to the selected implementation; it cannot be replaced by
these structural counts. This checkpoint does not close R1 or the 0.257 line.

## Shape-aware screening experiment — 2026-09-15

One focused Rust probe ran the maintained normalizer on 24 cases: four widths
(16/64/128/512) for distinct-field text, distinct-field casefolded text,
independent equal-bound pairs, same-field increasing lower bounds, eligible
OR-to-IN and explicit IN. Text operands contained 1,024 ASCII bytes. Field names
were `field_0000` onward in ascending order. Temporary test-only hooks counted
pair dispatch, calls to equality/order comparison and emitted raw sort-key bytes.
Each normalized result passed an idempotence assertion. No runtime budget was
enabled, and the instrumentation has been removed from the source tree.

The candidate covers only flat scalar-comparison ANDs. A borrowed scan records
child count `n`, counts `g`/`l` of inclusive lower/upper bounds, total scalar
payload bytes `P`, and maximum field-name length `F`. It uses the existing
admitted raw-key capacity walker to obtain `K`, without encoding the input.
It introduces no domain grouping or semantic comparison in preflight:

- Possible replacements: `r = min(g, l)`; each consumes an inclusive bound pair.
- Pair envelope: `Q = sum(C(n-j, 2), j=0..r)`.
- Screening step estimate:
  `Q * (1 + 2F) + P * (n-1) * (r+1) + K * (n-1)`.

The terms separate structural/field checks, scalar payload visits and key
construction. The final term is a candidate sorting-work envelope, **not a
proven contract of Rust's stable sort**. This is an early usefulness screen,
not a complete admission implementation: it excludes nested shapes, full
scratch growth, coercion metadata and several value families. Sizing-walk
charges and the rest of query preparation would consume additional budget.

Representative observations:

| Shape | Children | Actual pair checks | Actual simplifier value comparisons | Actual key bytes emitted | Candidate expression steps |
| --- | ---: | ---: | ---: | ---: | ---: |
| Distinct fields, text | 64 | 2,016 | 0 | 135,828 | 8,860,320 |
| Distinct fields, text | 128 | 8,128 | 0 | 273,812 | 35,714,432 |
| Distinct fields, casefold | 64 | 2,016 | 0 | 135,828 | 12,989,088 |
| Distinct fields, casefold | 128 | 8,128 | 0 | 273,812 | 52,360,576 |
| Independent equal bounds | 128 | 131,104 | 64 | 6,804 | 17,169,216 |
| Same-field increasing bounds | 512 | 511 | 511 | 0 | 38,361,792 |

The current expression-step ceiling is 16,000,000. The candidate rejects both
128-field text cases, and two 64-field calls exceed that ceiling cumulatively
before other preparation. Field eligibility eliminates their simplifier payload
comparisons; already-ordered children also make actual key construction much
smaller than the envelope. This is evidence against the candidate's usefulness,
not a claim that the observed columns constitute the full resource cost or prove
these synthetic shapes fit every schema/query admission gate.

All observed flat-AND pair counts fit `Q`. The independent-bound observations
also reproduce the earlier analytical scan counts. Eligible OR and explicit IN
cases emitted no predicate sort keys; the OR still performs membership value
canonicalization, which these hooks do not count. The flat-AND candidate does
not cover either shape. No estimate is reported for them.

Stop this candidate at the necessary usefulness gate. Nested/map payloads,
shuffled inputs, long common field prefixes, full allocation bounds and repeated
runtime rejection behavior remain unqualified; do not mark the full matrix
passed or add increasingly precise grouping/reduction prediction to rescue it.
The observed operation counts and emitted bytes are bound-analysis evidence,
not IC instructions/cycles, peak heap measurements or performance metrics.

## Selected construction outcome

The user subsequently approved this outcome. Its implementation and qualification
are recorded in the [handoff](0.257-explain-remaining.md#expression-to-predicate-construction--2026-09-15).
The experiment's rejection and remaining normalization limitations are unchanged.

`query/intent/mutation.rs::append_filter_expr` already has `PreparationWork`,
but `NormalizedFilter::from_normalized_expr` and predicate extraction do not
receive it. SQL lowering also has that authority before extraction. Meanwhile,
`query/plan/expr/predicate/compile.rs` directly clones literals/text and allocates
membership vectors and predicate boxes.

The next proposed implementation should pass existing authority to those
construction sites, reuse the current admitted copy/container helpers, and
return `Result<Option<Predicate>, QueryError>` (or the existing caller's error
equivalent). `None` must continue to mean unsupported extraction, never resource
exhaustion. Include typed-query and SQL propagation, pre-publication failure
tests and retained coverage semantics in that one handoff. No new request,
normalizer, cache, profile or replay budget is needed for this construction
outcome. It does not, by itself, finish boolean normalization admission.

Validation: the focused probe passed all 24 cases and its count/idempotence
assertions. Production files were restored byte-for-byte after removing only
the temporary hooks; formatting and diff checks pass. No full suite or Wasm/IC
measurement was run. Only this assessment and the two status references remain
changed by the experiment; the pre-existing Cargo.lock diff is untouched.

## Reduced predicate chain representation — 2026-09-15

Continuation after the integrity index-list handoff found a concrete construction
issue in `predicate/parser/expression/chain.rs`: each same-operator term wraps the
entire preceding tree in another binary node. `normalize_and`/`normalize_or` then
normalize those prefixes before flattening their parent. This creates repeated
intermediate work before cumulative construction admission is added.

The ordering matters beyond construction. For strict text equalities, the first
two OR leaves collapse to IN; the next parent sees IN plus equality, which cannot
use the same-equality OR collapse. In contrast, a flat OR reaches that collapse
with every original equality still present. Example:
`name = 'v0' OR name = 'v1' OR name = 'v2'` yields an OR of IN and equality today;
the explicit flat form yields one IN. This is not evidence of wrong row results,
but it disproves canonical-shape/digest parity for the proposed parser rewrite.

A temporary Rust probe exercised both OR and AND at widths
2/3/4/16/64/128/129. OR used one field with distinct text literals; AND used
distinct fields. It compared the maintained parser against a directly built flat
predicate through the same normalizer and normalized fingerprint encoder.

| Shape | Current parsed nodes/depth | Current normalized nodes | Flat normalized nodes | Same predicate digest? |
| --- | --- | --- | --- | --- |
| Two-term OR | 3 / 2 | 1 | 1 | Yes |
| Three-term OR | 5 / 3 | 3 | 1 | No |
| 128-term OR | 255 / 128 | 128 | 1 | No |
| 128-term distinct-field AND | 255 / 128 | 129 | 129 | Yes |

At 129 terms both parsed chains reject with the current expression-depth error;
the corresponding directly constructed flat input has depth 2. Automatically
admitting larger chains would therefore widen input admission while derived-work
bounds are still incomplete. Token/byte limits alone do not establish that this
widening is useful or safe for conjunction simplification.

Recommended next outcome, requiring approval of the identity change: construct
flat same-operator chains at the reduced parser owner, retain operator precedence
and explicit nesting, and qualify it across normalization, index selection,
membership evaluation, nullable-unique acceptance and dependency discovery.
Keep the current admission envelope for this first change unless widening is
separately justified. Do not add compatibility normalization, a second parser,
another budget profile or a cost simulator. The old successful-digest parity
requirement must be explicitly revised for affected shapes before implementation.

The observed digest change is not proof that persisted schema bytes change:
the snapshot codec stores predicate SQL text. Plan/cache/cursor impact still needs
consumer qualification; do not claim a database reinstall requirement from this
probe alone. Broader replay accounting remains deferred.

Validation: the one focused probe passed across all 14 cases, including explicit
three-term OR shape/digest and over-depth rejection assertions. Its temporary
test was removed, leaving no runtime/test-source change. Counts are structural
observations, not performance measurements; raw Wasm and IC cycles/instructions
remain unmeasured. The prior integrity-admission diff is preserved.

### Approved implementation

The user approved the recommended hard cut. Each reduced AND/OR parser now
accumulates children directly instead of constructing binary-prefix trees.
It retains `max(prefix, right) + 1` source-complexity admission, including nested
child complexity, separately from output depth. Explicit parentheses are not
flattened by parsing; the existing normalizer still owns later simplification.
The implementation adds no enum variant, mode, ceiling, budget or parser path.

The canonical-byte parity requirement is relaxed only for affected reduced
predicate chains. Tests protect the new flat form and its membership identity,
not a retained predecessor representation. Qualification and remaining bounds
are tracked in the status/remaining-work documents. Broader replay accounting
and wider-input admission remain outside this handoff.
