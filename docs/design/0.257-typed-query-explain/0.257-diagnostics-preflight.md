## Verdict

After slice 7, the remaining decision is scope, not another proposed
normalization repair. The CASE budget and single expansion owner are complete;
they do not establish a bound on all ordinary preparation/candidate work. The
post-slice-7 review below recommends narrowing that part of slice 5's guarantee.
This recommendation is pending approval; the approved design is not silently
weakened and no diagnostic runtime changes have been made.

### Earlier CASE recommendation

The two-outcome split is adopted and comparator re-entry is repaired. No
diagnostic production changes have started. Remaining CASE expansion still
precedes diagnostic projection, so checking the finished plan cannot establish
the promised preparation bound.

Recommend a bounded CASE rewrite at the existing canonicalizer: retain its
already-supported compact CASE representation when expansion would exceed the
budget. This is a proposed contract change, not an implemented limit or a
complete diagnostics safety proof. It avoids a new query-rejection policy but
can change canonical identity and access-path opportunities for affected queries.
The user approved that policy change as slice 7. Ordinary identity preservation
remains a requirement of slice 5 against the resulting current canonical form.

## Newly established source findings

1. [Boolean ordering](../../../crates/icydb-core/src/db/query/plan/expr/canonicalize/normalize.rs)
   compares operands using `render_scalar_filter_expr_plan_label`.
2. That [label helper](../../../crates/icydb-core/src/db/query/plan/model.rs)
   clones its expression and invokes `normalize_bool_expr` before rendering.
3. Nested boolean groups therefore re-enter normalization and sorting from the
   comparator. Traversal descends into subtrees, so this is repeated finite work,
   not a claim of infinite recursion. Debug normal-form checks also use this
   comparator and amplify the effect.
4. [Searched CASE lowering](../../../crates/icydb-core/src/db/query/plan/expr/canonicalize/case.rs)
   guards each arm with two copies of its condition. Its limit is eight arms per
   CASE, not a bound on the total expanded tree. Nesting inside the condition
   multiplies those copies. A shallow source tree can consequently manufacture
   many nested groups that exercise the ordering path above.
5. SQL scalar SELECT/DELETE WHERE reaches this owner through
   [predicate lowering](../../../crates/icydb-core/src/db/sql/lowering/predicate/mod.rs)
   and its scalar normalization stage. This happens before the shared prepared
   plan lookup and logical explain projection; a rejection added only to
   `AccessPlannedQuery::explain()` cannot bound that earlier work.

The ownership-preserving alternative to investigate is rendering already
normalized comparator operands directly with the existing scalar label renderer.
Do not assume that substitution preserves every canonical byte without testing
comparison direction, mixed operators, functions, CASE, NULLs and duplicates.
Even if it removes the repeated work, CASE's expanded size still needs accounting.

## Native probe

The probe invokes the real `canonicalize_scalar_where_bool_expr_artifact`, not
a reconstructed lowering algorithm. Start with boolean field `field_0000`;
each level wraps the previous expression as the condition of one CASE arm,
with distinct boolean fields for THEN and ELSE. Thus one level corresponds to
`CASE WHEN previous THEN next_field ELSE another_field END`.

Input construction and iterative node/depth counting are outside the timer.
The timer includes canonicalization and its temporary allocations, but excludes
final output counting/disposal, parsing, accepted-schema validation, planning,
row execution and rendering the final explain report. These are single-run
observations, not stable microbenchmark medians or IC measurements.

## Resumed preflight after slice 6

The comparator repair removes repeated normalization, not expression growth.
The previously measured six-level CASE still expands from 19 source nodes to
694 canonical nodes. Every containing CASE can copy that produced condition
again. A diagnostic-only depth/byte check on the source or finished plan is not
a pre-allocation bound on these copies.

There is a smaller alternative to adding query-wide rejection plumbing.
`normalize_bool_case_expr` already retains `Expr::Case` when the expansion owner
declines a rewrite, currently for more than eight arms. The compiled expression
owner already compiles/evaluates CASE directly. Extend that existing optimization
decision to account for produced nodes, depth and copied payload before
construction, rather than duplicating the expansion algorithm in EXPLAIN.
Exact caps and cumulative-work accounting still need qualification before code.

This is not a new compatibility fallback: both representations are maintained
semantic forms today. Proposed state-space delta: zero modes, public APIs,
formats or execution routes; change one existing rewrite policy. Preserve
first-match/NULL behavior and ordinary query admission. Qualify access-path and
execution-admission consequences rather than assuming representation changes
are performance-neutral. Canonical fingerprints and continuation signatures
can change where CASE remains compact; approval must explicitly cover that hard
cut, with no predecessor identity path. If approved, record the owner-local
outcome separately before resuming the rest of slice 5.

The alternative that preserves current ordinary canonical bytes is a
diagnostic-only conservative expansion admission pass. It is feasible in
principle, but must remain coupled to CASE construction rules, reject before
lowering, and separately establish formatting/candidate bounds. Prefer the
shared-owner rewrite budget for simplicity; neither option has been implemented.

### Disproved SQL constant-expansion hypothesis

A temporary probe attempted `name = REPLACE('x', 'x', 'xxxxxxxxxxxxxxxx')`,
then intended to nest that expression at most five times, with at most 1 MiB
of produced text. It failed on the first parse with typed `InvalidSyntax /
ExpectedToken { expected: Identifier, found: StringLiteral }`; no folding or
large allocation was reached. The current
[REPLACE parser](../../../crates/icydb-core/src/db/sql/parser/projection/functions.rs)
requires a field as its first operand. The generic evaluator's allocating
`text.replace` implementation therefore does **not** establish this SQL
construction vulnerability. Do not add scalar-evaluator limits on that evidence
or report the intended output sizes as measured results.

The probe was not retried and its temporary source was removed. The original
SQL predicate test file hash is restored:
`31dc45a260a32b1d75b03d5cf66dd10e459031bef3193598495009f40186525b`.
The focused canonical-normalizer selection in that compiled all-feature test
binary passes four tests, with one manual benchmark ignored. The failed probe
is an invalid workload assumption, not a production regression or a passing
diagnostic gate. No full suite, maintained lint rerun, Wasm/cycle measurement,
application change or network lifecycle action was needed. There are no net
Rust changes in this resumed preflight and no new performance claim.

### Recommended contract adjustment — not yet adopted

Bound **additional diagnostic projection and canonical rendering**, rather than
making this release prove an end-to-end bound on the shared planner. Planning
continues to use the normal query pipeline and its existing limits. This does
not establish complete allocation, work or stack safety for that pipeline.

Keep the following requirements unchanged:

- Typed input depth/size admission before conversion and safe rejected-input
  disposal remain slice 1 obligations. They are not proof of bounded downstream
  preparation or caller allocation.
- Current accepted authority, ordinary query admission/identity, execution-plan
  freshness/invalidation, and no result-row scanning remain mandatory.
- Shared logical projection remains one owner for SQL PLAN/JSON and the later
  typed terminal. No separate planner, compatibility flow or truncation policy.
- Admit diagnostic copies, labels, canonical output and relevant intermediate
  allocations before creating them. The returned DTO remains detached and the
  public canonical renderers keep their infallible `String` signatures.
- Charge repeated diagnostic work to the existing request; later detached
  formatting has a per-call bound, not an implicit new session lifecycle.
- Freeze and qualify the numeric projection/render limits and incremental cost
  gates before implementation. None is claimed satisfied by this scope review.

The alternative is to retain the stronger guarantee and explicitly fund
whole-preparation accounting: either construction-time checks at shared owners,
with ordinary-admission implications, or a diagnostic-only predictive admission
model tied to those owners' expansion rules. Neither is an implementation detail
to add without acknowledging the scope/maintenance cost. Prefer the narrower
feature contract; do not start another optimization prerequisite on generic
continuation.

No production changes or new limits were made in this review. Existing explain
tests are regression checks of the current surface, not qualification of the
unimplemented bounded feature. Release notes for the completed CASE slice remain
unchanged; this design-only review adds no new changelog entry.
