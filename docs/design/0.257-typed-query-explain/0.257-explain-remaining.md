### R5 maintenance authority and encoder sequencing

The user approved the split on 2026-09-10. The first landing implements explicit
maintenance construction ownership; the encoder landing remains open.

Contract and rationale:

- Need: shared encoding cannot rely on an active query tracker during schema
  maintenance. An optional ambient lookup would silently bypass bounds.
- Simplest owner: `MaintenanceConstructionBudget` beside the existing hard-budget
  tracker. Reuse `MUTATION_HARD_BUDGET` unchanged: 128 MiB temporary bytes,
  16,000,000 expression/nested-value steps, 30,000,000,000 instruction units and
  its existing 5,000,000,000-instruction failure reserve. Other resource ceilings
  remain those of that same profile, not a new maintenance configuration.
- Lifetime: one owner per unique-validation scan or migration validation,
  rewrite or final-validation page; migration programs within a page share it.
  Complete schema-index staging retains one owner across before/after projection,
  all observed rows and finish. No per-key or per-row counter reset.
- Failure: preserve the first typed exhaustion, reject later charges/segments
  and finalization, and return an error before the page result or staged
  replacement reaches publication. Soft page limits still yield as before.
  Hard exhaustion never becomes successful empty progress; an oversized item
  returns an explicit error on repeated attempts, not an internal retry loop.
  Earlier committed pages remain committed. No new persisted failure state or
  automatic retry behavior is introduced.
- State-space delta: one volatile existing tracker plus an optional fixed-size
  first-exhaustion record; no public mode, new resource, encoded discriminator,
  schema reconstruction, or thread-local fallback. It does not replace an active
  execution tracker. Ordinary write/request authority must still be propagated
  explicitly in the encoder landing; do not infer an active scope for every call.
- Qualification boundary: row visits, page source-byte visits, key derivation
  visits and instruction watermarks are charged now. Encoder scratch/output
  construction, numeric conversion and optional-predicate error propagation are
  NOT yet accounted. A post-key staged-output cap is still not an encoder bound.

The following preflight inventory explains why that ownership was required;
its descriptions of missing maintenance authority are historical findings.

The next codec change is not yet safe as mechanical signature propagation.
The following are current source findings, not observed production failures:

| Caller | Existing authority and missing contract |
| --- | --- |
| Query access lowering | `PreparationWork` already implements required `ConstructionBudget`; it can charge the shared encoder without another request lifetime. |
| Active execution | `ExecutionConstructionBudget` requires an active tracker and returns an invariant error when absent. `session/mutation_job.rs` installs a mutation scope for durable mutation advances; this does not establish one for every write, validation or migration caller. |
| Staged schema indexes | `StagedUserIndexDomainBudget` in `schema/mutation/user_index_domain.rs` counts source rows/bytes, row-index projection units and staged output. `derive_row` calls `PreparedUserIndex::derive_key` before charging the resulting key bytes; the key builder has no construction authority. Existing staged-byte accounting is not cumulative scratch accounting. |
| Constraint activation / migration | `UniqueConstraintProjection::derive_key` reaches the same rebuild key constructors. `constraint_activation_runner.rs::scan_unique_validation_page` has row/decoded/staged page limits, with staged bytes checked after key derivation. `migration_validation.rs` also carries page limits, not a codec construction authority. Neither key-derivation API accepts such authority. |
| Index predicates | `index/predicate/mod.rs::literal_index_component_bytes` calls `.ok()?` on encoding; `compile_index_program` and `compile_index_program_for_targets` return `Option`. Adding exhaustion to the encoder without changing this chain would turn resource failure into unavailable pushdown. |

Installing the strict execution adapter indiscriminately can reject legitimate
out-of-execution callers. Using the optional execution charger would leave them
unmetered. Charging scratch to staged-output bytes would silently change what
that existing limit means. None is an acceptable default implementation.

Approved sequencing:

1. Establish construction authority for the existing maintenance/validation
   operation lifetime. Inventory all write/rebuild callers, define the scratch
   and work allowance and its owner, and specify exhaustion versus page yield.
   Preserve progress/publication boundaries and prove that a single oversized
   row cannot produce an endless retry. Keep this private and volatile, with no
   new persisted format or public configuration. Any additional counters/limits
   require explicit design approval. Implemented using the existing mutation
   profile as described above, with no new numerical policy.
2. Land shared scalar encoding accounting with complete caller propagation:
   typed error preservation through predicate compilation, scalar/text/decimal/
   bigint construction checks, accepted enum encoding, and query/write/rebuild
   qualification. Retain one encoder and unchanged canonical bytes. Split further
   only if independently reviewable outcomes are identified and approved.

These boundaries stay within existing slice 11 / R5. The first is implemented;
the second remains the next implementation target. R5 and typed `.explain()` are
not complete, and no new minor is authorized.
