# Accepted query-type expansion preflight

Date: 2026-09-16. Scope: existing 0.257 R1/R4 accepted metadata construction.

Status: the follow-up below implements expansion admission. The original
preflight finding and decision against eager storage remain documented here.

## Original finding

Do not move all nested query-type construction into accepted-schema startup yet.
The current accepted catalog can encode shared references compactly, but query
projection expands those references into owned trees. A recursion-depth limit
does not bound the number of expanded nodes tightly enough.

The focused catalog test constructs a natural-number newtype, then eight newtypes
whose map key and value both refer to the preceding definition. The current
encoder and decoder accept all nine definitions in less than 1 KiB. Kind and
type projection agree, and the resulting type contains 511 nodes. Queryability
also agrees with the owned result. The test deliberately uses small fixtures;
it does not allocate a worst-case tree or measure runtime performance.

For this family, adding one definition doubles the prior expanded tree and adds
one map node: `nodes(n) = 2 * nodes(n - 1) + 1`, starting at one scalar node.
This is structural growth evidence, not a cycle/instruction estimate.

## Source boundaries

- `schema/composite_catalog.rs::matches_kind_at_depth` validates a composite
  reference by membership in the catalog; it does not charge its transitive
  expanded size. Every local definition can be small and valid.
- `schema/types/query_projection.rs::project_at_depth` recursively projects both
  map children into the selected output. Its depth limit is 64; reusing a
  definition on two branches is valid and is not a cycle.
- `SchemaInfo::from_snapshot` already materializes direct-field query metadata.
  `SchemaNestedFields::field_type` materializes nested types on demand. A root
  record remains opaque to query-type projection, so eagerly visiting all its
  nested leaves would newly perform work for previously unused nested types.
- `AcceptedSchemaEntityRuntime::compile` constructs `SchemaInfo` during accepted
  runtime setup. Moving work here is not request admission.
- Cache retained-byte admission runs after construction. It cannot bound memory
  already allocated while building a type.
- The queryability-only output avoids owned type trees but still shares the
  traversal. It does not solve expanded traversal work.

The executable evidence covers catalog encoding/decoding and projection, not a
full application schema installation or a demonstrated production failure.
The startup consequence is a source-backed reason to reject the proposed eager
optimization, not a claim that ordinary schemas currently fail startup.

## Preflight decision and next boundary

The eager shared nested-type prototype is not retained. Existing direct/nested
ownership and query behavior remain unchanged. No new cache mode, lazy cell,
budget counter or persisted state is introduced; state-space delta is zero.

Before reconsidering eager ownership, establish an expanded construction limit
at the canonical projection/accepted-schema boundary. Prefer an existing schema
resource policy where suitable; its exact limit and typed error propagation
still need qualification. Check kind, type and boolean outputs together so they
cannot disagree or silently turn exhaustion into whole-tree fallback.

Any construction check must act before oversized allocation and cover shared
acyclic references as well as depth/cycles. A global seen-set that simply skips
repeated definitions would change semantics. More retention accounting, moving
the work to startup, or adding per-consumer counters would not fix this boundary.

At preflight this prerequisite remained open under R1/R4; the follow-up below
closes the per-kind expansion gap, not the broader preparation audit.

## Implemented follow-up

Accepted bundle cross-component validation checks every root and nested field
with the shared projection traversal, producing no recursive output. All fields
in one entity share the existing 512-KiB schema-size ceiling, charged at a fixed
128 bytes per visited kind plus relation-label byte lengths. The fixed charge conservatively
covers either output's inline nodes and is identical on native and Wasm targets.
Repeated catalog references are charged on every expanded visit. Existing depth,
newtype resolution and early whole-tree fallback are unchanged.

An oversized candidate returns the existing typed store-unsupported error;
persisted reconstruction applies its existing store-corruption mapping. Resource
rejection is distinct from semantic fallback. Once a bundle becomes immutable
accepted authority, ordinary projection needs no new counter or error path.
The earlier eager-retention prototype remains unimplemented.

Tests cover exact node and relation-text limits, an exponential graph rejected
without constructing its output, fallback ordering, and direct/nested schema
candidate and persisted-reload boundaries. Small shared graphs still round-trip.
Cumulative coverage combines direct fields and nested leaves, checks continuation
after opaque-field fallback, admits 255 scalar fields and resets between entities.

Scope: this bounds cumulative projection visits/text for each entity, not
database-wide construction, allocator overhead or total IC instructions. Original unexpanded fallback is
still subject to existing source schema bounds. Pure-wrapper resolver scratch
and repeated catalog lookups remain at their existing owner; this is not a new
request budget or broader write/replay accounting. It does not retain expanded
nested metadata or introduce another schema representation.
