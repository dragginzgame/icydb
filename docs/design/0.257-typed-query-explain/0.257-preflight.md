## Outcome

The small typed terminal remains justified, but its current single-slice bounds
contract is not implementation-ready. The preflight makes two obligations
concrete: safe disposal of rejected recursive input, and construction/rendering
bounds that cover work already performed by shared planner helpers. Numerical
limits alone do not close either obligation.

Recommend requesting approval to separate shared bounded logical diagnostics
from the typed terminal. This is a proposed scope adjustment, not authorization
to redesign the planner or change public renderers. No new planned slice has
been added. The original diagnostic/ordinary-query isolation invariant remains.

The source findings do not establish an unbounded operation for every query,
nor do they prove a general planner rewrite is necessary. They identify missing
proof and one reproduced rejection-cleanup hazard. The current readiness verdict
is deliberately narrower than either claim.

## Native rejected-input cleanup probe

Evidence directory: `/tmp/icydb-0257-preflight.w1NZ5O` (temporary, not a durable
project dependency). Source: `rejection_drop.rs`, SHA-256
`1eba1fcc281e95882bab7d1f3784b2d9737927d191cb63af0ff6b906a2dd37c5`.
The probe links the freshly built SQL-free IcyDB library and uses its real
public `FilterExpr`, not a substitute tree type.

Method:

1. Spawn a native thread with an explicit 64-KiB stack.
2. Construct nested `FilterExpr::Not(Box<FilterExpr>)` iteratively, with a
   `Constant(true)` leaf, so construction itself is not recursive.
3. Borrow the tree and stop validation at the 65th node, rejecting a prospective
   64-node ceiling. These numbers are probe parameters, not proposed API limits.
4. Compare normal owned destruction with a unary-only iterative cleanup control.

| Shape and cleanup | Result |
| --- | --- |
| Depth 16; normal drop | 16 nodes visited, not rejected, cleanup completed; exit 0. |
| Depth 8,192; normal drop after bounded rejection | 65 nodes visited, rejected; thread stack overflow and process abort, exit 134. |
| Depth 8,192; iterative unary cleanup after the same rejection | 65 nodes visited, rejected, cleanup completed; exit 0. |

Only the isolated probe process aborted. Core dumps were disabled. No canister,
database or network was involved. The failing case was not repeatedly rerun.
The optimized native build is not a Wasm stack or IC instruction measurement.
No `.explain()` implementation exists yet; this reproduces a property of its
prospective owned input/rejection boundary, not a bug in a shipped terminal.

The decisive control uses this operation on the same owned value:

```rust
while let FilterExpr::Not(child) = filter {
    filter = *child;
}
```

That is evidence only for the unary probe, not a production repair. A real
disposal policy must cover branching filters and nested values and account for
work proportional to rejected input. Iterative drop is stack-safe for this
shape but is not constant-work rejection. Leaking rejected input, skipping
destruction or substituting dummy query models are not acceptable fixes.
Changing to a borrowed terminal would move ownership responsibility, not make
eventual caller/temporary destruction inherently safe; do not silently change
the consuming API as a substitute for a stated safety contract.

## Proposed scope decision

Keep the small public API and existing detached `String` renderers. Approve a
revised two-outcome plan only if the following separation is useful:

1. Shared bounded logical diagnostic construction, exercised end-to-end through
   the maintained SQL explain surface; exact canonical bytes and identity
   contracts preserved. Establish pre-allocation/intermediate-render bounds and
   numerical cost ceilings here. No general query-admission hardening is implied.
2. Typed `.explain()` with diagnostic-only input admission, explicit owned-input
   rejection/disposal contract, cursor/shape validation and SQL-free qualification,
   reusing the first outcome. Retain the no-result-row-execution proof.

Do not begin either under this proposal without scope approval. If no acceptable
rejection/expansion contract can be established without changing ordinary query
behavior or a general renderer rewrite, stop again and narrow/defer the feature.
This recommendation is about containing foundational work, not adding new modes
or accepting a second diagnostic implementation.
