# Physical allocation report qualification

The existing controller-only `icydb_snapshot` endpoint returns
`StorageReport::memory_allocations()`. The CLI snapshot command displays the
same canister-wide report before its database tables. No additional endpoint,
feature flag, allocator, cache or persisted state is introduced.
Canisters expose this through the existing
`icydb::endpoints! { icydb_snapshot; }` declaration.

The projection retains all 255 slots, including zero-size slots and allocated
slots whose current binding is unknown. The ledger is already in the totals.
Range claims describe current policy; they do not establish historical
ownership or grant permission to open a slot. An absent report means no default
runtime exists. Other collection failures reject the snapshot through the
existing internal store-error boundary.

The dependency owns manager validation and the fixed 34,848-byte metadata read.
Only the physical-allocation part is bounded this way; this work does not bound
the existing per-store snapshot scan or close the separate query-diagnostics
tracker. Regenerate consumers for the current Candid response. Database and
allocation-ledger formats remain unchanged.

Accounting checks:

- Physical bytes equal manager metadata plus assigned bucket bytes plus
  unmanaged residual bytes.
- Assigned bucket bytes equal virtual extent plus bucket slack, and also equal
  known-binding plus unknown-binding bytes.
- Payload occupancy is unavailable. Neither virtual extent nor bucket slack
  measures live application payload or reusable space inside a stable structure.

## Fresh bucket trial

The focused native fixture bootstraps an isolated runtime for each setting,
opens IcyDB data/index/schema/journal stores, then writes 2,048 raw rows to the
canonical data store with 1,024-byte row payloads. It includes the allocation ledger with the
shared core fixture's declarations. These are measured backing allocations,
not end-to-end transaction or IC performance measurements.

| Bucket pages | Empty physical bytes | Populated physical bytes | Populated virtual bytes | Populated bucket slack |
| ---: | ---: | ---: | ---: | ---: |
| 128 | 42,008,576 | 42,008,576 | 2,883,584 | 39,059,456 |
| 16 | 5,308,416 | 7,405,568 | 2,883,584 | 4,456,448 |

Both settings preserve Candid round trips and accounting identities. Collection
leaves backing bytes and committed generation unchanged. Reopening before
bootstrap preserves physical extent and reports application ownership as
unknown. An explicit mismatched setting returns typed `BucketSizeMismatch`
without changing the backing bytes.

The 16-page setting reduces this fixture's rounding allocation, but the shared
bucket table's capacity falls from 256 GiB to 32 GiB before platform/backing
limits. Buckets are not reclaimed when rows are deleted. This evidence does not
establish IC cycle/instruction costs or justify changing the production default.

To trial 16 pages in a fresh application, the existing bootstrap owner calls
`bootstrap_default_memory_manager_with_config(MemoryManagerConfig::new(16)?,
&policy)` before any IcyDB/default-runtime access, mapping the constructor error
into its normal error type. A host using IcyDB lifecycle participation does this
before invoking the participant. Ordinary reopen honors the persisted setting;
explicit configuration must match it. Existing 128-page deployments cannot be
shrunk with this call. Automatic slot placement and reclamation remain separate.

## Validation

Native accounting/Candid qualification, CLI rendering and the generated
controller-only endpoint's PocketIC checks passed. The endpoint exposes all
slots and leaves stable memory unchanged across repeated queries. A disposable
PocketIC instance was created for this qualification.

The matched `canister_test_sql` probe (Rust 1.98.1, `wasm-release`,
`candid-export`, SQL feature disabled) grows from 3,490,141 to 3,512,130 raw Wasm
bytes: +21,989 (+0.630%). This is the allocation-report/serialization addition
on top of the preceding dependency update, not a bucket-size comparison.
IC cycle and instruction deltas are unmeasured. Full-suite execution remains
user-owned.

This follow-up touches 16 files, approximately +650 net lines including tests
and documentation. Diagnostic DTOs and their projection add implementation
complexity; allocation ownership and production configuration remain unchanged.
