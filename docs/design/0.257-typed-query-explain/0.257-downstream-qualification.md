## 030: bounded native attribution

The Linux-only ignored fixture probe runs in separate processes with 1, 2 and
4 workers. Each worker owns an isolated thread-local database, reaches native
readiness, remains alive for the observation, then inserts/reads the same one
row and remains alive for a second observation. All runs pass. This is native
OOM attribution, not a performance benchmark; no wall-clock metric is used.

| Concurrent databases | Initialized process RSS, KiB | Aggregate backing bytes |
| --- | ---: | ---: |
| 1 | 506,368 | 511,770,624 |
| 2 | 1,005,056 | 1,023,541,248 |
| 4 | 2,004,480 | 2,047,082,496 |

Baseline RSS was 3,584 KiB per process. Each database reports exactly
511,770,624 physical backing bytes, 463,994,880 virtual bytes and 47,710,208
bucket slack bytes. Writing one row does not grow either extent. Manager
buckets are 8,388,608 bytes. These extents are capacities, not live payload.

Allocation attribution for one initialized database:

| Role | Virtual bytes | Allocated bucket bytes |
| --- | ---: | ---: |
| Ledger | 65,536 | 8,388,608 |
| Data | 65,536 | 8,388,608 |
| Index | 65,536 | 8,388,608 |
| Schema | 65,536 | 8,388,608 |
| Journal | 589,824 | 8,388,608 |
| Commit control, including schema checkpoint storage | 463,142,912 | 469,762,048 |

The additional 65,536 bytes are manager metadata. Source attribution:

1. `ic-memory 0.13.2` owns a thread-local default runtime. Native
   `ic-stable-structures 0.7.2` uses `VectorMemory`, whose growth resizes and
   zero-fills a dense `Vec<u8>`; each worker pays its own backing cost.
2. IcyDB's `schema/live_schema_checkpoint.rs` places a restricted checkpoint
   region at page 4096 (256 MiB) inside commit control. Growing that view also
   grows the gap below it; it is not sparse storage.
3. `LiveSchemaCheckpointBytes::BOUND` advertises a maximum over 22 MiB. The
   stable B-tree derives its allocation page from the maximum key/value node
   size when both are bounded. `LiveSchemaCheckpointStore::open` inserts a
   small header into that large-page tree even before checkpoint payload exists.
4. The same store also owns migration/lineage records. A journaled-only schema
   does not imply that this region remains unused. Reducing memory-manager
   buckets would address slack, not the dominant virtual extent.

This establishes a concrete IcyDB allocation mechanism and concurrency
amplification. It does **not** account for every byte of Toko Miner's reported
27,440,640-KiB OOM, prove a release regression, or establish a leak. That exact
application needs its own allocation trace; it was not modified or run here.

## Follow-up boundary

Keep application native test concurrency bounded as an operational mitigation.
The next storage correction should separate encoded-record admission limits
from B-tree page sizing and inspect the fixed-gap control layout. Prove behavior
for journaled stores, live-only checkpoints, migration/lineage and recovery
before changing it. Do not disguise the cost with a native-only storage policy,
change production limits, or add a second persisted format in this integration
slice. Existing stored allocation cannot be reclaimed merely by smaller defaults.

Full workspace tests and publication remain user-owned. The existing explain
instruction ceiling and ordinary-read control qualification remain separate.

## Authorized hard cut: one compact schema-control tree

The user authorized database recreation before 1.0. This landing slice removes
the fixed partition entirely: one physical variable-page tree follows the
existing 257-page bounded marker reservation. The 33-byte key is a fixed family
prefix followed by the existing 32-byte owner key. Application and checkpoint
namespaces share one checksummed `ICYSCMAP` version-1 header; lineage and
migration retain their checkpoint-owned keys and codecs. The current database
boot identity is `ICYDBCTL`, version 1. This is an **internal pre-1.0 hard cut**:
recreate databases; no prior decoder, conversion, fallback or automatic memory
reclamation is provided. No application or existing database was changed.

Two namespace views may coexist. Each operation reloads the physical tree's
current root/allocator metadata, preventing interleaved writes from using stale
roots. Namespace counts walk bounded keys rather than adding persisted counters;
application retention materializes at most 64 keys, not every record payload.
These are explicit costs of sharing one owner, not new authority or caching.
Record limits, idempotence, retention and marker-owned compare/replace remain
at their existing semantic owners. No new memory-manager policy is introduced.
