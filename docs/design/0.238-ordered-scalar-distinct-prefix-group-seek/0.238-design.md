## Release Boundary

`v0.237.2` at `ea37811122eb706ec88fbb13f972b5d55229f92c` is the
published code baseline. The current 0.237.3 candidate adds the final SQL
measurement matrix and regression gates but no production database-runtime
change. It is the last authorized 0.237 candidate.

0.238 begins only with the bounded implementation described here. No 0.238
runtime code is part of the 0.237.3 candidate, and the active 0.238 release
ledger must not claim shipped behavior before that predecessor is published
and implementation lands.

## Objective

Replace complete upstream materialization for a narrowly proven ordered scalar
`DISTINCT` window with at most one accepted-index representative per requested
distinct group plus one lookahead representative.

For the initial cohort, the executor must:

- return the same projected values and order as the current route and SQLite;
- visit at most four physical user-index entries;
- perform at most four range refills and row-presence probes;
- perform no data-row gets;
- cost no more than 5,000,000 instructions at the frozen 2,048-row maximum
  fixtures; and
- add no public API, Candid, stable format, persisted state, cache, mutable
  owner, invalidation edge or schema authority.

The feature is a small covering-index primitive, not a general `DISTINCT`
rewrite.

## Measured Need

0.237 held the target data, query results, selected secondary-order family and
lifecycle constant. The existing adjacent DISTINCT owner uses bounded state,
but it receives its iterator only after scalar execution has fetched every
source row.

| Frozen query | Instructions | DISTINCT candidates | Data-row gets | Physical index entries | Range scans |
| --- | ---: | ---: | ---: | ---: | ---: |
| `age ASC LIMIT 1` | 92,605,670 | 129 | 2,048 | 2,048 | 33 |
| `age ASC LIMIT 3` | 93,144,415 | 385 | 2,048 | 2,048 | 33 |
| `age DESC LIMIT 3` | 92,261,973 | 1,793 | 2,048 | 2,048 | 33 |
| `name ASC LIMIT 3` | 90,861,504 | 64 | 2,048 | 2,048 | 33 |

The corresponding non-`DISTINCT` `age ASC LIMIT 3` covering query costs
1,366,834 instructions, visits three index entries and performs no data-row
get. The absolute measured gap is 91,777,581 instructions. It is a removable
cost ceiling, not a candidate forecast.

A sequential adjacent stop is insufficient as the accepted design. It would
consume 385 candidates ascending but 1,793 descending in the same fixture. A
prefix-group seek makes work depend on the bounded output window instead of
duplicate population or direction.

## Non-Goals

0.238 does not authorize:

- aggregate `COUNT(DISTINCT ...)` optimization;
- expressions, expression indexes or computed ordering;
- nullable distinct fields or delayed NULL handling;
- composite distinct tuples or equality-prefix suffix projection;
- live/exhaustive cursors or continuation-format changes;
- residual predicates, intersections, prefix families or hybrid row fields;
- persisted distinct catalogues, background materialization or statistics;
- a general seek method on every ordered key stream;
- a planner configuration option or user-visible execution mode; or
- weakening an instruction, physical-work, corruption, Wasm or compatibility
  gate after measurement.

## Singular Admission Authority

Admission is decided once during canonical prepared-plan construction and
carried in one immutable execution contract. The executor may validate the
contract's internal invariants, but it may not reconstruct eligibility from
projection fields, SQL syntax, generated models or observed index shape.

The current `projection_distinct_strategy` leading-equivalence decision must
move to, or be directly owned by, the query/prepared-plan layer. It must not be
copied into a second planner helper while the executor version remains live.
The maintained flow is:

```text
accepted EntityAuthority + logical projection/order/page + selected access
  -> canonical prepared-plan admission
  -> Option<OrderedDistinctGroupSeekPlan>
  -> covering executor consumes the contract
  -> existing adjacent DISTINCT accumulator finalizes equality/window/output
```

Conceptually:

```rust
struct OrderedDistinctGroupSeekPlan {
    direction: Direction,
    output_offset: usize,
    output_limit: usize,
    representative_limit: usize,
}
```

This pseudocode is illustrative. The maintained type must contain only facts
the executor needs and must bind directly to the already lowered single index
range. It must not carry schema authority, generated model metadata, a cache
key or a separately refreshable fingerprint.

`representative_limit` is exactly
`output_offset + output_limit + one_lookahead`, using checked arithmetic and
bounded by the constant below. The planner freezes it; the executor does not
recalculate it.

## Frozen Initial Admission

The initial route is admitted only when every condition below is true:

1. The query is a scalar load with `DISTINCT` and a finite authored limit.
2. `LIMIT + OFFSET` is at most
   `MAX_ORDERED_DISTINCT_GROUP_SEEK_OUTPUT_WINDOW`, whose initial value is
   exactly `3` and whose canonical owner is the prepared covering-plan module.
3. One additional lookahead group makes the maximum representative count
   exactly `4`. `LIMIT 0` returns without store access.
4. The complete projection is exactly one direct, non-nullable accepted field.
5. The field's admitted scalar kind is `Int32` or `Text`, the two measured
   0.237 cohorts. Other scalar kinds remain on the predecessor path until
   their normalization and ordering are separately proven.
6. The covering plan sources the field from component zero of one accepted
   user secondary index.
7. The selected access lowers to exactly one index range, and its physical
   order completely satisfies the resolved projection order in either ASC or
   DESC direction.
8. The current canonical leading-equivalence classifier proves
   `OrderedAdjacent`.
9. The row-presence policy is the fail-closed `MissingRowPolicy::Error`; ignore
   semantics remain on the predecessor route.
10. There is no nullable output, expression, residual expression, residual
   predicate, prefix family, intersection, post-access sort, hybrid row field,
   primary-store route, cursor, continuation progress or page-work envelope.

Oversized and incompatible requests decline contract construction before any
store access. They use the exact predecessor route and retain its physical-work
and error behavior. Increasing the value `3`, admitting another scalar kind or
adding another access shape is outside 0.238.0 and requires new evidence and a
separately accepted design.

## Exact Physical-Work Definition

For this design, a **physical index entry visited** means one actual user-index
`RawIndexStoreKey` and `IndexEntryValue` pair delivered to an index-range scan
visitor or decoded into a covering component row. The count includes:

- emitted group representatives;
- the lookahead representative;
- malformed entries delivered before a typed failure; and
- any entry read speculatively or buffered and later discarded.

Constructing a synthetic low/high prefix boundary does not itself count as an
entry visit because no stored user entry was delivered. Internal stable B-tree
node traversal is captured by the instruction gate, not hidden in the entry
metric.

Source inspection shows that the existing diagnostic
`index_store_entry_reads` counter already measures entries delivered through
the common and journal-overlay visitors, but the raw heap-range visitor calls
its consumer directly and does not increment that counter. Patch 1 must make
the store-owned counter cover every entry delivered by the new raw-range path
and prove parity for heap and journaled backings. That repaired
`index_store_entry_reads` remains the one canonical measurement; the
implementation may not introduce a second executor-local approximation.

For the maximum admitted window, all successful executions must prove:

| Metric | Hard maximum |
| --- | ---: |
| Physical user-index entries visited | 4 |
| Index range scan/refill calls | 4 |
| Authoritative row-presence probes | 4 |
| Data-row gets | 0 |
| DISTINCT representatives offered to finalization | 4 |

The admitted fail-closed row policy returns on the first missing
representative. Ignore-policy reads retain the predecessor route, preventing a
missing duplicate from turning the four-entry maximum into a semantic budget.

## Group-Seek Execution

The consumer performs these phases:

1. Receive the immutable admitted contract and its already selected/lowered
   single index range.
2. Open the existing covering component stream with a one-entry refill. A
   larger refill would physically read duplicates only to discard them and
   would violate the entry contract.
3. Pull one raw entry, validate its raw key and witness, apply the existing
   fail-closed authoritative row-presence policy, and decode the projected
   component using the accepted covering codec.
4. Offer that representative to the existing adjacent DISTINCT accumulator.
   The accumulator remains the sole owner of canonical projected equality,
   offset/limit, lookahead, output and DISTINCT diagnostics.
5. Decode the retained one-entry raw anchor and verify its component agrees
   with the covering payload.
6. Ask the canonical index codec for the exact raw low/high bounds of that
   encoded component through `raw_keys_for_component_prefix_with_kind`.
7. For ASC, resume strictly after the group high boundary. For DESC, resume
   strictly before the group low boundary. Validate the synthetic anchor
   against the original lowered scan envelope; reaching the envelope edge
   means exhaustion.
8. Clear the one-entry buffer and repeat until the planner-frozen
   representative limit, semantic exhaustion or typed error.

The implementation must reuse canonical raw prefix framing, directional
continuation comparison, envelope validation, accepted covering decode and
row-presence ownership. It must not calculate byte successors, infer index
arity from generated models, retain a stable-store borrow across a row probe,
or fall back after the first entry has been visited.

## Equality, NULL And Direction Proof

Prefix skipping is safe only if one physical component group is exactly one
projected SQL DISTINCT group for admitted kinds.

For `Int32` and `Text`, focused tests must prove both directions of the
equivalence:

```text
projected SQL values compare equal
  iff
canonical accepted-index component bytes compare equal
```

The proof includes negative/zero/positive integers, minimum/maximum encoded
edges, empty and non-empty text, embedded zero bytes, escaped bytes, Unicode,
and case-distinct text. No executor-local normalization is permitted.

Nullable fields remain excluded, but exclusion itself needs proof:

- a nullable direct field never produces the immutable seek contract;
- NULLS-first and NULLS-last queries retain the predecessor route;
- a nullable expression and an expression order retain `GlobalReplay`; and
- no NULL sentinel is accepted as a physical group boundary in the new lane.

ASC and DESC tests must prove that exact group low/high sentinels exclude all
duplicates of the current value and neither skip nor repeat the adjacent
value. The proof covers first/last index groups, inclusive/exclusive outer
bounds, empty ranges, one group, exactly full output, lookahead, and physical
chunk edges.

## Corruption And Fallback

Every physically visited entry must validate before it affects output. A bad
raw key, invalid witness, missing representative, covering-component mismatch,
impossible group bound, escaped anchor or borrow conflict returns the existing
typed error taxonomy. It is never converted into “not admitted” after
execution begins.

Entries skipped by a proven exact prefix bound are not physically visited.
This matches the existing finite-window rule: a query is not an integrity scan
of an unrequested suffix. The release proof must nevertheless corrupt the
actual boundary representative in both directions so the new route cannot
hide accessed corruption.

Planner rejection is the only fallback boundary. Every incompatible or
oversized case proves, before store access, that the predecessor route and its
physical counters remain unchanged.

## Hostile Distribution Matrix

The accepted implementation must use deterministic 2,048-row fixtures that
place duplicate groups adversarially rather than measuring one favourable
ordering.

| Distribution | Required query interactions | Required conclusion |
| --- | --- | --- |
| First groups near low edge | ASC and DESC | both directions remain at most four entries |
| First groups near high edge | ASC and DESC | both directions remain at most four entries |
| One enormous duplicate group | enormous group first and last | cost does not scale with duplicate population |
| Mostly unique values | ASC and DESC, maximum admitted window | group seek remains below 5M; oversized control falls back |
| Non-zero offset | `OFFSET 1 LIMIT 2` in both directions | offset plus limit plus lookahead is at most four representatives |
| Exact end of index | fewer than requested groups and exactly three groups | exhaustion is exact without an invented lookahead |
| Corrupt boundary | first/current representative in both directions | same typed corruption; no fallback |

Results and order must equal SQLite. Physical entry, refill, presence-probe,
row-get, route and DISTINCT-candidate counters are asserted independently of
the instruction total.

## Frozen Performance Gates

At the maximum 2,048-row shape, each of the four original 0.237 direct-field
queries and each admitted hostile-distribution counterpart must satisfy all of
these gates:

- total instructions `<= 5,000,000`;
- physical user-index entries `<= 4`;
- range scan/refill calls `<= 4`;
- authoritative row-presence probes `<= 4`;
- data-row gets `== 0`;
- exact result and order equality;
- predecessor saving `>= 75,000,000` instructions for each original frozen
  query; and
- true-warm execution retains a compiled-command hit and the same physical
  maximum.

The 5M ceiling is a release gate, not a forecast. A candidate at 5,000,001
instructions fails. No ceiling may be raised, distribution removed, fixture
redefined, route renamed or physical metric weakened within 0.238 because the
implementation “still looks fast.” Stop, preserve the measurements and return
to design review.

Mostly-unique data is the crossover control. If four deliberate B-tree seeks
miss the frozen instruction gate or cause another admitted query to regress,
the candidate returns to design review. The executor may not choose
dynamically after reading, and 0.238 may not remove that hostile fixture.

## Cross-Query No-Regression Proof

0.238 must run the existing six shipped 0.237 optimization proofs with their
exact physical assertions and approximately one-percent CI ceilings. It must
also retain the 0.237 DISTINCT controls:

- nullable `CASE` global replay;
- expression order global replay;
- direct adjacent candidate accounting on an oversized fallback;
- non-`DISTINCT` covering finite windows;
- unbounded direct projection; and
- accepted-index missing-row corruption.

An intentional change to a 0.237 performance ceiling is outside this design.
This prevents a DISTINCT win from restoring work in count, extrema, compound
range, checked-hybrid, secondary-limit or prefix-cardinality families.
