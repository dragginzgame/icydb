## Decision Summary

IcyDB will support database-owned monotonically increasing identities on its
existing exact unsigned integer field kinds:

- Nat8 / u8;
- Nat16 / u16;
- Nat32 / u32;
- Nat64 / u64; and
- Nat128 / u128.

This is an insert-generation policy, not a new scalar type. IcyDB will not add
Serial8, Serial16, Serial32, Serial64, or Serial128 field kinds. A field remains
an exact Nat field in accepted schema and remains the corresponding Rust
integer in generated APIs. The accepted write policy separately states that
the database owns identity generation.

The proposed generated-schema spelling is:

~~~rust
field(
    name = "id",
    value(item(prim = "Nat64")),
    generated(insert = "Identity::next")
)
~~~

The accepted representation remains an enum:

~~~rust
enum FieldInsertGeneration {
    Ulid,
    Timestamp,
    Identity,
}
~~~

There will not be an auto_increment boolean. IcyDB already has multiple
mutually exclusive insert-generation semantics, so an enum is the exact model
and keeps schema, codec, diagnostics, and execution exhaustive.

Version 1 identity generation is deliberately narrow:

- the field is the sole primary-key field;
- the field is one non-null scalar Nat8, Nat16, Nat32, Nat64, or Nat128;
- generation starts at one and advances by one;
- the generator is GENERATED ALWAYS: ordinary callers cannot author or
  override the value;
- committed values are never reused after deletion;
- a rejected operation does not consume an identity;
- one atomic statement allocates deterministic consecutive values per
  identity owner;
- overflow fails before the commit marker with a typed exhaustion error; and
- identity state advances atomically with the rows that receive the values.

Nat64 is the recommended default. Nat8 and Nat16 are appropriate only for
deliberately bounded catalogs whose lifetime allocation limit is understood.
Nat32 is a compact domain choice, Nat64 is the normal local database identity,
and Nat128 is available when the domain contract genuinely requires it.

Narrower accepted kinds do not currently imply narrower physical storage.
Nat8, Nat16, Nat32, and Nat64 all use the Nat64 runtime value and scalar codec,
with accepted-schema range checks providing their exact semantics. Any future
compact integer codec is a separate persisted-format design applying to Nat
fields generally, not a side effect of identity generation.

### Non-Negotiable Invariants

1. Accepted schema is the sole runtime authority for whether a field is an
   identity.
2. Identity is an insert-generation enum variant, never inferred from a field
   name, Rust integer type, primary-key position, or missing value.
3. Identity generation does not introduce a Serial scalar kind or wrapper
   codec.
4. The accepted field kind remains exact and determines the maximum admitted
   identity.
5. Version 1 permits identity only on the required sole primary key.
6. The first generated identity is one, the step is one, and cycling is never
   allowed.
7. Ordinary create, insert, save, update, replace, and structural write lanes
   cannot author an identity value.
8. Identity generation occurs only for a new logical row. Updates,
   replacements of an existing row, deletes, index rebuilds, integrity scans,
   recovery, and reads never allocate.
9. Rejected accepted-schema admission, durable constraints, resource
   admission, relation or index preflight, or commit preparation does not
   consume an identity. Application operations execute before database entry.
10. Guarded mutation execution performs no `await`, yield, or re-entrant call
    between recovered-state inspection and marker publication.
11. Marker publication revalidates every participating identity owner's
    expected high-water and publishes no marker unless the complete comparison
    set succeeds.
12. A durable marker makes row publication and identity-state publication one
    atomic recovery fact.
13. A committed identity is never made available again by row deletion,
    rollback of an uncommitted attempt, schema reconciliation, or index
    rebuild.
14. One statement reads identity state once per participating identity owner
    and commits at most one contiguous range advance per owner.
15. Allocation order is deterministic and follows the admitted row-intent
    order.
16. Durable high-water state uses one canonical u128 representation for every
    supported unsigned field width.
17. Converting the canonical high-water value to the accepted field kind is
    checked before row construction.
18. A published identity declaration has an explicit zero-state control
    record. Missing state after publication is corruption, not an implicit
    zero.
19. Recovery replays admitted row bytes and identity advances; it never calls
    the generator again or derives state from MAX(id).
20. Active and retired identity-state records are retained for the database
    incarnation, and their accepted `(EntityTag, FieldId)` owner IDs are never
    reused.
21. Every range is bound to its exact marker, journal batch, journal sequence,
    and record ordinal. Numeric equality alone never proves idempotent replay.
22. Committed high-water includes marker-authorized work; materialized
    high-water is only its live control-state projection.
23. Accepted policy drift to or from identity is rejected unless an explicit
    catalog-native migration is designed and executed.
24. Persisted state and journal decoding are bounded, fallible, checksummed
    where required, and current-form only.
25. No compatibility alias for the experimental Sequence::next spelling or
    Sequence enum variant is retained before 1.0.0.
26. SQL, typed, and structural mutation lanes lower to the same accepted
    identity owner.

## Normative Contract

The maintained contract is:

> An unsigned identity field is an exact accepted Nat field whose accepted
> insert-generation policy assigns the next store-local, entity-local value
> when and only when a new logical row is admitted. The generator's operational
> high-water state commits atomically with those rows and is never reconstructed
> from generated Rust models or current row contents.

The authorship rule is:

> Identity means GENERATED ALWAYS. Omission or explicit SQL DEFAULT requests
> the accepted generator. Supplying a numeric value through an ordinary write
> lane is an authorship violation even when that value equals the next
> available identity.

The durability rule is:

> A rejected operation consumes no identity. Once an operation's durable
> commit marker is published, recovery must complete both its rows and its
> identity range. A later deletion does not rewind the range.

The admission rule is:

> Guarded recovery leaves identity control state quiescent before mutation
> planning. From the first state read through marker publication the current
> synchronous mutation path may not await, yield, or re-enter. Immediately
> before publication, IcyDB revalidates the complete expected-high-water set
> and publishes the marker only if every owner still matches. A stale
> comparison publishes no row, range, or marker and returns a typed conflict;
> version 1 does not retry invisibly.

The negative contract is:

> IcyDB does not promise dense visible IDs, global uniqueness across entities
> or databases, secrecy, smaller physical encoding for narrower Nat kinds,
> caller-selected sequence values, or compatibility with SQLite rowid
> behavior.

## Problem Statement

### 1. Serial Types Conflate Value Kind With Generation Policy

A u64 field and a database-generated u64 identity have the same value domain,
comparison, index, relation, and wire semantics. Their difference is
authorship at insertion and the operational state needed to choose a value.

Adding Serial64 as a scalar kind would duplicate the Nat64 codec and leak a
write policy into every type consumer. It would also require five Serial kinds
for width flexibility.

### 2. A Boolean Cannot Represent Existing Generator Semantics

IcyDB already supports distinct insert generators for ULID and Timestamp. An
auto_increment boolean would either sit beside that enum with invalid
combinations or become a second source of generator authority.

One exhaustive FieldInsertGeneration enum is simpler and makes unsupported
combinations unrepresentable.

### 3. Auto-Increment Is Durable State, Not A Number Helper

Choosing current + 1 is the smallest part of the feature. The high-water mark
must agree with row commits through interruption, journal publication, replay,
fold, batch rejection, retained-state lifecycle, and schema transition.

Updating the row and identity state independently can either expose a row
without advancing state or advance state without the row. Deriving from live
rows can reuse deleted IDs. Both violate the contract.

### 4. Width Generality Needs One Canonical State Model

Separate u8, u16, u32, u64, and u128 state codecs would multiply persisted
formats and branch recovery by schema width. A canonical u128 high-water value
can represent every admitted domain, while accepted field kind supplies the
exact upper bound and runtime value conversion.

### 5. Narrower Domains Are Not Automatically Smaller Encodings

Today Nat8, Nat16, Nat32, and Nat64 share a fixed-width Nat64 scalar encoding.
Allowing identity generation for those exact kinds is useful for domain
contracts, API types, overflow testing, and deliberate capacity limits. It is
not evidence of a persisted-byte saving.

### 6. Insert-Shaped Work Is Not Always A Logical Insert

Recovery and integrity code may project an existing row into empty derived
index state using a before-absent/after-present shape. That shape must not
trigger identity allocation or demand an identity advance.

The commit path needs explicit logical mutation intent. Identity correctness
must never depend only on optional before/after bytes.

### 7. Tentative Allocation Needs Stale-Range Exclusion

Two statement cursors that both observe high-water 100 would both propose 101
without an admission proof. The current Internet Computer mutation contract is
synchronous and serialized, but the design must make that premise structural:
no interleaving is permitted before marker publication, and publication must
revalidate the complete expected-high-water set before making any marker
durable.

### 8. Retired State Is Allocation History

An identity control record remains authoritative after its entity or field is
removed. Losing that record, reusing its accepted owner IDs, or omitting it
from integrity enumeration could restart a previously consumed domain. Active
and retired records therefore share one bounded durable inventory.

## Goals

1. Support exact generated identities for all bounded unsigned primitive
   integer kinds already owned by IcyDB.
2. Preserve one scalar-kind system and one insert-generation enum.
3. Make Nat64 the documented default without artificially forbidding other
   exact domains.
4. Bind identity allocation to accepted schema, final after-image validation,
   and the durable commit marker.
5. Keep rejected writes free of identity consumption.
6. Aggregate batch allocation into one range advance per identity owner.
7. Make stale-range exclusion, recovery, and integrity checking explicit.
8. Provide stable typed diagnostics for authorship, exhaustion, state
   corruption, and migration incompatibility.
9. Keep the implementation bounded in rows, bytes, instructions, and stable
   control-state growth.
10. Preserve all active and retired allocation history for one database
    incarnation.

## Non-Goals

0.214 does not add:

- new Serial scalar types;
- signed or arbitrary-precision identities;
- identities on non-primary-key fields;
- identities on composite primary keys;
- multiple identity fields per entity;
- caller-selected start values or increments;
- cycling, caching, reseeding, setval, or session-local sequence functions;
- GENERATED BY DEFAULT or an ordinary override escape hatch;
- a last_insert_rowid-style session global;
- global uniqueness across stores, canisters, replicas, or applications;
- gapless visible row numbering;
- implicit conversion of existing Nat or ULID primary keys;
- MAX(id) reconstruction;
- compact Nat codecs;
- an automatic Toko schema migration;
- SQL DDL syntax for creating or altering identity policy;
- a backup, restore, raw import, or general backfill product surface;
- multi-entity public transaction support; or
- a compatibility alias for the experimental Sequence name.

## Vocabulary

### Identity Field

The sole non-null unsigned primary-key field whose accepted insert-generation
policy is Identity.

### Identity Domain

The exact accepted Nat8, Nat16, Nat32, Nat64, or Nat128 range of an identity
field.

### Identity Owner

One immutable `(database incarnation, EntityTag, FieldId)` tuple inside the
identity owner's physical store namespace. Current source names and row slots
are resolved metadata and are not durable control-state identity.

### Committed High-Water

The greatest identity whose allocation is durably committed, including values
whose rows were later deleted. A published marker contributes to committed
high-water even before its control-state projection is materialized.

### Materialized High-Water

The value currently written in the identity control record. Guarded recovery
must make it equal committed high-water and clear the authoritative pending
marker before any new mutation reads it.

### Identity Range

One contiguous statement allocation represented as exclusive previous
high-water and inclusive new high-water values.

### Pre-Key Insert Candidate

One engine-neutral accepted insert intent containing immutable entity
identity, exact authored/omitted/`DEFAULT` field intents, and a stable `u32`
input ordinal, but no caller-authored storage key. Identity resolution produces
the primary key, complete row, and `DataKey`.

### Logical Insert

A mutation that creates a row for a previously absent primary key under
ordinary accepted write semantics.

### Derived Projection

Index, relation, diagnostic, or recovery work computed from an already
authoritative row. It may look insert-shaped to a derived store but is not a
logical row insertion.

### GENERATED ALWAYS

The identity field is database-authored on logical insert and cannot be
assigned through ordinary caller write intent.

## Exact Domain Guidance

| Rust / accepted kind | Maximum committed allocations | Guidance |
|---|---:|---|
| u8 / Nat8 | 255 | Tiny immutable or deliberately bounded catalogs; exhaustion tests |
| u16 / Nat16 | 65,535 | Small bounded catalogs with a proven lifetime ceiling |
| u32 / Nat32 | 4,294,967,295 | Explicit 32-bit domain or interoperability requirement |
| u64 / Nat64 | 18,446,744,073,709,551,615 | Recommended general-purpose IcyDB local identity |
| u128 / Nat128 | 2^128 - 1 | Exceptional domains needing a 128-bit sequential key |

The capacity is lifetime committed allocation, not current row count. Deleting
rows does not restore capacity.

Nat8 and Nat16 are supported because exact field kinds should compose
consistently, not because they are safe defaults. Documentation and
introspection must expose the exact domain and exhaustion state. IcyDB should
not emit a noisy runtime warning on every insert.

## Public Schema Surface

The generated DSL uses one spelling for every width:

~~~rust
field(
    name = "id",
    value(item(prim = "Nat32")),
    generated(insert = "Identity::next")
)
~~~

Identity::next is a well-known declarative generator token. Runtime database
authority is the accepted FieldInsertGeneration::Identity enum value, not a
function pointer or an arbitrary Rust callback.

Schema validation requires:

1. exactly one primary-key field;
2. the identity field is that field;
3. the field is non-null and single-valued;
4. the primitive is Nat8, Nat16, Nat32, Nat64, or Nat128;
5. no database default;
6. no other insert generator;
7. no engine-managed write policy.

Generated adapter validation separately requires that the typed insert input
omit the identity field. This is a `TypedWriteAdapter`/code-generation
contract, not an accepted-schema shape property. Regardless of frontend, the
database still rejects an authored value for an accepted identity field.

An ordinary unsigned primary key without the generator remains caller-authored:

~~~rust
field(name = "external_id", value(item(prim = "Nat64")))
~~~

That is the correct model for imported protocol numbers, externally allocated
IDs, or values whose exact numeric identity belongs to the application.

## Accepted Authority Model

Accepted field write policy owns:

~~~rust
enum FieldInsertGeneration {
    Ulid,
    Timestamp,
    Identity,
}
~~~

The Identity variant carries no width payload. Duplicating the field kind
inside the generator would permit drift such as Identity(Nat32) on a Nat64
field. The accepted field kind is the sole width authority.

Accepted schema integrity verifies the full eligibility rule whenever a
snapshot is decoded, published, selected, or checked. Generated EntityModel
may propose the policy during reconciliation, but runtime allocation never
falls back to generated metadata.

The accepted schema fingerprint includes the Identity variant. Operational
high-water state does not enter that fingerprint because it changes on every
committed insertion. Schema provenance does not change runtime ownership:
generated proposals and any future SQL DDL both submit policy, while the
accepted database owns generation.

## Operational State

Each identity owns one stable control record whose logical identity is:

~~~text
(DatabaseIncarnationId, EntityTag, FieldId)
~~~

Store ownership is proven by placement in that store's dedicated stable control
namespace; ordinary schema evolution cannot rebind an identity-bearing entity
to another store. Every record envelope additionally binds the durable
`DatabaseIncarnationId`, so copying bytes between databases fails closed.
Accepted IDs survive an explicit 0.218 rename while current names and row slots
may change. `EntityTag` and `FieldId` are therefore the persisted owner key,
not cached projections of an authored name.

Conceptually:

~~~rust
enum IdentityStateLifecycle {
    Active,
    Retired,
}

struct IdentityState {
    database_incarnation: DatabaseIncarnationId,
    entity_source: EntitySourceKey,
    field_source: FieldSourceKey,
    accepted_kind: AcceptedFieldKind,
    lifecycle: IdentityStateLifecycle,
    materialized_high_water: u128,
    last_applied_advance: Option<IdentityAdvanceId>,
}
~~~

The persisted record owns:

- a dedicated key namespace;
- fixed magic;
- one current format version;
- the exact bounded owner identities and accepted Nat kind;
- active or retired lifecycle;
- a fixed-width big-endian u128 high-water value;
- the exact last-applied marker/batch/sequence/record identity; and
- a checksum over the current-form payload.

The state is operational control data, not accepted catalog data. It can live
in SchemaStore's control namespace without becoming part of accepted schema
fingerprints or snapshot replacement.

### Publication And Absence

Publishing a new identity declaration atomically creates a zero high-water
record. Once accepted schema declares Identity, a missing record is corruption.
The runtime must not use unwrap_or(0) for an already published declaration.

This distinction matters after all rows have been deleted: live rows cannot
prove whether identities were previously committed. The control record is the
only no-reuse authority.

Identity control records survive ordinary accepted-snapshot replacement. When
an identity declaration is removed through an otherwise valid empty-entity
transition, the same marker atomically changes its record from `Active` to
`Retired`; it does not delete the record. Version 1 never garbage-collects a
retired record and never reuses its accepted `(EntityTag, FieldId)` owner
within the same database incarnation.

The combined active-and-retired inventory is capped at
`MAX_IDENTITY_STATE_RECORDS_PER_DATABASE = 65_536`. Publication of a new
identity owner rejects with typed resource exhaustion at that lifetime cap.
Full destructive store recreation mints a new `DatabaseIncarnationId` and is
the only version-1 operation that resets the inventory.

### Canonical Width

All states persist u128. Nat8 through Nat64 still emit Value::Nat64 after a
checked conversion; Nat128 emits Value::Nat128. One helper owns:

~~~text
u128 high-water
    -> checked next
    -> accepted-kind bounds check
    -> exact runtime Value
    -> primary-key and row-slot equality proof
~~~

The extra state bytes over a u64-only record are per identity field, not per
row, and avoid a second persisted state format when Nat128 is used.

## Allocation Semantics

### Start, Step, And Exhaustion

The initial high-water mark is zero. The first value is one. Each generated
value is the previous value plus one.

Before constructing a row, allocation checks:

1. u128 addition does not overflow;
2. the result is at most the accepted field kind's maximum;
3. conversion to Value::Nat64 or Value::Nat128 is exact; and
4. the same value is present in the row primary key and accepted field slot.

Failure returns IdentityExhausted before the marker. The high-water state and
all rows remain unchanged.

### Statement-Local Cursor

One statement-local cursor is created lazily per participating identity owner.
Guarded recovery first completes any marker-authorized advance, materializes
the committed value, and clears the marker. The cursor then reads that
quiescent materialized high-water once and allocates in admitted intent order.

The cursor mutates only statement-local memory. Durable state changes only
through the successful commit marker and its journal publication.

### Serialized Admission And Stale-Range Exclusion

The current runtime contract serializes canister update execution and permits
no `await`, yield, thread handoff, callback, or logical re-entry from guarded
recovery through marker publication. Identity allocation relies on this
existing single-message critical section; adding an asynchronous mutation path
would require a separate concurrency design.

Even under that contract, marker publication performs an explicit final
comparison:

1. the marker slot is still empty;
2. `DatabaseIncarnationId` still matches;
3. every participating identity record is active and well formed;
4. every materialized high-water equals its range's
   `expected_high_water`; and
5. the complete owner set matches the marker's prepared ranges exactly.

The checks and marker installation form one synchronous, non-reentrant
publication step. Multi-owner internal commit fixtures compare all owners
before writing anything; version 1 does not expose a new multi-entity public
transaction surface.

A stale comparison returns a typed `IdentityStateConflict`. It publishes no
marker, row, or range and consumes no identity. Version 1 leaves retry to the
caller rather than rerunning arbitrary application work invisibly.

### Deterministic Order

Within one entity:

- SQL multi-row INSERT follows VALUES order;
- typed batch creation follows input order;
- catalog-native atomic batches follow their stable admitted intent order; and
- retries against unchanged durable state produce the same candidate values.

No ordering is promised between independent identity owners because each has
its own state.

### Range Aggregation

Commit preparation aggregates all generated rows for one identity owner into:

~~~rust
struct IdentityRangeAdvance {
    owner: IdentityOwner,
    expected_high_water: u128,
    new_high_water: u128,
    allocation_count: u32,
}
~~~

The exact owner type may differ, but its invariants do not:

- `new_high_water - expected_high_water` equals
  `u128::from(allocation_count)`;
- `allocation_count` is persisted as corruption-detection redundancy,
  cross-checked on decode and apply, and is nonzero;
- one identity owner may allocate at most `u32::MAX` rows in one marker; all
  existing statement, byte, and 16 MiB marker bounds apply earlier and are
  normally much tighter;
- every allocated row has exactly one value in that range;
- values are contiguous and appear in deterministic intent order; and
- at most one range exists per identity owner in one commit window.

This is both smaller and easier to validate than one journal record per row.

The range record does not duplicate its journal envelope identity. Its
`IdentityAdvanceId` is the exact tuple of commit-marker ID, journal-batch ID,
journal sequence, and canonical record ordinal. Marker validation proves that
all rows receiving identities from the range are in the same bound batch and
that their owner, count, exact value set, and deterministic order match the
range before publication.

### Gap Semantics

Rejected operations do not consume values, but IcyDB does not advertise
gapless visible IDs:

- deleted rows leave gaps;
- an exact future data-movement artifact may retain a high-water mark greater
  than every live row;
- future explicit migrations may reserve a range; and
- current row count says nothing about remaining capacity.

Applications must not use identity arithmetic as a row-count or completeness
proof.

## Mutation Ingress

Every mutation ingress lowers to the existing engine-neutral accepted mutation
intent before identity handling. Application behavior and database admission
remain separate:

~~~text
optional caller-invoked application normalization/validation
    -> TypedWriteAdapter or SQL/structural frontend lowering
    -> AcceptedMutationIntentPatch
    -> pre-key accepted insert candidate
    -> accepted omission and DEFAULT resolution
    -> tentative database generators, including Identity
    -> complete structural after-image, primary key, and DataKey
    -> accepted exact-kind and durable constraint enforcement
    -> relation, index, and resource preflight
    -> stale-range comparison and marker publication
~~~

Application normalizers and validators are never callbacks from the database.
An application rejection occurs before database entry and naturally consumes
nothing. Once an engine-neutral request enters IcyDB, only accepted-schema
policy determines database validity.

### Pre-Key Insert Candidate

Identity-bearing insert preparation extends the current
`AcceptedMutationIntentPatch` owner rather than introducing a parallel row DTO.
Conceptually, each item carries:

~~~rust
struct AcceptedPreKeyInsert {
    entity: AcceptedEntityIdentity,
    fields: AcceptedMutationIntentPatch,
    input_ordinal: u32,
}
~~~

It has no caller-authored `DataKey`. Omission, explicit SQL `DEFAULT`, and
authored values remain distinct. The candidate count is checked into `u32`
before allocation. Accepted generation resolves the identity field, constructs
the full row and key, and only then enters ordinary final-after-image
enforcement. Update and replacement begin with an existing target key and
cannot enter this generation path.

### Typed Insert

The generated insert input omits the identity field.
`TypedWriteAdapter::encode_write` lowers only the caller's application values
and does not resolve database policy. Accepted insertion then allocates the
identity and follows the shared flow above.

The created entity returned to the caller contains the concrete integer ID.

### SQL INSERT

Both omission and explicit DEFAULT request identity generation:

~~~sql
INSERT INTO Event (payload) VALUES ('created') RETURNING id;
INSERT INTO Event (id, payload) VALUES (DEFAULT, 'created') RETURNING id;
~~~

An explicit numeric identity rejects:

~~~sql
INSERT INTO Event (id, payload) VALUES (42, 'created');
~~~

RETURNING is the supported way to obtain generated IDs. IcyDB does not add
last_insert_rowid(), a mutable connection register, or a session-global current
sequence value.

### Save, Replace, And Update

An existing entity carries its identity as row identity. Saving or replacing
that existing row preserves the value and allocates nothing.

A caller-authored full entity whose key is absent from storage cannot use save
as a backdoor insertion with a chosen identity. It rejects and directs the
caller to the insert surface.

UPDATE cannot assign, clear, default, or regenerate the identity field.

### Structural Writes

Ordinary structural insert and replace lanes obey the same authorship rules as
typed and SQL writes. A raw or structurally valid numeric value is not enough
to bypass accepted ownership.

Catalog migrations use separate explicit authority. Import and restore are not
supported product surfaces in 0.214. There is no boolean bypass on ordinary
structural mutation.

### Atomic Batches

The complete batch is preflighted before marker publication. If the final row
fails, no row and no identity range commits.

Successful batches commit all row effects and one range advance per identity
owner in the same marker. Returned rows preserve the input order and expose
their allocated IDs. The current public atomic batch remains single-entity;
0.214 does not add multi-entity transaction semantics.

### Derived Work

The current `CommitPrepareMode::{NormalWrite, RecoveryReplay,
DerivedRebuild}` is the sole preparation-mode owner. Identity generation occurs
only while resolving a pre-key insert in `NormalWrite`, before ordinary commit
preparation. `RecoveryReplay` consumes marker-authorized row/range bytes, while
`DerivedRebuild` projects existing authoritative rows; neither may allocate or
require a new identity advance. 0.214 does not add a second intent enum or a
private derived-projection boolean.

## Commit, Journal, And Recovery

### Commit Marker

The marker owns:

- admitted row before/after bytes;
- derived index and relation effects;
- accepted schema fingerprint binding; and
- the aggregated identity range advances.

Preparation proves all range and row associations before the marker is
written. Publication performs the all-owner stale-range comparison described
above, then installs the marker through the existing empty-slot guard. Applying
a marker with an identity mismatch is an internal invariant or corruption
failure, not a recoverable caller validation error.

### Journal Record

Journaled stores encode one current-form identity range record per identity
owner per commit window. The record carries immutable owner identity plus
expected/new u128 high-water values and the redundant `u32` allocation count.
Its containing `JournalBatch` supplies exact marker ID, batch ID, journal
sequence, and canonical record ordinal.

Heap stores use the same semantic owner without claiming durability beyond the
heap store's declared lifecycle.

### Apply Order

The marker is the atomic authority, so interruption may occur around physical
row, index, relation, and identity-state writes without changing the logical
outcome. Recovery either completes the exact committed marker or observes no
committed operation.

Immediately after marker publication, the range's `new_high_water` is committed
even if the live identity record still contains `expected_high_water`.
Therefore no new mutation may read identity state until guarded recovery has
applied the marker, materialized the committed value, verified journal fold,
and cleared the marker.

No public contract depends on whether the live identity projection is
physically updated immediately before or after the row projection. Guarded
entrypoints expose only the recovered quiescent state.

### Replay And Fold

Marker validation and replay require:

- exactly one range per identity owner;
- the exact owner and accepted-kind contract;
- exact set equality between marker rows and
  `expected_high_water + 1..=new_high_water`;
- no duplicate, missing, zero, or out-of-range row identity;
- primary-key/row-slot equality for every row;
- increasing identity assignment in stable per-owner input order; and
- a bound `IdentityAdvanceId` derived from the exact marker ID, journal-batch
  ID, journal sequence, and record ordinal.

First apply requires materialized high-water to equal
`expected_high_water`. Idempotent live replay may accept
`new_high_water` only when the record's `last_applied_advance` equals the exact
`IdentityAdvanceId`. Numeric equality alone is insufficient.

Canonical fold applies the same expected/new and advance-identity proof. It may
accept an already-folded value only when the canonical record identifies that
exact advance and the containing journal's fold watermark is before or at the
batch position being completed. Once the watermark has passed the batch,
normal recovery does not replay it. An older range presented after a later
advance has been materialized is corruption, never idempotence.

Any skip, rewind, owner mismatch, duplicate range, row/range divergence,
advance-identity mismatch, malformed count, or accepted-width mismatch is
store corruption.

Recovery never:

- calls Identity::next;
- scans for MAX(id);
- treats missing state as zero;
- allocates for index rebuild; or
- changes an admitted row's identity.

### Corruption Precedence

Identity-state contradictions are classified before generic key uniqueness:

- a generated candidate key already exists above recorded materialized
  high-water;
- any live identity is greater than effective committed high-water;
- an active declaration has no active state record;
- a retired owner collides with a newly published declaration;
- a record belongs to another database incarnation;
- marker rows do not form the exact declared range; or
- materialized value and last-applied advance disagree.

These fail as typed identity-state corruption. A generic duplicate-key
diagnostic must not hide a state record that has fallen behind its rows.

## Schema Transitions

### New Entity

A newly accepted entity may declare an identity. Catalog publication creates
its zero-state control record atomically with the declaration.

### Existing Entity

Version 1 rejects transitions that:

- add Identity to an existing field;
- remove Identity from an existing field;
- move Identity to a different field;
- change the identity field's exact Nat width;
- change the primary key between scalar and composite; or
- move an identity-bearing entity to another physical store; or
- reuse an active or retired identity owner's accepted `(EntityTag, FieldId)`.

These are migration operations, not metadata edits.

### Why MAX(id) Is Not A Migration

Seeding from the greatest live ID can reuse a larger ID whose row was deleted.
Even if no deletion is known, proving that fact requires durable history not
present in the live row set.

A future explicit adoption migration must require a caller-supplied authority
or a source control-state proof, validate every existing key, and publish the
chosen high-water mark with the accepted policy. 0.214 does not invent that
surface.

### Drop And Recreate

Dropping rows does not change identity state. Removing an empty identity-bearing
entity atomically marks its control record `Retired`; it does not delete it.
The active and retired record inventory is checked before every new
declaration, so no candidate can attach to a retired accepted owner.

A genuinely new identity domain requires fresh accepted entity and field IDs.
Reusing a current source name after explicit removal does not resurrect the
retired record: the new accepted IDs form a distinct domain. Full destructive
store recreation is the only version-1 operation that may discard retired
records, and it must mint a new `DatabaseIncarnationId`.

## External Data Movement And Backfills

### Unsupported Import And Restore Surfaces

IcyDB does not currently expose a supported backup, restore, or raw import
surface. 0.214 does not create one, and ordinary structural writes cannot be
used as an identity-authoring substitute.

Any future exact backup/restore design must preserve the complete
active-and-retired identity-state inventory, immutable owner identities,
database-incarnation rules, and last-applied advance evidence. It may never
infer high-water from live rows. A current-form artifact must be recovered and
quiescent before export: no pending commit marker, no unfolded journal batch,
and materialized high-water equal to committed high-water.

The current durability contract requires a restore or replacement lane to mint
a fresh `DatabaseIncarnationId`. A future exact restore must therefore
authenticate the source database identity and physical store mapping, then
atomically rebind every active and retired record to the newly issued
incarnation while preserving store placement, accepted entity/field owner IDs,
lifecycle, accepted Nat kind, high-water, and advance evidence. Partial
rebinding is corruption.

If a later design deliberately accepts an interrupted artifact, it must first
replay the exact marker and journal in an isolated restore authority and
validate against effective committed high-water. It cannot validate rows only
against the stale materialized record. Those requirements are future surface
preconditions, not 0.214 implementation or closeout obligations.

### Internal Backfills

Schema backfills do not regenerate existing identities. A backfill that creates
new logical rows is outside 0.214 unless it already enters the ordinary bounded
insert pipeline. Any future resumable partial row creation requires an explicit
design and idempotency key; it cannot reserve unbounded ranges in advance.

## Integrity Checking

### Quick Check

The bounded quick check verifies:

- every accepted identity declaration has exactly one current-form active
  state record;
- every control record is enumerated exactly once as active or retired;
- every retired record retains immutable owner identity and accepted Nat kind;
- no active declaration reuses a retired owner;
- the combined record count is at most 65,536;
- state magic, version, length, and checksum;
- database incarnation, physical store placement, and accepted entity/field
  owner IDs;
- u128 high-water within the accepted field domain;
- identity eligibility remains structurally valid; and
- no active marker or journal shape contradicts the declared state owner.

Quick runs after guarded recovery. A leftover authoritative marker must be
completed before the active/retired inventory is classified; raw materialized
state is not treated as committed authority while a marker is present.

### Deep Resumable Check

For each identity row, the deep scan verifies:

- storage key matches the row primary-key field;
- the value decodes under the exact accepted Nat kind;
- value is at least one;
- value is no greater than committed high-water;
- no duplicate primary key exists; and
- all ordinary row, index, relation, and constraint checks still pass.

At clean completion, the scanner proves maximum live identity is no greater
than high-water. It does not require equality.

The scan carries accepted schema identity, captured store revision, bounded
findings, and canonical primary-key continuation as defined by 0.212. A
concurrent revision change invalidates the proof rather than silently blessing
a mixed snapshot.

The checker never repairs, rewinds, or derives identity state.

## SQL DDL

The catalog-native concept maps to standard identity terminology:

~~~sql
id BIGINT GENERATED ALWAYS AS IDENTITY
~~~

SQL DDL creation and alteration of identity policy are explicitly deferred
from 0.214. The parser form above remains unsupported for this release. SQL
`INSERT`, `DEFAULT`, `RETURNING`, and schema introspection still consume
identity policy accepted from maintained schema proposals.

When SQL DDL identity authoring is designed later, SQL will be only a frontend
to this same accepted policy and operational-state publication. DDL provenance
will not create a second runtime generator owner.

Unsupported forms fail explicitly:

- GENERATED BY DEFAULT;
- custom START WITH;
- custom INCREMENT BY;
- MINVALUE or MAXVALUE overrides;
- CYCLE;
- CACHE;
- ALTER IDENTITY;
- RESTART or RESEED; and
- identity on an added non-primary-key column.

Accepted identity policy is introspectable through SQL but cannot be silently
removed or redefined by DDL.

## ULID Versus Unsigned Identity

Use an unsigned identity when:

- one IcyDB entity is the sole allocator;
- values are created through the database;
- small ordered numeric keys are useful;
- IDs need not be created offline or merged across independent databases; and
- enumeration is not a security concern.

Use ULID when:

- callers or multiple systems must allocate before reaching IcyDB;
- data may be merged across stores or canisters;
- a 128-bit globally unique value is part of an external contract;
- time-sortable decentralized allocation is valuable; or
- exposing a simple row count approximation through sequential public IDs is
  undesirable.

ULIDs are not authorization secrets. Numeric identities are not promised to
be physically smaller until the actual key and row codecs are measured.

## Post-Closeout Toko Evaluation

Toko is not an implementation slice, closeout requirement, or release gate for
0.214. It is a separate project after the IcyDB feature has closed, shipped,
and produced its own evidence.

The Toko audit will classify each entity:

1. keep ULID for externally visible, cross-system, preallocated, or mergeable
   identity;
2. consider Nat64 Identity for purely local database-owned rows;
3. use Nat32 or narrower only with a documented lifetime allocation ceiling;
4. retain caller-authored Nat fields for external protocol numbers; and
5. avoid converting an existing primary key merely to save bytes without an
   end-to-end storage measurement.

The audit must include public Candid/API shape, relations, fixtures, imports,
stable data, migration cost, and client assumptions. It does not automatically
rewrite existing ULID tables.

## Alternatives Considered

### Add Serial8 Through Serial128 Types

Rejected. These types duplicate Nat value semantics and couple authorship to
scalar kind. Generation belongs in accepted write policy.

### Add An auto_increment Boolean

Rejected. IcyDB already has ULID and Timestamp insert generation. A boolean
creates invalid combinations and provides no useful exhaustive match point.

### Support Only Nat64

Rejected as the final contract. Nat64 remains the recommendation, but the
engine already owns exact bounded unsigned kinds and one u128 operational state
can serve them consistently. A Nat64-only persisted state would create needless
format churn when Nat128 or a narrower exact domain is later requested.

### Support Nat32 And Nat64 Only

Rejected. It saves little implementation complexity once conversion and bounds
are centralized, while making otherwise composable exact kinds inconsistent.
The danger of small domains is handled by explicit opt-in and clear capacity
documentation.

### Include Signed Integers

Rejected. Negative identity space, start rules, and overflow semantics add no
current domain value. Applications needing signed external numbers should use
ordinary caller-authored Int fields.

### Include NatBig

Rejected. Identity state and exhaustion must remain fixed-width and bounded.
Nat128 already supplies a practically unbounded sequential domain.

### Generate MAX(id) Plus One

Rejected. It requires a scan or index lookup, loses deleted allocation history,
couples correctness to derived index state, and cannot provide the same
recovery proof as explicit control state.

### Consume IDs As Soon As They Are Requested

Rejected for IcyDB's initial semantics. It creates gaps for rejected writes and
requires a separate durable allocation transaction. Marker-bound allocation
keeps the guarantee stronger without concurrent connection contention.

### Permit Explicit Values With GENERATED BY DEFAULT

Rejected. It complicates high-water synchronization, imports, conflict
semantics, and caller expectations. Applications needing authored numbers can
use an ordinary Nat primary key.

### Expose last_insert_rowid

Rejected. It introduces mutable session state and ambiguity for batches. The
existing INSERT RETURNING surface returns exact generated values directly.

### Compress Nat8, Nat16, And Nat32 During This Work

Rejected as scope coupling. Compact codecs would change every persisted Nat
field and key, require independent ordering and format evidence, and should be
justified by measurements.

Each slice is a review and landing unit. No slice may introduce a generated
model fallback, an implicit identity, a second mutation owner, or a

## Focused Validation

### Schema Matrix

- Identity accepts Nat8, Nat16, Nat32, Nat64, and Nat128 sole primary keys;
- nullable, collection, relation, signed, NatBig, non-primary, and composite
  forms reject;
- default, management, and second-generator combinations reject;
- generated typed insert inputs omit the identity field;
- codec and fingerprint round trips preserve Identity exactly; and
- policy or width drift rejects during reconciliation.

### Allocation Matrix

- first identity is one for every width;
- consecutive insertions advance exactly once;
- Nat8 and Nat16 reach their exact maximum and then reject;
- Nat32, Nat64, and Nat128 exercise boundary conversion cases;
- deletion never permits reuse;
- rejected accepted constraints, uniqueness, relation, resource, and final-row
  failures consume nothing;
- a stale second cursor publishes nothing after a first cursor commits;
- internal multi-owner marker fixtures compare every owner atomically; and
- allocation counts above `u32::MAX` reject before cursor creation.

### Ingress Parity

- typed insert without invoking application callbacks;
- SQL INSERT omission;
- SQL INSERT DEFAULT;
- SQL multi-row INSERT RETURNING;
- atomic typed batch;
- structural insert;
- save of an existing row;
- attempted save-as-insert;
- UPDATE and replace;
- direct test helpers that construct commit operations.

Every ingress must reach the same accepted owner or reject before marker
publication.

### Atomicity And Recovery

Interrupt around:

- local allocation before marker;
- marker persistence;
- row journal publication;
- identity range journal publication;
- live row apply;
- live identity apply;
- canonical row fold;
- canonical identity fold;
- fold watermark update;
- marker clearing; and
- derived index rebuild.

After recovery, the outcome is either the complete committed row/range or the
unchanged pre-marker state. No duplicate, rewind, reuse, skipped row, or
generator reevaluation is admitted.

Also prove:

- marker publication has no await, yield, or re-entrant boundary;
- a marker-authorized range is committed before its live projection advances;
- guarded re-entry materializes that range before a new cursor reads state;
- `current == new` is accepted only for the exact advance identity;
- a prior batch cannot replay after a later range; and
- marker rows exactly equal the declared owner range.

### Integrity And Lifecycle

- absent active state;
- bad magic, version, length, checksum, and u128 payload;
- wrong database incarnation;
- state beyond accepted kind maximum;
- row zero or row above high-water;
- candidate key already present above recorded high-water;
- row key/slot mismatch;
- high-water greater than live maximum after deletion;
- active-to-retired transition without state deletion;
- retired owner reuse rejection;
- active and retired inventory at the 65,536-record cap; and
- concurrent deep-scan invalidation.

### Performance Evidence

Measure at least:

- generated versus caller-authored Nat64 insert;
- generated Nat128 insert;
- one-row and maximum admitted multi-row batches;
- journal bytes per identity-owner range;
- recovery with identity-bearing commits;
- stable control bytes per active and retired identity owner;
- raw non-gzipped wasm delta; and
- source line and owner-count complexity.

## Performance And Complexity Budget

### Write Runtime

Identity allocation adds one state lookup per participating identity owner per
statement, one checked increment per generated row, one final expected-state
comparison per owner, and one range-state write per owner per successful
commit. It must not scan rows or indexes.

Batch preparation may store allocated values already required for the rows,
but must not build an unbounded secondary allocation structure beyond the
existing admitted row cap.

### Persisted Bytes

Operational state is one bounded control record per active or retired identity
owner. Journal overhead is one range record per identity owner per commit, not
one record per inserted row.

Row and primary-key encodings remain the existing exact Nat encodings. The
design claims no Nat8/Nat16/Nat32 space saving.

### Wasm

The implementation adds no dependency. Closeout reports raw non-gzipped wasm
bytes for representative generated and SQL canisters. Gzip is secondary
context.

### Source Complexity

The desired final shape adds:

- one accepted enum variant;
- one exact eligibility helper;
- one canonical conversion helper;
- one active/retired operational state owner;
- one statement cursor;
- one marker/journal range owner; and
- integrity and introspection integration.

It should remove Nat64-specific branches, per-row advance records, absent-as-
zero fallback, and shape-based derived projection exceptions from the spike.

## Risks And Mitigations

### Risk: Small Domains Exhaust Unexpectedly

Mitigation: generation is explicit, capacities are documented and
introspectable, exhaustion is typed, and Nat64 is the recommended default.

### Risk: A Missing Record Restarts At One

Mitigation: zero state is explicitly published and missing active state is
corruption.

### Risk: Batch Failure Burns A Range

Mitigation: cursors are statement-local and range state is marker-bound only
after all preflight succeeds.

### Risk: Two Preparations Allocate The Same Range

Mitigation: guarded mutation is synchronous and non-reentrant through marker
publication, and publication revalidates the complete expected-high-water set.
A stale comparison returns a typed conflict without publishing a marker.

### Risk: Recovery Applies A Range Twice

Mitigation: expected/new validation, exact marker/batch/sequence/record
identity, last-applied state, and fold watermark permit only exact idempotent
replay.

### Risk: Derived Index Rebuild Looks Like An Insert

Mitigation: the existing `CommitPrepareMode` separates normal writes,
recovery replay, and derived rebuild; only accepted pre-key insert resolution
allocates.

### Risk: Entity Removal Loses Allocation History

Mitigation: removal atomically retires the record, immutable owner identities
cannot be reused, and the combined inventory has an explicit lifetime cap.

### Risk: Future Restore Reuses Deleted IDs

Mitigation: no restore surface is part of 0.214. Any later design must preserve
every active and retired record and use a recovered, quiescent artifact rather
than deriving state from live rows.

### Risk: Width Is Duplicated In State

Mitigation: state is canonical u128; accepted field kind is the sole domain
width.

### Risk: Narrow Types Are Mistaken For Compact Storage

Mitigation: documentation, introspection, and measurement explicitly separate
semantic width from current physical codec width.

### Risk: Public Numeric IDs Leak Volume

Mitigation: identity selection guidance treats enumerability as a domain
choice; ULID remains available and authorization never relies on ID opacity.

### Risk: The Spike Becomes Accidental Format Authority

Mitigation: status remains proposed, all experimental names and formats are
hard-cut, and no compatibility tests or aliases are retained before 1.0.0.

- numeric identity is entity-local and store-local;
- narrower kinds do not currently promise smaller physical keys;
- INSERT RETURNING is how SQL obtains generated IDs;
- SQL DDL identity authoring is deferred;
- ordinary Nat primary keys remain caller-authored;
- ULID remains the choice for decentralized or cross-system allocation; and
- removal retires rather than deletes allocation history.

Active README examples are updated only when implementation is complete. No
documentation should claim the feature is on the main branch while the
ringfenced implementation remains a spike.
