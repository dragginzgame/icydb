## 1. Summary

Patch 1 reproduced the current 60-entity Toko `project_instance` from clean,
exact source against released IcyDB `v0.248.1` and Canic `v0.109.22`. The
current Binaryen 132 `-Oz` artifact has a 10,800,042-byte code section. It
exceeds the 10 MiB platform limit by 314,282 bytes and the selected 256 KiB
reserve target by 576,426 bytes, while its 22,881 declared functions remain
below the 50,000-function structural threshold.

Exact named attribution found that the largest candidate was the shared
ordered-overlay traversal itself: 31 monomorph rows, about 28,503 bytes of
monomorph bloat and a 29,518-byte complete pre-transform body. Patch 1 initially
rejected it against the provisional 32 KiB intake gate. Review reopened that
decision because the gate was an evidence filter rather than a technical lower
bound and a clean reduction below it was still useful to the constrained actor.

Patch 2 replaces the visitor- and error-specialized traversal function with one
allocation-free ordered-overlay iterator. The exact frozen Toko A/B saves 13,781
final raw bytes, 13,746 final code bytes and 20 declared functions after
Binaryen 132 `-Oz`, with no added indirect calls. Public exports, Candid,
persisted bytes and traversal semantics are unchanged. The actor remains above
the platform limit, so this is a retained IcyDB reduction rather than a complete
deployment fix.

Patch 3 measured the next-ranked covering-projection family against the
retained Patch 2 artifact. Moving its presence/window traversal into a concrete
iterator saved only 502 final raw bytes and 507 final code bytes, while adding
two declared functions, one `call_indirect`, 233 gzip bytes and a new state
type. The candidate was rejected and removed.

Review then explicitly authorized ICYDB-013 for `0.249.0` as Patch 4. It adds
one operation-local result beside the existing bounded live-page result for
ordinary dynamic and typed/fluent reads. The result contains only fixed route
and cache enums plus instruction, scanned-row and emitted-row counters. It
does not mutate retained metrics, retain query identity, enable SQL, or make
the broad diagnostics feature part of Toko's dependency graph. Patch 4 is
complete with fixed-envelope, state-invariance, cold/warm cache, instruction
and dead-strip proof.

New exact downstream evidence then identified a larger boundary cost outside
Patch 1's core-only family ranking: Toko repeated mutation execution,
cardinality validation and accepted-row projection for each generated entity,
although only final row decoding depends on that entity. Patch 5 moves the
shared work behind concrete IcyDB terminals. Its exact production A/B saves
79,140 final raw bytes, 77,887 code bytes and 126 declared functions without
changing Candid, exports or indirect dispatch. Patch 6 qualifies the complete
retained line at 92,354 fewer final raw bytes, 91,275 fewer code bytes and 147
fewer declared functions than exact `v0.248.1` under one current pipeline.

Before the active release was tagged, the user explicitly folded the remaining
pagination finding into `0.249.0`. Patch 7 moves public/trusted dispatch,
continuation movement, exhaustion and repeated-token detection into one
non-entity page driver while consumers retain page-local decode. The exact
sequential production A/B saves another 14,776 final raw bytes and 14,433 code
bytes. The extended cumulative result is 107,159 fewer raw bytes and 105,737
fewer code bytes than `v0.248.1`.

Patch 8 corrects the subsequent release-validation regressions. Ordinary
projections again return the route-free result shape, explicit attribution
captures the physical route separately, and the ordered-overlay merge checks
visibility only after choosing the winning entry. The failed SQL gates now pass
without raising their ceilings, and the attribution state proof no longer
compares a volatile report-generation timestamp. The Patch 7 Wasm totals remain
the last exact receipt until the corrected tree is requalified.

After `0.249.1` was published, a supplied disposable Toko A/B found that the
already-boxed request child still specialized the same request-root poll shell
for every endpoint future type. Patch 10 type-erases only that child while

## 2. Immediate Headroom Is Not 0.249 Work

Toko should take the independently compiling Canic and IcyDB upgrades now.
Their combined supplied reduction is the new dependency floor, not a saving
credited to 0.249.

The remaining work has three distinct owners:

| Owner | Opportunity | Boundary |
| --- | --- | --- |
| Toko | Upgrade its pins; split `project_instance` only if shared-library reductions still cannot meet the measured platform reserve or repository budget | Downstream application work |
| Canic | Generate the managed command, status and ingress-inspection runtime from each validated role contract | External framework work |
| IcyDB | Retain the measured ordered-overlay convergence; do not broaden the line without another independently justified candidate | Patch 2 complete |

An artificial Canic build that removed the complete managed runtime bundle
saved 644,835 final `-O3` bytes and 876 optimized functions. That is a ceiling,
not a production candidate: `project_instance` still needs some management
operations. A role-specific Canic design must be qualified in Canic and may
intentionally change that role's generated management contract. It is not an
IcyDB patch and its bytes cannot be mixed into a 0.249 A/B.

Likewise, changing Toko's actor boundary is an application architecture
decision. The 0.249 result reports the remaining reserve explicitly and does
not conceal it by changing the proving application.

## 3. Evidence And Interpretation

The already released reductions explain why the dependency floor moved:

- Canic's 0.109 release train removed redundant per-endpoint code and the
  final debug Candid export, admitted a final optimizer, moved supported local
  Candid generation to a sidecar and removed redundant topology/auth sorting;
- IcyDB 0.245 made explicit-removal lowering unreachable in generated-only
  actors, saving about 107 KiB in its representative final raw Wasm;
- IcyDB 0.246 shared bounded control-plane sorting and removed 103,780 final
  raw SQL-Wasm bytes in its closeout subject; and
- IcyDB 0.247 converged compact sort, retained scan and ordered-map construction,
  reducing its exact Toko Miner code section by 34,072 bytes after the then
  official Binaryen pipeline.

Those are prior shipped outcomes, not 0.249 candidates. The much larger
0.241-to-0.247 downstream delta includes several of them and must not be
described as the effect of one monomorphisation patch.

The supplied pre-Binaryen attribution identifies these broad areas:

| Area | Approximate shallow attribution |
| --- | ---: |
| Schema runtime | 447 KiB |
| Session and request processing | 322 KiB |
| Executor | 274 KiB |
| Query planning | 206 KiB |

These numbers locate investigation areas. They are not additive saving
estimates, because generic bodies, downstream types, drop glue and shared
callees cross name-based ownership boundaries, and Binaryen may already fold

The earlier 0.247 line also constrains this design:

- compact sort and retained scan already converged onto shared kernels;

- cold outlining was rejected when final artifacts did not improve; and

0.249 does not repeat those experiments without new exact downstream evidence.
In particular, the 447 KiB schema-runtime attribution is not authority for a

## 6. Retention And Performance Gates

Patch 1 records three independent outcomes:

| Outcome | Gate |
| --- | --- |
| Platform compliance | Final code section at or below 10,223,616 B and a passing canonical validator/install result |
| Structural compliance | Fewer than 50,000 declared functions and every other current validator constraint passes |
| Repository objective | At least 256 KiB cumulative final raw-Wasm reduction from IcyDB-only changes |

0.249 selects a 256 KiB code-section safety reserve independently of the
256 KiB raw-Wasm objective. The platform target is therefore:

```text
10,485,760 B - 262,144 B = 10,223,616 B
```

After Patch 1 measures the canonical current code section, the required code
reduction is:

```text
max(0, current final code bytes - 10,223,616 B)
```

The reserve is explicit so later application growth does not immediately
reopen platform noncompliance. Production review may change it only by
updating the design with a measured Toko growth requirement before selecting a
source candidate. A reserve change does not change the independent 256 KiB raw
objective.

A production candidate is normally retained only when all of these hold:

1. final raw Wasm shrinks by at least 32 KiB on the exact Toko A/B;
2. the final code section shrinks and the complete structural validator result
   does not regress;
3. the named generic family materially converges rather than moving attribution
   under a new helper name;
4. exports, Candid, results, typed errors, cursor identity, logical work,
   physical visits and deterministic persisted bytes remain identical;
5. instruction regressions remain within the frozen workload-specific
   allowance; and
6. implementation shape becomes simpler or stays neutral.

The 32 KiB threshold is an intake control, not an architectural minimum.
Review may admit a named sub-threshold candidate when the exact A/B is positive,
the code section also shrinks, the implementation remains neutral or simpler,
and no new allocation, indirect dispatch, state or behavior axis is introduced.
Patch 2 is the sole reviewed exception: it saves 13,781 final raw bytes and
13,746 final code bytes, removes 20 declared functions and leaves the final
`call_indirect` count unchanged at 1,038.

The ordinary allowed regression is at most:

```text
max(250,000 instructions, 3% of baseline instructions)
```

Cheap per-row and frequently called hot-path controls use the tighter:

```text
max(25,000 instructions, 3% of baseline instructions)
```

Patch 1 classifies controls before any candidate is measured. With a frozen
toolchain, deterministic instruction counts should not need a broad noise
allowance. If a control is genuinely variable, Patch 1 records repeat ranges
and obtains review of its gate before production work rather than widening the
gate after seeing a candidate.

A more complex implementation is rejected even if it barely clears the byte
gate. Allocation, indirect dispatch or repeated mode checks inside per-row hot
loops require explicit instruction and physical-work proof and are expected to
fail the simplicity gate.

The 256 KiB cumulative raw target is not the no-build threshold. A smaller
cumulative result may proceed when it provides the complete measured code
headroom, passes the validator, clears the default intake gate or an explicit
reviewed exception, and adds no complexity. Failure to reach the repository
raw target is reported separately.

Patch 1 normally closes the production line as a no-build when no isolated
candidate can clear the intake gate and the credible cumulative result cannot
provide the required code headroom. Review may reopen one specifically named
candidate under the exception above. It does not authorize broad IcyDB changes
merely to reach the raw target.

If Patch 1 finds that the canonical actor already passes the selected platform
reserve, the required code reduction is zero. Any later production proposal
must then be justified against Toko's exact repository budget and the separate
raw-Wasm objective; it may not claim a deployment emergency.

### Patch 2 — Allocation-Free Ordered Overlay

Replace `visit_ordered_overlay`, whose visitor, error and visibility closures
specialize the complete merge state machine, with one iterator that owns only
canonical/live peeking, direction, key projection and tombstone visibility.
Data, index and schema stores retain their existing concrete visitors and typed
errors outside the iterator. Heap and journaled backing, ascending and
descending order, equal-key live precedence, tombstone filtering and early stop
remain the existing semantic matrix.

Required proof includes identical order, range bounds, live overrides,
tombstones, early stop and borrowed backing. The candidate may not allocate,
box, use unsafe erasure or add per-entry dynamic dispatch. Exact A/B evidence
must report the preflight and final raw/code/function results; a final artifact
that remains above the platform limit is reported rather than concealed.

### Patch 3 — Concrete Covering Projection Traversal

Converge the repeated generic folds and decode/map shells in
`db/executor/covering.rs` around concrete `IndexComponentValues`, `Value`, row
keys and window state. Terminal-specific mapping remains at a narrow boundary
after the shared stale-row, presence, offset, limit and component-decode work.

Required proof includes strict and ignore-missing parity, single- and
multi-component parity, identical early-stop and row-check attribution, and
fail-closed unsupported component kinds. The candidate may not introduce a
second covering executor or allocate complete rows on a route that currently
stays covering.

The measured candidate preserved strict and ignore-missing behavior, but its
exact sequential A/B saved only 502 final raw bytes and 507 code bytes. It also
added two declared functions, one indirect call and 233 gzip bytes. That result
fails the structural and simplicity gates, so the iterator and all production
source changes were removed.

### Patch 4 — Bounded Operation-Local Read Attribution

Add one explicit attributed live-page terminal to the existing public dynamic
and typed/fluent read surfaces. The attributed terminal must execute the same
accepted-schema, planner, admission, executor, cursor and typed-decoding owners
as the ordinary live-page terminal. It may return only a fixed-size diagnostic
envelope containing total and typed-response-decode instructions, one bounded
access-route enum, one bounded execution-route enum, one bounded plan-cache
outcome, and rows scanned/emitted.

The surface is operation-local and does not write retained metrics or database
state. It must not return or retain entity names, index names, predicates,
literals, query text, caller identity or attacker-controlled labels. The
attribution envelope requires a fixed Candid-size bound, ordinary-versus-
attributed result parity, query-state invariance, cold/warm cache proof and a
measured instruction-overhead result. It is a directly selected API rather
than a new runtime mode or broad diagnostics feature, so actors that do not
call it retain no new endpoint or Candid surface.

The Toko adoption proof is downstream-owned: after an immutable IcyDB release,
Toko must expose one authorized query wrapper and demonstrate that a cheap and
an intentionally expensive typed/fluent read have distinct operation-local
cost while returning unchanged normal results.

### Patch 5 — Concrete Typed Mutation Projection

Add one non-entity terminal for a `TypedWrite` that executes through the
existing accepted mutation owner, requires exactly one returned row and
projects it through the write's owned binding. Add one same-entity structural
batch terminal that checks the supplied binding and every target before
execution, preserves the existing bounded atomic batch, requires one result
and one row per mutation, and returns `Vec<OutputRow>`. Mark both substantial
terminals `#[inline(never)]` so fat LTO cannot reintroduce their orchestration
inside each generated entity wrapper.

Only the final `TypedRowAdapter::decode_row` remains generic on the entity.
Accepted catalogs remain runtime authority, and lowering, identity allocation,
admission, constraints, commit ordering, journal bytes and recovery remain in
their existing owners. The existing dynamic-result APIs retain their distinct
caller-facing result contract; the new terminals are concrete projection
boundaries rather than a second mutation executor.

Required proof is an exact production Toko A/B after Binaryen 132 `-Oz`, plus
single-row and structural-batch host semantics, pre-execution foreign-entity
rejection, unchanged exports and Candid, no additional indirect dispatch, and
no Wasm regression for actors that do not select the terminals.
