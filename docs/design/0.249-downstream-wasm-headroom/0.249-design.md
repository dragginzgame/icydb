# IcyDB 0.249 — Measured Downstream Wasm Headroom

- **Status:** Draft Patch 1 measurement investigation; production not authorized
- **Date:** 2026-08-29
- **Target line:** 0.249 after accepted 0.248 closeout and explicit 0.249 start
- **Current released reference:** `v0.248.0`, revision
  `a0d620c83a90c3f90f459e6409a1b3e766959ae2`, tree
  `136e06b6811aa0fc41b660df60e2b99be73e0b54`
- **Predecessor status:** `v0.248.0` is released, but the planned 0.248
  arithmetic and closeout patches remain incomplete and are not authorized;
  the 0.248 line is therefore not yet accepted as closed
- **Qualifying subject:** current Toko `project_instance`, 60 generated entities

## 1. Summary

The supplied current 60-entity Toko `project_instance` artifacts exceed the
project's downstream Wasm budget after moving to IcyDB 0.247. They do not yet
establish whether the canonical artifact violates the IC code-section limit.
Patch 1 must distinguish platform noncompliance from insufficient repository
headroom.

The supplied downstream builds show that the newer Canic and IcyDB pins
materially help:

| Dependency set | Final raw Wasm after `-O3` | Functions | Delta |
| --- | ---: | ---: | ---: |
| Canic 0.109.9, IcyDB 0.241.0 | 12,503,370 B | 22,789 | — |
| Canic 0.109.20 only | 12,312,092 B | 22,154 | -191,278 B |
| IcyDB 0.247.0 only | 12,261,302 B | 22,363 | -242,068 B |
| Both upgrades | 12,047,756 B | 21,713 | -455,614 B / -3.64% |

With both upgrades and `wasm-opt -Oz`, the supplied final artifact is
11,526,112 bytes, 458,155 bytes below its matching pinned control.

These figures are intake evidence, not yet the 0.249 qualifying baseline. They
do not identify the exact Toko revision, Rust toolchain, Cargo lockfile,
optimizer binary, optimizer command, code-section size or validator/install
result. The IcyDB-only row also spans 0.242 through 0.247 and therefore cannot
attribute all 242,068 bytes to the 0.247 monomorphisation work. It does
establish that the release sequence did not literally have zero effect on this
subject.

The current official IC limits relevant to this investigation are:

| Constraint | Limit | Current evidence |
| --- | ---: | --- |
| Complete Wasm module | 100 MiB | Supplied artifacts are clearly below it |
| Code section | 10 MiB / 10,485,760 B | Not supplied |
| Declared functions | 50,000 | About 21,700; not close |
| Repository raw-Wasm budget | Project-defined | Reported exceeded; exact policy must be frozen |

The complete list includes other structural constraints. Patch 1 uses the
current [IC resource limits](https://docs.internetcomputer.org/references/resource-limits/)
and [Wasm validation errors](https://docs.internetcomputer.org/references/execution-errors/)
as the platform authorities and captures the actual canonical validator or
installation result rather than inferring acceptance from section totals.

The 0.249 hypothesis is that one or two of the remaining IcyDB-owned generic
execution shells can be replaced by concrete internal kernels. Patch 1 ranks
the candidate families after the frozen optimizer. A later production review
may admit at most the largest two credible families and stops the line when
the measured headroom requirement is satisfied.

The repository objective remains at least 256 KiB of cumulative final raw-Wasm
reduction on the exact current Toko subject. It is independent from platform
compliance and is not a no-build threshold. Raw non-gzipped Wasm remains the
primary repository optimization result; code-section bytes and the actual
validator/install result determine platform compliance.

## 2. Immediate Headroom Is Not 0.249 Work

Toko should take the independently compiling Canic and IcyDB upgrades now.
Their combined supplied reduction is the new dependency floor, not a saving
credited to 0.249.

The remaining work has three distinct owners:

| Owner | Opportunity | Boundary |
| --- | --- | --- |
| Toko | Upgrade its pins; split `project_instance` only if shared-library reductions still cannot meet the measured platform reserve or repository budget | Downstream application work |
| Canic | Generate the managed command, status and ingress-inspection runtime from each validated role contract | External framework work |
| IcyDB | Converge proven repeated planner, scan, decode, mutation and retry bodies onto concrete internal kernels | Proposed 0.249 work |

An artificial Canic build that removed the complete managed runtime bundle
saved 644,835 final `-O3` bytes and 876 optimized functions. That is a ceiling,
not a production candidate: `project_instance` still needs some management
operations. A role-specific Canic design must be qualified in Canic and may
intentionally change that role's generated management contract. It is not an
IcyDB patch and its bytes cannot be mixed into a 0.249 A/B.

Likewise, changing Toko's actor boundary is an application architecture
decision. 0.249 must report when its cumulative candidate still misses the
measured platform reserve or repository budget; it must not conceal that
result by silently changing the proving application.

## 3. Evidence And Interpretation

The already released reductions explain why the dependency floor moved:

- Canic's 0.109 release train removed redundant per-endpoint code and the
  final debug Candid export, admitted a final optimizer, moved supported local
  Candid generation to a sidecar and removed redundant topology/auth sorting;
- IcyDB 0.245 made explicit-removal lowering unreachable in generated-only
  actors, saving about 107 KiB in its representative final raw Wasm;
- IcyDB 0.246 shared bounded control-plane sorting and removed 103,780 final
  raw SQL-Wasm bytes in its closeout subject; and
- IcyDB 0.247 converged compact sort, retained scan and ordered-map construction,
  reducing its exact Toko Miner code section by 34,072 bytes after the then
  official Binaryen pipeline.

Those are prior shipped outcomes, not 0.249 candidates. The much larger
0.241-to-0.247 downstream delta includes several of them and must not be
described as the effect of one monomorphisation patch.

The supplied pre-Binaryen attribution identifies these broad areas:

| Area | Approximate shallow attribution |
| --- | ---: |
| Schema runtime | 447 KiB |
| Session and request processing | 322 KiB |
| Executor | 274 KiB |
| Query planning | 206 KiB |

These numbers locate investigation areas. They are not additive saving
estimates, because generic bodies, downstream types, drop glue and shared
callees cross name-based ownership boundaries, and Binaryen may already fold
part of the source duplication.

The earlier 0.247 line also constrains this design:

- compact sort and retained scan already converged onto shared kernels;
- redundant canonical sorts were removed;
- cold outlining was rejected when final artifacts did not improve; and
- a pre-lowered generated schema removed about 16.7 KiB of code but added
  about 33 KiB of embedded data, growing the final artifact by about 16 KiB.

0.249 does not repeat those experiments without new exact downstream evidence.
In particular, the 447 KiB schema-runtime attribution is not authority for a
second schema representation. Accepted schema snapshots remain runtime
authority, and generated models remain proposal, reconciliation, model-only
convenience and test inputs.

## 4. Candidate Owners

Source inspection identifies five bounded candidates for Patch 1 attribution.
They are an inventory, not an approved production ledger. Their generic
signatures only justify measurement; they do not prove retained Wasm
duplication.

| Candidate | Current owner | Dimensions to measure | Intended convergence |
| --- | --- | --- | --- |
| Merged index ranges | `db/index/scan/raw.rs` | order key plus admission, decode and visit closures across backing/direction lanes | one concrete merged-range traversal driver with narrow route adapters |
| Covering projection | `db/executor/covering.rs` | accumulator, next-row, decode and mapping types across windowed and materialized routes | concrete component-row, decode and window kernels using runtime `Value` |
| Structural mutation | `db/session/write.rs` | result, mutation-source and precommit closure types across save, delete and bounded-prefix callers | one concrete accepted packing/precommit outcome with thin caller projections |
| Planner traversal | `db/query/plan/semantics/access_projection.rs` and `db/query/plan/validate/semantic_gates.rs` | child iterator/projection and validation closure combinations | concrete access/explain traversal and scalar validation owners |
| Residual retry | `db/executor/kernel/mod.rs` | attempt result and materializer closure for row and kernel-row outcomes | one concrete retry schedule/decision kernel with route-specific materialization outside it |

The intended shape is not blanket type erasure. A candidate may introduce one
private request or outcome value when it replaces generic control flow, but it
must not add a public mode, persisted discriminator, runtime registry, heap
boxing requirement or per-row dynamic dispatch. Borrowed index iteration,
bounded decoding and typed errors remain intact.

Generic canister-kind boundaries are not candidates merely because they name a
type parameter. An actor normally retains one canister kind. Patch 1 must prove
multiple material instances before any such boundary enters this line.

Patch 1 ranks the five families by isolated post-optimizer raw/code saving,
implementation complexity, affected hot-path cost and contribution to the
measured code-headroom requirement. Production review selects at most one or
two. Unselected families move to later designs only when they retain an
independent demonstrated need; Toko pressure does not authorize an engine-wide
refactor campaign.

## 5. Frozen Measurement Contract

Existing exact artifacts can establish the intake control and support initial
attribution. Source-changing production A/B qualification additionally
requires the exact Toko source and a reproducible build environment. A local
checkout is valid when its commit, tree, generated-source fingerprint,
lockfile and clean or precisely recorded dirty state match the frozen subject.
An unverified or merely similar checkout is not valid.

The frozen receipt records:

1. Toko commit and tree, dirty-tree state, the 60-entity schema fingerprint and
   generated-source fingerprint;
2. `Cargo.toml` dependency selections and complete `Cargo.lock` hash;
3. Rust and Cargo versions, target, linker flags, feature set and release
   profile;
4. Canic and IcyDB versions and revisions;
5. every post-link tool version, executable SHA-256 and exact ordered command;
6. raw artifact, code section, declared/defined functions, globals, exports,
   custom sections, gzip bytes and SHA-256 before and after final optimization;
7. the canonical IC validator result, including tool or replica version,
   command, exit status and complete diagnostic, plus the normal application
   install or upgrade result when that qualification path is available;
8. export names and kinds plus public Candid hash; and
9. the named attribution input and report hashes.

The dependency intake matrix is reproduced first. The source-changing 0.249
control then uses exact IcyDB `v0.248.0` and one frozen Canic version. Every
candidate changes IcyDB only. Canic changes, optimizer changes and Toko source
changes are separate comparisons and may not occur between a candidate's
before and after artifacts.

Patch 1 measures every plausible family in isolation against exact
`v0.248.0`, with the same frozen Toko, Canic and optimizer inputs. After
production review selects the largest one or two families, each retained
candidate also receives a sequential A/B against the preceding cumulative
candidate. The release decision uses the sequential result. Closeout reports
the cumulative artifact and never adds isolated deltas, because Binaryen
folding makes those deltas non-additive.

The no-`U256` Patch 2 evidence from 0.248 grew a representative actor by 4,181
raw bytes and 4,017 code bytes. Toko does not get an assumed free pass from
0.247 to 0.248; Patch 1 must build the released 0.248 predecessor directly.

Each source-changing candidate records:

- pre- and post-optimizer raw bytes, code bytes and defined functions;
- named instance count, shallow bytes and approximate bloat for the targeted
  family, with the residual instances explained;
- representative query results, typed errors, cursor bytes, logical work,
  physical visits and instruction counts;
- cold and populated startup/recovery instructions, callbacks, stable writes
  and cycle balance where the harness exposes them;
- exact public exports, Candid parity and validator/install outcome;
- focused owner tests and the current downstream application gate; and
- files touched, approximate line delta and complexity/state-space delta.

Raw non-gzipped Wasm is the primary repository optimization result. Platform
compliance is decided independently by the final code section and the complete
validator/install result; gzip is secondary distribution context.

## 6. Retention And Performance Gates

Patch 1 records three independent outcomes:

| Outcome | Gate |
| --- | --- |
| Platform compliance | Final code section at or below 10,223,616 B and a passing canonical validator/install result |
| Structural compliance | Fewer than 50,000 declared functions and every other current validator constraint passes |
| Repository objective | At least 256 KiB cumulative final raw-Wasm reduction from IcyDB-only changes |

0.249 selects a 256 KiB code-section safety reserve independently of the
256 KiB raw-Wasm objective. The platform target is therefore:

```text
10,485,760 B - 262,144 B = 10,223,616 B
```

After Patch 1 measures the canonical current code section, the required code
reduction is:

```text
max(0, current final code bytes - 10,223,616 B)
```

The reserve is explicit so later application growth does not immediately
reopen platform noncompliance. Production review may change it only by
updating the design with a measured Toko growth requirement before selecting a
source candidate. A reserve change does not change the independent 256 KiB raw
objective.

A production candidate is retained only when all of these hold:

1. final raw Wasm shrinks by at least 32 KiB on the exact Toko A/B;
2. the final code section shrinks and the complete structural validator result
   does not regress;
3. the named generic family materially converges rather than moving attribution
   under a new helper name;
4. exports, Candid, results, typed errors, cursor identity, logical work,
   physical visits and deterministic persisted bytes remain identical;
5. instruction regressions remain within the frozen workload-specific
   allowance; and
6. implementation shape becomes simpler or stays neutral.

The ordinary allowed regression is at most:

```text
max(250,000 instructions, 3% of baseline instructions)
```

Cheap per-row and frequently called hot-path controls use the tighter:

```text
max(25,000 instructions, 3% of baseline instructions)
```

Patch 1 classifies controls before any candidate is measured. With a frozen
toolchain, deterministic instruction counts should not need a broad noise
allowance. If a control is genuinely variable, Patch 1 records repeat ranges
and obtains review of its gate before production work rather than widening the
gate after seeing a candidate.

A more complex implementation is rejected even if it barely clears the byte
gate. Allocation, indirect dispatch or repeated mode checks inside per-row hot
loops require explicit instruction and physical-work proof and are expected to
fail the simplicity gate.

The 256 KiB cumulative raw target is not the no-build threshold. A smaller
cumulative result may proceed when it provides the complete measured code
headroom, passes the validator, clears the individual 32 KiB gate and adds no
complexity. Failure to reach the repository raw target is reported separately.

Patch 1 closes the production line as a no-build when no isolated candidate
can clear the 32 KiB retention gate and the credible cumulative result cannot
provide the required code headroom. It also closes when attribution shows that
the needed bytes are primarily owned by Canic or Toko. It does not authorize
broad IcyDB changes merely to reach the raw target.

If Patch 1 finds that the canonical actor already passes the selected platform
reserve, the required code reduction is zero. Any later production proposal
must then be justified against Toko's exact repository budget and the separate
raw-Wasm objective; it may not claim a deployment emergency.

## 7. Measurement Authorization And Possible Production Line

Only Patch 1 is proposed for authorization after the 0.248 closeout. It changes
no production Rust. Patches 2–4 describe the maximum shape of a later line;
their exact owner and authorization remain contingent on a new review of the
Patch 1 evidence.

| Patch | Bounded outcome | Authorization state |
| ---: | --- | --- |
| 1 | Freeze the exact current Toko subject, reproduce the dependency matrix and released 0.248 control, validate/install the canonical artifact, calculate required headroom and rank isolated candidates | Measurement only; proposed |
| 2 | Implement the single largest admitted family, with isolated and sequential A/B evidence | Not authorized; owner selected after Patch 1 review |
| 3 | Implement the second-largest admitted family only if Patch 2 does not satisfy measured headroom and the second family independently clears every gate | Not authorized; optional |
| 4 | Qualify the cumulative artifact and report IcyDB, Canic and Toko outcomes separately | Not authorized |

If Patch 2 satisfies the selected platform reserve and the reviewed repository
requirement, Patch 3 is skipped. 0.249 admits at most two source families.
Remaining candidates require a later design and independent demonstrated need.
Each admitted source candidate remains build/no-build: rejected source is
removed within its landing patch and its measured decision stays in the status
record.

### Patch 1 — Exact Baseline And Candidate Ledger

Patch 1 retains no production Rust. Disposable candidate worktrees may be used
for isolated A/B builds, but only the evidence and ranked decision record land.
It must answer these questions before any production patch is authorized:

- Does the canonical validator/install path pass or fail, and which exact
  platform or project budget applies?
- What are the current final code bytes, selected reserve and calculated
  required code reduction?
- What exact raw-Wasm budget and reserve does Toko enforce independently of the
  platform code limit?
- Which named candidate families survive before and after the frozen final
  optimizer, and how many instances and bytes remain?
- Which one or two families have the largest credible isolated post-optimizer
  raw/code result without counting Candid, Canic, Toko-generated endpoints,
  Rust sorting or drop glue twice?
- Does the 60-entity shape amplify IcyDB generic bodies, or is most growth in
  application-generated endpoints and application domain code?
- How much headroom comes from the dependency upgrade alone, independently of
  any 0.249 source candidate?

Patch 1 ends with a review record recommending exactly one of: no production
patch, the largest one family, or the largest two families in ranked order. It
does not authorize the complete candidate inventory.

### Candidate Contract — Concrete Merged-Range Traversal

Measure and, only if admitted, replace the retained
`visit_raw_entries_in_merged_ranges<K, Admit, Decode, Visit>` control-flow body
with one concrete traversal kernel. Heap and journaled backing, ascending and
descending order, tombstone filtering and the mixed-overlay fallback remain
the existing semantic matrix. Adapter selection occurs outside the per-entry
loop.

Required proof includes identical order, range bounds, early stop, structural
byte admission, stale-entry handling and borrowed backing. The candidate may
not allocate canonical order keys merely to erase `K` unless the full memory,
instruction and byte result passes the gates.

### Candidate Contract — Concrete Covering Projection Kernels

Converge the repeated generic folds and decode/map shells in
`db/executor/covering.rs` around concrete `IndexComponentValues`, `Value`, row
keys and window state. Terminal-specific mapping remains at a narrow boundary
after the shared stale-row, presence, offset, limit and component-decode work.

Required proof includes strict and ignore-missing parity, single- and
multi-component parity, identical early-stop and row-check attribution, and
fail-closed unsupported component kinds. The candidate may not introduce a
second covering executor or allocate complete rows on a route that currently
stays covering.

### Candidate Contract — Concrete Structural Mutation Outcome

Make accepted structural mutation packing produce one concrete private
prepared outcome before save, delete and bounded-prefix callers project their
specific return value. Accepted catalogs remain the sole runtime authority;
entity scheduling, identity allocation, byte admission, constraint ordering,
commit directives and commit atomicity remain in their current owners.

Required proof includes identical admitted/stopped reports, returned values,
mutation order, journal and stable bytes, recovery behavior and typed failures.
The candidate is rejected if separating caller projection duplicates commit
logic or retains large row buffers longer than the predecessor.

### Candidate Contract — Concrete Planner Traversal

Replace closure- and iterator-specialized access/explain child traversal and
scalar semantic validation only if Patch 1 shows meaningful retained bodies.
The canonical logical plan, access plan and explain DTO remain distinct public
internal models; this patch shares traversal/control flow, not their semantic
authority.

Required proof includes identical access plans, explain labels, validation
ordering, field-role error attachment, tie-break rules and generated Candid.
A broad planner rewrite is outside this patch.

### Candidate Contract — Concrete Residual-Retry Scheduling

Factor the retry schedule, widening decision and terminal fallback out of
`ResidualRetrySession::materialize<A, MaterializeAttempt>` only if both
materialization families remain measurably duplicated. Route-specific row and
kernel-row payload construction stays outside the concrete scheduling kernel.

Required proof includes identical probe counts, widened fetches, residual
underfill behavior, merge semantics, unbounded fallback, scan budgets and
results. There may be no new retry policy, persisted state or per-row indirect
dispatch.

### Later Production Qualification And Closeout

Rebuild the frozen current Toko source against exact `v0.248.0` and the final
retained 0.249 candidate with one frozen Canic and optimizer pipeline. Report
each patch's sequential result and the cumulative raw/code/function,
attribution, instruction, startup/recovery, export, Candid and validator/install
results. Do not sum isolated candidate deltas.

Then report, in separate rows:

- the Toko dependency-upgrade floor;
- the final IcyDB-only 0.249 delta;
- any independently released Canic role-specific delta; and
- the remaining bytes to the 10 MiB platform code limit, selected code reserve
  and exact repository raw-Wasm budget.

If the exact current actor still fails its selected platform reserve or exact
repository budget, closeout must say so. It then hands the remaining decision
to Canic role specialization or a Toko actor split rather than opening another
unmeasured IcyDB abstraction.

## 8. Non-goals

0.249 does not add or perform:

- an IcyDB feature profile, size mode, runtime configuration or second engine;
- a generated-model fallback or a second accepted-schema representation;
- another pre-lowered-schema or cold-outlining experiment without new exact
  attribution that clears its prior rejection;
- SQL, diagnostics or migration removal from actors where those features are
  already disabled;
- a blob-storage feature toggle; Toko currently uses blob APIs in source and
  Candid unconditionally;
- a blanket replacement of generics, dynamic dispatch, boxing or unsafe erased
  storage;
- an optimizer-version change credited as an IcyDB source saving;
- Canic role-contract generation or management endpoint implementation;
- a Toko entity reduction, endpoint removal or actor split;
- a public API, Candid, schema, cursor, catalog or persisted-format change; or
- a compatibility shim, predecessor decoder or legacy path.

The demonstrated need is downstream size pressure: the supplied current

dependency reductions. Platform noncompliance is unproven until Patch 1
captures the final code section and validator/install result. The simplest

design adds no independent behavior axis; it changes implementation shape only
when the final artifact proves the benefit.

## 10. Activation And Exit Criteria

This document does not activate 0.249. Activation requires:

1. accepted completion and closeout of the planned 0.248 line;
2. explicit user authorization to start 0.249; and
3. access to the exact current Toko source and reproducible build environment
   required for source-changing A/Bs. Existing exact artifacts may establish
   the intake control but cannot qualify a production candidate alone.

Patch 1 is complete when every inventory family has an isolated measurement or
a recorded evidence-based reason it cannot clear the retention gate, and the
review record selects zero, one or two production families. A later production
line is complete when the selected candidates are accepted or rejected, the
exact cumulative downstream qualification is recorded and the remaining
platform and repository headroom are explicit. Full repository and workspace
suites remain the user-owned validation workflow under repository governance.
