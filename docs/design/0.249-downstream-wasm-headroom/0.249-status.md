## Decision

At the 0.249 intake, the exact Toko `project_instance` remained above the IC
code-section limit after the IcyDB-owned Binaryen 132 `-Oz` pipeline. Patch 1
found that the largest IcyDB family is ordered-overlay traversal, with 31
monomorph rows, about 28,503 bytes of bloat and a 29,518-byte complete
pre-transform body. It was initially rejected against the provisional 32 KiB
intake gate.

Review admitted this one sub-threshold family because a smaller exact win was
still useful and the replacement could stay allocation-free and structurally
neutral. Patch 2 saves 13,781 final raw bytes, 13,746 final code bytes and 20
declared functions. Static key projection leaves `call_indirect` unchanged at
1,038. No public surface, runtime behavior or persisted format changes.

The Patch 2 code section is 10,786,296 bytes: still 300,536 bytes above the
platform limit and 562,680 bytes above the selected reserve in its original
Canic 0.109.22 pipeline. Remaining deployment headroom therefore still belongs
primarily to Canic's generated/runtime build boundary and Toko's final
optimizer or canister architecture.

Patch 3 tested the next-ranked covering-projection family against Patch 2. A
concrete fallible iterator preserved existing-row checks and effective-window
semantics, but saved only 502 final raw bytes and 507 code bytes. It added two
declared functions, one `call_indirect`, 233 gzip bytes and a new iterator state
type. The candidate was rejected and removed; the retained artifact and
production source remain the Patch 2 result.

The user explicitly authorized ICYDB-013 for `0.249.0` after the Wasm session
stopped. Patch 4 completes that narrow contract: one fixed-size operation-local
result for an ordinary dynamic or typed/fluent live page, using the existing
accepted-schema, planner, admission, executor, cursor and typed-decode owners.
It suppresses retained metrics and exposes no query or caller-controlled
labels. It does not reopen rejected Wasm candidates or authorize Patch 5
production work by itself.

The user then supplied new isolated evidence for a different boundary than the
rejected Patch 1 structural-mutation family: Toko repeats typed mutation
execution, cardinality validation and accepted-row projection for every
generated entity even though only final row decoding depends on that entity.
Patch 5 adds concrete IcyDB single-write and same-entity structural-batch row
terminals. The exact production A/B saves 79,140 final raw bytes, 77,887 code
bytes and 126 declared functions. Indirect dispatch, Candid and exports are
unchanged. Patch 6 measured the then-complete retained line against exact
`v0.248.1`: 92,354 fewer final raw bytes, 91,275 fewer code bytes and 147 fewer
declared functions.

Before the untagged release was published, the user explicitly folded the
separately measured pagination finding into the same active `0.249.0`. Patch 7
adds one non-entity page driver and adopts it in the disposable Toko typed and
projected-ULID consumers. Its exact sequential A/B saves another 14,776 final
raw bytes and 14,433 code bytes, with three added declared functions and
unchanged indirect dispatch. The extended cumulative result is 107,159 fewer
raw bytes, 105,737 fewer code bytes and 144 fewer functions than `v0.248.1`.
The actor still exceeds the platform code limit by 134,147 bytes, so remaining
installability work belongs to Canic role specialization or a Toko actor split.

The first user-owned release validation then exposed two deterministic SQL
instruction regressions plus one timestamp-sensitive attribution test. Patch 8
restores the ordinary route-free scalar projection result, captures the
physical route only for the explicit attributed terminal, and removes an eager
live-key tombstone lookup from the ordered-overlay iterator. Visibility is now
checked only for the merge entry actually selected, matching the retained
visitor's work contract without restoring visitor/error monomorphs. The two
focused SQL gates pass at 1,742,018 and 1,514,826 instructions against ceilings
of 1,760,100 and 1,525,972. The retained-metrics proof now compares counters,
entity counters and active-window identity while excluding the report-generation
end timestamp. Because Patch 8 changes production source, the Patch 7
cumulative downstream Wasm totals below remain the last exact artifact receipt
until the user-owned release flow requalifies the final tree.

The user subsequently published `v0.249.0`. Post-publication review identified
that Patch 7 committed its next continuation before downstream row decoding
and removed that continuation from the returned page. A failed decode could
therefore leave retained adapter state pointing past the rejected page, while
`into_page()` could return a non-exhausted DTO with no continuation. Patch 9
hard-cuts that contract: advancement borrows the prior token, returns one
uncommitted intact page and moves its token only when a consuming `commit`
follows successful processing. The duplicate exhaustion field and eager
movement helper are removed; no compatibility path remains.

Focused unit, public-facade compile, canister compile/Clippy and PocketIC gates
pass. The PocketIC proof executes both lanes, retries the same rejected first
page, commits it once, advances to the next boundary and retains the existing
ten-page 10,001-row traversal. The exact same-path Toko A/B now saves 15,548
final raw bytes and 15,214 code bytes after its disposable adapter adopts
decode-then-commit. It retains the prior three-function cost and unchanged
indirect dispatch while improving the published Patch 7 raw saving by 772
bytes.

The user then supplied a disposable Toko prototype showing that the
already-boxed request child still specialized one request-root poll shell per
endpoint future type. Patch 10 changes only that child to a type-erased future,
retaining the existing single allocation and adding one indirect child poll.
The supplied final code saving is 23,808 bytes, and all nine request-scope tests
pass. The actor remains approximately 85 KiB above its limit, leaving any Canic
dispatch-level scope integration as separate work.

The published `v0.249.2` boundary is clean at revision
`60c7130204a21465cb6f6f7d4fd05bc5e278d958`. The user then supplied and
explicitly authorized an ABI-preserving 0.249.3 safe set. The retained

The user published `v0.249.3`, clarified that the tracker planning range is not

After Patch 13 completion, the user explicitly authorized the one-public-value

The exact current-toolchain Toko A/B is size-neutral: +1,269 raw bytes, +984
