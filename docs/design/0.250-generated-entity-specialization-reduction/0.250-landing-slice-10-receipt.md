# 0.250 Landing Slice 10 Receipt — Cumulative Fluent Filters

Date: 2026-08-31

Status: Complete

## Outcome

Repeated typed and dynamic `.filter(...)` calls now retain every clause as one
`AND` predicate. The natural exact compound lookup therefore reaches IcyDB's
existing compound-prefix planner and public admission path:

```rust
db.query::<InventoryStack>()?
    .filter(InventoryStack::OWNER_ID.eq(owner_id))
    .filter(InventoryStack::SLOT.eq(slot))
    .limit(1)
    .execute_live_page(None)?;
```

The accepted schema remains runtime authority. No generated descriptor or Rust
model metadata participates in index selection.

## Root Cause And Owner

The supplied downstream report reproduced as E184 in IcyDB's accepted-schema
session harness before the fix. The planner already supported an equality for
every leading field of a compound index. The request builder did not deliver
that shape: `DynamicQuery::filter` replaced its stored expression on every
call, so the example reached planning as only `slot == value`.

The smallest semantic owner is the existing concrete `DynamicQuery`. Its
filter method now joins subsequent expressions with the prior expression by
`AND`. When the prior expression is already an `AND` junction, the builder
extends that vector instead of allocating a nested junction. Generated typed
queries continue to delegate to the same owner and add no entity-generic
planner path.

The following alternatives were rejected:

- weakening E184 or treating `LIMIT 1` as a scan-work bound, because result
  cardinality does not bound rows inspected;
- adding a compound-index-specific typed terminal, because the existing
  planner already owns that semantic route; and
- changing planner prefix selection, because it behaved correctly once it
  received the complete predicate.

## Behavioral And Compatibility Evidence

The focused regression uses an accepted two-field compound index and public
read admission. Before the fix it returned `Unsupported(184)`. After the fix,
the same chained spelling returns the expected filtered row. A paired request
containing only the non-leading equality plus `LIMIT 1` still returns
`UnboundedFullScanRejected` (E184).

`FilterExpr`, public result records, generated adapters, accepted schema,
persistence and cursor formats are unchanged. The maintained typed-query
Candid remains byte-identical at 64 bytes with SHA-256
`1005c63f5415d1de4bb7da89190f33212d1c926c881108a1acfeadfa93fff766`.
