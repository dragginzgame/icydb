## 1. Summary

The existing finalized one-to-ten-entity audit pair reports only 145 raw Wasm
bytes per added entity because its endpoint reaches `get::<E>` for one entity;
the other generated entity adapters can be dead-stripped. That remains a valid
schema-cardinality control, but it does not measure an application that reaches
typed query, exact-key and write adapters for every generated entity.

The supplied downstream audit does measure those reachable paths. Across 11
generator entities it attributes approximately 49.7–54 KiB to direct
database/entity monomorphization and 112–128 KiB to all entity-specialized
supporting code. Those ranges are substantially above the maintained 2 KiB
per-added-entity raw-Wasm ceiling when the generated adapters are actually
reachable.

The largest reported families are:

| Family | Approximate attributed code |
| --- | ---: |
| Typed page execution | 36.8 KiB |
| Typed page decoding | 29.8 KiB |
| Single-row insert | 34.6 KiB |
| Single-row update | 28.1 KiB |
| Atomic delete | 16.3 KiB |
| Typed query/delete wrapper methods | 59.7 KiB collectively |
| Generated insert/update encoders | 93.2 KiB across 79 functions |
| Generated `typed_binding` for the 11 entities | 4.5 KiB |

The figures overlap through inlining, retained callees and Binaryen merging.
They are attribution lenses, not additive saving estimates. Removing the
complete generator studio saves about 425 KiB, but that comparison also removes
schema, application behavior and generated endpoints and is not an IcyDB
monomorphization target.

One disposable experiment moved only common execution plumbing behind an
entity-erased page boundary. It reduced the optimized code section by roughly
49–51 KiB without changing schemas or removing entities. Its dynamic page
callback also added roughly 95 optimized functions through vtable shims, so
that exact shape is rejected. The 0.250 line instead converges existing
control flow through concrete request, page, exact-key and write terminals;
only final generated value encoding and `E::decode_row` remain entity-specific.

## 2. Demonstrated Need And Smallest Outcome

The demonstrated problem is final deployable Wasm growth in a real generated
consumer, not generic code in isolation. The smallest useful outcome is to
move control flow that does not inspect `E` behind existing concrete IcyDB
authorities while retaining generated leaf conversion where Rust types differ.

The simpler alternatives are insufficient:

- the current entity-scale actor does not make every generated adapter
  reachable and therefore cannot guard the observed slope;
- `#[inline(never)]` alone cannot merge functions whose signatures and bodies
  remain specialized over `E`;
- removing generated entities or endpoints changes the application rather than
  fixing IcyDB ownership;
- a trait-object page callback produced the expected code saving but added an
  entity-scaled shim family; and
- pre-lowered generated schema data previously moved code into data and grew
  final raw Wasm, so generated descriptors must stay narrow binding metadata.

The canonical owners already exist:

```text
generated descriptor/data -> accepted binding validation
DynamicQuery / structural intent -> existing session execution
dynamic result -> concrete prepared rows
prepared row -> generated leaf encode/decode
```

No new planner, executor, storage route, persisted state or query mode is
needed.

## 3. Architecture Boundary

### Concrete Typed Query State

`DynamicQuery` remains the canonical non-entity request specification. The
typed `Query<E>` facade may remain as a compile-time leaf for return-type
selection, but it must not own repeated execution, continuation validation,
page preparation or request mutation bodies. Its generic methods become thin
delegations into concrete state and terminals.

Downstream generated `QuerySpec` and `DeleteSpec` holders must likewise store
only non-generic dynamic query or structural mutation state. They are facade
ergonomics, not new IcyDB semantic authorities. 0.250 does not add a second
query specification beside `DynamicQuery` or a second delete specification
beside the existing structural/core delete owners merely to copy those names.

### Concrete Prepared-Page Driver

One concrete prepared-page driver owns:

- public or trusted page execution through the existing lane-specific session
  entry points;
- prior and next continuation movement;
- repeated-token rejection and commit-after-success behavior already owned by
  `LivePageStep`;
- accepted binding freshness and entity/column validation; and
- construction of `PreparedLivePageOutput` / `PreparedOutputRows`.

The driver is generic only on `CanisterKind`, which normally has one material
instance per actor. It does not accept an entity callback, trait object, erased
row sink or per-row function pointer. Public and trusted entry points remain
explicit and converge before entity decoding without adding a stored lane or
caller-selectable mode. Generated code loops over prepared rows and calls only
`E::decode_row`.

If a concrete owner cannot retain the measured saving, a function-pointer
descriptor may be measured only as a replacement experiment. It is not
retained unless the exact artifact proves that it creates no per-entity shim
slope or material function-count regression.

### Static Generated Entity Descriptors

Runtime-enabled generated entities emit one static, data-only descriptor with:

- immutable entity source key;
- ordered primary-key source keys;
- ordered field source keys;
- the current typed field shape and nullability contract; and
- only metadata required to issue and validate the opaque accepted binding.

`TypedEntityAdapter` returns that descriptor and the session validates it
against the accepted schema snapshot. Recursive field shapes use borrowed
static data rather than constructing `Box`, `String` and `Vec` request trees in
every generated binding body.

The descriptor is not accepted schema authority, a generated runtime catalog,
a persisted format, a pre-lowered schema, or a fallback reconstruction path.
Accepted snapshots remain the sole runtime authority, and a stale or
incompatible descriptor fails with the existing typed binding errors.

### Exact-Key Prepared Rows

The exact-key terminal executes lookup, validates the binding, prepares the
shared projection and returns bound `OutputRow` values plus the bounded
position mapping from the existing exact-key result. Key encoding and final
`E::decode_row` remain typed leaves. Duplicate-position reconstruction may
remain a small generic loop over decoded rows; lookup, stored-row projection,
budgeting and validation may not remain under `E`.

### Same-Entity Typed Write Batch

One concrete terminal equivalent in responsibility to
`execute_trusted_typed_write_batch_rows(binding, writes)` validates a
non-empty same-entity `TypedWrite` batch, executes it through the existing
canonical atomic batch owner, enforces exact result cardinality and prepares
rows once. Generated code retains only value-to-`InputValue` encoding and final
row decode. The existing typed mutation contract may gain its missing delete
case so generated delete wrappers encode only the key and enter the same
terminal; this exposes the already maintained delete operation rather than
adding another mutation route.

The proving consumer must delete its parallel structural field encoders when
it adopts this terminal. The existing mixed-entity typed batch remains the
owner for heterogeneous writes. 0.250 does not add another transaction mode,
batch limit, commit path or recovery state.

## 4. Frozen Measurement Contract

Landing Slice 1 freezes the exact proving inputs before any production
candidate is retained. The receipt records:

1. IcyDB predecessor revision/tree and dirty state;
2. downstream source revision/tree, generated source fingerprint and the exact
   list of 11 reachable entities;
3. `Cargo.toml` selections, complete lockfile hash and relevant feature set;
4. Rust/Cargo versions, target, linker flags and release profile;
5. Canic and every post-link optimizer version, executable hash and ordered
   command;
6. final raw non-gzipped Wasm, code section, declared/defined functions,
   `call_indirect`, exports, Candid bytes, deterministic gzip and SHA-256;
7. named Twiggy monomorphization/top/retained evidence for every reported
   family; and
8. focused query, exact-key, insert, update, delete and same-entity batch
   instruction controls.

The same frozen source and toolchain produce each predecessor/candidate pair.
No Canic, optimizer, schema, endpoint or application-source change may occur
inside an IcyDB source A/B. Sequential landing slices use the accepted prior
slice as their immediate predecessor and retain a cumulative comparison to
`v0.249.6`.

IcyDB also adds or corrects one maintained reachable-entity audit comparison.
It must call the same selected generated operations for every entity rather
than relying on declarations that the linker removes. The existing
schema-cardinality pair remains separately identified; its 145-byte slope must
not be presented as the reachable-adapter slope.

The downstream repository's complete CI, live install and application release
remain downstream- and user-owned. IcyDB owns the exact disposable build,
artifact comparison and focused generated-database checks recorded by this
design. A downstream result without source/toolchain identity remains intake
evidence rather than a frozen A/B.

## 5. Retention And Regression Gates

Raw non-gzipped final Wasm is the primary size result. Final code-section bytes
determine IC code headroom; declared functions, `call_indirect` and deterministic
gzip provide structural and distribution context.

Every retained production candidate must:

- reduce final raw Wasm on the affected reachable-entity subject;
- reduce or hold final code bytes, with no code-to-data trade that grows raw
  Wasm;
- reduce the targeted entity-specialized family or explain every residual;
- add no per-entity callback/vtable shim slope;
- preserve public exports and Candid unless a separately authorized hard cut is
  demonstrated before implementation;
- preserve exact results, typed error identity, cursor bytes, logical work,
  physical visits and accepted binding failure behavior; and
- preserve persisted version-1 bytes and accepted-schema authority.

The concrete prepared-page candidate has stronger evidence. It should retain
at least 32 KiB of final code reduction on the frozen 11-entity subject and
must not reproduce the experimental roughly 95-function increase. If it misses
that gate, Landing Slice 2 records the result and removes the candidate rather
than broadening into blanket type erasure.

A query or write regression is material when it adds both more than 250,000
instructions and more than 3% to a frozen affected control. A candidate that
crosses both thresholds is rejected unless the trade-off is measured and
explicitly approved before retention. Allocation class, callback count,
stable writes and cycle charge are reported where the harness exposes them.

Closeout reports:

- final raw/code/function/indirect-call deltas per landing slice and
  cumulatively;
- reachable-entity bytes per added entity against the maintained 2 KiB raw
  ceiling;
- named residual specialization families;
- files touched and approximate line delta;
- delivery domains crossed; and
- whether implementation structure became simpler, stayed neutral or became
  more complex.

Landing Slice 1 records the new reachable-operation slope without weakening
or immediately repurposing the passing schema-cardinality gate. By closeout,
the maintained reachable-entity comparison must pass the same 2 KiB final raw
ceiling. If it does not, the line reports an incomplete size objective rather
than raising the ceiling or relabeling unused-entity evidence as sufficient.

## 7. Slice Boundaries

### Landing Slice 1 — Reachable-Entity Baseline

This slice changes measurement subjects, reporting contracts and design/status
evidence only. It does not change the `icydb`, `icydb-core`, model or macro
production libraries.

The maintained comparison must distinguish at least:

- schema declarations present but unused;
- one reachable generated entity; and
- the same operation mix reachable for ten or eleven generated entities.

The operation mix is limited to paths selected by the supplied evidence:
bounded typed page execution, exact-key lookup, single write, same-entity batch
write and delete. It does not become a broad generated-feature matrix.

### Landing Slice 2 — Concrete Prepared-Page Driver

This is one facade ownership change. Non-generic request state and concrete
page execution belong together because splitting them would leave the repeated
generic terminal alive or create a temporary second flow.

Ordinary typed pages, attributed pages and downstream public/trusted adapters
must converge on the same preparation owner. Exhaustive pages reuse the same
row preparation but retain their existing proof owner and error type. Grouped
queries remain dynamic outputs and do not gain typed row decoding.

### Landing Slice 3 — Static Entity Descriptors

This slice changes only generated binding metadata and its validation bridge.
It does not use descriptors to execute reads or writes and does not move
accepted names, slots or schema facts into generated authority.

The generated descriptor is emitted once per entity as static data. Binding
issuance may materialize one bounded runtime request from that data, but the
macro must not emit an executable field-construction statement for every field
of every entity.

### Landing Slice 4 — Prepared Exact-Key Rows

This slice composes the existing exact-key executor with the existing prepared
projection owner. It does not add caching, a new key format or an unbounded
lookup route. `get` remains the one-item convenience over `get_many`.

### Landing Slice 5 — Same-Entity Typed Write Batch

This slice composes `TypedWrite`, the canonical atomic typed mutation batch and
prepared output rows. It admits delete through that same typed intent rather
than retaining a structural-only generated delete path. Generated value and
key encoders are still required once per Rust input shape; only duplicate
single/batch/structural control flow is deleted. The 93.2 KiB generated encoder
attribution is therefore a ceiling, not a promised saving.

### Landing Slice 6 — Cumulative Qualification

Closeout changes no production behavior. It records exact sequential and
cumulative artifacts, checks that the maintained reachable-entity subject
measures the intended operations and classifies residual generated
specialization as required leaf conversion, accepted cost or a separately
reviewable future design.

## 8. Non-Goals

0.250 does not add:

- blanket object-safe typed adapters or trait-object query/write execution;
- per-row callbacks, erased sinks, heap boxing or generated vtables;
- a runtime entity registry or generated-model schema reconstruction;
- pre-lowered accepted schema data or a second catalog representation;
- a new query, delete, exact-key, transaction, batch or recovery mode;
- SQL grammar, planner or executor semantics;
- Candid endpoint generation changes unrelated to direct propagation;
- a cursor, catalog or persisted-format version change;
- a Toko actor split, entity removal or generator-studio removal;
- removal of necessary final Rust value encoding/decoding; or
- compatibility wrappers for replaced pre-1.0 facade shapes.

## 9. Authority And State-Space Delta

| Concern | Canonical owner after 0.250 | State-space delta |
| --- | --- | ---: |
| Accepted runtime schema | Accepted schema snapshot | 0 |
| Generated source contract | Static data-only entity descriptor, validated by accepted authority | 0 behavior axes; executable construction becomes data |
| Query intent | Existing `DynamicQuery` | 0; typed/generated specs become holders only |
| Delete/write intent | Existing structural and typed mutation contracts | 0 |
| Page execution and continuation | Existing session executor and `LivePageStep`, composed by one concrete prepared driver | 0 persisted/cursor states; one transient owner replaces repeated control flow |
| Row projection | Existing `PreparedOutputRows` / `OutputRow` | 0 |
| Exact-key execution | Existing bounded exact-key terminal | 0 |
| Atomic batch commit and recovery | Existing typed/dynamic mutation batch owner | 0 |
| Final Rust conversion | Generated value encoders and `E::decode_row` | 0; retained only where the Rust type differs |
| Persisted and cursor formats | Existing current version-1 codecs | 0 |

The only new maintained representation is a compile-time data descriptor for
the generated source contract. It replaces generated construction statements
and adds no user choice, runtime mode, persisted discriminator or independent
execution route.

## 10. Activation And Exit Criteria

0.250 was explicitly started after the read-only 0.249 closeout reported
`v0.249.6` at `HEAD`, complete release notes and all 17 prior landing slices
complete. Landing Slice 1 is complete; generic continuation now starts exactly
Landing Slice 3 within the ordered ledger. Landing Slice 2's concrete driver
was removed after saving 27,201 final code bytes, 5,567 bytes short of its
frozen acceptance gate.

The line is complete only when:

- the maintained measurement suite distinguishes declared/dead-stripped entity
  scale from reachable generated adapter scale;
- the exact downstream receipt identifies its source, toolchain and artifacts;
- common page execution, continuation validation and row preparation no longer
  specialize over `E`;
- the prepared-page result retains at least 32 KiB of final code saving without
  an entity-scaled shim family;
- generated bindings consume static data-only descriptors while accepted
  snapshots remain runtime authority;
- exact-key lookup and same-entity typed batches return prepared rows from
  concrete terminals;
- parallel structural encoders enabled only by missing IcyDB terminals are
  removed from the proving consumer;
- focused semantic, instruction, public surface, persisted-byte and cursor
  gates pass;
- final raw/code/function/indirect and per-reachable-entity deltas are recorded;
- the maintained reachable-entity comparison passes the 2 KiB final raw
  ceiling without weakening the existing schema-cardinality control; and
- no rejected callback, compatibility path or second execution owner remains.
