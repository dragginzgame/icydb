## Frozen Identity Decision

The existing implementation is simpler than the original 0.216 design
assumed:

- `RuleSourceKey` is the validated bounded local rule name;
- one source declaration is identified by
  `(TypeSourceKey, RuleSourceKey)`;
- reachable-rule discovery deduplicates that pair; and
- each persisted-root use derives its `ConstraintSourceKey` from
  `(FieldSourceKey, TypeSourceKey, RuleSourceKey)`.

The constraint derivation is frozen as:

~~~text
"rule:" + lowercase_hex(
    sha256(
        "icydb:constraint-source:targeted-field-rule:v1"
        || u32_be(field.len) || field
        || u32_be(target.len) || target
        || u32_be(rule.len) || rule
    )
)
~~~

All three inputs are canonical source-key strings bounded to 128 bytes. The
result is 69 bytes. The maintained golden vector is:

~~~text
field/user/age
type/age
rule/range

rule:9ec7c7a93d5c6ee1f23f0310ee6b58113454a1e04c2eb0f34f3748e2c5c2e260
~~~

The derivation excludes Rust paths, declaration order, operation, operands,
and generated token order. Patch 3 preserves it exactly. A changed local rule
or type name remains remove/add until the 0.218 migration owner exists.

Primary owners:

- `crates/icydb-schema/src/key.rs` owns bounded source keys and the
  constraint-key derivation;
- `crates/icydb-model/src/fragment.rs` owns reachable source-rule discovery
  and one root/type/rule lowering path; and
- `crates/icydb-schema/src/fragment.rs` owns the proposal fragment shape.

## Grammar And Operation Contract

### Current 0.215.7 Form

~~~rust
rule(
    name = "range",
    kind = "numeric_range_inclusive",
    args(0, 100)
)
~~~

`crates/icydb-model-macros/src/node/type.rs` parses `name`, a string `kind`,
and positional `Args`. `crates/icydb-model/src/node/type.rs` validates the
closed three-operation set and expected argument count.

| Current operation | Positional operands | Current source/accepted meaning |
| --- | --- | --- |
| `length_range_inclusive` | `min`, `max` | inclusive logical-length range |
| `numeric_minimum_inclusive` | `value` | inclusive exact numeric minimum |
| `numeric_range_inclusive` | `min`, `max` | inclusive exact numeric range |

### Frozen 0.216 Form

~~~rust
rule(name = "length", length_range_inclusive(min = 1, max = 40))
rule(name = "minimum", numeric_minimum_inclusive(value = 0))
rule(name = "maximum", numeric_maximum_inclusive(value = 100))
rule(name = "range", numeric_range_inclusive(min = 0, max = 100))
rule(name = "step", multiple_of(divisor = 5))
~~~

Exactly one operation is required. Operation-specific named operands are
closed: no `kind` string, `args`, catch-all map, general value, callback, or
arbitrary expression survives.

Patch 3 adds these variants to `SourceRuleAuthoringOperation`; Patch 4 appends
their exact target-bound forms to the proposal and accepted operation enums:

~~~rust
NumericMaximumInclusive { value: ScalarLiteral }
MultipleOf { divisor: ScalarLiteral }
~~~

Minimum, maximum, and range admit literals exactly against every accepted
numeric kind supported by the existing targeted evaluator. Length operands
are `u64`; length applies only to the current eligible text, blob, or
collection targets. `MultipleOf` applies only to exact integer and fixed-scale
decimal targets, rejects zero and inexact divisors, and has no float form.

Rule names are nonempty canonical schema names, at most 128 bytes, and unique
within one named type. The parser rejects missing, repeated, unknown, or
cross-operation operands before proposal construction.

## Invocation And Authority Map

| Boundary | Input authority | What executes | Database effect |
| --- | --- | --- | --- |
| Source macro expansion | authored type metadata | parser and model validation | none |
| Model fragment lowering | generated proposal model | reachable rule discovery and typed lowering | proposal only |
| Schema acceptance | `SchemaProposal` | root/target binding and exact literal admission | accepted constraint or activation |
| Typed, structural, SQL, or batch write | accepted schema snapshot | compiled accepted targeted-rule evaluator on final after-images | authoritative admission |
| Quick/deep integrity | accepted schema snapshot | accepted targeted-rule inspection | reports only |
| `icydb_model::normalize` | application value | preorder `normalize_self`, `normalize_custom`, then children | mutates caller value only |
| `icydb_model::validate` | application value | preorder `validate_self`, `validate_custom`, then children | application issues only |
| Recovery, replay, retry, derived work | durable database state | no application callback | accepted-state recovery only |

The only public application entry points today are
`normalize(&mut dyn Visitable)` and `validate(&dyn Visitable)`. There is no
composed API at the freeze. Patch 5 may add the accepted explicit
normalize-then-validate convenience without changing the callback-free write
boundary.

Accepted runtime ownership is concentrated in:

- `crates/icydb-core/src/db/schema/application_lowering.rs` for proposal
  binding and accepted/activation construction;
- `crates/icydb-core/src/db/schema/check/targeted.rs` for the sole compiled
  targeted evaluator;
- `crates/icydb-core/src/db/schema/check/compile.rs` for its integration with
  accepted row constraints; and
- `crates/icydb-core/src/db/schema/integrity/constraint.rs` for accepted-native
  integrity inspection.

Generated models never become runtime fallback authority. Application
normalizers and validators do not enter SQL, structural writes, mutation
admission, activation, recovery, replay, or integrity.

## Proposal And Persisted Format Freeze

### Current Form

- `ProposalContractVersion::CURRENT = 1` (`u16`).
- Proposals and fragments use canonical Candid encoding.
- One encoded fragment is bounded to 512 KiB; one proposal to 2 MiB.
- One proposal has at most 1,024 fragments; one fragment has at most 256
  accepted constraint declarations.
- The nested source operation enum contains exactly the three current
  operations in the grammar table.
- The accepted snapshot is version 1, canonical Candid, bounded to 512 KiB,
  with contract profile `ICYT`.
- Accepted source and activation operations mirror the same three variants and
  store exact numeric operands as `AcceptedCheckLiteralV1`.

There is no separate proposal profile and no legacy proposal decoder.

### Frozen 0.216 Current Form

Patch 4 changes the sole version-1 proposal shape in place by appending
`NumericMaximumInclusive` and `MultipleOf`. It atomically changes the accepted
snapshot profile to `ICYU` (`49 43 59 55`). It adds no proposal version 2,
legacy decoder, compatibility alias, dual read, or dual write.

Accepted targeted-operation fingerprint tags are frozen as:

| Operation | Tag |
| --- | ---: |
| `LengthRangeInclusive` | 1 |
| `NumericMinimumInclusive` | 2 |
| `NumericRangeInclusive` | 3 |
| `NumericMaximumInclusive` | 4 |
| `MultipleOf` | 5 |

The accepted semantic fingerprint domain remains
`icydb.accepted-schema.semantic.v1`; it consumes the exact current snapshot
bytes. Rows, row keys, layouts, indexes, relations, journals, commit markers,
cursors, integrity progress, and public Candid responses do not change in
0.216 Patch 4. Development stores encoded with `ICYT` must be recreated.

## Evolution Boundary

Patch 6 routes a same-identity operation or operand edit through the existing
catalog-native constraint transition. The old accepted rule and one exact
same-ID activation coexist while the candidate gates new writes and historical
proof runs. Direct proof promotes immediately; durable proof uses the existing
activation job, publication, recovery, and integrity owners. Promotion replaces
the accepted operation under the stable ID, while abort retains the prior
operation and source binding. No source-rule-specific migration engine or
inferred rename exists.
