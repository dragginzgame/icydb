# 0.216 Explicit Application Behavior And Durable Rule Ergonomics

Status: proposed

Design cut: 2026-07-28

Implementation order: after 0.215 closeout

Maintained baseline: 0.213.39 N1-N7 complete

## Decision Summary

0.216 makes the application-behavior and reusable durable-rule surfaces
established by 0.213 easier to author, review, evolve, and diagnose. It does
not reopen their ownership.

The maintained separation remains:

1. a durable rule is explicit bounded source metadata that lowers into the
   accepted targeted-rule constraint owned by its persisted root and nominal
   target;
2. the accepted schema and existing accepted evaluator are the only database
   authority for that rule;
3. a validator is explicit application-only checking;
4. a normalizer is explicit application-only transformation; and
5. SQL, structural writes, recovery, integrity checking, and database
   admission never execute or infer Rust callbacks.

The current durable-rule declaration is mechanically precise but unnecessarily
loose:

~~~rust
ty(rule(
    source_key = "icydb.base.rule.num.percent.range.v1",
    kind = "numeric_range_inclusive",
    args(0, 100)
))
~~~

It repeats a global identity, selects a closed operation through a string, and
places typed operands in a positional heterogeneous argument list. Those
degrees of freedom do not represent real variability.

0.216 hard-cuts that spelling to a typed, locally identified declaration:

~~~rust
ty(rule(
    key = "range",
    numeric_range_inclusive(min = 0, max = 100)
))
~~~

The compiler derives the global `RuleSourceKey` from the containing immutable
`TypeSourceKey` and the bounded local rule key. The operation and operands are
represented by one closed typed enum. There is no string dispatch, positional
`Args`, callback path, or second evaluator.

The frozen version-1 rule vocabulary becomes:

- inclusive numeric minimum;
- inclusive numeric maximum;
- inclusive numeric range;
- inclusive text, blob, or collection length range; and
- exact integer or decimal multiple-of.

`MultipleOf` reuses the exact integer/decimal semantics already owned by
accepted checks, but it lowers as a new closed targeted-rule operation rather
than returning to the retired source-rule-as-check path. It does not add a
second runtime evaluator or float semantics. It extends the closed source and
accepted targeted-rule operation enums and is executed by the existing bounded
targeted-rule evaluator. A zero divisor, inexact decimal operand, unsupported
kind, or impossible conversion rejects during proposal construction.

0.216 also freezes explicit application behavior:

- normalization and validation remain separately callable;
- a named convenience operation may compose normalization followed by
  validation, but it is still application-only;
- normalizers run in declared traversal order;
- validators observe the value supplied to validation;
- retries and database recovery never rerun either operation;
- callback identity and diagnostics remain typed application concerns; and
- generated write adapters do not invoke application behavior implicitly.

0.216 consumes the completed 0.213.39 nominal-target contract. A rule on one
named type is instantiated once for each persisted root field whose accepted
type graph reaches that type, and it governs every finite runtime occurrence
below that root, including records, enums, collections, maps, tuples, repeated
values, and recursive named-type graphs. Top-level uses follow the same
targeted-rule path.

0.216 changes only how authors spell and locally identify those rules. It does
not add expanded schema paths, per-route selectors, occurrence-specific
opt-outs, another traversal engine, or another accepted constraint kind.

The line is planned as seven substantive landing patches. It must not begin
until 0.213, 0.214, and 0.215 have their own accepted closeout boundaries.

### Non-Negotiable Invariants

1. Accepted schema snapshots remain the sole runtime authority for durable
   database rules.
2. Generated `EntityModel`, `IndexModel`, type nodes, and rule metadata are
   proposal inputs only; they are never runtime fallback authority.
3. Every durable rule lowers to one accepted targeted-rule constraint for each
   persisted root field whose accepted graph reaches the ruled nominal type.
4. The accepted targeted-rule compiler and evaluator remain the only database
   evaluator for durable rules.
5. No rule is inferred from a Rust callback body, path, function name, type
   name, local key, documentation, or argument convention.
6. The public durable-rule operation is a closed typed enum, not a string plus
   positional arguments.
7. A local rule key is immutable authored identity within one type and is not
   semantic data.
8. The global rule identity is derived only from the containing immutable type
   source identity and the local rule key through one domain-separated
   algorithm.
9. Editing a rule's operands or operation while retaining its local key is a
   semantic schema change, not removal and recreation.
10. Editing a local rule key is an explicit identity replacement. No alias,
    translation, rename map, or compatibility lookup preserves the old key.
11. Reordering declarations or renaming Rust types, modules, fields, or display
    labels does not change rule identity.
12. Copying the same local key onto two different type source identities does
    not create a collision.
13. Local keys are nonempty, bounded, unique within their containing type, and
    validated before proposal lowering.
14. Accepted constraint identity remains derived from the persisted root field
    source identity, target type source identity, and rule source identity.
15. A representable durable restriction is not also attached as a Rust
    application validator.
16. An application validator never claims SQL, structural-write, recovery,
    integrity, or database-wide enforcement.
17. A normalizer never becomes accepted schema, persisted behavior, a recovery
    callback, an implicit write hook, or a database rewrite language.
18. Generated conversion and write adapters do not implicitly normalize or
    validate.
19. A convenience operation that composes application behavior always
    normalizes before it validates and is named so the behavior is visible at
    the call site.
20. Direct validation validates the supplied value; it does not silently
    normalize a copy first.
21. Normalizer and validator failures preserve typed operation identity and
    complete bounded value paths without error-string classification.
22. Normalizer and validator execution order is deterministic and derived from
    the maintained generated traversal, not registration order at runtime.
23. Database retries, statement retries, marker replay, recovery, and
    integrity checking never execute application validators or normalizers.
24. `MultipleOf` is exact for supported integer and decimal kinds, rejects a
    zero divisor, and is never defined through floating-point remainder.
25. Rule literals are admitted once against the exact accepted field kind.
    Runtime evaluation performs no parsing, narrowing, or kind inference.
26. Unsupported rule/kind combinations, unresolved nominal targets, and
    unreachable root/target pairs reject before an accepted candidate can be
    published.
27. A reachable nominal rule applies to every finite occurrence below its
    persisted root. It never disappears, degrades to application validation,
    or applies only to typed writes.
28. Rule evolution uses existing catalog-native accepted-constraint
    reconciliation, activation, bounded proof, publication, and recovery
    ownership.
29. SQL DDL remains a frontend to catalog-native schema mutation. 0.216 does
    not add SQL syntax for source-rule declarations.
30. The authoring cut preserves the 0.213.39 target identity, traversal,
    diagnostic-path, activation, and recovery contracts. New closed operation
    variants change the source and accepted targeted-rule codecs as the
    explicit current-form hard cut described below; row, cursor, journal, and
    marker formats do not change.
31. The old `source_key` plus `kind` plus `args` rule grammar is removed in the
    same patch that introduces the typed grammar.
32. No deprecated grammar, compatibility parser, alias, wrapper, dual macro
    expansion, feature flag, or anti-resurrection test is retained.
33. Public documentation explains durable rules, validators, and normalizers
    as three different authorities and does not imply interchangeable
    enforcement.
34. The no-rule database write path performs no per-row source-rule work.
35. Raw non-gzipped Wasm bytes are the primary size evidence. Gzip is
    secondary context.
36. 0.216 does not introduce a generic policy, callback, plugin, annotation,
    reflection, or migration framework.

## Normative Contract

The durable-rule contract is:

> A durable rule is bounded compiler-authored metadata owned by one reusable
> source type. Each persisted root field that can reach the ruled nominal type
> instantiates the rule as one accepted targeted-rule constraint. That
> constraint governs every finite occurrence of the target below that root.
> Runtime enforcement, reconciliation, activation, recovery, integrity
> verification, and diagnostics consume that accepted constraint and never
> the source model.

The application-validation contract is:

> A validator is an explicitly invoked Rust application check. It may express
> behavior outside the accepted database language, but it has no database-wide
> enforcement claim and is never invoked by database admission.

The application-normalization contract is:

> A normalizer is an explicitly invoked Rust application transformation. It
> changes an authored application value before the caller submits that value.
> It is not accepted schema and is never repeated by retries, recovery, SQL, or
> structural mutation lanes.

The identity contract is:

> One source type owns one immutable `TypeSourceKey`. Each durable rule within
> that type owns one short immutable local key. The compiler derives the
> `RuleSourceKey` from those two facts. Semantics may evolve under the same
> identity; identity changes only when the author changes the local key or the
> containing type source identity.

The hard-cut contract is:

> The maintained authoring surface accepts the typed rule grammar only.
> Pre-0.216 source declarations are edited directly. IcyDB does not parse,
> translate, preserve, or test the retired grammar.

## Current State And Problem

0.213.39 established the correct ownership shape:

- reusable model types may carry explicit source-rule metadata;
- fragment lowering derives one root/target/rule constraint source identity;
- the proposal contains one targeted rule per reachable persisted-root and
  nominal-target pair;
- accepted-schema construction binds and compiles that targeted rule;
- all write lanes and integrity verification use the accepted evaluator;
- supported built-in numeric and length restrictions no longer retain
  equivalent Rust validators; and
- nested and recursive occurrences use one bounded accepted traversal with
  stable concrete diagnostic paths.

The remaining weakness is authoring shape, not runtime authority.

### Loose Operation Selection

The macro parser accepts a string such as
`"numeric_range_inclusive"` and translates it to a closed enum. The string is
not genuine extensibility. It delays typo and operand-shape failures, obscures
editor support, and makes generated examples harder to understand.

### Positional Untyped Operands

All source-rule operands currently travel through a general `Args` collection.
The rule node then checks argument count and numeric shape. The type system
already knows whether an operation needs `min`, `max`, or `divisor`; the
transport does not encode that invariant.

### Repeated Global Rule Identity

Authors currently supply a fully qualified rule source key in every rule
declaration even though the containing type already has an immutable source
identity. Long manually repeated keys are easy to copy incorrectly and make a
local reusable constraint appear globally registered.

### Application Behavior Discoverability

`normalize()` and `validate()` are correctly explicit, but the public contract
must make their ordering and composition unambiguous. Users should not have to
guess whether validation normalizes, whether write adapters invoke either
operation, or whether a retry can run a normalizer twice.

### Incomplete Frozen Vocabulary

0.213 classified exact numeric/decimal multiple-of as accepted-constraint
behavior, and the accepted check evaluator already owns its exact arithmetic.
The current targeted-rule operation enum does not expose it, leaving a
representable reusable rule without the maintained durable authoring path.

### Nominal Target Semantics Must Stay Closed

0.213.39 made nested durable rules accepted-native by selecting one nominal
target below one persisted root. The accepted target is not an expanded route:
the same ruled type reused through several branches below one root remains one
constraint, and every finite occurrence is evaluated.

An ergonomics change must not accidentally reintroduce route identity,
generate one constraint per occurrence path, or let an author opt out of one
record member, collection position, or recursive branch. Those would change
cardinality, identity, evolution, and runtime semantics and require a separate
design.

## Authority Map

| Concern | Sole owner | Source-model input | Runtime consumers |
| --- | --- | --- | --- |
| Type identity | `TypeSourceKey` in the authoring graph | explicit type `source_key` | fragment lowering and reconciliation identity |
| Local rule identity | containing type declaration | bounded `key` | rule-source derivation only |
| Global rule identity | model compiler | type source identity plus local rule key | targeted constraint identity derivation |
| Rule operation and operands | typed `SourceRule` variant | typed macro form | fragment lowering |
| Root/target constraint identity | schema fragment lowering | persisted root field source plus target type source plus rule source | accepted source catalog |
| Accepted rule meaning | accepted constraint catalog | lowered targeted rule | admission, activation, recovery, integrity, introspection |
| Rule compilation | accepted targeted-rule compiler | accepted target and operation | compiled accepted-rule cache |
| Rule evaluation | accepted targeted-rule evaluator | compiled nominal traversal and operation | every maintained mutation ingress and integrity |
| Application validation | `icydb-model` generated traversal | explicit validator attachments | explicit application calls only |
| Application normalization | `icydb-model` generated mutable traversal | explicit normalizer attachments | explicit application calls only |
| Schema evolution | catalog-native schema mutation | changed proposal facts | activation/publication/recovery machinery |
| SQL mutation enforcement | accepted write admission | final after-image | SQL write frontend |
| Diagnostics | typed owner at each boundary | stable identities and paths | Rust, generated, SQL, and CLI projections |

There is no source-rule registry at database runtime. There is no callback
registry in accepted schema. The table describes one lowering chain, not
several synchronized authorities.

## Typed Durable-Rule Authoring

### Public Grammar

The proposed macro grammar is:

~~~rust
#[newtype(
    source_key = "app.type.rating.v1",
    primitive = "Nat8",
    item(prim = "Nat8"),
    ty(
        rule(
            key = "range",
            numeric_range_inclusive(min = 10, max = 100)
        ),
        rule(
            key = "step",
            multiple_of(divisor = 5)
        )
    )
)]
pub struct Rating {}
~~~

Exactly one operation appears in each `rule(...)`. The parser rejects:

- a missing operation;
- multiple operations;
- unknown operation names;
- operands belonging to another operation;
- missing or repeated operands;
- unknown operands;
- an empty, malformed, oversized, or duplicate local key; and
- a literal that cannot be admitted exactly for the declared primitive.

The parser does not retain a catch-all `args(...)` field. The generated schema
node does not retain a string operation name.

### Source Representation

The target authoring representation is conceptually:

~~~rust
pub struct SourceRule {
    local_key: RuleLocalKey,
    operation: SourceRuleOperation,
}

pub enum SourceRuleOperation {
    LengthRangeInclusive { min: ExactNat, max: ExactNat },
    MultipleOf { divisor: ExactNumber },
    NumericMaximumInclusive { value: ExactNumber },
    NumericMinimumInclusive { value: ExactNumber },
    NumericRangeInclusive { min: ExactNumber, max: ExactNumber },
}
~~~

The exact implementation may use bounded literal nodes already owned by
`icydb-schema`, but it must preserve the invariant-bearing shape above. It
must not use `Args`, `Vec<Value>`, `AnyValue`, `serde_json::Value`, or another
general transport.

`RuleLocalKey` is a bounded authoring identity. It is not public runtime state
and does not enter accepted schema separately from the derived constraint
source identity.

### Identity Derivation

The global key is derived as:

~~~text
RuleSourceKey =
    domain_hash(
        "icydb.rule-source.v1",
        TypeSourceKey,
        RuleLocalKey
    )
~~~

The exact byte framing, domain label, maximum input lengths, and output
encoding must be frozen by golden-vector tests before implementation lands.
Concatenation without length or field framing is forbidden.

The derivation does not include:

- Rust module or type path;
- display name;
- operation variant;
- operands;
- declaration ordinal;
- field identity; or
- generated token order.

Those exclusions are intentional. A semantic edit under the same local key
must reconcile the existing rule identity. A persisted root/target use is
distinguished later when fragment lowering derives its
`ConstraintSourceKey`.

### Local-Key Evolution

The authoring rules are:

- keep the local key when changing the rule's supported operands or operation
  as an intentional semantic evolution;
- change the local key only when replacing the rule's identity;
- use different local keys for distinct restrictions on one type;
- never encode version numbers in a key merely because operands change; and
- never recover a removed key through an alias.

A rule identity replacement is subject to the same ownership and removal
checks as other source-owned accepted constraints. It is not an in-place
rename.

## Frozen Rule Vocabulary

### Numeric Minimum

~~~rust
rule(
    key = "nonnegative",
    numeric_minimum_inclusive(value = 0)
)
~~~

The operand must be exactly representable by the newtype's accepted numeric
kind. The rule lowers to the canonical accepted targeted minimum operation
applied to every selected nominal value. It does not introduce a special
minimum evaluator.

### Numeric Maximum

~~~rust
rule(
    key = "maximum",
    numeric_maximum_inclusive(value = 100)
)
~~~

The operand must be exactly representable by the newtype's accepted numeric
kind. The rule lowers to the canonical accepted targeted maximum operation
applied to every selected nominal value. It does not require an artificial
lower bound and does not introduce a special maximum evaluator.

### Numeric Range

~~~rust
rule(
    key = "range",
    numeric_range_inclusive(min = 10, max = 100)
)
~~~

Both operands must be exactly representable and `min <= max` under the exact
accepted kind semantics. Lowering uses the existing canonical accepted
targeted inclusive-range operation.

### Length Range

~~~rust
rule(
    key = "length",
    length_range_inclusive(min = 1, max = 64)
)
~~~

`min` and `max` are exact nonnegative cardinalities with `min <= max`.
Semantics remain those frozen by the accepted targeted-rule contract:

- Unicode scalar count for text;
- octet count for blobs; and
- logical cardinality for a directly eligible collection value.

The source compiler rejects a kind whose accepted targeted operation cannot
express the documented measure. It never substitutes encoded byte length.

### Multiple Of

~~~rust
rule(
    key = "step",
    multiple_of(divisor = 5)
)
~~~

`MultipleOf` is supported only for exact integer and fixed-scale decimal
accepted kinds already supported by the accepted numeric operation. The
divisor:

- must be nonzero;
- must be exactly admitted against the accepted numeric kind;
- uses the existing exact signed/unsigned/decimal semantics;
- does not use binary float remainder;
- does not round or normalize an authored value; and
- produces the same accepted targeted operation regardless of generated or
  manually authored proposal origin.

Float, cross-kind, row-dependent, callback-defined, or approximate
multiple-of semantics reject.

### Deliberately Excluded Rules

0.216 does not add durable regex, URL, MIME, phone, ISO, hash, case, locale,
authorization, external lookup, arbitrary predicate, or callback rules.
Those remain application validators unless a later design freezes a bounded
accepted database expression for them.

Enum membership remains an accepted enum/type fact where possible. Not-null
remains a structural constraint. Decimal scale remains an accepted field-kind
fact. Managed timestamps and generated identities remain write policies.
Normalizing trim, case conversion, and rounding remain application behavior.

## Placement And Reuse

A durable rule is reusable below every persisted root field whose accepted
nominal graph reaches the ruled type. The same rule governs direct uses and
every finite occurrence through records, enums, lists, sets, maps, tuples,
repeated values, newtypes, and recursive named-type graphs.

For example, `Rating` may be used by many entities and every reachable
persisted-root use receives its own accepted constraint identity derived from:

~~~text
persisted root field source identity
    + Rating type source identity
    + Rating rule source identity
~~~

The reusable type does not create one global database constraint shared by all
entities, nor one constraint per route below a root. Fragment lowering emits
one source-bound targeted rule for the root/type/rule identity, and accepted
evaluation visits every finite occurrence. A violation reports the first
deterministic concrete path, but that path is evidence rather than constraint
identity.

0.216 may improve the typed spelling of the operation and local rule key. It
must not add route selectors, occurrence-specific opt-outs, expanded
schema-path identity, or a second nested traversal.

## Explicit Application Behavior

### Separate Operations

The maintained direct operations remain conceptually:

~~~rust
icydb_model::normalize(&mut value)?;
icydb_model::validate(&value)?;
~~~

Generated types may expose equivalent methods. A direct `validate()` call
never normalizes. A direct `normalize()` call never claims that validators
have passed.

### Named Composition

One convenience operation may be provided:

~~~rust
let value = authored.normalize_and_validate()?;
~~~

Its exact receiver/return shape is selected during the application-surface
patch, but its semantics are fixed:

1. operate on an application-owned value;
2. run the complete generated normalizer traversal;
3. stop and return typed normalization errors if normalization fails;
4. validate the resulting value through the complete generated validator
   traversal; and
5. return the normalized value only when both stages succeed.

It does not:

- evaluate accepted database constraints;
- open or resolve a database binding;
- persist a value;
- retry callbacks;
- hide a write;
- run automatically from `insert_typed`, `save`, structural mutation, or SQL;
  or
- imply that application validation is database enforcement.

If one convenience method cannot express the ownership cleanly without
allocating or cloning large values, 0.216 retains only the two explicit calls.
The implementation must not add a framework merely to provide chaining.

### Deterministic Traversal

Normalizers execute in the generated declaration and value-traversal order
frozen by `icydb-model`. Validators execute through the corresponding
read-only traversal. Map and set traversal must use their canonical generated
order rather than hash iteration.

The order is an application contract, not accepted schema. Reordering
normalizer declarations may change application output and must be visible in
source review. Validator ordering may affect diagnostic order but never
database acceptance.

### Retry Boundary

Application behavior executes only when application code explicitly requests
it. Once a value crosses into an IcyDB mutation:

- the mutation carries authored intent or a canonical value;
- accepted write policy constructs the final after-image;
- accepted constraints validate that after-image;
- a retry reuses or reconstructs database-owned mutation state according to
  the maintained mutation contract; and
- no application callback is invoked.

Normalizers therefore need not be made safe for database replay. Applications
remain responsible for avoiding accidental repeated explicit normalization if
a normalizer is not idempotent.

## Schema Evolution

Changing a durable rule while preserving its local key changes the proposed
accepted constraint meaning under one source identity.

The existing catalog-native owner decides whether the change:

- can be proved atomically within the direct bound;
- requires a bounded activation;
- conflicts with an existing activation;
- is unsupported for the affected accepted schema; or
- must reject before publication.

0.216 does not add a source-rule-specific scanner, job, staging store,
publication controller, or recovery path.

Future writes must never begin using changed rule semantics before the
accepted transition and any required gate are atomically authoritative.
Existing rows must never be declared valid without the proof required by the
accepted constraint design.

Changing or removing an application validator or normalizer has no accepted
schema, row-layout, recovery, integrity, or persisted-format effect.

## Diagnostics

Durable-rule authoring failures use typed source-model diagnostics. They
identify the type source, local key, operation, operand, and persisted-root or
nominal-target context needed to correct the declaration.

After lowering, database diagnostics use accepted constraint identity. They
must not leak the source macro's string spelling or depend on the generated
model being present.

Application behavior failures preserve:

- whether the failure came from normalization or validation;
- the declared callback/type identity;
- the bounded logical value path;
- typed child causes; and
- deterministic aggregation order.

They must not be parsed from prose to select behavior. A validator and an
accepted constraint that happen to describe similar concepts remain different
error domains because their authorities differ.

## Public And Generated Surface

0.216 may change:

- `icydb-model` source-rule authoring nodes;
- `icydb-model-macros` rule parsing and generated metadata;
- source and accepted targeted-rule operation enums, codecs, and
  fingerprints;
- generated application-only normalization/validation convenience methods;
- typed application behavior errors;
- model/base reusable type declarations; and
- public documentation and examples.

0.216 does not add:

- a database callback registration API;
- a public accepted-expression builder through the rule macro;
- a general runtime value type;
- a caller-authored accepted constraint ID;
- SQL source-rule DDL;
- runtime source-model loading;
- persisted callback identity;
- dynamic callback dispatch; or
- an application behavior hook in mutation admission.

Public types expose only variability that callers can legitimately choose.
Compiler-only local-key and operation nodes should remain compiler/model
surface rather than being re-exported through the top-level database prelude
unless a demonstrated source-authoring use requires them.

## Persistence And Hard Cut

0.216 preserves the 0.213.39 targeted-rule kind and target representation, but
it is not codec-neutral:

At the maintained N7 baseline, `ProposalContractVersion::CURRENT` is `1` and
the accepted schema snapshot is version 1 with contract profile `ICYT`.

- source rules continue to lower only to the existing targeted-rule
  representation;
- `NumericMaximumInclusive` and `MultipleOf` extend the closed source and
  accepted targeted-operation enums;
- the sole version-1 `SchemaProposal` contract hard-cuts its nested
  fragment/operation shape in place, with no version-2 wrapper or old-shape
  decoder;
- the accepted-schema codec/fingerprint moves directly to one new current
  contract profile;
- rule local keys are compiler input and do not persist as parallel runtime
  authority;
- the derived rule identity occupies the existing root/target/rule
  constraint-source identity position; and
- rows, layouts, indexes, relations, journals, markers, cursors, and integrity
  progress do not change.

Patch 1 freezes the exact replacement accepted-profile identity before
implementation. Patch 3 hard-cuts the version-1 proposal shape and replaces
`ICYT` atomically with the new operation variants, then updates the
persisted-format inventory. The retired proposal shape and `ICYT` profile
receive no dedicated decoder, translation, or fallback.

Because global rule source identity changes from an authored global string to
a derived key, existing development accepted schemas may no longer reconcile
with newly generated proposals. Before 1.0.0 the resolution is an explicit
hard cut:

- development stores may be recreated;
- no old-key lookup is retained;
- no alias maps old keys to new keys;
- no decoder rewrites old keys;
- no proposal emits both keys;
- no migration guesses correspondence from kind and operands; and
- no test preserves the old authoring or accepted identity.

The implementation release notes must state the recreation requirement
precisely if maintained development stores from the preceding release are
affected.

## Performance And Complexity Budget

The expected runtime database effect is neutral:

- no-rule writes execute no source-rule-specific work;
- existing ruled writes use the existing accepted targeted evaluator;
- the new maximum and multiple-of branches execute only for explicitly
  declared rules;
- accepted targeted rules remain compiled once per accepted fingerprint;
- application validators and normalizers run only on explicit application
  calls; and
- no source graph ships as database runtime authority.

The implementation must measure:

- representative no-rule and ruled write instructions;
- explicit normalize, validate, and composed-call instructions where the
  convenience operation lands;
- generated token and compile-time change for representative ruled types;
- raw non-gzipped Wasm bytes for the maintained comparison canister;
- gzip only as secondary context;
- host package size where typed rule nodes change it; and
- files touched, approximate line delta, and complexity direction per landing
  patch.

The primary complexity goal is a net reduction:

- delete string rule dispatch;
- delete positional source-rule argument validation;
- derive rather than repeat global rule keys;
- do not add a second evaluator;
- do not add an expanded or route-specific nested-path framework;
- do not add callback registration; and
- do not add compatibility machinery.

A convenience application API is rejected if it requires more state,
dispatch, cloning, or error translation than the two explicit operations it
would compose.

## Failure Model

Failures before accepted schema include:

- invalid or duplicate local rule key;
- malformed typed rule operands;
- unsupported rule/kind combination;
- inexact or out-of-range literal;
- inverted range;
- zero `MultipleOf` divisor;
- derived identity collision; and
- invalid model traversal or callback attachment.

Failures during schema evolution use the existing typed accepted-schema and
activation errors. Failures during mutation use the existing typed accepted
constraint violation. Application normalization and validation failures stay
in their application error domain.

No failure is converted to:

- silent rule omission;
- generated-only enforcement;
- `Unknown` accepted-check success caused by corrupt metadata;
- callback fallback;
- default or zero operands;
- generic boxed prose;
- panic or assertion in maintained production paths; or
- compatibility reconstruction.

## Validation Plan

### Rule Grammar And Identity

- compile-pass coverage for every typed rule operation;
- compile-fail coverage for missing, duplicate, unknown, and cross-operation
  operands;
- exact literal admission for every supported integer and decimal kind;
- zero-divisor and inverted-range rejection;
- local-key grammar, length, and per-type uniqueness;
- golden vectors for domain-separated rule-source derivation;
- identity stability across Rust rename, module move, display rename,
  declaration reorder, and operand edit;
- identity difference across local-key and type-source-key changes; and
- per-root constraint identity difference for repeated uses.

### Lowering And Accepted Semantics

- each operation lowers to the exact canonical accepted targeted operation;
- generated and directly constructed proposals produce identical accepted
  meaning;
- no application validator is emitted for a durable rule;
- accepted evaluation parity across typed, structural, SQL, batch, recovery,
  and integrity-relevant paths;
- exact integer and decimal `MultipleOf` boundaries;
- text/blob/collection length unit semantics;
- direct, nested, repeated, and recursive nominal-target resolution;
- unsupported kind/operation rejection;
- current source/accepted codec round trips and typed rejection of noncurrent
  profiles; and
- no source-model dependency after accepted runtime construction.

### Application Behavior

- explicit normalize-only behavior;
- explicit validate-only behavior;
- normalize-then-validate composition when retained;
- deterministic nested traversal and diagnostic ordering;
- typed path and callback identity preservation;
- no implicit behavior in generated conversion or write adapters;
- no behavior in SQL, structural writes, recovery, or integrity;
- no retry invocation; and
- package-shaped downstream examples using the real macro expansion.

### Evolution And Recovery

- semantic rule edit under stable identity;
- direct clean publication where bounded;
- activation where historical proof is required;
- failure and abort leave accepted authority unchanged;
- local-key replacement follows explicit remove/add ownership;
- recovery resumes accepted transition state without the source model;
- validator/normalizer edits have no schema fingerprint or persisted effect;
  and
- development stores with old rule identity fail or require recreation exactly
  as the hard cut documents.

### Structural Guards

- no source-rule string dispatch or positional `Args` remains;
- no runtime generated-model fallback;
- no application callback path enters accepted schema;
- no duplicate durable/application evaluator for maintained base types;
- no nested durable rule silently disappears;
- no compatibility parser, alias, or old grammar test remains;
- no public re-export exposes compiler-only internals without a current
  consumer; and
- no new persisted family is omitted from the format inventory.

### Focused Release Evidence

Each patch runs only the focused package, target, and named tests affected by
that patch. The human push workflow owns the full workspace suite. Closeout
evidence must additionally include repository architecture/layering guards,
generated downstream checks, warnings-denied focused Clippy, formatting,
raw-Wasm comparison, and diff hygiene.

## Non-Goals

0.216 does not:

- infer durable behavior from Rust;
- persist Rust callback paths;
- execute callbacks from IcyDB;
- add accepted normalizers, triggers, rewrites, or computed columns;
- add arbitrary custom accepted predicates;
- make application validators authoritative for SQL or structural writes;
- automatically invoke application behavior from write adapters;
- add expanded or route-specific accepted field-path rules;
- add regex or locale semantics;
- add floating-point `MultipleOf`;
- merge not-null, enum membership, field kind, generated values, managed
  timestamps, or relation rules into the source-rule enum;
- expose accepted constraint IDs for authors to allocate;
- add compatibility for the retired source-rule grammar or identity;
- migrate old development stores automatically;
- add a general rule registry, provider, plugin, callback, or policy
  framework;
- redesign accepted constraint activation;
- redesign integrity checking;
- change query, cursor, index, relation, or row-layout semantics; or
- start 0.216 implementation before 0.215 closeout.

## Acceptance Decision

This design is ready for review as a future line, not implementation.

Review should decide only whether the typed grammar, derived identity, exact
`MultipleOf`, explicit application behavior, and preservation of the completed
nominal-target contract are the right bounded 0.216 contract. It should not
reopen the 0.213 decision that accepted schema owns database semantics and
Rust validators/normalizers are application behavior.
