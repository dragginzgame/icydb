# 0.216 Duplicate-Shape Follow-up Audit

## Verdict

The approved deletion patches are behavior-neutral and pass their focused and
feature-matrix validation. No failure caused by those patches was found.

The aggregate representation and index-prefix cardinality lookup
consolidations were subsequently implemented as separate bounded patches.

The crate-level query-without-SQL `dead_code` expectation remains necessary.
The bounded reexport cleanup completed below makes the separate
`unused_imports` expectation removable without moving engine-neutral
implementation beneath SQL authority.

This audit does not change public APIs, persisted formats, response formats,
query semantics, execution behavior, or storage behavior.

## Worktree scope

The validated deletion work consists of three independent changes:

- one `AggregateCacheKey` now owns projected and grouped aggregate cache
  identity;
- direct and kernel row scanning now share `RowScanResult<T>`; and
- the empty aggregate spec forwarding module and three empty inherent impls
  are removed.

Concurrent macro, model, facade, fixture, and 0.216 design/status edits were
present in the worktree. They were preserved and are not findings of this
audit. The feature and facade builds necessarily compiled their current state,
but this report does not claim to review those unrelated edits.

## Patch 2 implemented: canonical raw aggregate shape

### Implementation result

`AggregateShape` now owns the four raw fields in the engine-neutral query plan
layer. `AggregateExpr` and `GroupAggregateSpec` each wrap that shape and retain
their original equality contracts. Raw explain/admission DISTINCT reads are
now explicit, while semantic planning and execution continue through
`AggregateIdentity` and `AggregateSemanticKey`.

### Prior duplication

Before this patch, `AggregateExpr` in
`crates/icydb-core/src/db/query/builder/aggregate/expr.rs` and
`GroupAggregateSpec` in
`crates/icydb-core/src/db/query/plan/model.rs` independently owned:

```text
kind: AggregateKind
input_expr: Option<Box<Expr>>
filter_expr: Option<Box<Expr>>
distinct: bool
```

`GroupAggregateSpec::from_aggregate_expr` copied all four fields. Grouped
projection lowering later reconstructed an `AggregateExpr` through
`group_aggregate_spec_expr`. The duplicate storage was accidental; the two
equality contracts are not.

### Exact equality contracts

`AggregateExpr` has raw declaration equality:

- kind is significant;
- the structurally canonicalized input expression is significant;
- the filter expression is significant; and
- the authored DISTINCT bit is significant for every kind.

Consequently `min_by("x")` and `min_by("x").distinct()` are unequal as builder
values even though DISTINCT cannot alter MIN's result.

`GroupAggregateSpec` has semantic plan equality through
`AggregateSemanticKey`:

- kind is significant;
- filter expression is always significant;
- DISTINCT is ignored for MIN and MAX;
- DISTINCT remains significant for COUNT, SUM, AVG, EXISTS, FIRST, and LAST;
- non-distinct COUNT of a non-null literal is equal to COUNT rows; and
- other input-expression differences remain significant.

This semantic equality flows into `GroupSpec` and `GroupPlan` equality. It must
not be replaced with raw field equality.

The current plan-to-builder projection also normalizes the DISTINCT bit for MIN
and MAX. That round trip must remain unchanged. Explain projection and admission
summary, by contrast, currently observe the raw authored DISTINCT bit and must
continue to do so.

### Owner and shape

A private `AggregateShape` now lives at:

`crates/icydb-core/src/db/query/plan/aggregate_shape.rs`

It owns the four raw fields and raw accessors. The existing wrappers remain:

```text
AggregateExpr     { shape: AggregateShape }  -- raw PartialEq/Eq
GroupAggregateSpec { shape: AggregateShape } -- semantic PartialEq/Eq
```

The builder already depends on planner-owned `AggregateKind`, `Expr`, and input
canonicalization, so this location introduces no dependency reversal. The
shape must remain internal; it is not a new public query DTO.

Distinct meanings are explicit at call sites:

- `raw_distinct()` for explain and admission syntax accounting;
- `semantic_distinct()` for execution, strategy, hashing, and validation; and
- `semantic_key()` for plan equivalence and aggregate deduplication.

`group_aggregate_spec_expr` constructs from the shared shape while applying
exactly the existing semantic DISTINCT normalization; it does not return a raw
clone accidentally.

### Call-site consequences

The consolidation preserves these consumers:

| Consumer | Required meaning |
|---|---|
| `QueryIntent::push_group_aggregate` | clone raw declaration into plan wrapper |
| `GroupSpec` / `GroupPlan` equality | semantic equality |
| explain grouping | raw kind/input/filter/DISTINCT response values |
| admission summary | raw DISTINCT declaration count |
| grouped projection lowering | current normalized plan-to-expression round trip |
| HAVING matching and SQL aggregate lowering | semantic key |
| fingerprints and cache keys | semantic aggregate identity |
| grouped strategy and executor compilation | semantic DISTINCT and identity |

`GroupedAggregateExecutionSpec` is not duplicate raw storage. It owns resolved
field slots, compiled expressions, and executor handoff state, so it remains a
separate necessary representation.

### Regression coverage

- raw builder equality distinguishes MIN with and without authored DISTINCT;
- grouped plan equality equates those MIN shapes;
- grouped plan equality equates non-distinct COUNT(non-null literal) and COUNT
  rows while raw builder equality does not;
- SUM DISTINCT, filters, and non-equivalent inputs remain significant;
- plan-to-builder projection retains current MIN/MAX normalization;
- explain and admission retain raw DISTINCT behavior; and
- existing fingerprint, cache-key, grouped-policy, and aggregate tests remain
  unchanged.

### Format, performance, and Wasm impact

This is an in-memory Rust layout refactor only. It changes no codec, hash
preimage, cursor, response DTO, or accepted schema. Nested single-field wrappers
should optimize to the same runtime layout and accessors should inline. No
meaningful performance or raw Wasm change is expected, but the implementation
was not measured in isolation because the shared dirty worktree contains
concurrent macro and facade changes. The layout and operations are unchanged,
so the expected impact is toolchain-level noise only.

The bounded aggregate patch touches eleven existing production/query files and
adds one internal module. Excluding this report, the changelog, and the two
regression tests, it is approximately 117 net added source lines. Most of that
increase is the documented carrier/accessor boundary; the architecture is
simpler because there is now one field owner and no four-field copy/rebuild
path.

### Resolved naming decision

The implementation uses `AggregateShape`, avoiding conceptual collision with
semantic plan and execution specs.

## Patch 3 implemented: index-owned cardinality lookup key

### Prior duplication

Two types previously had the same lookup payload:

- query-gated `LoweredIndexPrefixCardinalitySpec` in
  `db/access/lowering.rs`; and
- executor-local `LoweredIndexPrefixCardinalityKey` in
  `db/executor/index_prefix_cardinality.rs`.

Both owned an `IndexId` and already encoded `Vec<Vec<u8>>` prefix components.
The executor-local type existed only because executor branch liveness could
not depend on an access-lowering-owned payload.

The private `db::index::cardinality::IndexPrefixCardinalityKey` remains a
different storage concern: it includes `IndexKeyKind`, implements ordered-map
identity, and supports metadata maintenance and range sentinels. It is not the
query/executor lookup DTO.

### Owner and representation

`UserIndexPrefixCardinalityKey` now lives in
`crates/icydb-core/src/db/index/cardinality.rs` and is re-exported internally
from `db::index`. It owns exactly:

```text
index_id: IndexId
prefix_components: Vec<Vec<u8>>
```

The `User` qualifier makes the previously implicit `IndexKeyKind::User`
invariant explicit without adding a discriminant or changing object layout.
It derives `Clone`, `Debug`, `Eq`, and `PartialEq`; no consumer requires `Ord`.

The completed flow is:

- access lowering returns `Vec<UserIndexPrefixCardinalityKey>`;
- the SQL compiled count cache stores that type;
- direct count execution consumes it;
- executor branch liveness constructs the same type; and
- both former duplicate types and their impls are deleted.

Index metadata maintenance keeps its private ordered map key. This preserves a
clean distinction between the engine lookup contract and the store's
multi-kind ordered storage representation.

### Feature consequences

- The owner module remains unconditional, but the lookup type and its internal
  re-export use `cfg(any(test, feature = "query"))`, exactly matching executor
  liveness and query-lowering consumers.
- Query-only and SQL lowering remain feature-gated at their current functions;
  only their payload type moved downward.
- The index layer gained no dependency on access, query, SQL, or executor.
- No feature edge changed.

### Format, performance, and Wasm impact

The shared type has the same two fields and ownership as both former lookup
types. Encoded prefix bytes, metadata lookup arguments, cache contents, and
allocation counts remain unchanged. It is not persisted or returned publicly.
The no-query production build does not compile the type, so this change adds
no mutation-only Wasm surface. Query builds replace one same-layout carrier
with another and delete the second carrier, so no meaningful raw Wasm or
runtime change is expected.

The bounded patch touches ten core files. Excluding its two focused tests,
this report, and the changelog, it removes approximately nineteen net
production lines. The implementation shape is simpler: two lookup carriers
are replaced by one owner, with no additional runtime allocation or dispatch.

### Regression coverage

- the shared key preserves the complete `IndexId`, including physical
  generation, and already encoded component bytes;
- no-feature index-cardinality tests still prove synchronized versus stale
  generation behavior;
- query lowering still produces identical encoded component bytes;
- SQL direct COUNT and compiled-cache tests still pass;
- mixed physical generations remain distinct through `IndexId`; and
- stale cardinality generations still fail open to conservative scanning.

### Retained boundary

`IndexStore::exact_prefix_cardinality` still accepts its explicit
`IndexKeyKind`, `IndexId`, and component arguments. Making it accept the shared
key would widen the mechanical scope across metadata maintenance tests without
removing another representation, so the bounded patch deliberately leaves
that storage lookup boundary unchanged.

### Test-target matrix inventory

- 22 under `query,diagnostics` (the same 15 plus the seven diagnostics

The 15 are exact-cardinality lowering; boolean simplification and truth

structural projection scan/evaluation helpers.

### Correction

Keep the crate-level production expectation. Replacing 742 or 769 deliberate
dormant-item suppressions with item-level attributes would increase noise and
maintenance cost, and gating the entire dormant substrate behind `sql` would
incorrectly make SQL the owner of engine-neutral query code. It could also
materially shrink query-only Wasm, which is outside this behavior-neutral pass.

The implemented patch gates only unused internal re-exports at their actual
consumer boundary after reverse-call verification:

- SQL-owned re-export chains for direct cardinality lowering, boolean
  normalization/admission, SQL function surfaces, cursor response encoding,
  alias construction, predicate test compilation, grouped HAVING/type
  resolution, structural projection DTOs, structural aggregate execution,
  grouped execution, and SQL scan/evaluation helpers now use `feature = "sql"`
  at every forwarding hop.
- SQL diagnostics re-export chains for query compilation, scalar aggregates,
  grouped execution, covering decode/assembly counters, and direct/kernel row
  phase attribution now use
  `all(feature = "sql", feature = "diagnostics")`.
- Query-owned implementations and modules remain under `query`; none moved
  beneath SQL authority.

Warnings-denied all-target Clippy now passes for both `query` and
`query,diagnostics`. The now-unneeded crate-level `unused_imports` expectation
is deleted, so new query-only import drift is once again reported normally. The
production `dead_code` expectation remains: the patch changes internal name
reachability only and does not pretend that the complete neutral substrate is
publicly exercised by every frontend.

The changed items are internal `use` gates only. They add no runtime branch,
allocation, codec, response field, or persisted state. No meaningful raw Wasm
or performance change is expected; no isolated Wasm artifact was measured in
the shared dirty worktree.

The patch touches seventeen module roots plus the crate root and adds five net
source lines because mixed re-export groups were split by consumer while the
obsolete crate-wide import suppression was deleted. Runtime complexity is
unchanged; compile-time visibility is more precise.

### Unresolved decision

The repository still needs an explicit long-term feature contract: does
`query` intentionally compile the complete engine-neutral substrate even when
the public query-only facade has no caller for some capabilities, or should
those capabilities receive finer neutral subfeatures? That is a feature-design
decision, not dead-code cleanup, and is not made here.

### Bounded follow-up resolution

A later feature-matrix pass resolved the separable part without changing that
feature contract. SQL schema capabilities and formatting, schema-transition
planning, strict SQL literal conversion, SQL insert omission handling, SQL
metadata description, SQL index-drop reporting, and the runtime-value SQL
projection handoff are now gated by `sql` rather than `query`. A forced
query-only dead-code inventory fell from 762 to 678 diagnostics, removing 84
SQL-owned dormant items while leaving the engine-neutral grouped, cursor, and
aggregate substrate under `query`.

The remaining grouped substrate must not be moved beneath SQL merely to make a
query-only liveness report smaller. Its intended consumer is a current
accepted-schema fluent boundary, but that boundary is more than one terminal
method: it must freeze explicit grouped execution limits, an engine-neutral
page/result type, and cursor continuation semantics. That public addition is a
separate planned query slice. It must adapt into the existing structural query
and grouped executor rather than restore the retired generated-entity facade or
introduce another planner/executor flow.
