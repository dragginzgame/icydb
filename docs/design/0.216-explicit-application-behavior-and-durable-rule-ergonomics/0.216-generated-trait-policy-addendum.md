# 0.216 Generated Trait Policy Addendum

Status: implementation complete and focused follow-up closeout audited

Accepted: 2026-08-01

Applies to: entity, enum, list, map, newtype, record, set, and tuple
application-value macros

## Decision Summary

The `traits(add(...), remove(...))` syntax remains part of the generated
application-value surface.

It solves two real problems on stable Rust:

1. `remove(Trait)` suppresses a generated implementation so the application
   can provide a specialized implementation without a coherence conflict.
2. `add(Trait)` requests an ergonomic implementation without making the
   author know whether the macro realizes it through a Rust derive, a helper
   derive or a generated implementation.

The syntax is not a free-form trait list. Its accepted meaning is closed by
the pair `(application node kind, trait kind)`. Every explicit directive must
change generated output. A directive rejects if it is redundant, cannot emit
an implementation for that node, or attempts to change a compiler-required
trait.

This preserves the purpose of the trait system: generated application types
should feel like ordinary Rust values without requiring routine `.inner()`,
`*`, `&`, or hand-written forwarding implementations. It removes accidental
configuration states rather than removing those ergonomics.

## Current Defect

The current resolver starts with one generic configurable set, applies
`add`/`remove`, and only later adds node- and shape-derived traits. Some
accepted declarations therefore do not describe the emitted type:

- `traits(add(Inherent))` and `traits(add(Collection))` can parse on a record
  while emitting no corresponding implementation;
- `From` is selected by default for nodes whose emitters do not implement it;
- a shape-derived trait can be added after explicit removal was validated;
- a redundant addition can be accepted and later deduplicated; and
- token generation silently tolerates a selected trait for which no derive,
  implementation, or attribute strategy exists.

The required-trait cut completed in the original 0.216 Patch 1 is correct.
The remaining defect is the absence of one complete node-specific policy and
the resolver phase order needed to enforce it.

The inventory also identifies four entries that do not belong in the target
trait vocabulary:

- `Inherent` is an emitter mode, not a trait;
- `Sorted` is enum authoring policy, not a trait; and
- `Collection` and `MapCollection` duplicate standard-container methods
  already exposed by the generated `Deref` implementation.

The hard cut removes all four from `TraitKind`. `Sorted` remains supported as
a top-level enum option. `Collection` and `MapCollection`, their generated
implementations, prelude imports, and facade reexports are deleted; list, set,
and map ergonomics remain available through `Deref` and `DerefMut`.

## Policy States

Every `(node, trait)` pair has exactly one policy state:

| State | Baseline output | `add` | `remove` |
| --- | --- | --- | --- |
| Required | Always generated | Reject as redundant | Reject as forbidden |
| Generated overrideable | Generated by the node or its shape | Reject as redundant | Allow |
| Opt-in | Not generated | Allow | Reject as not generated |
| Unsupported/internal | Not author-selectable | Reject | Reject |

For capability-derived traits, the accepted node and its field/item shape
determine whether the trait is currently `Generated overrideable` or
`Opt-in`. For example, a supported primitive newtype may receive arithmetic
traits automatically, while another newtype may request one explicitly and
let Rust trait bounds decide whether its inner type supports it.

`remove` does not try to prove that a manual implementation exists. Removal
is also a legitimate opt-out. Normal Rust compilation and downstream use
remain the authority for whether the resulting type meets application trait
bounds.

## Resolution Order

The compiler must resolve traits in this order:

1. select the global required set;
2. select the node baseline;
3. select shape- and capability-derived baseline traits;
4. validate explicit removals against traits classified as generated and
   overrideable;
5. validate explicit additions against traits classified as opt-in;
6. reject a trait present in both lists; and
7. prove that every selected trait has exactly one derive, generated
   implementation, or helper implementation strategy.

Token emission may not silently ignore a selected trait. The resolver must
produce a macro diagnostic before emission if its policy and emitter drift.

## Required Traits

These ten traits are required on all eight application node kinds. They are
never author options:

| Trait | Strategy |
| --- | --- |
| `CandidType` | derive with maintained Candid attributes |
| `Clone` | Rust derive |
| `Debug` | Rust derive |
| `Deserialize` | derive with maintained Serde attributes |
| `Eq` | Rust derive |
| `NormalizeAuto` | generated application marker/implementation |
| `PartialEq` | Rust derive |
| `Path` | generated path implementation |
| `ValidateAuto` | generated application marker/implementation |
| `Visitable` | generated visitor implementation |

The existing required-trait diagnostics and compile-fail coverage remain the
contract. This addendum does not make any required trait overrideable.

## Frozen Node Baselines

The table describes traits in addition to the required set.

| Node | Generated baseline | Supported opt-ins |
| --- | --- | --- |
| Entity | `NormalizeCustom`, `ValidateCustom` | `Default`, standard derives |
| Record | `NormalizeCustom`, `ValidateCustom` | `Default`, standard derives |
| Tuple | `NormalizeCustom`, `ValidateCustom` | `Default`, standard derives |
| Enum | `NormalizeCustom`, `ValidateCustom`; unit-only enums also receive `Copy`, `Hash`, `PartialOrd` | `Default`, standard derives not already generated |
| Newtype | `From`, `Inner`, `NormalizeCustom`, `ValidateCustom`; compatible primitive shapes also receive their arithmetic and standard helper set | `Default`, `Display`, `Deref`, `DerefMut`, supported arithmetic/helper traits not already generated, standard derives not already generated |
| List | `Default`, `Deref`, `DerefMut`, `From`, `NormalizeCustom`, `ValidateCustom` | standard derives not already generated |
| Set | `Default`, `Deref`, `DerefMut`, `From`, `NormalizeCustom`, `ValidateCustom` | standard derives not already generated |
| Map | `Default`, `Deref`, `DerefMut`, `From`, `NormalizeCustom`, `ValidateCustom` | standard derives not already generated |

Here, `standard derives` means only `Copy`, `Hash`, `Ord`, and `PartialOrd`.
Their normal Rust field bounds remain the final compile-time check.

`Default` retains its established application meaning:

- list, set, and map have an intrinsic empty-value default which may be
  removed for an application override or opt-out;
- entity, record, tuple, newtype, and enum require explicit opt-in;
- newtype default still requires the authored default value;
- enum default still requires exactly one applicable default variant; and
- record/entity/tuple default still requires a constructible generated value.

`Default` does not define a database column default or change write
admission.

## Sorted Enum Policy

Sorted enum enforcement remains useful, but it is independent of trait
generation. Its maintained source form becomes a top-level Darling flag:

~~~rust
#[enum_(
    sorted,
    variant(name = "A"),
    variant(name = "B")
)]
pub struct Example {}
~~~

`sorted` is accepted only by `enum_`. It emits the maintained compile-time
sorted-order attribute. `traits(add(Sorted))` is removed without an alias or
fallback.

## Complete Trait Inventory

All 37 current `TraitKind` variants are accounted for below. The hard cut
removes `Inherent`, `Sorted`, `Collection`, and `MapCollection`, leaving 33
actual target trait variants. No target variant remains governed by a generic
fallback.

### Required Everywhere

`CandidType`, `Clone`, `Debug`, `Deserialize`, `Eq`, `NormalizeAuto`,
`PartialEq`, `Path`, `ValidateAuto`, and `Visitable` follow the required policy
above.

### Generated Application Overrides

- `NormalizeCustom` and `ValidateCustom` are generated and overrideable on
  every node.
- `From` is generated and overrideable only on newtype, list, set, and map.
  It is unsupported on entity, record, tuple, and enum.
- `Inner` is generated and overrideable only on newtype.

### Shape And Capability Traits

- `Copy`, `Hash`, `Ord`, and `PartialOrd` are standard opt-ins when not already
  generated. A unit enum or compatible primitive newtype may generate a
  subset as an overrideable baseline.
- `Deref` and `DerefMut` are generated and overrideable on list, set, and map;
  they are opt-in on newtype and unsupported elsewhere.
- `Add`, `AddAssign`, `Div`, `DivAssign`, `Mul`, `MulAssign`, `Rem`, `Sub`,
  `SubAssign`, and `Sum` are newtype-only. They are generated and overrideable
  when the maintained primitive capability table selects them, and otherwise
  are opt-in on a newtype. Rust bounds on the inner type decide whether an
  explicit opt-in compiles.
- `NumericValue` is newtype-only. It is generated and overrideable for a
  maintained compatible primitive and otherwise may be requested explicitly
  on a newtype whose inner type implements the required contract.
- `Display` is a newtype-only opt-in.
- `Default` follows the node-specific policy frozen above.

### Removed From The Trait Vocabulary

- `Inherent` is replaced by an explicit inherent-versus-trait implementation
  mode in the emitter.
- `Sorted` moves to the top-level enum option frozen above.
- `Collection` and `MapCollection` are deleted. Their `iter`, `len`, and
  `is_empty` methods already resolve through the generated standard-container
  dereference. No maintained generic bound consumes either custom trait.

Explicit `add` or `remove` using any of these four retired names rejects as
unknown input. There is no compatibility spelling.

## Maintained Directive Ledger

The current repository contains a small set of intentional explicit uses:

| Use | Purpose | Required policy |
| --- | --- | --- |
| `RgbHex`, `RgbaHex` add `Default` | Domain-selected wrapper default | Newtype opt-in |
| `RgbaHex` removes `From` | Suppress the generated generic conversion | Newtype generated override |
| `Utf8` removes `ValidateCustom` | Permit its manual validator | Generated application override |
| Four numeric range wrappers remove `ValidateCustom` | Permit their manual validators | Generated application override |
| Macro fixtures add `Default` to newtypes | Prove authored wrapper defaults | Newtype opt-in |
| Macro fixture adds `Sorted` to an enum | Migrate to the top-level `sorted` flag | Enum authoring option |

These are maintained consumers, not exceptions to the policy. Each must keep
changing output after the resolver hard cut. Required-trait negative fixtures
also remain maintained contract tests.

## Diagnostics

Macro diagnostics must distinguish these failures without relying on a later
Rust error:

- required trait addition: the compiler already generates the trait;
- required trait removal: the trait is required for every generated value;
- redundant addition: the node or its admitted shape already generates it;
- absent removal: the node does not currently generate it;
- unsupported trait: the trait has no supported strategy for that node;
- conflicting directive: the same trait appears in both `add` and `remove`;
- invalid trait-specific shape, for example an unconstructible `Default`; and
- emitter drift: a selected trait has no implementation strategy.

The top-level `sorted` flag owns its own enum-only and declaration-order
diagnostics; it does not pass through trait resolution.

Diagnostics should name the application node kind and trait. Ordinary Rust
trait-bound errors remain acceptable after a supported opt-in whose inner
fields do not implement the requested standard or helper trait.

## Compatibility And Scope

This is a pre-1.0 hard cut. There are no aliases, deprecated spellings,
fallback resolver phases, or tolerated no-op declarations. Maintained source
is migrated in the same landing patch that changes its policy.

This addendum does not:

- add specialization or permit overlapping generated/manual impls;
- infer whether the application wrote a manual implementation;
- make Rust paths or traits persisted schema identity;
- change accepted schema, rows, keys, journals, cursors, Candid, or Wasm
  endpoint surfaces;
- change normalization or validation ownership;
- introduce arbitrary trait paths into `traits(...)`; or
- remove the `add` and `remove` syntax.

## Staged Implementation

The original eight 0.216 patches remain historical release boundaries. This
follow-up is implemented as bounded correction landings rather than rewriting
that history:

1. **Authority and inventory freeze.** Accept this addendum and link it from
   the design and status tracker. No generated output changes.
2. **Trait vocabulary hard cut.** Replace `Inherent` with an emitter mode,
   move sorted enforcement to the top-level enum flag, and delete the
   redundant `Collection` and `MapCollection` traits, implementations,
   imports, and reexports. Compile the maintained downstream fixtures before
   accepting the deletion.
3. **Resolver authority and phase order.** Introduce the closed node policy,
   compute shape baselines before directives, and make missing emission
   strategy an invariant error while preserving maintained trait output.
4. **Generated/custom strategy audit.** Enforce the individual policies for
   `From`, `NormalizeCustom`, `ValidateCustom`, `Inner`, and `NumericValue`,
   with positive and negative fixtures for each trait before moving to the
   next.
5. **Derive/helper strategy audit.** Enforce `Default` first, then audit each
   standard, dereference, display, and arithmetic/helper trait independently.
   Mechanically identical traits may share a reviewable landing only after
   their individual node matrices and diagnostics are proved.
6. **Closeout.** Search for no-op paths and obsolete generic resolver state,
   run focused macro/model/schema consumers and compile fixtures, measure raw
   Wasm only if emitted maintained output changes, and refresh the 0.216
   closeout evidence.

One implementation turn stops at one reviewable landing. Discovery that
requires a new trait meaning or another node category stops for a design
decision rather than widening the current landing.
