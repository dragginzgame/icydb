## Patch 1 — Contract And Current-State Inventory

Status: complete.

### Reconstructed Authority

- The entity macro parses and validates nonzero `version`, but fragment
  lowering drops it. `EntityFragment`, `SchemaProposal`, accepted source
  bindings, and accepted runtime snapshots are currently unaware of declared
  entity source versions.
- Runtime `SchemaVersion`, accepted store revision, `RowLayoutVersion`, and
  proposal contract version are distinct maintained authorities. None can be
  reused as `DeclaredEntityVersion` or `AcceptedEntitySourceVersion`.
- Accepted source bindings are already the sole source-key-to-accepted-ID
  authority. Renames must replace keys at publication, never leave aliases.
- Store-local `EntityTag` allocation requires lineage keys to include
  `TargetStoreIdentity`.
- Current DDL already converges on catalog-native mutation admission and fails
  closed without required physical work. Constraint activation supplies a
  bounded store-local job pattern, not a general database migration owner.
- The live-schema checkpoint map owns the remaining database-control range.
  Current commit markers atomically cover journal work and one application
  record effect but cannot yet publish lineage and progress together.
- Physical index IDs already contain an isolated `u64` generation. There is no
  need for a second migration index-key codec.
- No migration runtime, endpoint, CLI operation, compatibility decoder, or
  implicit source/target authority exists.

### Frozen Contract

- Entity source lineage is per entity and one-step only. There is no global
  source schema version.
- Existing databases require a separate explicit controller adoption before
  their first source migration.
- The source grammar has one database-scoped coordinated plan and current
  entity declarations only. Patch 2 may refine parser punctuation, not
  ownership or semantics.
- Proposal transport hard-cuts to sole current contract version 2 with
  capability 8 and retains its 2 MiB proposal/512 KiB fragment bounds.
- V1 checked casts are closed to fixed signed/unsigned integers and Decimal
  under exact representability rules; Decimal-to-integer and all other scalar
  families are excluded.
- Catalog-only migration becomes operational in Patch 4. Physical migration
  gates the complete database from validation until terminal publication or
  a permitted pre-rewrite abort.
- Lineage and active migration state use two reserved records in the
  generalized live-schema checkpoint map: `ICYSLIN1` and `ICYSMIG1`, both
  version 1 and bounded to 2 MiB. Lineage has at most 4,096 entries.
- Candidate indexes reuse current nonzero physical generations and bind the
  generation to the exact plan, store, and accepted index identity.
- Patch 5 hard-cuts the commit marker to version 2 with at most four canonical
  database-control compare-and-replace operations. No marker version-1
  decoder remains after quiescent upgrade admission.
- Public operations are controller-only update `icydb_schema_migrate` and
  query `icydb_schema_migration`. `Advance` is one bounded engine call; CLI
  `run` loops while database, head, deployment, and plan identities remain
  exact.

## Patch 3 — Catalog-Native Rename And Lineage Planner

Status: complete.

### Implemented Contract

- `EntitySourceDigest` now hashes one current entity's generated-owned meaning,
  reachable named-type closure, and exact relation target fields while
  excluding its declared version and migration instructions.
- The generalized live-schema control map reserves the fixed lineage and
  active-migration keys. The current `ICYSLIN1` lineage record is length- and
  CRC-framed, bounded to 2 MiB and 4,096 canonical `(store, entity)` entries,
  and distinguishes `Unadopted` from adopted positive version/digest state.
- Initial source lineage and explicit v1 adoption are derived without writes.
  Adoption requires exact no-op reconciliation and rejects stale heads,
  adopted state, non-v1 source, or any unexplained difference.
- The catalog-native migration planner binds predecessor selectors only
  against accepted source bindings, applies every rename simultaneously to a
  temporary accepted-ID view, rebuilds dependent display/path metadata, and
  feeds all remaining additions, removals, and semantic edits through the

  durable-rule, and inferred index rekeys preserve their accepted IDs. Old

- Exact-head migration application now performs this read-only preflight when
  the capability is compiled, then still returns unsupported. Patch 4 remains

- Physical transforms are classified as `PhysicalRunnerMissing`; Patch 3 does

## Patch 4 — Metadata Migration Publication And Explicit Operations

Status: complete.

### Implemented Contract

- Fresh source application, explicit version-1 adoption, and metadata-only
  migration now publish the exact accepted candidates, source lineage, and
  application receipt through one existing database commit marker. The
  lineage compare-and-replace is preflighted, applied, and recovered beside
  the receipt; missing, stale, or divergent state fails closed.
- Adoption requires one exact no-op version-1 proposal and publishes lineage
  without changing the accepted head. Metadata advance binds the exact
  database, predecessor head, proposal digest, and coordinated plan digest,
  then publishes all store candidates and lineage together. Physical plans
  remain typed `PhysicalRunnerMissing` failures before publication.
- Exact terminal receipts make adoption and metadata advance idempotent. A
  repeated advance resolves the receipt's accepted terminal head before
  applying stale-predecessor checks, while a different proposal, plan, or
  durable outcome fails closed.
- The public capability adds the closed `Adopt`, `Advance`, and `Abort`
  commands plus bounded status types. Patch 4 has no nonterminal job to abort;
  abort returns an already-applied terminal status or a typed missing-job
  failure. Patch 5 remains the sole owner of the abortable durable lifecycle.
- `icydb_schema_migrate` is one controller-authorized update and
  `icydb_schema_migration` is one controller-authorized query. Both wrappers
  authorize before calling private generated handlers. Capability without a
  declaration exports nothing, and an active declaration without
  `icydb/migration` fails at compile time.
- `icydb schema migration status|advance|run|abort|adopt` calls only the
  selected deployed canister. `run` performs independently bounded advances
  and stops on terminal status, no progress, or database/plan drift;
  destructive abort and adoption require `--yes`.

### Format And API Impact

- The existing schema-application record encoding is unchanged. Patch 4's

- Patch 4 begins publishing the bounded `ICYSLIN1` current lineage record

## Patch 5 — Durable Offline Migration Lifecycle

Status: complete.

### Implemented Contract

- One database-scoped `ICYSMIG1` record now retains the exact database,
  accepted-before and candidate heads, proposal and plan digests, canonical
  entity transitions, accepted entity/source identities, staged generation
  ownership, lifecycle phase, bounded cursors, counters, and typed findings.
  Its version-1 codec is length-bound, checksummed, canonical, and capped at 2
  MiB before allocation.
- The persisted phase machine is closed over `Prepared`, `Validating`,
  `ReadyToRewrite`, `RewritingRows`, `RebuildingIndexes`, `FinalValidation`,
  `Publishing`, `Applied`, `Rejected`, and `Aborted`. Progress is monotonic;
  immutable database/head/deployment/plan identity cannot drift during a
  compare-and-replace transition.
- Ordinary routes consult one cached database-wide readiness state after
  guarded recovery. `Prepared` remains available only when the migration
  capability is compiled. Validation through publication, plus rejected work
  awaiting abort, blocks ordinary reads, writes, relation work, schema
  mutation, and DDL with typed `MigrationInProgress`. A nonterminal record in
  a Wasm without `icydb/migration` also fails readiness.
- Explicit migration and integrity operations recover through a narrow
  control-plane path without clearing the gate or opening an ordinary data
  route. A pre-rewrite abort atomically advances the exact record to terminal
  `Aborted`; row rewriting and later phases return typed `AbortTooLate`.
- Status and advance bind any active record to the deployed proposal digest,
  plan digest, database identity, and correct predecessor or applied head.
  Deployment or plan drift fails closed as `PlanChanged`; there is no inferred
  plan, retry under new code, or generated-model fallback.
- Commit-marker envelope version 2 replaces the retired optional application
  effect with at most four canonically ordered database-control operations.
  Application receipt, entity-source lineage, and migration progress now
  share one preflight, marker, apply, verification, and recovery transaction.

### Format And API Impact

- The commit-marker envelope hard-cuts from version 1 to sole current version
  2. Version 1 has no decoder. Current payloads retain the existing 16 MiB
  ceiling and add a bounded operation count plus tagged exact before/after
  control effects.
- The generalized live-schema checkpoint map begins publishing one reserved
  `icydb.schema-migration.key.v1` value using `ICYSMIG1`, record version 1,
  big-endian lengths, and CRC32C. Reserved lineage and checkpoint bytes remain
  unchanged.
- Public migration Candid, accepted schemas, rows, primary and secondary keys,
  journals, cursors, application receipts, and existing endpoint names are
  unchanged. Physical transforms, staged writes, and candidate index work
  remain rejected until Patch 6 supplies the closed compiler and validator.

### Evidence

- Reserved-map tests prove checkpoint-count neutrality, reopen persistence,

- Marker tests prove the version-1 hard cut, the four-operation decode bound,

## Patch 6 — Closed Transform Compiler And Validation Runner

Status: complete.

### Implemented Contract

- The four V1 transform forms now compile once from source keys into exact
  accepted-before and candidate entity, field, and slot identities. Literal
  fill, exact copy, checked fixed-integer/Decimal cast, and nullable coalesce
  run over the accepted row decoder without Rust paths, callbacks, generated
  model fallback, time, randomness, SQL, or external calls.
- Physical candidate construction now owns the complete target row layout. It
  reserves exact new field, index, relation, and generated row-constraint
  identities; assigns isolated nonzero physical generations to new indexes and
  relations; and compiles changed candidate constraints directly for the
  offline proof. Metadata-only migrations retain the existing activation path.
- A physical migration checks every transformed source store before the
  `Prepared` record and every candidate reverse-generation target before row
  scanning or staging. All must be durable and journaled; otherwise the runner
  returns typed `PhysicalRunnerMissing` without writing candidate keys.
- Each `Advance` scans at most 256 rows, 1 MiB of accepted row bytes, and 1 MiB
  of staged derived keys in deterministic store/entity/primary-key order. The
  row is decoded under accepted-before authority, transformed transiently,
  admitted under the complete candidate field/constraint contract, checked
  against candidate relations, and projected through candidate unique indexes.
- Validation findings have deterministic row-local precedence: transform,
  constraint, relation, then uniqueness. The durable `ICYSMIG1` finding keeps
  accepted store/entity/primary-key identity; transform findings additionally
  keep accepted source and target field IDs plus the typed overflow,
  negative-to-unsigned, precision-loss, null-source, or value-contract reason.
  The already-frozen public Candid finding summary remains unchanged.
- Candidate unique and reverse-relation keys use the ordinary index codec and
  journaled index store under planner-invisible generations. A clean page folds
  those exact keys before its progress marker advances. Repeating a page after
  interruption accepts only the same raw keys and is idempotent; a conflicting
  value fails closed. A page containing any finding publishes no staged keys.
- Validation never mutates accepted row bytes, accepted schema, source lineage,
  or runtime-visible generations. Complete clean validation advances only to
  `ReadyToRewrite`; Patch 7 remains the sole row-rewrite, generation-activation,
  abandoned-generation cleanup, and final-publication owner.

### Evidence

- Planner tests cover all four closed transform forms, checked-cast accepted-ID
  binding, full single-version candidate layouts, new unique-index generations,
  primary-key exclusion, and unchanged metadata-only activation behavior.
- Transform tests cover signed/unsigned overflow, negative-to-unsigned,
  Decimal precision loss, null source, and unsupported value contracts.
- One journaled end-to-end fixture validates a clean two-row migration, stages
  exactly one candidate unique key per row, replays the uncheckpointed page

- A second journaled fixture scans five ordered rows and reports constraint,

- Current migration-record codec tests retain the exact transform finding

## Patch 7 — Physical Rewrite, Index Activation, And Final Publication

Status: complete.

### Implemented Contract

- `ReadyToRewrite` now enters a deterministic accepted-ID row scan. Each page
  decodes predecessor rows under accepted-before authority, runs the already
  validated closed transform, admits the complete candidate row, proves the
  row/primary/storage-key binding, and emits the current candidate row envelope.
- The same page derives every changed or new candidate index plus every
  changed or new reverse-relation generation through the ordinary index and
  relation projection owners. There is no migration-only row, primary-key,
  secondary-key, or reverse-key codec.
- Rewrite work is bounded by 256 rows, 1 MiB of row bytes, 1 MiB of derived-key
  bytes, 16,384 journal records, and 8 MiB of exact journal-record payloads.
  An individual row that cannot fit rejects before marker publication; a later
  row resumes on the next page without advancing its cursor.
- Two additive current journal-record tags carry exact migration row puts and
  candidate index puts. Every record binds its target store and exact plan
  digest. Row records advance the existing durable data-mutation revision;
  index-only work does not.
- Candidate rows, derived effects, and the next migration cursor publish under
  one commit marker. Recovery validates the exact active plan, completes the
  marker from marker-only, journal-published, and physical-effects-applied
  interruptions, and preserves the gated mixed-layout/candidate-generation
  state instead of rebuilding it through predecessor authority.
- `RebuildingIndexes` records the exact completed candidate domain inventory.
  Bounded final validation reopens every row under candidate authority and
  proves row/key binding, accepted row constraints, relation targets, and every
  expected candidate forward and reverse key before publication.
- Final publication atomically replaces candidate accepted snapshots, source
  lineage, the schema-application receipt, and the migration record with its
  terminal `Applied` form. The predecessor source key is absent immediately;
  old physical generations remain inert for later explicit cleanup.
- A permitted pre-rewrite abort scans at most 512 index entries and 1 MiB of
  keys per call, advances over unrelated entries, removes only exact candidate
  generations, retains all predecessor rows, and publishes `Aborted` only when
  cleanup is complete. The CLI confirms once and drains these bounded pages
  while the database and plan identities remain exact.
