# IcyDB 0.218 Contract And Current-State Inventory

Status: frozen by Patch 1 on 2026-08-02

Design: [0.218-design.md](0.218-design.md)

Baseline: `v0.217.3` at
`02d439796afcae1fec5e1a152eff9925f96fc259`

This inventory records the maintained authorities that 0.218 changes or
reuses. It is evidence for the accepted design, not a second specification.
Where this inventory and the design differ, the design is normative.

## Conclusions

- `#[entity(version = ...)]` is currently parsed and validated but becomes
  inert before `EntityFragment`; no proposal or accepted runtime object sees
  it.
- The current `SchemaVersion`, accepted store revision, and
  `RowLayoutVersion` are real persisted authorities but none is an entity's
  source-lineage version.
- Accepted source bindings already preserve current source keys to accepted
  IDs. Migration must rekey that catalog exactly; it must not add aliases or
  reconstruct identity from generated models.
- `EntityTag` is store-local. Durable entity lineage therefore requires
  `(TargetStoreIdentity, EntityTag)`.
- Existing constraint activation supplies useful bounded-job and recovery
  patterns but is store-local and cannot become the database-wide migration
  authority.
- The live-schema checkpoint map already owns the remaining bounded
  database-control memory range. It must be generalized with reserved record
  keys rather than overlapped by another stable structure.
- The current marker can atomically carry journal batches and one application
  receipt replacement only. Migration requires a bounded generalized
  database-control transaction in the marker.
- Current index keys already contain a nonzero physical generation. Migration
  staging can isolate a candidate generation without a second index codec.
- No migration endpoint, CLI command, general row migration runner, or durable
  database-wide migration job exists at the baseline.

## Declared Entity Version Trace

| Boundary | Current owner | Finding |
| --- | --- | --- |
| proc-macro input | `icydb-model-macros/src/node/entity.rs` | parses `version` as `u32` and rejects zero |
| generated host model | `icydb-model/src/node/entity.rs` | retains the authored value and validates it |
| fragment lowering | `icydb-model/src/fragment.rs::lower_entity` | constructs `EntityFragment` without the value |
| public fragment | `icydb-schema/src/fragment.rs::EntityFragment` | has no declared-version field |
| database proposal | `icydb-schema/src/proposal.rs::SchemaProposal` | has no per-entity source version or migration plan |
| accepted runtime | `icydb-core/src/db/schema` | has no accepted entity-source lineage catalog |

The value is therefore authoring metadata only at 0.217.3. Patch 2 must make
it effective through one direct current-form transport hard cut. Runtime must
never fall back to the generated `EntityModel` to recover it.

## Frozen Version Vocabulary

| Name | Cardinality and owner | Meaning |
| --- | --- | --- |
| `DeclaredEntityVersion` | one current source entity | authored source-lineage target |
| `AcceptedEntitySourceVersion` | one adopted generated-owned accepted entity | last published declared version |
| `SchemaVersion` | one accepted entity snapshot | catalog semantic version used by current DDL and transition admission |
| `AcceptedSchemaRevision` | one accepted store bundle | monotonic store publication revision |
| `RowLayoutVersion` | one accepted row layout | physical row-envelope slot layout |
| `ProposalContractVersion` | one proposal transport | current wire-shape discriminator |
| `EntitySourceDigest` | one current/adopted entity source meaning | canonical generated-owned target closure, excluding migration rules |
| `SchemaMigrationPlanDigest` | one resolved coordinated plan | exact transition and candidate identity |

There is no canister-level or database-level source schema version.

## Proposal And Source-Binding Authority

`SchemaProposal` is the bounded canonical Candid envelope. At the baseline it
contains contract version 1, capabilities, target database, submission key,
expected accepted head, fragments, store assignments, and removals. It is
bounded to 2 MiB; each reusable fragment is bounded to 512 KiB.

Patch 2 freezes the next sole current form as:

- `ProposalContractVersion::CURRENT == 2`;
- capability 8, `VERSIONED_MIGRATIONS`;
- one declared version on every entity fragment;
- zero or one canonical coordinated migration plan on the proposal; and
- the existing 2 MiB proposal and 512 KiB fragment byte ceilings.

The version-1 proposal decoder is removed in the same hard cut.

The accepted source-binding catalog in
`icydb-core/src/db/schema/source_binding.rs` is store-local and maps current
proposal keys to accepted entity, field, type, relation, index, constraint,
and rule identities. Its current frame is `ICYDBASB`, codec version 1, with a
2 MiB maximum. It is already the right durable name-to-ID authority. Migration
must derive a temporary accepted-ID rekeying view, validate the complete
candidate, and replace the accepted bindings only at atomic publication.

## Accepted Catalog And Layout Authority

The accepted store bundle and root are the sole runtime schema authority:

- bundle: `ICYDBAEB`, codec 1, maximum 16 MiB;
- root: `ICYDBAER`, codec 1, fixed 94 bytes; and
- entity snapshot: direct `ICYUSNP\0` tagged binary payload, format version 1,
  maximum 512 KiB.

The database-wide accepted head hashes canonical store identity together with
each selected store revision and fingerprint. Its revision is the maximum
selected store revision. It is an optimistic publication head, not a source
schema version.

`SchemaRowLayout` retains a nonzero current `RowLayoutVersion`, a history
floor, and accepted field-to-slot assignments. The row decoder may read the
bounded accepted layout window. That facility supports ordinary catalog
evolution; it is not a durable transform runner and does not authorize a
version fallback.

The row envelope remains `IY`, format version 1, maximum 4 MiB, carrying the
exact `RowLayoutVersion`. Physical migration writes this current form rather
than introducing a migration-specific envelope.

## DDL And Schema-Mutation Authority

The current catalog-native mutation target covers:

- field addition, default change, drop, nullability change, and rename;
- field-path and expression index addition; and
- secondary-index drop.

`MutationPlan` classifies publication as metadata-only or requiring physical
index work. Publication preflight either admits immediate work or fails closed
when the required physical runner is absent. SQL DDL lowers into this
authority and continues to own explicit accepted `SchemaVersion` expectations;
it does not advance source lineage.

0.218 must extend this catalog-native planner. It must not construct accepted
snapshots in a source frontend, invent a parallel SQL migration executor, or
let authored transform classes bypass derived mutation classification.

## Constraint Activation

`ConstraintValidationJob` is the closest maintained durable-work pattern:

- codec 1/profile `ICJB`;
- maximum 64 KiB;
- exact accepted revision/fingerprint and activation identity;
- bounded forward and verification phases; and
- journaled job put/delete effects with recovery and integrity coverage.

It remains store-local and activation-specific. 0.218 may reuse its design
lessons and existing constraint candidate generations, but the database-wide
migration record, gate, plan digest, and publication receipt have one separate
schema-migration owner.

## Application Receipt And Database-Control Memory

`SchemaChangeReceipt` binds database identity, submission key, proposal digest,
prior accepted head, and outcome. The application-record store uses:

- header `ICYSAH01`, version 1;
- record `ICYSAR01`, version 1;
- domain-separated 32-byte record keys;
- maximum 64 KiB per record and 64 records; and
- commit virtual-memory pages 257 through 4,095.

The live-schema checkpoint map uses pages 4,096 through 4,194,303, 32-byte
keys, header `ICYSLVHD`, and checkpoint frame `ICYSLIVE`, both version 1. A
checkpoint holds the store path, accepted bundle/root, and complete Identity
inventory under the existing compile-time bound.

Because this map owns the remaining database-control range, Patch 3
generalizes its record value and key validation while preserving every current
checkpoint byte. It adds exactly two reserved current-form records:

| Record | Reserved key profile | Frame and bound |
| --- | --- | --- |
| accepted entity-source lineage | `icydb.schema-lineage.key.v1` | `ICYSLIN1`, version 1, length, CRC, 2 MiB, at most 4,096 entries |
| active or terminal migration | `icydb.schema-migration.key.v1` | `ICYSMIG1`, version 1, length, CRC, 2 MiB |

Lineage entries are keyed by `(TargetStoreIdentity, EntityTag)`. Existing
databases begin `Unadopted`; adoption is a separate controller operation and
does not invent version 1 during a `1 -> 2` migration.

## Commit, Journal, And Recovery Boundary

The journal batch remains `IJBT`, version 1, maximum 16 MiB. The commit marker
is also bounded to 16 MiB and now uses sole current envelope version 2. Its
payload owns one commit ID, canonical journal batches, and at most four
canonically ordered exact database-control compare-and-replace operations.

Recovery:

1. restores live schema checkpoints;
2. publishes marker-bound journal batches;
3. applies the exact application, lineage, and migration-progress transaction;
4. folds journal tails into canonical stores;
5. rebuilds and verifies derived state; and
6. clears the marker only after the durable outcome is quiescent.

Patch 5 set the only accepted marker envelope version to 2 and replaced the
single application-record field with at most four canonically ordered,
compare-and-replace database-control operations. The target domain is closed
to the application-record store or generalized checkpoint/control map. Each
operation binds exact key, expected-before bytes, and after-or-delete state.
The operations and journal batches share the existing 16 MiB aggregate marker
ceiling. Admission sizes the full marker first and reduces a bounded work page
or rejects before publication; individual record maxima do not imply that all
maxima can coexist in one marker. There is no version-1 decoder after the cut;
upgrade readiness must first prove the transient old marker is absent.

## Index Generation Authority

`IndexId` encodes `(EntityTag, u16 ordinal, u64 generation)` in every physical
index-key prefix. Accepted unique-index and relation activation already use a
nonzero generation and keep planner-invisible candidates out of accepted
runtime lookup.

Migration reuses that codec. One staged generation is owned by
`(SchemaMigrationPlanDigest, TargetStoreIdentity, SchemaIndexId,
physical_generation)`. The nonzero generation is persisted in the migration
record before entries are written and cannot equal an accepted or other staged
generation for the logical index. Final publication changes accepted
generation authority atomically; it does not copy staged entries into a
name-derived key space.

## Endpoint And CLI Baseline

At 0.217.3:

- `icydb::start!()` installs private lifecycle wiring and exports no migration
  method;
- `icydb::endpoints!` has no migration declarations;
- the CLI has schema inspection but no adopt, status, advance, run, or abort
  migration command; and
- there is no config file or target-derived endpoint policy.

Patch 4 adds exactly the explicit controller-only methods frozen in the
design: update `icydb_schema_migrate` and query `icydb_schema_migration`.
Capability without declaration exports nothing. CLI operations consult only
the selected deployed canister and preserve method-not-found failures.

## Frozen V1 Transform Matrix

The only program forms are typed literal fill, exact copy, checked scalar
cast, and optional-to-required coalesce with a typed literal.

| Source | Target | Rule |
| --- | --- | --- |
| any fixed `Int8..Int128` or `Nat8..Nat128` | any fixed `Int8..Int128` or `Nat8..Nat128` | exact representability required |
| any fixed integer | `Decimal { scale }` | exact scaling and signed-128 mantissa required |
| `Decimal { scale }` | `Decimal { scale }` | exact rescale; no precision loss; signed-128 mantissa required |
| `Decimal` | fixed integer | unsupported in V1 |
| `IntBig`, `NatBig`, floats, temporal, identifiers, text, blob, enums, structured values | any cast target | unsupported in V1 |

Every admitted conversion uses one checked owner. There is no separate
unchecked widening path.

## Patch Ownership Of Remaining Work

- Patch 2 owns effective entity versions and the proposal/grammar hard cut.
- Patch 3 owns lineage persistence, adoption, rename binding, and planning.
- Patch 4 owns metadata publication, explicit endpoints, and CLI operations.
- Patch 5 owns the durable lifecycle, database gate, and marker version 2.
- Patch 6 owns transform compilation, validation, and staged generations.
- Patch 7 owns row rewrite, index activation, and final publication.
- Patch 8 owns maintained consumer migration, documentation, and closeout.

No current source or persisted path should be described as already providing
these capabilities merely because it supplies a reusable lower-level pattern.
