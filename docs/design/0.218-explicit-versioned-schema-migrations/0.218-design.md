# 0.218 Explicit Versioned Schema Migrations

Status: tentative

Design cut: 2026-07-28

Implementation order: after 0.217 closeout

## Decision Summary

0.218 introduces explicit, source-declared migrations between persisted
accepted entity schemas and current source entity declarations.

The core rule is:

> For each entity, the accepted catalog is the `from` schema and the current
> source declaration is the `to` schema. A database-scoped migration plan may
> coordinate several entity transitions atomically, but it carries no second
> global schema version.

An application does not compile complete `v1` and `v2` Rust models together.
For one entity upgrading from version 1 to version 2:

- stable memory contains the accepted version-1 catalog, source bindings,
  accepted IDs, row layouts, and data;
- the new Wasm contains that entity's current version-2 declaration and one
  explicit `1 -> 2` migration transition;
- the migration planner binds old names only against that entity's accepted
  version 1;
- it binds new names only against that entity's current version-2 proposal;
- accepted IDs remain the durable identities;
- successful renames replace old source-binding keys with new keys rather than
  retaining aliases; and
- any required physical work completes before entity version 2 becomes
  accepted runtime authority.

The first public contract is deliberately one-step per entity:

```text
accepted entity-source version == current entity version
    -> exact current-state reconciliation only

accepted entity-source version + 1 == current entity version
    -> require the exact declared entity transition

anything else
    -> fail with a typed version-gap or downgrade error
```

Skipping versions for one entity is not supported in 0.218. An entity accepted
at version 1 must pass through its version-2 declaration before version 3 can
be accepted. Other entities may remain at their own current versions or
advance independently. This avoids shipping historical Rust models, hidden
schema snapshots, migration aliases, or an unbounded in-Wasm migration ladder.

Fresh databases initialize each entity directly at its declared current
version and do not replay historical migrations.

0.218 supports two migration classes:

1. **Catalog-only migration**
   - exact entity, field, named-type, record-member, enum-variant, relation,
     constraint, and durable-rule renames;
   - source-binding rekeying while preserving accepted IDs;
   - ordinary catalog-native additions, removals, and semantic edits already
     admitted by the current mutation and activation machinery; and
   - no historical row rewrite.
2. **Bounded offline data migration**
   - a closed, typed transformation vocabulary over accepted version-1 fields
     and current version-2 fields;
   - physical rewrite support only for durable journaled stores;
   - resumable validation, row rewrite, and index rebuild work;
   - affected entities unavailable while irreversible physical work is active;
   - progress committed atomically with each bounded row chunk; and
   - target entity versions publish only after all required physical work and
     validation succeeds.

The first transformation vocabulary is intentionally small. It contains typed
literal fill, exact copy, checked scalar cast, and optional-to-required
coalescing with a typed literal. It does not execute arbitrary Rust callbacks,
SQL text, user Wasm functions, network calls, cross-row aggregates, or
cross-entity lookups.

0.218 is not a compatibility framework. It adds no old-name alias lookup, dual
schema authority, fallback row decoder, historical proposal decoder, inferred
rename, or best-effort migration path.

## Motivation

The current source grammar now has one name vocabulary:

- entity and store names come from their Rust declarations;
- named value types have one current `name`, defaulting to their Rust
  declaration;
- fields, enum variants, relations, constraints, and durable rules use
  `name`; and
- indexes derive canonical names from their entity and key shape.

This is substantially clearer than requiring a second handwritten stable key
for every declaration. It also means a source rename deliberately changes the
proposal key.

For example, version 1 may have:

```rust
field(name = "email", value(item(prim = "Text", unbounded)))
```

The initial proposal carries:

```text
FieldSourceKey("email")
```

After acceptance, the catalog stores:

```text
(UserId, FieldSourceKey("email")) -> FieldId(2)
```

If version 2 simply changes the declaration to:

```rust
field(name = "primary_email", value(item(prim = "Text", unbounded)))
```

the compiler emits:

```text
FieldSourceKey("primary_email")
```

The compiler cannot know that `primary_email` used to be `email`, and
reconciliation must not guess based on position, type, or similar spelling.
The missing information belongs in an explicit migration:

```text
field User.email -> User.primary_email
```

The accepted transition then becomes:

```text
before: (UserId, "email")         -> FieldId(2)
after:  (UserId, "primary_email") -> FieldId(2)
```

The old source binding is removed. It is not retained as an alias. Physical
row slots, values, accepted constraints, relations, and index generations keep
their accepted identities unless another explicit migration rule changes their
meaning.

## Current Baseline

0.218 starts from the following completed boundaries:

- accepted schema snapshots are runtime authority;
- generated models produce proposals and typed adapters but are not runtime
  fallback authority;
- source proposals bind through persisted source-to-accepted identity
  catalogs;
- accepted IDs are distinct from row slots and current names;
- row envelopes carry `RowLayoutVersion`;
- accepted row layouts can admit a bounded history window;
- schema application already owns optimistic database-head checks, candidate
  publication, receipts, and cross-store commit participation;
- constraint activation already has bounded validation, durable progress,
  recovery, abort, and publication concepts;
- SQL DDL already lowers through catalog-native mutation admission;
- physical-work-required mutation plans fail closed when no matching runner
  exists;
- generated source application already distinguishes accepted-before from
  candidate-after;
- 0.216 provides current named durable-rule declarations;
- 0.217 makes public operational endpoints explicit in source; and
- no maintained row migration runner or durable general migration job exists.

There is also one authoring inconsistency to resolve:

- `#[entity(version = ...)]` is parsed and retained in the host model;
- it does not currently enter `EntityFragment` or generated schema-proposal
  lowering; and
- runtime `SchemaVersion` is an accepted entity-snapshot version used by DDL
  and row-layout evolution, not a working source migration lineage.

0.218 must not silently pretend that the current entity macro field already
implements source migrations.

## Version Vocabulary

The implementation must keep the following identities distinct.

| Identity | Owner | Meaning | Advances when |
| --- | --- | --- | --- |
| Declared entity version | one `#[entity]` source declaration | application-declared entity lineage used for one-step migration admission | that entity's generated-owned schema intentionally changes |
| Accepted entity-source version | persisted generated-source lineage | last declared entity version accepted for one generated-owned entity | that entity's source migration publishes |
| Accepted store revision | accepted schema bundle | monotonic publication identity for one store-local accepted bundle | that store publishes a new accepted bundle |
| Accepted entity schema version | accepted entity snapshot | entity-local semantic schema version used by DDL and accepted snapshots | an accepted entity transition publishes |
| Row-layout version | accepted entity row layout | physical row-envelope layout identity | physical field-slot layout changes |
| Proposal contract version | `icydb-schema` transport | wire/profile version of `SchemaProposal` | the proposal transport format hard-cuts |
| Entity source digest | source compiler and accepted lineage | canonical generated-owned target meaning for one entity and its reachable generated-owned closure, excluding migration instructions | that entity's target meaning changes |
| Migration plan digest | migration compiler and runtime | exact identity of one resolved `from -> to` plan | any migration rule, input contract, or candidate meaning changes |

The public source field remains:

```rust
#[entity(
    store = "ApplicationStore",
    version = 2,
    // entity declarations...
)]
pub struct Account {}
```

Internally it should be named `DeclaredEntityVersion`; it must not reuse the
unqualified runtime `SchemaVersion` type. The accepted counterpart should be
`AcceptedEntitySourceVersion`. The existing runtime `SchemaVersion` remains an
accepted snapshot revision advanced by DDL and catalog-native publication.

The current `#[entity(version = ...)]` spelling is retained and becomes
effective. It lowers through `EntityFragment` and `SchemaProposal` and is
persisted in the generated-source lineage for the accepted entity. There is no
canister- or database-level source version.

SQL DDL continues to use accepted entity schema versions. It does not
implicitly change an accepted entity-source version. Generated-owned objects
and DDL-owned objects retain their current ownership rules.

## Tentative Source Grammar

Entity versions remain beside the schema they version. The migration plan
belongs to the canister/database declaration because one atomic publication
may coordinate several entity transitions, stores, shared named types,
relations, and constraints. The plan lists only transitioning entities and
does not introduce a global version.

The tentative attribute grammar is:

```rust
#[canister(
    migrations(
        entity_migration(
            entity = "Account",
            from = 1,
            from_name = "User",
            renames(
                field(from = "email", to = "primary_email"),
                named_type(from = "Status", to = "AccountStatus"),
                variant(named_type = "Status", from = "Active", to = "Enabled"),
                record_field(
                    named_type = "Profile",
                    from = "display",
                    to = "display_name"
                ),
                constraint(
                    from = "email_valid",
                    to = "primary_email_valid"
                ),
                rule(
                    named_type = "Rating",
                    from = "range",
                    to = "valid_range"
                ),
            ),
            transforms(
                rewrite(
                    from = "age",
                    to = "age",
                    checked_cast(to = "Nat16")
                ),
                fill(
                    to = "status",
                    literal(enum(
                        named_type = "AccountStatus",
                        variant = "Enabled"
                    ))
                ),
            ),
        ),
        entity_migration(
            entity = "Post",
            from = 3,
            renames(
                relation(from = "author", to = "creator")
            ),
        )
    ),
    memory_namespace = "application",
    memory_min = 100,
    memory_max = 110,
    commit_memory_id = 109,
)]
pub struct ApplicationCanister {}

#[entity(
    store = "ApplicationStore",
    version = 2,
    // current Account schema...
)]
pub struct Account {}

#[entity(
    store = "ApplicationStore",
    version = 4,
    // current Post schema...
)]
pub struct Post {}
```

The exact punctuation is tentative. The semantic contract is not:

- every entity has exactly one current declared version;
- there is at most one active database-scoped migration plan;
- an entity appears at most once in that plan;
- `to` is the referenced entity's current declared version and is omitted from
  `entity_migration`;
- `from + 1 == current entity version`;
- `entity = "Account"` selects the current target entity, while an optional
  `from_name = "User"` and nested `from` selectors refer to accepted-before
  names;
- every `to` name refers to the current source proposal;
- a shared named-type or cross-entity relation transition must list the
  complete affected entity set in the same plan;
- changing a shared named type increments every generated entity whose
  accepted contract reaches that type; unchanged consumers cannot retain a
  different meaning for the same accepted type identity;
- operations are declarative and order-independent;
- the compiler canonicalizes operations before hashing or transport;
- the marker Rust type, module path, declaration order, and Cargo package name
  are not migration identity; and
- `#[cfg]` may include or exclude the complete migration capability for a
  deployment artifact, but may not conditionally remove individual operations
  from one declared plan.

An empty `entity_migration` is invalid. Each entity version bump must identify
at least one semantic difference after DDL-owned facts are excluded. An
unchanged entity does not increment merely because another entity migrates.

## One-Step Upgrade Contract

0.218 intentionally supports each entity's current version and immediate
predecessor only.

For one entity declared at version `N`:

- a fresh entity initializes directly at `N`;
- accepted entity-source lineage recorded at `N` may reconcile only when its
  generated-owned source meaning is already exact;
- lineage recorded at `N - 1` requires the entity's exact transition whose
  `from = N - 1`;
- lineage older than `N - 1` fails with `VersionGap`;
- lineage newer than `N` fails with `Downgrade`;
- an existing generated-owned entity with no entity-source lineage is
  `Unadopted`, not silently version 1; and
- an unadopted nonempty entity may enter version 1 only through explicit,
  controller-authorized adoption that binds its exact live accepted identity
  and database head.

The operational release sequence for one entity is therefore:

```text
entity accepted at v1
    -> deploy Wasm with entity v2 and transition 1 -> 2
    -> complete migration and accept entity v2
    -> deploy later Wasm with entity v3 and transition 2 -> 3
```

Deploying that entity's v3 declaration directly over its accepted v1 lineage
is rejected. Operators must deploy the v2 artifact first. Another entity at
v7 is unaffected unless the same database-scoped plan includes its own
contiguous transition.

This restriction is deliberate:

- source contains only current entity declarations and one coordinated plan;
- no old Rust model remains;
- no hidden encoded intermediate schema snapshot remains;
- no unbounded migration registry grows in Wasm;
- upgrade behavior is reviewable from one source diff; and
- deleting an old migration does not create an alias or fallback path.

A future multi-hop migration-bundle design may relax this restriction, but it
must own artifact distribution, intermediate schema contracts, and cumulative
Wasm cost explicitly.

## Per-Entity Source-Lineage Record

Generated-source lineage is persisted per accepted entity in a dedicated
database-control catalog. It is not inferred from:

- maximum accepted store revision;
- accepted entity `SchemaVersion`;
- row-layout versions;
- current Rust declarations;
- Candid or Wasm module versions;
- application package version; or
- migration receipt count.

Each entry contains at least:

```rust
struct AcceptedEntitySourceLineage {
    entity: EntityTag,
    version: AcceptedEntitySourceVersion,
    accepted_head: ExpectedAcceptedHead,
    source_digest: EntitySourceDigest,
}
```

The exact type remains internal. The entity identity, accepted head, and entity
source digest bind the version number to one exact accepted generated-owned
meaning.

`EntitySourceDigest` hashes the canonical generated-owned target meaning of one
entity, including its reachable type and relation closure. A shared type
therefore participates in every referencing entity digest, and changing it
requires all affected entity versions to advance in the same coordinated
plan. The digest excludes migration declarations so removing an
already-applied plan from a later same-version Wasm does not pretend that the
accepted entity changed.
`SchemaProposalDigest` remains the exact submission/idempotency digest and may
cover both target schema and migration instructions. The two digest domains
must not be reused interchangeably.

The lineage catalog should use one new bounded reserved entry in the existing
database-control region rather than changing every accepted store-root codec.
Absence for an existing generated-owned entity is the typed state
`Unadopted`; it is never silently decoded as version 1.

Every later accepted publication updates the relevant entries'
`accepted_head`. SQL DDL therefore changes the recorded head while preserving
each entity-source version and digest. The next source migration binds the
latest accepted head, including legitimate DDL-owned differences, rather than
requiring the database to remain byte-identical to its last source
publication.

Adoption of an existing pre-0.218 database:

1. is an explicit controller action;
2. is allowed only when every adopted source entity declares version 1;
3. captures the exact live database head;
4. proves current generated source reconciliation is a no-op for every
   adopted entity;
5. writes all adopted entity-lineage entries atomically; and
6. publishes no accepted schema change.

Fresh initialization writes each current entity lineage together with initial
accepted publication.

## Authority Model

| Concern | Sole owner |
| --- | --- |
| Current target schema | current source proposal before acceptance; accepted candidate after publication |
| Current entity versions | `#[entity(version = ...)]` declarations before acceptance; per-entity lineage after publication |
| Runtime schema meaning | accepted catalog and accepted entity snapshots |
| Old migration input | persisted accepted-before catalog and rows |
| Rename correspondence | explicit migration rules |
| Accepted structural identity | accepted IDs |
| Source-binding rekey | schema migration planner |
| Physical row transform meaning | versioned schema-owned migration program |
| Physical progress | durable migration job record |
| Row and index commits | ordinary commit/journal authority extended with migration progress |
| Candidate publication | existing schema application publication boundary |
| Public operational exposure | explicit 0.217-style endpoint declarations |
| CLI orchestration | repeated calls to deployed migration methods; never local source inference |

Generated models remain proposal-only. Migration execution never calls a
generated entity constructor, generated decoder, `Default`, validator,
normalizer, or application callback.

SQL DDL remains a frontend over catalog-native mutation. It does not own the
source migration plan, durable job, progress cursor, row transform evaluator,
or final publication.

## Rename And Rekey Semantics

Every rename rule binds one accepted-before object and one current-proposal
object of the same logical kind.

The planner must prove:

- the accepted-before owner exists exactly once;
- the current-proposal target exists exactly once;
- neither side participates in another rename of the same kind;
- the accepted ID is compatible with the current target contract;
- no unrelated accepted object already owns the target source key or name;
- no current target already binds to a different accepted ID;
- all dependent references remain resolvable after the complete rename set;
  and
- every generated-owned source-key mismatch is explained by exactly one
  rename, addition, removal, or supported semantic mutation.

The migration is simultaneous rather than sequential. For every included
entity transition, all `from` references bind against that entity's accepted
predecessor and all `to` references bind against its current declaration
before any accepted state changes.

### Entity Rename

An entity rename:

- preserves `EntityTag`;
- replaces the entity source binding;
- updates accepted display/path metadata;
- preserves field IDs, relation IDs, constraint IDs, and physical stores;
- updates generated dependent canonical names;
- preserves row and index storage unless another rule requires physical work;
  and
- does not rename the Rust store or move the entity between stores.

Entity movement between stores is not a rename and remains unsupported.

### Field Rename

A field rename:

- preserves `FieldId`;
- preserves the physical slot;
- replaces the field source binding;
- updates accepted field display metadata;
- updates field-path index and expression-source labels;
- updates relation and constraint diagnostic paths;
- rekeys derived targeted-rule constraint bindings where required; and
- preserves physical index generation when the resolved key contract is
  otherwise unchanged.

### Named-Type Rename

A named-type rename:

- preserves `EnumTypeId` or `CompositeTypeId`;
- replaces the type source binding;
- updates the accepted current type name;
- updates references from accepted entity and nested type contracts;
- preserves accepted recursive-graph identity; and
- requires complete coverage across every store-local accepted copy.

### Enum Variant And Record Member Rename

Variant and record-member renames preserve `EnumVariantId` and
`CompositeFieldId` respectively. Record-member layout and enum wire meaning
remain unchanged when the value contract is unchanged.

### Relation, Constraint, And Rule Rename

Relation and constraint renames preserve `RelationId` and `ConstraintId` when
their accepted semantics remain compatible.

A durable-rule rename maps the old local rule name to the new current rule
name. The planner updates the domain-separated derived source binding for every
accepted root/type/rule occurrence while preserving the accepted targeted
constraint identity when the rule operation and target remain compatible.

If the rule meaning also changes, normal accepted constraint activation and
historical validation rules apply after identity correspondence is resolved.

### Indexes

Indexes have no authored rename operation. Their canonical source names derive
from entity and key shape.

The migration planner follows accepted index identity through an entity or
field rename when the resolved key, predicate, uniqueness, and physical
generation remain semantically identical. A changed key or predicate is an
index mutation and may require rebuild. Similar canonical text is never used
to guess correspondence.

### No Alias Retention

After successful publication:

- only current source keys resolve for every migrated entity;
- predecessor source keys do not resolve;
- typed adapters bind current names only;
- source removals name current accepted bindings only; and
- no compatibility map translates an old name at runtime.

Migration receipts may retain old names for audit diagnostics, but receipts
are not lookup authority.

## Candidate Derivation

Migration planning proceeds in this order:

1. recover all registered stores and the database-control region;
2. load the exact accepted-before database head;
3. load or adopt the accepted per-entity source-lineage entries;
4. compile and validate the current source proposal;
5. validate every declared entity `from -> current` version contract;
6. bind every rename `from` selector to accepted IDs;
7. bind every rename `to` selector to current proposal keys;
8. construct a temporary rekeyed accepted identity view;
9. reconcile the complete current proposal against that view;
10. classify every difference as metadata-only, activation, physical
    transform, physical index work, supported removal, or unsupported;
11. compile typed transforms against accepted-before and candidate-after
    contracts;
12. derive the exact candidate accepted bundles;
13. compute the migration plan digest and candidate head; and
14. persist a prepared migration record before any physical work begins.

The rekeyed view is planner-local. Accepted source bindings do not change
during preparation or validation.

Candidate derivation must reject:

- an unexplained source-key replacement;
- a rename whose structural kind changes;
- a rename combined with an incompatible primary-key change;
- a generated-owned target that would steal a DDL-owned identity;
- an incomplete cross-store named-type rename;
- a dependent index/relation/constraint that cannot be mapped exactly;
- a physical transition without a supported runner;
- an unsupported transform;
- a migration plan that does not converge exactly on the current proposal; or
- a plan whose candidate head differs when recompiled against the same
  accepted head.

## Closed Data-Transformation Vocabulary

The transformation program is schema-owned, versioned, bounded, and
serializable. The tentative current form is `MigrationProgramV1`.

It operates on accepted field IDs, typed scalar values, and explicit
candidate-field IDs after binding. Authored names disappear during compilation
except in diagnostics.

Both the source and target fields must be generated-owned objects participating
in the declared source transition. `MigrationProgramV1` cannot read, replace,
or adopt a DDL-owned field.

Physical data transforms require a durable journaled store. Heap stores may
take catalog-only migrations, and a fresh/reinitialized heap store starts
directly at the current schema, but 0.218 does not pretend that volatile rows
survive an upgrade or attach durable migration progress to them.

### Literal Fill

```text
target = typed literal
```

The literal must be exactly representable by the candidate field contract.
This supports adding required fields with a fixed historical value.

### Exact Copy

```text
target = source
```

Source and target value contracts must be identical. This supports replacing
one field with another accepted identity when an identity-preserving rename is
not intended.

An ordinary rename does not need an exact-copy transform because it keeps the
same accepted field and physical value.

### Checked Scalar Cast

```text
target = checked_cast(source, target_scalar_kind)
```

The initial cast matrix is restricted to exact, deterministic scalar
conversions:

- widening within signed integer kinds;
- widening within unsigned integer kinds;
- checked signed/unsigned integer conversion;
- checked integer narrowing;
- checked integer-to-decimal conversion at the candidate scale; and
- checked decimal rescaling only when no precision is lost.

Float casts, text parsing, locale-sensitive conversion, timestamp parsing,
principal parsing, blob/text reinterpretation, and lossy rounding are
unsupported.

Every cast failure reports the accepted entity ID, primary key, source field
ID, target field ID, and typed reason without matching an error string.

### Coalesce With Literal

```text
target = coalesce(source, typed_literal)
```

The source must be optional and compatible with the target. Existing non-null
values are preserved; null uses the exact typed literal. This supports a
common optional-to-required transition.

### Deliberately Excluded From V1

`MigrationProgramV1` does not include:

- arbitrary Rust functions or closures;
- application validators or normalizers;
- SQL strings or stored procedures;
- arbitrary expression ASTs;
- cross-field arithmetic beyond checked cast/coalesce;
- text concatenation, regex, locale, or time-zone behavior;
- enum remapping beyond identity-preserving variant rename;
- collection element rewrites;
- nested record restructuring;
- cross-entity reads or relation lookups;
- row filtering, row insertion, row deletion, or row fan-out;
- aggregates or cross-row uniqueness logic;
- external canister calls;
- nondeterministic time, randomness, identity, or environment access; or
- primary-key transformation.

These exclusions keep migration replay deterministic and prevent source
callbacks from becoming persisted database authority.

## Planning Classification

Every admitted plan receives one exact class:

| Class | Historical row work | Index work | Publication |
| --- | --- | --- | --- |
| Exact | none | none | no publication |
| Metadata only | none | none | atomic candidate publication |
| Activation | bounded historical validation | as currently required | existing activation publication rules |
| Physical rewrite | validate then rewrite affected rows | rebuild affected generations | publish after all work |
| Unsupported | none | none | reject before work |

One migration may contain metadata, activation, and physical work. The runtime
uses the strongest required class and retains the complete ordered phase plan.

The classification is derived from accepted IDs and contracts after rename
binding. It is not selected by an author flag.

## Durable Migration Record

One database may have at most one nonterminal source migration.

The durable record contains at least:

```rust
struct SchemaMigrationRecord {
    transitions: Vec<EntityVersionTransition>,
    accepted_before: ExpectedAcceptedHead,
    candidate_head: ExpectedAcceptedHead,
    entity_source_digests: Vec<(EntityTag, EntitySourceDigest)>,
    submission_digest: SchemaProposalDigest,
    plan_digest: SchemaMigrationPlanDigest,
    phase: SchemaMigrationPhase,
    affected_entities: Vec<AcceptedEntityIdentity>,
    progress: SchemaMigrationProgress,
}
```

The exact current-form codec is bounded and fallible. It is stored in the
database-control region and covered by the database commit/recovery protocol.

Persisted progress uses accepted IDs and raw primary-key cursors. It does not
persist Rust type names, Rust paths, callback symbols, generated entity
objects, or executable bytecode.

If a new Wasm presents a different plan digest while a migration is
nonterminal, recovery fails closed with `PlanChanged`. Restoring the exact
migration plan or completing an explicit pre-rewrite abort is required.

## Execution Lifecycle

The tentative lifecycle is:

```text
Unadopted
  -> Adopted

Idle
  -> Prepared
  -> Validating
  -> ReadyToRewrite
  -> RewritingRows
  -> RebuildingIndexes
  -> FinalValidation
  -> Publishing
  -> Applied
```

Rejection before irreversible work:

```text
Prepared / Validating
  -> Rejected
  -> Aborted
```

Recovery after a trap or upgrade:

```text
nonterminal phase
  -> recover exact durable cursor and plan digest
  -> resume the same phase
```

### Prepared

Preparation binds the exact accepted-before head, resolves the migration plan,
derives the candidate, and persists the plan digest. No row or accepted catalog
state changes.

### Validating

Validation scans every affected historical row through accepted-before decode
contracts and the compiled transform program.

Before the first validation cursor is persisted, the engine durably installs
the affected-write gate and captures the exact accepted-before head. This is
required because IcyDB has no migration MVCC snapshot from which a concurrent
writer could be excluded retroactively.

It proves:

- every source row decodes under accepted-before authority;
- every transform succeeds;
- every candidate row admits under candidate field and constraint contracts;
- every relation target remains valid;
- every candidate unique index key is unique; and
- the same accepted-before head and plan digest remain active.

Validation may build durable staged index generations. It does not make them
runtime-visible.

### Ready To Rewrite

This is the last generally abortable phase. The engine records that complete
historical validation succeeded.

An explicit abort before row rewrite:

- deletes staged physical generations;
- leaves predecessor entity versions and all rows unchanged;
- retains a terminal diagnostic receipt; and
- clears the affected read/write gates.

### Rewriting Rows

Once the first row rewrite commits, user abort is not supported. The job must
resume to publication of the declared target entity versions or fail closed
for operator intervention.

Each bounded chunk:

1. resumes after the last durably committed primary key;
2. decodes with accepted-before row contracts;
3. evaluates the already-validated transform program;
4. encodes the candidate row layout;
5. writes candidate index generations or staged index effects;
6. commits row/index/journal effects and the next migration cursor atomically;
   and
7. returns progress before exceeding the fixed instruction/work budget.

Retrying a committed chunk observes the advanced durable cursor. Retrying an
uncommitted chunk repeats the same deterministic work.

### Rebuilding Indexes

Affected indexes are rebuilt into non-visible physical generations owned by
the migration job. Existing accepted indexes remain authoritative but are not
queried for affected entities while the migration gate is active.

### Final Validation

Final validation proves:

- every affected row uses the candidate layout;
- every staged index generation exactly covers the candidate row domain;
- relation and constraint validation is complete;
- no accepted-before row remains above the durable cursor;
- the live accepted database head still equals `accepted_before`; and
- the compiled source proposal and plan digests still match the prepared job.

### Publishing

Publication atomically:

- installs all candidate accepted bundles;
- activates candidate index generations;
- replaces all renamed source-binding keys;
- records every affected accepted entity-source lineage;
- marks the migration receipt applied;
- advances runtime schema/cache epochs; and
- removes the affected-entity migration gate.

Normal runtime execution never observes a catalog containing only part of the
coordinated entity-version plan.

Old physical generations and retired slots may be reclaimed only through an
explicit schema-owned cleanup plan after publication. Publication correctness
does not depend on immediate reclamation.

## Availability And Concurrency

0.218 chooses bounded offline migration for affected entities rather than
inventing dual-write online migration.

While `Prepared`:

- ordinary reads and writes may continue;
- a concurrent schema mutation or accepted publication invalidates the
  prepared job before validation; and
- the job must be re-prepared against the new head.

From `Validating` through `ReadyToRewrite`:

- reads through accepted predecessor entity schemas remain available;
- writes to affected entities are blocked;
- relation writes whose source or target is affected are blocked;
- every validation step rechecks the exact accepted-before head and durable
  gate identity;
- schema mutation and DDL affecting any involved store are blocked; and
- abort remains available because accepted rows are unchanged.

From `RewritingRows` through `Publishing`:

- reads of affected entities fail with `SchemaMigrationInProgress`;
- writes to affected entities fail with `SchemaMigrationInProgress`;
- relation operations whose source or target is affected fail with the same
  typed classification;
- schema mutation and DDL affecting any involved store fail with
  `SchemaMigrationInProgress`;
- unaffected entities remain available when the registry can prove their
  routes do not consume affected relation or store-local migration state; and
- integrity and migration operations explicitly report whether they are
  observing accepted-before or private candidate state.

The first implementation may conservatively gate the complete database if a
safe affected-entity closure cannot be proven. It must report that choice and
may not silently claim per-entity availability.

No user write is queued for later replay.

## Failure, Abort, And Recovery

| Failure point | Accepted authority | Row state | Required action |
| --- | --- | --- | --- |
| Compile/bind/preparation failure | predecessor entity versions | unchanged | fix declaration and retry |
| Historical validation finding | predecessor entity versions | unchanged | fix data or migration rule; abort/reprepare |
| Concurrent accepted-head change before rewrite | latest accepted head | unchanged by migration | reprepare |
| Explicit abort before rewrite | predecessor entity versions | unchanged | optional retry with a new exact plan |
| Trap during rewrite | predecessor entity versions, affected entities gated | partially rewritten under durable cursor | resume exact plan |
| Plan digest changed during rewrite | predecessor entity versions, affected entities gated | partially rewritten | restore exact plan; no fallback |
| Corrupt migration record or row | fail closed | unknown/current durable state | operator repair; no inferred recovery |
| Publication race after rewrite | predecessor entity versions, affected entities gated | candidate physical state complete | recheck; publish only if exact head remains |
| Successful publication | declared target entity versions | candidate rows/indexes | normal operation |

Rollback after row rewriting starts is not offered in 0.218. Supporting
rollback would require retaining complete inverse transforms or shadow copies
and is a separate design.

Recovery restores the exact durable gates before affected stores become
available. `start!()` may install private lifecycle recovery and gates, but it
never creates a public migration method and never silently begins a new
migration.

## Public Rust And Endpoint Surface

The exact names are tentative, but the capability split is:

- `icydb/migration` compiles migration planning, status, and execution;
- the canister/database declaration provides the current coordinated
  migration plan;
- a compiled capability does not imply public exposure; and
- missing capability makes a migration plan declaration or endpoint fail
  clearly at compile time.

0.217-style endpoint declarations are explicit:

```rust
icydb::start!();

icydb::endpoints! {
    icydb_schema_migrate;
    icydb_schema_migration;
}
```

Each declaration creates one method:

| Declaration | Mode | Authorization | Purpose |
| --- | --- | --- | --- |
| `icydb_schema_migrate` | update | controller | adopt, prepare, advance, resume, or pre-rewrite abort |
| `icydb_schema_migration` | query | controller | report lineage, plan identity, phase, progress, and last typed finding |

The update takes a closed command enum. The query takes no arguments. Exact
Candid signatures, bounds, and error DTOs must be frozen before Patch 4.

Application code may call the same private Rust capability from a handwritten
controller API instead of declaring these maintained endpoints.

A Wasm that omits `icydb/migration` while a nonterminal migration record exists
must fail readiness rather than expose partially migrated state. After a
migration is applied, a later same-version Wasm may omit the completed
migration plan declaration and capability; accepted per-entity lineage remains
authoritative. Each entity version bump requires its own
immediate-predecessor transition in the coordinated plan.

Fixture reset/reinstall commands must refuse to erase a nonterminal migration
unless the fixture endpoint's existing destructive contract explicitly resets
the complete database.

## CLI Contract

The tentative CLI surface is:

```text
icydb schema migration status
icydb schema migration advance
icydb schema migration run
icydb schema migration abort
icydb schema migration adopt
```

The CLI:

- calls the deployed canister only;
- never reads local migration declarations to predict deployed behavior;
- never consults `icydb.toml`;
- preserves actual method-not-found and authorization errors;
- treats `run` as repeated bounded `advance` calls;
- prints exact phase, accepted head, plan digest, row progress, and findings;
- requires explicit confirmation for abort and adoption;
- stops if the deployed plan or database identity changes; and
- never fabricates success from local entity versions.

CLI looping is operational convenience, not execution authority. Every update
call remains independently bounded and idempotent.

## Relationship To SQL DDL

Source migrations and SQL DDL share catalog-native mutation and publication
owners but remain different frontends.

SQL DDL:

- binds one accepted entity version;
- expresses an operator-authored accepted mutation;
- may mutate DDL-owned objects; and
- continues to use its explicit `EXPECT/SET SCHEMA VERSION` contract.

Source migration:

- binds the exact accepted head plus every affected entity's source lineage;
- reconciles generated-owned current source declarations;
- supplies rename correspondence and closed data transforms; and
- may coordinate several accepted entities and stores.

Neither frontend may:

- construct accepted snapshots directly;
- bypass mutation compatibility;
- publish before required physical work;
- create a separate index rebuild runner;
- update source bindings outside schema-owned migration planning; or
- override the other's ownership classification.

0.218 does not add a general SQL migration-script language. A future SQL
frontend may lower a versioned migration draft into the same internal migration
plan, but it must not execute SQL text from a persisted source migration.

## Persistence And Format Impact

0.218 adds current-form persisted state for:

- accepted per-entity source lineage;
- durable migration record and phase;
- migration plan digest;
- bounded row and index progress cursors;
- candidate/staged physical generation ownership; and
- terminal migration receipts/findings.

It may hard-cut the current schema proposal transport to carry:

- each entity's current declared version;
- the closed coordinated migration plan; and
- its canonical digest inputs.

The implementation must inventory and freeze:

- proposal contract version/profile;
- database-control record magic/version/maximum bytes;
- migration progress codec and maximum bytes;
- candidate index-generation key space;
- commit-marker migration effect shape;
- recovery decoder ownership;
- accepted schema fingerprint coverage;
- application receipt coverage; and
- raw row/index formats affected by physical rewrite.

There is no decoder for an abandoned 0.218 prototype format. Patch 1 freezes
the exact current form before production persistence is introduced.

Existing pre-0.218 accepted catalog, row, index, journal, and schema-store
formats remain readable because 0.218 migrates their current semantic content;
it does not translate an obsolete codec. The new lineage record begins as
`Unadopted` for an existing database and requires explicit adoption.

## Security And Resource Bounds

- Migration control endpoints are controller-only.
- Migration declarations and transform programs are bounded before transport.
- Every scan and rewrite call uses fixed engine-owned work limits.
- Persisted cursors and staged generation identifiers are bounded and
  validated.
- A malicious or malformed proposal cannot select arbitrary stable memory.
- Transform programs cannot call application code or external canisters.
- Candidate rows pass the same accepted value bounds as ordinary writes.
- Candidate index keys pass the same key-size and uniqueness contracts.
- Status responses are bounded and paginated where findings exceed one page.
- No endpoint accepts an arbitrary instruction limit, memory ID, store handle,
  callback path, or raw internal plan.

## Performance And Wasm Budget

When `icydb/migration` is not compiled:

- no migration endpoint or transform evaluator is present;
- no migration plan is linked;
- no runtime migration registry exists; and
- normal read/write cost must remain neutral.

When the capability is compiled but no migration is active:

- normal operations may pay at most one cheap readiness/gate check;
- no accepted row is decoded for migration;
- no staged index generation is opened; and
- no source proposal is rebuilt on the hot path.

Each implementation patch reports:

- raw non-gzipped Wasm delta;
- migration-disabled and migration-enabled package size;
- no-active-migration read/write instruction delta;
- rows validated/rewritten per bounded call;
- stable-memory staging growth;
- files and approximate line delta; and
- whether owner structure became simpler, neutral, or more complex.

Gzip remains secondary context.

## Validation Plan

### Authoring And Versioning

- entity version zero rejects;
- migration `from` zero rejects;
- a noncontiguous entity `from -> current` transition rejects;
- two active plans or duplicate transitions for one entity reject;
- an entity version bump without a semantic change rejects;
- a semantic generated-source change without that entity's version bump
  rejects;
- fresh initialization at entity version 2 skips its version-1 transition;
- accepted entity version 1 admits its exact `1 -> 2` transition;
- accepted entity version 0/gap and version 3/downgrade reject against a
  current version 2 declaration;
- different entities may remain at different versions;
- one coordinated plan may atomically advance several contiguous entity
  transitions;
- unadopted nonempty entities require explicit adoption; and
- module moves and declaration reorder do not change migration identity.

### Rename Binding

- every supported object kind preserves its accepted ID;
- old source keys stop resolving after publication;
- new source keys resolve to the preserved ID;
- duplicate sources and targets reject;
- kind mismatch rejects;
- ambiguous shape similarity never creates correspondence;
- field rename updates index/relation/constraint path metadata;
- named-type rename covers every store-local accepted copy;
- rule rename preserves accepted targeted constraint IDs where compatible;
- index canonical names rekey only through exact accepted ownership; and
- a simultaneous entity plus child rename is order-independent.

### Metadata-Only Publication

- no row or index bytes change;
- accepted head and affected entity lineages advance atomically;
- application receipt records exact prior/candidate heads;
- runtime cache invalidation occurs only after publication;
- a publication race leaves predecessor entity versions accepted; and
- retry returns the same terminal receipt.

### Transformation Compilation

- literal, copy, checked cast, and coalesce type-check exactly;
- unsupported kinds reject before scanning rows;
- overflow, sign, precision, and null findings are typed;
- no application callback token or function path enters the plan;
- plan digest changes for every semantic rule edit;
- diagnostic-name edits that do not change accepted targets do not change
  executable meaning unless they are an explicit rename; and
- compiled programs contain accepted IDs rather than Rust paths.

### Durable Execution

- each chunk commits row/index effects and cursor together;
- trap before commit repeats the same chunk;
- trap after commit resumes after the committed key;
- plan change during a nonterminal job fails closed;
- affected reads/writes reject during irreversible phases;
- unaffected routes remain available only when closure is proven;
- validation finding permits abort before rewrite;
- abort after rewrite begins rejects;
- final publication activates candidate index generations atomically;
- startup recovery restores the exact gate and phase;
- journal replay does not publish candidate schema early; and
- corruption never falls back to source reconstruction.

### Cross-Frontend And Ownership

- DDL-owned objects are not captured by generated migration renames;
- source migration and DDL cannot run concurrently over the same affected
  store;
- generated proposal application, DDL, and migration use one candidate
  publication owner;
- accepted schema remains runtime authority throughout;
- typed adapters bind new names only after their target entity versions
  publish; and
- no generated model decodes historical rows.

### Endpoint And CLI

- `start!()` alone exports no migration method;
- each declaration adds exactly one fixed Candid/Wasm method;
- missing capability fails compilation;
- controller authorization is exact;
- undeclared methods are absent, not disabled stubs;
- CLI preserves deployed method-not-found errors;
- `run` stops on database identity, plan digest, or deployment change; and
- no config-file or local-source preflight is reintroduced.

## Principal Risks

### Entity And Accepted Version Vocabulary Drift

The current entity macro version is not yet propagated into proposals. 0.218
must wire it through as `DeclaredEntityVersion` without conflating it with the
accepted snapshot `SchemaVersion`, `AcceptedEntitySourceVersion`, or
row-layout version. A database-scoped plan coordinates entity transitions but
must never acquire a competing global version. Patch 1 freezes the exact names
and owners before persisted state is added.

### Rename Cascades Become Aliases

Dependent key updates are a one-time planner operation. Runtime lookup must not
consult old names after publication.

### Partial Physical Rewrite

Once row rewrite begins, predecessor entity versions remain accepted while
affected entities are gated. Durable progress and exact-plan recovery are
mandatory; without them, physical transforms must remain rejected.

### Staging Cost

Unique-index validation and candidate generations may require stable memory
proportional to affected data. The runner must report and bound allocation; it
must not stage an unbounded in-heap copy.

### Overbroad Transform Language

An arbitrary expression or callback language would become a persisted
execution engine. The first vocabulary remains intentionally closed.

### Cross-Store Atomicity

Candidate publication may span several stores. The existing database commit
and schema-application receipt boundary must remain the only final publication
owner.

### Rollback Expectations

Users may expect migration abort to mean rollback. 0.218 supports abort only
before irreversible row rewrite and documents resume-only behavior afterward.

### Endpoint Becomes Hidden Upgrade Work

`start!()` detects and gates incomplete jobs but does not start a new migration.
Public operational methods remain explicit source declarations.

- retain complete historical Rust schema models;
- support a version gap or multi-hop migration ladder for one entity;

- retain old source-key aliases after publication;
- change store allocation identity or move entities between stores;
- change primary keys;
- transform primary-key values;
- provide online dual-write or zero-downtime migration;
- permit writes to affected entities during irreversible work;
- offer rollback after row rewrite begins;
- execute arbitrary Rust callbacks, validators, or normalizers;

- add arbitrary expression, scripting, trigger, or stored-procedure support;
- transform nested collections or recursive named values in v1;
- perform cross-entity data joins or external canister calls;
- adopt DDL-owned objects into generated ownership;
- publish partially migrated schema;
- reconstruct accepted schema from generated models during recovery;
- add a legacy proposal or progress decoder;
- make migration endpoints implicit;
- reintroduce config-file endpoint authority; or

## Tentative Verdict

This direction preserves the simplification gained by replacing
`source_key`/`ident` authoring with current `name`.

Normal schema declarations remain concise. Migration-only information appears
only when a developer intentionally changes accepted identity or historical
data meaning. For each affected entity, the accepted catalog supplies the
predecessor, its current source declaration supplies the target, and the
coordinated migration plan supplies only the missing correspondence and
deterministic transform rules.

The per-entity one-step restriction is the main simplifying decision. It
makes migration behavior explicit and bounded without forcing unrelated
entities to advance together or turning the canister into a host for every
historical Rust model or an open-ended migration scripting runtime.
