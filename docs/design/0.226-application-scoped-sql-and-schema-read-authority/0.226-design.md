The cross-repository predecessor is the maintained Canic authentication and
access surface, audited from Canic 0.101.53 before this design cut. That surface
separates authenticated application subjects from infrastructure authority,
supports Fleet-audience and role-scoped delegated tokens, and verifies tokens
locally. It remains Canic authority; this IcyDB document cannot authorize a
Canic public API, persisted-state, or release change.

## Planning Status And Authorization

This line makes generated read authority separable from canister
controllership. It adds one application-supplied authorization contract for the
opt-in generated SQL query and schema query surfaces while preserving their
read-only execution rules and the existing controller/public declaration
forms. It does not authorize implementation.

Implementation requires a completed 0.225 closeout, a Patch 1 reconciliation
against the exact IcyDB and Canic predecessors, an accepted paired Canic design
for any Canic-side gap, review of the seven-patch tracker and hard cuts, and
explicit user authorization for 0.226.

## Production Evidence And Demonstrated Gap

The Explorer production report establishes two concrete failures in the
maintained controller-only SQL boundary:

1. a principal allowed to read generated SQL is necessarily able to exercise
   canister lifecycle authority outside IcyDB; and
2. a coordinator-created Canic child may be controlled only by a canister, so
   no human principal can call its otherwise-present generated SQL surface.

The reproduced Toko/Canic 0.101.45 fleet contained six canisters exporting the
surface. Both available human identities received the SQL controller-required
diagnostic on every canister. The fleet coordinator remained the controller
and exposed no external controller-bootstrap path.

The newer maintained Canic 0.101.53 authority makes the design requirement
stronger, not weaker: Canic already distinguishes application authentication
from topology and controller authority. IcyDB should provide a narrow way for
an application to consume that decision; it should not add a competing reader
registry or treat a controller list as application policy.

## Predecessor Authority Reconciliation

Patch 1 must re-read maintained code, contracts, tests, generated artifacts,
and accepted status from both repositories. The current evidence establishes
this provisional baseline:

| Concern | Current authority | Gap owned by 0.226 |
| --- | --- | --- |
| Generated SQL query | source declaration emits `icydb_query : (text) -> Result query`; wrapper calls `require_sql_controller()` before dispatch | No application-owned read decision can replace controllership while retaining the standard generated surface |
| Generated schema query | source declaration explicitly chooses `authorization = public` or `authorization = controller` | No fail-closed application-policy choice exists between public and controller-only |
| SQL command safety | trusted SQL parser/policy admits only the maintained read/introspection statement set on `icydb_query`; mutation remains rejected | Authorization must not weaken or configure the read-only dispatcher |
| Trusted facade | `execute_trusted_sql_query` permits an application-owned wrapper after its own authorization | A hand-written wrapper is possible but does not provide one standard generated ABI/declaration contract for Explorer tooling |
| Runtime diagnostics | SQL controller denial and schema controller denial have distinct frozen boundary codes | Policy denial is currently indistinguishable because no policy mode exists |
| Startup admission | 0.225 owns `Ready`, `Recovering`, terminal startup failure, and ordinary-operation gating | A guard must run before ordinary database work and must not become a readiness or recovery bypass |
| Canic application auth | delegated tokens bind subject, Fleet audience, target role, expiry, and scopes and are verified locally | The current proof-bearing endpoint guard expects the token as Candid argument zero, while the standard IcyDB SQL ABI has only the SQL text |
| Canic sessions and caller predicates | current local state can resolve subjects and topology/config predicates | Patch 1 must prove whether one existing locally decidable authority can provide the required SQL/schema scope decision without a second grant store |

Current schema snapshots, SQL parsing, read admission, request budgets,
continuation semantics, and startup coordination remain authority. An
authorization guard cannot replace or reconstruct any of them.

## Decision Summary

IcyDB adds an explicit application-guard declaration form for the two generated
read surfaces:

```rust
icydb::icydb_endpoints! {
    icydb_sql_query(
        introspection = false,
        authorization = guard(my_app::may_read_sql),
    );
    icydb_schema(authorization = guard(my_app::may_read_schema));
}
```

The existing SQL declaration without an authorization field remains exactly
controller-gated. Existing schema `public` and `controller` declarations
remain exact. A guarded declaration replaces controller authority for that
surface; it does not mean `controller OR guard`.

The guarded SQL and schema endpoints retain their maintained public Candid
signatures. The guard receives only bounded local context:

```text
ReadAuthorizationContext {
    caller: Principal,
    surface: Sql { introspection_enabled: bool } | Schema,
}

ReadAuthorizationDecision {
    Allow,
    Deny,
}
```

The generated wrapper rejects anonymous callers before invoking the guard.
For every other caller it invokes exactly the declared synchronous guard before
SQL parsing, schema observation, startup admission, database construction, or
request execution. `Allow` continues into the existing wrapper. `Deny`, a
missing authority dependency, or any application-side inability to decide must
fail closed.

The guard receives no SQL text, parsed statement, entity, field, row value,
continuation, or mutable database handle. This line deliberately authorizes a
whole declared read surface, not row-level security or per-table policy.

Canic participates as the reference fleet authority. A consuming Canic
application supplies the small adapter from one maintained locally decidable
Canic subject/scope decision to IcyDB's `Allow`/`Deny`. IcyDB does not decode
Canic tokens, store Canic grants, depend on Canic, or define Fleet revocation.

## User Outcome

- A human reader can query an opted-in canister without becoming its
  controller.
- A Canic child controlled only by its coordinator can authorize a human
  application subject through Canic's application-auth lane.
- Removing or expiring application read authority does not require changing
  canister controllers or upgrading IcyDB.
- SQL and schema reads can use separate application guards and policy-denial
  diagnostics.
- Anonymous remains denied unless the application deliberately exports the
  existing public schema mode; there is no public SQL mode in this line.
- SQL mutation rejection remains unconditional.
- Tooling can distinguish method absence, controller denial, and application
  policy denial.

## Canonical Ownership

Authority is split deliberately:

1. the consuming application owns the decision to export each generated
   surface and the exact guard path attached to it;
2. IcyDB owns declaration grammar, wrapper ordering, anonymous rejection,
   guard-context shape, fixed policy-denial mapping, read-only SQL dispatch,
   startup admission, and response bounds;
3. Canic owns Fleet subject authentication, proof issuance and verification,
   role/scope policy, local authorization evidence, expiry/revocation
   semantics, and Fleet auditability;
4. the application adapter owns the explicit mapping from its Canic scopes to
   IcyDB SQL and schema decisions; and
5. Explorer owns proof/session establishment and human-facing explanation of
   absent, controller-denied, policy-denied, expired, or unavailable authority.

The canonical call order is:

```text
method present
  -> reject anonymous in guarded mode
  -> application guard over caller + declared surface
  -> existing 0.225 startup admission
  -> existing SQL/schema handler and request budgets
  -> existing bounded response
```

No layer may infer another layer's authority. In particular, an IcyDB
controller check is not a Canic subject check, a Canic token is not an IcyDB
query continuation, and an IcyDB continuation is never authentication proof.

## IcyDB Guard Contract

The guard is synchronous, local, bounded, side-effect free, and total over
untrusted principals. It must not:

- perform an inter-canister call or await;
- parse or inspect caller SQL;
- enter IcyDB, call `db!()`, observe readiness, or drive recovery;
- mutate application, Canic, or IcyDB state;
- panic or rely on caller-controlled allocation without a fixed bound; or
- expose application-internal denial text through the generated endpoint.

The generated wrapper type-checks the exact function shape at compile time.
There is no dynamic registration, string lookup, optional runtime guard, guard
chain, fallback guard, or controller bypass.

The guard context reports whether the SQL declaration enabled introspection.
It does not report which statement was submitted because authorization occurs
before parsing. An application requiring independent row-read and
introspection scopes must declare `introspection = false` for SQL and export a
separately guarded `icydb_schema` surface. Choosing guarded SQL with
`introspection = true` deliberately grants the same caller both admitted SQL
row reads and SQL introspection statements.

## Canic Integration Contract

The reference Canic integration must reuse one maintained Canic authority and
remain locally decidable on the child canister. Query-time calls to the parent,
root, coordinator, issuer, management canister, or another service are
prohibited.

Patch 1 must audit the exact current token, session, whitelist, role, scope,
and audit surfaces. If no existing local decision retains the authenticated
subject and required scope after bounded proof/session establishment, the
paired Canic design may add the smallest extension to its existing
token/session authority. It may not add an independent IcyDB-specific reader
registry merely to satisfy this integration.

The reference scope mapping is provisional until Patch 1 freezes Canic naming:

```text
IcyDB Sql guard     <- one Canic application read scope
IcyDB Schema guard  <- one distinct Canic application schema scope
```

Canic must define exactly what revocation means. Either a local authoritative
receipt can be removed immediately, or issuer-policy removal takes effect
after a measured maximum token/session lifetime. The application and Explorer
must report that bound honestly. "Revocable" cannot mean changing controller
settings or waiting for an unspecified future upgrade.

Canic audit evidence must answer which issuer/policy, target Fleet role,
scopes, and maximum lifetime can authorize the child. It need not enumerate
every already-issued bearer token if the token model cannot do so, but it must
not claim that a guard function path alone answers "who may read this?".

If Patch 1 proves that satisfying this contract requires a second Canic grant
authority, an unbounded local session map, a remote query-time call, or an
IcyDB dependency on Canic, promotion stops and the line is redesigned or
contracted to an application-owned wrapper.

## Diagnostics And Observability

Controller declarations retain the existing SQL-controller-required and
schema-controller-required codes. Guarded declarations add one fixed
surface-specific policy-denied code for SQL and one for schema. Anonymous,
explicit `Deny`, and fail-closed unavailable decisions use the relevant policy
code; application details are not placed in the public IcyDB error.

Method absence remains the IC method-not-found result. IcyDB does not turn it
into an authorization error. Canic-specific expiry, issuer, grant, or local
authority detail remains available only through Canic's bounded diagnostic or
audit surface.

Authorization success and denial must be measurable without logging SQL text,
row values, tokens, continuations, or principals. Patch 1 must decide whether
existing endpoint metrics can carry a bounded mode/outcome label or whether no
new IcyDB metric is needed. Metrics are not authorization authority.

## Scope

0.226 includes:

- a source-declared application guard for generated `icydb_query`;
- a source-declared application guard for generated `icydb_schema`;
- one shared bounded caller/surface context and allow/deny decision contract;
- unconditional anonymous denial in guarded mode;
- replacement, not union, of controller authority when a guard is declared;
- distinct SQL and schema policy-denial diagnostics;
- preserved controller defaults and schema public/controller choices;
- a Canic-owned locally decidable reference authorization adapter;
- explicit bounded expiry or revocation behavior and inspectable Canic policy;
- generated compile, Candid, artifact, CLI/Explorer, and real-fleet evidence;
  and
- documentation for applications that choose combined SQL introspection or
  separate SQL/schema scopes.

## Non-Goals

0.226 excludes:

- public anonymous SQL;
- DDL, SQL update, integrity, fixture, metrics-reset, snapshot, migration, or
  recovery-driver authorization changes;
- row-level security, column masking, tenant filtering, per-entity policy, or
  statement-sensitive guards;
- passing SQL text, parsed plans, rows, or schema contents to a guard;
- an IcyDB reader/grant/token/session store or policy engine;
- Canic controller assignment or management-canister lifecycle changes;
- remote guard calls, async authorization, callback protocols, or cached
  remote decisions owned by IcyDB;
- bound SQL parameters or a new SQL request envelope;
- public SQL continuation integration, snapshot isolation, or a second cursor;
- general typed SQL diagnostics owned by provisional 0.231;
- weakening the trusted-lane warning or read-admission budgets; and
- compatibility aliases, old/new declaration spellings, fallback authorities,
  or dual endpoint formats.

## Persisted And Public Hard Cuts

- The guarded declaration is one new current source form. No alias, secondary
  attribute syntax, dynamic registry, or environment toggle is added.
- Existing SQL declaration syntax continues to mean controller-only. Existing
  schema `public` and `controller` modes retain their exact meaning.
- Guarded mode has the same SQL and schema Candid signatures as the maintained
  endpoint it replaces. It does not add an auth blob or token field.
- A declared guard is the sole read-authority decision for that surface;
  controllers do not receive an implicit bypass.
- Anonymous is rejected before application code in guarded mode. Public schema
  remains available only through the explicit existing public declaration.
- Guard failures map to fixed IcyDB policy codes. No arbitrary application or
  Canic error is serialized as IcyDB diagnostic detail.
- IcyDB persists no reader authority. Any Canic persisted change belongs to
  one paired current Canic format and has no legacy decoder or dual write.
- Bound invocation and continuation work moves to provisional 0.232 and must
  extend this authority boundary rather than replacing it with a second one.

## Non-Negotiable Invariants

1. A reader never gains controller, install, stop, delete, or upgrade authority
   merely by being allowed to read IcyDB.
2. Missing or unavailable application authority fails closed.
3. Anonymous never passes a guarded SQL or schema surface.
4. A guard replaces controller authority; it is not implicitly unioned with
   it.
5. Authorization runs before parsing, startup observation, database entry, or
   recovery work.
6. SQL mutation rejection and the admitted statement set are independent of
   authorization mode.
7. SQL and schema guards are independently declarable and have distinct denial
   codes.
8. Guard context contains no SQL, schema, row, plan, or continuation content.
9. Guard evaluation is synchronous, local, bounded, side-effect free, and
   non-panicking on maintained production paths.
10. IcyDB owns no Canic token, session, grant, expiry, or revocation state.
11. Canic authorization reuses one maintained application-subject authority
    and performs no query-time inter-canister call.
12. Revocation or expiry has a documented finite maximum latency and does not
    require an IcyDB upgrade.
13. Method absence, controller denial, and policy denial remain distinguishable.
14. Continuations remain query-progress evidence, never authentication proof.
15. 0.225 readiness remains authoritative and cannot be bypassed by an allowed
    guard.
16. Generated models never become authorization or schema authority.
17. No compatibility decoder, alias, shim, fallback authority, or dual format
    is introduced.
18. Raw non-gzipped Wasm remains the authoritative footprint measure.

## Baseline And Acceptance Measurements

Patch 1 records current controller/outsider/anonymous instructions before SQL
parse and schema read; allowed SQL and schema instructions; Candid bytes and
method modes; raw final Wasm; deterministic gzip as secondary context; Canic
local authorization lookup instructions; token/session/grant stable bytes and
maximum cardinality; grant/expiry/revocation latency; controller topology; and
complexity signals.

Acceptance requires denial before SQL parsing or schema/database work; no
query-time inter-canister call; guard work independent of row, index, schema,
and retained-journal cardinality; unchanged SQL execution ceilings after
authorization; explicit bounded Canic authority storage; finite documented
revocation/expiry latency; unchanged controller/public behavior for declarations
that do not opt into a guard; and accepted raw-Wasm, stable-memory, Candid, and
instruction deltas.

Measurements distinguish endpoint wrapper cost `W`, local authorization cost
`A`, normal query cost `Q`, authority-record count `G`, authority stable bytes
`S`, revocation latency `R`, and raw Wasm delta `M`. `A` must be a bounded local
lookup and must not scale with database rows, indexes, journal history, or SQL
text length.

## Complexity And Maintenance Gate

Demonstrated need: controller-only generated reads grant excessive lifecycle
authority and are unusable for human readers on coordinator-controlled Canic
children.

Simplest alternative: a hand-written application endpoint can already
authorize and call the trusted SQL facade. Patch 1 must compare that route
honestly. The generated guard is justified only if one standard opt-in ABI,
schema separation, diagnostics, Explorer interoperability, and reduced
per-application security code outweigh the new declaration and decision types.

Canonical owner: IcyDB owns only the generated guard boundary. Canic owns the
reference subject/scope authority. The application owns their one explicit
adapter.

State-space delta: one new declaration choice and one two-way decision per SQL
or schema surface. IcyDB adds no persisted state, auth mode registry, token
format, grant lifecycle, remote cache, row policy, or continuation authority.
Canic may extend only one already-maintained auth lifecycle if Patch 1 proves a
gap.

Promotion fails if implementation adds an IcyDB reader store, generic policy
engine, auth blob, async/remote guard, implicit controller union, statement
parsing before authorization, per-table rules, duplicate Canic grants,
unbounded sessions, or a second SQL/continuation route. Every handoff reports
files/line delta, semantic owners, states, duplicate flows,
instruction/stable/raw-Wasm effects, and whether implementation structure got
simpler, stayed neutral, or became more complex.

## Promotion Gate

0.226 becomes implementation authority only when:

1. 0.225 has a reported ready/complete closeout;
2. Patch 1 freezes the exact maintained IcyDB generated ABI, wrapper ordering,
   diagnostics, SQL safety, startup gate, and controller/public defaults;
3. Patch 1 freezes the exact maintained Canic token, session, scope, local
   decision, revocation/expiry, audit, and child-controller surfaces;
4. the application-guard route is accepted over a hand-written Canic endpoint
   with measured simplicity and interoperability evidence;
5. one Canic locally decidable authority and any required paired Canic design
   are accepted without a second reader/grant store;
6. guard signature, SQL/schema separation, anonymous rule, replacement
   semantics, fixed diagnostics, and unchanged Candid signatures are frozen;
7. instruction, stable-memory, authority-cardinality, revocation-latency,
   Candid, raw-Wasm, and complexity gates are accepted;
8. the real coordinator-controlled fleet harness and lifecycle-denial probe are
   available for Patch 7; and
9. the user explicitly authorizes 0.226 implementation.

Until then, this document is proposed design authority only. It authorizes no
IcyDB or Canic code, public API, persisted format, version, changelog, or
release work.
