# 0.213 R5 — Accepted Mutation-Constraint Scheduler

## Decision

Normal SQL, structural, and typed writes must enter one internal accepted
mutation-constraint schedule before a commit marker can be opened. Recovery
replays an already-prepared marker and therefore does not re-run user
admission or current-schema constraint interpretation.

The schedule has four ordered phases:

1. mutation policy constructs the logical final after-image;
2. fingerprint-bound row-local constraints evaluate that after-image;
3. storage-backed unique and relation proofs run against one commit-batch
   overlay;
4. index/reverse-index maintenance is prepared and the atomic commit window
   opens.

The scheduler owns phase ordering and the shared constraint-diagnostic
boundary. It does not replace the specialized evaluators:

- row-local `CHECK` and `NOT NULL` rules remain compiled slot programs;
- unique rules remain overlay-aware index proofs;
- relations remain target-existence and reverse-index proofs;
- defaults and managed timestamps remain mutation policy, not constraints.

## Internal boundary

`AcceptedMutationConstraintScheduler` is the only normal-write constructor of
an `AcceptedMutationConstraintBatch`. Save rows cannot enter commit preflight
until their logical after-images have passed the row-local program. Delete
batches cannot enter commit preflight until relation delete protection has
seen the complete key set.

Commit preparation compiles one accepted storage-constraint schedule from the
same fingerprint-bound snapshot used for row decoding. It contains:

- active accepted indexes and any pending unique activation;
- active accepted relation projections and any pending relation activation;
- the accepted row contract used by both proof families.

All row images in a multi-row commit are seeded into the data overlay before
storage-backed proofs begin. Index mutations remain staged in row order. This
lets self-referential relation targets resolve anywhere in the same atomic
batch. It also lets a unique proof recognize that the committed owner of a key
is moved or deleted by another final batch image. The membership is released
only when that final image no longer maps to the same unique key, so duplicate
final values remain violations.

## Diagnostics

R4 established the diagnostic representation. R5 does not add another error
family. Active and activating row-local, unique, and relation failures retain
accepted constraint ID, name, kind, entity, key when available, and field
paths through `ConstraintDiagnostic`.

Corrupt accepted metadata, row bytes, indexes, or reverse indexes remain
typed corruption/internal errors rather than constraint violations.

## Delete semantics

For a self-referential relation, deleting both the source and target in one
atomic batch is valid: delete protection ignores a source row included in the
same batch. A surviving source still blocks target deletion. Candidate
activation barriers remain fail-closed.

## Compatibility and durability

This is an internal pre-1.0 consolidation. It changes no accepted-schema,
commit-marker, row, index, cursor, receipt, or recovery format and adds no
compatibility path.

`CommitPrepareMode` makes the recovery distinction explicit:

- normal writes validate relation targets and maintain active/candidate
  generations;
- replay maintains the recorded active/candidate generations without
  re-running current relation-target admission;
- derived rebuild reconstructs active generations without admitting writes or
  advancing candidate work.
