## Patch 2B Source-Binding Slice

The accepted store-local revision bundle now owns one bounded source-binding
catalog. It maps immutable entity, named-type, enum-variant, field, check,
index, and relation source keys only to existing accepted identities; accepted
snapshots, value catalogs, constraints, indexes, and relations remain the sole
semantic owners. Enum-variant bindings are scoped by their accepted enum type
and close exactly over every variant whenever the enum type itself is bound.
The binding catalog cannot allocate identities or reconstruct structural
meaning.

## Patch 2B Atomic Publication Foundation

Plain accepted-candidate publication now has one preflighted plural owner. It
validates every store-local candidate and activation closure before opening
the commit window, orders stores canonically, persists every journal batch in
one commit marker, appends all batches before exposing any new live root, and
lets recovery complete every store after a partial append. Mixed
already-current and new candidate sets fail closed; a wholly repeated
candidate set is an idempotent no-op. Multi-store publication rejects volatile
stores because they have no durable recovery authority capable of completing
an interrupted database-scoped change. Existing single-store publication
variants that couple one candidate to derived-domain or validation-job effects
remain separate until proposal application reuses the 0.211 activation owner.

This work also corrects the shared durable batch identity model. Journal
sequences are tail-local, so equal next sequences in different stores are now
valid inside one marker, while every additional batch receives a distinct
marker-local ID. The established single-store batch bytes remain unchanged.
Commit-marker, journal, accepted-bundle, row, index, and relation codecs do not
change.

## Patch 2B Durable Receipt Protocol

Schema application now has one public terminal/pending receipt contract and
one bounded current-form durable record. A pending record carries the exact
canonically ordered 0.211 activation identities owned by its opaque job;
terminal records cannot retain activation state. Job identity covers the
database token, submission key, proposal digest, and prior accepted head.

The record store is one database-wide checksummed BTreeMap in a restricted
region after the existing bounded commit-control region. It does not consume
another canister memory ID and cannot overlap the transient marker frame.
Records are capped at 64 KiB, pending jobs at 512 activation identities, and
the store at 64 retained submissions; the smaller value bound avoids
multi-megabyte stable BTree nodes for ordinary receipts. Each commit marker
may carry one exact record compare-and-replace effect. Apply and recovery
accept only the expected prior bytes or the already-applied final bytes,
verify the final record before marker clearance, and fail closed on checksum,
key, state-closure, capacity, or compare drift.

Focused evidence covers canonical record codec/checksum behavior, pending and
terminal state closure, exact replay, compare conflict, reopen, marker
round-trip, and interrupted marker recovery. The public session lookup is
guarded by recovery and requires the exact database identity plus immutable
submission key.

This foundation changes the transient commit-marker payload shape and adds the
first schema-application record format. It does not change the control-slot
envelope, stable allocation identity, accepted schema, row, index, relation,
journal, cursor, or 0.211 validation-job bytes. Superseded in-flight
development markers are not decoded; no compatibility path exists.

Catalog-native proposal lowering and the application caller still must create
these record effects inside the same marker as multi-store publication and
reuse the 0.211 activation runners. Therefore the Patch 2B durable-receipt
checklist item remains open until the proposal ingress is connected end to
end.

entity by immutable relation source key. Lowering removes the accepted
relation, its paired generated constraint, and its source binding together,
then advances the source entity schema version exactly once. A missing or
ambiguous binding, non-generated paired constraint, live activation, candidate
generation, or combined remove-and-add replacement rejects before candidate
publication.

Application preflight proves both physical sides of the no-write transition.
The source store's maintained exact entity cardinality must be zero, and a
relation-owned bounded observer must prove that the removed relation's exact
reverse generation has no surviving key in the accepted target store. The
observer derives physical identity from the accepted source entity, first
local field slot, and relation generation, then scans the target store's
canonical merged view. A non-ready target index store, malformed key,
oversized observation, stale reverse entry, missing target authority, or
ambiguous target path rejects before the durable receipt or accepted candidate
can publish.

Because both authoritative source rows and the target-owned reverse physical
domain are empty, the transition performs no row rewrite, reverse-index
deletion, or replacement staging. It reuses the existing atomic
schema-plus-receipt publication boundary. The accepted-bundle, source-binding,
entity snapshot, row, index, relation, journal, marker, cursor, and
application-receipt codec shapes are unchanged.

Focused evidence covers public application and exact replay, paired constraint
and source-binding retirement, unchanged target authority, nonempty-source
rejection without a receipt, and stale reverse-state rejection without a
receipt. The complete 25-test schema-application group, core no-default
compilation, all-target/all-feature warnings-denied Clippy, schema/model,
layer-authority, and mutation-atomicity guards, formatting, and diff hygiene
pass. The Cargo-based warnings-denied and no-default checks were repeated in
an isolated source copy because the committed workspace manifests are
`0.213.18` while the committed lockfile still records workspace packages as
`0.213.17`; the repository lockfile remains untouched for the human-owned
release workflow. Full repository validation remains human-owned under
`AGENTS.md`.

## Patch 2B Exact-Empty Generated Entity Removal

An exact existing-head proposal may now remove one generated entity by its
immutable entity source key. Entity removal is an intentionally isolated
transition: the proposal may carry no fragment, assignment, or second removal.
Lowering deletes the exact accepted snapshot and its complete entity-scoped
field, constraint, index, and relation source-binding subtree together. Named
type definitions remain accepted because proposal absence still means
unchanged and type removal remains explicit.

Application preflight proves that no retained authority is hidden by the
schema-only transition. Maintained exact cardinality must prove zero rows, the
bounded user-index observer must prove no physical user-index key for the
entity, and every outgoing relation's exact target-owned reverse generation
must be empty. The accepted-after database topology is then checked for any
retained relation that still targets the removed entity. Nonempty or corrupt
row/index/reverse state, an incoming relation, a missing or ambiguous target,
live activation, or candidate generation rejects before a durable receipt or
accepted candidate can publish.

The transition performs no row, forward-index, or reverse-index write and
reuses the existing atomic schema-plus-receipt marker boundary. The affected
store revision advances once. Other entity snapshots and source bindings
remain unchanged. Accepted-bundle, source-binding, entity snapshot, row,
index, relation, journal, marker, cursor, and application-receipt codec shapes
are unchanged.

Focused evidence covers successful removal to an empty accepted entity map,
exact receipt replay, complete source-binding subtree removal, rejection of a
nonempty row domain, corruption classification for stale user-index state,

## Patch 2B Exact-Empty Record-Member Rename

Exact existing-head proposals can now rename generated record members through
their immutable `(CompositeTypeId, FieldSourceKey) -> CompositeFieldId`
binding. The accepted composite catalog remains the sole owner of the editable
member name and preserves the member ID, value contract, type ID, structural
codec, entity field identity, row layout version, field slots, index
generations, relation generations, and all source bindings.

Record member names are part of canonical composite map values, so this is not
a general metadata-only rename. Before publication, application preflight
requires exact zero row cardinality for every entity whose accepted nested-leaf
projection changes. It also proves that the entity's complete physical
user-index domain and every outgoing relation's exact reverse generation are
empty. A nonempty or corrupt logical or derived domain rejects before a
durable receipt or accepted schema publication. Every accepted store-local
copy bound to the same record source must receive the identical redeclaration,
so a partial cross-store proposal also fails closed.

The successful transition changes accepted catalog and display-path metadata
only. It performs no row, index, relation, journal, or layout rewrite and adds
no migration runner, compatibility reader, fallback reconstruction, or
generated-model authority. Rewriting record member names inside existing
persisted values remains intentionally unsupported by the 0.213 design's
no-rewrite boundary.

Focused lowering and journaled-session coverage proves stable member/source
identity, unchanged row layout, canonical nested-leaf relabeling, durable exact
receipt replay, and rejection without publication when a physical row exists.
