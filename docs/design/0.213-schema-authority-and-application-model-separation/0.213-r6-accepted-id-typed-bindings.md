# 0.213 R6 — Accepted-ID Typed Bindings

## Outcome

Generated typed adapters bind immutable authored source identities directly to
the current accepted entity and field identities. Below binding issuance,
typed writes no longer translate field source keys through editable display
names before accepted mutation lowering.

This is an opaque adapter hard cut. It changes neither accepted/persisted schema
formats nor the public structural and SQL name-driven frontends.

## Authority boundary

Binding issuance resolves:

```text
entity source key
  -> accepted entity tag + immutable entity path + store
  -> accepted revision/fingerprint/layout generation

field source key
  -> durable accepted field ID
  -> accepted row slot
  -> current display label
```

The opaque binding retains the source key, accepted ID, and slot. The display
label is retained only for result-column metadata and diagnostics.

Currentness is proved through the immutable entity source path and accepted
identity tuple. A rename therefore makes an older binding stale because the
accepted fingerprint/revision changes, while a newly issued binding resolves
the same source identity to its current label. Reusing an old display name for
a differently sourced entity or field cannot make an old binding current.

## Typed writes

Generated writes produce an opaque bound mutation:

```text
field source key + authored WriteCell
  -> binding-owned field ID + slot
  -> accepted mutation intent patch
  -> ordinary policy/constraint/commit pipeline
```

The session verifies, before accepting each bound field:

- the binding is current for the database incarnation;
- the bound entity tag and immutable path match the selected accepted catalog;
- the slot still contains the bound durable field ID; and
- no duplicate source, field ID, or slot occurs in one patch.

Database-owned fields, omission/default/null/value intent, defaults, managed
timestamps, constraints, relations, indexes, encoding, and commit behavior stay
owned by the shared accepted structural mutation pipeline.

## Typed reads and queries

Typed query routing selects the accepted catalog through the binding's
immutable entity identity rather than its display name. Query expressions and
explicit projections remain frontend syntax and are resolved by the accepted
query compiler.

The engine still returns engine-neutral values plus display labels. At the
typed result boundary, current accepted labels are associated with the
binding's accepted slots once. Generated decoding then selects values by the
bound slot. Labels do not recover an accepted field identity and do not enter
planning, validation, or persistence.

Projection aliases, missing generated fields, duplicated labels, or a stale
binding fail closed at the typed result boundary.

## Named values

Named-type paths, enum-variant names, and record-member names remain in the
binding because `InputValue` and `OutputValue` expose accepted public named
values. These mappings are value-boundary labels backed by immutable
named-type/member source identities. They are not row routing, layout, query,
validation, or persistence authority.

## Recovery and formats

Bindings are ephemeral and are reissued from the current accepted catalog.
They are not persisted or recovered. R6 changes no accepted catalog, row,
index, cursor, commit, journal, or recovery format.

## Focused evidence

R6 must prove:

- typed writes lower source keys directly to accepted field IDs/slots;
- entity and field display renames cannot redirect an old binding;
- old-name reuse by a different source cannot satisfy currentness;
- structurally identical differently sourced fields cannot bind;
- stale bindings fail as typed adapter failures rather than name-lookup
  database errors;
- typed read and write generation still compiles; and
- structural and SQL name-driven APIs remain unchanged.
