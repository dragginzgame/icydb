# 0.213 R7 — Engine-Neutral Query Feature

## Status

Complete. This is the seventh and final current-state remediation patch. It is
a pre-1.0 feature and internal ownership hard cut. It changes no persisted,
cursor, accepted-schema, row, index, journal, commit, or recovery format.

## Problem

The accepted-schema query engine is independent of SQL in authority and
execution, but not in feature and response ownership:

- dynamic and typed reads are enabled by the `sql` feature;
- the structural projection contract is owned by the SQL session module;
- dynamic response construction round-trips through `SqlProjectionPayload`
  and `SqlStatementResult`;
- typed-query-only canisters therefore retain the SQL parser, lowering, DDL,
  mutation, and statement-response surface.

This does not create a second engine, but it obscures the actual dependency
direction and prevents query-only consumers from proving that SQL is optional.

## Final dependency direction

```text
accepted catalog
  -> query feature
       -> expression/query contracts
       -> shared plan cache
       -> planner and executor
       -> structural projection contract/result
       -> dynamic and typed adapters

query feature
  <- SQL frontend
       -> parse/lower SQL
       -> SQL statement/result adaptation
       -> SQL DDL and mutation commands
```

The Cargo feature graph is:

```text
query = engine-neutral reads and query contracts
sql = query + SQL frontend
sql-explain = sql + SQL explain surface
```

There is no legacy alias or fallback feature.

## Ownership contracts

### Query feature

The `query` feature owns:

- dynamic query requests and results;
- the public expression and ordering DSL;
- accepted-schema semantic planning;
- the shared prepared-plan cache and its accepted-head identity;
- scalar projection execution;
- ordinary bounded public-read admission;
- typed query construction and output adaptation.

It does not own SQL parsing, SQL statement dispatch, SQL DDL, SQL mutation
commands, SQL response enums, or SQL rendering.

### Structural projection boundary

One engine-neutral structural projection contract carries canonical output
labels and fixed decimal scales derived from the frozen projection
specification. It is consumed by both dynamic/typed response adaptation and the
SQL statement adapter.

Dynamic execution converts runtime values directly to accepted public output
values. It must not construct or destructure a SQL response DTO.

SQL retains its SQL-specific response envelope and diagnostics attribution, but
it obtains the prepared structural plan and projection contract through the
same query-owned cache boundary as dynamic and typed reads.

### Execution and cache parity

Query-only and SQL reads must share:

- `StructuralQuery`;
- accepted entity authority and schema fingerprints;
- normalized predicate and plan-cache identities;
- logical/access planning;
- executor projection materialization;
- response row and public-output bounds;
- cursor and continuation contracts where exposed.

The feature split must not clone planner, executor, cache, or admission logic.

## Public surface

With `query` enabled, `icydb` exposes:

- `db::query` and the typed `Query` adapter;
- `DynamicQuery` and `DynamicQueryResult`;
- dynamic query session methods;
- query errors and engine-neutral query DSL/result contracts.

The SQL statement APIs and SQL response types remain available only with
`sql`.

This is a hard cut before 1.0. Typed-query-only maintained fixtures enable
`query`, not `sql`; no compatibility feature is retained.

## Failure behavior

- Accepted-schema lookup and stale typed-binding behavior are unchanged.
- Ordinary dynamic/typed reads retain bounded public-read admission.
- Trusted dynamic reads retain the same explicit unbounded-policy
  responsibility as trusted SQL callers.
- Runtime-to-public-value conversion failures remain typed query invariant
  failures and are not flattened through SQL response matching.

## Validation

Focused evidence must include:

- core and facade no-default checks;
- core and facade `query`-only checks;
- core and facade `sql` and `sql-explain` checks;
- query-only typed-adapter and generated typed-query fixtures;
- dynamic and typed execution without the SQL feature;
- SQL projection and response regressions with SQL enabled;
- warnings-denied Clippy for query-only and SQL feature combinations;
- formatting, diff hygiene, dependency/feature inspection, and searches proving
  dynamic/typed modules no longer import SQL response or projection DTOs.

Full repository tests, performance suites, and Wasm measurements remain
user-owned release validation.

## Completion evidence

- `icydb-core` and `icydb` define `query`; `sql` depends on it and
  `sql-explain` continues to depend on `sql`.
- Dynamic and typed reads compile and execute with `query` and without `sql`.
- The query session owns `StructuralProjectionContract` and
  `StructuralProjectionPayload`; SQL adapts that payload only when constructing
  `SqlStatementResult`.
- The duplicate `SqlProjectionContract`, `SqlProjectionPayload`, and
  SQL-owned public dynamic-projection bridge are deleted.
- The maintained one- and ten-entity typed-query canisters enable only
  `query`, and a focused PocketIC regression executes both typed endpoints
  through exact accepted primary-key access.
- Focused no-default, query, SQL, SQL-explain, compile-pass, runtime,
  generated-canister, and warnings-denied Clippy evidence passes.
- Current raw non-gzipped `wasm-release` artifacts are 3,543,033 bytes for
  `one_entity_typed_query` and 3,545,250 bytes for
  `ten_entity_typed_query`. No comparable R6 artifact exists, so no size delta
  is claimed. Runtime instruction performance was not measured.
