# IcyDB 0.213 Closeout Audit

Status: closeout corrections in progress  
Audit date: 2026-07-28

## 1. Executive Verdict

**Verdict: materially incomplete.**

The 0.213 line established the intended accepted-schema architecture and
removed most of the former generated persistence/runtime machinery. No P0 row
corruption or loss-of-commit-atomicity defect was found in the audited
snapshot. Closeout C4 corrects the receipt-store exhaustion contradiction. The
repository still retains one reachable P1 contradiction:

- application validation and normalization still had competing public
  implementations in `icydb-core` and `icydb-model`.

Closeout C1 corrects the generated identity boundary. C2 corrects
single-live-store application and replaces generated-proposal reconstruction
with a marker-owned durable checkpoint of the exact accepted candidate. C3
corrects accepted removal of closed recursive named-type components. C4 gives
bounded receipts deterministic terminal retention and pending generated
checks an acknowledgement-bound atomic abort. The remaining C5-C7 findings
prevent a complete/coherent verdict.

## 2. Reconstructed Final Architecture

The intended and predominantly implemented direction is:

```text
icydb-model authored declarations
        |
        | sealed host graph and exact database closure
        v
icydb-schema bounded proposal
        |
        | database-scoped composition and catalog-native reconciliation
        v
accepted candidate + immutable source bindings
        |
        | one marker-owned durable publication
        v
accepted catalog / row layout / value catalog
        |
        +--> structural and typed reads/writes
        +--> SQL planning and writes
        +--> index and relation maintenance
        +--> integrity, activation, replay, and recovery
```

`icydb-schema` owns portable proposal contracts and canonical public scalar
values. `icydb-model` owns source authoring, proposal construction, and
optional source-bound typed adapters. `icydb-core` owns proposal admission,
accepted catalogs, runtime enforcement, physical rows, durable application,
activation, and recovery. `icydb` is the public runtime facade.

This direction is now absolute for application publication, recovery, and
generated-check terminalization: live-only schema allocations restore from
exact durable accepted-candidate bytes, never from an authored/generated
proposal, while an abort mutates accepted activation/source-binding authority
and the canonical validation job under one marker. The application behavior
stack remains duplicated, so the final architecture is not yet complete.

## 6. Findings

### P0

No P0 finding was established. The marker path binds candidate publications,
live accepted checkpoints, and application-record replacement in one commit,
and recovery verifies and replays the same marker payload.

### P1-1: Application receipts reject a valid single volatile-store apply — corrected C2

- **Evidence:** `publish_accepted_schema_candidates_with_optional_application_record`
  in `crates/icydb-core/src/db/commit/schema_publication.rs` has a direct
  volatile single-store publication branch, but returns
  `store_unsupported()` whenever an application record accompanies it.
- **Violated invariant:** the canonical application protocol must work for
  every registered database configuration that can otherwise publish an
  accepted candidate.
- **Consequence:** a schema proposal for a database containing only one heap
  store can lower successfully and still fail solely because application
  receipts were added.
- **Correction:** C2 routes this case through the same marker protocol as
  mixed-store application and checkpoints the exact accepted candidate before
  exposing the live catalog or receipt. Focused completion and interrupted
  revision-2 recovery tests cover the corrected case.

### P1-2: Mutually recursive named types cannot be removed — corrected C3

- **Evidence:** `lower_existing_store_candidate` rejects more than one type
  removal, while `with_removed_type` validates the remaining catalog after
  each individual deletion.
- **Violated invariant:** explicit absence should remove an unreferenced
  accepted named-type component, including a valid admitted cycle, by stable
  IDs.
- **Consequence:** a two-node accepted SCC introduced by 0.213.34 can be
  created but never removed even when no entity or external named type
  references it.
- **Correction:** C3 resolves every source removal to each store-local
  accepted ID, subtracts the complete bounded enum/composite set, then
  validates the retained catalogs and entity fields once. Internal cycle
  edges are therefore removed atomically, while partial removal and external
  references fail closed.

### P1-3: Application history permanently exhausts after 64 submissions — corrected C4

- **Evidence:** `MAX_SCHEMA_APPLICATION_RECORDS` is 64 in
  `application_store.rs`; before C4 capacity rejected before mutation and no
  retention, compaction, or terminal-record deletion path existed.
- **Violated invariant:** bounded durable replay metadata must not turn normal
  long-lived schema evolution into permanent unavailability.
- **Consequence:** the 65th distinct submission key fails regardless of record
  size or whether all prior jobs are terminal.
- **Correction:** C4 preserves all pending records and, only when admitting a
  new key at capacity, deterministically retires the lowest stable-key
  terminal record. An all-pending store fails closed. Exact replay remains
  available for retained terminal records; retirement explicitly ends that
  bounded replay window rather than blocking all future applications.

### P1-4: Application behavior has two public owners

- **Evidence:** `crates/icydb-core/src/visitor/**` and
  `crates/icydb-model/src/visitor/**` contain substantially parallel visitor,
  validation, and normalization contracts; `icydb-core` also exposes
  behavior-facing model traits while the final architecture assigns
  application behavior to `icydb-model`.
- **Violated invariant:** accepted runtime owns durable enforcement and
  `icydb-model` owns explicit application behavior; neither should be a
  fallback for the other.
- **Consequence:** types and semantics can drift, including scalar coverage,
  diagnostics, and traversal behavior, while both stacks continue compiling.
- **Action:** open for C5. Prove consumers, migrate the maintained owner, and
  delete the obsolete stack and facade exports rather than forwarding them.

### P1-5: Generated schema/SQL surfaces retained mutable identity authority

- **Evidence before C1:** generated schema called
  `try_describe_entity_by_name` with a Rust path, and generated SQL emitted one
  `identifiers_tail_match` arm per authored Rust path and display name.
- **Violated invariant:** generated code may bind through immutable source
  identities but accepted catalog names are the runtime SQL/introspection
  authority.
- **Consequence:** an accepted rename could make the schema endpoint fail and
  make SQL reject the new accepted name before catalog resolution.
- **Correction:** C1 adds source-key introspection and delegates non-empty SQL
  entity dispatch to the accepted-catalog runtime. Generated fixture-reset
  statements still use the current authored names and are inventoried for C7
  because fixtures are explicit destructive application behavior, not query
  routing.

### P2-1: Generated proposal remains reachable in live-only recovery — corrected C2

- **Evidence:** public `rebuild_generated_live_schema` accepts a
  `SchemaProposal`, discovers retained durable bindings, and publishes absent
  `LiveRebuiltMetadata` candidates outside ordinary `apply_schema`.
- **Risk:** the old lane reconstructed every live store as revision 1 and
  retained only cross-store entity tags. Evolved field/type/object identities
  and the committed accepted fingerprint therefore had no durable recovery
  owner.
- **Correction:** C2 deletes the generated rebuild entry point and special
  lowering/retained-ID machinery. Marker publication now compare-and-replaces
  a bounded, checksummed checkpoint containing the exact accepted bundle/root;
  recovery restores that checkpoint before ordinary marker replay and verifies
  the same bytes. The final version-1 database identity rejects pre-checkpoint
  development stores instead of adding a legacy reconstruction fallback or a
  version ladder.

### P2-2: SQL-only library-test feature ownership is inconsistent

- **Evidence:** helpers compiled under `cfg(any(test, feature =
  "sql-explain"))` consume `LoweredSqlQuery`, while its module ownership is
  SQL-feature dependent. The SQL-only lib-test combination does not express
  one coherent gate.
- **Risk:** the supported feature matrix and the test feature matrix diverge.
- **Action:** C7 aligns ownership and adds exact SQL-only/no-default evidence.

### P2-3: Model-era metadata survives beyond a justified boundary

- **Evidence:** public `FieldTypeMeta`, core `FieldModel`/
  `CompositeFieldModel`, and model-derived `SchemaInfo` constructors survive
  alongside accepted-native runtime contracts.
- **Risk:** these DTOs can rebuild a second view of field/type/layout meaning
  and make retired generated-model machinery appear supported.
- **Action:** C6 classifies every call site, deletes metadata used only by
  obsolete tests/convenience, and retains only a separately proven proposal or
  source-adapter responsibility.

### P2-4: Application state exposes unreachable transitions — corrected C4

- **Evidence before C4:** `SchemaChangeOutcome::Failed` was decodable and
  replayable, but production application flow had no failure-terminalization
  operation; `SchemaChangeActivationKind` included non-check variants while
  continuation rejected every activation except `Check`.
- **Risk:** persisted variants imply lifecycle guarantees the application
  engine cannot produce or complete.
- **Correction:** C4 hard-cuts `Failed`, its failure DTO, and the activation
  kind enum. The application record now carries only the store/entity/check
  identity actually supported by the canonical runner, with `Applied` and
  `Aborted` as the only terminal pending transitions. New version-1 application
  and database magic identities reject obsolete development bytes.

### P2-5: Pending generated-check application has no explicit abort/expiry — corrected C4

- **Evidence before C4:** continuation could advance/acknowledge the one check
  activation, but the public application protocol had no abort or expiry path
  tied to the receipt/job owner.
- **Risk:** a pending job can retain application state indefinitely and
  interact poorly with later removal/reconciliation.
- **Correction:** C4 adds an explicit owner-invoked abort. A validating job
  cannot be aborted past a retained finding page without its exact sequence
  acknowledgement. One marker deletes the canonical validation job, removes
  the accepted pending activation and immutable source binding, advances the
  accepted head, and replaces the application record with replayable
  `Aborted`. There is deliberately no clock-based expiry: pending evidence is
  never evicted implicitly.

### P2-6: Diagnostics frequently flatten distinct closeout failures

- **Evidence:** application lowering contains broad
  `store_unsupported()` translations across identity, graph, removal, bound,
  and physical-proof failures; repository tests still have areas that assert
  broad classes rather than exact typed domains.
- **Risk:** source mismatch, unsupported graph placement, stale target, and
  corrupt storage become difficult to distinguish at public boundaries.
- **Action:** C4/C7 introduce typed distinctions only where the final
  contract is already clear; they must not add message matching.

### P2-7: Production physical/schema paths retain panic-style invariants

- **Evidence:** production `unreachable!` remains in accepted structural-field
  conversion, persisted-row reading, schema type projection, physical access,
  and SQL lowering.
- **Risk:** corrupt persisted state or a future exhaustive-match change can
  trap rather than produce the required typed corruption/internal error.
- **Action:** C7 traces reachability and replaces reachable cases with fallible
  invariant helpers. Test-only unreachable matches are not in scope.

### P3-1: Sealed graph reports construction-order “first error”

- **Evidence:** `Schema::register` retains the first duplicate/late error and
  `seal` returns it.
- **Risk:** invalid graphs with multiple failures can report a constructor
  order-dependent diagnostic even though successful graph bytes are
  deterministic.
- **Action:** C7 either canonicalizes retained graph diagnostics or documents
  why deterministic failure class, rather than diagnostic selection, is the
  contract.

### P3-2: Active roadmap documentation uses retired terminology

- **Evidence:** `docs/1.0-FEATURES.md` still calls application behavior
  “sanitizers”; later active design prose also uses the retired word when
  describing current snapshots.
- **Risk:** current-facing docs teach an API spelling removed by 0.213.
- **Action:** C7 updates active docs while leaving historical changelogs and
  superseded design evidence intact.

## 8. Durability and Recovery Analysis

The current durable schema application sequence is:

1. issue a target from recovered registry authority and the exact accepted
   database head;
2. digest and check the proposal/submission identity;
3. load current accepted bundles and build catalog-native candidates;
4. preflight physical emptiness/check activation requirements;
5. construct one receipt/application record;
6. preflight every candidate, live accepted checkpoint, and
   application-record compare value;
7. acquire a commit marker containing store journal batches and the exact
   application-record operation;
8. append journal batches, checkpoint live-store accepted candidates, apply
   accepted candidates, and apply the record;
9. finish/remove the marker;
10. return the durable receipt.

Observed interruption behavior:

| Interruption point | Observable/recovery behavior | Audit status |
| --- | --- | --- |
| Before marker publication | no candidate or receipt is visible | coherent |
| Marker durable, before journals/checkpoints | recovery restores the previous live checkpoint, applies marker checkpoints, validates the exact marker payload, and completes it | coherent for journaled and live-only stores |
| Some journals appended | marker identity and batch IDs drive idempotent completion | coherent |
| Candidates applied, receipt absent | recovery applies the same record operation | coherent |
| Receipt applied, marker present | compare-and-replace verification makes replay idempotent | coherent |
| Marker finished | accepted heads and receipt agree | coherent |
| One volatile store plus application record | one marker owns checkpoint, accepted candidate, and receipt | corrected C2 |
| Completed live projection missing after upgrade | recovery republishes the exact durable accepted checkpoint before runtime access | corrected C2; no authored/generated fallback |
| Interrupted evolved live revision after upgrade | recovery restores the prior or already-advanced checkpoint and replays the exact marker candidate idempotently | corrected C2 |
| Pending generated check continuation | canonical check runner advances one bounded page and binds acknowledgement receipt | coherent |
| Abort before validation starts | marker removes the accepted activation/source binding and terminalizes the application record | coherent; no validation job may exist |
| Abort with a validation job | exact retained-page acknowledgement is checked before the marker deletes the job, publishes the catalog-native candidate, and records `Aborted` | coherent; wrong/missing acknowledgement fails before mutation |
| Abort marker interruption | recovery replays candidate publication, validation-job deletion, and application-record replacement from the same marker | coherent; focused journaled recovery evidence |
| Terminal receipt capacity | the lowest stable-key terminal record is retired only while admitting a new record at the 64-record limit | coherent; pending records are never selected |
| All-pending capacity | admission conflicts before marker publication | coherent; no pending evidence is discarded |

Exact proposal replay returns the stored receipt only when database identity,
submission key, proposal digest, and prior expected head all match. A different
proposal under the same idempotency key conflicts. The marker carries the
application record, so an unrelated operation cannot overwrite its key without
failing preflight. Terminal replay is exact while the receipt remains in the
bounded retention window; once retired, an old expected head is stale and
cannot recreate or overwrite current accepted authority.

## 10. Named-Type and Boundedness Analysis

0.213.34 correctly distinguishes a cyclic schema graph from an infinite value.
Named references are resolved to stable accepted IDs; catalogs can contain
strongly connected components; runtime values remain finite and value
admission/encoding consumes explicit depth and byte budgets. The Toko-shaped
`Values -> FieldValue -> Value -> Values` graph and qualified payload enums
round-trip through proposal lowering, accepted bundle encoding, recovery, and
finite value encoding.

The audit found no recursive catalog inlining requirement in the accepted
representation. Resolution/publication traversals use identity-based state,
and persisted codecs bound collection counts and input bytes before
construction. C3 closes the former lifecycle contradiction by resolving the
explicit removal set across every store-local accepted copy and subtracting
all selected IDs before validation. This removes any fully selected closed
component without requiring recursive SCC expansion. Retained catalog
validation rejects references from a non-selected named type, and accepted
bundle validation rejects entity-field references. Source bindings and their
variant/member children are retired only in the valid candidate; row layouts
do not change.

Bounds inventoried for the closeout include stores, fragments, entities,
fields, named definitions, graph edges, variants, members, tuple arity,
nesting depth, proposal/accepted bytes, source bindings, receipt bytes/count,
activation findings/pages, SQL response bytes/rows, and physical proof pages.
C4 keeps the receipt store at 64 records and makes that bound a retention
window: only terminal records can be recycled and the stable application key
defines the deterministic candidate. Decoding remains bounded to 64 KiB per
record and 64 records before any retained record is inspected.

## 11. Corrections Made

Closeout patch C1 changes:

- `icydb-core` resolves an accepted entity context from an exact
  `EntitySourceKey` and then uses the same accepted schema description path as
  display-name lookup;
- the `icydb` facade exposes that source-bound introspection operation;
- generated schema endpoints embed immutable entity source keys instead of
  Rust paths passed to a display-name API;
- generated SQL surfaces retain only the fact that the model graph is
  non-empty and delegate every actual entity name to accepted SQL authority;
- obsolete generated query/DDL/update match-arm builders and the hidden
  `identifiers_tail_match` re-export are removed;
- model token tests cover immutable schema binding, absence of generated
  identity allowlists, and the empty-graph fail-closed case.

No accepted schema, row, receipt, marker, cursor, or public value wire format
changes in C1.

Closeout patch C2 changes:

- all live-only accepted-schema publications use the marker path and
  compare-and-replace an exact accepted-candidate checkpoint before the live
  projection or optional receipt is exposed;
- recovery restores completed checkpoints, handles a checkpoint that advanced
  before an interrupted live projection, replays the same marker candidate,
  and verifies accepted/checkpoint bytes together;
- one live-only store plus an application receipt is admitted through the same
  protocol as mixed-store publication;
- generated proposal-based live reconstruction, its special initial-lowering
