# IcyDB 0.246 SQL Ingress Owner Audit

Status: COMPLETE — MEASURED NO-BUILD

Last updated: 2026-08-26

Exact released predecessor: tag `v0.245.0`, revision

## Objective

Explain the final-Wasm premium retained by a minimum SQL query actor, map that
premium to its real semantic and execution owners, and decide whether one broad
flow contraction can reduce it without adding query-shape fast paths, runtime
modes, parallel authorities or performance regressions.

Patch 1 is an audit only. It changes no production runtime, generated surface,
test fixture, package version, Candid, export or stable format. An audit finding
does not authorize implementation.

## Demonstrated Need

The clean 0.245 final artifacts measure:

| Actor | Final raw Wasm |
| --- | ---: |
| `one_entity_typed_query` | 2,010,198 |
| `one_entity_dynamic_query` | 2,864,615 |
| `one_entity_sql_query` | 3,179,832 |
| SQL minus typed (directional) | 1,169,634 |
| SQL minus dynamic (directional) | 315,217 |

The predecessor `WASM-3.0` attribution assigned 1,125,250 retained bytes to the
SQL query export's execution closure. That evidence predates the 0.245 startup
contraction and must be refreshed before selecting an owner.

The actor subtraction is directional, not a proof that all 1,169,634 bytes are
removable SQL overhead. The actors expose different endpoints and instantiate
different query contracts. Only same-toolchain reachability, dominator and
source-consumer evidence may assign bytes to a candidate owner.

## Audit Questions

1. Which final and symbol-bearing functions are reachable only from SQL
   ingress rather than the shared database/runtime floor?
2. How much of the closure belongs to parsing, semantic lowering, command
   preparation, route planning, physical execution, diagnostics and result
   projection?
3. Where do typed and SQL requests first converge on a common accepted-schema
   and execution contract?
4. Does SQL retain two representations or decision owners after one has served
   its purpose?
5. Are large helpers required by the supported SQL surface, or are they pulled
   in by an avoidable adapter, generic instantiation or duplicated flow?
6. Can a candidate delete or narrow an existing path while keeping runtime
   instruction work neutral?

## Authority And Convergence Contract

The maintained shape is:

```text
SQL text
  -> SQL parser
  -> accepted-schema semantic lowering
  -> planner-owned immutable execution contract
  -> shared physical executor
  -> canonical result projection
```

The audit must distinguish frontend syntax ownership from accepted-schema
authority. Parser and lowering may reject or resolve authored SQL, but only the
pinned accepted-schema request/session snapshot may authorize fields, indexes
and runtime behavior. Planner eligibility must flow in one immutable artifact;
the executor must not reparse or independently reclassify SQL.

Typed and SQL frontends need not share source representations. Convergence is
valuable only where semantics, failure behavior and physical work are already
equivalent. Type erasure, boxed dispatch, allocation or runtime interpretation
is not an acceptable size-only convergence strategy without paired instruction
evidence.

### Authority and convergence finding

The current flow already has the intended singular owners:

```text
SQL text
  -> parser-owned current AST
  -> accepted-catalogue semantic compilation
  -> CompiledSqlCommand
  -> SqlCompiledCommandExecutionContext bound to accepted authority
  -> shared structural planner/executor
  -> SQL result projection
```

`CompiledSqlCommand` is the only cached prepared representation. The execution
context binds it to the pinned accepted catalogue and authority before the
executor runs. No parser, cache or generated model can establish runtime schema
authority, and no parallel execution authority was found.

The retained executor closure is broad because SQL supports more than the
point lookup used by the audit actor: ordered and filtered projection, global
and grouped aggregates, explain, describe and show/introspection all enter
through the same query surface. Splitting those capabilities into a smaller
runtime mode would add a behavior axis and would not be a flow contraction.

### Repeated-parse finding

One broad DRY and instruction defect was found. On a compiled-command cache
miss, trusted query ingress first calls `sql_statement_entity_name`, which
fully parses the text to select the accepted catalogue. The compile cache then
parses the same text again to obtain the AST. A cache hit still performs the
first routing parse. Diagnostic facade methods can add another parse before
entering the core attribution seam.

The existing compile attribution begins after the routing parse. Consequently
its reported compile and total instruction values omit real SQL frontend work.
A focused predecessor audit passed and measured 21,936–42,079 instructions in
the separately counted cache-miss parse for representative simple and grouped
queries. The uncounted routing parse uses the same complete parser, but its
exact instruction cost was not separately instrumented; treating that range as
its cost is an inference, not a measurement.

This finding does not clear the 32 KiB final-Wasm gate. The parser itself must
remain, its complete named retained subtree is only 37,345 bytes, and parse-once
would remove orchestration/control duplication rather than that parser
implementation. The visible routing helper is far below the gate. A prototype
solely to rescue a footprint target would therefore be disproportionate.

Parse-once remains a valid future performance and measurement-correctness
candidate if separately authorized. Its acceptable shape is to carry one
already parsed statement from ingress into compilation while keeping catalogue
selection, compiled-command caching and accepted authority singular. It must
not introduce a second AST cache, execution route or runtime mode.

## Verdict

`NO-BUILD — SQL PREMIUM IS CURRENTLY JUSTIFIED`

No broad removable owner conservatively clears 32 KiB final raw Wasm. The
1.17 MiB typed comparison mostly measures the general planner/executor surface
against a planner-free direct lookup. The closer, still-unmatched dynamic
comparison narrows the directional SQL delta to 315,217 bytes, which is
explained by the required parser/lowering frontend, SQL-only result semantics
and the broader supported query surface. Production implementation is not
authorized and the one-patch 0.246 line is closed.

## No-Build And Complexity Gate

A production candidate is viable only if Patch 1 proves all of the following:

1. one current owner or duplicated flow is identified from symbol-bearing and
   source-consumer evidence;
2. at least 32 KiB of final raw SQL Wasm is conservatively removable;
3. the change serves a broad SQL stage or shared physical contract rather than
   one spelling, aggregate, scalar type or query shape;
4. no new execution route, cache, persisted state, mutable owner, invalidation
   edge, configuration, compatibility path or widely consumed enum variant is
   required;
5. accepted-schema authority, planner authority, typed failures, Candid and
   stable behavior remain unchanged;
6. representative cold and warm SQL instruction work can be held within 1% of
   the predecessor unless the candidate is itself a measured performance
   improvement; and
7. the source shape becomes simpler or demonstrably neutral after production,
   test and evidence lines are counted.

If the removable phase is smaller, ambiguous, coupled to supported semantics,
or requires an additional behavior axis, the correct verdict is no-build.

## Rejected Shortcuts

- Treating the complete actor-size subtraction as removable SQL overhead.
- Removing supported SQL syntax merely because typed APIs can express it.
- Adding another exact-query or scalar-specific execution branch.
- Moving parser or planner decisions into the executor to reduce source files.
- Sharing unlike generic types through heap allocation or dynamic dispatch
  without instruction evidence.
- Using gzip savings to rescue a raw-Wasm miss.
