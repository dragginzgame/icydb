## Patch 1 Evidence — Accepted Runtime Root

- One `AcceptedSchemaRuntimeRoot` now captures every registered store root and
  compiles all accepted entity inspection plans, `SchemaInfo` tables, row
  layouts, fingerprints, and executor authority before publishing one `Rc`
  handle. A context retains that complete root revision.
- Runtime-root identity binds the durable database incarnation plus the
  canonical ordered set of present and absent store roots. Structural plan and
  SQL compile cache keys also bind that complete identity, so unchanged entity
  fingerprints cannot reuse a plan across a different accepted root.
- Warm lookup revalidates compact persisted store-root records. It does not
  encode or hash accepted entity snapshots. SQL DDL invalidates the whole root,
  while ordinary publication/recovery drift is detected by root revalidation.
- The former per-entity query cache, per-context lazy `SchemaInfo`, repeated row
  layout construction, and projection-time accepted snapshot fingerprinting
  are removed. Accepted schema snapshots remain the sole runtime authority.
- Counter-backed native coverage executes 1,000 point queries after warm-up
  and observes zero accepted snapshot fingerprint builds, runtime-root identity
  hashes, entity-runtime compilations, or root publications. Separate tests
  prove atomic replacement, retained old-root contexts, canonical store-root
  identity, and mixed-root plan-cache rejection.

## Patch 2 Evidence — Native Bounded Key Batches

- `DbSession::get` and `DbSession::get_many` accept entity-bound `Id<E>` values
  and execute their primary-key reads directly against the accepted store.
  They do not construct a `DynamicQuery`, compile a plan, or populate the
  general plan cache.
- Generated scalar and composite entities implement the existing `EntityKey`
  contract. `get_many` returns exactly one `Option<Row>` per input key in
  request order. Missing positions remain `None`; duplicate positions remain
  duplicated in the result while sharing one stored-row fetch and decode.
- One batch admits at most 1,024 positions, 256 KiB of canonical stored-key
  bytes before deduplication, 4 MiB of raw rows across distinct keys, and
  4 MiB of logical projected result bytes. Count and input bytes charge the

  bytes charge every original position, including duplicates.

  row contract and schema tables, resolve one store handle, and validate each
  found row's persisted primary key before projection. Typed-binding issuance

  and result-byte exhaustion. The CLI renders each boundary explicitly rather
  than relying on a wildcard. Stale bindings fail closed without accessing a
  store. No persisted schema, row, index, journal, or cursor format changed.

  ordering, missing and duplicate positions, one physical read per distinct

  families, an explicit typed scope and lane, one literal-free normalized-shape

## Patch 5 Evidence — Physical-Route Accounting

- Prepared scalar, grouped, scalar-aggregate, direct-count, SQL, dynamic,
  public, and trusted read routes now execute under one finite per-execution
  hard budget. A synchronous nested prepared route inherits the active counter
  set instead of installing fresh counters. Patch 6 still owns the non-resettable
  request root across separate calls, sessions, retries, and `.await`.
- Physical key/index visits, row fetches, stored bytes, decoded/materialized
  bytes, predicate/projection and nested-value work, sort entries/comparisons
  and temporary storage, grouped/distinct entries and state, cursor work,
  diagnostics, and logical result rows/bytes are charged at maintained owners.
  Grouped sorts and top-k heaps precharge before their expensive operation.
- Primary scans account for the current duplicate backend read instead of
  pretending it is free. Covering routes avoid row-fetch charges when they do
  not fetch a row; hybrid/fallback routes charge the payload they actually
  obtain. Patch 10 subsequently removed the redundant primary-enumeration
  payload read while preserving those physical charges at their real owner.
- On Wasm, maintained loops open an instruction watermark after 64 charge
  seams or one charge of at least 1 MiB, periodically sample it, and close it
  before returning. Small bounded executions rely on their work-unit ceilings
  and reserved headroom rather than paying a performance-counter call on every
  query. The production budget profile is immutable and borrowed, so its 21
  limits are not copied per execution.
- Optional diagnostic recording is fail-soft once its finite allowance is
  exhausted. It cannot select a different plan or turn a successful query into
  an error, while its admitted work is still charged.
- The guarantee remains limited to maintained charged database work. Planning
  performed before the current per-execution scope, arbitrary application
  work, and final application/Candid encoding are not claimed as endpoint-wide
  trap protection. Patch 6 moves scope ownership to request entry and owns
  aggregate planning/request accounting.
- Focused injected-budget coverage proves fallback, covering, residual,
  grouped state, actual SQL grouped sorting, cursor, result, and exact-key
  routes return E273 for the corresponding zero allowance. Existing successful
  heap/journal exact-key and scalar/grouped results remain unchanged.

## Patch 6 Evidence — Root Request Scopes

  Generated endpoints install it automatically; manual endpoints use the thin
  `#[icydb::request_execution]` boundary or the corresponding sync/async
  helper. Nested helpers keep the zero-argument `db!()` API, and no database

  exposing it ambiently only during each poll.

## Patch 7 Evidence — Scalar Page Coordinator And Work Envelopes

- One internal scalar-page coordinator now separates successful bounded
  progress from hard execution failure. Its immutable `PageWorkEnvelope`
  reuses the 21-resource hard-budget vocabulary, admits only the 17 physical
  page resources, and keeps every page ceiling strictly below the enclosing
  read budget.
- A successful page carries rows, an exact work receipt, and either no
  continuation after proven exhaustion or progress containing the last
  emitted logical boundary, last fully consumed physical anchor, optional
  unconsumed lookahead match, rows skipped for the initial offset, rows emitted
  against the total limit, and the immutable envelope/window identity.
- Residual-only progress can therefore return an empty page with a
  continuation. An exact-full page continues bounded lookahead through a
  nonmatching tail; a discovered next match remains unconsumed and is re-read
  on resume, so no cursor can anchor beyond an unreturned row.
- Page-envelope exhaustion returns completed rows plus progress. The enclosing
  hard budget still returns E273 with no partial page. A single inspection or
  emission unit larger than an empty envelope returns the new terminal E274
  `PageUnitTooLarge` with resource, limit, and attempted work, preventing an
  unchanged-continuation loop.
- Initial offset, total query limit, and page-envelope identity are bound as
  one resume contract. A changed value is rejected before traversal. Offset is
  consumed once and the total limit is never reinterpreted as a per-page
  allowance.
- Patch 7 deliberately does not expose scalar page DTOs or cursor bytes. The
  current rows-only surfaces are not truncated or routed through a continuation
  they cannot return; Patch 8 owns the authenticated live-page hard cut and
  production route integration, while Patch 9 owns revision-strict exhaustive
  pages.
- Focused coverage passes for empty progress pages, exact-full nonmatching
  tails, lookahead replay, page-versus-hard exhaustion, terminal oversized
  units, offset/limit completion, contract mismatch, default envelope
  headroom, diagnostic registry round trips, CLI rendering, and warning-denied
  all-target/all-feature core lint. No production query shape, Candid response,
  cursor, or persisted format changes in this internal-only landing.

The coordinator is not reachable from a current production query surface, so
Patch 7 does not claim an instruction improvement before Patch 8 integrates

## Patch 9 Evidence — Read-Set Proofs, Exhaustive Pages, And Atomic Job Advance

- `ReadSetRevisionProof` is one canonical bounded source authority containing
  the database incarnation, accepted runtime-root revision/fingerprint, and a
  sorted distinct list of participating physical-store identities with data
  and access-state revisions. It admits at most 64 stores and 8 KiB of
  canonical bytes; zero, duplicate, unordered, oversized, or unknown source
  authority fails with a typed revision error.
- Journaled stores reuse their existing row-mutation revision and now retain a
  separate nonzero version-1 access-state control entry. Actual index
  `Building`/`Ready` transitions advance that authority; unchanged publication
  does not. Heap stores use the same monotonic concept in memory and remain
  eligible for one-call exhaustive reads but not durable cross-call jobs.
- Typed and dynamic `execute_exhaustive_page` return rows, work,
  continuation, and the complete proof. The proof is compared before and
  after each page and its canonical bytes are bound into the authenticated
  scalar cursor signature. Resume without the proof, reuse after row/access

  a store absent from the proof does not invalidate it.

  identity, and one replayable receipt in a distinct `ICYRJOB1` record family
