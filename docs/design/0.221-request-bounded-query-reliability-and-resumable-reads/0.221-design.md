# 0.221 Request-Bounded Query Reliability And Resumable Reads

Status: proposal only; 0.221 is not started

Design cut: 2026-08-05

Implementation order: only after a ready/complete 0.220 closeout and a later
explicit user direction to start 0.221

## Decision Summary

0.221 makes point-lookup-heavy and exhaustive-read workloads physically
bounded, cheap to repeat, explicit about incompleteness, and diagnosable before
an Internet Computer message reaches its instruction trap limit.

The motivating incident is Toko's `set_live_readiness` query. For a batch of
`N` candidate tokens, its batch context performs useful preload work, but its
per-token loop bypasses that context and repeats approximately six IcyDB
queries plus two large snapshot decodes per token. IcyDB amplifies that
application defect by rebuilding accepted-schema state, compiling
literal-specific plans, permitting scope-less trusted execution, and exposing
rows-only scalar results that cannot prove exhaustion.

The approximate incident cost is:

~~~text
queries ~= batch_queries + 6N
large_snapshot_decodes ~= distinct_batch_snapshots + 2N
~~~

At `N = 100`, the observed workload is approximately 690 dynamic queries and
200 repeated decodes of mostly identical 40-300 KB snapshots. At the advertised
`N = 1,000` endpoint limit, the per-token loop alone permits approximately
6,000 unnecessary queries. The endpoint's 10,000-row scan caps introduce a
separate correctness risk: page fullness is being treated as exhaustion even
though a larger dataset may remain.

This is a real production reliability problem, but it is not primarily a
0.219 regression and it has two owners:

- Toko must remove the N+1 reads, add the useful compound index, define safe
  endpoint composition, and persist resumable validation progress; and
- IcyDB must remove avoidable per-query fixed work, provide direct bounded key
  reads, enforce physical and request-wide budgets, make scalar incompleteness
  structural, avoid unnecessary payload work, and expose bounded request
  diagnostics.

Eleven ordered landing patches cover the IcyDB line. This is above the normal
6-8-patch planning target because request budgets and resumable scalar reads
each contain three independently reviewable authority boundaries; combining
them would make the safety contracts harder to validate. This document does
not start any patch, change the active 0.220 tracker, or authorize
implementation.

## Non-Negotiable Invariants

1. Accepted schema snapshots remain runtime authority. Generated models never
   reconstruct runtime schema state or supply a fallback.
2. One immutable `AcceptedSchemaRuntimeRoot` owns every entity runtime for one
   accepted root revision. Publication atomically replaces that root handle;
   independently published entity runtimes may not expose mixed revisions.
3. Runtime-cache identity includes the durable database incarnation and the
   accepted root revision. An entity's reusable numeric schema version is
   never sufficient identity by itself.
4. A warmed accepted schema performs no snapshot serialization or
   cryptographic hashing during ordinary query execution.
5. Exact typed primary-key reads do not require the general dynamic-query
   planner.
6. Parameterized plan reuse never removes literals from an existing cache key
   while leaving literal values embedded in the cached plan. Plans use typed
   parameter slots and execution-time binding.
7. Every execution lane has finite physical limits. `Trusted` bypasses public
   admission policy, not physical resource accounting.
8. One non-resettable root request scope is created at request/session entry.
   Every child session, nested operation, failure, rollback, and retry shares
   and charges its counters. Creating an ordinary new session cannot mint a
   fresh aggregate allowance.
9. A `PageWorkEnvelope` governs successful resumable progress independently
   from the absolute `HardExecutionBudget`. Page-envelope exhaustion returns a
   page plus continuation; hard-budget exhaustion returns a typed error and no
   partial page.
10. Every bounded scalar page structurally returns rows and an optional
    continuation. A non-null continuation means traversal is not yet proven
    exhausted; it does not promise that another matching row exists.
11. Page fullness is never exhaustion. A null continuation is emitted only
    after bounded lookahead or equivalent route-owned proof establishes
    exhaustion.
12. Scalar continuation binds every order term and direction, null/comparison
    semantics, the complete last-emitted logical tuple, the last physically
    examined entry, any lookahead state, a deterministic primary-key
    tiebreaker, query window, canonical query shape, database incarnation, and
    accepted-root revision. Exhaustive continuation additionally binds the
    complete read-set revision proof.
13. Exhaustive continuation across a changed source revision fails with a
    typed invalidated/restart result. IcyDB does not silently translate,
    replay, or reconstruct stale progress. Live keyset pagination is a
    separate explicitly mutation-tolerant contract.
14. No rows-only scalar enumeration helper may discard a continuation or
    retain a name or contract that implies complete enumeration. Exact
    `get`/`get_many` may return directly because their requested finite key set
    is itself the exhaustion proof.
15. Index-covered predicates run before stored-row fetch. Residual predicates
    run before unrelated payload fields are decoded or materialized. A visited
    stored row is fetched at most once, and only when the route requires it.
16. Diagnostics are fail-soft and bounded, contain no unbounded raw key or
    query-text retention, charge their work, and never alter plan choice or
    successful query semantics.
17. Current-form cursor, budget, result, and cache contracts are hard-cut.
    0.221 adds no legacy cursor decoder, alias, dual dispatch, or compatibility
    fallback.
18. IcyDB precharges or periodically checks all maintained database work and
    reserves instruction/result-encoding headroom to construct a typed
    failure. This guarantee covers charged IcyDB work only, not arbitrary
    application work outside IcyDB.
19. Final limits are selected from canister instruction and byte measurements
    with recorded headroom. Native debug timings are supporting evidence only.

## Current-Head Baseline

The Toko trace was captured against IcyDB 0.219.1 behavior. Patch entry must
reproduce the workload against the clean post-0.220 baseline instead of
assuming every old implementation detail remains current.

The 2026-08-05 source audit already establishes these current facts:

- `AcceptedSchemaCatalogContext` retains an `AcceptedInspectionPlan`, its
  accepted fingerprint, and a lazy `SchemaInfo`, but scalar structural
  projection still calls `accepted_schema_cache_fingerprint` over the accepted
  snapshot. Accepted row-layout/executor authority is also rebuilt from the
  snapshot at query setup, and cached entity contexts are not yet published as
  one captured root handle.
- The shared structural cache key contains literal `Value` identity. Point
  lookups with different keys therefore do not reuse one parameterized plan.
- Trusted dynamic execution passes no public admission policy. The existing
  `StructuralProjectionScanBudget` is a narrow SQL-write scan guard, not a
  complete read-execution or request budget.
- Fresh public `DbSession` values can currently be constructed over the same
  registry without one non-resettable request counter root.
- `RowProjectionOutput` has rows but no continuation. The public typed
  `execute_rows` convenience returns only `Vec<Row>`, while the grouped result
  already carries `next_cursor`. Scalar dynamic execution rejects cursor input.
- Existing continuation signatures bind canonical plan and accepted-schema
  revision/fingerprint facts, but the scalar public result contract does not
  expose resumable pages and the continuation identity does not yet supply the
  complete database-incarnation plus source-data-revision contract required by
  long-running validation.
- Each journal tail already maintains a durable physical-store row
  `data_mutation_revision`; job-only records do not advance it. The 0.212
  integrity job plus trusted resumable SQL update provide current examples of
  incarnation-bound, revision-checked, bounded continuation.
- Structural sorting already compares each resolved order term with its own
  direction and treats null as lower before applying direction. Some optimized
  index-order contracts still require one uniform direction, so mixed-order
  cursor semantics must remain correct through fallback even when they cannot
  use a direct index-order route.
- Current scalar row runtime can evaluate residual filters through a raw-row
  reader before full `Value` projection on several paths. 0.221 must measure
  and close only the remaining clone, stable read, decode, and projection
  gaps; it must not reimplement work already present on current head.
- Existing per-execution traces and plan metrics record useful route and row
  counters, but they do not aggregate all database calls made by one
  application operation or identify repeated normalized shapes/keys.

The repository has an important parameterization precedent. 0.98 introduced
an internal prepared-SQL lane, and 0.99 replaced its sentinel values with
symbolic parameter slots for an admitted fixed-route subset. That work did not
parameterize ordinary fluent `DynamicQuery` literals or add planner-wide slot
ownership. 0.119 later removed the explicit prepared-session API and its
template/rebinding scaffolding because it was a parallel, unshipped path whose
only remaining caller was its test module.

0.221 must retain that lesson. Parameter reuse belongs on the maintained shared
dynamic/SQL planning and execution boundary, not in another session-owned
prepared subsystem. A reusable template is accepted only when a real public or
generated runtime route consumes it, the literal and parameterized spellings
converge on the same semantic owner where promised, and production-shaped
tests prove different bindings reuse the template without stale access bounds.
Exact typed keys should use `get`/`get_many` instead of creating a second
parameterized point-lookup lane. No 0.98/0.99 API, fallback, or compatibility
surface is restored.

Patch 1 freezes the exact current behavior and instruction attribution before
production code changes. If a reported 0.219 cost is already absent, the
tracker records the proof and the owning patch narrows to the remaining
current-head gap rather than preserving a stale remediation target.

## Accepted-Schema Runtime Root

IcyDB will publish one immutable root for the complete accepted authority:

~~~text
AcceptedSchemaRuntimeRoot
  identity
    database_incarnation
    accepted_root_revision
    accepted_root_fingerprint
    fingerprint_method_version
  accepted_root_snapshot
  shared value/catalog and lookup state
  bounded root-scoped plan-cache identity
  entity_runtimes
    entity_path/tag/store
    entity_schema_version
    entity_schema_fingerprint
    inspection_plan
    schema_info and field lookup tables
    row layout and decode contracts
    compiled validation/planner metadata
~~~

`accepted_root_revision` is the single maintained term and durable type for
accepted publication order. No generation synonym is used for that identity.
Entity schema version and source-data revision remain distinct concepts.

The exact fields may remain private, but the root is one authority, not a set
of independently refreshed entity caches. Acceptance and recovery build every
entity runtime and shared catalog contract against one candidate root. Only
after the complete root validates does publication atomically swap one `Rc`
root handle. Queries and multi-entity operations capture that handle once and
cannot combine entity A from revision 12 with entity B from revision 13.

SQL DDL, schema reconciliation, recovery, database replacement, and test
database teardown publish or invalidate through the same root owner. A cache
hit must revalidate current root authority without hashing the snapshot.
Pointer-derived `cache_scope_id` may remain a process-local lookup aid, but it
is not semantic identity and cannot substitute for database incarnation plus
accepted root revision/fingerprint.

The plan-cache scope includes the complete root identity and access-path/index
authority that affected plan selection. An entity runtime may be independently
addressable after root capture, but it is never independently published.

Acceptance evidence includes a counter-backed test that runs thousands of
single- and multi-entity queries after one accepted publication and observes
zero schema encodes, fingerprint hashes, `SchemaInfo` builds, row-layout
builds, or inspection-plan compiles after initial construction. A concurrent
root replacement either leaves an operation entirely on its captured root or
returns typed stale-authority failure; it never produces a mixed-root result.

## Direct Bounded Primary-Key Reads

Typed exact reads gain a native path with two semantic operations:

- `get(key)` returns one optional row; and
- `get_many(keys)` returns one position per supplied key in request order,
  where each position is explicitly found or missing.

Duplicate input keys preserve duplicate result positions but are deduplicated
for physical store reads and decoding. This makes ordering, duplicates, and
missing keys observable without requiring callers to infer them from a shorter
row vector. Composite primary keys use their canonical encoded tuple order.

One key batch performs:

1. one accepted-runtime and typed-binding validation;
2. one IcyDB lane/admission-profile validation supplied by its owning request
   scope, separate from caller authorization owned by the application;
3. checked key-count and total encoded-key-byte admission charged before
   deduplication;
4. direct store lookups under one execution budget;
5. at most one decode for each distinct stored key; and
6. checked result-row and result-byte projection charged by original input
   positions, including duplicates.

It does not construct a `DynamicQuery`, compile a general plan, or populate the
general plan cache. Public and trusted profiles may use different admitted
limits, but both are finite and both charge the same physical resources.
Generated `EntityModel` metadata supplies only the typed binding/key codec;
the captured accepted runtime root remains lookup and decode authority.

The public page limit remains unrelated to the internal exact-key batch limit.
The latter is selected from total encoded key bytes, worst-case result bytes,
and IC instruction evidence rather than an arbitrary item count.

The accounting contract is exact: input items/bytes use the caller-supplied
list, physical reads/decoded bytes use distinct canonical keys, and returned
rows/materialized/result bytes use the original result positions. Deduplication
is an execution optimization, never a way to evade admission or response
budgets.

## Safe Parameterized Plan Reuse

General dynamic and SQL queries still use the shared planner. Reuse across
different literal values requires a real prepared template:

~~~text
PreparedQueryTemplate
  structural cache identity
  typed parameter slots
  parameter-independent logical/access topology
  projection/order/group/cursor contracts

BoundQueryExecution
  prepared template handle
  accepted and canonicalized parameter values
  execution-specific key/range bounds
  execution/request budget handle
~~~

The structural key includes operator topology, resolved field identities and
types, projection order, every ordering direction, distinct/grouping shape,
missing-row policy, pagination mode, comparison/collation version, accepted
root identity, and every access-path/index visibility fact that can affect plan
selection. It does not claim two statements are reusable merely because their
rendered strings look similar.

`IN` uses a bounded typed list parameter, not one cached template per exact
arity. Empty, singleton, and multi-value operator classes remain distinct when
their semantics or access topology differ. The bound list carries checked item
count and encoded bytes; a bounded execution-time route finalizer may choose
the safe exact-key or scan access from its actual cardinality without mutating
the cached template. Nested `IN` topology and element types remain in the
structural key.

Binding validates every value against accepted schema and builds literal key
or range bounds after cache lookup. Cached plans cannot retain the first
caller's literal bounds. Cursor signatures bind the template shape and a
canonical bound-parameter digest, so a cursor for `collection_id = A` cannot
resume `collection_id = B`.

Exact `get`/`get_many` remains outside this machinery. Parameterization exists
for the rest of the dynamic/SQL surface and is not a reason to route exact keys
back through the planner.

This is a shared-plan capability, not a revival of the removed prepared-session
API. Fluent and SQL inputs may keep distinct parsing and authoring surfaces,
but after lowering they use one parameter-slot, binding, validation, cache, and
execution authority. No template-only helper tree is retained unless a
maintained runtime route exercises it and its measured reuse justifies the
additional machinery.

The template cache is itself bounded per accepted runtime root by entry count,
estimated retained bytes, and planning-work admission. It uses deterministic
eviction and exposes hits, misses, insertions, evictions, rejected-oversize
templates, and overflow. Adversarial query topology or varying bound-list
cardinality cannot create unbounded retained templates. Failed compilations do
not reserve permanent cache capacity.

## Physical And Request-Wide Budgets

`HardExecutionBudget` is the absolute safety ceiling for charged IcyDB work.
It exists at both per-execution and aggregate request scope and covers at
least:

- query executions;
- planning work and plan compilations;
- key/index entries visited;
- rows visited;
- stored bytes fetched;
- predicate and expression evaluation steps;
- nested-value traversal steps;
- bytes decoded;
- bytes materialized;
- sort entries, comparisons, and temporary bytes;
- group and distinct cardinality/state bytes;
- cursor decoding, encoding, and lookahead;
- temporary allocations owned by maintained database operators;
- diagnostic aggregation work;
- result rows; and
- result bytes plus reserved final Candid/response-encoding headroom.

Every query has a finite per-execution allowance. One
`RequestExecutionRoot` is minted at request entry and owns the aggregate
`RequestExecutionScope`. The root request-facing session and every child
session, query builder, nested operation, retry, and resumed synchronous
database segment share the same monotonic counters. Failed and rolled-back
work remains charged. There is no refund operation.

Public one-shot methods execute through the already-existing root scope; they
do not create scopes. Creating a raw `DbSession` is not an execution escape
hatch. Generated endpoint entry owns normal root minting, and manual endpoint
integration enters through one guarded request-root constructor. A second root
for the same active request is rejected. Only internal test infrastructure and
the restricted runtime configuration owner can mint roots directly.

Trusted profile selection is a separate restricted execution-policy
capability. It chooses finite lane/admission/budget limits and is not caller
authorization. Application authentication and authorization remain outside
IcyDB and cannot be inferred from possession of a budget scope.

The root and scope are owned capabilities threaded through session/request
objects. They are not an ambient thread-local held across `.await`, because
canister call reentrancy could attribute another message's work to the wrong
caller. An async application may retain the root in its future. Every session
derived after an `.await` keeps the same counters but revalidates the current
accepted runtime root and any required data authority before executing.

Charging occurs at the physical owner before the work or allocation whenever
the size is known, and immediately after bounded framing when it is not. Cache
hits avoid compilation charges but still charge lookup, execution, reads,
decode, materialization, and response work. Nested queries cannot reset the
request counters.

Maintained loops use conservative precharge and periodic checks. On IC targets,
an actual instruction watermark is sampled at bounded loop boundaries wherever
the platform exposes it reliably. The runtime reserves enough unspent
instruction and output-byte headroom to build and encode the typed failure.
Operators without a reliable instruction watermark use measured work-unit
precharge and remain inside the same conservative headroom contract.

Exhaustion returns a typed `ExecutionBudgetExceeded` carrying:

- the exhausted resource;
- configured limit;
- observed/attempted usage;
- per-execution or request scope;
- bounded normalized query-shape identity; and
- the execution lane.

The error contains no raw literal or key value. For atomic database operations,
budget failure preserves existing rollback semantics. Read APIs do not return
partial rows beside this error.

The guarantee is deliberately narrow:

> IcyDB precharges or periodically checks every maintained database operator
> and reserves sufficient instruction and encoding headroom to return a typed
> failure for charged IcyDB work. It does not bound arbitrary application work,
> external calls, or application response construction outside IcyDB.

Normal resumable progress is governed by the separate `PageWorkEnvelope`
below. Callers must not use hard-budget failure as pagination control flow.

## Scalar Page Progress

0.221 exposes two deliberately named scalar page contracts:

- `execute_live_page` is revision-tolerant keyset pagination for UI browsing.
  It preserves deterministic cursor/order semantics but makes no exhaustive
  snapshot claim across concurrent mutations.
- `execute_exhaustive_page` is revision-strict traversal for validation,
  export, and other complete-set work. It binds every page to one source proof
  and invalidates on change.

There is no generic `execute_page` whose revision behavior callers must guess,
and the ambiguous rows-only helper is removed. Exact `get`/`get_many` may
return rows directly because their finite requested key set is the exhaustion
proof.

Both page results are structurally equivalent to:

~~~text
BoundedPage<Row> {
    rows,
    continuation,
    work,
}
~~~

The exhaustive result additionally returns its `ReadSetRevisionProof`. The
concrete types are bounded and Candid-safe. A non-null continuation means
traversal is not yet proven exhausted; it does not guarantee that another
matching row exists. An empty page with a continuation is valid when physical
progress crosses only non-matching rows. A null exhaustive continuation means
the engine proved exhaustion under the returned source proof.

### PageWorkEnvelope

`PageWorkEnvelope` is successful progress control, not a safety error. It
contains finite allowances for output rows, physical/index entries, stored
bytes, predicate/expression steps, decoded/materialized bytes, sort/group
state where admitted, cursor/lookahead work, and output bytes. Its limits are
strictly inside the enclosing per-execution `HardExecutionBudget` with the
reserved failure/encoding headroom left untouched.

Reaching any page-envelope limit returns the rows already completed plus a
continuation anchored after all consumed physical work. The page may be empty.
Exceeding `HardExecutionBudget` instead returns `ExecutionBudgetExceeded` and
no page. Retrying a hard failure with the same limits is not a progress
protocol.

If one indivisible stored row, ordering tuple, cursor boundary, group, or
encoded result cannot fit into an otherwise empty page envelope, execution
returns a typed terminal `PageUnitTooLarge` identifying the bounded resource,
limit, and attempted bytes/steps. It does not return the unchanged
continuation, preventing an infinite retry loop.

### Physical Progress And Lookahead

The continuation distinguishes:

- the last emitted logical ordering tuple;
- the last fully consumed physical entry; and
- an optional unconsumed lookahead match.

Non-matching examined entries are consumed and advance the physical anchor,
even when no row is emitted. When bounded lookahead finds the next matching
row after a full output window, it charges the inspection but does not consume
that match. The token records the bounded physical key as unconsumed and keeps
the resume boundary strictly before it; the next page re-reads and may emit
that row. The token never embeds a potentially large row payload.

If lookahead crosses non-matching entries and reaches its envelope before it
finds a match or physical exhaustion, those non-matches remain consumed and a
continuation is returned. If lookahead proves physical exhaustion, the
continuation is null even when the preceding output window was exactly full.
No cursor may anchor beyond an unreturned matching row.

## Complete Scalar Cursor Contract

One canonical ordered term records the resolved field/expression identity,
its own `ASC` or `DESC` direction, null policy, comparison version, and encoded
boundary value. Mixed directions compare lexicographically term by term. The
current comparison contract is frozen as `CanonicalComparisonV1`: null sorts
before non-null before direction is applied (`NULLS FIRST` for `ASC`, `NULLS
LAST` for `DESC`); text is exact case-sensitive canonical UTF-8 ordering; blob
ordering is lexicographic bytes; and no locale collation participates.

Every explicit primary-key order term stays in its declared position and
direction. If the explicit order does not already contain the complete
accepted primary-key tuple as a uniqueness proof, the planner appends the
complete primary-key components in accepted schema order as hidden terms.
Each appended component uses the last explicit term's direction, or `ASC` when
there is no explicit order. Thus `score ASC, id DESC` retains its explicit
mixed direction, while a non-unique `score DESC` becomes `score DESC, id DESC`.

The authenticated scalar token binds all of:

- live versus exhaustive page mode;
- every explicit and hidden order term, direction, null policy, and comparison
  version;
- complete last-emitted logical ordering values;
- last consumed physical anchor and optional unconsumed lookahead key;
- canonical query/template and bound-parameter identity;
- accepted access path and index authority;
- original query `LIMIT`, initial `OFFSET`, rows skipped/emitted, and remaining
  total window;
- immutable `PageWorkEnvelope` identity;
- database incarnation;
- accepted root revision/fingerprint and entity authority; and
- for exhaustive mode, the complete source revision proof.

The initial offset is consumed exactly once and its progress is carried in the
token. Query `LIMIT` is a total traversal limit, not a per-page limit. Page
envelope size cannot change on resume; callers omit it and reuse the token's
contract or supply an exact match. A changed limit, offset, envelope, page
mode, projection, order, parameter, access authority, or comparison version is
a typed cursor mismatch.

The decoded binary scalar token is capped at 8,192 bytes, the same ceiling as
the maintained cursor family. Its combined encoded logical ordering tuple is
capped at 4,096 bytes and 32 terms; physical keys retain their existing bounded
key contract. The outward string encoding has a checked corresponding maximum.
An ordered text/blob/nested value or tuple above the boundary cap returns
`PageUnitTooLarge` before cursor emission; it cannot produce a looping cursor.

Cursor framing and declared lengths are bounded before allocation. A
per-database secret MAC key, generated and persisted with the database
incarnation, authenticates the entire canonical token header and payload.
After minimal bounded framing/version checks, the MAC is verified before any
semantic field is used. Only then are query, authority, window, ordering, and
revision contracts decoded and compared.

Database initialization and recovery provision or load that key before the
runtime root becomes query-visible. Query execution never lazily creates or
persists key material. A missing, malformed, or incarnation-mismatched key is
a typed database-availability failure, not a reason to emit an unsigned token.

"Opaque" means the representation is unsupported for callers to construct or
interpret. It does not mean confidential: the authenticated token is not
encrypted and is not a field-level secrecy boundary. Ordering fields and
primary keys may be present even when not projected. The application must
authorize every ordering field before exposing the cursor and must not expose
cursors where those values require stronger secrecy. The IcyDB execution scope
does not confer or infer that authorization. Encryption is outside 0.221.

Live cursors bind incarnation, accepted root revision/fingerprint, query,
ordering, and access authority but not data revision. Concurrent mutations may
move the live set; the contract promises strict keyset progress from each
validated boundary, not snapshot completeness. Exhaustive cursors bind the
full proof below and return typed `ExhaustiveReadInvalidated` on any protected
change.

## Read-Set Revision Proof And Resumable Jobs

`data_mutation_revision` is standardized as `StoreDataRevision`: one monotonic
revision per physical data store. For journaled stores it is the durable
`JournalTailStore::data_mutation_revision`, advanced by row put/delete records
in that physical store, not by schema-control or dedicated progress-job
records. A physical store may contain multiple entities, so a mutation to any
of them conservatively invalidates all proofs containing that store. A
mutation to an unrelated physical store absent from the proof does not.

Heap-only stores use an incarnation-bound in-memory `StoreDataRevision` and
cannot back a durable cross-upgrade validation job. Accepted root revision
covers index definitions. A separate per-store access-state revision covers
index generation/readiness changes that can alter physical traversal without a
row mutation.

The canonical proof is:

~~~text
ReadSetRevisionProof {
    database_incarnation,
    accepted_root_revision,
    accepted_root_fingerprint,
    stores: [
        (store_identity, store_data_revision, access_state_revision),
        ...
    ],
}
~~~

Store entries are deduplicated and sorted by canonical store identity. The
proof admits at most 64 stores and 8,192 encoded bytes. Capturing or extending
a proof beyond either bound returns a typed admission error. Every store read
by an exhaustive job must appear in the proof before the first page; hidden
late expansion of the read set is rejected.

IcyDB owns cursor/proof correctness and a generic atomic
`compare_proof_and_advance` boundary. Toko owns its validation phases,
batch-wide blockers, accumulators, authorization, and result composition. Job
records and replay receipts reside in a dedicated progress store excluded from
the protected read set; admission rejects a job configured in a protected
source store so progress cannot invalidate itself.

Each resume update follows this exact transition:

1. Toko authorizes the caller and loads the job by application job identity;
2. verify the expected job sequence and idempotency key;
3. if that exact request already committed, replay its persisted bounded
   receipt without executing or appending accumulators again;
4. capture and compare the complete canonical read-set proof;
5. execute exactly one page into temporary continuation, accumulator delta,
   and receipt state under the same request root and budgets;
6. recompare the complete proof;
7. on change, discard the candidate delta and atomically persist a typed
   invalidated/restart receipt in the excluded progress store; otherwise
8. atomically persist the next continuation, accumulator delta, next sequence,
   idempotency key, and replayable receipt.

The post-page comparison and progress write occur under one mutation
serialization/commit boundary. A lost reply followed by the same resume
request returns the stored receipt and never applies the fragment twice. A
different acknowledgement or idempotency key at an old sequence returns a
typed stale-sequence error.

Completion requires null continuation for every traversal under one unchanged
proof. A full page, 10,000 rows, or exhausted frontend chunk is never
completion by itself. Because query messages cannot persist progress, job
start/resume operations are updates. This is a protocol requirement, not an
attempt to solve the incident by relying on the update instruction ceiling.
Frontend-only chunking is allowed only after Toko proves all validation results
and batch-wide cap blockers compose across chunks.

## Decode-Once Row Access

Patch 10 audits every maintained scalar, grouped, covering, stable, and
journal-overlay row path against one physical accounting model.

The target execution order is:

1. visit and charge one physical key/entry;
2. evaluate index-covered predicates without fetching the stored payload;
3. fetch and charge the stored payload at most once when residual/order/output
   work requires it;
4. open one bounded row reader;
5. decode only residual-predicate/order-required slots;
6. reject non-matching rows;
7. decode only projection-required slots for accepted rows; and
8. construct a full entity only when the outward typed projection requires it.

The predicate-required and projection-required slot sets are planned once.
Decode-once means a slot already decoded for filtering or ordering is reused by
projection. It does not require retaining a full entity. Stable/journaled
overlay traversal carries the fetched row into filtering/materialization
instead of resolving the same key through a second backend read.

Some current routes already satisfy part of this contract. The patch lands
only evidence-backed remaining changes and deletes any superseded duplicate
path. Large-payload acceptance fixtures prove that a residual predicate on a
small metadata field does not decode unrelated snapshot/blob/map payloads for
filtered-out rows.

## Request Diagnostics And N+1 Visibility

An opt-in bounded request summary aggregates by normalized query-shape identity:

- execution count;
- plan compilations, cache hits, and cache misses;
- keys/rows visited and rows returned;
- stored, decoded, materialized, and returned bytes;
- exact-key lookups and bounded repeated-key counts;
- residual predicate terms;
- selected index/access path; and
- bounded useful compound-index candidates derived from equality-prefix,
  residual, and ordering fields.

Repeated-key observation uses bounded hashed identities or a bounded
heavy-hitter structure. It does not retain raw keys indefinitely. Shape labels
are normalized and bounded; literal values remain excluded from diagnostics.
When capacity is exceeded, an explicit overflow count preserves the fact that
the report is incomplete.

Diagnostics charge evaluation, hashing, aggregation, retained bytes, and
response bytes to the same request root. When their own bounded allowance is
exhausted, they fail soft by incrementing an overflow/suppression count and
stop collecting detail. They never select a different plan or change a
successful query result, but their cost is not treated as free.

The Toko incident fixture should produce a warning equivalent to:

> One normalized provenance point lookup executed approximately 200 times;
> candidate validation repeatedly decoded a shared snapshot. Consider one
> bounded `get_many` preload and reuse the result within the request.

Compound-index suggestions are diagnostic only. IcyDB does not mutate schema
or make generated models runtime authority. For the Toko Live scan, the
evidence should identify equality on `collection_id` plus residual equality on
`stage` as the useful ordered compound prefix.

## Cross-Patch Acceptance Matrix

### Accepted Runtime Root

- after initial publication/recovery, repeated reads perform zero accepted
  snapshot encodes and zero schema fingerprint hashes;
- derived schema/planner/row-layout metadata constructs once per accepted
  authority;
- DDL publication swaps one complete runtime root and a multi-entity operation
  observes one root revision or typed stale-authority failure, never a mixture;
  and
- reused visible schema versions across database replacement cannot hit an old
  runtime or plan cache entry.

### Exact And Planned Reads

- direct `get_many` performs one validation, one bounded distinct-key read set,
  and at most one decode per distinct found key;
- input ordering, duplicate positions, and missing positions are exact;
- input count/bytes charge before deduplication, physical work charges by
  distinct key, and output charges by original result position;
- point-lookups with different literals reuse one parameterized template when
  every structural dimension matches;
- parameter changes cannot reuse literal bounds or cursor tokens; and
- changing operator topology, types, projection, ordering, grouping, accepted
  root, or index/access authority produces a distinct template; and
- many topologies and bounded-list cardinalities prove deterministic
  cache-capacity enforcement, eviction, and rejected-oversize behavior.

### Budgets

- public, trusted, typed, dynamic, SQL, grouped, covering, and fallback routes
  all charge finite physical work;
- predicate/expression/nested traversal, sorting, grouping/distinct, cursor,
  lookahead, temporary bytes, diagnostics, and response encoding are included;
- hundreds of individually small queries exhaust the shared request allowance
  with `ExecutionBudgetExceeded` while charged IcyDB work retains the measured
  typed-failure headroom;
- error facts identify resource, limit, attempted usage, lane, scope, and
  normalized shape without exposing literals; and
- no new session, nested operation, failure, rollback, retry, cache hit, or
  alternate route resets or refunds counters; and
- a retained request root crossing `.await` keeps its counters while each new
  derived session revalidates runtime/data authority.

### Pages And Resumable Work

- a highly selective scan may return an empty page with non-null continuation
  after advancing its physical anchor;
- an exact-full result page followed by a long nonmatching tail consumes the
  tail across bounded progress pages and eventually proves exhaustion;
- page-envelope exhaustion returns progress while hard-budget exhaustion
  returns no page;
- one row, order tuple, or cursor boundary too large for an empty page returns
  terminal `PageUnitTooLarge` without an identical continuation;
- page-size-plus-one and datasets above 10,000 traverse without gaps or
  duplicates;
- mixed ASC/DESC ordering with nulls, duplicate secondary values, explicit
  differently directed primary keys, and hidden unprojected order values
  resumes exactly;
- lookahead never anchors beyond an unreturned match;
- token size/term/tuple caps, whole-token MAC authentication, tampering, and
  the documented non-confidentiality contract are covered;
- live pages retain documented mutation-tolerant keyset semantics, while
  exhaustive schema/incarnation/query/parameter/data changes return typed
  invalidation; and
- an application job can persist one page at a time and report completion only
  after all traversals return null continuation under one unchanged bounded
  read-set proof;
- job-progress writes do not change their protected proof, an unrelated-store
  mutation does not invalidate it, and a mutation in a participating physical
  store does; and
- lost-response replay returns the persisted receipt without applying an
  accumulator delta twice.

### Row Work And Diagnostics

- index-covered rejection fetches no stored payload and every other visited
  payload is fetched at most once per execution attempt;
- filtered-out large rows decode only predicate/order-required fields;
- decoded slots shared by filter/order/projection are reused;
- request summaries reconcile executions, compilations, rows, and bytes with
  underlying per-execution traces; and
- diagnostic capacity exhaustion is charged, fail-soft, and visible through
  overflow/suppression counts; and
- the Toko-shaped inefficient fixture exposes repeated provenance/snapshot
  access and the missing `collection_id + stage` compound-index opportunity.

## Performance, Wasm, And Complexity Evidence

Every production patch reports:

- matched canister instructions for cold and warmed point lookups, key batches,
  selective scans, live/exhaustive continuation, page-envelope progress,
  hard-budget exhaustion, and typed-failure encoding;
- schema encodes/hashes/builds, plan compilations/cache hits, physical reads,
  rows visited/returned, predicate/expression/sort/group/cursor/diagnostic work,
  stored/temporary/decoded/materialized/result bytes, actual instruction
  watermark where available, and reserved response headroom;
- raw non-gzipped final deployable Wasm bytes as size authority, with gzip only
  as secondary context;
- affected Candid bytes/hash and method-name/mode exports;
- files touched, approximate line delta, delivery domains, and whether the
  implementation became simpler, stayed neutral, or became more complex; and
- focused validation plus explicitly user-owned full-suite validation.

The representative integration workload uses shared 40 KB, 150 KB, and 300 KB
snapshot payloads; 100- and 1,000-key exact batches; repeated dynamic point
lookups; selective and non-selective compound-index scans; and an exhaustive
dataset above 10,000 rows. Limits are frozen only after query-message
measurements retain meaningful headroom below the 5-billion instruction cap.
Update-message measurements are secondary safety context and do not select the
read limits by themselves.

The closeout claim is limited to maintained, charged IcyDB work. The fixture
separately records application-only work and final generated-endpoint encoding
so a successful IcyDB budget result is never presented as proof that arbitrary
endpoint code cannot trap.

## Non-Goals

- Implementing Toko's `BatchReadinessCtx`, token schema index, frontend, job
  phases, accumulators, or application result semantics in this repository.
  IcyDB owns only the generic excluded progress-store and atomic proof/advance
  boundary.
- Treating a larger IC update ceiling as the reliability fix.
- Freezing 400 as the internal batch size without measurement.
- Providing snapshot isolation or replaying historical row versions. Revision
  change invalidates and restarts instead.
- Encrypting cursor tokens. They are authenticated and opaque but explicitly
  not confidential.
- Automatically creating compound indexes from diagnostics.
- Making arbitrary dynamic queries use the exact-key direct path when their
  semantics are not a proven finite primary-key set.
- Retaining the old rows-only scalar or cursor wire surface behind aliases.
- Reopening accepted-schema authority, current storage formats, or generated
  runtime fallback policy.
