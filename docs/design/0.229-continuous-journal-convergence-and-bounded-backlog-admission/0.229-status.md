## Patch 1 Reconciliation Results

### Complete-batch predecessor

- `FoldRecordCursor` was removed in accepted 0.228 with no replacement.
- The fold watermark plus oldest retained complete batch are the only
  owner-local progress authority.
- Raw inspection, complete Validate/preflight, mechanical Apply, watermark
  publication, and immutable batch retirement occur in one synchronous
  message.
- Recovery stops between complete batches only. A later mutation can occur
  before a callback or between callbacks, never inside Validate/Apply.

### Ordered admission and zero-debt theorem

- Accepted 0.228 already applies exact prepared-work admission
  `W = 4R + I + 4A + 4P <= 16,384`, plus existing record, byte, fanout,
  marker, and structural limits.
- Those individual failures remain non-pressure errors and have priority.
- Every maximum Gate-1-valid batch/record/byte and multi-store contribution
  must fit the final Gate 2 tuple against zero retained debt.
- Gate 2 may reject a legal proposal only because existing debt consumes
  capacity; sufficient convergence must make retry possible.
- Admission and publication consume the same encoded prepared batch bytes;
  identity and database commit sequence may be previewed but never durably
  advanced on rejection.
- Patch 4's evaluator is test/audit-only and cannot reject a production commit.

### One-message fit and heap

- The 0.228 one-batch proof is not assumed to cover new 0.229 work.
- Patch 5 must include exact aggregate maintenance, maximum positioned
  retirement, 38-head selection, and driver bookkeeping in the callback
  instruction proof, or Gate 1 must be tightened.
- Overlay heap bytes and maximum decode/preflight/Apply/retirement scratch are
  bounded mechanically, not inferred from effect count alone.
- Gate 2 bounds outstanding debt and cannot substitute for per-batch fit.

### Activation and persisted authority

- Fresh installation requires absent recognized authority plus provably fresh
  declared allocation roots, then atomically creates the incarnation, format
  identity, bounded registry, database commit sequence, and zero controls.
- Upgrade requires runtime-observable accepted 0.228 controls, `Ready`, empty
  tails, no matching terminal startup failure receipt, and absent 0.229
  authority. `Ready` is an authorized observation, not a persisted positive
  receipt. Nonempty 0.228 tails drain under exact 0.228.3 before 0.229
  installation.
- Operators quiesce writes, reinstall/upgrade 0.228.3, wait for authorized
  `Ready`, keep writes stopped, and then install 0.229. A racing write is caught
  by the activation recheck.
- 0.229 adds no predecessor-tail scanner, decoder, or compatibility drain.
- Missing controls after current-format activation are corruption.

### Current-format registry and cross-store order

- Application memory identifiers span `100..=254`; three canister controls and
  four allocations per journaled store yield absolute `S_max = 38`.
- The convergence-format identity, registry, and global sequence use the
  existing commit-control allocation, so they add no fourth canister memory
  reservation.
- Persisted current-format authority retains every active or retired quartet;
  retired identifiers never reuse within the database incarnation.
- New stores require fresh collision-free allocations and atomic zero-control
  initialization; removal requires an empty tail and leaves a retired entry.
- Accepted 0.228 journal sequence is tail-local. The 0.229 version-3 envelope
  adds one fingerprint-bound database commit sequence.
- The driver selects minimum `(database commit sequence, store allocation,
  journal sequence)` across at most 38 exact heads, preventing hot-store
  starvation without a scheduler cursor.

### Current-state overlay authority

- Current-process `Ready` may carry bounded debt only with a complete live
  overlay; install/upgrade without overlays uses `Recovering` for retained
  current tails.
- Query execution, mutation preparation, constraints, identity allocation,
  validation, and migration all consume live-before-canonical state.
- Patch 2 must classify every accepted `JournalRecord` and derived effect with
  an exhaustive no-wildcard Rust match as positive, tombstone, terminal-only,
  or prohibited online.
- Position starts with store allocation, tail-local batch sequence, and logical
  target. A family-local ordinal requires evidence of a repeated same-batch
  target; no general ordinal is authorized.

### Driver and residual bounds

- Tail controls prove actionable work; no durable `work_pending` Boolean is
  added.
- The existing driver self-chains while debt remains, and every normally
  returned actionable callback progresses, quiesces, or publishes terminal
  failure.
- Diagnostic and integrity surfaces remain available through the existing
  authorized failure lane when ordinary database work is blocked.
- Residual work snapshots `B_0` at the start of a no-new-debt interval:

```text
P_fold_normal <= B_0
M_total_normal <= B_0 + C_driver
I_total_normal
  <= B_0 * I_fold_callback_max
   + C_driver * I_driver_overhead_max
```

`C_driver` includes every fixed normal driver/lifecycle message. The formula
does not misuse current remaining `B`. It covers normal callbacks after
one-message fit excludes instruction exhaustion. Unexpected rollback traps are
outside the normal bound and cannot falsely claim durable terminalization.

### Steady-state and physical bounds

```text
B <= B_max, R <= R_max, Y <= Y_max, S <= S_max <= 38
O <= g(B, R, Y, W_0_229_max, F_max)
H_overlay
  <= H_fixed + sum(alpha_f * O_f) + beta * Y + gamma * B + delta * S
H_callback_peak
  <= H_overlay + H_head_scan_max + H_decode_max
   + H_preflight_max + H_apply_max + H_retire_max
```

Physical retained chunk entries satisfy
`K = sum(ceil(y_b / 65,536)) <= B + floor(Y / 65,536)`. Patch 5 must also prove
allocator reuse through repeated fill/drain/refill cycles; logical bytes alone
are insufficient.

No right-hand side contains historical population, historical commits, or
retired journal history. Wall-clock timer delivery remains outside the claim.

## Patch 2 Positioned Overlay Results

### Singular owner-local representation

- The existing data, index, and schema live maps and tombstone sets remain the
  only current-state value authority. Patch 2 adds one parallel position map
  to each journaled owner; it does not add a second value projection.
- Each position is exactly `(store allocation, tail-local journal sequence)`;
  the family map key is the logical target. There is no general record ordinal,
  cursor, persisted overlay, scheduler state, or configuration axis.
- Publication preflights allocation consistency and monotonic sequence before
  changing the live effect. Retirement preflights the exact position before
  removing anything. An older batch observes `Superseded` and leaves the newer
  value or tombstone intact; an absent, future, or cross-allocation position
  fails typed and closed.
- Existing production owner paths do not touch positioned provenance. Patch 6
  must atomically route online publication through these state machines and
  include position reset in the established projection-reset boundaries; no
  mixed positioned/unpositioned production state is authorized.
