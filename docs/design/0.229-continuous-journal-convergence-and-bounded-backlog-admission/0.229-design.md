## Planning Status And Authorization

This line proposes one continuous convergence lifecycle around the accepted
0.228 complete-batch engine, one existing 0.225 driver, exact owner-local tail
controls, exact pre-marker cumulative admission, and journal-positioned live
overlays. It adds no second decoder, cursor, compactor, scheduler, or
caller-configurable policy.

Patch 1 is documentation and evidence only. It reconciles the predecessor,
selects the empty-tail activation cut, separates individual commit admission
from cumulative pressure admission, proves the deployment bound on the store
registry, and states the residual-work lemma. It does not authorize persisted,
runtime, generated, Candid, or public API changes.

Dormant implementation is authorized only for the explicitly approved named
patch. Patches 2 through 5 are not independently releaseable or deployable and
must remain unreachable from ordinary production entry points. They introduce
no public mode, feature setting, or compatibility route. Runtime behavior may
activate only in Patch 6, after the integrated dormant candidate has frozen its
tuple, callback, driver, heap, and stable-allocation evidence.

## Decision Summary

The accepted 0.228 engine remains cursor-free. Each driver work message selects
the oldest retained complete batch, performs bounded raw inspection, complete
read-only validation and fold/terminal preflight, and then mechanically Applies
the batch, advances the fold watermark, subtracts the batch's exact aggregate
contribution, retires the immutable batch, and removes only overlay effects
whose exact position is now canonical and which are not superseded by a newer
committed position. Terminal arithmetic and overlay positions are proved before
canonical mutation; any contradiction during the mechanical phase traps and
rolls back the message. Those transitions occur in one synchronous replicated
message.

The existing 0.225 driver remains the singular scheduler. Current-process
`Ready` may coexist with bounded online tail debt only while the complete live
overlay is present as current-state authority for queries, mutation
preparation, constraints, identities, validation, and migrations. After
install or upgrade, volatile overlays are absent, so any current-format
retained tail keeps startup `Recovering` until the same complete-batch engine
empties it.

Commit admission is deliberately two-stage:

1. Gate 1 preserves accepted 0.228 individual admission and, before activation,
   incorporates any exact tightening required to prove the complete 0.229
   callback shape fits; and
2. 0.229 cumulative admission proves that adding that individually valid
   commit will not exceed any component of the fixed database backlog tuple.

An individual-limit failure remains the existing non-pressure boundary error,
even if cumulative limits would also fail. An individually valid proposal that
would exceed cumulative capacity returns the new retryable convergence-pressure
error. Pressure never conceals a commit that remains invalid with an empty
backlog.

## Pre-1.0 Activation Contract

0.229 selects an empty-tail hard cut. It does not scan, translate, or drain a
0.228 tail through a compatibility route.

The release-process predecessor and the runtime-observable predecessor are
different authorities:

- the audited predecessor release is exact `v0.228.3`, commit, and tree named
  above; and
- runtime activation can inspect only persisted format/control identities,
  database incarnation, startup failure receipt, allocation roots, and bounded
  tail state. It does not claim to inspect a Git tag or source commit that
  0.228 did not persist.

The only eligible upgrade state has:

- accepted 0.228 persisted commit, startup, journal, and schema control shapes;
- an existing database incarnation, an authorized startup observation of
  `Ready`, and no matching terminal startup failure receipt;
- every registered journal tail empty; and
- no 0.229 format marker or aggregate controls.

A fresh installation is a distinct transition. Absence of recognized database
authority plus provably fresh declared allocation roots initializes one new
database incarnation, the 0.229 convergence-format identity, the bounded store
registry, the database commit-sequence control, and zero tail controls
atomically before ordinary work. Freshness is proved from bounded canonical
root/control inspection, not a history-sized memory scan. Partly initialized,
unknown, or nonempty allocations fail typed; absence is not treated as
freshness by itself.

The quiesced upgrade protocol is:

1. stop external application writes while exact `v0.228.3` remains installed;
2. reinstall or upgrade that exact release to enter its startup recovery lane;
3. wait for the existing authorized readiness observation to report `Ready`,
   which proves the registered 0.228 tails are empty;
4. keep writes quiesced and install 0.229; and
5. let 0.229 recheck the runtime-observable controls and empty tails before it
   publishes current-format authority.

A write racing between the readiness observation and installation makes the
activation recheck fail typed. Operators must return to the exact 0.228.3 drain
protocol; 0.229 never consumes the new predecessor debt.

For the eligible empty predecessor, activation atomically publishes the current
0.229 persisted-format identity, bounded store registry, database commit
sequence, and zero-valued aggregate/head controls before ordinary database work
is admitted. Once the 0.229 identity exists, a missing registry or control is
corruption and fails closed. There is no ordinary startup reconstruction,
legacy decoder, dual control shape, or history-sized first cutover recovery.
Fresh and upgrade activation completely preflight every bounded allocation and
control before the mechanical publication phase; a post-preflight
contradiction traps and rolls the complete message back.

The 0.229 residual-work guarantee begins at the first `Ready` state after this
activation. Because activation requires empty predecessor tails, historical
0.228 debt is outside the current format rather than an exception to the bound.

## Canonical Ownership

1. accepted schema snapshots own row, index, relation, constraint, and layout
   semantics;
2. the commit marker owns atomic mutation publication;
3. immutable journal batches own committed effects not yet folded;
4. the fold watermark and oldest retained complete batch own convergence
   progress;
5. canonical stores own folded stable state;
6. journal-positioned live overlays own latest current-state effects ahead of
   the watermark for every query and mutation consumer;
7. each journal tail owns its exact retained batch, record, and encoded-byte
   controls;
8. commit admission owns the ordered individual and cumulative checks;
9. the convergence-format control owns the bounded persisted store registry
   and database-wide commit-sequence high-water; and
10. the accepted 0.225 driver owns replicated invocation and self-chaining.

The convergence-format control is a current field/slot under the existing
commit-control allocation, not a fourth canister-level memory allocation.
Owner-local aggregate/head controls remain under each existing journal
allocation. The three-reservation store-bound proof therefore remains exact.

The database backlog is the exact bounded sum of owner-local controls. There is
no second persisted database-wide aggregate or advisory estimate. Overlay
provenance is volatile and derived during current-process publication; it is
not a second durable mutation log.

## Two-Layer Admission

### Gate 1: inherited and revalidated individual admissibility

The inherited prepared-work equation is:

```text
W = 4R_row + I_index + 4A_identity + 4P_progress
W <= 16,384
```

`R_row` is prepared row work, `I_index` is the exact prepared index-mutation
count, `A_identity` is prepared identity-range work, and `P_progress` is
prepared progress-successor work. The accepted batch-record, encoded-byte,
fanout, marker, and structural limits also apply. Their current errors remain
non-pressure errors.

Patch 5 revalidates those inherited limits against the complete 0.229 callback
shape. If measured headroom is insufficient, Gate 1 gains the smallest exact
retirement/control work term or tightens the relevant family limit. Such a
failure is still an individual non-pressure error that can occur at zero debt;
it is never reclassified as Gate 2 pressure.

### Gate 2: 0.229 cumulative backlog admissibility

After Gate 1 succeeds, the coordinator sums the exact immutable prepared batch
contribution with current owner-local controls and proves:

```text
B_current + B_proposed <= B_max
R_current + R_proposed <= R_max
Y_current + Y_proposed <= Y_max
```

`B_max`, `R_max`, and `Y_max` are fixed engine constants, not settings. Their
numeric values are a pre-activation measurement gate; Patch 1 does not invent
values without current online overlay and callback evidence. Patch 6 cannot
activate until Patch 5 has populated and reviewed the tuple and derived
callback maximum.

The tuple must dominate every individually legal proposal at zero debt. Let
`B_gate1_max`, `R_gate1_max`, and `Y_gate1_max` be the maximum exact
multi-store contributions of any proposal admitted by Gate 1. Before
activation:

```text
B_gate1_max <= B_max
R_gate1_max <= R_max
Y_gate1_max <= Y_max
```

Therefore Gate 2 always admits a Gate-1-valid proposal against an empty
backlog. It may reject that proposal only because existing retained debt
consumes capacity, and draining sufficiently—at worst to zero—makes retry
admissible. The theorem covers the maximum legal batch count, record count,
encoded bytes, and one maximum legal multi-store commit independently and in
combination.

Admission consumes the same immutable prepared bytes later appended under the
marker. It must not encode independently for checking and publication.
Preparation may preview identities and construct the exact marker-bound batches
against the observed identity high-water. Rejection occurs before durable
identity advancement, marker persistence, journal append, live-overlay
publication, or any other externally committed effect.

A normally returned pressure error may request the existing driver while
returning no mutation result, provided it durably changes no mutation state.
The request is an idempotent liveness action, not admission of the rejected
proposal. The dormant Gate 2 evaluator in Patches 4 and 5 is unreachable from
the production commit path and cannot reject a production mutation. Gate 2
becomes authoritative only in the same Patch 6 activation that makes online
`Ready` debt actionable through the driver.

## Exact Tail Controls

For every registered journal tail, the current control owns:

- `batch_count` is the number of complete retained journal batches strictly
  above the fold watermark;
- `record_count` is the sum of the immutable verified header-declared record
  counts of those batches; and
- `encoded_batch_bytes` is the sum of the exact current envelope lengths read
  by the convergence decoder, including the current complete header and
  fingerprint; and
- `head_database_commit_sequence` is absent exactly when `batch_count` is zero
  and otherwise names the database commit sequence in the oldest retained
  complete batch.

Accepted 0.228 version-2 envelopes have a codec-derived 85-byte fixed header.
Because 0.228 journal sequence is owner-local, Patch 3 hard-cuts the empty-tail
0.229 format to one version-3 envelope that adds an eight-byte
`database_commit_sequence`, includes it in the fingerprint, and therefore has
a codec-derived 93-byte fixed header before record payload. There is no dual
decoder for retained predecessor batches. Append uses the exact prepared
encoded envelope. Complete-batch retirement subtracts that selected batch's
verified immutable contribution and updates the exact head control in the same
message that publishes its watermark and retires it.

The database commit sequence is a monotonic `u64` owned by the
convergence-format control. Preparation previews the next sequence without
durable mutation. Every batch in one marker carries that sequence; store
allocation and tail-local journal sequence break ties. Successful marker
publication advances the high-water atomically, marker replay retains the same
value, and Gate 1 or Gate 2 rejection consumes no sequence.

Routine startup validates only bounded control invariants: decodability,
arithmetic range, watermark/head/tail ordering, current format identity, and
other facts available from fixed controls. It cannot claim to recompute
aggregate equality without reading the tail. A mismatch discovered while
appending, replaying, or retiring a selected batch fails typed and closed. A
full aggregate comparison belongs to an explicit integrity operation.

Malformed encoding, overflow, subtraction underflow, impossible sequence
relationships, or missing current-format controls are corruption. Generated
models and historical scans never guess or repair admission authority.

## Deployment-Bounded Store Sum

Database admission may sum registered owner-local controls because the
registry is statically deployment-bounded.

The generated canister allocation range has 155 application memory identifiers
(`100..=254`). Three are reserved for commit, startup, and integrity-progress
authority. Every journaled store consumes four distinct identifiers for data,
index, schema, and journal ownership. Therefore:

```text
S_max_absolute = floor((155 - 3) / 4) = 38
```

The 0.229 convergence-format control persists the canonical registry of every
store-allocation quartet ever admitted in the current database incarnation.
It resides in the existing commit-control allocation and consumes no new
application memory identifier.
The generated store set is reconciliation input, not runtime authority.
Activation seeds the registry from the accepted empty-tail deployment. Later
code/schema installation reconciles generated proposals before `Ready`:

- a new quartet must be in range, collision-free, absent from every active or
  retired registry entry, and backed by provably fresh allocation roots;
- the quartet and its zero tail controls become authoritative atomically before
  its first admission;
- removing a generated store requires its exact controls to be zero, then marks
  the registry entry retired;
- retired entries and their allocation identifiers remain reserved for the
  database incarnation and are never reused; and
- active and retired entries count toward `S_max`, while retired zero controls
  remain harmless in the bounded database sum.

Historical schema changes within one store do not add entries. Historical
store churn can consume but never exceed 38 quartets. Exhausting the registry
fails typed rather than evicting or resurrecting allocation authority.
Schema/build validation rejects an allocation set above the fixed range or
with collisions.

Store reconciliation likewise performs complete bounded read-only preflight
before registry/control publication; it cannot return normally after a partial
new-store or retirement transition.

Consequently database admission is `O(S)` with a deployment constant no larger
than 38. A persisted database-global duplicate aggregate is not justified by
the current registry bound.

## Starvation-Free Cross-Store Selection

Accepted 0.228 `JournalSequence` is tail-local and cannot order batches from
different stores. The current 0.229 envelope's database commit sequence is the
singular cross-store age authority.

Each work callback scans the exact head controls of at most 38 registered
tails and selects the minimum actionable key, using the journal-memory
allocation identity as the store tie-break:

```text
(database_commit_sequence, store_allocation, journal_sequence)
```

All batches from one marker share the database sequence; allocation and local
sequence provide deterministic ties. Every later successful commit has a
strictly greater database sequence, so a newly appended hot-store batch cannot
move ahead of an already retained cold-store head. An existing head is retired
after only the finite set of already retained smaller keys. This provides
starvation freedom without a scheduler cursor, persisted round-robin pointer,
or unbounded scan.

The selector scan, head-control validation, and tie comparison are included in
the callback instruction and scratch-heap maxima. Validation includes a
continuously replenished hot store and a cold store with an older head; the cold
batch must retire before any later hot-store commit.

## Online State And Driver Liveness

The lifecycle rules are:

| State | Tail and overlay rule | Driver rule |
| --- | --- | --- |
| Current process, `Ready` | A bounded current-format tail may exist only while the complete positioned live overlay remains current-state authority for all consumers | Tail controls are durable proof of work; the existing driver is requested and self-chains |
| Install or upgrade | Volatile overlays are absent; any retained current-format tail means `Recovering` | The same driver folds complete batches until empty or terminal failure |
| Quiescent `Ready` | Tail controls are zero and no retired overlay debt remains | No wake-up remains actionable |
| Terminal convergence failure | Durable startup/convergence failure receipt is authoritative | Ordinary reads and writes are blocked; authorized status, diagnostic, and integrity surfaces remain available; the watchdog stops and cannot hot-loop |

No persisted `work_pending` Boolean is added. Exact tail controls and lifecycle
state are the singular durable evidence.

A post-commit driver request must be infallible and non-propagating at the API
boundary, or a trap must roll the complete commit message back. A mutation is
not “already committed” until its synchronous message returns successfully.
When debt remains after a callback, the driver self-chains; progress cannot
depend on a later successful or rejected mutation requesting another wake-up.

Every successful callback that begins with actionable debt must retire at least
one complete batch, reach quiescence, or publish a typed terminal failure. A
successful zero-progress callback loop is prohibited. This extends the 0.225
invariant that actionable recovery work has a surviving watchdog wake-up.

The failure lane does not hide the receipt it needs operators to investigate.
Existing controller/lifecycle authorization continues to gate status,
diagnostic, integrity, and repair observations while ordinary database work is
blocked.

## Overlay Effect-Family Contract

The minimal common provenance is `(store allocation, batch sequence, logical
target)`. A general record ordinal is not part of the design. Accepted 0.228
duplicate-target restrictions are reused. Patch 2 must prove the restriction
for each maintained family; only an effect family that can genuinely repeat a
logical target inside one admitted batch may add a family-local ordinal.

For every effect below, a positive live entry or negative tombstone precedes
canonical state. Only the newest committed position for a logical target is
retained. After a complete batch becomes canonical, an overlay entry is removed
only if its exact position belongs to that batch and no newer position
supersedes it.

“Current-state authority” is broader than query visibility. Every consumer
whose correctness depends on committed state reads live-before-canonical:

- current-row lookup during update and delete preparation;
- unique-index conflict detection and index-maintenance predecessor reads;
- relation, referential, and other constraint admission;
- accepted-schema lookup and schema-transition decisions;
- identity high-water allocation;
- validation-job and candidate-index decisions; and
- migration reads, writes, and derived index decisions.

| Effect family | Logical target and representation | Visibility and retirement owner |
| --- | --- | --- |
| Row put | Store allocation plus row key; positive row | Point and ordered/range row reads merge live-before-canonical; exact-position retirement |
| Row delete | Store allocation plus row key; negative tombstone | Point and ordered/range row reads hide canonical data; exact-position retirement |
| Unique-index insert | Index allocation plus encoded index key; positive owner entry | Unique lookup exposes exactly one newest owner and cannot reveal old and new owners together |
| Unique-index remove | Index allocation plus encoded index key; negative tombstone | Unique lookup hides canonical ownership until the removal is canonical |
| Non-unique index insert | Index allocation plus full encoded membership key; positive entry | Equality, ordered, and range reads merge without duplicates |
| Non-unique index remove | Index allocation plus full encoded membership key; negative tombstone | Equality, ordered, and range reads hide the canonical membership |
| Schema snapshot put | Schema allocation plus entity tag; positive persisted snapshot | Schema snapshot readers observe the newest candidate snapshot; exact-position retirement |
| Accepted-schema publication and accepted-index suffix | Accepted revision/root or suffix index key; positive publication plus exact positive/negative suffix entries | Publication family is atomic at complete-batch scope; accepted-schema readers and suffix reads consume the overlay |
| Identity advancement | Identity owner; positive high-water advancement | Allocation observes the newest committed high-water; retire only when the exact advancement is canonical |
| Validation-job put/delete | Entity tag plus constraint identity; positive job entry or tombstone | Job/status readers use live-before-canonical; complete-batch retirement preserves the newest transition |
| Validation candidate-index put | Full encoded candidate membership key; positive entry | Validation lookup sees each admitted key once and retires it only with its exact job-owned batch |
| Migration row/index effects | Same row or full index target as ordinary effects; positive entry or tombstone | Migration reads and ordinary reads share the same precedence and retirement rules |

Patch 2 derives its classification exhaustively from the accepted 0.228
`JournalRecord` enum rather than relying on this prose table. Production uses a
Rust `match` with no wildcard and assigns every variant to exactly one explicit
decision: positive current-state overlay, tombstone, terminal-only effect that
needs no overlay, or prohibited online family. The maintained variants are
`RowPut`, `RowDelete`, `SchemaPut`, `AcceptedSchemaPublish`,
`AcceptedSchemaIndexDelete`, `AcceptedSchemaIndexPut`,
`ConstraintValidationJobPut`, `ConstraintValidationJobDelete`,
`ConstraintValidationIndexPut`, `IdentityRangeAdvance`, and the feature-gated
`SchemaMigrationRowPut` and `SchemaMigrationIndexPut`. Derived ordinary index
effects receive the same exhaustive positive/tombstone decision under their
maintained effect type; Patch 2 does not add a second classification model when
an existing exhaustive type can own it.

The implementation must preserve the accepted same-batch restrictions already
proved for ordinary rows, migration row/index targets, identity owners,
constraint-validation index keys, accepted-schema publication, and validation
job transitions. Patch 2 closes any remaining accepted-index suffix or
derived-index target ambiguity before selecting representation. Classification
tests enumerate every maintained family, and compile-time exhaustive matching
forces a new record/effect variant to make an explicit online decision.

Later commits may publish before an earlier batch callback begins or between
two complete-batch callbacks. Tests must exercise those boundaries. They must
not describe an impossible ordinary write interleaving inside synchronous
Validate/Apply.

## Mechanical Boundedness Lemma

Accepted 0.228 provides the starting work and fanout model, but not the final
0.229 one-message-fit proof. Define exact retirement work by effect family:

```text
W_0_228_batch <= W_0_228_max = 16,384
F_batch <= F_max
W_0_229_batch
  = W_0_228_batch
  + W_aggregate_control
  + W_head_selection_share
  + sum(c_family * E_family_batch)
W_0_229_batch <= W_0_229_max
```

Before activation, Patch 5 must prove either that the accepted Gate 1 limits
leave measured instruction headroom for maximum control maintenance and
positioned retirement, or that Gate 1 has been tightened with the exact added
work term. In both cases every Gate-1-valid batch must fit a normal 0.229 fold
callback at `S_max`, maximum family fanout, and maximum overlay retirement.
Gate 2 cannot supply this proof: it bounds how many batches are outstanding,
not whether one batch fits one message.

After current-format activation, the steady-state premises are:

```text
B <= B_max
R <= R_max
Y <= Y_max
S <= S_max <= 38
```

For a bounded no-new-debt interval, let `B_0` be the database-wide retained
batch count observed when the interval begins. A startup `Recovering` interval
has no ordinary writers. An online quiescence interval starts only after new
admission is stopped. Current `B` remains the instantaneous debt bound; it is
not substituted for `B_0` in residual-work formulas.

Normal-path derived bounds are:

```text
O <= g(B, R, Y, W_0_229_max, F_max)
P_fold_normal <= B_0
M_total_normal <= B_0 + C_driver
I_total_normal
  <= B_0 * I_fold_callback_max
   + C_driver * I_driver_overhead_max
```

`O` is retained volatile overlay effects, `P_fold_normal` is normally returned
fold callbacks, and `M_total_normal` counts every normally deliverable
protocol message in the interval. Fixed `C_driver` includes the initial driver
request, final readiness/quiescence handoff, coalesced duplicate or no-work
callback, and every fixed watchdog transition. Patch 5 freezes the exact
constant and proves the list exhaustive. Batch count is the direct fold-message
bound because every normal actionable fold callback retires at least one
complete batch. Record, byte, fanout, memory, and instruction limits remain
distinct resource bounds.

The formula covers normal callbacks after the one-message-fit proof excludes
instruction exhaustion for every admitted current-format batch. A typed
preflight failure terminalizes through the durable failure lane and is included
in `C_driver`. An unexpected invariant trap or platform fault rolls its message
back and is explicitly outside the normal residual guarantee; 0.229 makes no
false claim that a receipt can be persisted by a trapping message. Patch 5
fault injection must prove every representable malformed/control mismatch is
caught before mechanical Apply and becomes typed. A repeated mechanical trap
is an implementation defect handled by the surviving 0.225 watchdog and
authorized diagnostics, not a normal bounded recovery outcome.

The right-hand side never contains historical row population `N`, historical
commit count, or already retired journal history. The design bounds replicated
work and callback count, not wall-clock duration; timer delivery and scheduler
fairness remain platform assumptions.

## Mechanical Heap Bound

Effect count alone is not a heap proof. Let `O_f` be retained effects in family
`f`, and let all coefficients below be fixed implementation constants or
measurement-backed upper bounds:

```text
H_overlay
  <= H_fixed
   + sum(alpha_f * O_f)
   + beta * Y
   + gamma * B
   + delta * S

H_callback_peak
  <= H_overlay
   + H_head_scan_max
   + H_decode_max
   + H_preflight_max
   + H_apply_max
   + H_retire_max
```

`H_overlay` includes keys, values, tombstones, map/container overhead, and
position metadata. `H_callback_peak` additionally includes the maximum
38-head selection scan, encoded batch decode, complete preflight, Apply, and
retirement scratch space. Patch 5 freezes the family coefficients and maxima
using maximum legal records, bytes, fanout, and skew. Neither formula may
contain historical population or retired history.

## Physical Stable Allocation Bound

Logical retained bytes are not by themselves proof of bounded physical stable
allocation. With current journal tail chunk size `C = 65,536`, for retained
batch envelope lengths `y_b` the exact number of live chunk entries is:

```text
K = sum(ceil(y_b / C))
K <= B + floor(Y / C)
```

Patch 3 implements the exact control and allocation shape. Patch 5 binds
stable-map node and allocator high-water to fixed `K_max`, fixed controls, and
memory-manager overhead. Evidence repeatedly fills to the ceiling, drains to
zero, and refills, proving that retired chunk/map capacity is reused and
historical commit count does not keep increasing stable allocation. The current
stable B-tree allocator has reusable free nodes, while the virtual-memory
high-water does not shrink; the required result is therefore a fixed
post-ceiling high-water, not physical shrinkage after drain. Raw non-gzipped
Wasm remains the authoritative footprint measure; gzip is secondary context.

## Canonical Constants And Drift Guards

Numeric values in this design describe reviewed relationships; implementation
has one code owner for each value. Codec and generator code must expose or
derive canonical constants for:

- journal batch format and fixed header bytes;
- `APP_MEMORY_ID_MIN` and `APP_MEMORY_ID_MAX`;
- the three canister-level control allocations;
- the four-allocation journaled-store width;
- `JOURNAL_TAIL_CHUNK_BYTES`; and
- every Gate 1, backlog, driver, instruction, and heap maximum.

Accepted 0.228.3 evidence derives its 85-byte version-2 header from an actual
encoded empty envelope; current mechanical tests derive the 93-byte version-3
header without retaining a version-2 encoder or decoder. Tests also derive
`S_max_absolute` from the canonical allocation constants and fail if generator
allocation roles or codec fields drift. The design, codec, and generator do not
maintain independent magic numbers.

## User Outcome

- Healthy normal operation continuously retires journal and overlay debt.
- A successful write never relies on a later history-sized upgrade to pay its
  accumulated debt.
- An individually oversized commit retains its existing non-pressure error.
- An individually valid write that would exceed the fixed backlog tuple fails
  before durable mutation with one typed retryable pressure result.
- Queries, mutation preparation, constraints, identities, validation, and
  migrations observe the latest committed live value while older complete
  batches become canonical.
- Same-key, delete/reinsert, schema, identity, validation, migration, and index
  effects cannot expose intermediate canonical state.
- A future current-format startup has a fixed residual callback and replicated

## Complexity And Maintenance Gate

Demonstrated need: bounded complete-batch callbacks do not bound the number of
callbacks created by database-lifetime debt. Online folding alone also cannot
bound a writer that outpaces it or safely retire overlay authority. Tail-local
sequence plus fixed store order cannot prevent online starvation, and generated
current stores alone cannot preserve allocation authority across later store
removal/addition.

Simplest retained shape: extend the existing engine, driver, commit admission,
journal tail, and live overlay owners. The static maximum of 38 stores makes a
bounded owner-local sum simpler than another persisted global aggregate. One
database commit sequence in the current envelope is simpler than a scheduler
cursor or persisted round-robin state. One bounded no-reuse registry is simpler
than reconstructing allocation history or permitting authority resurrection.

Canonical new owner: the convergence-format control owns only the current
format identity, database commit-sequence high-water, and at most 38 active or
retired store quartets. Owner-local tail controls remain the singular backlog
facts.

State-space delta: one current aggregate-control shape, family-specific
volatile provenance, one cumulative within-limit/pressure outcome, and an
online-debt extension of existing lifecycle states, plus one monotonic database
commit sequence and one bounded no-reuse store registry. It adds no
configuration, scheduler cursor, engine, scheduler, compatibility format, or
global duplicate aggregate.

Promotion fails if implementation introduces a second fold route, cursor,
database-global duplicate aggregate, full-tail startup or admission scan,
unbounded overlay retention, after-marker pressure rejection, independently
encoded admission bytes, reusable retired allocations, compatibility formats,
or an activation patch before all pressure, fit, heap, fairness, and liveness
evidence is frozen.
