## Decision Summary

0.233 closes the production-adoption gaps found while Toko evaluated durable
mutation jobs for collection-wide rarity changes.

The existing job architecture remains the authority:

```text
start fixed intent
  -> bounded Forward pages
  -> stable Verify pass
  -> Completed or RestartRequired
  -> sequence-checked acknowledgement
```

Commit-marker atomicity, exact successful-request replay, bounded row-count
steps, current-format recovery, and stable Verify completion remain valid. The
gap is liveness: a page can fail safely before commitment while also being
guaranteed to select the same unexecutable work on every retry.

0.233 makes five bounded corrections:

1. keep the frozen statement timestamp for canonical SQL/business meaning, but
   use one current advance-message timestamp for writer-managed `updated_at`;
2. bound Forward by exact staged bytes as well as keys and rows, and bound
   Verify by scanned bytes as well as keys;
3. add idempotent sequence-zero cancellation, bounded retained-job inventory,
   and reserved integrity-job capacity;
4. make mutation-job Verify observe the target entity's mutation revision
   rather than the whole physical store; and
5. expose bounded target-failure reasons and lifecycle metrics, then repair the
   current-authority documentation.

The line does not add rollback for already committed pages, atomic multi-job
transactions, mutation-job owners, application quotas, caller-selected page
sizes, a second executor, or legacy continuation support.

## Junior Mental Model: Safety Is Not Liveness

The original implementation was safe in the narrow transaction sense. If a
Forward page failed, neither its target rows nor its next progress record
committed. Retrying after response loss also returned the exact successful
receipt without running the page twice.

Those properties did not prove that every valid Active job could eventually
advance. Two examples show the distinction.

### Frozen-time loop

```text
message 1: start job at time 10
           retain statement timestamp 10

message 2: insert or update a matching row at time 20
           row.updated_at becomes 20

message 3: advance job
           try to write row.updated_at = 10
           managed timestamp validation rejects 10 < 20
           no row, checkpoint, sequence, or receipt commits

message 4: retry the same sequence and request key
           no successful receipt exists to replay
           execute the same row again with timestamp 10
           fail in the same way
```

Freezing one logical statement timestamp was reasonable. Reusing it as the
physical commit timestamp for every later page was not. The same value had
accidentally become both business time and storage time.

### Count-bounded but byte-unbounded loop

```text
Forward chooses at most 56 matching rows
  -> structural writer stages key + before row + after row
  -> staged data exceeds 16 MiB
  -> writer rejects before progress commits
  -> retry chooses the same oversized prefix
```

Fifty-six small rows are bounded work. Fifty-six rows that may each approach
4 MiB are not. The implementation bounded the number of units without bounding
the cost of those units.

These failures also invalidate the operational assumption that every Active
job will eventually become terminal. An Active record cannot currently be
acknowledged, so a deterministic pre-commit failure can retain one of the 64
shared progress slots indefinitely.

## Promotion Findings

The current source confirms every promoted concern:

- mutation-job start captures `Timestamp::now()` once and every Forward page
  passes that retained value into structural mutation execution;
- managed timestamp validation rejects an operation timestamp older than the
  row's existing `created_at` or `updated_at`;
- Forward admission stops only at 208 examined keys or 56 candidate rows;
- one persisted row may contain up to 4 MiB while structural mutation staging
  admits at most 16 MiB across key, canonical before-row, and after-row bytes;
- mutation jobs have no owner quota, sequence-zero cancellation, or partial-job
  abandonment surface, and Active records cannot be acknowledged;
- all retained job families share the 64-record progress allocation;
- Verify scans one entity but compares the store-wide journal data-mutation
  revision before and after each page;
- revision drift and residual work use the same persisted Forward-restart
  transition;
- structural execution failures are flattened to `TargetMutationFailed` and
  traversal failures to `TargetQueryFailed`;
- mutation-job execution records only generic rows-scanned metrics despite the
  accepted 0.223 design requiring lifecycle observability; and
- current-authority documentation still describes 224/56 pages and the removed
  caller-custodied continuation flow, while runtime authority is 208/56.

The historical 0.229 changelog is correct. Its 0.229.0 entry records the
original 224/56 policy and its 0.229.1 entry records the later 208/56 policy.
0.233 must not rewrite that history.

## No-Build Gate

### Demonstrated need

Toko already reached IC0522 while eagerly applying rarity-change effects. Its
PocketIC audit reproduced a valid mutation job becoming permanently unable to
advance after a later matching managed-timestamp row appeared. Source review
also proves a deterministic wide-row staging failure and unrelated-entity
Verify restarts.

This is a correctness-of-service and capacity-recovery problem, not a
speculative convenience request.

### Smallest sufficient outcome

Repair the existing Forward/Verify coordinator and shared progress store:

- separate statement time from managed-write time;
- add fixed engine-owned byte budgets beside existing count budgets;
- allow removal only when the retained record proves no page ever committed;
- narrow Verify's revision authority to its target entity; and
- preserve bounded typed operational evidence at the existing error and metric
  boundaries.

### Simpler alternatives

- **Retry the same failed advance:** insufficient because both identified
  failures are deterministic and retain the same sequence/checkpoint.
- **Lower the fixed row count:** insufficient because row sizes vary and any
  count above one can exceed the current staging envelope.
- **Use only the frozen timestamp:** preserves one visible time but violates
  managed timestamp monotonicity after later writes.
- **Use `max(frozen, existing_updated_at)` per row:** avoids regression but
  makes writer-managed time depend on the row instead of the actual committing
  message and can hide that a later write occurred.
- **Allow acknowledgement of every Active record:** unsafe because the name
  would conceal abandonment of already committed pages.
- **Add a rollback log:** disproportionate; Forward pages are intentionally
  independently committed and a rollback protocol would add a second durable
  mutation engine.
- **Add atomic multi-job start:** unnecessary once an application can cancel a
  proven-unadvanced first job after a later start fails.
- **Add mutation-job owners and quotas:** no canonical application owner exists
  at the trusted session boundary. A fixed integrity reservation protects
  system work without adding owner state.
- **Keep the store-wide revision because it is conservative:** correctness-safe
  but liveness-hostile under normal multi-entity traffic, which is Toko's
  deployed shape.
- **No build:** leaves valid production workloads permanently retrying and can
  consume shared progress capacity indefinitely.

## Goals

- Every normally admissible matching row remains executable after later
  messages update or insert matching rows.
- Every Forward and Verify advance has fixed count and byte/work bounds owned
  by the engine.
- A page never checkpoints past a matching candidate whose mutation did not
  join that page's commit.
- A sequence-zero job with no committed effects can be removed safely and
  idempotently.
- Integrity work retains capacity even when application-owned progress families
  fill their admitted share.
- Unrelated entity writes do not restart Verify.
- Target-entity writes during Verify still prevent false completion.
- Operators can distinguish timestamp regression, staging-budget rejection,
  revision drift, residual work, replay, completion, cancellation, and
  acknowledgement without seeing SQL, keys, or values.
- Exact successful-request replay, marker recovery, accepted-schema authority,
  and current version-1 persisted formats remain fail-closed.

## Non-Goals

- No rollback of target rows committed by earlier Forward pages.
- No `abandon_mutation_job` for partially applied jobs in this line.
- No atomic reservation or start of multiple mutation jobs.
- No cross-entity Toko workflow coordinator.
- No job owner field, caller principal, tenant quota, application namespace, or
  bearer authorization.
- No caller-selected key, row, byte, time, or instruction budget.
- No alternate large-row executor or spill-to-stable-memory path.
- No SQL grammar, fixed-intent eligibility, accepted-schema, source-row, index,
  or cursor-format change.
- No change to generic revision-strict `ResumableJob` or exhaustive-read proof
  semantics.
- No compatibility alias, old continuation decoder, dual batch policy, or
  predecessor mutation-job record path.

## Maintained Invariants

1. A mutating Forward page commits target journal effects and the exact next
   mutation-job record through one commit marker or commits neither.
2. A zero-update Forward page, Verify page, terminal transition, cancellation,
   and acknowledgement change only bounded progress state.
3. Exact replay is available only for a successfully committed request and
   returns the retained byte-equivalent receipt without rescanning.
4. A failed pre-commit attempt may observe a later message timestamp on retry;
   it has no committed result whose timestamp must be replayed.
5. The canonical intent retains statement/business meaning and accepted-schema
   identity; runtime state never reconstructs authority from generated models.
6. Forward checkpoint authority ends at the last row whose nonmatching result
   or admitted mutation is covered by the committed transition.
7. `Completed` still requires clean target-entity Verify exhaustion at one
   unchanged target-entity revision.
8. Cancellation succeeds only when the retained current record itself proves
   sequence zero and zero committed effects.
9. No operational response exposes SQL, predicate bytes, patch bytes, primary
   keys, row values, or private continuation bytes.
10. Every pre-1.0 persisted/runtime format discriminator remains exactly
    version `1` and recognizes only the current canonical form.

## Canonical Authority And Flow

```text
start SQL admission
  -> CanonicalMutationIntent(statement_timestamp, target, scope, patch, policy)
  -> current mutation progress record

advance Forward
  -> capture one advance_timestamp
  -> target-entity ordered scan
  -> writer-owned exact staging charge
  -> count + byte prefix packer
  -> structural commit + progress replacement

advance Verify
  -> target-entity revision capture/compare
  -> key + raw-row scan-byte budget
  -> continue Verify, restart Forward, or complete

operations
  -> state / bounded inventory / cancel-unadvanced / acknowledge-terminal
```

| Concern | Canonical owner |
| --- | --- |
| Frozen SQL/business time | Canonical mutation intent |
| Managed `updated_at` time | One non-replay Forward advance message |
| Key and row count limits | Mutation-job batch policy |
| Exact staged-byte charge | Structural mutation writer |
| Candidate/checkpoint prefix | Mutation-job Forward scanner/packer |
| Verify scan-byte accounting | Mutation-job Verify scanner |
| Target-entity revision | Journal tail row-mutation authority |
| Zero-effect cancellation proof | Current mutation progress record |
| Global/family capacity | Shared excluded progress store |
| Error reason registry | Mutation-job public error contract |
| Lifecycle events | Existing metrics event/sink boundary |

No layer reparses SQL, estimates writer bytes independently, reconstructs
entity identity from generated models, or infers lifecycle reason from error
text.

## Statement Time And Managed-Write Time

The retained `operation_timestamp` is redefined and named in documentation as
the **statement timestamp**. It remains part of canonical intent identity and
continues to own any frozen SQL/business semantics.

Every non-replay mutating Forward advance captures exactly one
`advance_timestamp = Timestamp::now()` after request replay and authority
validation. All rows committed by that page use that timestamp for
writer-managed `updated_at`.

The advance timestamp is not added to canonical intent or the progress record:

- a successful advance already persists its materialized after-rows and exact
  receipt through the commit marker;
- exact replay does not re-execute and therefore does not need the timestamp;
- a failed pre-commit attempt has no committed outcome, so a later retry may
  correctly use the later retry message's timestamp; and
- Verify tests patch satisfaction, not equality to a historical managed
  timestamp.

One page uses one timestamp rather than one timestamp per row. This keeps rows
within a committed page consistent and avoids repeated clock reads.

Managed timestamp validation remains strict. A row whose managed timestamp is
later than the current IC message time indicates broken managed-time authority,
not ordinary concurrent work. When read-only page preparation detects that
case, it persists terminal
`RestartRequired(ManagedTimestampRegression)` without target-row effects. The
job can then be acknowledged instead of remaining Active on a deterministic
failure.

The batch-policy identity increments its timestamp-policy component so an
older retained execution policy cannot silently continue under the new
semantics.

## Dual Count And Byte Page Budgets

### Forward policy

Forward retains the existing maxima of 208 examined keys and 56 staged row
updates. It adds a fixed engine-owned staged-byte maximum no larger than the
structural writer's 16 MiB batch envelope.

The exact charge is owned by the structural writer and includes the same bytes
the writer later validates:

```text
raw primary key bytes
+ canonical before-row bytes
+ materialized after-row bytes
```

The mutation-job packer consumes that writer-owned charge. It must not copy the
formula or maintain a second staging limit.

For each visited row:

1. a nonmatching or already-satisfied row may advance the committable
   checkpoint;
2. a matching row is materialized sufficiently to obtain the exact writer
   charge;
3. if the row and cumulative page charge fit, the mutation joins the page and
   the committable checkpoint advances through it;
4. if adding it would exceed the byte or row budget, scanning stops before the
   candidate and the committed checkpoint remains before it; and
5. any already admitted prefix may commit normally.

The row that causes a stop is not lost. The next advance revisits it as the
first uncommitted candidate.

The fixed page envelope must admit at least one maximum valid current row under
the exact key/before/after charge. A focused boundary assertion freezes this
relationship. If future row or writer limits make one valid row impossible to
admit, read-only page preparation persists terminal
`RestartRequired(CandidateExceedsBatchPolicy)` without target-row effects
rather than leaving an unchanged Active checkpoint loop.

Index fanout does not change the row-image staging formula. Maximum accepted
index fanout receives separate native and PocketIC instruction evidence. If it
exceeds message headroom, the engine-owned row maximum is reduced or an
existing writer-owned effect budget is reused; 0.233 does not add a caller
knob or approximate index-byte estimator.

### Verify policy

Verify retains the 208-key maximum and adds a fixed scan-byte budget charged
before full row decoding:

```text
raw key bytes + persisted raw row bytes
```

If the next row would exceed the remaining budget after earlier rows made
progress, Verify persists only the checkpoint through the admitted prefix. The
budget must admit one maximum valid row. Verify still stops immediately when a
residual matching row is found and restarts Forward.

### Policy identity

The current batch-policy identity explicitly binds:

- Forward key maximum;
- Forward row maximum;
- Forward staged-byte maximum;
- Verify key maximum;
- Verify scan-byte maximum;
- packing/checkpoint semantics; and
- statement-versus-managed-time semantics.

Numeric limits participate directly rather than relying only on a comment or
manual version bump. The private continuation format version remains `1`.

## Sequence-Zero Cancellation And Capacity Recovery

The trusted session surface adds:

```text
cancel_unadvanced_mutation_job(job_id, expected_sequence) -> Result<(), MutationJobError>
```

Cancellation is permitted only when all current-record facts hold:

- the record is `Active`;
- `expected_sequence == actual_sequence == 0`;
- phase is `Forward`;
- keys-scanned, rows-updated, and Verify-restart totals are zero;
- no last receipt exists; and
- the current continuation is a decodable current-format initial continuation.

A prior batch-policy identity does not prevent cancellation when every
zero-effect fact holds. Cancellation does not execute that policy; it only
proves and removes the initial record.

These facts prove that start persisted intent but no target page ever
committed. Cancellation removes only the progress record. It does not need a
target commit marker and cannot roll back a row.

An absent record returns success so retry after a lost cancellation response
is safe. A retained nonzero sequence fails with `StaleSequence`; terminal jobs
remain owned by acknowledgement. Removing the record makes the application-
owned job ID reusable, so applications must not race cancellation with a new
start using the same ID.

### Bounded inventory

The shared progress-store owner adds one trusted read-only inventory. Because
the complete allocation contains at most 64 retained records, it returns one
bounded result without introducing a cursor format.

The result reports:

- global retained count and hard limit;
- reserved integrity headroom;
- retained count by job family; and
- for each current decodable record, family, application-owned ID, bounded
  lifecycle status, and sequence when that family has one.

It exposes no SQL, owner principal, predicate, patch, row, key, continuation,
or idempotency key. Authorization remains application-owned around the trusted
Rust API; the job ID is not bearer authority.

### Integrity reservation

The global hard limit remains 64. New non-integrity progress records are
admitted only while at least eight global slots remain available for integrity
work. Eight reuses the existing integrity per-owner bound and adds no persisted
quota or owner identity.

Existing retained records are never evicted. If an upgrade observes more than
the new non-integrity admission threshold, those records remain valid, but new
non-integrity starts fail until usage drops below the threshold.

## Entity-Scoped Verify Revision

The store-wide journal data-mutation revision remains canonical for generic
store-wide proof consumers. Mutation-job Verify switches to a new
entity-scoped revision owned by `JournalTailStore`.

For every journal batch containing an ordinary row put/delete or other current
row mutation, the journal derives the affected entity tag from the canonical
row key and advances the revision for each distinct affected entity to that
batch's mutation sequence. A batch touching multiple entities advances each of
those entities atomically with the batch.

Entity revision metadata:

- is bounded by the current entity-tag authority rather than by mutation
  count;
- survives journal folding;
- is advanced idempotently during marker replay/recovery;
- is validated against journal sequence authority;
- uses one current version-1 canonical encoding; and
- is not reconstructed from generated models or by scanning target rows.

Forward exhaustion captures the predicted post-commit revision for the target
entity when the page mutates rows, or the current target-entity revision for a
zero-update page. Verify compares only that target entity before and after its
scan.

Therefore:

- a write to the target entity restarts Forward;
- a residual matching target row restarts Forward;
- a write to another entity in the same physical store does not restart the
  job; and
- schema/allocation/policy drift continues to use the existing terminal
  authority checks.

When both residual work and revision drift are visible in one page, residual
work is the primary bounded diagnostic reason because it is already sufficient
to restart Forward. Metrics may count the simultaneous revision change as a
secondary fact, but no new combined lifecycle state is added.

## Errors And Observability

`MutationJobError` remains a closed bounded enum. Target execution failures gain
one safe reason registry rather than exposing `InternalError`, diagnostic text,
SQL, or values. Initial reasons are limited to demonstrated boundaries:

```text
StagingByteBudgetExceeded
ExecutionBudgetExceeded
Other
```

Managed timestamp regression and a single candidate that cannot fit the
current batch policy are detected during read-only preparation and become the
two new bounded terminal `MutationJobRestartReason` variants described above.
They are not ordinary retryable target errors.

Known page-packing overflow must normally be prevented before writer execution;
the staging reason remains as a fail-closed diagnostic if writer and packer
authority ever diverge. Tests assert that ordinary wide-row packing never
reaches it.

Lifecycle metrics distinguish:

- start inserted and exact-start replay;
- state load;
- advance exact replay;
- Forward and Verify step commitment;
- Forward-to-Verify transition;
- Verify restart due to revision drift or residual work;
- completion and terminal restart;
- sequence-zero cancellation;
- terminal acknowledgement;
- target failure reason;
- keys, rows, and bytes charged in the step;
- checked cumulative totals;
- retained record bytes; and
- shared capacity used, limit, reservation, and family count.

Job ID, idempotency key, SQL, entity values, keys, and continuations are never
metric labels or payloads. Phase, operation, outcome, family, and bounded reason
may be low-cardinality labels; sequence, totals, bytes, and capacity are numeric
observations.

0.233 deliberately does not add a Verify-restart reason field to the retained
public receipt. Exact replay would make that field part of the persisted
last-receipt format, creating an incompatible progress-record hard cut solely
for observability. The existing receipt continues to expose phase and restart
count; bounded metrics distinguish the cause. This is the smallest sufficient
operational outcome.

## Multi-Job Coordination And Partial Effects

Toko remains the owner of the cross-entity rarity-change coordinator. Its safe
setup sequence is:

```text
start Tier job
start Scoring job
if Scoring start fails before either advances:
    cancel Tier at sequence zero
otherwise:
    advance jobs according to application policy
```

Atomic multi-job start is deferred. It would require a new bounded request,
multi-intent admission transaction, replay identity, and failure surface for a
workflow IcyDB does not otherwise own.

Partially applied abandonment is also deferred. Once sequence is nonzero,
earlier pages may have committed real row effects. Removing the record without
a durable terminal audit would make an incomplete operation look cleaned up,
while retaining an `Abandoned` record would not immediately recover capacity.
No production adopter currently requires that tradeoff after the timestamp and
packing wedges are removed.

If a future demonstrated incident requires abandonment, it must be a separate
design that explicitly states:

- previously committed rows are not rolled back;
- authorization remains external to the trusted session API;
- exact expected sequence and lost-response behavior;
- terminal audit and capacity-release semantics; and
- interaction with replay, recovery, inventory, and application repair.

## Public, Persisted, And Compatibility Impact

Public/trusted Rust additions are limited to:

- sequence-zero cancellation;
- bounded progress inventory/capacity state; and
- bounded target-failure reason codes; and
- terminal `ManagedTimestampRegression` and
  `CandidateExceedsBatchPolicy` restart reasons.

They are not generated public canister endpoints automatically. Applications
must authorize any wrapper on every call.

Persisted/runtime changes are limited to entity-scoped journal revision
metadata and batch-policy identity. No source row, accepted schema, ordinary
journal row record, index, cursor, or generated model encoding changes.

Before `1.0.0`, all affected formats remain version `1`. New current-form
metadata and policy replace their prior meaning in place. No predecessor
decoder, translator, fallback revision, dual policy, or legacy fixture is
retained. Older Active mutation jobs encounter the changed batch-policy
identity and transition through the existing typed `BatchPolicyChanged`
restart path rather than executing under mixed semantics.

## Security And Trust Boundaries

- Mutation-job APIs remain trusted session APIs and add no automatic public
  method.
- Application authorization is checked outside IcyDB on every operation.
- A job ID identifies work but grants no authority.
- Inventory is bounded by the existing 64-record hard cap and omits semantic
  payloads.
- Failure reasons are closed numeric/variant identities, never rendered
  internal errors.
- Entity revisions are internal convergence evidence and are not caller
  supplied.
- Page limits are fixed engine policy and cannot be raised by a caller.
- Persisted decoding remains bounded, fallible, and current-form only.

## State-Space And Complexity Delta

The demonstrated liveness gap requires one new durable authority: an
entity-tag mutation revision beside the existing store-wide revision. It
combines only with journaled stores and existing Forward/Verify phases. Missing,
malformed, future, or nonmonotonic revision metadata fails closed at the journal
owner.

Other additions do not create new lifecycle states:

- statement time and advance time replace one overloaded timestamp meaning;
- byte budgets extend existing fixed batch policy;
- two bounded terminal reasons reuse the existing `RestartRequired` state;
- cancellation removes only the already-representable initial state;
- inventory observes existing retained state;
- integrity reservation changes start admission without persisting a quota;
- diagnostic reasons classify existing failures; and
- lifecycle metrics observe existing transitions.

The implementation must not add a second scan, patch materializer, byte
estimator, revision source, progress allocation, or job state machine. The
expected complexity shape is a narrow increase in journal metadata and public
operations, offset by removal of ambiguous timestamp authority and elimination
of deterministic retry loops.

## Validation Strategy

### Owner-local proofs

- statement timestamp remains stable in canonical intent while managed
  timestamps use one advance-message value;
- exact staging and scan-byte accounting accepts exact limit and rejects
  max-plus-one;
- checkpoint never advances through an excluded matching candidate;
- cancellation validation derives entirely from the current record closure;
- entity revisions advance for exactly the row-mutated entity tags; and
- public failure reasons are closed, bounded, and independent of error text.

### Cross-message and PocketIC proofs

- start, advance time, insert/update a later matching managed row, advance to
  stable completion, and replay a committed request;
- several wide valid rows cross a page byte boundary, commit as multiple
  prefixes, revisit the boundary row, and converge without duplication or
  omission;
- maximum accepted index fanout remains below the named instruction ceiling;
- a first job cancels safely when a second setup call fails;
- unrelated entity traffic during every Verify page does not prevent
  completion; and
- target-entity traffic still restarts and eventually converges when traffic
  quiesces.

### Recovery proofs

- every mutating failpoint preserves target/progress atomicity;
- entity revisions and progress replacement recover together to one exact
  current transition;
- fold/reopen retains target-entity revision authority;
- cancellation and acknowledgement are idempotent after response loss; and
- older policy identity becomes typed `RestartRequired(BatchPolicyChanged)`.

### Negative-space guards

- no caller-custodied mutation continuation surface returns;
- no caller-selected page budget appears;
- no generated-model runtime fallback is added;
- no mutation-job owner/quota or partial abandonment state appears;
- no raw SQL/value/key/idempotency data reaches inventory, error reasons, or
  metric labels; and
- no old progress, continuation, revision, or policy decoder remains.

### User-owned validation

Repository-wide suites and the release workflow remain user-owned under
`AGENTS.md`. Each landing patch runs only its focused native, package, canister,
and named integration checks. Closeout reports skipped full validation rather
than running it automatically.
