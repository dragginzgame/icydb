## Decision Summary

0.226 changes the journal from an indefinitely accumulating deferred
canonicalization log into a bounded write-ahead tail that converges continuously
during normal canister operation.

One catalog-native convergence engine owns both:

- steady-state background folding after successful commits; and
- residual startup recovery after an interruption or upgrade.

Normal commits retain the current marker-authorized atomic publication model.
After a commit publishes its live effects and clears its marker, generated
runtime wiring schedules bounded convergence. The convergence engine reads the
canonical predecessor directly, validates one immutable journal batch through a
durable validation phase, applies records through a durable apply phase,
advances the fold watermark, and clears only the batch it proved complete.

The active live data, index, and schema projections remain query authority while
the canister process is running. Online convergence updates canonical stable
state underneath those projections without clearing or rebuilding them. After
an upgrade, volatile projections are absent, so ordinary database work remains
gated until any residual tail has converged.

Startup becomes explicit:

```text
DatabaseStartupState {
    Ready,
    Recovering,
}
```

Loading `db!()` from an ordinary endpoint observes this state but does not
silently execute a recovery page. Only a dedicated replicated update driver
advances convergence. Applications can inspect readiness and defer their own
scheduler restoration without racing IcyDB's continuation timer. A convergence
failure is returned as a typed error, not represented as a third successful
state.

Exact entity and index-prefix cardinality become durable derived evidence tied
to canonical fold progress. Existing populated stores initialize the new
current metadata through an explicit bounded build job outside `post_upgrade`;
planning falls back conservatively until publication. Startup never scans rows
or indexes to reconstruct cardinality.

0.226 exposes no recovery batch-size configuration, compaction mode, alternate
startup policy, or compatibility path. Limits are fixed engine policy measured
against the predecessor.

## User Outcome

For a healthy canister under ordinary write load:

- journal debt stays within one fixed engine-owned backlog envelope;
- an unchanged-schema upgrade performs bounded control work and schedules at
  most a fixed number of residual convergence pages;
- total time to database readiness is independent of historical row, index, and
  journal counts;
- application timers can distinguish `Recovering` from `Ready` before touching
  database state, without a guessed grace period or generic-conflict retry;
- a query never spends instructions on recovery work whose mutations will be
  rolled back;
- application callbacks never share one recovery page's instruction envelope;
- canonical IDs, rows, accepted schema, identity ranges, indexes, and
  validation jobs remain exact across interruption and upgrade; and
- populated stores regain exact cardinality-driven planning without a startup
  scan.

For a canister upgraded with legacy accumulated journal debt from the accepted
predecessor, the same convergence engine drains that existing tail in bounded
messages. The one-time drain may take work proportional to the inherited tail,
but it occurs outside `post_upgrade`, remains explicitly observable, and leaves
the canister in the continuously converged steady state. No later upgrade may
recreate unbounded historical debt.

## Incident And Current Limitation

The motivating populated Toko Feed canister retained 16,715 historical journal
batches. On 0.222.2, its unchanged-schema installation/upgrade message exceeded
the IC's 300-billion-instruction limit before reaching the former full index
rebuild. The separate 0.222.3 regression made 20 IcyDB store tests fail with
accepted-enum `RUNTIME_CORRUPTION`; an isolated snapshot-restore test reproduced
that failure, ruling out parallel-test interference.

0.223 correctly removed the false accepted-enum corruption result and made
startup fold work durably record-resumable. The complete 0.223.0 dependency
family passes the isolated snapshot restore and all 28 IcyDB-backed Toko store
tests. An in-place populated upgrade completed in 14.5 seconds while retaining
37 accepted entities, scheduler rows, canonical Aquapolis data, provider
evidence, and representative populations of 294 canonical items, 119 variants,
175 Pokemon metadata aggregates, 1,139 Magic extension rows, and 1,382 replayed
provider records plus their observations. Recovery pages stayed close to the
configured 20-billion-instruction envelope.

That repair established the right immediate safety boundary, but the retained
tail also demonstrated the missing readiness contract. A read-only `SHOW
ENTITIES` and application scheduler queries attempted recovery work until they
exceeded the local five-billion-instruction query limit instead of cheaply
returning a typed pending result. A zero-delay application timer shared the
generated timer executor with IcyDB continuation work and the combined message
exceeded its 40-billion-instruction limit before a conflict could be returned.
Toko therefore waits one minute and retries only the recovery conflict before
restoring its scheduler. That workaround is evidence for an engine contract,
not application policy that 0.226 should preserve.

The audit found five remaining structural limitations:

1. normal writes still append debt that is folded only when recovery is
   entered, so time-to-ready continues to grow with journal history;
2. generated `db!()` returns success while recovery is pending and application
   zero-delay timers can run between IcyDB pages;
3. later records are validated only after earlier records in the same logical
   batch may already have changed canonical state;
4. populated stores reopen with exact entity and prefix cardinality
   unavailable, permanently disabling maintained cardinality-dependent planning
   until another full reconstruction path runs; and
5. the nominal recovery byte envelope is checked after a complete batch has
   already been decoded and deliberately admits an oversized first unit.

These are not reasons to restore full startup rebuilding or relax corruption
checks. They demonstrate that canonical convergence, readiness, validation,
and exact derived metadata need one bounded current design.

## No-Build And Alternatives Gate

### Demonstrated need

The need is established by a real canister exceeding the IC instruction limit,
read-only queries spending their complete instruction budget on discarded
recovery work, a generated-timer/application-timer message exceeding its
instruction limit before it could return the recovery conflict, an ever-growing
journal tail under maintained writes, and the deliberate loss of cardinality
evidence after populated-store reinitialization.

### Rejected: raise the upgrade instruction limit

The IC limit is external, and a larger limit would leave work proportional to
database history. It would not correct readiness, validation ordering, or
cardinality loss.

### Rejected: keep startup-only resumable folding as the final design

Bounded pages protect each message but do not bound the number of pages required
for a normal future upgrade. The database remains unavailable while the
historical tail drains.

### Rejected: restore automatic whole-store rebuild

Rebuilding every row and index is not required when journal transitions preserve
canonical semantics. It duplicates mutation authority, scales with database
size, and can hide genuine inconsistency instead of reporting it.

### Rejected: synchronously fold every complete commit before returning

A logical commit can contain more row/index work than the maintained
single-message recovery page. Requiring full canonical fold before response
would move the same instruction failure into ordinary writes. The bounded
background driver reuses one convergence engine without changing caller batch
limits into an implicit synchronous compaction promise.

### Rejected: caller-selected compaction or recovery tuning

There is one safe policy derived from current commit and IC execution limits.
Configuration would multiply startup, backlog, cursor, and cost states without
a deployment-specific semantic need.

### Rejected: reconstruct cardinality from generated models

Generated models do not own accepted runtime indexes or stored rows. Exact
cardinality is derived only from canonical accepted data and index entries.

## Canonical Authority And Ownership

Authority order is:

1. accepted schema snapshots own entity, field, index, relation, constraint,
   and layout semantics;
2. the commit marker owns interrupted publication authority;
3. the journal sequence and immutable batch bytes own ordered committed effects;
4. the convergence cursor owns validated progress through one exact batch;
5. canonical data, index, and schema stores own folded stable state;
6. the fold watermark owns the boundary between canonical state and remaining
   journal authority;
7. durable cardinality generations own exact derived counts only when bound to
   the published canonical fold boundary; and
8. generated canister wiring owns timer scheduling, never recovery semantics.

The implementation should converge on one internal operation:

```text
inspect next batch
        |
        v
bounded Validate phase --corruption--> typed failure, no canonical mutation
        |
        v
bounded Apply phase ----interruption--> exact durable record cursor
        |
        v
watermark + tail clear + derived-generation publication
```

Startup and online compaction call this operation with different visibility
guards. They do not implement separate record decoders, index derivation, or
fold semantics.

The current large recovery module must not absorb every new responsibility.
Implementation should separate:

- startup/readiness orchestration;
- journal convergence state and phase transitions;
- record validation and prepared canonical application;
- journal control storage/codec; and
- generated timer driving.

This is a responsibility split around one flow, not permission to introduce a
second engine.

## Steady-State Journal Convergence

### Commit relationship

Normal mutation publication remains:

```text
prepare -> persist marker -> publish journal/live effects -> verify -> clear marker
```

After marker clear, the runtime records that convergence work exists and
ensures one background driver is scheduled. Scheduling is idempotent. It is not
part of mutation success and cannot cause an already committed user mutation to
be reported as failed.

### Online fold

Online convergence must:

- read canonical row predecessors without consulting a newer live overlay;
- derive canonical index transitions from accepted schema authority;
- preserve the live overlay and tombstones used by current requests;
- fold schema, identity, constraint-validation, migration, row, and index
  records in journal order;
- update exact durable cardinality in the same record transition when its
  generation is ready;
- leave planner-visible live indexes ready while their complete live overlay is
  present; and
- advance the watermark only after the complete batch Apply phase succeeds.

The online path never clears all live maps, rebuilds all indexes, or scans the
database.

### Backlog admission

Journal tail metadata maintains bounded aggregate batch, record, and byte facts
without scanning stored batches. Patch 1 freezes an outstanding backlog ceiling
as a small fixed multiple of one maximum admitted commit.

Before publishing a new marker, mutation admission proves the resulting tail
fits that ceiling. If it cannot, the mutation returns a typed retryable resource
or convergence-pressure error before marker persistence and schedules the
driver. The engine does not accept the write and hope a later upgrade can pay
unbounded debt.

Existing predecessor debt above the new steady-state ceiling remains recoverable
through the dedicated startup driver. The ceiling governs new commits; it does
not make an already accepted predecessor store unreadable.

## Explicit Startup And Readiness

### Startup probe

Generated initialization performs only bounded control inspection:

- database-format admission;
- commit-marker presence;
- fold cursor and tail aggregate metadata;
- accepted-schema checkpoint identity; and
- current cardinality-generation state.

It does not decode a journal batch, traverse a row or index, or run a convergence
page inside an ordinary query.

If no marker, cursor, or tail remains, generated schema reconciliation proceeds
through its maintained bounded exact-match path and publishes `Ready`.

If recovery work remains, generated wiring publishes `Recovering`, schedules
the replicated driver when the current execution context can durably do so, and
returns without applying the generated schema fragment.

### Application contract

The public trusted Rust surface exposes a bounded readiness query, conceptually:

```text
database_startup_state() -> Result<DatabaseStartupState, Error>
```

No canister endpoint is automatically exported. Applications may expose or use
the state inside their own authorized lifecycle code.

Ordinary data operations while the state is `Recovering` return a dedicated
retryable recovery-pending error. The error remains distinct from corruption,
schema conflict, optimistic mutation conflict, and generic storage failure.

Applications that restore timers or cached state after upgrade follow:

```text
Ready      -> restore application state
Recovering -> reschedule bounded readiness check
Err        -> surface/log the typed failure and stop retrying blindly
```

IcyDB does not persist application callbacks, invoke user hooks, or own
application scheduler policy.

### Driver behavior

Only replicated update execution advances convergence. Queries observe state
and fail cheaply while pending; they never perform stable writes that will be
discarded.

The driver is single-flight and trap-aware. A failed or out-of-instructions
callback must not leave a volatile `scheduled=true` flag with no surviving
timer. The chosen IC timer mechanism and recovery after callback trap require a
real-canister proof before Patch 2 completes.

A typed convergence error is cached for the current process so subsequent
database entrypoints surface the same failure rather than returning generic
pending forever. An upgrade may retry against new code; no durable legacy error
translation is introduced.

## Two-Phase Durable Batch Validation

The current record cursor becomes a current-only phase cursor:

```text
ConvergenceCursor {
    batch_sequence,
    batch_id,
    batch_digest,
    record_count,
    phase: Validate | Apply,
    next_record_ordinal,
}
```

### Validate

Validate is read-only with respect to canonical data, indexes, schema, identity,
and cardinality. It checks, in bounded pages:

- batch header, version, sequence, identity, count, and digest;
- one-store routing and storage capabilities;
- accepted-schema and candidate-schema identity;
- every row key, payload, field wire, and commit schema fingerprint;
- constraint-validation job/index closure;
- identity range ownership;
- schema/migration plan identity when compiled; and
- the complete record family and final batch closure.

Only after every record validates does the cursor transition durably to
`Apply { next_record_ordinal: 0 }`.

### Apply

Apply recomputes one prepared canonical transition at a time from the immutable
batch and canonical predecessor. All fallible preparation happens before store
mutation. The store-level mutation for one prepared record must then be
infallible under the validated backend contract, or be owned by an exact
marker/cursor transition that can reconcile both before and after states.

After each record, the cursor advances durably. After the final record, one
transition publishes the next fold watermark, clears the cursor, and deletes
the completed batch. A canister upgrade or message interruption at every
boundary resumes exactly.

Corruption in a later record is therefore detected before any record in that
batch mutates canonical state. Strict detection is retained for malformed
bytes, missing derived evidence, invalid index transitions, incompatible
formats, and impossible cursor state.

## Truthful Physical And Instruction Bounds

The page contract distinguishes three limits:

1. maximum encoded journal batch bytes;
2. maximum cumulative batch bytes admitted by one page; and
3. maximum records and instructions advanced by one page.

A page never claims a byte bound smaller than a batch it has already decoded.
The journal store must inspect a bounded raw header containing length, identity,
and digest before materializing records. If the predecessor storage wrapper
decodes values on lookup, it must retain the raw envelope long enough to enforce
admission first rather than reporting an after-the-fact estimate.

Patch 1 decides whether the existing maximum commit batch is the single decode
unit or whether physical journal chunks are required. Chunking is permitted
only if measurement proves the existing maximum cannot fit the fixed memory and
instruction safety envelope. A new chunk format is not added merely to preserve
the historical 8 MiB label.

Instruction stopping uses the IC performance counter with a measured
single-record overshoot allowance. The frozen page ceiling must leave enough
headroom below the IC message limit for batch decode, cursor publication,
watermark clear, timer/runtime overhead, and the largest admitted record/index
fanout.

Host tests use explicit deterministic record/batch limits and do not pretend a
zero host instruction counter proves the Wasm instruction gate.

## Durable Exact Cardinality

Entity cardinality and user-index prefix cardinality are derived evidence, not
independent schema or data authority.

Their durable generation binds:

- database incarnation;
- store identity;
- accepted schema root or index identity set;
- canonical fold watermark/epoch; and
- a current cardinality format version.

Counts update with canonical row/index fold transitions. A generation is
planner-visible only when every required count is complete and synchronized
with its canonical boundary. Missing, building, stale, malformed, or
incompatible generations return `None` to planning and are reported by
integrity inspection where appropriate; they never synthesize a count.

### Existing populated stores

The predecessor has no durable cardinality generation for populated canonical
maps. 0.226 initializes a current `Building` generation and schedules an
explicit bounded build outside startup. The build:

- scans canonical accepted rows/index entries in stable key order;
- writes candidate counts to isolated current storage;
- checkpoints exact physical progress;
- binds to the canonical mutation/fold revision;
- discards the isolated candidate and restarts from a fresh checkpoint when
  that revision changes;
- publishes only after a complete clean pass; and
- remains optional for correctness while conservative planning fallback is
  active.

This is a build of new current derived evidence from maintained canonical
authority, not a decoder or translator for a legacy cardinality format.

Empty stores retain exact zero counts without a scan. Once a populated current
generation is published, later normal convergence maintains it incrementally so
future upgrades do not rebuild it.

If 0.225 introduces a planner-statistics store, 0.226 must extend or reuse its
canonical storage and generation contract. It must not add a second parallel
cardinality/statistics authority. Exact cardinality remains integrity-bound
evidence, not an advisory estimate.

## State-Space Delta

0.226 adds only demonstrated states:

| Axis | Current values | Owner | Invalid combinations |
| --- | --- | --- | --- |
| Startup readiness | `Ready`, `Recovering`, or typed failure | startup coordinator | `Ready` is impossible with marker, cursor, or tail debt |
| Convergence phase | `Validate`, `Apply` | durable convergence cursor | Apply cannot begin before complete digest-bound validation |
| Backlog admission | within ceiling or retryable pressure | journal/commit admission | marker publication is rejected before exceeding the ceiling |
| Cardinality generation | `Building`, `Ready`, or unavailable/error | data/index cardinality store | planner cannot consume unbound or stale counts |

There is no user configuration axis. Online and startup execution reuse one
convergence engine. The former startup-only full-tail fold path disappears, and
startup row/index scans remain deleted.

## Persisted And Public Hard Cuts

Potentially breaking changes are explicit:

- the fold cursor gains a digest and phase and moves directly to one current
  format;
- journal tail aggregate controls and cardinality generations add current
  persisted records/allocations;
- exhaustive Rust matches must handle `DatabaseStartupState` and the dedicated
  recovery-pending error kind;
- `db!()` no longer performs a recovery page as an incidental side effect of an
  ordinary query or endpoint; and
- write admission may return typed convergence pressure before marker
  publication when the fixed tail ceiling is reached.

No old cursor decoder, dual tag map, fallback cursor reconstruction, or
compatibility alias is added. A predecessor canister with an unfinished old
fold cursor must complete that current recovery before the 0.226 upgrade or
recreate development state, as specified during release preparation.

The record-tag shift identified in the 0.223 audit is not reassigned to 0.226.
If 0.223 has not been published, the additive tag should be corrected in that
line without a compatibility layer. If it is part of the accepted predecessor,
0.226 treats the predecessor tag map as current input and does not casually
renumber it.

No canister endpoint is automatically added. Any public types remain
Candid/Serde-compatible for applications to embed in their own authorized
surface.

## Non-Negotiable Invariants

1. Accepted schema snapshots remain runtime authority.
2. One convergence engine owns online and startup journal folding.
3. A normal commit never succeeds unless its marker and journal/live effects
   satisfy the existing atomic publication contract.
4. New commits cannot grow tail debt beyond the fixed steady-state envelope.
5. Startup `Ready` requires marker absence, no fold cursor, no remaining tail,
   and successful generated-schema reconciliation.
6. Queries never execute recovery mutations that will be rolled back.
7. No canonical record in a batch changes before the complete Validate phase
   succeeds.
8. The convergence cursor is bound to exact batch identity, digest, count,
   sequence, phase, and ordinal.
9. Partial Apply progress is never query-visible after startup and remains
   shadowed by the complete live projection during online convergence.
10. Canonical row and derived-index transitions advance together according to
    accepted schema semantics.
11. A watermark never advances beyond an unapplied record.
12. Exact cardinality is consumed only at a synchronized canonical generation.
13. Missing cardinality causes conservative planning, never a guessed count.
14. Whole-store integrity work remains explicit, bounded, and resumable outside
    `post_upgrade`.
15. Genuine malformed data, index, journal, cursor, schema, or identity state
    retains typed corruption reporting.
16. No recovery path reconstructs runtime authority from generated models.
17. Production convergence and timer paths contain no panicking operations.
18. Raw non-gzipped Wasm remains the authoritative footprint measure.

## Scope

0.226 includes:

- fixed baseline and failure/cost authority for current startup and tail debt;
- explicit startup readiness and a dedicated replicated driver;
- two-phase digest-bound durable convergence cursors;
- one shared online/startup canonical fold engine;
- fixed backlog admission and automatic convergence scheduling;
- truthful batch, record, byte, instruction, and overshoot limits;
- durable exact entity and prefix cardinality generations;
- a bounded initial cardinality build for populated predecessor stores;
- focused generated-canister lifecycle and interruption evidence;
- populated Toko-shaped scale and ID/count/index preservation evidence; and
- instruction, stable-memory, raw Wasm, Candid, and complexity reporting.

0.226 does not add:

- caller-selected recovery or compaction settings;
- application callbacks, scheduler custody, or persisted user hooks;
- a second commit, journal, schema, index, or statistics authority;
- automatic whole-store repair during startup;
- relaxed corruption or exact-index checks;
- a legacy fold-cursor decoder or record-tag compatibility map;
- replacement of the live runtime projection/cache model;
- generic database maintenance jobs unrelated to convergence/cardinality;
- durable mutation, aggregate, ingestion, rollup, or partition features owned by
  other minor lines;
- the low-risk accepted-enum fast-path helper cleanup; or
- changes to successful query results, row IDs, or accepted schema meaning.

### Retained Adjacent Toko Ingestion Feedback

The populated Toko Feed investigation against locked IcyDB 0.223.0 found no
correctness failure across relations, uniqueness, pagination, or 1,821 stored
records, but observed ten-card pages grow from roughly 5--8 seconds during
Alpha to 19--25 seconds during Legends. The provider contributed only a
one-second intentional delay. Revised took roughly nine minutes and Legends
roughly eleven minutes. This is a performance signal, not yet an isolated
IcyDB defect or an accepted 0.226 requirement.

Toko owns the first response: avoid replaying the complete cache before every
new-set refresh, skip unchanged `ProviderRecord` replacements, preload repeated
collection, parent-set, record, and observation lookups, use the maintained
same-entity mutation batch after one bounded preflight, and consider a cache
manifest handshake for an already-warm canister. After those changes, repeat
the populated benchmark and separate new-row cost from identical replay cost.

Retain the following possible IcyDB follow-up if that benchmark still shows
per-new-record cost growing with table size:

- a bounded same-entity batch upsert or insert-if-absent operation keyed by a
  primary or unique index, with `Inserted`, `Updated`, or `Unchanged` reported
  per row;
- state-neutral byte-identical replacement, avoiding journal and index churn;
- operation diagnostics for selected index, candidate keys visited, rows
  decoded, relation checks, journal bytes, and instruction cost; and
- resumable upsert/import only if bounded batching remains insufficient.

Patch 1 should preserve a Toko-shaped ingestion baseline, and patch 6 should
compare bounded new-row and identical-replay batches at increasing population
and journal histories. The 0.226 acceptance question is only whether cost stops
growing with historical journal debt; generic ingestion and UPSERT design stay
outside this line unless separately reviewed and authorized.

- instructions spent by a query and update that arrive while recovery is
  pending;
- instructions spent by the bounded readiness query itself and by an ordinary
  read rejected while `Recovering`, with proof that neither decoded a journal
  batch or mutated stable state;
- recovery-driver and application-timer instructions when independently ready,
  interleaved, and scheduled at the same timestamp;
- normal mutation instructions before any convergence work;
- online convergence instructions per record family and maximum index fanout;
- entity and prefix-cardinality availability before and after upgrade;
- planner route/entry/row-read effects when cardinality is unavailable;
- compiler and final raw Wasm for maintained dynamic and typed subjects;
- deterministic gzip as secondary context;
- stable bytes for journal controls, tails, cursor, and any current statistics
  authority; and
- production Candid bytes and exported method modes.

The line must freeze numeric gates before implementing the behavior they judge.
At minimum:

- `post_upgrade` startup control work remains far below the IC message limit and
  does not grow with rows/indexes/history;
- one convergence page retains a fixed safety margin below the IC message
  limit including worst measured record overshoot;
- one generated recovery-driver callback retains a fixed safety margin below
  the maintained timer-message envelope, including scheduling and trap-recovery
  overhead;
- steady-state backlog implies a fixed maximum number of residual startup pages;
- query-side pending checks perform no stable mutation or journal batch decode;
- query-side state/pending checks remain safely below the reproduced
  five-billion-instruction query ceiling and do not grow with retained tail;
- application callbacks do not inherit recovery-page work in the same generated
  timer callback;
- no maintained canister exceeds the per-patch or line-level raw Wasm review
  thresholds accepted from the predecessor; and
- cardinality persistence/build reports both planner benefit and stable/write
  amplification rather than treating restored route selection as free.

The reproduced five-billion query ceiling, 20-billion page observation,
40-billion timer ceiling, and 300-billion IC message limit are investigation
context, not permission to preserve an unmeasured envelope.

## Validation Matrix

Focused evidence must cover:

### Startup and scheduling

- empty install and unchanged-schema upgrade;
- marker-only, tail-only, cursor-only, and marker-plus-tail recovery;
- query, update, and application zero-delay timer while `Recovering`;
- read-only `SHOW ENTITIES` and an application scheduler query return the
  dedicated pending error without advancing or decoding recovery;
- readiness polling needs no fixed delay and no matching of the generic
  recovery-conflict category;
- an application timer and IcyDB driver scheduled for the same timestamp run in
  separate bounded callbacks rather than sharing one instruction envelope;
- timer callback success, typed error, and trap/out-of-instructions simulation;
- duplicate scheduling and driver reentry;
- generated schema application only after convergence reaches `Ready`; and
- no automatic public endpoint or method-mode drift.

### Validation and apply

- corruption in the first, middle, and last record;
- batch digest, count, sequence, ID, store, and cursor mismatch;
- interruption before/after cursor creation, phase transition, each record,
  watermark publication, batch clear, and readiness publication;
- row put/delete, accepted-schema publication, identity advance,
  constraint-validation job/index records, and migration records when enabled;
- one logical batch spanning multiple messages and upgrades; and
- strict index/data verification after completion.

### Online convergence

- append during Validate and Apply of an earlier batch;
- multiple updates to one key across batches;
- deletion followed by reinsertion;
- live overlay precedence while canonical state catches up;
- backlog ceiling and pre-marker pressure rejection;
- canister idle long enough to quiesce;
- upgrade before and after quiescence; and
- no full live-map clear or whole-store traversal.

### Cardinality

- exact empty zero without scan;
- populated predecessor with unavailable metadata;
- bounded build checkpoint reopen and canister upgrade;
- canonical revision drift and eventual clean publication;
- incremental insert, replace, delete, candidate index, and schema changes;
- stale, malformed, short, overcounted, and undercounted metadata;
- exact planner admission after publication and conservative fallback before;
  and
- Deep integrity interaction without startup repair.

### Real integration

- a Toko-shaped population at least as large as the motivating fixture;
- inherited journal history larger than one page;
- canonical first/last ID samples and complete entity counts before/after;
- all 37 accepted entities plus at least 294 canonical items, 119 variants, 175
  Pokemon metadata aggregates, 1,139 Magic extension rows, and 1,382 provider
  records with their observations;
- retained scheduler rows, canonical Aquapolis data, and provider evidence;
- scheduler restoration delayed until `Ready`;
- no application-owned one-minute recovery window or generic-conflict retry;
- repeated ordinary writes followed by another same-schema upgrade; and
- raw Wasm, instructions, stable growth, Candid, and method modes.

Repository-wide suites remain push-owned. Each landing patch runs only its
focused package, target, canister, compatibility, formatting, warning-denied
lint, and invariant checks.

## Complexity And Maintenance Gate

The intended simplification is architectural:

- one convergence engine replaces startup-only historical canonicalization;
- journal debt becomes bounded rather than database-lifetime state;
- readiness becomes explicit instead of inferred from timer ordering;
- complete batch validation precedes canonical mutation; and
- exact cardinality survives upgrades without startup reconstruction.

The accepted complexity cost is:

- one phase bit and digest in the convergence cursor;
- one explicit readiness result;
- fixed backlog aggregate controls and pressure outcome; and
- one durable cardinality generation/build lifecycle.

Patch 1 must reject the design or rescope it if the current predecessor already
provides an equivalent authority, if continuous convergence requires a second
commit flow, or if cardinality persistence duplicates a 0.225 statistics owner.

Every implementation handoff reports:

- independent states added or removed;
- duplicate flows added, removed, or retained with reason;
- files and approximate line delta;
- delivery domains and whether width is semantic or mechanical;
- instruction, stable-memory, and raw Wasm deltas;
- current debt resolved, accepted, or added; and
- whether the implementation shape became simpler, stayed neutral, or became
  more complex.

## Audit Finding Disposition

| Audit finding | 0.226 disposition |
| --- | --- |
| Journal debt recurs and readiness remains history-sized | Included: continuous convergence plus fixed backlog admission |
| `db!()` readiness is implicit and races application timers | Included: explicit state and replicated-only driver |
| Read-only queries execute recovery until the query instruction limit | Included: constant-cost state/pending admission with no recovery decode or mutation |
| Generated recovery and application timers share one instruction envelope | Included: independently bounded driver callback and application-timer interleaving proof |
| Applications need a guessed delay and generic-conflict retry | Removed from the application contract: poll explicit readiness and restore only at `Ready` |
| Later corruption can be found after earlier canonical apply | Included: digest-bound Validate then Apply phases |
| Populated-store cardinality disappears after upgrade | Included: durable generation and bounded initial build |
| The 8 MiB claim does not bound pre-admission decode | Included: truthful raw-envelope and page limits |
| Missing real populated lifecycle regression | Included in every owner patch and Patch 6 closeout |
| Accepted-enum fast-path whitelist duplication | Excluded as unrelated low-risk owner-local cleanup |
| 0.223 journal record-tag shift | Must be decided in its owning published/predecessor line; no 0.226 compatibility layer |

## Promotion Gate

This design becomes implementation authority only when:

1. predecessor closeouts and explicit 0.226 authorization satisfy the planning
   gates at the top of this document;
2. Patch 1 confirms the demonstrated gaps still exist;
3. the actual predecessor owner inventory selects one convergence and one
   cardinality authority;
4. backlog, batch, page, instruction, stable-byte, and raw Wasm gates are frozen;
5. persisted/public hard cuts and development-state recreation requirements are
   reviewed; and
6. the six-patch tracker is accepted without combining independent outcomes or
   splitting direct fallout into micro-patches.

Until then, this document is proposed future design authority only. It must not
be cited as permission to change runtime, persisted state, public APIs, Candid,
generated wiring, changelog entries, or package versions.
