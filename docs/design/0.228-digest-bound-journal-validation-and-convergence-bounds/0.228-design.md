## Planning Status And Authorization

Patch 1 was a no-build investigation. Its IC evidence selects one mandatory
producer-side correction: Patch 2 may add the fixed canonical joint-admission
bound below. It must not change the journal format, recovery engine, persisted
controls, generated Candid, or scheduler. Later convergence patches remain
unauthorized.

The investigation must prefer the smallest protocol that is truthful on the
IC. Durable paged validation, physical journal chunk redesign, a prepared log,
and the former seven-patch plan are not presumed outcomes. The pre-1.0 format
transition is an unconditional hard cut: no compatibility decoder, upgrader,
repair bridge, or dual-format interval is permitted.

## Decision Summary

Patch 1 selects the first IC-safe shape in this order:

1. one synchronous batch message performs raw inspection, complete read-only
   validation, complete preparation, mechanical Apply, and terminal retirement;
2. only if complete prepared Apply cannot fit with reviewed headroom, one
   validation message publishes a fingerprint-bound cursor and later messages
   Apply prepared bounded pages; or
3. if validation alone cannot fit even after selecting the smallest useful
   admitted maximum, stop for a new product decision.

No record mutates canonical state until the exact batch has passed validation.
The one-message shape is preferred because IC rollback then removes all
intra-batch persisted progress and replay states.

Patch 1 has now proved that unchanged admission cannot simply reuse the current
fold loop as the one-message shape: a maintained 1,024-row batch with 64
accepted secondary indexes is emitted by one 22,135,010,413-instruction update,
then requires 56,121,104,133 current recovery-work instructions across three
messages. Current Apply alone therefore exceeds the IC's 40-billion external
message limit. This does not prejudge how much owner-prepared mechanical Apply
can remove, but it makes the comparison and a smaller hard-cut admission policy
mandatory before a cursor is selected.

The demonstrated need for an additional fixed admission axis is that
row and byte bounds do not constrain derived-index work. The simplest
alternative to persisted progress is a canonical compile-time joint work bound
owned by structural commit preparation, expressed over admitted rows and exact
prepared transitions. Patch 2 freezes that bound as:

```text
W = 4R + I + 4A + 4P
W <= 16,384
```

`R` is the number of prepared canonical row transitions, `I` is the number of
actual prepared index-store mutations including counter-neutral candidate and
reverse-index work, `A` is the number of identity-range applies, and `P` is
zero or one for an exact mutation-progress successor. Every addition and
multiplication is checked. The producer charges each row as soon as its owner
has prepared the exact transition and rejects the first excess with typed
`RUNTIME_BOUNDARY_MUTATION_BATCH_COMMIT_WORK_EXCEEDED` before commit-marker or
journal publication. It does not finish preparing an already-disqualified
high-fanout batch.

The fixed value leaves more than 15 billion instructions beneath the IC's
40-billion replicated-message limit across the measured admitted shapes. It
admits at most 4,096 zero-index transitions, 240 inserts with 64 actual
secondary-index mutations, and 124 worst-case
64-index replacements that remove and insert every key. The existing 16-MiB
staged-input and 1-MiB result bounds remain independent, so one wide row is not
penalized merely for its bytes and cheap batches retain materially higher row
capacity. The new axis adds one scalar accumulator and one public diagnostic,
but no caller setting, mode, persisted state, cursor, or execution route.

Only the second shape needs a replacement cursor, provisionally:

```text
ApplyCursor {
    batch_sequence,
    batch_id,
    batch_fingerprint: [u8; 32],
    record_count,
    next_record_ordinal,
    next_record_offset,
}
```

There is no durable Validate phase or validation ordinal. If paged Apply is
necessary, the cursor binds sequence, ID, fingerprint, count, next Apply
ordinal, and the exact byte offset of that record's tag. It never reconstructs
missing fields from the batch, a generated model, or a retired cursor shape. If
complete prepared Apply fits, there is no replacement cursor at all.

The selected replacement journal envelope exposes bounded header facts before record
materialization: encoded length, sequence, batch ID, marker ID, record count,
and fingerprint. Raw inspection reads only the fixed header from stable chunks,
then rejects oversized, truncated, mismatched, or unsupported envelopes before
assembling or allocating the complete batch.

Validation is read-only with respect to canonical data, indexes, schema,
identity, validation jobs, cardinality, journal bytes, and recovery controls.
It either returns a typed failure with no write, continues into completely
prepared same-message Apply, or publishes the optional Apply cursor after the
complete batch has been proved.

Apply prepares every transition admitted by the selected batch or page from the
immutable batch and canonical predecessors before it mutates state. Every fallible
decode, lookup, schema check, key derivation, allocation/capacity proof,
serialization, and cursor encoding occurs before mutation. The prepared page,
its canonical effects, and exact next cursor are committed synchronously. The
terminal message publishes the watermark and clears the exact cursor and batch
without ever losing an unapplied record or replaying a non-idempotent
transition.

## IC Execution Model Authority

This is an IC recovery protocol, not a conventional process/WAL protocol. Its
boundaries and evidence follow the replicated execution model:

- recovery contains no `await`, yield, callback, remote call, or re-entrant
  application execution;
- an upgrade cannot interrupt a currently executing message;
- trap or instruction exhaustion rolls back the complete replicated message;
- a normally returned `Err` does **not** roll back earlier writes, so every
  normal fallible operation must complete before the first mutation;
- Apply is paged only if measured stable-memory work, Wasm heap pressure, or
  replicated-message instructions prevent the complete prepared batch from
  fitting with reviewed headroom;
- header inspection must bound heap allocation before stable chunks are joined;
- measurements use Wasm performance counters, Wasm heap-page high-water plus a
  deterministic maximum-live-byte proof, stable reads/writes/growth, and worst-
  unit instruction overshoot; host wall time and a zero host counter are not
  evidence; and
- recovery instruction probes drive the real generated watchdog and read its
  canonical `ic-timers` scheduler/work measurements only after completion; a
  test-admin observer may project those inert measurements but must not invoke
  the private driver, add a second execution route, or replace timer ownership;
- timer-owned start/end Wasm and stable page extents may replace host-side
  before/after extent sampling when available, but neither form proves exact
  sub-page live bytes; owner-derived retained/temporary byte accounting remains
  mandatory; and
- each ceiling reserves measured headroom for the 0.225 driver, timer callback,
  cursor/terminal publication, runtime overhead, and the largest admitted
  record fanout.

A database or host-filesystem analogy cannot introduce interruption states
that the IC cannot durably expose, nor may IC rollback be used to excuse a
normal post-mutation error path.

## Fingerprint And Envelope Contract

The selected format uses an unkeyed 32-byte SHA-256 batch fingerprint. It detects
accidental corruption, stale cursor reuse, and batch substitution. It is not an
authenticator against an actor able to rewrite the batch and recompute the
fingerprint.

The fingerprint is:

```text
SHA-256(
    b"ICYDB-JOURNAL-BATCH-FINGERPRINT\0" ||
    canonical envelope bytes with the 32-byte fingerprint field omitted
)
```

The preimage therefore covers the envelope magic and version, exact encoded
length, batch ID, marker ID, sequence, record count, and canonical record bytes.
The fingerprint field itself is excluded. Patch 1 must freeze the exact offset,
integer byte order, header size, maximum values, and allocation proof before
runtime work is promoted. This is one new current envelope, not a wrapper over
the retired encoding.

Encoding and verification update SHA-256 incrementally while canonical bytes
are emitted or bounded stable chunks are copied. They do not allocate a second
fingerprint preimage or reserialize a decoded batch. In the paged fallback,
successful validation also freezes the exact sequence's chunks until terminal
retirement: append cannot overwrite them, ordinary sessions remain startup-
gated, and only terminal cleanup may delete them. Each Apply page matches the
fixed header to the cursor but does not rehash or decode the entire preceding
record prefix. This immutability proof is required to avoid history-dependent
IC instructions without weakening the validation result.

## User Outcome

- Corruption in the final record is reported before the first canonical record
  changes.
- If Apply pagination is needed, recovery resumes at every Apply ordinal
  without guessing; otherwise a failed batch message restarts from immutable
  bytes under whole-message rollback.
- No page decodes a batch whose raw envelope already violates its byte limit.
- Batch, cumulative bytes, record count, instruction work, index fanout, and
  worst-record overshoot are separate measured bounds.
- A trap or instruction exhaustion rolls back its complete message; an upgrade
  between successful validation, Apply, and terminal messages resumes exactly.
- Startup readiness continues to use the 0.225 driver and state contract.

## Canonical Ownership

Authority order is:

1. accepted schema snapshots own record semantics;
2. the commit marker owns interrupted publication into the journal;
3. immutable current envelope bytes plus sequence, ID, count, and fingerprint own
   the batch being converged;
4. an optional `ApplyCursor` proves complete validation and owns Apply ordinal
   progress only when paged Apply is measured as necessary;
5. canonical data, index, schema, identity, and validation-job stores own folded
   state;
6. the fold watermark owns the highest completely applied sequence; and
7. the accepted 0.225 driver owns replicated invocation only.

The convergence engine owns one flow:

```text
preferred: raw inspect -> Validate -> prepare complete batch -> Apply -> retire
fallback:  raw inspect -> Validate -> Apply cursor -> prepared Apply pages
                                           -> atomic terminal retirement
```

Journal storage owns raw envelope access and control codecs. Record-family
owners supply validation and prepared canonical transitions. The convergence
coordinator orders them; it does not absorb schema, identity, or index
semantics.

## Validate Contract

Validate proves in one bounded read-only message:

- envelope magic/version, encoded length, sequence, ID, count, and fingerprint;
- one-store routing and required storage capabilities;
- accepted and candidate schema identity where relevant;
- every row key, row payload, field wire, and commit schema fingerprint;
- exact derived index transition evidence;
- constraint-validation job and candidate-index closure;
- identity range owner, expected high-water, count, and record ordering;
- current schema/migration plan identity when that record family is enabled;
- complete known record-family coverage; and
- canonical final batch closure with no trailing or missing bytes.

Validation reads canonical predecessors only when needed to prove that Apply
can be prepared under the same startup-gated fold order. It performs no write
before preparation. If paged Apply is necessary, its only write is the final
Apply cursor publication after every record succeeds.

Current producers must also prove why validation needs no logical shadow
database. Structural batches reject duplicate target keys and journal one final
transition per row key after validating the complete final-row overlay.
Accepted-schema publication orders the schema record before either bounded
user-index changes bound to the exact accepted-after fingerprint or one
validation-job transition; the codec rejects those two suffix families when
combined. Constraint validation and migration record families carry their
job/plan/candidate evidence and visit each owned key once. Patch 1 must
enumerate and test these producer invariants for every record family. If any
later record semantically depends on an earlier unapplied effect that cannot be
checked from its own evidence, promotion stops; 0.228 must not add an overlay,
prefix replay, or durable prepared shadow to paper over the gap.

## Preparation Strategy Gate

Patch 1 compares two complete-message Apply strategies against the same
validated immutable batch:

1. retain every owner-prepared transition until validation and preparation are
   complete, then apply the retained values mechanically; and
2. during complete validation, prove every semantic, decoding, serialization,
   allocation, stable-capacity, and ordinary failure condition, then stream a
   mechanically infallible record-family Apply without retaining a second full
   transition graph.

The second strategy is not allowed to mean "call the current fallible Apply and
assume it succeeds." Patch 1 must inventory every current `Result` branch in
row/index/schema/identity/job/migration Apply, identify the owner that can prove
it before mutation, and show that the post-validation operation has no normally
returned error. Platform traps remain whole-message rollback. If making
streaming Apply genuinely mechanical requires duplicate semantic authority or
more complexity than bounded retained preparation, retain preparation instead.

The promotion record reports instructions, Wasm heap-page high-water, checked
maximum live bytes, stable work, raw Wasm implications, and owner/state-space
complexity for both strategies. Memory pressure created only by retaining a
second batch representation cannot by itself justify paged Apply before the
streaming alternative is measured.

## Terminal Failure Visibility

0.228 adds no failure state. A normally returned validation corruption follows
the accepted 0.225 path in the same replicated driver message:

```text
convergence returns StartupRecoveryFailure::JournalStore
  -> driver classifies the typed persisted corruption as JournalRecovery
  -> driver captures the exact incarnation/allocation/tail proof/cursor binding
  -> existing bounded StartupFailureReceipt is published
  -> driver returns Terminal
  -> publishing callback returns success and Stop
  -> later startup_state() returns that matching typed failure
  -> lifecycle reconciliation retires the watchdog; any callback already
     invoked against the failure returns invariant_failure and Stop
```

Receipt publication and the `Terminal` result are one synchronous update. A
publication error returns retryable failure without falsely claiming a durable
terminal state. The receipt is stale only when the existing bound authority
changes under an authorized transition. Patch 1 must reproduce this chain with
a late-record corruption fixture before runtime promotion.

## Apply And Terminal Contract

Apply starts only after complete validation, in the same message where possible
or from a fingerprint-bound cursor when paging is necessary. For the complete
batch or each fallback page it:

1. uses the same validated decoded batch in the preferred shape, or reads the
   bounded fallback record under the cursor fingerprint;
2. prepares all admitted transitions and any exact encoded next cursor;
3. proves stable capacity and performs all normal fallible work before mutation;
4. applies the page mechanically under record-family idempotency proofs; and
5. publishes the exact next cursor or completes terminal retirement in the same
   synchronous message.

No normal `Err` is reachable after step 4 begins. A trap remains possible at a
platform or stable-memory boundary, but the IC rolls back the whole Apply
message, including its cursor write.

After the final prepared transition, the same bounded synchronous message
validates the next epoch, publishes the watermark, clears any cursor, and
retires the batch. Its durable states are only before the message and after
successful return:

| Boundary | Separately durable? | Reason |
| --- | --- | --- |
| Complete validation / optional Apply cursor | Only in the paged fallback | The preferred shape continues into prepared Apply in the same message |
| One prepared Apply page / next cursor | Only in the paged fallback | Each page ends one successful update message |
| Apply mutation / cursor write within that page | No | No `await`; trap rolls the complete message back |
| Watermark / cursor clear / batch retirement | No | One synchronous terminal message with no successful partial return |

Trap failpoints around individual writes remain required rollback evidence, but
they are not extra persisted protocol states. A retained batch at or below the
watermark is cleanup-only only if a future implementation deliberately splits
terminal cleanup; the reduced protocol does not do so.

## Truthful Bounds

The engine freezes distinct fixed limits for:

- maximum encoded bytes in one journal batch;
- maximum cumulative encoded batch bytes admitted by one page;
- maximum records advanced by one page;
- maximum instructions used by one page;
- maximum derived row/index/schema fanout of one admitted record; and
- measured overshoot after the last safe instruction check.

Raw inspection precedes record allocation. The page reserves measured headroom
for header and fingerprint work, record decode, maximum prepared fanout, cursor
publication, terminal transitions, driver/runtime overhead, and overshoot.
Host tests use explicit deterministic limits and do not treat a zero host
performance counter as instruction evidence.

Patch 1 tested whether lowering admission was sufficient, and Patch 2 freezes
the joint prepared-effect policy above without lowering the independent staged-
byte limit. It retains the 4,096-row zero-index maximum and the exact largest
single operation promised by maintained row and derived-effect limits while
preventing row count from concealing excessive fanout. Historical maxima are
not a compatibility promise before 1.0.

Patch 1 measures legal producer outputs, not a Cartesian product of unrelated
maxima. It constructs the worst feasible combined batch for each mutually
exclusive producer family, then selects the greatest measured instruction and
live-memory cases:

- structural mutation: the maximum coexisting operation count, encoded rows,
  identity-range records, accepted index fanout per row, and one-store routing
  that the maintained precommit path can actually publish;
- accepted-schema index replacement: the largest accepted candidate together
  with the exact old/new user-index key deletion and insertion chunks;
- accepted-schema job transition: the largest accepted candidate with its one
  permitted validation-job put/delete and no user-index chunks;
- constraint validation: its job record plus the maximum candidate-index entry
  set admitted in the same batch; and
- schema migration where enabled: the largest source row and derived index
  effects that the maintained migration page can co-publish.

Each fixture must be built through the maintained producer/admission authority.
It may not hand-construct an impossible mixed record set. Separate scalar
maxima remain explanatory context only; they cannot establish the final bound.

The complete-message live-memory comparison includes fixed-header bytes,
complete raw batch assembly, the decoded representation, canonical predecessor
reads, the retained prepared graph for that strategy, and the largest temporary
value for streaming Apply. Instruction evidence includes stable chunk reads,
SHA-256 work, validation, preparation/proof, Apply, terminal retirement, driver
entry/exit, and worst-record overshoot.

If complete Apply does not fit, the fallback evidence separately measures the
necessary validation/Apply double decode. A paged Apply implementation must not
decode or replay the entire record prefix on every page. This is binary:

- paged Apply is promotable only if the current self-delimiting record encoding
  plus `next_record_offset` permits bounded reading and decoding of the next
  record directly from the existing 64 KiB chunks; and
- if the decoder needs earlier records or the complete batch, paged Apply is not
  promotable.

Wasm heap cannot retain a decode across messages. An offset table, record index,
or new physical addressing format is a separately reviewed format decision and
is not implied by the fallback. History-dependent `O(R * pages)` decode work is
prohibited.

Physical chunk redesign or durable Validate pages require a separate product
decision. They may be proposed only if exact Wasm evidence proves both that:

1. complete validation alone cannot fit the reviewed instruction and memory
   envelope; and
2. reducing the admitted maximum to the smallest useful contract still cannot
   fit.

Until both are demonstrated, the existing stable chunks remain physical
storage only and one logical batch remains the validation unit.

## No-Build And Alternatives Gate

- Raising the page threshold does not make post-decode byte accounting truthful.
- Validating each record immediately before Apply does not protect earlier
  records from later corruption.
- One-message complete validation, preparation, Apply, and retirement is tested
  first because the admitted batch has a fixed maximum and IC rollback removes
  all intra-batch durable states when it fits.
- Copying decoded records into a second durable prepared log duplicates journal
  authority and write cost.
- A legacy cursor decoder or inferred phase makes two formats current before
  1.0 and is prohibited.

Patch 2 freezes the smallest useful structural admission policy. The remaining
investigation freezes the envelope encoding and exact IC message boundaries;
its promotion result is either the reduced one-shot protocol, an Apply-only
fallback explicitly selected from evidence, or a stop for a new product
decision. It must not silently promote durable validation or invent a parallel
envelope.

## Scope

0.228 includes:

- one current raw journal envelope and bounded inspection path;
- no cursor when a complete batch fits, otherwise fingerprint, sequence, ID,
  count, Apply ordinal, and direct record-offset cursor binding;
- complete read-only Validate before Apply;
- complete-message Apply where it fits, otherwise prepared paged canonical
  Apply without history-dependent prefix decoding;
- interruption safety at real successful-message boundaries;
- fixed truthful batch, cumulative-byte, record, instruction, fanout, and
  overshoot limits; and
- focused host and real-canister evidence for the convergence engine.

## Non-Goals

0.228 excludes:

- online convergence after normal commits;
- post-commit scheduling or live-overlay visibility rules;
- tail aggregate metadata, backlog pressure, or pre-marker rejection;
- exact entity or index-prefix cardinality;
- application readiness changes beyond reusing 0.225;
- caller-selected convergence limits;
- general repair, compaction modes, or integrity jobs;
- durable validation pages, a validation cursor, or a prepared shadow log
  without a separately reviewed promotion decision; and
- approximate statistics, planner policy, ingestion, rollups, or partitions.

## Persisted And Public Hard Cuts

- `FoldRecordCursor` is removed when complete prepared Apply fits. If Apply
  pagination is measured as necessary, it moves directly to the sole current
  `ApplyCursor` format.
- The journal envelope moves directly to the current fingerprint-bearing form with
  bounded pre-materialization header inspection.
- Every 0.227-to-0.228 canister transition, including production, is reinstall/
  recreation-only. No 0.227 canister is an eligible in-place upgrade subject,
  even when its observed tail and cursor are empty. The release procedure and
  release notes must reject/forbid upgrade mode and require an explicit backup/
  export decision before destructive reinstall. Installing 0.228 over retained
  predecessor bytes is unsupported and fails closed; corrupt old tails are not
  rescued by 0.228.
- Unknown, malformed, retired, or mismatched cursor/envelope forms fail typed
  and closed.
- No legacy decoder, cursor synthesis, alias, shim, dual format, tag fallback,
  or generated-model reconstruction is added.
- No eligibility endpoint or repair surface is added. This line changes no
  successful query result, Candid method, or accepted schema meaning.

## Non-Negotiable Invariants

1. No canonical record changes before complete validation of its exact batch.
2. No replacement cursor exists unless Apply pagination is measured as
   necessary; if it exists, it binds sequence, ID, fingerprint, count, and next
   Apply ordinal.
3. Validate is read-only until same-message prepared Apply or the optional final
   Apply-cursor publication.
4. Apply cannot begin before successful complete validation.
5. Every Apply page is fully prepared before canonical mutation.
6. Canonical row and derived index effects advance together under accepted
   schema semantics.
7. Identity, schema, validation-job, and migration record families retain their
   existing singular authorities.
8. A watermark never advances past an unapplied record.
9. Cursor and batch retirement cannot erase the only authority for incomplete
   work.
10. A batch at or below the watermark is never applied again.
11. Raw byte admission happens before record materialization.
12. A validated fallback batch's chunks are immutable until terminal retirement;
    Apply never rehashes or decodes an unbounded prefix.
13. Any fallback cursor binds the next record's exact byte offset; no offset
    table or physical record index is introduced implicitly.
14. Typed validation corruption uses the existing bound 0.225 terminal-failure
    receipt and stops the watchdog without adding state.
15. Every stated physical and instruction limit includes measured worst-unit
    overshoot and fanout.
16. Malformed or unsupported state fails typed and closed.
17. Generated models never reconstruct runtime authority.
18. Production convergence contains no panicking operations.
19. IC message atomicity is modelled at actual synchronous message boundaries,
    not between individual stable writes.
20. Raw non-gzipped Wasm is the authoritative footprint measure.

## Baseline And Acceptance Measurements

Patch 1 records representative and worst-feasible producer batch bytes,
raw-header bytes, record count, per-family encoded size, coexisting row/index/
schema fanout, optional cursor/offset bytes, retained-preparation and validation-
proved streaming instructions/live memory, fallback page instructions and any
double-decode cost, Wasm heap-page high-water and maximum-live-byte proof,
terminal instructions, overshoot, stable reads/writes/growth, final
raw Wasm, deterministic gzip secondary, Candid/method modes, and complexity
signals. Measurements execute the maintained production watchdog path in the
exact Wasm artifact; an audit-only endpoint may observe its committed timer

Acceptance requires rejection before materialization when raw bounds fail;
complete validation before canonical mutation; fixed heap, stable-memory, and
instruction headroom below the maintained IC message envelope; exact resume at
every real durable boundary; no history-dependent per-page work; no method-mode

Performance claims distinguish batches `B`, encoded bytes `Y`, records `R`,
derived fanout `F`, and instructions `I`. A page limit expressed in only one of
those quantities is insufficient.

## Complexity And Maintenance Gate

Demonstrated need: the predecessor can mutate early records before discovering
late corruption and cannot truthfully claim a pre-decode page byte bound.

Simplest selected alternative: lower the admitted maximum if necessary, inspect
the fixed raw header, and validate, prepare, Apply, and retire one complete batch
in a rollback-safe message. A fingerprint-bound paged Apply cursor is retained
only if that measured complete-message shape cannot fit. Per-record
validate/apply with a larger page does not solve late corruption; durable
Validate is not authorized without measurement.

Canonical owner: the existing convergence coordinator over record-family
semantics and canonical stores, plus one Apply cursor only if measurement proves
it necessary.

State-space delta: the preferred shape removes `FoldRecordCursor` and adds no
persisted progress state. The fallback replaces it with one 32-byte
fingerprint-bound Apply cursor carrying ordinal and byte offset. Neither shape
adds a phase enum, validation ordinal, overlay, prepared log, offset table,
record index, or scheduler. One raw envelope revision replaces the old envelope.

Promotion fails if the implementation needs a second prepared log, separate
startup/online decoders, legacy formats, generated authority, a logical overlay,
prefix replay, or unbounded validation. A need for durable Validate or physical
chunk redesign stops for a new product decision. Each handoff reports files/
line delta, domains, state axes, duplicate flows, instruction/heap/stable/raw-
Wasm effects, and the resulting complexity direction.

## Promotion Gate

Patches 3 and later become recovery implementation authority only when:

1. Patch 1 confirms the released 0.227 predecessor did not redefine the
   accepted 0.225 recovery authority;
2. exact Wasm probes over worst legally feasible producer batches compare
   retained preparation with validation-proved streaming Apply and first prove
   whether combined validation, Apply, and retirement fit;
3. every record producer proves independent validation of later records without
   an overlay, prefix replay, or second semantic authority;
4. exact envelope, fingerprint preimage, optional direct-offset Apply cursor
   decision, retired formats, and universal 0.227 reinstall-only hard cut are
   frozen;
5. batch, byte, record, fanout, instruction, heap, overshoot, stable, and raw-
   Wasm gates are frozen from IC evidence;
6. typed validation corruption is reproduced through the existing durable
   0.225 receipt, startup observation, and watchdog-stop path;
7. every actual successful-message boundary has an explicit expected durable
   state, and impossible mid-message states are removed from the protocol; and
8. the user reviews Patch 1's result and explicitly authorizes the selected
   runtime implementation.

If validation still cannot fit at the smallest useful batch contract, Patch 1
reports the evidence and stops. A combined-path failure may select the bounded
paged Apply fallback only after proving it avoids history-dependent prefix
decode. Neither result automatically authorizes durable Validate pages,
physical chunk redesign, or more landing patches.
