## Decision Summary

Patch 3 selects one synchronous batch message: raw inspection, complete
read-only validation/proof, mechanical streaming Apply, and terminal
retirement. If later implementation evidence invalidates its frozen instruction
or live-memory bound, the line stops for a new product decision.

No record mutates canonical state until the exact batch has passed validation.
The one-message shape is preferred because IC rollback then removes all
intra-batch persisted progress and replay states.

Patch 1 proved that unchanged structural admission could not simply reuse the
current fold loop: a maintained 1,024-row batch with 64 accepted secondary
indexes required 56,121,104,133 current recovery-work instructions. Patch 2
then bounded admitted structural work. Patch 3 covered the remaining larger
producer family by publishing the maintained maximum 65,536-key accepted index
through ordinary SQL DDL. Its current recovery completed in two work messages
totalling 22,076,602,490 instructions, including per-record cursor publication,
repeated callback materialization, and terminal retirement. The maximum one
message was 20,028,875,541 instructions.

Validation-proved streaming performs each semantic proof and canonical write
once, moves every normal failure before the first mutation, and removes the
measured cursor and repeated-callback work. Its complete-message instruction
bound is therefore conservatively the measured 22,076,602,490 aggregate,
leaving 17,923,397,510 instructions below the IC's 40-billion limit before the
format implementation is optimized. The observed Wasm extent rose from 26 to
259 pages, which is a conservative 16,973,824-byte live-memory upper bound
because Wasm memory does not shrink. Retaining a second prepared transition
graph adds memory and semantic plumbing without removing stable writes, so it
is rejected. The selected shape is one complete read-only validation followed
by mechanically infallible streaming Apply and retirement in the same message.

The demonstrated need for an additional fixed admission axis is that
row and byte bounds do not constrain derived-index work. The simplest
alternative to persisted progress is a canonical compile-time joint work bound
owned by structural commit preparation, expressed over admitted rows and exact
prepared transitions. Patch 2 freezes that bound as:

```text
W = 4R + I + 4A + 4P
W <= 16,384
```

`R` is the number of prepared canonical row transitions, `I` is the number of
actual prepared index-store mutations including counter-neutral candidate and
reverse-index work, `A` is the number of identity-range applies, and `P` is
zero or one for an exact mutation-progress successor. Every addition and
multiplication is checked. The producer charges each row as soon as its owner
has prepared the exact transition and rejects the first excess with typed
`RUNTIME_BOUNDARY_MUTATION_BATCH_COMMIT_WORK_EXCEEDED` before commit-marker or
journal publication. It does not finish preparing an already-disqualified
high-fanout batch.

The fixed value leaves more than 15 billion instructions beneath the IC's
40-billion replicated-message limit across the measured admitted shapes. It
admits at most 4,096 zero-index transitions, 240 inserts with 64 actual
secondary-index mutations, and 124 worst-case
64-index replacements that remove and insert every key. The existing 16-MiB
staged-input and 1-MiB result bounds remain independent, so one wide row is not
penalized merely for its bytes and cheap batches retain materially higher row
capacity. The new axis adds one scalar accumulator and one public diagnostic,
but no caller setting, mode, persisted state, cursor, or execution route.

There is no replacement cursor, durable Validate phase, validation ordinal,
prepared log, or second recovery route. The predecessor `FoldRecordCursor` is
removed by the format hard cut. Failed execution traps roll back the complete
synchronous validation/Apply/retirement message and retry from immutable
journal bytes.

The selected replacement journal envelope is version 2 and exposes bounded
header facts before record materialization. All integers are little-endian:

| Byte range | Current field |
| --- | --- |
| `0..4` | magic `IJBT` |
| `4` | format version `2` |
| `5..9` | payload length, including all bytes after offset 9 |
| `9..25` | batch ID |
| `25..41` | commit-marker ID |
| `41..49` | journal sequence |
| `49..53` | record count |
| `53..85` | SHA-256 batch fingerprint |
| `85..total_len` | canonical self-delimiting records |

The total encoded maximum remains 16 MiB and the record maximum remains
16,384. Inspection reads the 85-byte fixed header, checks `9 + payload_len`
without overflow against the encoded maximum, requires at least the 76 fixed
payload bytes, and validates IDs, sequence, count, truncation, trailing bytes,
and physical sequence binding before allocating the complete batch.

Validation is read-only with respect to canonical data, indexes, schema,
identity, validation jobs, cardinality, journal bytes, and recovery controls.
It either returns a typed failure with no canonical write or continues into
same-message mechanically infallible streaming Apply.

Apply proves every transition admitted by the selected immutable batch from
canonical predecessors before it mutates state. Every fallible decode, lookup,
schema check, key derivation, allocation/capacity proof, and serialization
occurs before mutation. Mechanical streaming Apply and terminal watermark/tail
retirement then complete synchronously in that same message.

## IC Execution Model Authority

This is an IC recovery protocol, not a conventional process/WAL protocol. Its
boundaries and evidence follow the replicated execution model:

- recovery contains no `await`, yield, callback, remote call, or re-entrant
  application execution;
- an upgrade cannot interrupt a currently executing message;
- trap or instruction exhaustion rolls back the complete replicated message;
- a normally returned `Err` does **not** roll back earlier writes, so every
  normal fallible operation must complete before the first mutation;
- the selected complete message must remain below the 40-billion instruction
  limit with the frozen headroom and live-memory bound;
- header inspection must bound heap allocation before stable chunks are joined;
- measurements use Wasm performance counters, Wasm heap-page high-water plus a
  deterministic maximum-live-byte proof, stable reads/writes/growth, and worst-
  unit instruction overshoot; host wall time and a zero host counter are not
  evidence; and
- recovery instruction probes drive the real generated watchdog and read its
  canonical `ic-timers` scheduler/work measurements only after completion; a
  test-admin observer may project those inert measurements but must not invoke
  the private driver, add a second execution route, or replace timer ownership;
- timer-owned start/end Wasm and stable page extents may replace host-side
  before/after extent sampling when available, but neither form proves exact
  sub-page live bytes; owner-derived retained/temporary byte accounting remains
  mandatory; and
- each ceiling reserves measured headroom for the 0.225 driver, timer callback,
  terminal publication, runtime overhead, and the largest admitted record
  fanout.

A database or host-filesystem analogy cannot introduce interruption states
that the IC cannot durably expose, nor may IC rollback be used to excuse a
normal post-mutation error path.

## Fingerprint And Envelope Contract

The selected format uses an unkeyed 32-byte SHA-256 batch fingerprint. It
detects accidental corruption and batch substitution. It is not an
authenticator against an actor able to rewrite the batch and recompute the
fingerprint.

The fingerprint is:

```text
SHA-256(
    b"ICYDB-JOURNAL-BATCH-FINGERPRINT\0" ||
    canonical envelope bytes 0..53 || canonical record bytes 85..total_len
)
```

The preimage therefore covers the envelope magic and version, exact encoded
length, batch ID, marker ID, sequence, record count, and canonical record bytes.
The fingerprint field itself is excluded. Payload length still includes the
32-byte field, so substitutions cannot alter framing. The offsets, little-
endian integers, 85-byte fixed header, 16-MiB total maximum, 16,384-record
maximum, and checked allocation proof above are frozen. This is one new current
envelope, not a wrapper over the retired encoding.

Encoding hashes slices of the already-built canonical envelope, and decoding
hashes the bounded raw envelope after stable chunks have been assembled under
the inspected length. Neither path allocates a second fingerprint preimage or
reserializes a decoded batch. The decoded batch remains the immutable
message-local authority until same-message terminal retirement; there is no
cross-message validation claim to bind with persisted progress.

## User Outcome

- Corruption in the final record is reported before the first canonical record
  changes.
- A failed batch message restarts from immutable bytes under whole-message
  rollback; there is no persisted intra-batch progress.
- No recovery message decodes a batch whose raw envelope already violates its
  byte limit.
- Batch, cumulative bytes, record count, instruction work, index fanout, and
  worst-record overshoot are separate measured bounds.
- A trap or instruction exhaustion rolls back the complete message; an upgrade
  can occur only before it starts or after its successful terminal return.
- Startup readiness continues to use the 0.225 driver and state contract.

## Canonical Ownership

Authority order is:

1. accepted schema snapshots own record semantics;
2. the commit marker owns interrupted publication into the journal;
3. immutable current envelope bytes plus sequence, ID, count, and fingerprint own
   the batch being converged;
4. canonical data, index, schema, identity, and validation-job stores own folded
   state;
5. the fold watermark owns the highest completely applied sequence; and
6. the accepted 0.225 driver owns replicated invocation only.

The convergence engine owns one flow:

```text
raw inspect -> Validate/prove complete batch -> mechanical streaming Apply
            -> atomic terminal retirement
```

Journal storage owns raw envelope access and control codecs. Record-family
owners supply validation and prepared canonical transitions. The convergence
coordinator orders them; it does not absorb schema, identity, or index
semantics.

## Validate Contract

Validate proves in one bounded read-only message:

- envelope magic/version, encoded length, sequence, ID, count, and fingerprint;
- one-store routing and required storage capabilities;
- accepted and candidate schema identity where relevant;
- every row key, row payload, field wire, and commit schema fingerprint;
- exact derived index transition evidence;
- constraint-validation job and candidate-index closure;
- identity range owner, expected high-water, count, and record ordering;
- current schema/migration plan identity when that record family is enabled;
- complete known record-family coverage; and
- canonical final batch closure with no trailing or missing bytes.

Validation reads canonical predecessors only when needed to prove that Apply
can execute under the same startup-gated fold order. It performs no write
before mechanical Apply begins.

Current producers must also prove why validation needs no logical shadow
database. Structural batches reject duplicate target keys and journal one final
transition per row key after validating the complete final-row overlay.
Accepted-schema publication orders the schema record before either bounded
user-index changes bound to the exact accepted-after fingerprint or one
validation-job transition; the codec rejects those two suffix families when
combined. Constraint validation and migration record families carry their
job/plan/candidate evidence and visit each owned key once. Patch 3 enumerates
and tests these producer invariants for every record family. If any
later record semantically depends on an earlier unapplied effect that cannot be
checked from its own evidence, promotion stops; 0.228 must not add an overlay,
prefix replay, or durable prepared shadow to paper over the gap.

## Preparation Strategy Decision

Patch 3 compared two complete-message Apply strategies against the same
validated immutable batch:

1. retain every owner-prepared transition until validation and preparation are
   complete, then apply the retained values mechanically; and
2. during complete validation, prove every semantic, decoding, serialization,
   allocation, stable-capacity, and ordinary failure condition, then stream a
   mechanically infallible record-family Apply without retaining a second full
   transition graph.

Streaming is selected. The current maximum accepted-index path already performs
each record's semantic validation and Apply once; moving those checks before
the mutation boundary need not duplicate them. Its two-callback aggregate is a
conservative complete-message bound because it additionally includes repeated
materialization, candidate reconstruction, per-record cursor writes, timer
entry/exit, and terminal work. Retained preparation performs the same stable
writes while adding a second maximum-sized transition graph and more ownership
plumbing. Patch 4 inventories every current `Result` branch in row/index/
schema/identity/job/migration Apply and moves its proof to the owning
pre-mutation validator; the later Apply contradiction path traps so a normal
error cannot return after mutation begins.

## Terminal Failure Visibility

0.228 adds no failure state. A normally returned validation corruption follows
the accepted 0.225 path in the same replicated driver message:

```text
convergence returns StartupRecoveryFailure::JournalStore
  -> driver classifies the typed persisted corruption as JournalRecovery
  -> driver captures the exact incarnation/allocation/tail proof binding
  -> existing bounded StartupFailureReceipt is published
  -> driver returns Terminal
  -> publishing callback returns success and Stop
  -> later startup_state() returns that matching typed failure
  -> lifecycle reconciliation retires the watchdog; any callback already
     invoked against the failure returns invariant_failure and Stop
```

Receipt publication and the `Terminal` result are one synchronous update. A
publication error returns retryable failure without falsely claiming a durable
terminal state. The receipt is stale only when the existing bound authority
changes under an authorized transition. Patch 3 reproduces this chain with
persisted semantic corruption: the driver publishes a bound `JournalRecovery`
receipt, observation returns typed `STORE_CORRUPTION`, repeat driving returns
`Terminal`, and the generated callback maps terminal success or an already
observed failure to `Stop`.

## Apply And Terminal Contract

Apply starts only after complete validation in the same message. It:

1. uses the same validated decoded batch;
2. proves all admitted transitions and terminal retirement inputs;
3. proves stable capacity and performs all normal fallible work before mutation;
4. applies records mechanically under record-family proofs; and
5. completes terminal retirement in the same synchronous message.

No normal `Err` is reachable after step 4 begins. A trap remains possible at a
platform or stable-memory boundary, but the IC rolls back the whole message.

After the final transition, the same bounded synchronous message validates the
next epoch, publishes the watermark, and retires the batch. Its durable states
are only before the message and after successful return:

| Boundary | Separately durable? | Reason |
| --- | --- | --- |
| Complete validation / first canonical mutation | No | The same synchronous message continues into mechanical Apply |
| Individual Apply mutation / later Apply mutation | No | No `await`; trap rolls the complete message back |
| Watermark / batch retirement | No | One synchronous terminal message with no successful partial return |

Trap failpoints around individual writes remain required rollback evidence, but
they are not extra persisted protocol states. A retained batch at or below the
watermark is cleanup-only only if a future implementation deliberately splits
terminal cleanup; the reduced protocol does not do so.

## Truthful Bounds

The engine freezes distinct fixed limits for:

- maximum encoded bytes in one journal batch;
- maximum cumulative encoded batch bytes admitted by one page;
- maximum records advanced by one page;
- maximum instructions used by one page;
- maximum derived row/index/schema fanout of one admitted record; and
- measured overshoot after the last safe instruction check.

Raw inspection precedes record allocation. The page reserves measured headroom
for header and fingerprint work, record decode, maximum prepared fanout,
terminal transitions, driver/runtime overhead, and overshoot.
Host tests use explicit deterministic limits and do not treat a zero host
performance counter as instruction evidence.

Patch 1 tested whether lowering admission was sufficient, and Patch 2 freezes
the joint prepared-effect policy above without lowering the independent staged-
byte limit. It retains the 4,096-row zero-index maximum and the exact largest
single operation promised by maintained row and derived-effect limits while
preventing row count from concealing excessive fanout. Historical maxima are
not a compatibility promise before 1.0.

Patch 3 measures legal producer outputs, not a Cartesian product of unrelated
maxima. It constructs the worst feasible combined batch for each mutually
exclusive producer family, then selects the greatest measured instruction and
live-memory cases:

- structural mutation: the maximum coexisting operation count, encoded rows,
  identity-range records, accepted index fanout per row, and one-store routing
  that the maintained precommit path can actually publish;
- accepted-schema index replacement: the largest accepted candidate together
  with the exact old/new user-index key deletion and insertion chunks;
- accepted-schema job transition: the largest accepted candidate with its one
  permitted validation-job put/delete and no user-index chunks;
- constraint validation: its job record plus the maximum candidate-index entry
  set admitted in the same batch; and
- schema migration where enabled: the largest source row and derived index
  effects that the maintained migration page can co-publish.

Each fixture must be built through the maintained producer/admission authority.
It may not hand-construct an impossible mixed record set. Separate scalar
maxima remain explanatory context only; they cannot establish the final bound.

The complete-message live-memory comparison includes fixed-header bytes,
complete raw batch assembly, the decoded representation, canonical predecessor
reads, the retained prepared graph for that strategy, and the largest temporary
value for streaming Apply. Instruction evidence includes stable chunk reads,
SHA-256 work, validation, preparation/proof, Apply, terminal retirement, driver
entry/exit, and worst-record overshoot.

Paged Apply is not selected. An offset table, record index, new physical
addressing format, or replacement cursor would be a new product decision and
is outside this line's current authority.

Physical chunk redesign or durable Validate pages require a separate product
decision. They may be proposed only if exact Wasm evidence proves both that:

1. complete validation alone cannot fit the reviewed instruction and memory
   envelope; and
2. reducing the admitted maximum to the smallest useful contract still cannot
   fit.

Until both are demonstrated, the existing stable chunks remain physical
storage only and one logical batch remains the validation unit.

## No-Build And Alternatives Gate

- Raising the page threshold does not make post-decode byte accounting truthful.
- Validating each record immediately before Apply does not protect earlier
  records from later corruption.
- One-message complete validation, preparation, Apply, and retirement is tested
  first because the admitted batch has a fixed maximum and IC rollback removes
  all intra-batch durable states when it fits.
- Copying decoded records into a second durable prepared log duplicates journal
  authority and write cost.
- A legacy cursor decoder or inferred phase makes two formats current before
  1.0 and is prohibited.

Patch 2 freezes the smallest useful structural admission policy. Patch 3
freezes the reduced one-shot protocol and exact IC message boundary. Durable
validation, paged Apply, or a parallel envelope require a new product decision.

## Persisted And Public Hard Cuts

- `FoldRecordCursor` and its startup-receipt binding field are removed; no
  replacement cursor exists.
- The journal envelope moves directly to the current fingerprint-bearing form with
  bounded pre-materialization header inspection.
- Every 0.227-to-0.228 canister transition, including production, is reinstall/

- No legacy decoder, cursor synthesis, alias, shim, dual format, tag fallback,

- No eligibility endpoint or repair surface is added. This line changes no

2. No recovery cursor exists.
3. Validate is read-only until same-message mechanical Apply.
4. Apply cannot begin before successful complete validation.
5. The complete batch is fully proved before canonical mutation.

18. IC message atomicity is modelled at actual synchronous message boundaries,

## Complexity And Maintenance Gate

Demonstrated need: the predecessor can mutate early records before discovering
late corruption and cannot truthfully claim a pre-decode page byte bound.

Simplest selected alternative: inspect the fixed raw header, validate/prove,
mechanically stream Apply, and retire one complete batch in a rollback-safe
message. Per-record validate/apply does not solve late corruption; durable
Validate and paged Apply are not authorized.

Canonical owner: the existing convergence coordinator over record-family
semantics and canonical stores.
