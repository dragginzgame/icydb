## Current Verdict

Patch 1 reduced the proposed protocol and established the independently
necessary Patch 2 canonical 16,384-unit joint row/derived-effect admission
limit. Patch 3 selected cursor-free complete-batch recovery. Authorized Patch 4
now implements that selection as one pre-1.0 hard cut: journal batches use the
version-2 fingerprinted envelope, complete read-only validation precedes every
canonical mutation, Apply plus watermark/tail retirement stays in the same
replicated message, and `FoldRecordCursor` plus its receipt binding are removed.

The evidence-only Patch 3 added maintained producer fixtures, canonical-watchdog
measurements, owner-local malformed-batch regressions, terminal-receipt
observation, and documentation. It changes no production recovery behavior,
journal envelope, cursor encoding, scheduler ownership, or persisted state.

The post-0.228.0 continuation added one bounded predecessor-envelope primitive:
journal-tail reads now inspect the fixed `IJBT` header, version, and declared
payload length, batch ID, marker ID, sequence, and record count before
allocating the assembled raw batch. The reader reserves only the exact declared
current-form length and rejects oversized declared payloads, impossible counts,
sequence drift, missing tail bytes, or trailing persisted chunks before record
decode. Interrupted prefix republish remains prefix-tolerant through the
append-only comparison path. That landing did not change the journal format;
Patch 4 now consumes the primitive as the 85-byte version-2 fixed header and
removes the predecessor cursor path completely.

The same continuation also hardens the record-family dependency proof for row
and migration batches. Current-form batch decoding now rejects duplicate
ordinary row put/delete targets, duplicate migration row/index targets, and
mixed migration plan digests inside one batch. That keeps complete read-only
validation from needing a same-batch overlay for these families. Patch 3 closed
the remaining family gate before Patch 4 consumed it. Accepted-schema index
chunks now also fail closed when a
delete/put suffix names a store path different from the leading
`AcceptedSchemaPublish`, keeping those suffix records bound to one accepted
store authority. Constraint-validation job put/delete records are likewise
limited to one transition per batch, matching maintained producer shapes and
preventing same-batch job overlay semantics. Accepted-schema publication
records are also limited to one ordinal-zero publication followed only by
schema-owned suffix records maintained producers can emit.

Fresh production-Wasm evidence now rules out treating the current fold loop as
that one-message solution at unchanged admission. One accepted 1,024-row batch
with the accepted maximum 64 secondary indexes is produced in 22,135,010,413
local instructions, but current recovery needs 56,121,104,133 work instructions
across three messages before complete validation is added. The selected hard
cut charges four units per prepared row, one per actual prepared index-store
mutation, four per identity-range apply and four for an exact progress
successor. It preserves 4,096 cheap zero-index rows but admits only the exact
fanout that fits the same fixed budget. It may not quietly call the nominal
20-billion threshold a ceiling or assume row count is a sufficient bound.

The format transition remains a complete pre-1.0 hard cut. No predecessor
cursor/envelope decoder, upgrade bridge, repair path, or dual-format interval
will be built. Every development or production 0.227-to-0.228 transition is
reinstall/recreation-only; there is no supported in-place upgrade subject.

## IC Execution And Durability Reconstruction

Recovery is synchronous and has no `await`. The IC cannot upgrade during an
executing message, and trap or instruction exhaustion rolls back the whole
replicated message. A normal returned error does not roll back writes.

Therefore the maintained and proposed durable boundaries are:

| Work | Durable boundary |
| --- | --- |
| Complete Validate/prove/streaming Apply/retire | Before the update, or the entire batch folded after successful return |
| One Apply mutation versus another | Not separately durable; a trap rolls the complete message back, while normal errors must be impossible after mutation starts |
| Watermark and batch retirement | Not separately durable inside the same synchronous message |

This removes the proposed durable Validate phase, fold cursor, and false
terminal cross-product. It does not weaken error atomicity: every decode,
lookup, capacity check, and serialization for the selected batch must be proved
before the first canonical mutation.

## Preparation Strategy Finding

The current `validate_journal_batch_records` is not yet sufficient to make the
current streaming `apply_journal_record` mechanically infallible. Apply repeats
fallible row decoding/preparation, accepted-schema candidate decoding and
publication, validation-job decoding, identity-state checks, migration-plan
checks, and row/index/schema fold operations. Therefore Patch 1 cannot simply
measure the current loop and declare the streaming strategy proven.

The measurement must compare:

- retained owner-prepared transitions, including their complete live-memory
  graph; and
- an owner-proved streaming shape in which validation/capacity preflight closes
  every normal error before the first mutation and the later operation contains
  only mechanical stable writes.

If the latter needs duplicate record-family semantics or converts an ordinary
error into an unexplained trap, it fails the simplicity/correctness gate.

| Current Apply family | Fallible work still repeated after validation |
| --- | --- |
| Row put/delete | raw-row reconstruction, canonical predecessor load, `CommitRowOp` construction, accepted row/index preparation, index folds, and data fold |
| Schema put/publish | snapshot or candidate decoding, runtime routing/incarnation lookup, and schema-store fold/publication |
| Accepted index chunks | per-key index fold and store-state checks |
| Validation job/index | job decoding, job-state fold/removal, and candidate-index fold |
| Identity range | advance-ID construction, live checkpoint update where applicable, and identity-state fold |
| Migration | plan revalidation, row/key reconstruction, and data/index fold |

Patch 3 selected streaming Apply from the two candidates. Patch 4 moved each
listed failure proof before mutation and traps if the later mechanical Apply
contradicts that complete preflight.

## Existing Terminal-Failure Path

The accepted 0.225 path already owns durable corruption visibility:

1. convergence returns `StartupRecoveryFailure::JournalStore`;
2. `record_recovery_failure` maps it to `StartupFailureKind::JournalRecovery`;
3. `classify_terminal_failure` accepts persisted corruption and incompatible-
   format codes while leaving operational failures retryable;
4. the predecessor driver captured database incarnation, store allocation,
   exact journal proof, and the then-current fold cursor, then published one
   bounded `StartupFailureReceipt`;
5. the driver returns `GeneratedStartupDriverStep::Terminal`;
6. that callback maps `Terminal` to `success` with `Stop`;
7. `startup_state()` later matches the receipt before pending controls and
   returns its typed failure; and
8. lifecycle reconciliation retires the watchdog, while any callback already
   invoked against the failure returns `invariant_failure` with `Stop`.

Receipt publication occurs before `Terminal` in the same update. Publication
failure returns an error, so the watchdog continues retryably rather than
falsely stopping. No new 0.228 state is needed. Patch 3 reproduces the chain
with persisted semantic record corruption and exact terminal replay.

## Rejected Paged-Apply Alternative

The current record encoding is sequential and self-delimiting, but Patch 3's
complete-message evidence removes the demonstrated need for cross-message
direct seek. Paged Apply, an offset table, a record index, a bounded chunk
reader, and a replacement cursor are outside the selected protocol and require
a new product decision.

## Upgrade Policy

All 0.227-to-0.228 upgrades are unsupported, regardless of whether an old tail
or cursor appears empty. The only supported transition is explicit reinstall/
recreation after the operator makes any required backup/export decision. This
universal rule is the eligibility predicate; no runtime endpoint or legacy
decoder is needed. Release documentation and the real-canister transition
fixture must use reinstall mode and must show that installing over retained
predecessor bytes fails closed rather than partially recovering them.

## Record-Family Dependency Inventory

The maintained producer contracts currently support validation without a
shadow database:

- structural batches reject duplicate target keys and construct the complete
  final-row overlay before journaling one final transition per row key;
- accepted-schema publication journals schema authority first, followed by
  either 64-key accepted user-index delete/put chunks bound to the
  accepted-after candidate or one validation-job transition; codec authority
  rejects those two suffix families when combined;
- constraint-validation index records carry the candidate/job authority needed
  for their exact key transition; and
- migration records bind the exact plan digest and the source page visits each
  owned row/key once.

Promotion still requires an exhaustive record-variant table and focused tests
proving that record N never needs an earlier unapplied effect that is absent
from its own immutable evidence. Discovery of such a dependency is a stop, not
permission to add a logical overlay, prefix replay, or durable prepared store.

The static variant inventory is now exhaustive:

| Record family | Maintained dependency authority | Read-only validation disposition |
| --- | --- | --- |
| `RowPut` / `RowDelete` | structural preparation rejects duplicate target keys and constructs one final transition per primary key | validates against the canonical predecessor; no earlier row record for the same key is legal |
| `SchemaPut` | encoded snapshot and store path bind the accepted runtime entity | no preceding record effect is required |
| `AcceptedSchemaPublish` | must be ordinal zero, unique, and carries the complete candidate bundle/root and expected revision | candidate is decoded before the record loop and remains immutable evidence for every schema-owned suffix; late, duplicate, or non-schema suffix shapes fail closed |
| `AcceptedSchemaIndexDelete` / `Put` | exact publication store path, entity/fingerprint and 1..=64 canonical keys bind the leading candidate | validates against the decoded leading candidate, not an applied schema change; suffix records with a different store path fail closed |
| `ConstraintValidationJobPut` / `Delete` | the batch-wide validator permits one exact job transition and checks candidate closure; codec shape validation rejects multiple job transitions in one batch | full-batch observation supplies the transition without canonical mutation |
| `ConstraintValidationIndexPut` | codec requires the leading job-put record and exact matching entity/constraint identity | validator reads that immutable first record directly; no earlier index Apply is required |
| `IdentityRangeAdvance` | owner/incarnation, exact range and ordinal-derived advance ID are record/batch facts | validation reads canonical identity commit state; same-batch row records do not alter that authority |
| `SchemaMigrationRowPut` / `IndexPut` | one exact plan digest plus producer-sorted/deduplicated row/key ownership | validation binds the plan and decodes each owned key independently |

This closes the source inventory, not the focused malformed-batch evidence.
Promotion still requires a maintained regression for every row in this table
and must stop if any producer can emit a duplicate logical target that the
inventory missed.

## Worst Feasible Shape Policy

The current record maxima are not freely composable. Patch 1 uses maintained
producer paths to construct the legal candidate families rather than
hand-building one impossible super-batch:

| Producer | Coexisting facts to maximize |
| --- | --- |
| Structural mutation | admitted operations in one store, cumulative encoded rows, identity-range record, and derived index fanout of those same accepted rows |
| Accepted-schema index replacement | accepted candidate bytes, old-index deletions, and new-index insertions in canonical 64-key chunks; no validation-job record |
| Accepted-schema job transition | accepted candidate bytes and one permitted validation-job put/delete; no user-index chunk |
| Constraint validation | exact job record and all candidate-index entries that the same job/page may publish |
| Schema migration | rows and derived index effects emitted by one admitted migration page under one plan digest |

The maintained ceilings that constrain those legal families are:

| Family | Producer ceiling before the common 16-MiB / 16,384-record journal cap |
| --- | --- |
| Structural mutation | 4,096 operations and 16 MiB staged row input; each accepted row may materialize 64 secondary-index effects |
| Accepted-schema index replacement | 65,536 deletion keys, 256 MiB staging and exact 1..=64-key journal chunks; actual encoded batch remains subject to the common journal cap |
| Accepted-schema job transition | one candidate plus one put/delete job; encoded job at most 64 KiB |
| Constraint validation | 256 rows, 4 MiB decoded row bytes, 4 MiB staged bytes and 64 findings per page |
| Schema migration | 256 rows, 1 MiB row bytes, 1 MiB index bytes, 8 MiB journal bytes and at most 16,384 effects per rewrite page |

For each resource—encoded bytes, records, instructions, and live memory—the
acceptance ceiling uses the greatest reachable producer result. Separate maxima
are still reported, but neither an impossible Cartesian product nor a
convenient light fixture can set the final gate.

## Patch 3 Promotion Decision

The accepted-index replacement family is the largest maintained direct-effect
producer: one ordinary SQL DDL operation scanned 65,536 rows and journalled
65,536 exact index keys. Constraint validation is limited to 256 rows per page,
migration to 16,384 effects, structural work to Patch 2's 16,384 units, and the
wide-row fixture remains independently byte-bound. The accepted-index fixture
therefore closes the greatest direct stable-write count without constructing an
impossible Cartesian-product batch.

The current engine's 22,076,602,490-instruction aggregate performs every
accepted-index record validation and canonical write once and additionally
pays per-record cursor persistence, two callback entries, repeated raw decode
and candidate reconstruction, and terminal retirement. The selected streaming
shape moves those same proofs before mutation and removes that overhead, so the
aggregate is a conservative complete-message ceiling. Its 17,923,397,510-
instruction reserve is materially larger than the measured scheduler and
terminal costs and maximum post-unit overshoot.

Wasm extent after recovery was 259 pages. Because Wasm linear memory cannot
shrink, 16,973,824 bytes bounds the coexisting raw assembly, decoded batch,
canonical predecessor reads, per-record temporary state, timer execution, and
allocator high-water. Retained preparation would add a second maximum-sized
transition graph to that set without reducing stable writes. Streaming is
therefore both the lower-state and lower-memory choice. Paged Apply, double
decode, direct-offset access, and a replacement cursor are not selected.

## Patch 2 Implementation And Validation

The structural commit owner now accumulates one checked scalar while it streams
already-canonical preparation. Each row is charged before it enters the
retained prepared batch; rejection therefore stops further high-fanout work and
