# IcyDB 0.240 Singular Global-Aggregate Compiled Plan Cache

Status: IMPLEMENTED — FOCUSED VALIDATION PASSED

Last updated: 2026-08-24

Candidate evidence revision:
`44410102e4e956ed3a20e0ddd423e4b78d1ddae5` (`0.239.1` candidate).

The user explicitly authorized implementation against the validated but
unpublished 0.239.1 candidate, which remains the exact predecessor.

## Outcome

Replace the two independently populated compiled-plan cache slots on SQL global
aggregate commands with one fingerprint-bound cache entry that carries exactly
one already-selected execution preparation:

- an owned exact-cardinality target; or
- the existing shared prepared aggregate plan.

The change must remove cache and resolver complexity, shrink final raw Wasm,
and preserve or improve current query cost. It adds no query capability,
execution route, accepted-schema authority, persisted state, configuration,
public API, Candid method or compatibility path.

## Demonstrated Need

The current `CompiledSqlCommand::GlobalAggregate` owns two `OnceLock` slots:

- `plan_cache` for ordinary prepared aggregate execution; and
- `count_plan_cache` for the exact-cardinality specialization added in 0.237.

The surrounding implementation consequently carries separate cache-entry
types, lookup/set methods, direct-count target and outcome adapters, and
measured versus unmeasured resolution branches. The principal files in this
flow currently contain 1,515 lines, including 528 lines in
`session/sql/execute/direct_count.rs`. That total is only a discovery signal.
The concrete dual-cache surface selected for removal is:

- the `count_plan_cache` field beside `plan_cache`;
- `SqlGlobalAggregateCountPlanCacheEntry` and its separate
  `SqlGlobalAggregateCountPlanTarget` payload;
- `cached_global_aggregate_count_plan` and
  `set_cached_global_aggregate_count_plan`;
- `cached_compiled_direct_count_cardinality_entry` and
  `cache_compiled_direct_count_cardinality_target`;
- the separate direct-count versus prepared-plan compiled-cache hit/miss
  branches; and
- the duplicated semantic branch families in
  `resolve_compiled_direct_count_cardinality_target` and its measured sibling,
  plus `execute_direct_count_cardinality_target` and its measured sibling; and
- the separate `DirectCountCardinalityOutcome` and
  `MeasuredDirectCountCardinalityOutcome` adapters, replaced by one semantic
  resolution/execution result with optional diagnostics attribution.

`SqlGlobalAggregatePlanCacheEntry` remains the fingerprint wrapper and is
expanded in place. The current direct-count target vocabulary may be renamed or
absorbed, but a second fingerprint wrapper is not introduced.

This is not an accepted-schema correctness defect. Both slots are
fingerprint-bound and the exact-cardinality executor remains singular. It is a
current complexity and footprint opportunity: one compiled command can retain
two memoized preparations for one global aggregate even though only one is the
preferred preparation for a given accepted snapshot.

The 0.237 evidence proves that the specialization itself must remain. At 2,048
rows, schema-proven row-equivalent global counts fell from
96,891,236–126,777,804 instructions to 815,629–854,348 instructions, and a true
warm exact count cost 731,475 instructions. Removing the exact-count path or
forcing it through full prepared-plan construction would discard a measured
hot-path benefit. The intended cleanup therefore converges its cache and
resolution ownership without generalizing away the fast path.

## Selected Structure

Conceptually, one compiled global-aggregate command retains one cache slot by
reusing the existing `SqlGlobalAggregatePlanCacheEntry` wrapper:

```rust
struct SqlGlobalAggregatePlanCacheEntry {
    schema_fingerprint: SqlCompiledSchemaFingerprint,
    prepared: SqlGlobalAggregateCachedPlan,
}

enum SqlGlobalAggregateCachedPlan {
    ExactEntityCardinality,
    ExactUserIndexPrefixes(Rc<[UserIndexPrefixCardinalityKey]>),
    Prepared(SharedPreparedExecutionPlan),
}
```

The enum name is illustrative. It is the widened/renamed form of the existing
`SqlGlobalAggregateCountPlanTarget`, not an additional wrapper. The existing
count cache-entry wrapper disappears, so this sketch has a net production-type
reduction even though the retained plan entry gains variants.

Resolution follows one owner-carried flow:

1. Pin the request's accepted catalogue and entity authority.
2. Check the command's single cache entry against that catalogue fingerprint.
3. On a valid hit, consume the cached exact target or prepared plan without
   reclassifying the SQL shape.
4. On a miss, let the existing direct-count semantic owner decide whether an
   exact-cardinality target exists.
5. Cache that target when it exists; otherwise resolve and cache the existing
   shared prepared plan subject to the current lifecycle-recheck rule.
6. Execute through the existing exact-cardinality executor or aggregate
   executor.
7. Project the result through the existing SQL response boundary.

## Prepared Fallback Owner

If an exact target is valid but its optional cardinality evidence is currently
unavailable, the fallback belongs to the existing registry-scoped shared query
plan cache in `db::session::query::cache`, reached through
`cached_shared_query_plan_for_accepted_authority_with_catalog`. It does not
belong to the compiled command.

That existing owner is `QUERY_PLAN_CACHES`, a `BoundedCache` selected by the
database registry's `cache_scope_id`. Its `QueryPlanCacheKey` contains:

- entity path;
- `SchemaCacheIdentity`: accepted runtime-root identity, accepted revision,
  schema version, fingerprint method version and fingerprint;
- current `QueryPlanVisibility`; and
- the structural query cache key, including the normalized-predicate
  fingerprint or prepared parameter contract where applicable.

On a hit, the owner additionally calls
`cached_cardinality_tiebreak_is_current`. A prepared plan carrying unavailable
cardinality evidence is reusable only when its retained lifecycle stamp still
matches the store's current evidence stamp. A mismatch becomes a shared-cache
miss and rebuild; neither the compiled command nor the fallback can prove
freshness itself.

Therefore an exact command entry never gains a hidden
`OnceLock<SharedPreparedExecutionPlan>`. When exact evidence is unavailable,
the request calls the named shared owner with the same pinned authority,
catalogue and structural query. That owner may return a hit or build and insert
on a miss under its existing bounded eviction/retention policy. No direct
ephemeral preparation path may bypass it. If the existing bounded cache elects
not to retain an artifact, the returned plan remains valid for that request;
this is existing shared-cache behavior, not a second command-local state.

A later request reuses the command's same exact target and asks the canonical
cardinality executor about current metadata again. An unavailable-to-available
transition therefore changes only the executor outcome: the command entry is
not replaced or mutated. Public exact-count calls retain their current
fail-closed no-scan behavior.

## Exact Cache State Machine

| Command entry | Current metadata | Action |
| --- | --- | --- |
| Empty | any | Classify once against the pinned catalogue; install an exact target, or install a cacheable prepared plan when no exact target exists |
| Exact target | available | Execute through the canonical exact-cardinality executor |
| Exact target | unavailable | Resolve the fallback exclusively through `QUERY_PLAN_CACHES`; do not retain it in the command |
| Prepared plan | any | Execute the prepared plan after the entry's fingerprint check |
| Fingerprint mismatch | any | Reject the command-local entry; follow the outer compiled-command lifecycle below and never mutate or replace the populated `OnceLock` |

## Fingerprint Mismatch And Replacement Lifecycle

The existing outer SQL compiled-command cache, `SQL_COMPILED_COMMAND_CACHES`,
owns replacement. Its `SqlCompiledCommandCacheKey` already contains the SQL
surface, entity path, accepted runtime-root identity, accepted revision, schema
version, schema fingerprint and raw SQL text. Publication changes that key, so
a new request misses the outer cache and receives a newly compiled command with
an empty plan slot. The old command remains under its old bounded-cache key
until ordinary eviction; it is not mutated into authority for the new root.

An in-flight request retains its old immutable catalogue and matching compiled
command, so its populated entry remains valid for that request. If a retained
command is defensively invoked with a different catalogue outside the normal
outer-cache path, the inner fingerprint mismatch makes the entry unusable. The
current request re-resolves against its pinned catalogue, using exact execution
or `QUERY_PLAN_CACHES`, but does not call `OnceLock::set` and does not acquire
command-local reuse for the mismatched catalogue. Subsequent normal requests
use the new outer cache key and new command.

Diagnostics must observe this same resolution and execution. Instrumented and
non-instrumented entrypoints may have different return envelopes, but they may
not maintain separate eligibility, cache-admission, freshness or fallback
branch trees.

## Frozen Invariants

1. Accepted schema snapshots remain runtime authority.
2. A compiled cache hit cannot select or authorize a schema.
3. Every cached entry is derived from and checked against one pinned accepted
   catalogue fingerprint.
4. Cache absence, loss or fingerprint mismatch affects performance only; the
   outer SQL compiled-command cache owns new-command creation after publication.
5. Exact entity and user-index-prefix cardinality remain owned by the current
   cardinality authority and executor.
6. The exact-count semantic classifier remains singular; execution and
   diagnostics do not reconstruct its policy.
7. SQL retains row-execution fallback when exact metadata is unavailable.
8. Public exact-count APIs retain their typed no-scan failure when exact
   metadata is unavailable.
9. The existing lifecycle-recheck rule continues to prevent stale advisory
   evidence from becoming a compiled decision.
10. Publication, journal overlay/fold, recovery, reinstall and cache loss do
    not gain a new invalidation edge.
11. Missing or corrupt rows and index entries retain the current fail-closed
    behavior of whichever canonical executor is selected.
12. No dynamic dispatch, boxed callback, generic recorder abstraction or new
    allocation may be introduced merely to share the resolver.
13. No public, persisted, stable-memory, cursor, Candid or export shape changes.
14. No compatibility alias or dual cache path remains after the hard cut.
15. An exact entry's prepared fallback is supplied only by the existing
    registry-scoped shared query-plan cache; no nested or adjacent command-local
    fallback cache is permitted.

## Scope

Included:

- the compiled global-aggregate cache entry and its command accessors;
- exact-cardinality target ownership needed by that entry;
- global-aggregate direct-count and prepared-plan resolution;
- diagnostics attribution over the same semantic resolver;
- owner-local tests and the existing exact-count performance sentinels;
- raw and gzip Wasm, complexity and public-surface equality evidence.

Excluded:

- new aggregate semantics or SQL syntax;
- `COUNT(DISTINCT ...)` optimization;
- ordered `DISTINCT` group-seek changes;
- new cardinality metadata or persisted generations;
- changing planner selection, index visibility or cardinality readiness;
- consolidating scalar and grouped executors;
- changing fallback, corruption or recovery semantics;
- a generic cache framework for other command families.

## Rejected Alternatives

### Delete the exact-count specialization

Rejected. It would restore 96M–126M-instruction scans for simple counts and is
contrary to current measured evidence.

### Always prepare the fallback plan with the exact target

Rejected. It keeps two preparations and transfers planner work onto the cold
fast path solely to make the cache shape look uniform.

### Retain two slots behind a new wrapper

Rejected. Moving the existing state into another struct does not remove a
memoized state or reduce the resolver's combinations.

### Add a prepared-plan slot inside the exact variant

Rejected. A nested `OnceLock` would preserve the second memoized state while
making it less visible. Prepared fallback reuse already has a canonical owner
in `QUERY_PLAN_CACHES`.

### Prepare fallback directly and ephemerally

Rejected. Fallback must enter through
`cached_shared_query_plan_for_accepted_authority_with_catalog`, so its complete
schema/visibility/query key and cardinality lifecycle recheck remain singular.

### Create a generic cache or instrumentation abstraction

Rejected. The demonstrated duplication is one owner-local global-aggregate
flow. A generic framework would add concepts and monomorphization risk without
a second evidenced consumer.

### Carry the prepared plan directly in the transient direct-count target

Rejected after closeout measurement. This removed the repeated prepared-plan
extraction branches, but increased final raw SQL audit Wasm from 8,196,454 to
8,212,215 bytes: 15,761 bytes above the selected implementation and 7,251
bytes above the predecessor. The transient target therefore continues to
retain the singular fingerprint-bound entry; this does not add a cache slot or
memoized state.

### Fold `COUNT(DISTINCT ...)` into this line

Rejected. That query needs a separate physical-work and worst-case-distribution
design. Cache convergence neither proves nor authorizes index group traversal
for an unbounded distinct aggregate.

## Complexity And Performance Gates

Implementation is accepted only if all gates pass against the exact authorized
predecessor. For this line, that is the validated but unpublished 0.239.1
candidate explicitly accepted by the user:

| Dimension | Gate |
| --- | --- |

| Production runtime lines | net decrease; no compensating generic framework |
| Production types | net decrease by at least two; reuse the current fingerprint wrapper |
| New execution routes, modes or invalidation edges | zero |

| Candid, exports and stable extent | byte-for-byte or exact equality as applicable |

Raw non-gzipped Wasm is the footprint authority. Gzip remains secondary
context. The comparable Wasm pair must use clean predecessor and candidate
trees, Rust 1.97.1 from `rust-toolchain.toml`, locked dependencies, the
`sql_perf` canister's production `candid-export,diagnostics,sql` feature policy,
production build mode, Cargo `release` profile, Candid export enabled and the
same final link/shrink pipeline. The compared artifact is
`.icp/local/canisters/sql_perf/sql_perf.wasm`; compiler-emitted raw and
deterministic gzip sizes are secondary attribution. Any toolchain, profile,
feature, lockfile or post-link difference makes the pair non-comparable.
Predecessor and candidate builds use separate clean target/staging directories.
The 1,024-byte gate applies only after a same-revision repeat build reproduces
the exact final raw size and SHA-256, excluding stale artifacts and build noise.

If the implementation does not shrink raw Wasm, does not remove a
memoized state, or requires a second semantic route, close 0.240 as a no-build
and revert the candidate rather than weakening these gates.

## Candidate Evidence

The exact 0.239.1 predecessor rebuild reproduced a final raw Wasm of 8,204,964
bytes with SHA-256
`66c4061888838261483bd55d40ce01333199bba79e5e70eebc550312bbd8a82a`.
The current candidate is 8,196,454 bytes with SHA-256
`37c420b19444a996ff831896df1920e1a857174cfeb051bae354186111b0de9c`,
an 8,510-byte reduction; deterministic gzip falls from 2,632,767 to 2,630,288
bytes. A same-source repeat reproduced the exact candidate size and hash.
Compiler-emitted Wasm grows by 6,935 bytes, while the unchanged post-link
pipeline removes an additional 15,445 bytes, producing the authoritative final
raw reduction.

The focused 2,048-row exact-count predecessor/candidate instruction pairs are:

| Query | Predecessor | Candidate | Delta |
| --- | ---: | ---: | ---: |
| `COUNT(*)` | 816,118 | 815,926 | -192 |
| `COUNT(id)` | 855,042 | 854,839 | -203 |
| `COUNT(1)` | 846,040 | 845,837 | -203 |
| `COUNT(*) WHERE true` | 827,975 | 827,783 | -192 |
| true-warm `COUNT(*)` | 731,724 | 731,718 | -6 |

Every case continues to fetch zero rows and visit zero index entries. The
owner-local cache proof covers empty-to-exact, empty-to-prepared, fingerprint
rejection and attempted replacement of a populated entry.

Ordinary prepared aggregates remain materially flat against the isolated
predecessor build:

| Query/path | Predecessor | Candidate | Delta |
| --- | ---: | ---: | ---: |
| cold `COUNT(DISTINCT age)` | 120,671,186 | 120,664,059 | -7,127 |
| warm `COUNT(DISTINCT age)` | 120,460,269 | 120,426,858 | -33,411 |
| cold aggregate `FILTER` | 114,058,947 | 114,088,942 | +29,995 |
| warm aggregate `FILTER` | 113,927,409 | 113,903,815 | -23,594 |

The largest regression is 0.026%, far below the frozen 2% gate. The existing
sentinel now retains the four predecessor figures and enforces their absolute
2% ceilings. The unavailable-metadata lifecycle proof also passes through
fallback, Ready publication, live maintenance and same-Wasm upgrade. Candid is
byte-identical and the normalized 70-method export set is unchanged.

The production-shaped unavailable exact-target fallback now proves the named
shared owner directly. Its first persistent request records one compiled-command
miss and one `QUERY_PLAN_CACHES` miss; the next request records one
compiled-command hit and one shared-plan hit while visiting the same 512 index
entries. Against predecessor cold/warm costs of 116,170,059 and 53,841,143
instructions, the candidate costs 116,237,383 (`+67,324`, `+0.058%`) and
53,976,446 (`+135,303`, `+0.251%`). Both stay below frozen 5% ceilings.

The final production SQL diff removes one mutable cache slot, three production
types and 22 net runtime lines. No compensating cache framework, execution
route, invalidation edge or persisted state was added.
