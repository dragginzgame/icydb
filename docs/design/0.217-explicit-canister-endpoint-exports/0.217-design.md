# 0.217 Explicit Canister Endpoint Exports

Status: implemented through Patches 1-8; closeout audited

Design cut: 2026-07-28

Implementation order: after 0.216 closeout

## Decision Summary

0.217 hard-cuts `icydb.toml` as an authority over generated canister
endpoints. Cargo features determine which IcyDB capabilities can compile.
Source declarations in the canister crate determine which IcyDB methods are
publicly exported.

The maintained rule is:

> Build generation creates private capabilities only. IcyDB's maintained
> source macros are the only route by which IcyDB creates its maintained
> public endpoint wrappers.

Application code remains free to define ordinary IC methods, including a
method whose public name overlaps an `icydb_*` spelling. Such an overlap with
an active IcyDB declaration is a duplicate export and fails the build; it is
not a second IcyDB generation route.

The target-sensitive development rule is:

> Target-sensitive development endpoints are controlled by explicit
> canister-owned Cargo features. The feature enables both the required IcyDB
> capability and its source declaration. Production builds omit that feature,
> producing a separate Wasm in which the endpoint, its endpoint-specific
> private handler, and every capability used exclusively by that endpoint are
> absent.

If another production endpoint or handwritten application API independently
requires a lower-level capability, that shared capability remains compiled;
the local endpoint wrapper and its endpoint-specific handler still disappear.
A feature is not permitted to enable a hidden endpoint without a visible
`#[cfg]` declaration.

A canister that writes only:

```rust
icydb::start!();
```

exports no `icydb_*` Candid method. `start!()` includes the private generated
schema, store, session, proposal, and adapter wiring required by the canister.
It does not imply an operational, observability, SQL, fixture, schema, or
snapshot endpoint.

Public IcyDB methods are declared beside the canister's other IC methods:

```rust
icydb::start!();

icydb::endpoints! {
    #[cfg(feature = "local-sql-query")]
    icydb_sql_query(introspection = true);

    icydb_ddl;
    icydb_update(admission = bounded_deterministic);
    icydb_integrity;

    icydb_metrics(authorization = public);

    #[cfg(feature = "local-extended-metrics")]
    icydb_metrics_extended(authorization = controller);

    icydb_metrics_reset;
    icydb_snapshot;
    icydb_schema(authorization = controller);

    #[cfg(feature = "test-admin-api")]
    icydb_fixtures_reset;

    #[cfg(feature = "test-admin-api")]
    icydb_fixtures_load(handler = load_fixtures);
}
```

Each declaration creates exactly one fixed Candid method. No declaration
creates a family of methods. In particular:

- `icydb_metrics` does not also create `icydb_metrics_reset`;
- `icydb_metrics_extended` does not also create `icydb_metrics`;
- `icydb_fixtures_load` does not also create
  `icydb_fixtures_reset`; and
- `icydb_sql_query` does not create DDL, mutation, integrity, schema, or
  observability methods.

The public macro has no `all`, `admin`, `testing`, `observability`, or other
grouped production preset. Maintained test canisters also list their exact
methods rather than hiding them behind a multi-endpoint helper.

0.217 is a public/build/CLI hard cut before 1.0:

- all seven maintained `icydb.toml` files are deleted;
- config discovery, parsing, precedence, and target resolution are deleted;
- `ICYDB_CONFIG_PATH` and config-driven `ICYDB_BUILD_TARGET` policy are
  deleted;
- `icydb config init`, `show`, and `check` are deleted;
- endpoint preflight no longer consults local source configuration;
- config-derived generated exports are deleted;
- the `icydb-config` crate is deleted after its complete responsibility
  inventory is migrated or removed; and
- no alias, compatibility parser, fallback config path, deprecated macro, or
  dual endpoint-generation route remains.

0.217 changes no accepted schema, row, index, relation, cursor, journal,
commit, receipt, or recovery format.

## Why The TOML Authority Is Removed

`icydb.toml` was introduced as a host-only endpoint-generation configuration
surface. That direction kept TOML out of Wasm runtime execution, but it also
created a second indirect owner of the deployed public interface.

The public API of a canister is expected to be visible in its source. Under the
current shape, a reviewer must inspect:

1. the canister source and Cargo features;
2. the canister `build.rs`;
3. the nearest discovered `icydb.toml`;
4. an optional `ICYDB_CONFIG_PATH` override;
5. the selected local or IC build-target policy; and
6. generated actor output

to know which `icydb_*` methods are exported.

That indirection has concrete costs:

- installing IcyDB requires another manifest and discovery model;
- a root config can affect a nested canister without a source edit;
- local config can disagree with the already deployed Wasm;
- CLI preflight can describe source intent rather than deployed truth;
- endpoint choices duplicate existing typed code-generation options;
- defaults can create methods that are not visible in the canister source; and
- parser, resolver, CLI, reporting, and test code substantially outweigh the
  seven small manifests they serve.

The hard cut keeps the useful distinction between compiled capability and
public exposure while deleting the separate file authority.

### Frozen Production And Test Builds

Patch 5 changes the repository build helpers to pass complete feature sets and
deletes their build-target enum and `ICYDB_BUILD_TARGET` environment writes.
Canonical builds use `--no-default-features`; package defaults are not an
unrecorded input.

The exact command forms are:

```text
CARGO_TARGET_DIR=target/icydb/canister-production \
  cargo build --locked --target wasm32-unknown-unknown --profile wasm-release \
```

`icp.yaml` local environments use the local target. Production packaging uses
the production target. 0.217 does not add `icydb build --local` or
`icydb build --production`; adding CLI build-profile sugar is a separate
design and is not a replacement config authority in this line.

### Ergonomics Relative To TOML

The source design is simpler for endpoint ownership even though local versus
production Wasm composition still has two real controls:

| Concern | `icydb.toml` | Source declaration and Cargo feature |
| --- | --- | --- |
| See exported methods | indirect discovery and generated output | visible in the canister's one `endpoints!` block |
| Invalid endpoint or option | host parser/build error | Rust compile error at the declaration |
| Conditional endpoint | target/config policy | ordinary declaration-level `#[cfg]` |
| Remove exclusive SQL/report Wasm cost | still requires Cargo feature control | canister feature explicitly removes capability and declaration together |
| Stale policy risk | config, build target, and source can disagree | source and feature graph are compiled together |
| Files involved for local-only SQL | TOML plus Cargo/build policy | `Cargo.toml` feature plus visible `lib.rs` declaration |

The source design does not pretend endpoint export and capability composition
are the same concern. Cargo answers whether implementation can compile;
`endpoints!` answers whether one fixed public method exists. The canister-owned
profile feature binds those decisions operationally without making Cargo
features an invisible export authority.

## Authority Model

After 0.217 the authority chain is:

```text
Cargo capability feature
        |
        v
private generated/runtime handler availability
        |
        v
source endpoint declaration
        |
        v
one IC export + one Candid method
```

The following asymmetry is intentional:

- capability compiled, endpoint not declared: valid;
- endpoint declared, required capability not compiled: compile error;
- endpoint undeclared: IcyDB contributes no wrapper or export; in a canister
  without a same-named handwritten application method, it is absent from
  Candid and Wasm;
- endpoint declared inside an inactive `#[cfg]`: absent from generated Candid
  and Wasm exports;
- endpoint declared twice in one active build: compile error; and
- CLI call to an undeployed method: report the replica/method-not-found
  failure without consulting local configuration.

An undeclared IcyDB endpoint is not emitted as a guarded stub returning
"disabled." There is no runtime endpoint registry and no dynamic dispatch
that can make an undeclared maintained wrapper reachable.

## Source Declaration Contract

### Placement

`icydb::start!()` and every `icydb::endpoints!` invocation are crate-root-only
items in the canister library. Nested-module invocation is unsupported and
must fail a compile fixture. There is no supported same-module-but-nested
form.

Exactly one active `start!()` invocation is required. It owns:

- the fixed private crate-root module `crate::__icydb_generated`;
- the fixed generated-actor binding marker used by `endpoints!`;
- inclusion of the one `OUT_DIR/actor.rs` produced for this canister crate;
  and
- private database and endpoint-handler wiring.

Two active `start!()` invocations collide on the fixed module and binding
marker and fail compilation. `endpoints!` without `start!()` expands a
compile-time reference to the named binding marker and fails with a targeted
"call `icydb::start!()` exactly once at crate root" diagnostic. An inactive
`#[cfg]` invocation does not count.

Declaration order does not matter. Rust item resolution permits `endpoints!`
to appear before or after `start!()` in the crate root, and both orders are
compile fixtures.

The build script generates exactly one actor module for the consuming
canister crate. `endpoints!` accepts no actor argument and can bind only to
`crate::__icydb_generated`; it cannot select another generated actor. The
single-argument build macro described below removes the independently authored
string path that could otherwise select a different model.

Each canister has zero or one active `endpoints!` invocation. Conditional
publication belongs on individual declarations inside that block:

```rust
icydb::start!();

icydb::endpoints! {
    icydb_schema(authorization = controller);

    #[cfg(feature = "local-extended-metrics")]
    icydb_metrics_extended(authorization = controller);
}
```

A second active `endpoints!` invocation collides on a fixed crate-root
declaration-registry marker and fails compilation. One block makes the whole
IcyDB-generated public interface reviewable in one source location and lets
the macro reject duplicate method declarations before Rust/IC export
generation.

An ordinary handwritten `#[query(name = "icydb_schema")]` or equivalent
`#[update]` using the same Candid name as an active declaration also fails the
canister build through duplicate IC export/Candid registration. There is no
first-wins or last-wins precedence. Compile and Wasm-link fixtures cover both
query and update collisions.

`icydb::endpoints!` owns the method attributes and therefore contributes the
declared methods to IC CDK's method registry. The canister's one
`ic_cdk::export_candid!()` invocation remains the owner of Candid metadata
collection and export. `start!()` does neither. Omitting
`export_candid!()` omits the Candid custom section but does not remove the
actual IC methods; maintained builds enable `candid-export` so the two
artifacts can be compared.

### Closed Grammar

The macro accepts only the endpoint declarations frozen by this document.
It rejects:

- unknown endpoint names;
- duplicate declarations in one invocation;
- a second active invocation in the same crate;
- missing required options;
- unknown options;
- repeated options;
- options belonging to another endpoint;
- declaration attributes other than `#[cfg(...)]`;
- arbitrary Candid names;
- arbitrary query/update mode selection;
- grouped aliases or presets; and
- arbitrary handler signatures.

Each declaration accepts zero or more ordinary `#[cfg(...)]` attributes.
They are copied to the generated wrapper, its capability assertion, its
private-handler reference, and its Candid registration as one unit. An
inactive declaration therefore triggers no missing-capability diagnostic and
retains no endpoint-specific handler. Multiple attributes have ordinary Rust
AND semantics. `cfg_attr`, `doc`, lint, export, name, and arbitrary procedural
attributes are not part of the grammar.

Endpoint names are fixed. The macro does not support renaming
`icydb_schema` to an application-selected method name or mapping one
declaration to several aliases.

### One Declaration, One Method

Each accepted declaration expands directly to:

1. one Rust wrapper item with one collision-stable internal name;
2. one `ic_cdk` query or update attribute;
3. one fixed public Candid name;
4. one authorization path;
5. one call to one private IcyDB handler; and
6. no other exported item.

Shared private types, authorization helpers, and handler functions may be
referenced by several wrappers, but they are not Candid methods and do not
carry export attributes.

### Exact Candid Method Shapes

The following is the exact top-level service shape. Type names stand for the
structural Candid definition derived from the identically named public Rust
type; they are not opaque blobs and are not application-selected aliases.

```text
icydb_query :
  (text) -> (variant { Ok : SqlQueryPerfResult; Err : IcydbError }) query
icydb_ddl :
  (text) -> (variant { Ok : SqlQueryResult; Err : IcydbError })
icydb_update :
  (text) -> (variant { Ok : SqlQueryResult; Err : IcydbError })
icydb_integrity :
  (text) -> (variant { Ok : IntegrityCheckResult; Err : SqlIntegrityError })
icydb_fixtures_reset :
  () -> (variant { Ok : null; Err : IcydbError })
icydb_fixtures_load :
  () -> (variant { Ok : null; Err : IcydbError })
icydb_metrics :
  (opt nat64) -> (variant { Ok : CompactMetricsReport; Err : IcydbError }) query
icydb_metrics_extended :
  (opt nat64) -> (variant { Ok : EventReport; Err : IcydbError }) query
icydb_metrics_reset :
  () -> (variant { Ok : null; Err : IcydbError })
icydb_snapshot :
  () -> (variant { Ok : StorageReport; Err : IcydbError }) query
icydb_schema :
  () -> (variant { Ok : vec EntitySchemaDescription; Err : IcydbError }) query
```

Patch 1 checks in the canonical transitive Candid definitions for
`IcydbError`, `SqlQueryResult`, `IntegrityCheckResult`,
`SqlIntegrityError`, `CompactMetricsReport`, `EventReport`,
`StorageReport`, and `EntitySchemaDescription` from the current public Rust
types before endpoint generation changes. Those checked-in definitions, plus
the service lines above, are normative ABI fixtures. A field, variant, label,
numeric width, optionality, tuple/record layout, or nested type change is a
Candid contract change and cannot be hidden behind this endpoint migration.

`SqlQueryPerfResult` becomes the public
`icydb::db::sql::SqlQueryPerfResult` DTO with this exact Candid record:

```text
record {
  result : SqlQueryResult;
  instructions : nat64;
  planner_instructions : nat64;
  store_instructions : nat64;
  executor_instructions : nat64;
  pure_covering_decode_instructions : nat64;
  pure_covering_row_assembly_instructions : nat64;
  decode_instructions : nat64;
  compiler_instructions : nat64;
}
```

This is a relocation of the current generated DTO, not a payload redesign.
To make the public SQL result ABI independent of capability selection, Patch 2
also keeps the outward `SqlQueryResult::Explain { entity, explain }` variant
compiled whenever `icydb/sql` is compiled. `icydb/sql-explain` continues to
control parsing and execution of `EXPLAIN`; it no longer changes the public
result enum's Candid shape.

### Authorization Failure Contract

Authorization executes in the generated public wrapper before its private
handler. A failed check returns the typed value below. It does not call the
handler, reject the ingress message, or trap.

| Endpoint class | Required check | Exact authorization failure |
| --- | --- | --- |
| SQL query, DDL, update, fixture reset/load | caller is a controller | `Err(icydb::Error)` with `RuntimeBoundaryCode::SqlSurfaceControllerRequired` and `ErrorOrigin::Interface` |
| SQL integrity | caller is a controller | `Err(SqlIntegrityError::Sql(icydb::Error))` carrying `RuntimeBoundaryCode::SqlSurfaceControllerRequired` and `ErrorOrigin::Interface` |
| Schema with `authorization = controller` | caller is a controller | `Err(icydb::Error)` with `RuntimeBoundaryCode::SchemaSurfaceControllerRequired` and `ErrorOrigin::Interface` |
| Metrics reports with `authorization = controller`, metrics reset, snapshot | caller is a controller | `Err(icydb::Error)` with the new `RuntimeBoundaryCode::OperationalSurfaceControllerRequired` and `ErrorOrigin::Interface` |
| Metrics or schema with `authorization = public` | no IcyDB authorization check | not applicable; handler failures still return their declared typed error |

`AUTH` is not a string and does not accept an arbitrary policy object.

### SQL Authorization

The fixed `icydb_query`, `icydb_ddl`, `icydb_update`, and
`icydb_integrity` methods remain controller-owned administrative surfaces.
0.217 does not reopen the read-admission contract by turning
`icydb_query` into a public SQL template.

Applications that want public or application-authorized reads and mutations
continue to define ordinary canister methods and call the maintained dynamic,
typed, structural, or SQL session APIs themselves. Application authorization
is application code, not a loose option on the fixed administrative endpoint
macro.

### SQL-Query Naming And Introspection

The source declaration is deliberately named `icydb_sql_query` after R7
because it requires the SQL frontend and exports the historical
controller-only SQL administration method. The fixed Candid name remains
`icydb_query` to avoid an unrelated deployed-method rename. Neither name
denotes the engine-neutral `icydb/query` Rust capability.

`introspection = false` admits ordinary read-only `SELECT` and rejects
`EXPLAIN`, `DESCRIBE`, `SHOW CONSTRAINTS`, `SHOW INDEXES`, `SHOW COLUMNS`,
`SHOW ENTITIES`, `SHOW STORES`, and `SHOW MEMORY` before execution with
`Err(icydb::Error)` carrying
`RuntimeBoundaryCode::SqlIntrospectionDisabled` and
`ErrorOrigin::Interface`.

`introspection = true` admits those operational-introspection families.
Because that contract includes `EXPLAIN`, the declaration requires both
`icydb/sql` and `icydb/sql-explain`. A `true` declaration without
`sql-explain` is a targeted compile error rather than a reduced runtime
contract. The option changes admission only; the wrapper signature and Candid
shape are identical for `true` and `false`.

### Update Admission

`admission` describes the sealed SQL mutation shapes accepted after
authorization. It is not an authorization policy.

The only accepted values are:

- `primary_key_only`; and
- `bounded_deterministic`.

The old TOML boolean `update = true`, its implicit mapping, and the old
`GeneratedSqlUpdatePolicy` config vocabulary are deleted. No default admission
mode is inferred. Omitting `admission` is a macro error.

### Read-Only Report Authorization

Metrics and schema reports require an explicit `authorization` token because
both public and controller-only deployment choices are legitimate. There is
no default.

Snapshot reports are controller-only in 0.217 because they expose physical
storage and allocation state. Metrics reset is controller-only because it
mutates operational state.

0.217 does not add arbitrary authorization callbacks to the macro. A canister
requiring application-specific authorization writes an ordinary endpoint and
calls the corresponding maintained IcyDB API. This keeps the endpoint macro a
closed export declaration rather than a general policy language.

## Fixture Safety Contract

IcyDB's maintained fixture declarations require three independent properties:

1. an exact source declaration for each exported method;
2. an active canister-owned `test-admin-api` Cargo feature; and
3. controller authorization at runtime.

Rust cannot prevent an application from hand-writing an unrelated IC method
with the same public spelling. Such a method is wholly application-owned and
does not receive IcyDB's safety claims. After Patch 5, maintained repository
canisters contain no handwritten `icydb_fixtures_reset` or
`icydb_fixtures_load` export; the source and Wasm checks enforce that local
policy.

A fixture declaration without the consuming canister feature fails at compile
time with a targeted diagnostic. Enabling the feature without a source
declaration exports nothing.

The canister manifest must declare the feature explicitly:

```toml
[features]
test-admin-api = []
```

`test-admin-api` must not appear in the package's `default` feature list. A
production build does not enable it. Deployment scripts and tests that need
fixture methods request it deliberately.

The load declaration accepts one handler path with the exact signature:

```rust
fn() -> Result<(), icydb::Error>
```

Macro expansion performs a function-item coercion to that signature. Async
handlers, arguments, alternate error types, generic callables, closures, and
implicit naming conventions reject at compile time.

Reset uses the private generated reset capability derived from the current
canister's accepted entity closure. Load invokes reset first through that same
private capability and then invokes the explicitly named handler. The load
declaration still creates only the `icydb_fixtures_load` method; reset is
public only when separately declared.

Fixture reset and load are deliberately non-transactional administrative test
operations. The exact sequence is:

1. authorize the caller before any mutation;
2. reset accepted entities in deterministic generated order using their
   normal committed mutation paths;
3. if reset completed, invoke the custom handler; and
4. return the first typed `icydb::Error`, if any.

There is no transaction spanning all reset operations and handler writes, no
compensating reset, and no rollback of already committed work. A reset failure
may leave some entities reset. A load-handler failure may leave the database
fully reset or partially reloaded, depending on which normal mutations the
handler committed before returning `Err`.

This behavior is acceptable only because the endpoint is controller-only and
requires the explicit test capability. Recovery is explicit: fix the cause,
call reset again, then call load again. Fixture handlers are expected to be
deterministic under that retry sequence, but the macro does not pretend an
arbitrary user function is one atomic mutation transaction.

## Capability Checks

The public facade owns hidden compile-time capability assertions. Endpoint
macro expansion invokes the relevant assertion before emitting a wrapper.

For example, SQL declarations use an assertion selected by how the `icydb`
dependency itself was compiled:

```text
icydb built with feature "sql"     -> assertion expands successfully
icydb built without feature "sql"  -> assertion emits a targeted compile error
```

The capability conjunctions are exact:

- `icydb_sql_query(introspection = false)`, DDL, update, integrity, and both
  fixture declarations require `icydb/sql`;
- `icydb_sql_query(introspection = true)` additionally requires
  `icydb/sql-explain`;
- fixture declarations additionally require the consuming canister's active
  `test-admin-api` feature; and
- extended metrics requires `icydb/metrics-extended`;
- compact metrics, metrics reset, snapshot, and schema require no optional
  IcyDB feature beyond the base runtime.

`icydb/diagnostics` is present in local SQL tests and the performance canister
but is not an endpoint-declaration capability. Enabling or disabling it never
creates or removes a method.

The check does not rely only on a same-named feature in the consuming
canister. A canister feature may forward to `icydb/sql`, but the dependency's
actual compiled capability is authoritative.

Capability checks produce diagnostics that name:

- the endpoint declaration;
- the missing IcyDB Cargo feature; and
- the expected dependency feature spelling.

They do not silently omit an active declaration.

After the hard cut, build generation may emit:

- store declarations and registry wiring;
- accepted schema proposal bytes and submission metadata;
- private database/session constructors;
- typed adapter binding support;
- private SQL dispatch helpers when `sql` is compiled;
- private fixture reset support;
- private schema-description support;
- private metrics and snapshot handlers; and
- private types used by source-declared wrappers.

Private generated output must contain none of:

- `#[update]`;
- `#[export_name]`;
- `#[no_mangle]`;
- `canister_query ...` export construction;
- `canister_update ...` export construction; or
- another attribute or linker route that can create a public IC method.

The code-generation tests inspect syntax structure and exact forbidden tokens.
The Wasm tests remain final authority over whether an accidental export
exists.

### `start!()` Invariant

`icydb::start!()` continues to include the generated private actor module.

The frozen 0.217 invariant is:

> `start!()` creates no public Candid method and no IC query or update export.

At the design cut `start!()` does not install lifecycle exports. Adding
initialization, upgrade, timer, heartbeat, or other lifecycle exports later
requires a separate explicit design. 0.217 does not rename `start!()` because
that naming cleanup is independent from endpoint authority.

## Build-Script Surface

Canister build scripts continue to select the authored canister model whose
private wiring is generated. They no longer select a config entry or endpoint
policy.

The intended shape is:

```rust
fn main() -> Result<(), Box<dyn std::error::Error>> {
    icydb::build::build_canister!(application_schema::Canister);

    Ok(())
}
```

The config canister-name argument is removed because no TOML lookup remains.
The duplicated string model path is also removed: the macro obtains the
generation path with `stringify!($canister_ty)` from the same typed argument
used for the host-side type check. That makes a separately authored type/path
drift unnecessary and ensures the one generated actor binding names the
selected type.

`build_configured_canister!` is deleted rather than retained as an alias or
tombstone. The testing helper forwards the same one typed argument to
`build_canister!`.

Public build options that exist only to choose endpoint exports are deleted.
Any code-generation option proven unrelated to public endpoint selection is
retained under the narrow private build owner. At the design cut the only
non-endpoint option in `BuildOptions` is dependency path rewriting; it remains
an internal/testing concern rather than justification for a project config
file.

The hard cut names the current live symbols explicitly:

- `icydb_model::build::BuildOptions` and `BuildSqlUpdatePolicy` cease to be
  public exports;
- `icydb_model::build::generate_with_options` is deleted as a public entry
  point;
- any still-required dependency-path rewrite input is moved to a narrow
  package-private generator argument rather than preserving a generalized
  public options carrier; and
- schema-only build fixtures call the maintained typed build boundary instead
  of keeping the retired options API reachable for tests.

These symbols are not removed before the Patch 5 authority cut because
`icydb-config` still calls them today. Patch 5 removes their live config
consumer and the symbols in the same handoff; Patch 6 verifies that no hidden
test, example, or build-script consumer kept them alive.

Removing `build.rs` entirely is outside 0.217. The current model graph is
sealed and rendered at host build time; replacing that generation architecture
is a separate project.

## Cargo Feature Role

Cargo features own compilation capability, not public exposure.

Examples:

- `icydb/sql` compiles SQL parsing, lowering, execution, and private handler
  support;
- `icydb/query` compiles engine-neutral query capability;
- `icydb/sql-explain` compiles explain capability;
- `icydb/metrics-extended` compiles rich metrics report construction and its
  public DTO graph;
- `icydb/diagnostics` compiles diagnostic capability; and
- a canister-owned `test-admin-api = ["sql"]` feature compiles the fixture
  dependency capability and activates the visible fixture declarations.

Features may conditionally include source endpoint declarations:

```rust
icydb::endpoints! {
    icydb_metrics(authorization = controller);

    #[cfg(feature = "local-extended-metrics")]
    icydb_metrics_extended(authorization = controller);

    icydb_schema(authorization = controller);
}
```

This does not make the feature a second export authority. With the feature
enabled, the source declaration is compiled and owns the export. With the
feature disabled, the declaration is inactive and contributes no export.
For a target-sensitive development endpoint, the canister feature must also
forward the exact IcyDB capability required by that declaration; a cfg-only
feature that leaves the exclusive capability compiled in production does not
satisfy this design.

A downstream canister whose entire SQL administration surface is local-only
uses the direct shape:

```toml
[features]
default = []
local-admin-api = ["icydb/sql", "icydb/sql-explain"]
```

```rust
icydb::start!();

icydb::endpoints! {
    #[cfg(feature = "local-admin-api")]
    icydb_sql_query(introspection = true);
}
```

Its local build enables `local-admin-api`. Its production build uses
`--no-default-features` without that feature. The production Wasm therefore
contains neither `icydb_query` nor the SQL/query/explain capability pulled in
solely for it.

IcyDB does not add dependency features such as:

- `export-all-endpoints`;
- `export-admin`;
- `export-metrics`;
- `export-schema`; or
- `export-fixtures`.

Such features would again make dependency configuration create methods that
are not visible as active source declarations.

It retains no project-config command, parser, dependency, preflight, report,

### Operational Call Behavior

SQL, metrics, snapshot, and schema commands:

1. verify that the selected canister exists in the selected ICP environment;
2. call the fixed method on the deployed canister;
3. decode and render a successful typed result; and
4. preserve the actual replica/tooling failure when the method is absent.

The shared call-error renderer may append a source-declaration hint keyed by
the attempted fixed method, but it must retain the original method-not-found
diagnostic and must not inspect the checkout, Cargo features, a manifest, or a
generated Candid file. For `icydb_query`, the hint names
`icydb_sql_query(introspection = false)` and notes that `true` additionally
requires `sql-explain`; it does not claim which choice the deployed canister
should use.

The CLI never claims that the source currently checked out matches the
deployed Wasm. Deployed behavior is authoritative for an operational call.

`icydb canister refresh` remains an explicit fixture-refresh workflow. After
reinstall it attempts `icydb_fixtures_load` without local preflight:

- success loads fixtures;
- method-not-found, authorization, handler, cycles, transport, and decode
  failures remain failures with their original diagnostic.

No other lifecycle command attempts fixture loading. This preserves useful
local refresh behavior without reconstructing an endpoint registry or
matching replica error strings in the CLI.

## Candid And Wasm Verification

Generated Candid and built Wasm are complementary authoritative evidence of
the public surface. Token-string tests alone are insufficient.

- the Wasm export section proves the public method name and whether the IC
  export is `canister_query` or `canister_update`;
- generated Candid proves the public method name, argument shape, result
  shape, and declared query/update mode; and
- runtime calls prove authorization and handler behavior.

Neither artifact alone proves every property. In particular, Wasm exports do
not encode argument/result types, while a Candid file does not prove that no
extra linker export escaped into the built module.

### Required Positive Evidence

For every declaration, a focused canister proves:

- exactly one method is added to Candid;
- exactly one matching IC query or update export is added to Wasm;
- the name and mode agree across the two artifacts;
- Candid argument and result types match the normative golden definitions;
- authorization behavior is exact; and
- the wrapper calls the maintained private handler.

### Required Negative Evidence

The matrix proves:

- `start!()` alone exports no `icydb_*` method;
- a compiled capability without a declaration exports nothing;
- an inactive conditional declaration exports nothing;
- in a fixture with no same-named handwritten method, an undeclared IcyDB
  endpoint is absent from Candid and Wasm rather than present as a disabled
  stub;
- a fixture with `icydb/query` compiled and no endpoint declarations contains
  no IcyDB SQL-admin, fixture, snapshot, schema, metrics, or mutation export;
- private generated actor output contains no endpoint-producing attribute;
- fixture declarations fail without `test-admin-api`;
- SQL declarations fail without `icydb/sql`;
- `icydb_sql_query(introspection = true)` fails without
  `icydb/sql-explain`;
- `endpoints!` without `start!()` fails clearly;
- two active `start!()` invocations fail;
- two active `endpoints!()` invocations fail;
- nested `start!()` or `endpoints!()` invocations fail;
- declaration order on either side of `start!()` succeeds;
- duplicate declarations fail;
- declaration attributes other than `#[cfg(...)]` fail;
- a handwritten query or update with the same Candid name fails;
- unknown names and options fail;
- wrong fixture handler signatures fail; and
- no deleted config path can influence the resulting export set.

### Custom Handler Evidence

Two different valid fixture load handlers produce the same public Candid
signature. An invalid handler signature fails compilation. Handler selection
changes only the private function called after authorization and reset; it
never changes the exported method contract.

### Conditional Feature Evidence

One canister is built twice from the same source:

1. without the canister-owned endpoint feature; and
2. with the endpoint feature.

The Candid and Wasm export diff contains exactly the methods declared inside
the conditional declaration and no other IcyDB method. The production artifact
also lacks the endpoint-specific handler and any IcyDB capability enabled
exclusively by that canister feature. Raw non-gzipped Wasm is the authority for
the absence claim.

The repository also builds every row in the seven-config migration matrix and
the two implicit-default consumers with their exact production and local/test
feature sets. The expected difference is limited to `local-sql-query`,
`local-extended-metrics`, and `test-admin-api` behavior frozen above.

The minimal downstream installation no longer requires an IcyDB manifest:

2. keep the one-line private canister build generation;
3. call `icydb::start!()` in the canister source; and
4. list any desired public IcyDB methods explicitly with

- a canister with no IcyDB exports;
- controller-only operational methods;

  `icydb_sql_query`, while its Candid name remains `icydb_query`; and
- `SqlQueryResult` keeps a feature-independent outward `Explain` variant so
  endpoint Candid does not vary with `sql-explain`.

No persisted format changes. Rebuilding and redeploying changes actor exports,
not accepted database state.

## Principal Risks

### Macro Registration And Candid Drift

IC CDK attributes emitted by a declarative macro must participate in Candid
export exactly as ordinary source attributes do. The Candid/Wasm matrix is a
release gate, not an optional test.

### Private Helper Retention

Generating private capability helpers for an undeclared endpoint could retain
Wasm unexpectedly. Raw non-gzipped Wasm comparisons must prove linker
elimination or motivate a narrower private generation boundary. Source
complexity is not exchanged for unmeasured Wasm growth.

### Conditional Duplicate Detection

The one-block rule lets the macro reject duplicate declarations directly.
The fixed crate-root registry marker rejects a second active invocation, and
fixed internal Rust/IC export names remain the final collision guard against
handwritten same-name methods. Compile-fail fixtures prove each diagnostic is
understandable.

### Crate-Root Enforcement

Rust function-like macros do not receive an abstract module parent as an
ordinary input. The implementation must make root placement structural
through the fixed crate-root binding/module contract, not merely document a
preference. Nested-placement compile fixtures are a gate for the public macro.

### Feature Confusion

A canister feature may conditionally include a declaration, but the source
still contains that declaration. Documentation must keep "capability" and
"export" terminology distinct.

### Fixture Leakage

Source declaration, `test-admin-api`, and controller authorization are all
required. Release checks build production canisters without the test feature
and search their Candid/Wasm exports for fixture names.

### Loss Of Central Manifest View

The removed root TOML offered a centralized view across canisters. That view
was not authoritative for deployed Wasm and does not justify a second export
owner. Repository searches and generated Candid provide current-source and
built-artifact views respectively.

## Pre-Cut Internal Staging Boundary

Patches 3 and 4 do not define, export, or re-export any function-like endpoint
macro, including one named with an `__icydb_*` prefix or marked
`#[doc(hidden)]`.

They add only package-private machinery inside the existing build/codegen
owner:

- `pub(crate)` declaration/specification values representing the closed
  endpoint vocabulary;
- `pub(crate)` validation and wrapper-token emitters;
- package-private authorization and capability descriptors; and
- unit/snapshot tests in that same crate.

No production crate can name those items, and no test-only crate becomes a
normal dependency. Patches 3 and 4 therefore test parser/emitter semantics,
fixed wrapper tokens, handler selection, and internal validation without
creating a callable downstream route.

Patch 5 alone adds the public `icydb::endpoints!` grammar, the expansion-only
hidden support that the public macro requires, and downstream compile/UI
fixtures. That same patch deletes the old generated-export authority. A
`#[doc(hidden)]` exported prototype before Patch 5 is expressly forbidden.

### Post-closeout Patch 7: query-only grouped fluent activation

The follow-up feature-ownership audit established that grouped planning,
execution, limits, cursor validation, and public-value conversion are
engine-neutral `query` responsibilities, but no maintained non-SQL frontend
can currently invoke them. Patch 7 exposes that existing lane without adding a
planner, executor, SQL DTO, or generated-model authority.

The public request remains `DynamicQuery`, extended with ordered group fields,
ordered `AggregateExpr` declarations, explicit `grouped_limits(max_groups,
max_group_bytes)`, and an opaque continuation cursor. Dynamic callers use a
grouped session terminal; typed `Query<E>` forwards the same declarations and
uses its accepted source binding only to select and revalidate the entity.
Both enter the existing `StructuralQuery`, accepted-schema plan cache, grouped
executor, and public-value finalizer.

The result is one engine-neutral grouped page containing the accepted entity
name, ordered `GroupedRow` values, returned row count, and optional opaque next
cursor. Public execution uses the existing bounded-read admission policy;
trusted dynamic execution bypasses only admission, matching the existing
scalar dynamic contract. SQL continues to adapt the same grouped result into
its own response envelope.

Patch 7 does not add HAVING syntax, a second cursor format, generated physical
decoding, Rust-struct-driven planning, or a compatibility facade. It changes
no accepted schema, persisted data, existing SQL response, or cursor wire
format.

### Post-closeout Patch 8: grouped facade hardening

Patch 8 keeps Patch 7's architecture unchanged and closes two evidence gaps.
Malformed terminal shape and scalar-selection requests are query-intent
failures; absent or zero grouped limits use the existing grouped read-admission
diagnostic. Public group-budget, full-scan, and opaque-cursor failures retain
their existing accepted policy/cursor diagnostics. Caller mistakes must never
surface as planner invariants.

The one-entity query-only canister executes the generated
`Query<E>::execute_grouped()` terminal natively and verifies that its missing
limit rejection crosses the typed facade with exact structured diagnostic
identity. This is runtime evidence for the generated boundary, not a new
planner, adapter, endpoint, or response representation.

Patch 8 adds no HAVING, typestate builder, SQL DTO, compatibility surface, or
new diagnostic wire code. It changes no successful query result, accepted
schema, persisted data, cursor, or SQL response format. The only outward
behavior correction is the error class/origin/detail for malformed dynamic or
typed grouped requests.

One landing patch is the maximum implementation batch per turn. Completion of
one patch does not authorize the next.
