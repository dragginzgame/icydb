# 0.220 Measured Runtime Footprint And Query-Cost Contraction

Status: proposed; implementation not started

Design cut: 2026-08-04

Implementation order: after 0.219 closeout

## Decision Summary

0.220 is a bounded optimization line. It adds no product feature, SQL syntax,
public endpoint, schema semantic, or persisted format. It makes the current
runtime cheaper to deploy and cheaper to execute by acting only on measured
retained Wasm and current instruction evidence.

The line has four ordered objectives:

1. hard-cut the performance and Wasm evidence to one post-0.219 measurement
   identity;
2. make a pinned post-link optimizer part of the canonical deployable-Wasm
   pipeline when runtime proof accepts it;
3. remove measured metrics, schema-application, and SQL-boundary retention
   without creating a second semantic owner; and
4. remediate exactly one current ordered-range execution family selected by
   the refreshed profile.

The raw non-gzipped final deployable `.wasm` is size authority. Compiler output,
gzip, symbol-bearing attribution builds, function counts, and section sizes are
supporting evidence only. IC local instructions are execution-cost authority;
host latency is not used as a substitute.

0.220 consumes the completed 0.206 executor-remediation and 0.215 performance
contracts. It does not reopen their algorithms, revive retired baselines, or
start an executor rewrite. The current audit indicates that the largest safe
opportunities are whole-program code generation, discarded query-side metrics
work, repeated metrics representation, schema-application code shape, SQL
boundary dependency reachability, and ordered result materialization.

Seven landing patches cover the line. Each patch owns one end-to-end outcome,
its direct tests and evidence, its status update, and its root `Unreleased`
note when code changes. The design and status tracker themselves are
governance-only and require no release note.

### Symbol-Bearing Attribution

The `wasm-attribution` profile localizes retained code but is not deployable
size authority. Its shallow-symbol classification attributes approximately:

- 0.80 MB of the typed subject and 0.92 MB of the SQL subject to core schema
  code;
- 0.21 MB typed and 0.33 MB SQL to executor code;
- 0.25 MB typed and 0.32 MB SQL to query code; and
- 0.14 MB of the SQL subject specifically to SQL-owned code.

The largest named schema functions include existing-store candidate lowering,
application-candidate lowering, initial-store lowering, schema proposal
composition, and accepted-snapshot decoding. These measurements do not imply
that all schema code is removable. They identify the canonical schema
application owner as the place to inspect for repeated code generation,
monomorphization, and equivalent lowering shapes.

Generated `db()` currently calls a `OnceCell`-guarded schema application
boundary. Source inspection proves only process-local guard ownership; it does
not prove cross-message persistence. If an empty guard is first set during an
IC query, query heap rollback may discard the set and make a later query repeat
schema application. Upgrade also starts a fresh heap guard.

Patch 1 therefore measures schema-application lifecycle directly:

- the first query after install;
- the second query without an intervening update;
- the first query after upgrade;
- a query after an update has initialized the guard; and
- the maintained query-only actor, with an endpoint that distinguishes schema
  initialization failure from a legitimate empty result.

The evidence records schema-application outcome counters and total/phase
instructions for each case. Until that matrix is accepted, 0.220 does not call
Patch 5 footprint-only work. Repeated reconciliation may make Patch 5 a
query-cost remediation as well as a size contraction.

### Metrics Retention

The isolated metrics subject is 284,848 bytes above the empty subject. Current
instrumentation constructs path-owned events, and global dispatch repeatedly
looks up `BTreeMap<String, EntityCounters>` entries. `EntityCounters` also
stores a large field-per-counter state shape with a correspondingly broad
dispatch surface.

Core metrics state already declares that query-side instrumentation is not
surfaced because IC query heap changes do not persist. The opening question is
therefore not whether query metrics should become durable. It is whether
generated query method context can avoid global state work that will be
discarded while preserving explicit call-local attribution sinks and all
update-side metrics.

### Current Instruction Signal

One focused current P1 shard ran 235 scenarios without failure under PocketIC
15. Its aggregate local-instruction total was 794,084,035 versus 808,574,301
for the same scenario keys in the preserved 0.215 PocketIC 14 shard, a
directional reduction of 1.79%.

That comparison is not an accepted performance delta because the PocketIC
major version changed. It is only a no-obvious-regression signal.

The leading current scenario costs 24,941,814 instructions:

| Phase | Instructions |
| --- | ---: |
| compile | 252,437 |
| execute | 24,689,377 |
| planner | 280,373 |
| store | 6,694,209 |
| executor | 17,705,264 |

The highest current family remains ordered/range result execution. Compilation
is not the dominant phase in those cases. Patch 7 must select its exact family
from the accepted Patch 1 profile and remove general owner-level work rather
than special-case a scenario.

## Problem Statement

### 1. The Current Evidence Identity Is Split

The maintained 0.215 performance identity names PocketIC 14, while the current
host integration dependency requires PocketIC 15. The historical Wasm audit
also lacks several current target identities. Cross-version numbers can expose
gross drift, but they cannot accept or reject an optimization.

0.220 needs one clean post-0.219 source, toolchain, PocketIC binary, fixture,
feature graph, artifact pipeline, and profile identity before changing
production behavior.

### 2. The Deployable Pipeline Leaves Proven Structural Size Work

The Rust profile already uses `opt-level = "z"`, fat LTO, one codegen unit,
symbol stripping, and aborting panics. Exploratory Binaryen output is about
9% smaller for all three runtime-heavy query subjects. Ignoring that result
would direct the line toward riskier source rewrites before proving the safer
whole-program transformation.

The transformation is not free merely because it parses. It can change
instruction count, stack shape, custom sections, exports, and runtime behavior.
It needs a pinned tool contract and current IC execution evidence.

### 3. Query Metrics Can Perform Non-Durable Work

Metrics state is update-only by contract. Query execution can still construct
events, own entity-path strings, dispatch a large event enum, and mutate heap
state that the IC discards at the end of the query call.

The runtime needs an explicit method-context rule. Durable global metrics are
suppressed only inside a proven query method, while scoped attribution sinks
remain usable for performance evidence and update methods retain existing
metrics semantics.

The current generated IcyDB endpoint surface is synchronous. Patch 3 freezes a
synchronous closure-scoped context, not an async task-local approximation. A
query wrapper enters context only while invoking one synchronous handler. It
cannot retain the context in a returned `Future`, across `.await`, or across an
inter-canister callback. A future async/composite endpoint must enter a fresh
context independently for each synchronous poll/callback execution.

### 4. Metrics Representation Is Wider Than Its Semantic State

The metrics endpoint capability retains a large field-per-counter structure,
many repeated entity-path lookups, and broad match-driven dispatch. This makes
instrumentation expensive in code size even when an actor exposes only the
compact report.

One compact internal metric-code registry and dense counter storage can be
considered only if it preserves the current outward report and counter
semantics. 0.220 does not remove maintained metrics to make the binary smaller.

### 5. Schema Application Dominates Symbol-Bearing Attribution

Every generated actor must establish the current accepted schema and continue
to treat accepted snapshots as runtime authority. That requirement does not
make repeated generic lowering, duplicate initial/existing shapes, or avoidable
monomorphization necessary.

The schema patch must contract the existing `apply_schema` implementation. It
must not add a generated fast path, a second reconciliation algorithm, a
source-model reconstruction fallback, or a reduced bootstrap semantic.

### 6. SQL Retains A Distinct Boundary Premium

The one-entity SQL subject retains about 0.43 MB beyond typed query. Attribution
also identifies general Candid/scalar dependency code, including formatting,
big-number, time, CBOR, and Wasm/JavaScript adapters, in runtime-heavy actors.

Not every named dependency is removable: public scalar and Candid semantics
remain supported. Patch 6 first proves an exact dominator and consumer boundary,
then removes one selected general-purpose runtime reachability path without
changing wire or value semantics.

### 7. Ordered Result Execution Still Owns The Leading Instruction Cost

The current leading queries spend the overwhelming majority of their cost in
store and executor phases. This resembles the bounded-order families audited
in 0.206, but 0.220 does not assume the old remediation is incomplete.

Patch 7 reranks the current profile, classifies required scan work separately
from avoidable decode, materialization, copying, selection, and response work,
and selects exactly one current owner-level candidate.

## Goals

0.220 must:

1. establish one exact post-0.219 Wasm and performance evidence identity;
2. make raw final deployable Wasm bytes the primary size metric;
3. preserve compiler-emitted and attribution artifacts as supporting evidence;
4. pin every new Wasm transformation tool, version, feature, and pass order;
5. prove transformed artifacts through maintained IC runtime behavior before
   making them canonical;
6. preserve public Candid, method exports, accepted schema, persisted formats,
   query results, ordering, cursors, mutation atomicity, and error semantics;
7. avoid durable global metrics work during proven query methods while
   preserving scoped attribution and update-side metrics;
8. compact metrics representation without deleting maintained counters;
9. reduce schema-application code generation inside the existing semantic
   owner;
10. remove one evidence-proved SQL boundary retention path;
11. select and remediate exactly one current ordered-range execution family;
12. report raw Wasm, gzip, instruction, file, line, and complexity deltas for
    every production patch; and
13. close with a fresh complete matrix rather than blessing a partial shard.

## Non-Goals

0.220 does not:

- add SQL syntax, query semantics, endpoints, public configuration, or schema
  features;
- create a cost-based optimizer, cardinality estimator, plan search, or query
  hint;
- remove maintained metrics, diagnostics, schema validation, bounds, or
  recovery behavior to improve measurements;
- make generated `EntityModel` or `IndexModel` runtime authority;
- add a schema bootstrap fallback or second application/reconciliation path;
- use gzip reduction as the primary size result;
- report host latency as an IC instruction improvement;
- describe peak retained items as heap bytes without a typed heap measure;
- special-case a benchmark scenario, SQL string, entity name, or literal;
- add a runtime switch between old and optimized code;
- keep both pre- and post-optimization artifact pipelines after acceptance;
- rewrite the executor or schema subsystem broadly; or
- turn every attribution finding into production work in this line.

## Frozen Architecture Invariants

### Accepted Schema Authority

- Accepted schema snapshots remain runtime authority.
- Generated models and sealed fragments remain proposal/bootstrap inputs only.
- The canonical catalog-native `apply_schema` path remains the only schema
  mutation semantic owner.
- Required recovery, constraint, source-binding, and accepted-head checks are
  not feature-gated away from actors that need them.
- Current-format decode succeeds or returns a typed error. No old snapshot or
  generated-model reconstruction fallback is added.

### Runtime And Wire Behavior

- Public Candid types and IC method exports remain unchanged unless a later
  explicit design revision proves that one current pre-1.0 hard cut is part of
  the optimization. No patch may infer that authority from a size result.
- Rows, indexes, relations, journals, markers, accepted schemas, migration
  records, cursors, prepared-plan keys, and cache formats remain unchanged.
- Query results, ordering, ties, null behavior, limits, lookahead, cursors,
  budgets, and typed errors remain unchanged.
- Update-side metrics retain their current semantic meaning.
- Query-side global metrics remain non-durable by design.

### Metrics Routing, State, And Identity

Metrics dispatch precedence is exact:

1. an explicit scoped sink receives the event;
2. otherwise, synchronous query context suppresses the event; and
3. otherwise, the durable process-local global sink receives the event.

The query-context API is a synchronous closure boundary. It does not return a
guard, does not accept an async closure, and is exited before any returned
future can be polled. Current query wrappers enter it independently on every
message execution. A composite callback or later async surface must enter it
again for each synchronous callback/poll; context never spans `.await`.

With panic-abort Wasm, ordinary Rust unwinding is not the restoration contract.
A successful return restores the prior nesting depth. A query trap discards or
rolls back the query heap, so a later query/update must observe a clean context;
PocketIC trap-followed-by-query and trap-followed-by-update tests prove that
boundary. Host unwind tests remain supporting evidence only.

The current `EventState` is heap-only thread-local state. It has no stable
codec, `pre_upgrade` save, or `post_upgrade` restore path. Patch 4 freezes that
lifecycle: metrics accumulate across successful update calls in one installed
heap, reset explicitly through the reset endpoint, and reset on install or
upgrade. Patch 4 does not add upgrade persistence or a metrics migration.

The compact internal storage shape is:

```text
GlobalMetricCounters = [u64; GLOBAL_METRIC_SLOT_COUNT]
EntityMetricCounters = [u64; ENTITY_METRIC_SLOT_COUNT]
EventPerf = { three saturating u128 instruction totals, three u64 maxima }
entities = BTreeMap<MetricEntityPath, EntityMetricCounters>
```

`MetricEntityPath` is the canonical schema entity path after validation,
bounded by the existing accepted-schema path byte limit. Before first
acceptance, only the same validated path from the sealed schema proposal may be
used. The map is bounded by the existing maximum schema-assignment/entity
count. It is never a `Vec` indexed by `EntityTag`, and no caller-controlled or
sparse numeric entity identity is used as an allocation index.

Entity replacement at the same canonical path continues the same counters.
Removal or rename retains the old path entry until reset/upgrade and starts a
new entry for a new path, matching current path-keyed process-lifetime
semantics. Reports retain ascending canonical-path order.

Every internal metric code has an explicit fixed numeric value and an
exhaustive `code -> slot` mapping. Array slots never depend on Rust enum
declaration order or on the numeric size of an entity identity. Counter updates
and derived totals use saturating `u64` arithmetic; instruction totals retain
their current saturating `u128` arithmetic and maxima retain `u64`. Internal
metric codes have no persisted decoder; an unknown raw code cannot enter heap
state through a wire or stable format. Existing public compact metric codes
remain fixed, and unknown public report codes retain their current host-side
handling.

### Optimization Shape

- Every source optimization replaces its selected owner directly. No old/new
  feature flag, shadow dispatch, compatibility wrapper, or fallback remains.
- A Wasm post-link pipeline has one canonical order and one final deployable
  output.
- An optimization cannot be accepted by removing a scenario, weakening a
  bound, moving work into an unmeasured phase, or changing the test fixture's
  indexes.
- Shared runtime reductions must be demonstrated on dynamic and typed subjects;
  SQL-only reductions must also be demonstrated on the SQL subject.
- Size-only work must report instruction impact; performance work must report
  raw Wasm impact.

## Measurement Authority

### Wasm Artifact Stages

Patch 1 freezes names for these stages:

1. compiler-emitted `wasm-release` artifact;
2. transformed final deployable artifact;
3. gzip of the final deployable artifact; and
4. symbol-bearing `wasm-attribution` artifact.

The final deployable artifact is the exact byte sequence installed into
PocketIC or deployed to the IC after all accepted transforms, IC metadata,
Candid metadata/custom sections, and shrinking. Its SHA-256 is always computed
from those installed bytes. An earlier compiler or intermediate transformed
stage cannot supply final identity, size, or runtime proof. The report records
final exact bytes, SHA-256, function count, code/data/custom-section bytes,
method exports, and Candid bytes/hash where the subject exports Candid.

The maintained matrix contains at least:

- `default_empty`;
- `default_empty_metrics`;
- `one_entity_dynamic_query`;
- `one_entity_typed_query`;
- `one_entity_sql_query`;
- `ten_entity_typed_query`;
- the current SQL performance actor; and
- the maintained mutation-capable SQL actor.

Historical targets missing from an old report are recorded as incomparable;
they are not silently treated as zero or reconstructed through aliases.

### Post-Link Tool Contract

The selected transformer contract records:

- exact Binaryen version and acquisition/checksum authority;
- exact optimization flags;
- explicit Wasm proposal feature flags;
- proof that the transformer introduced no proposal feature outside the
  explicitly accepted IC feature set;
- exact ordering relative to IC metadata injection and shrinking;
- deterministic repeated-output proof for identical input;
- final parser/validator result;
- exact method exports and Candid identity;
- focused PocketIC query, update, schema-bootstrap, and upgrade behavior; and
- current instruction deltas for maintained sentinels.

Every PocketIC proof installs the final deployable bytes identified above. The
deep runtime/stack sentinel set includes:

- maximum maintained query-expression depth;
- maximum maintained check-expression depth;
- maximum-depth accepted-snapshot decoding;
- maximum bounded row and collection shapes;
- schema first creation, exact re-entry, and an accepted transition;
- the heaviest maintained mutation path;
- the heaviest maintained ordered-query path; and
- upgrade/reopen with populated rows, indexes, accepted schema, journal/marker
  state where applicable, and post-upgrade reads/writes.

The upgrade proof installs the pre-optimization final artifact, populates its
state, upgrades to the transformed final artifact, and verifies the populated
state and continued mutation/query behavior. Same-artifact empty-state upgrade
is not a substitute. Deep sentinels must complete without validation, install,
operand-stack, call-stack, or runtime traps.

The opening Binaryen 108 result does not freeze version 108. Patch 1 and Patch 2
must choose the version that can be reproduced in repository and CI workflows.

### Performance Profile

0.220 hard-cuts to a new profile identity because the PocketIC major version
changed. The old `icydb-sql-performance/0.215/v2` artifacts remain historical
evidence; no compatibility reader or cross-version acceptance bridge is added.

The new profile freezes:

- exact source revision and dirty-state rule;
- Rust and Wasm target toolchains;
- PocketIC server version and digest;
- final deployable Wasm digest;
- feature graph and generated actor identity;
- fixture identity and scenario catalog;
- cold/warm cache mode;
- phase and store-operation counters; and
- shard, repetition, aggregation, and comparison rules.

Phase ownership is explicit and versioned. The current intended relationship
is:

- `total = compile + execute + total residual`;
- `compile` owns mutually exclusive compile subphases plus its residual;
- `execute` owns mutually exclusive planner, store, executor-runtime, and
  response-finalization work plus its residual;
- `executor_invocation` is an inclusive cross-check whose additive children are
  store and executor-runtime, and is not added again to `execute`; and
- grouped, scalar-aggregate, direct-row, kernel-row, pure-covering, and hybrid
  executor lane counters are nested observations inside executor-runtime, not
  mutually exclusive children unless a later profile explicitly reclassifies
  them.

Every artifact carries the exact ownership table and reconciliation residuals.
Reports may rank inclusive parents and nested observations independently, but
must not add them together or describe them as exclusive phase shares.

Cache temperature is also exact:

- `cold` means the measured cache identities are absent at method entry and
  counters prove misses/inserts;
- `proven_warm_at_entry` means a successful prior **update** method populated
  the in-heap cache, a later measured method entered with the same cache/schema
  identity, and counters prove hits;
- `loop_local_reuse` means repeated execution inside one IC message and remains
  separate from warm-at-entry evidence; and
- sequential query calls alone never establish warmth, because query-created
  heap state is discarded.

The warmer method, warmed identity, intervening calls, schema head, cache hit
counters, and measured method are carried in the artifact. An unexplained
cache hit or miss fails the declared temperature classification.

Patch 1 publishes exact numeric acceptance budgets for Patches 2 through 7
before their production edits begin. A later patch may revise its budget only
through an explicit design/status update made before inspecting candidate
results.

Patch 1 also freezes line-level cumulative budgets measured directly from the
opening baseline to the final closeout artifact:

- one final raw-Wasm budget for every maintained subject;
- one aggregate and per-sentinel instruction budget for every maintained
  performance cohort; and
- explicit maximum accumulated regressions for all other measured dimensions.

Per-patch allowances do not reset the baseline. The tracker carries both each
patch delta and the cumulative baseline-to-current delta, so several locally
accepted regressions cannot accumulate into a line-level regression. At
minimum, no maintained final subject or instruction cohort may be worse than
its accepted opening baseline; Patch 1 must freeze stronger improvement targets
where the measured opportunity supports them.

## Landing Patches

Every patch may close without a production optimization when its accepted
evidence rejects the candidate. The patch still lands its bounded measurement,
decision, tests, and status outcome; it does not force a code change to justify
its place in the line. Patch 1 always establishes measurement authority, but
may reject every provisional owner or subtraction as non-attributable.

### Patch 1 — Measurement Authority And Opening Baseline

Canonical owners: Wasm audit scripts, SQL performance profile, integration
evidence, and the 0.220 tracker.

Bounded outcome:

- capture one clean exact post-0.219 baseline;
- hard-cut the performance profile to the PocketIC 15 identity;
- make all current Wasm subjects explicit and fail closed on missing targets;
- freeze controlled feature-pair manifests for metrics, typed, SQL, and entity
  scale comparisons;
- measure schema application on first/second post-install query, first
  post-upgrade query, query after update initialization, and the maintained
  query-only actor;
- freeze additive versus nested phase ownership and exact cold,
  proven-warm-at-entry, and loop-local cache modes;
- produce a retained-code/dominator ledger for metrics, schema application,
  SQL boundary dependencies, and ordered execution; and
- freeze exact per-patch and cumulative line-level acceptance budgets for the
  remaining patches.

This patch changes no production runtime behavior. It may change test/profile
formats directly to one current form. Old evidence remains immutable history;
the harness does not decode it as current evidence.

### Patch 2 — Canonical Post-Link Wasm Optimization

Canonical owner: Build / Canister artifact production.

Bounded outcome:

- select and pin one Binaryen tool contract;
- select one transform/metadata/shrink order;
- make the accepted output the sole deployable artifact;
- preserve exports, Candid, runtime behavior, upgrades, and persisted state; and
- prove the raw-size reduction and instruction impact across the maintained
  matrix, controlled pairs, and deepest maintained runtime/stack sentinels.

If runtime or instruction proof rejects the exploratory transformation, Patch
2 records the exact failed budget and does not install a partial or optional
pipeline.

### Patch 3 — Query-Context Metrics Routing

Canonical owner: generated endpoint method context and the metrics sink bridge.

Bounded outcome:

- establish an explicit synchronous closure-scoped query context at generated
  query wrappers;
- suppress only the default durable global sink inside that context;
- preserve explicit scoped sink overrides used by attribution and tests;
- preserve update-side global metrics exactly; and
- remove query-only event allocation, path ownership, dispatch, and state work
  proven unnecessary by the current metrics contract.

Core query code does not infer IC method mode. The generated method boundary
provides it. Precedence is explicit scoped sink, then query suppression, then
durable global sink. The closure context cannot span `.await`; every future
composite callback/poll enters independently. Successful nesting restores the
prior depth, while PocketIC trap-followed-by-query/update tests prove that a
trapped query cannot contaminate later method context.

### Patch 4 — Compact Metrics State And Dispatch

Canonical owner: metrics event registry, state, dispatch, and outward report
projection.

Bounded outcome:

- replace the selected repeated field/match/string representation with fixed
  explicitly numbered metric-code arrays plus a bounded
  `BTreeMap<MetricEntityPath, EntityMetricCounters>`;
- preserve every maintained counter and outward compact/extended report field;
- preserve saturating counter/total arithmetic and current heap-only
  reset-on-upgrade lifecycle;
- retain bounded deterministic report ordering; and
- delete the superseded internal representation in the same patch.

The entity map is bounded by schema path and assignment limits and never indexes
storage by `EntityTag`. The validated sealed-proposal path is the only
pre-acceptance entity identity. Metric-code-to-slot mapping is exhaustive and
independent of Rust enum declaration order. No stable metrics codec or
migration is added.

### Patch 5 — Canonical Schema-Application Codegen Contraction

Canonical owner: core schema application and application lowering.

Bounded outcome:

- select the leading repeated schema-application code shape from Patch 1
  attribution;
- contract duplicate initial/existing candidate lowering, generic
  monomorphization, or equivalent owner-local state transitions;
- keep `apply_schema` as the sole semantic path; and
- prove first-create, exact no-op, accepted transition, rejection, recovery,
  and generated bootstrap behavior.

The patch does not add a generated fast path or weaken the schema capability
required by an actor. If no safe owner-local contraction meets the frozen
budget, it records a no-change disposition instead of creating another schema
authority.

### Patch 6 — SQL Boundary Dependency Retention Hard Cut

Canonical owner: the exact SQL/DTO/scalar boundary selected by Patch 1's
dominator ledger.

Bounded outcome:

- select exactly one general-purpose retained dependency or duplicated adapter
  path with a proven SQL-subject dominator;
- replace it with the existing canonical value/Candid owner or a narrower
  owner-local representation;
- remove the superseded runtime dependency edge; and
- preserve public scalar, Candid, parsing, comparison, and persisted semantics.

This patch is not a dependency-version sweep. Host-only tooling and unrelated
dependency cleanup remain out of scope. Cargo dependency-tree removal is
supporting evidence only; the authoritative reachability proof is the matched
final-Wasm byte/dominator reduction for the selected SQL pair.

### Patch 7 — Ordered-Range Execution Remediation And Closeout

Canonical owner: the store/executor materialization boundary selected by the
accepted current profile.

Bounded outcome:

- rerank current P1/P2/scale evidence;
- classify required scan work separately from avoidable decode,
  materialization, copying, selection, and response work;
- select exactly one general ordered-range family;
- remove its frozen avoidable-work budget without changing query semantics; and
- complete the final performance, Wasm, dependency, sediment, and complexity
  implementation evidence.

If the accepted profile shows no removable work, Patch 7 closes with one
evidence-backed no-change disposition. It does not revive a 0.206 algorithm or
invent a benchmark-specific route.

After Patch 7 focused validation, the tracker may move to `implementation
complete; awaiting full validation`. It does not move to 0.220 complete until

  sections, and shrinking;

### Performance

Focused passing validation authorizes an agent handoff, not final line close.

## Risks And Mitigations

### Risk: A Smaller Wasm Executes More Instructions

Patch 2 reports the same-profile instruction matrix and cannot hide a sentinel
regression behind the aggregate raw-size win. A rejected transform is not kept
as an optional pipeline.

### Risk: Toolchain Drift Makes Artifacts Non-Reproducible

The transformer version, acquisition digest, feature flags, and pass order are
part of the profile identity. Missing or mismatched tools fail closed.

### Risk: Query Metrics Suppression Hides Useful Evidence

Only the default durable global sink is suppressed in proven query method
context. Explicit scoped sinks remain authoritative for call-local performance
and test evidence. Update-side metrics remain unchanged. The context is a
synchronous closure, never an async-spanning flag, and trap-followed-by-method
proof guards the panic-abort boundary.

### Risk: Metrics Compaction Changes Public Counters

The current outward reports are golden behavior. The new internal state must
project exactly the same field values and ordering before the old state shape
is deleted.

### Risk: Schema Size Work Creates A Second Authority

Patch 5 is restricted to the canonical schema application and lowering owner.
No generated shortcut, old/new path, or reconstruction fallback is accepted,
even if it would produce a larger size reduction.

### Risk: Dependency Removal Narrows Supported Values

Patch 6 begins from a proven runtime dominator and retains existing boundary
tests for every affected scalar and wire value. A named dependency is not
removed merely because it appears in attribution.

### Risk: The Executor Patch Repeats 0.206

Patch 7 selects from the new profile and current counters. Historical findings
are context only. No 0.206 implementation is reopened without fresh evidence
that its current owner performs removable work.

## Closeout Decision Rule

0.220 is complete only when:

1. one exact current profile and Wasm matrix are checked in;
2. every planned patch has an implemented or evidence-backed no-change
   disposition;
3. the canonical final Wasm pipeline is singular and reproducible;
4. all affected public Candid, exports, persisted formats, and semantics are
   unchanged or an explicit prior design revision records the current hard
   cut;
5. the final raw non-gzipped matrix and same-profile instruction matrix pass
   their per-patch and cumulative line-level budgets;
6. no old metrics representation, artifact pipeline, schema path, dependency
   edge, or executor strategy selected for replacement remains;
7. focused checks pass, the required user/CI-owned full suite and complete
   build/Wasm matrix have actually passed, and their exact evidence is recorded;
   and
8. the status tracker records files, approximate line delta, delivery domains,
   raw Wasm and performance deltas, and complexity shape for every landing.

Passing focused validation may mark implementation complete, but it cannot mark
the line complete. Before item 7 is recorded, the only valid terminal tracker
state is `implementation complete; awaiting full validation`.

The closeout report must distinguish measured production improvements from
attribution-only observations and gzip-only context.
