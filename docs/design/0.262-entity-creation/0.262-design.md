# 0.262 — Entity Creation

Authorised 2026-09-30 after the recorded scoped-ready 0.261 closeout.
Delivery owner: [status](0.262-status.md).

## Outcome

Add a declared entity to an existing journaled store in a populated database.
For example, retain populated `Item` and `Holder` declarations and add empty
`Quest` at source version 1. Existing accepted identities, rows, indexes,
relations, logical memory allocations and source lineage remain authoritative.
The new entity requires neither a placeholder nor a predecessor migration.

## Owners and demonstrated gap

The existing-head proposal lowerer requires every entity source to have an
accepted binding. Its initial lowerer already builds fields, indexes,
constraints and relations for an empty entity. Reuse that entity construction
against current accepted value catalogs, and extend the existing store candidate
with fresh entity-scoped bindings. Accepted snapshots remain runtime authority.

The application preflight currently assumes all candidate entities existed
before. Extend that owner to prove a newly allocated row/index/reverse domain
empty, then retain the existing removal and activation proofs for old entities.
Publish the catalog, source lineage and exact application receipt through the
existing compound journal publication. No second schema lifecycle is needed.

The simpler placeholder alternative requires predicting future entities and
does not meet the requested schema evolution. SQL DDL, a separate creation
command, a mode and a new migration opcode are unnecessary for declared entities.

## Contract

- Route additions only to stores with accepted catalogs; new-store admission
  is a separate outcome.
- Allocate tags above all current accepted entity tags, in canonical
  store/source order, with checked exhaustion. Preserve every existing tag.
- Require source version 1 for a genuinely new declaration. An occupied source
  remains an existing-entity transition, never replacement.
- Build an empty entity's field layout, initial indexes, constraints and
  relations through the maintained initial-entity lowering helpers.
- E1 establishes scalar and already accepted named field types. E2 adds newly
  declared named types; creation accompanying an explicit existing-entity migration is
  E3. Do not silently partially publish an unsupported proposal.
- Prove new physical domains empty before publication. Preserve populated
  old entities and reject stale heads, invalid definitions, misplaced sources,
  exhaustion and occupied physical domains through typed errors.
- With the migration feature, publish new version-1 source lineage atomically
  without adopting or changing old entity source meaning. An unadopted database
  must adopt its unchanged accepted source before feature-bearing creation.
- Without the feature, ordinary additive reconciliation remains available;
  it does not invent source lineage.
- Retain exact submission replay, normal startup readiness, accepted query/write
  binding, interruption recovery and current stale-authority rules.

State-space delta: previously rejected additive existing-store proposals become
admissible under the same candidate/publication flow. No new public command,
configuration, persisted phase, format, codec discriminator or runtime fallback.
All internal encodings remain current version 1. New entities are empty;
existing rows and physical generations need no rewrite.

## Boundaries and qualification

E2 extends the accepted value-catalog owners for definitions reachable from
added entities. Allocate fresh enum/composite IDs above the respective current
catalog maxima in source order, including accepted IDs without source bindings.
Preserve old definitions and source bindings exactly; validate any redeclaration
against the predecessor catalog before merging. New definitions may reference
old definitions or each other, including maintained recursive shapes. Build all
definitions before validating the complete closure, and publish type bindings,
catalogs and entities in the existing candidate. Missing references, orphan
declarations, identity exhaustion and any attempted old-type edit reject the
whole proposal. Requiring types to exist in a prior entity is the simpler
alternative, but does not satisfy creation of an entity with its own value types.
No new command, mode, persisted state, format or runtime reconstruction is needed.

E3 admits version-1 additions alongside explicit existing-entity transitions.
The ordinary lowerer continues to own additions against the planner's rekeyed
accepted view. This distinguishes fresh entities from renamed predecessors,
including an addition reusing a predecessor source name. The existing planner
combines transitioned lineage with new version-1 lineage; compound publication
owns both. Physical migration admission reuses the empty-domain proof for new
entities while retaining offline historical validation for migrated entities.
Splitting these into separate deployments is the simpler alternative, but does
not meet coordinated declaration upgrades. No new persisted state, command,
format or execution route is needed; existing physical phases remain unchanged.

The line excludes new-store creation, SQL CREATE TABLE, runtime-generated
schemas, throughput changes and additional entity-removal semantics.
Toko Miner saving optimisations remain downstream work.

E4 reuses the SQL actor's populated Item/Holder fixture and retained build
pipeline. Two test-only feature flags introduce Quest with new enum/record
definitions and select the physical Item field-addition successor. Existing
rename flags supply the metadata successor; source declarations are unchanged.
These separate artifacts prove actual generated deployment reconciliation,
which native proposal fixtures cannot prove. The canonical owners remain the
fixture declarations, SQL actor controls and migration-closeout target. This
adds test build combinations only, with no product configuration or durable
state. All-features lint builds select the existing metadata successor.

Native proof must cover populated preservation, new indexed writes, constraints
and relation enforcement, exact replay, feature-bearing lineage and recovery.
Generated IC proof must exercise a real successor Wasm with a new declaration,
normal readiness and same-release restart. Report raw Wasm, cycles and
instructions separately from implementation complexity; unavailable measurements
remain unmeasured. Full suites remain user-owned.

### Other improvement candidates

- **Explain rejected additions.** Creation failures should identify the store,
  entity and failed condition where the maintained diagnostic surface permits:
  missing adoption, stale authority, occupied domains, unresolved types or
  conflicting definitions. Start in proposal/application diagnostics and reuse
  existing typed errors. A separate preview endpoint would need its own
  demonstrated need and design; it is not required for clearer errors.
- **Allocate entity identities once per proposal.** The global allocation is
  currently recomputed for each store receiving additions. Consider one
  proposal-local allocation shared by store candidates in the existing lowerer.
  Preserve canonical ordering, checked exhaustion and accepted identities.
  No durable state is needed; instruction savings remain unmeasured and should
  justify any extra plumbing before implementation.
- **Extend generated qualification for application needs.** Candidate scenarios
  include several new entities referencing each other, cross-store relations,
  and newly introduced wrappers or named collections. The existing generated
  rehearsal covers enum/record values, a unique index and a restrictive
  relation; native coverage already covers several broader combinations.
  Add focused deployment cases for real workload boundaries through the same
  fixture/build/closeout owners, without a parallel migration harness.
- **Treat MMO write throughput as a separate outcome.** This line changes
  neither the fold backlog nor fold rate. Downstream dirty-state batching and
  bounded folding of several committed batches remain candidates for their
  respective application and convergence owners. They need separate IC
  cycle/instruction, atomicity, recovery and sustained-load qualification.
  The creation measurements provide no new throughput guarantee. New-store
  creation and online physical migration also remain outside this design.
