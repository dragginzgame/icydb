## Planning Status And Authorization

This line lets IcyDB participate synchronously in a canister whose application
or another framework owns the IC lifecycle methods. It does not choose that
external owner, complete any external framework's composition API, or alter the
0.225 watchdog protocol.

Patch 1 documentation/evidence inventory is complete. Patch 2 adds the one
participant form and duplicate protocol authorized by the user. Patch 3 adds
the framework-neutral evidence canister and application guidance. It changes
no IcyDB version, public Candid, persisted state, stable-memory allocation,
timer provider, or recovery authority. The final closeout patch still requires
explicit user continuation.

The released predecessor uses exact `ic-timers 0.3.4`. A separate user-owned
worktree correction moves the current candidate authority to exact
`ic-timers 0.3.8` and claim-scoped armed-wakeup observation. The user's Patch
2 continuation accepted that current surface as the one candidate timer
authority. The correction remains separately attributable and 0.227 neither
duplicates nor alters it.

## Demonstrated Need And Current Limitation

The accepted 0.225 design establishes that IcyDB must reconstruct its volatile
watchdog synchronously during init and post-upgrade before deferred
database-dependent application work. The maintained standalone
`icydb::start!()` form owns `canister_init` and `canister_post_upgrade` to meet
that contract.

A canister cannot also emit another framework's lifecycle macro when that macro
owns the same IC exports. Moving IcyDB registration into a deferred application
hook is insufficient: a later trap in that deferred message can roll back
registration, and application work may start before the engine participant
exists.

The smallest IcyDB-owned solution is a participant form that exposes the exact
synchronous 0.225 lifecycle work without exporting system methods. Composition
remains application or external-framework authority.

## Decision Summary

The standard standalone form remains exact:

```rust
icydb::start!();
```

For an externally owned lifecycle root, IcyDB adds one explicit form:

```rust
icydb::start!(participant);
```

Exactly one standalone or participant form is permitted per canister build.
Both are root-only item macros. Their expansion includes one common
compile-time ownership marker and a root-placement assertion so duplicate,
mixed, or nested-module use fails compilation. Patch 1 proved that the
maintained marker/binding check is the smallest required root assertion rather
than assuming Rust privacy establishes root placement.

The participant form emits the generated actor plus exactly two hidden
crate-visible Rust functions under the Patch-1-frozen namespace:

```rust
#[doc(hidden)]
pub(crate) mod __icydb_lifecycle_participant {
    #[doc(hidden)]
    pub(crate) fn init() {
        /* exact maintained IcyDB init participation */
    }

    #[doc(hidden)]
    pub(crate) fn post_upgrade() {
        /* exact maintained IcyDB post-upgrade participation */
    }
}
```

Each has exact Rust ABI type `fn() -> ()`. Neither is an IC export, Candid
method, function table, string-dispatched hook, public facade API, or callable
external executor. The application composition root invokes the matching
function exactly once from its single init or post-upgrade body.

The namespace is design authority, not an implementation detail. Patch 1
proved that `crate::__icydb_lifecycle_participant::{init, post_upgrade}` is
callable from the owning crate root and reduces the new collision surface to
one root module. No maintained IcyDB, application fixture, or inspected Canic
lifecycle item uses that module name. Duplicate, mixed, nested, and
pre-existing-module probes fail at compile time. Patch 2 reuses the maintained
`__IcydbStartRootMarker` / `__icydb_start_root_binding` assertion emitted by
the common actor owner; it adds no second root marker. It may not emit the
rejected top-level function spellings, retain aliases, select names per
consumer, or recover from collisions at runtime.

## Invocation And Duplicate Protocol

Both functions enter one shared volatile state:

```text
Idle -> Running -> Completed
```

- Every fresh Wasm instance begins `Idle`.
- The first participant invocation changes `Idle` to `Running` before touching
  timer or driver state.
- It runs the exact accepted 0.225 lifecycle path and changes to `Completed`
  only after successful reconstruction.
- Re-entry while `Running` deterministically traps before additional work. The
  enclosing message rollback restores participant, timer, and driver state, so
  a later lifecycle-message retry is safe.
- Invocation after `Completed`, including invocation through the other
  participant function, returns before resetting, clearing, replacing, or
  registering any timer.

Duplicate init, duplicate post-upgrade, and cross-function duplicate therefore
cannot lose the first registration claim or create a second watchdog.

The IC provides no trusted in-crate token proving that a `pub(crate)` call came
from the matching system-method body. A wrong-phase first invocation is not
reliably runtime-detectable and remains a forbidden composition defect. IcyDB
generates no ordinary endpoint that calls either function; maintained source
and complete lifecycle/Candid/Wasm export artifacts prove that absence. The
application-owned root and its source/artifact checks remain responsible for
proving that each first call occurs in the matching lifecycle phase. An
accidental ordinary call after correct lifecycle completion is inert through
the shared state.

## Framework-Neutral Partial Ordering

IcyDB freezes only the ordering it can require:

```text
one application-owned init/post-upgrade message
  -> restore local state required by application/framework ingress
  -> invoke the matching IcyDB lifecycle participant synchronously
  -> complete other synchronous framework reconciliation
  -> schedule deferred database-dependent application work
  -> return with exactly one lifecycle export of each kind
```

Independent synchronous restoration steps may be reordered, but IcyDB's
participant must run during both init and post-upgrade before any deferred
work. This requirement holds even when the lifecycle owner considers the
application inactive, `Prepared`, not yet activated, or otherwise unable to
serve ingress. IcyDB's watchdog must exist before deferred database-dependent
work, and all guard or application authority required at ingress must exist
before the lifecycle message returns. A participant trap aborts the lifecycle
message normally; no partial lifecycle is advertised as ready.

This is a participant contract, not a claim that composition is already
available everywhere. IcyDB 0.227 may close using a hand-written
framework-neutral root. A Canic application may not claim composed lifecycle
qualification until Canic independently exposes a synchronous participant
seam, or another single-owner root, that orders Canic restoration, IcyDB
watchdog reconstruction, and deferred application work exactly once. That
downstream change must preserve Canic's own macro-to-public-API-to-private
runtime/TimerOps layering and cannot move root orchestration into a deferred
user callback. It is not an IcyDB promotion or release gate.

Canic 0.103 needs no IcyDB lifecycle content to satisfy this design. Any Canic
single-owner lifecycle composition API belongs to a separate Canic design line
and is evaluated as a downstream consumer of this participant contract.

## Canonical Ownership

1. IcyDB owns standalone/participant grammar, hidden function shape,
   duplicate/trap protocol, and invocation of the accepted 0.225 lifecycle
   authority.
2. The accepted 0.225 coordinator, driver, and timer provider remain the only
   readiness/watchdog authority.
3. The consuming application or independent framework owns the single IC
   lifecycle root and ordering of its other participants.
4. No framework imports or controls another framework's internal runtime.

## Timer Boundary

0.227 preserves the exact timer provider and trap/instruction-exhaustion
protocol accepted by 0.225. Timer-provider substitution is outside this line
and must independently satisfy the complete 0.225 substitution gate.

## Scope

0.227 includes:

- one root-only participant value of the existing IcyDB start macro;
- two hidden crate-visible synchronous functions under the one Patch-1-frozen
  collision-safe namespace;
- one shared volatile `Idle/Running/Completed` guard;

## Persisted And Public Hard Cuts

- Exactly one root-level `icydb::start!()` or
  `icydb::start!(participant)` form is current.
- Participant functions are exactly `#[doc(hidden)] pub(crate) fn() -> ()`
  under the one namespace frozen by Patch 1 and have no alias or public
  re-export.
- Participant form emits zero lifecycle system methods; standalone emits the
  maintained exact pair.
- Shared participant state is volatile, has exactly three values, and is not
  stable-memory authority.
- Duplicate completion returns before timer mutation; running re-entry traps
  and rolls back.
- No external framework name, API, type, timer, or state enters IcyDB.
- Timer-provider and startup/recovery authority remain exact 0.225 owners.

## Non-Negotiable Invariants

1. One canister build selects exactly one root-level lifecycle form.
2. Standalone exports exactly one init and post-upgrade; participant exports
   neither.
3. The composition root calls the matching participant exactly once.
4. Duplicate/cross-function calls after completion are inert before timer
   mutation.
5. Running re-entry traps; rollback permits safe lifecycle-message retry.
6. Duplicate post-upgrade cannot lose the first handle or register another
   watchdog.
7. No ordinary generated endpoint calls either participant function.
8. Wrong-phase first invocation is forbidden and not falsely claimed to be
   runtime-authenticated; the application root and source/artifact evidence
   prove correct phase placement.
9. IcyDB watchdog reconstruction occurs in init and post-upgrade before every
   deferred work item, regardless of application activation state.
10. 0.225 Ready/Recovering/failure and timer semantics remain authoritative.
11. No persisted lifecycle state, external framework dependency, second timer
    provider, or recovery driver is added.
12. Raw non-gzipped Wasm remains footprint authority.

## Patch 1 Frozen Inventory

The maintained standalone expansion has one actor owner and one lifecycle
export owner:

| Boundary | Frozen owner and order |
| --- | --- |
| Actor/root ownership | `start!` invokes `__icydb_start_actor!`, which emits `__IcydbStartRootMarker`, `__icydb_start_root_binding`, private `__icydb_generated`, and the root `db`, `db_with_request_root`, and `startup_state` imports |
| Lifecycle exports | `__icydb_start_lifecycle!` alone emits `canister_init` and `canister_post_upgrade` through private Rust wrappers named `__icydb_startup_init` and `__icydb_startup_post_upgrade` |
| Engine participation | each wrapper synchronously invokes the matching `crate::__icydb_generated::__icydb_startup_*` helper before any composed application callback |
| Watchdog claim | generated actor state owns one `Option<WatchdogRegistration>` for fixed identity `icydb/startup/recovery`; init and post-upgrade initialize the shared runtime and reconcile that exact claim from durable startup state |
| Upgrade | a fresh Wasm instance reconstructs volatile timer/runtime state from the same durable readiness authority; no stable lifecycle phase or second recovery executor exists |

The complete new root-name decision is frozen as follows:

| Probe | Result |
| --- | --- |
| root `__icydb_lifecycle_participant::{init, post_upgrade}` and root calls | compile pass |
| participant nested below crate root | compile fail at the existing absolute root binding |
| duplicate participant | compile fail with duplicate marker, binding, and module |
| standalone plus participant | compile fail with duplicate common owner marker/binding |
| pre-existing `__icydb_lifecycle_participant` module | compile fail with duplicate module |

The two rejected top-level participant function names would create two root
collision domains and overlap the maintained standalone wrapper spelling. The
single hidden module creates one collision domain, has no match in maintained
IcyDB/application source or the inspected Canic lifecycle macros, and leaves
Canic's current `init`, `post_upgrade`, and `__canic_*` root items untouched.
Canic still lacks the synchronous composition seam needed to invoke it; that
downstream limitation is unchanged.

At the Patch 1 boundary, the generated helpers were timer-idempotent but were
not an exactly-once participant protocol. A second in-crate helper call
repeated startup observation and reconciliation; the retained identity
prevented a second logical Watchdog, but there was no common Completed latch
across init and post-upgrade. Patch 2 closes that precise duplicate-call
hazard outside the unchanged helpers. Neither helper is a public IC method,
and the IC cannot authenticate the lifecycle phase of a first crate-private
call.

## Complexity And Maintenance Gate

Demonstrated need: two lifecycle-exporting macros cannot coexist, while
deferred IcyDB registration violates the accepted synchronous 0.225 ordering.

Simplest alternative: an application can hand-write all 0.225 lifecycle work
only if IcyDB exposes it. The participant is that minimum seam. A generic
registry, framework-specific adapter, callback list, or second timer mode adds
state without improving the two required calls.

Canonical owner: IcyDB owns two synchronous participant functions; the
application owns one lifecycle root. State-space delta is one build-time start
form and one three-value volatile latch, with zero persisted state.

Promotion fails if implementation adds external-framework imports, runtime
registration, persisted phase, async IcyDB reconstruction, public participant
endpoints, duplicate timer owners, or compatibility forms. Every handoff
reports owners, state/flow delta, instructions, stable/raw-Wasm effects,
file/line delta, and whether structure became simpler, neutral, or more complex.
