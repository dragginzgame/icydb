## Current Boundary

0.227 is reserved for one IcyDB lifecycle participant seam. It is independent
of SQL/schema read authorization semantics and of every external framework.

`icydb::start!(participant)` form emits the same generated actor without

authority enters IcyDB.

## Patch 1 Inventory

The standalone expansion is one converged route:

`start!` -> `__icydb_start_actor!` -> private `__icydb_generated` actor, then
`__icydb_start_lifecycle!` -> one private init wrapper and one private
post-upgrade wrapper -> matching generated lifecycle helper -> shared timer
runtime initialization -> durable `startup_state()` observation -> one retained
`icydb/startup/recovery` Watchdog reconciliation. In the composed predecessor
form, the application callback runs only after that sequence.

The maintained root items are `__IcydbStartRootMarker`,
`__icydb_start_root_binding`, `__icydb_generated`, the root bindings `db`,
`db_with_request_root`, and `startup_state`, plus standalone wrappers
`__icydb_startup_init` and `__icydb_startup_post_upgrade`. Application fixtures
use distinct `application_startup_*` names. Inspected Canic lifecycle macros
own `init`, `post_upgrade`, and `__canic_*` items but no
`__icydb_lifecycle_participant` item.

The participant namespace is frozen as
`crate::__icydb_lifecycle_participant::{init, post_upgrade}`. Both functions
are `#[doc(hidden)] pub(crate) fn() -> ()` inside one
`#[doc(hidden)] pub(crate)` module. The existing actor marker/root-binding
assertion is the common standalone/participant owner and is reused unchanged.
No top-level participant-function aliases are allowed.

One-off Rust 2024 compile probes produced the exact matrix:

| Shape | Result |
| --- | --- |
| root participant module and both root calls | pass |
| nested participant | fail: missing absolute root binding |
| duplicate participant | fail: duplicate marker/binding/module |
| mixed standalone and participant | fail: duplicate common owner |
| pre-existing participant module | fail: duplicate module |

At the Patch 1 boundary, generated helpers had no shared Completed latch. Repeating either
helper repeats bounded startup observation and reconciliation; the retained
timer identity coalesces the claim, but this does not satisfy exactly-once
lifecycle participation. Patch 2 now supplies one common volatile
`Idle/Running/Completed` latch outside those unchanged helpers. No runtime
phase authentication is possible for a wrong first in-crate call.

## Patch 2 Implementation

`start!(participant)` reuses `__icydb_start_actor!` unchanged and then emits
exactly `crate::__icydb_lifecycle_participant::{init, post_upgrade}`. Each is a
safe `fn() -> ()` and coerces the matching generated 0.225 helper to that exact
function-pointer type. No callback table, string dispatch, allocation,
endpoint, compatibility form, or second executor exists.

Both functions enter one thread-local three-value latch. `Idle` becomes
`Running` before the generated helper. `Completed` is written only after it
returns. A Running re-entry traps before the helper, while a Completed call
returns before any generated timer or startup work. Native unwind uses a
non-Wasm-only rollback guard solely to model the IC's message rollback in the
owner-local regression; Wasm relies on replicated-message rollback.

## Patch 3 Composition Harness

The maintained `canister_test_lifecycle_participant` is the single framework-
neutral owner of its IC init and post-upgrade exports. Both roots visibly
restore ingress-local authority, invoke the matching hidden IcyDB participant,
finish independent synchronous reconciliation, and only then register an
application-owned retained readiness timer. The timer identity belongs to the
`application/startup/readiness` namespace, while IcyDB retains sole ownership
of `icydb/startup/recovery`.

The canister remains `Prepared` throughout the lifecycle message. Its bounded
snapshot records canonical order values 1 through 4 and the startup/watchdog
facts observed immediately after participation. Deferred work calls
`startup_state()` in later messages, retries Recovering, stops on typed failure,
and opens a database session exactly once only after Ready before becoming
Active. No endpoint invokes either participant function.

## Frozen Direction

- Keep standalone `icydb::start!()` exact.
- Add only root-level `icydb::start!(participant)`.
- Permit exactly one form per build; duplicate/mixed/nested uses fail compile.
- Emit two `#[doc(hidden)] pub(crate) fn() -> ()` functions under one
  Patch-1-frozen collision-safe namespace and no lifecycle exports in
  participant mode.
- Use one volatile `Idle/Running/Completed` state.
- Completed duplicates are inert before timer mutation; Running re-entry traps
  and rolls back for safe lifecycle-message retry.
- Wrong-phase first invocation is forbidden but not falsely claimed to be
  runtime-detectable; application-root source and complete artifact evidence
  prove correct phase placement.
- Run the participant during init and post-upgrade before every deferred work
  item even while the owning application is inactive, `Prepared`, or not yet
  activated.
- Preserve the candidate's exact `ic-timers 0.3.8` Watchdog provider and
  recovery protocol without absorbing its separately attributable correction.
- Provide a participant only; do not claim Canic or another framework already
  supplies a compatible composition root.
- Keep any Canic lifecycle-composition API in a separate Canic design line;
  Canic 0.103 needs no further lifecycle content.
