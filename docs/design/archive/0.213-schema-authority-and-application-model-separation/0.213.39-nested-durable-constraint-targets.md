# IcyDB 0.213.39 Nested Durable Constraint Targets

Status: N1-N7 complete; ready for the human-owned release workflow

Date: 2026-07-28

Baseline: `v0.213.38`

## Purpose

0.213.39 removes the remaining fail-closed limitation on durable rules below
structural fields. It does not broaden application validators into database
authority. It gives the existing closed numeric and length rule family one
bounded, source-bound target contract that can reach:

- record members;
- tuple elements;
- enum payloads;
- newtype values;
- list and set elements;
- map keys and values;
- repeated persisted values; and
- finite runtime values admitted through cyclic named-type graphs.

The accepted catalog remains the only runtime authority. Rust-authored type
metadata identifies a proposal-time reusable rule and its nominal owner. The
database resolves that source identity to accepted IDs, persists the accepted
target and operation, compiles one accepted enforcement artifact, and uses it
for normal mutation admission, activation, integrity checking, and recovery.

This design is the bounded follow-up to the current-architecture audit's E2
finding. It is intentionally separate from the 0.216 durable-rule authoring
ergonomics work. 0.213.39 establishes the accepted target and runtime
semantics; 0.216 may later improve how authors spell the same rules without
creating another database representation or evaluator.

## Current Evidence

The completed repository has one accepted-authority path:

- `icydb_model::Type` carries application normalizers, application validators,
  and explicit durable `SourceRule` values as separate concepts.
- `icydb-model/src/fragment.rs::reachable_source_rules` walks the bounded
  named-type graph iteratively and emits each ruled nominal target once per
  persisted root.
- `lower_field_rules` constructs the sole `TargetedRuleFragment`; the retired
  top-level source-rule-as-check lowering and nested-placement rejection no
  longer exist.
- `SourceCheckInstruction::Field` remains only for explicitly authored
  general checks. Built-in durable numeric and length rules do not use it.
- `AcceptedConstraintKind::TargetedRule` binds the persisted root and nominal
  type to accepted identities.
- `CompiledAcceptedRowConstraints` evaluates the final after-image and is
  shared by typed, structural, and SQL mutations, activation, and accepted
  integrity machinery.
- accepted enum, composite, record-member, and enum-variant IDs already
  provide stable identities for resolved recursive graphs.
- accepted value admission already proves each runtime value finite under
  explicit depth and byte budgets even when its schema graph is cyclic.

The target-selection gap is closed without adding another validation
authority.

## Non-Negotiable Invariants

1. Accepted schema owns all durable runtime enforcement.
2. A generated or handwritten Rust type never becomes a runtime target,
   evaluator, callback, codec, or fallback schema.
3. Application validators and normalizers remain explicit application
   operations and are never inferred as durable constraints.
4. One source rule under one persisted root field becomes one accepted
   constraint, even if the ruled nominal type is reachable through several
   branches or recursively.
5. A rule applies to every finite runtime occurrence of its nominal target
   below that root field.
6. Schema graphs may be cyclic; runtime values must be finite and bounded.
7. Target construction and evaluation never recursively expand the schema
   graph.
8. Display names and Rust paths are diagnostic labels only. Identity uses
   immutable source keys before acceptance and accepted IDs afterward.
9. Typed, structural, and SQL writes converge before target evaluation.
10. Activation and integrity use the same compiled operation and traversal
    semantics as normal writes.
11. No compatibility alias, dual decoder, old-format fallback, or version-2
    wrapper is introduced.
12. Row bytes, row layouts, indexes, relations, query results, and cursors are
    outside this change.

## Authority And Data Flow

```text
ruled nominal model type
        |
        v
TypeSourceKey + RuleSourceKey + closed rule operation
        |
        v
bounded per-root SourceDurableRuleTarget
        |
        v
database-scoped source binding
        |
        v
FieldId + AcceptedNamedTypeIdentity + bound operation
        |
        v
accepted constraint catalog and fingerprint
        |
        v
CompiledAcceptedTargetedRule
        |
        +--> final-after-image mutation admission
        +--> activation proof
        +--> integrity inspection
        +--> deterministic recovery reconstruction
```

The source model disappears after proposal construction. Recovery reconstructs
the compiled rule from the accepted bundle and accepted value catalogs only.

## Target Semantics

### Nominal Target, Not An Expanded Path

An accepted target is:

```text
persisted root FieldId
    + target AcceptedNamedTypeIdentity
```

The source equivalent is:

```text
persisted root FieldSourceKey
    + target TypeSourceKey
```

The target is not a vector containing every record, enum, or collection edge.
A recursively expanded path would be infinite for a valid graph such as:

```text
Values -> FieldValue -> Value -> Values
```

Instead, the compiler traverses the bounded named-definition catalog once per
persisted root and emits one target for each reachable ruled nominal type.
Runtime evaluation walks the finite admitted value and applies the rule
whenever traversal enters that accepted nominal type.

This also defines reuse precisely. If the same ruled type appears in a map key,
map value, record member, and recursive enum payload below one persisted field,
all occurrences are governed by one accepted constraint. If two persisted
fields use that type, each field receives a distinct accepted constraint.

### Source Identity

The constraint source identity is derived from:

```text
domain "icydb:constraint-source:targeted-field-rule:v1"
persisted root FieldSourceKey
target TypeSourceKey
RuleSourceKey
```

The byte framing must be length-delimited and covered by golden vectors. It
must not include:

- a display name;
- a Rust path;
- declaration order;
- a record-member name;
- a tuple or collection index;
- an accepted numeric ID;
- rule operands; or
- the current graph route from root to target.

Including the target type prevents two nominal types from colliding when
their local authoring rule identities are equal. Excluding graph routes keeps
one rule identity stable when another branch to the same target is added,
removed, or renamed.

### Accepted Identity

Application resolves:

- the root `FieldSourceKey` to its accepted `FieldId`; and
- the target `TypeSourceKey` to `AcceptedNamedTypeIdentity::Enum` or
  `AcceptedNamedTypeIdentity::Composite`.

The accepted constraint stores those IDs. Record traversal uses
`CompositeFieldId`; enum traversal uses `EnumTypeId` and `EnumVariantId`.
Tuple ordinals and collection positions are structural coordinates, not
replaceable schema identities.

Application rejects before mutation when:

- the root or target source binding is absent or ambiguous;
- the target is not reachable below the root's accepted contract;
- the operation is incompatible with the target's resolved value kind;
- the same canonical target/rule is proposed twice; or
- the entity constraint bound would be exceeded.

## Source And Accepted Representations

The intended source-side shape is conceptually:

```text
SourceConstraintKind
    Check(SourceCheckExpr)
    TargetedRule {
        root: FieldSourceKey,
        target_type: TypeSourceKey,
        operation: SourceRuleOperation,
    }
```

The intended accepted shape is conceptually:

```text
AcceptedConstraintKind
    ...
    Check(AcceptedCheckExprV1)
    TargetedRule {
        target: AcceptedRuleTarget,
        operation: AcceptedRuleOperation,
    }

AcceptedRuleTarget {
    root_field_id: FieldId,
    target_type: AcceptedNamedTypeIdentity,
}
```

Exact implementation names may change during N2/N3, but the ownership and
cardinality above may not. A targeted rule is not encoded as:

- a generated callback;
- a list of display-name path strings;
- a fully expanded schema path;
- an arbitrary user expression over a collection;
- a second physical-row validator; or
- a SQL-only expression.

Top-level source rules move to this same targeted representation. They do not
retain the old source-rule-to-general-check path in parallel. Manually authored
row `CHECK` expressions remain `Check` constraints because their row
expression lifecycle and dependency model are genuinely distinct.

## Operation Semantics

0.213.39 does not expand the rule vocabulary. It supports the maintained
closed numeric-minimum, numeric-range, and length-range operations.

- Numeric rules are valid only when the target nominal type resolves through
  transparent newtypes to one supported exact numeric value.
- Length rules use Unicode scalar count for text, octet count for blobs, and
  logical cardinality for eligible list, set, or map values.
- Record and tuple arity, enum variant count, encoded byte length, and
  recursively accumulated child count are not implied length meanings.
- A null target does not violate numeric or length rules. Nullability remains
  owned by the accepted field/member contract and `NOT NULL` where applicable.
- An enum branch that is not the selected runtime variant has no target value
  and therefore passes vacuously.
- An empty collection has no nested element targets. A rule on the nominal
  collection itself still evaluates its cardinality.
- Every selected occurrence must pass. One failure rejects the whole mutation
  atomically.

The scalar comparison and length primitives must be shared with the accepted
check evaluator. The targeted-rule compiler adds bounded target traversal; it
does not clone numeric, decimal, text, blob, or collection semantics.

## Bounded Recursive Traversal

The compiled artifact is conceptually:

```text
CompiledAcceptedTargetedRule {
    constraint identity and labels,
    root row slot,
    target accepted type identity,
    bound scalar operation,
}
```

Evaluation starts from the final after-image's root slot and walks the value
with its accepted contract:

- records visit members in stable `CompositeFieldId` order;
- tuples visit declaration ordinals;
- newtypes visit their single inner value;
- enums visit only the selected accepted variant payload;
- lists visit element order;
- sets visit canonical value order;
- maps visit canonical key order, with key before value at each entry; and
- nullable values stop at null.

Traversal is iterative. It must not rely on Rust call-stack recursion and must
not use a global visited-type set, because the same accepted type may occur
many times in one finite value. Work is bounded by:

- the existing accepted value depth ceiling;
- the existing accepted value byte ceiling;
- a checked visited-value-node budget no greater than the maximum representable
  admitted value work;
- the accepted constraint count bound; and
- bounded diagnostic-path storage.

The schema catalog is traversed by accepted ID lookup. A missing type, member,
variant, or value-shape mismatch after physical decode is corruption, not a
user constraint violation.

## Diagnostics

Every failure preserves the existing accepted constraint ID, source-bound
name, kind, and root field identity. A targeted-rule violation additionally
contains the first deterministic concrete value path.

Path components are typed:

- root field ID;
- record composite ID plus member ID;
- tuple composite ID plus ordinal;
- newtype composite ID;
- enum type ID plus selected variant ID;
- list/set element index; and
- map entry index plus key/value side.

Display names may be resolved when presenting the error, but they are not
stored as identity and are never parsed back into IDs.

Only the first violating occurrence per row and constraint is reported.
Deterministic traversal makes that occurrence stable for the same accepted
head and value. Mutation errors carry it directly. Activation findings retain
a bounded ID/ordinal/index path so acknowledgement and recovery preserve the
same evidence. A path bound failure is a typed resource-limit failure, never a
truncated or string-flattened violation.

## Mutation, Activation, Integrity, And Recovery

### Mutation

Defaults, generated/database-owned values, and managed timestamps complete the
final after-image first. The existing accepted mutation-constraint scheduler
then invokes the row-local program, including targeted rules, before
storage-backed unique and relation proofs and before commit. Typed, structural,
and SQL frontends cannot schedule or bypass targeted rules independently.

### Activation

Adding or strengthening a targeted rule to a non-empty entity uses the
existing accepted constraint activation protocol. The pending candidate owns
the exact accepted target and operation. Each historical row is decoded
against the candidate's accepted catalogs and evaluated by the same compiled
artifact used by normal writes.

### Integrity

Integrity inspection compiles from the active accepted head and invokes the
same traversal and scalar operation. It distinguishes:

- a valid value that violates an accepted constraint;
- a corrupt value/catalog/layout relationship; and
- evaluator resource exhaustion.

### Recovery

Recovery resumes marker/job state from the durable accepted candidate. It
does not reload authored schema, generated types, rule metadata, or Rust
callbacks. Cache reconstruction binds every compiled targeted rule to the
accepted revision and fingerprint in the same way as the existing row program.

## Persistence And Hard Cut

The accepted constraint kind, accepted-bundle bytes, source fragment/proposal
bytes, and activation-finding bytes will change. Row and index bytes do not.

Before 1.0, every affected format remains its single current version-1 form:

- do not introduce `V2`/`V3` public or internal variants;
- do not increment a persisted version discriminator merely to retain the old
  development form;
- do not decode old source-rule-as-check or old activation-finding bytes;
- do not translate an old accepted bundle into the new shape; and
- fail with the existing typed unsupported/corrupt-store boundary, with release
  notes requiring recreation of incompatible development stores.

Each format owner must update
`docs/contracts/PERSISTED_FORMAT_INVENTORY.md` in the patch that changes its
bytes. Golden encodings must cover the current version-1 form, trailing-byte
rejection, bounds, unknown discriminants, and cyclic target catalogs.

## Negative Space

0.213.39 does not:

- add custom database callbacks or arbitrary Rust validators;
- make `icydb-model` a runtime dependency of `icydb-core`;
- change explicit application normalizer/validator invocation;
- infer database rules from Rust constructors or `Default`;
- add nested SQL expression syntax;
- make records, enums, or tuples indexable by nested member;
- change row layouts or physical nested-value encoding;
- add cross-row nested uniqueness or nested relations;
- add regex, locale, URL, MIME, phone, or external lookup semantics;
- add aliases for the rejected pre-0.213.39 placement behavior;
- preserve the old source-rule lowering route; or
- redesign the query engine.

## Required Evidence

The completed line must prove:

- top-level source rules use the new sole targeted-rule path;
- a ruled newtype inside a record member rejects invalid values through typed,
  structural, and SQL writes;
- ruled values inside list, set, map key, map value, tuple, repeated field, and
  enum payload positions behave identically;
- the collection-scale `Values -> FieldValue -> Value -> Values` graph accepts
  finite values and evaluates every ruled recursive occurrence;
- excessive value depth, bytes, visits, diagnostic path, and constraint count
  fail with typed bounded errors;
- null, inactive enum branch, and empty-collection semantics are exact;
- defaults and managed timestamps precede targeted evaluation;
- batch mutations remain atomic;
- activation findings contain stable bounded paths and replay exactly;
- integrity and normal writes select the same first failing occurrence;
- recovery reconstructs without model/generated authority;
- type/member/variant renames retain target identity;
- old-name reuse cannot retarget a constraint;
- source removal and accepted target reachability fail closed;
- current version-1 codecs reject the retired bytes;
- schema-only proposals work without generated row structs; and
- application validators/normalizers remain absent from database execution.

## Principal Risks

- A selector based only on a nominal target intentionally governs every
  occurrence of that type below one root. Per-route opt-out would be a new
  authoring and identity decision and is not silently inferred.
- Activation findings now carry a durable concrete path. The N6 implementation
  publishes that evidence atomically with the candidate/job transition.
- Traversal can multiply work across many constraints over one large nested
  value. N4 bounds and groups rules by persisted root; N7 recorded the
  remaining single-rule cost with a one-off matched canister measurement and
  removed that evidence-only harness before release.
- Record values currently retain schema-visible member names in their
  canonical shape. Target identity must use member IDs even when value lookup
  necessarily consults the current accepted name.
- 0.216 now consumes this completed target contract without reopening its
  authoring-ergonomics scope.
