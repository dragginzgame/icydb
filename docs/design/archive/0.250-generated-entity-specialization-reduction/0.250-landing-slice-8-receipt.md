# IcyDB 0.250 Landing Slice 8 Receipt

## Outcome

Release validation now runs cheap deterministic checks as a fail-fast
preflight. Only a successful preflight starts the existing long Clippy,
feature-matrix and test targets, which continue across failures and retain all
failed-target output in one timestamped combined text log and `latest.log`.

The read-admission invariant follows the maintained Slice 2 architecture: the
typed query hands its binding and request to the concrete prepared cursor, and
that cursor enters identity-bound public admission. The removed direct typed
live-page wrapper is not restored.

## Evidence

The user-owned release receipt reported a three-second invariant failure after
formatting, workflow and shell preflights had passed. The old single runner
then continued through 115 seconds of Clippy, 126 seconds of feature checks and
1,619 seconds of tests. With the same observed timings, the corrected ordering
would return this class of failure after the cheap preflight, roughly eight
seconds rather than roughly 31 minutes. This is an ordering projection; the
already-completed full validation was not rerun.

Focused runner probes establish both policies:

- fail-fast mode did not execute a valid second target after a missing first
  target;
- accumulating mode executed two failing targets and retained both complete
  outputs under distinct headings in one `latest.log`; and
- the complete repository invariant gate accepts the current prepared-cursor
  admission boundary.

## Scope And Complexity

The implementation changes the Make validation order, the existing validation
runner and the two invariants that own those contracts. It adds no production
API, runtime behavior, state, format, Wasm byte or independent test mode.

The implementation footprint is five files and approximately `+107/-18`
lines. Five changelog, design, status and receipt files add approximately
`+119/-9` documentation lines. Wasm size and runtime performance deltas are
zero because no compiled product source changes.

Source structure is modestly more complex: the runner gains one explicit
fail-fast switch and one combined-log writer. Operational flow becomes simpler
and cheaper on deterministic failures while retaining the previous
multi-failure diagnostic behavior for expensive targets.
