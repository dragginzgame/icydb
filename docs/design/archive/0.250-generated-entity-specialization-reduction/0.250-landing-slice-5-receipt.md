# IcyDB 0.250 Landing Slice 5 Receipt

Date: 2026-08-31

Disposition: retained. One concrete same-entity typed-write terminal, typed
delete admission and removal of the proving consumer's parallel structural

## Retained Outcome

`DynamicTypedMutation` now admits delete by accepted primary key. Delete lowers
directly to the existing canonical structural delete intent; it does not add a
commit route, recovery state or batch mode.

The new same-entity core admission validates one exact binding, resolves one
accepted catalog and row contract, lowers a bounded non-empty sequence of
insert, update, replace and delete intents, then enters the existing canonical
atomic structural batch executor. The facade verifies that every `TypedWrite`
carries that binding, enforces exact result cardinality and returns one
`PreparedOutputRows` iterator sharing one accepted projection. Generated code
retains only value/key encoding and final typed row decoding.

The existing mixed-entity typed batch remains the heterogeneous-write owner.
No compatibility wrapper, alternate transaction, new limit, persisted state,
runtime registry or caller-selectable mode is added.

The disposable Toko proving source adopts the terminal in its same-entity
insert, update, replace and delete helpers. Its application trait and macro now
emit only source-bound typed insert, update and delete encoders; the parallel
structural insert/update field-construction families and structural delete
wrapper are removed. The original Toko worktree was not edited.

## Rejected Provisional Shape

The first facade-only shape delegated same-entity writes through the general
mixed-entity typed batch. Although it reduced the exact Toko actor by 12,197
raw and 11,796 code bytes, the ten-entity missing-delete sentinel increased by
294,446 instructions (`21.7%`), crossing both frozen material-regression
thresholds. It was not retained.

The final core admission removes repeated mixed-entity binding/catalog work and
uses the existing same-entity lowering/execution owner. The affected
ten-entity delete sentinel instead improves by 75,800 instructions relative to
Slice 4, while final raw and code savings also increase.

## Semantic And Cost Qualification

Focused core coverage exercises ordered insert/update/replace/delete mixtures,
empty and oversized rejection, stale and mixed/cross-store bindings, duplicate
atomic rejection, result cardinality/order and one-marker recovery after an
interrupted delete/insert batch. Facade coverage proves single/batch parity,
ordered row decoding, delete before-images, empty rejection and foreign-binding
rejection. The public compile contract and the exact disposable Toko package
check pass.

PocketIC controls preserve the selected operation results. Relative to Slice
4, the one- and ten-entity batch sentinels improve by 652,511 and 1,283,359
instructions; delete improves by 47,838 and 75,800. The largest selected
regression is only 159 instructions. No operation approaches the material
regression boundary of both 250,000 instructions and 3%.

Selected package all-feature Clippy passes with warnings denied. Public
exports, Candid, cursor formats, accepted-schema authority and persisted
version-1 bytes are unchanged. The full repository suite and downstream
CI/install remain user-owned validation.

## Complexity Delta

The IcyDB implementation and focused tests touch six files at approximately
`+334/-53` lines. Most additions are direct canonical-owner, recovery and
facade semantic coverage. Production adds one source-bound delete variant and
one same-entity admission helper; it reuses the existing lowerer, atomic batch
executor, result bound, commit marker and recovery path.

Source is larger because the optimized admission and its invariants are
explicitly tested. Execution flow is simpler for same-entity consumers: bind
once, lower once per intent, execute once, prepare one shared projection and
decode. The proving consumer deletes its duplicate structural encoder family.
Runtime state space remains neutral, with no new behavior axis, execution
route, registry, cache, persisted state, callback or compatibility layer.
