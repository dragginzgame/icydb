# 0.215 Atomic Mixed Structural Mutation Addendum

Status: implemented

Date: 2026-07-30

Audited tree: `main` at `839091e61eae526f9dde87361667fb24e0d291d8`

## Purpose And Relationship To The Main Design

This addendum records a data-integrity blocker discovered while migrating Toko
holding operations to the accepted-schema structural write boundary.

The current public API supports:

- one structural `Insert`, `Update`, `Replace`, or `Delete`;
- an atomic same-entity structural insert batch; and
- SQL updates in which every selected row receives the same authored patch.

It does not support one atomic same-entity batch containing heterogeneous
mutations such as:

- `Update` plus `Insert`;
- `Delete` plus `Update`; or
- multiple updates with different patches or after-images.

That missing boundary makes conservation-sensitive split, merge, and transfer
operations unsafe when expressed as separate calls. A later mutation failure
does not roll back an earlier successfully committed call, and compensation
cannot close an interruption window.

This addendum amends the bounded 0.215 scope with one separately reviewable
accepted-mutation landing slice. The main
[0.215 design](0.215-design.md) remains authority for SQL coverage,
performance evidence, and compound-range remediation. This addendum is
authority for the mixed structural mutation requirement and its acceptance
criteria.

The implementation must not be folded into SQL closeout, represented as a
loop over existing public methods, or delivered as independently committed
homogeneous batches. It must generalize the existing accepted mutation
pipeline so the complete mixed batch has one admission, preflight, marker,
journal, publication, and recovery outcome.

## Severity And Scope

Severity: P1 downstream migration blocker.

The existing single-operation APIs are not internally non-atomic; the
integrity risk appears when an application must compose separately committed
calls because the required atomic boundary is absent.

The required scope is deliberately bounded:

- every mutation targets one accepted entity;
- the batch contains a bounded number of operations;
- operations may be `Insert`, `Update`, `Replace`, or `Delete`;
- all operations use one accepted-schema snapshot;
- all generated database-owned values use one operation timestamp;
- all final rows and physical effects are validated before marker
  publication;
- every operation commits or none does;
- recovery cannot expose a committed prefix;
- results preserve deterministic input order; and
- no cross-entity transaction API is introduced.

The existing marker and journal format already represents mixed row puts and
row deletes through `CommitRowOp`. This requirement therefore does not
authorize a persisted-format change or a second transaction engine.

## Motivating Conservation Operations

### Split

Given holding A with quantity 100, the complete transition is:

1. update A from 100 to 60; and
2. insert B with quantity 40.

If those calls commit separately, an insert failure after the update can lose
40 units permanently.

### Merge

Given holding A with quantity 60 and holding B with quantity 40, the complete
transition is:

1. delete B; and
2. update A from 60 to 100.

If those calls commit separately, an update failure after the delete can lose
B's 40 units permanently.

### Transfer

A transfer may require several updates with distinct patches. A SQL update
that applies one patch to every selected row cannot express that operation.

## Public Contract

The maintained facade should expose the existing `StructuralMutation` family
through one mixed batch entry point equivalent to:

```rust
pub fn execute_trusted_structural_mutation_batch(
    &self,
    mutations: Vec<StructuralMutation>,
) -> Result<DynamicMutationResult, Error>;
```

The exact receiver and ownership shape may follow the maintained session
facade, but the semantic contract is fixed:

1. The batch is non-empty.
2. Every mutation resolves to the same accepted entity identity.
3. Name similarity is not sufficient proof of entity equality.
4. The item count and cumulative materialized/result bytes are bounded before
   marker publication with checked arithmetic.
5. Every update, replace, and delete resolves its target against the same
   accepted snapshot.
6. Database-owned defaults, managed timestamps, and Identity values are
   resolved under one operation timestamp and one accepted policy.
7. Constraints, uniqueness, relations, indexes, and physical resource
   admission observe the complete staged final state.
8. No committed prefix is visible if any later operation fails.
9. Marker publication and recovery treat the batch as one durable operation.
10. Results are returned in deterministic input order.

The result contract should retain one row per input mutation:

- inserts, updates, and replaces return their final after-images;
- deletes return their removed before-images; and
- aggregate affected-row accounting covers the complete successful batch.

Public-value conversion and response-bound validation are fallible and must be
completed before marker publication through the maintained precommit
preparation boundary. A committed mutation must not later appear to fail
because result conversion was deferred until after publication.

## Canonical Accepted Mutation Shape

The current accepted save batch applies one global `MutationMode`, while
deletes use a separate accepted batch and constraint schedule. The mixed
pipeline needs a per-item intent equivalent to:

```rust
enum AcceptedStructuralMutationIntent {
    Save {
        mode: MutationMode,
        target: AcceptedStructuralMutationTarget,
        patch: StructuralPatch,
    },
    Delete {
        key: DataKey,
    },
}
```

Equivalent variants for the four public operations are acceptable if they
retain the same information. The representation must preserve:

- stable input ordinal;
- accepted entity identity;
- save mode;
- authored omission, `DEFAULT`, null, and explicit value intent;
- expected or derived target key;
- the final before-image and after-image contract; and
- the operation-specific result row.

One operation may not target the same final key more than once in a batch.
Insert/update/delete sequences over one key would require ordered
in-transaction statement semantics and are outside this addendum. Duplicate
target keys across any operation combination must fail before marker
publication with a typed diagnostic.

The single-mutation and insert-batch paths should delegate to the canonical
mixed pipeline where that removes duplicate ownership. They must not remain
parallel policy engines.

## Canonical Preparation And Commit Flow

The required flow is:

```text
bounded mixed structural intents
    ↓
one accepted entity and schema-head resolution
    ↓
one operation timestamp and database-owned value policy
    ↓
all before-images and final after-images materialized
    ↓
one complete final-row overlay
    ↓
durable row constraints and cross-row/entity preflight
    ↓
relation and index transition preparation
    ↓
one ordered Vec<CommitRowOp>
    ↓
one marker and journal publication
    ↓
deterministic result publication
```

The existing `PreflightStoreOverlay` already seeds the final primary-row view
from mixed `CommitRowOp` values. Unique-index preparation correctly treats
updated and deleted old rows as releasing their previous membership. That
overlay and the existing generic structural commit window are the foundation
for this slice; another overlay or commit protocol must not be added.

The separate structural save and delete commit wrappers should converge on one
generic mixed row-operation owner. A proven single-row fast path may remain
internal only if it preserves the same accepted policy and recovery contract.

## Relation Validation Correction

Delete-side relation validation currently reads committed source rows directly
and recognizes same-batch changes only through a delete-key set. That is
insufficient for a mixed batch.

For example, deleting a target while updating a source row to remove the
reference is valid in the final staged state, but a committed-row-only check
would still see the old reference and reject the batch.

Delete relation proof must therefore consume the canonical final-row overlay:

- a source absent from the overlay is deleted;
- an updated source is validated from its final after-image;
- an inserted source is validated from its final after-image;
- an unaffected source falls through to committed accepted storage; and
- any final source that still references a deleted target rejects the entire
  batch before marker publication.

Save-side target validation must use the same overlay so an inserted or
updated relation can see a target created by the batch and cannot see a target
deleted by the batch.

Validation must not concatenate independently accepted save and delete
schedules. The complete staged final state is the semantic authority.

## Identity Allocation

Identity allocation remains tentative until marker publication and advances
one contiguous range per accepted Identity owner.

The current homogeneous insert path can use overall input position as the
allocation ordinal because every item inserts. A mixed batch cannot: inserts
may occur at non-contiguous batch positions.

Preparation must retain two ordinals:

- batch input ordinal for deterministic execution and results; and
- a contiguous Identity insert ordinal counting only allocations.

Only actual Identity-generating inserts contribute to the candidate count and
durable range. A pre-marker failure consumes no identity. Marker publication,
recovery, and replay retain the existing range contract and must neither skip
nor reuse values.

## Bounds And Diagnostics

Before implementation, the status amendment for this slice must freeze:

- the exact maximum operation count;
- the cumulative materialized input/row byte bound;
- the cumulative public result byte bound; and
- the relationship to existing per-row and commit-journal limits.

The existing exact SQL mutation limit of 4,096 rows is the preferred operation
cap unless focused implementation evidence requires a smaller bound. The
number must be made normative before code lands rather than inferred from
`u32` conversion or the journal byte ceiling.

Admission must fail with typed diagnostics for at least:

- empty batch;
- item-count or byte bound exceeded;
- mutations resolving to different accepted entities;
- duplicate target key;
- missing update/delete target;
- insert collision;
- replace-mode mismatch;
- constraint violation;
- uniqueness violation;
- relation violation;
- stale accepted adapter or accepted-head binding;
- corrupt or uninspectable physical state; and
- recovery inconsistency.

Errors must not be flattened to strings. No validation failure may publish a
marker or consume an Identity value.

## Durability And Recovery

The existing commit journal supports `RowPut` and `RowDelete` records in one
batch. The implementation must prove mixed recovery independently of Identity
state.

Focused interruption coverage must include:

1. failure before marker publication leaves no durable mutation;
2. recovery after marker publication reconstructs the exact admitted mixed
   row-operation set;
3. recovery after journal publication applies the same ordered set;
4. recovery after a partial physical application completes the batch without
   exposing a different semantic result;
5. replay cannot duplicate index or relation effects;
6. a completed batch returns the same semantic outcome on canonical replay;
   and
7. no recovery path consults authored or generated Rust model authority.

The current Identity-specific interruption hook is not sufficient proof for a
mixed caller-key batch. This slice needs a generic mutation commit
interruption harness or direct marker/journal recovery fixtures.

## Required Tests

The landing slice is incomplete without focused proof of:

- successful `Update` plus `Insert` split;
- a late split failure leaving the original quantity unchanged;
- successful `Delete` plus `Update` merge;
- a late merge failure leaving both original rows unchanged;
- multiple updates with distinct patches and after-images;
- exact conservation across successful split, merge, and transfer fixtures;
- empty, over-bound, mixed-entity, and duplicate-key rejection before writes;
- missing targets, insert collisions, and replace semantics;
- one accepted snapshot and one managed timestamp across the batch;
- a late durable row-constraint failure leaving every row unchanged;
- unique-value swap and release against the final overlay;
- deleting a target while updating its source to remove the reference;
- rejection when an updated or inserted final source still references a
  deleted target;
- an inserted or updated relation seeing a batch-final target;
- interleaved Identity inserts allocating one contiguous range;
- recovery at marker, journal, and partial-application phases;
- deterministic input-order results and delete-before/save-after row
  semantics;
- structural-only compilation without SQL, query, or generated entity
  authority; and
- SQL exact mutation paths retaining the same canonical accepted enforcement
  and commit owner.

Tests must use the maintained current API. No compatibility facade,
anti-resurrection fixture, generated persistence bridge, or test-only
transaction engine is permitted.

## Application Concurrency Caveat

This batch closes the partial-commit failure window. It does not by itself
protect a calculation based on a stale application read.

If an application reads quantities, crosses an `await` or another logical
interleaving point, and later submits the batch, it may need an
expected-before-image, revision, or other optimistic comparison. That is a
separate semantic requirement and is not silently implied by atomic batch
publication.

Callers that calculate and submit the complete batch without an interleaving
point receive the conservation guarantee defined here.

## Hard-Cut Rules

This is a pre-1.0 hard cut:

- do not add a loop over separately committed public mutations;
- do not expose separate homogeneous update, replace, and delete batches as a
  substitute;
- do not add a second accepted mutation or commit engine;
- do not add a compatibility alias or legacy typed persistence path;
- do not change the persisted marker or journal format without a separately
  approved finding proving it necessary;
- do not move application normalizers or validators into database
  enforcement;
- do not consult generated entity models at runtime;
- do not broaden the slice into cross-entity transactions; and
- do not add ordered multiple-mutation semantics for the same target key.

## Landing And Closeout

This addendum is Slice 6 of the 0.215 landing plan. It is independent of the
pending performance cohort and does not authorize Slice 4 before Slice 3's
existing evidence gate is satisfied.

Before Slice 6 implementation begins, its status entry must freeze the exact
item and byte bounds and name the focused test targets. The implementation is
one substantive handoff covering the public facade, accepted mutation
representation, common scheduler/preflight, relation-overlay correction,
Identity ordinal handling, commit/recovery proof, diagnostics, docs, and
direct tests.
