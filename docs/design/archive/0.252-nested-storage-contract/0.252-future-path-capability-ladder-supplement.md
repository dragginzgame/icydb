# IcyDB 0.252 — Future Path Capability Ladder Supplement

Status: ACCEPTED FUTURE-DESIGN GUIDANCE — FIRST RUNG RELEASED; NO FURTHER IMPLEMENTATION AUTHORITY

Date: 2026-09-01

Parent design: [0.252 Nested Storage Contract](0.252-design.md)

Active delivery tracker: [0.252 Status](0.252-status.md)

Current released baseline: immutable tag `v0.252.1`

## 1. Purpose And Authority

Direction B remains the normative 0.252 contract. This supplement records a
possible order for evaluating selected PostgreSQL-like composite and array
capabilities after that contract is complete. It does not add a 0.252 landing
slice, reserve syntax, approve a proof spike, or authorize implementation.

The pre-1.0 non-goals in the parent design are not permanent format
prohibitions. Future versions may introduce additional globally defined,
accepted-schema-owned path capabilities through separately measured designs.
Any extension must preserve existing whole-field semantics and must explicitly
define cardinality, indexing, cursor, mutation, recovery and resource-bound
behavior. No present syntax or runtime fallback reserves or implies such a
capability.

Each proposed rung must pass the pre-start evidence gate in Section 4 before it
may enter a delivery tracker. Every authorized implementation slice must then
pass the per-slice closeout gate in Section 6, and the completed rung must pass
the cumulative closeout gate in Section 7. Passing the pre-start gate only
makes a proposal eligible for a separate design and explicit user
authorization; it does not authorize work. The original 0.252.0 tracker remains
complete. The first rung's separate
[0.252.1 pre-start audit](0.252.1-scalar-record-path-parity-pre-start-audit.md)
returned **eligible for a separate design**; that verdict did not itself
authorize implementation. The user subsequently authorized the separate
[0.252.1 scalar-path grouping design](0.252.1-scalar-record-path-parity-design.md),
whose five landing slices are complete and released as `v0.252.1`. That
completed rung does not authorize any later rung in this supplement.

## 2. Extensibility Boundary

Accepted schema is the only authority that classifies a rooted field path. The
current classification remains:

1. direct root field;
2. scalar member path through required or optional named records; or
3. unsupported traversal.

A future accepted contract could add classifications such as:

- bounded-list existential path;
- positional list access; or
- multikey-indexed path.

Those classifications would be product semantics, not planner inference from a
runtime value. Existing query spellings must not silently acquire a different
cardinality or interpretation. Unsupported paths continue to reject before
planning until a complete future contract explicitly admits them.

An extension may be additive at the product-language level, but it does not
create pre-1.0 compatibility machinery. If it changes an internal protocol,
persisted/runtime representation, generated API encoding, cursor, or catalog
shape, IcyDB replaces that representation with the then-current version-1 form.
It does not retain an old decoder, dual format, fallback, or upgrade bridge;
reinstall, recreation, or explicit regeneration may be required.

## 3. Evaluation Ladder

The rungs are ordered from the narrowest single-valued extension to the largest
cardinality and storage change. They are not a roadmap commitment. A later rung
does not become eligible because an earlier rung ships, and independent rungs
must not be bundled merely because they appear in one ladder.

### 3.1 Complete Scalar Record-Path Parity — Released In 0.252.1

The 0.252 audit already admits scalar record paths for projection, filtering,
ordering, `DISTINCT`, aggregate arguments such as `SUM(profile.score)`, the
supported aggregate-expression form of `HAVING`, `CASE`, arithmetic, scalar
functions, internal prepared plans, and eligible composite indexes.

The completed rung addressed the demonstrated remaining gaps:

- `GROUP BY profile.rank`; and
- any raw group-key or raw-path `HAVING` semantics required by the accepted
  grouping contract.

Its audit re-enumerated the full ordinary-scalar matrix before implementation.
The released path still produces zero or one logical value per owning row and
uses accepted schema as its sole authority. No repeated-member capability was
implied or admitted.

### 3.2 Record-Member Updates

A future surface might admit an update such as:

```sql
UPDATE Player
SET profile.rank = profile.rank + 1
WHERE id = ?;
```

The narrow design would decode the named record, update the member, validate
the resulting complete record, and write the whole root field under the
existing row revision. Persistence, recovery, conflict granularity, indexes,
and authorization remain whole-row/whole-field unless a separately justified
design explicitly changes them.

The design must define optional-parent behavior, missing and explicit `NULL`,
expression typing, validation order, index reconciliation, diagnostics, and
whether any apparent member update can fail after reading the owning value.

### 3.3 Bounded-List Existential Predicates

A named list with a durable item-count maximum could eventually admit a bounded
existential predicate conceptually equivalent to:

```sql
WHERE EXISTS inventory ITEM WHERE ITEM.item_id = 500
```

The first candidate should be scan-only and preserve these invariants:

- no more elements are examined than the accepted named-list maximum;
- one owning row is returned at most once;
- no row expansion occurs;
- no index entry is created per element; and
- pagination and cursor identity remain those of the owning row.

The design must still define empty, optional, missing, `NULL`, duplicate-match,
short-circuit, nesting, instruction-budget, and diagnostic behavior. Physical
row/request/decode limits are not a substitute for an application-visible
durable item-count bound.

### 3.4 Positional List Access

A later candidate could evaluate projection or replacement at a position, for
example `inventory[3]`. An update may still lower to whole-field replacement
under the existing row revision.

Before admission, the design must define index origin, out-of-range behavior,
negative positions, optional and `NULL` values, whether positions can shift,
and concurrency when another write changes the list. It must also prove that
position syntax does not imply element identity or a finer conflict boundary.

### 3.5 Multikey Indexes

A multikey index such as `CREATE INDEX ON Player (inventory.item_id)` is a
storage, recovery, planning, and resource-accounting change. One owning row may
create up to the collection's durable maximum number of index entries.

Its design must cover at least:

- duplicate indexed values within one owning row;
- unique-index semantics across and within rows;
- old-versus-new entry reconciliation on whole-field replacement;
- atomic recovery and corruption detection;
- index generation and rebuild accounting;
- exact-cardinality metadata;
- ordering, pagination, and cursor boundaries;
- index fan-out and instruction budgets; and
- bounded decode, memory, and stable-write costs at maximum occupancy.

This rung requires a stronger whole-system audit than a scan-only predicate. It
must not be approximated by looping over elements inside the current
single-valued index path.

### 3.6 Relational Expansion And `UNNEST`

Relational expansion could conceptually produce one result row per collection
element. That conflicts with the current single-entity, no-join execution
model and changes result cardinality rather than merely resolving a field.

Any proposal must define planning, grouping, ordering, pagination, cursor
identity, duplicate owning rows, mutation interaction, resource bounds, and
the relationship to joins. It should be evaluated much later, if ever, and
requires the strongest system-wide evidence of the ladder.

## 4. Gate 1 — Mandatory Pre-Start Evidence

Before any rung is assigned a landing slice, changes a parser, or receives an
implementation spike, it requires a read-only baseline audit. The audit itself
does not authorize implementation. It must use the immutable tagged
predecessor and exact optimized build/toolchain identity selected by that
future design. The 0.252.1 scalar-path audit selects immutable `v0.252.0`; no
baseline is permanent across a later candidate line.

The audit establishes the original tagged baseline, forecasts the cost of the
complete rung and each proposed landing slice, and declares rejection budgets
before implementation. Forecasts must use the shared measurement contract in
Section 5 and the rung-specific plan in Section 8. A rung may not defer its
first real cost measurement until final closeout.

### 4.1 Raw Wasm Size

Raw, non-gzipped final `.wasm` bytes are the acceptance authority. The audit
must also record contextual section and surface evidence where available:

- code, data, and custom-section bytes;
- function, indirect-function, and export counts;
- Candid/public-method surface changes;
- gzip size as secondary context only; and
- always-retained versus feature-reachable cost; and
- per-entity, per-type, generated-binding, and additional-use growth.

At minimum, measurements must distinguish a minimal actor, a representative
entity workload, Toko, and any then-designated downstream actors, including
actors that cannot use the new route. The candidate design must set a
prospective retention/rejection budget from measured headroom before
implementation. This supplement does not invent one universal byte threshold
for features with different reachability.

### 4.2 Performance And Resource Cost

The audit must identify and baseline every directly affected hot path. Depending
on the rung, evidence includes:

- instruction count and stable-write/index-write work;
- examined rows and collection elements;
- heap allocation and retained memory;
- latency where the harness is stable enough to compare;
- positive-match, negative-match, empty, and declared-maximum cases; and
- mutation, recovery, rebuild, pagination, and cursor costs where reachable.

The proposed design must state its performance gate before implementation and
must separate fixed overhead, per-row slope, per-element slope, and bounded
worst case. A named maximum such as 51 elements bounds work; it does not by
itself prove that the maximum-cost path is acceptable.

The baseline suite must include an existing query and write that cannot use the
new route. Their predeclared control gates detect shared planner, executor,
decoder, write-admission, or generated-code regressions even when the new
operation itself is acceptably fast.

### 4.3 Complexity And State Space

The audit must map the current semantic owner and converged execution flow,
then disclose the proposed state-space delta. It must cover:

- parser and fluent syntax;
- lowering, accepted-path classification, planning, and execution;
- index, cursor, mutation, recovery, diagnostics, and `EXPLAIN` behavior;
- public, generated, persisted, or catalog representations;
- new modes, enum variants, branches, feature combinations, and fallbacks;
- expected delivery domains, reviewable landing slices, files, and approximate
  line delta; and
- code or authority that the proposal deletes, reuses, duplicates, or adds.

The audit must name the demonstrated user need, the simplest no-build or
whole-field/entity-modeling alternative, the canonical owner, and why one
converged flow remains possible. Runtime shape guessing, dual semantics,
capability tiers, compatibility fallbacks, and speculative format hooks are
complexity costs, not shortcuts.

### 4.4 Audit Receipt And Verdict

The audit deliverable must be a reviewable receipt containing:

1. immutable source, build, toolchain, actor, and workload identities;
2. the exact current capability/gap matrix;
3. raw Wasm, performance/resource, and complexity baselines;
4. expected reachability and cost slopes;
5. proposed whole-rung and per-slice acceptance and stop gates;
6. the no-build alternative and deferral cost; and
7. one verdict: **no-build**, **investigate**, or **eligible for separate
   design**.

Only the final verdict permits a proposal to seek explicit authorization for a
separate design. It does not authorize a landing slice. Evidence is rung- and
baseline-specific: it does not carry from scalar grouping to list predicates,
from scan-only predicates to multikey indexes, or across a changed tagged
predecessor without remeasurement.

## 5. Shared Measurement Contract

The same evidence vocabulary applies at pre-start, every slice closeout, and
rung closeout. A receipt must record a numeric value, a reproducible method, or
an explicit `not applicable` with the semantic reason for every category.
Silence is not evidence of zero cost.

| Cost category | Required evidence |
| --- | --- |
| Raw Wasm | Final non-gzipped bytes for minimal, representative, Toko, and any other designated-downstream actors. |
| Wasm sections | Code, data, and custom-section bytes. |
| Wasm structure | Functions, indirect functions/table entries, exports, Candid methods, and generated public methods. |
| Reachability | Always-retained runtime cost versus cost retained only by an actor using the feature. |
| Monomorphization | Per-generated-entity, per-generated-type, per-binding, and per-additional-use growth. |
| Runtime | Instructions for directly affected operations, separated into planning/preparation and execution where applicable. |
| Unaffected control | Instructions for at least one existing query and one existing write; each fixture must be unable to select the new route. |
| Physical work | Rows, elements, index entries, scans, gets, deletes, inserts, and writes. |
| Persistence | Stable-state bytes, journal bytes, index bytes, recovery/replay work, and rebuild cost. |
| Memory | Peak allocation and retained heap where reproducibly measurable. |
| Scaling | Fixed cost, per-row slope, per-element or per-entry slope, and per-additional-use Wasm slope. |
| Worst case | Declared maximum occupancy, maximum supported cardinality, and maximum request/batch shape. |
| Complexity | Production and test line delta, decision branches, enum variants, persisted/public formats, semantic authorities, and execution routes. |
| Benefit | Measured user-visible improvement over the no-build alternative, including payload, instructions, latency, or authoring/error reduction as applicable. |

### 5.1 Comparison Points

For a rung with accepted slices `S1` through `Sn`, every `Si` receipt compares
three exact source and artifact identities:

1. `B0`: the original immutable tagged predecessor selected by the pre-start
   audit;
2. `B(i-1)`: the immediately preceding accepted slice, or `B0` for the first
   slice; and
3. `Bi`: the candidate slice.

`B(i-1) → Bi` is the attributable incremental cost of the exact slice.
`B0 → Bi` is the cumulative cost of the rung to date. Both comparisons remain
visible even when a later slice removes cost introduced by an earlier slice.

All comparisons use the same optimized build profile, toolchain, lockfile,
actor definitions and inputs, workload data, warm/cold state, and repetition
policy. Each receipt records those identities. When a source change makes an
identity difference unavoidable, the receipt discloses it, rebuilds all
comparison points under the closest reproducible common environment, and
separates the environmental delta from the attributed result. An unexplained
input difference invalidates the comparison.

### 5.2 Wasm Attribution

Aggregate Wasm change alone is insufficient. Each receipt separates:

- runtime growth retained by every actor;
- growth retained only when the feature is reachable;
- growth per generated entity, composite type, or binding; and
- marginal growth from each additional feature use after the first.

The actor matrix must include both feature-using and unaffected-control actors.
This prevents a small generic implementation from hiding downstream
monomorphization or generated-binding growth.

### 5.3 Unaffected Controls

Each slice declares control fixtures before implementation. At least one
ordinary query and one ordinary write must be incapable of selecting the new
classification or execution route. The receipt measures their instructions and
physical work against both comparison points.

A feature-specific benchmark passing does not excuse a control regression.
Noise bands and rejection thresholds must be predeclared and justified by
repeated baseline measurements, not selected after observing the candidate.

## 6. Gate 2 — Per-Landing-Slice Measurement And Closeout

Every implementation landing slice must have one independently reviewable cost
receipt before it may be marked complete. Documentation, diagnostics, tests,
fixtures, and mechanical propagation belonging to that slice are included in
the candidate source identity even when they do not reach the final Wasm.

The receipt compares `B0`, `B(i-1)`, and `Bi` as defined in Section 5.1 and
records attributable and cumulative results for every Section 5 category. The
slice's predeclared gate must cover raw Wasm, code/data/custom-section bytes,
function and public-surface counts, runtime instructions, physical work,
stable-state cost, memory, complexity, affected actor reachability,
monomorphization, controls, worst case, and measured benefit.

A slice that introduces infrastructure but no reachable user benefit is an
**enabling-cost slice**. Its receipt records zero measured benefit and the full
attributable cost. The cost may not be hidden in, reassigned to, or reported
only with a later user-visible slice.

A slice fails closeout when any predeclared rejection gate is exceeded. It must
be reverted, narrowed, or returned for an explicitly accepted tradeoff before
it can be marked complete. Later savings may reduce the cumulative rung cost,
but they may not retroactively erase or excuse the slice's attributable cost.

No receipt may combine independent landing slices. If implementation evidence
shows that a planned slice contains separable cost centers requiring separate
accept/reject decisions, the tracker must split them before closeout rather
than averaging them into one result.

## 7. Gate 3 — Rung Measurement And Closeout

After the final accepted slice, the complete rung is rebuilt from its final
source identity and measured against `B0` with the same profile, toolchain,
lockfile, actor matrix, inputs, workloads, and repetition policy. The receipt
re-runs the full Section 5 matrix and the rung-specific plan in Section 8; it
does not merely add the per-slice deltas.

The permanent evidence ledger retains:

- every slice's `B(i-1) → Bi` attributable result;
- every slice's `B0 → Bi` cumulative result;
- the final rebuilt `B0 → Bn` rung result;
- all enabling-cost slices and zero-benefit results;
- disclosed environment or measurement discontinuities; and
- explicitly accepted tradeoffs, reversions, or narrowed scope.

The rung fails closeout when the cumulative rejection budget is exceeded, an
unaffected control regresses beyond its gate, a worst-case bound is not
measured, or the final semantics have more authorities/routes/formats than the
accepted design. It must be narrowed, reverted, or returned for an explicitly
accepted tradeoff. A favorable cumulative total does not rewrite a failed
slice receipt or conceal where cost entered.

## 8. Rung-Specific Measurement Plans

The following workloads are mandatory additions to the shared matrix. A route
that the future design deliberately does not admit is recorded as `not
applicable`; an eligible route may not be silently omitted.

### 8.1 Scalar Record-Path Parity

Compare nested grouping with the equivalent direct scalar query:

- `GROUP BY direct_rank` versus `GROUP BY profile.rank`;
- ordered and hash grouping strategies where either can be selected;
- one group, many groups, and maximum supported group cardinality;
- required, optional, missing, and explicitly `NULL` paths;
- cold planning, prepared-plan reuse, and execution as separate costs;
- index-supported and scan routes where eligible;
- fixed planner overhead and per-row slope; and
- raw Wasm/function growth in feature-using and unaffected actors.

Stable-write, journal, index-write, and recovery cost must record zero or `not
applicable`; grouping does not gain a persistence route. The predeclared
acceptance question is whether nested grouping costs materially more than
ordinary scalar grouping after path resolution.

### 8.2 Record-Member Updates

Compare member-update syntax with today's canonical read/construct/whole-record
replacement producing the identical final row. Measure:

- a non-indexed member;
- an indexed member with unchanged and changed index keys;
- required and optional parent records;
- explicit `NULL`, missing parent, and validation failure;
- single mutation and maximum supported atomic batch;
- successful, no-op, and late-rejected writes;
- instructions, row reads, stable bytes, and journal bytes;
- index gets, deletes, inserts, and unchanged-key reconciliation;
- recovery and replay cost; and
- raw Wasm, public method, generated API, and per-binding growth.

The gate must prove that ergonomic syntax creates no second persistence or
recovery route and must quantify how closely execution converges with explicit
whole-record replacement.

### 8.3 Bounded-List Existential Predicates

Use occupancies of zero, one, a representative middle size, and the declared
maximum such as 51. At every size measure a first, middle, final, absent, and
multiple-element match where the case exists, plus optional, missing, and
`NULL` roots. Record:

- rows and elements examined;
- the short-circuit point;
- instructions per owning row and examined element;
- decode and peak-allocation cost;
- result-payload reduction against retrieving complete lists and filtering in
  application code; and
- maximum rows multiplied by maximum list occupancy.

Publish the measured cost equation:

$$
C = C_{\text{fixed}} + R C_{\text{row}} + E C_{\text{element}},
\qquad E \leq R \times N_{\max}.
$$

Because the candidate is scan-only, index-entry, stable-write, journal, and
recovery work must record zero or `not applicable`, not be blended with a
future multikey design.

### 8.4 Positional List Access

Compare database-side positional projection with retrieving the complete list
and indexing it in application code. Measure:

- empty, one-item, representative, and maximum-occupancy lists;
- first, middle, and last valid positions;
- out-of-range and invalid positions;
- required, optional, missing, and `NULL` lists;
- projection and replacement separately;
- whether position zero still decodes or validates the complete list;
- result-payload savings;
- whole-list stable-write and journal bytes for positional updates; and
- reconciliation of any ordinary indexes on the owning row.

The receipt must not label access as constant-time merely because its syntax
contains a position. If the codec decodes or validates the complete list, the
measured slope remains linear in occupancy.

### 8.5 Multikey Indexes

Measure fan-out at zero, one, a representative occupancy, and the declared
maximum such as 51, with all-distinct, all-identical, and mixed-duplicate
values. The workload matrix includes:

- positive- and no-match reads;
- replacement from maximum old values to maximum completely different values;
- replacement with no indexed-value change;
- one-row write and maximum supported atomic batch;
- index construction and complete rebuild;
- recovery after interruption at every durable phase;
- stable bytes per index entry;
- instructions per inserted, deleted, and reconciled entry;
- cursor size and pagination/resume cost;
- exact-cardinality metadata maintenance; and
- corruption-detection work.

Publish measured bounds and slopes:

$$
\text{entries per row} \leq N_{\max}
$$

$$
C_{\text{write}} = C_{\text{row}}
  + D C_{\text{delete}} + I C_{\text{insert}},
\qquad D \leq N_{\max},\ I \leq N_{\max}.
$$

The maximum replacement case must include $D = N_{\max}$ and
$I = N_{\max}$. The benefit comparison must include the no-build relational
alternative: an `InventoryCell` entity with an ordinary scalar index.
Convenience alone does not establish that multikey indexing is the cheaper
product.

### 8.6 Relational Expansion And `UNNEST`

Measure both owning-row and expanded-row cardinality across:

- zero, one, representative, and 51 elements per owner;
- one owner and the maximum supported owner input;
- projection-only expansion;
- filtering before and after expansion;
- ordering, grouping, and pagination when proposed;
- maximum response payload and rejection behavior above it;
- peak memory and instructions per produced row;
- cursor representation, size, and resume cost; and
- equivalent child-entity queries.

The governing cardinality equation is:

$$
R_{\text{output}} = \sum_{i=1}^{R_{\text{owners}}} N_i.
$$

For example, 2,048 owners with 51 elements each imply 104,448 logical rows.
The design must measure that maximum, or the exact bounded admission/rejection
path that prevents it, rather than citing only the per-list bound.

## 9. Stop And Retention Rules

A proposal stops or remains unsupported when any of the following is true:

- no demonstrated need outweighs the no-build/entity/whole-field alternative;
- accepted schema cannot remain the sole path-classification authority;
- semantics depend on inspecting runtime value shape;
- cardinality, missing/`NULL`, ordering, cursor, or mutation behavior is
  incomplete;
- raw Wasm or performance cost lacks a predeclared measurable gate;
- measured cost exceeds that gate without an explicitly accepted tradeoff;
- a landing slice lacks both incremental and cumulative closeout receipts;
- an unaffected control or downstream actor is omitted;
- the design creates multiple semantic authorities or uncontrolled feature
  combinations; or
- a representation change depends on a pre-1.0 legacy decoder, dual format,
  fallback, or upgrade bridge.

Until a future design is explicitly authorized, do not add reserved grammar,
placeholder classifications, dormant enums, format tags, feature flags, empty
hooks, fallback routes, or speculative fixtures. Direction B's current
whole-field and zero-or-one scalar-path semantics remain complete on their own.

## 10. Why Direction B Preserves The Ladder

Direction B provides the useful foundations without committing IcyDB to a
document or array-query product:

- composites and collections have exact accepted types;
- named collections may own durable application-visible maximum lengths;
- accepted schema is the only path authority;
- unsupported traversals reject before planning;
- current admitted paths have zero-or-one-value-per-row semantics; and
- no premature multikey index, expanded-row, cursor, or recovery format needs
  preservation.

Whole-field replacement therefore remains the storage primitive beneath any
future ergonomic member or positional update. Each additional capability can
be judged on measured value and cost, while unsupported rungs remain absent
rather than partially implied.
