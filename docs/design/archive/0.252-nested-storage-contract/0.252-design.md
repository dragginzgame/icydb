## 1. Decision Summary

IcyDB is a relational database with exact typed composite values, not a partial
document database. Direction B—single-valued composites and repeated
aggregates—is accepted as the long-term pre-1.0 centre.

The accepted narrow contract is:

- scalar leaves beneath one required or optional named record retain only the
  exact query and index cells enumerated in Section 4.2;
- all repeated values remain physically bounded by row, request and decode
  limits, while only named collection types may own an application-visible
  durable item-count bound; repeated collections remain aggregate values with
  whole-field admission and replacement but no member-path traversal,
  multikey indexes or subpath mutation;
- independently queried repeated children are modeled as entities;
- accepted schema remains the sole runtime authority for both admitted paths
  and deliberate rejections; and
- SQL, generated and structural surfaces describe the same capability boundary
  even when their authoring ergonomics differ.

This direction mostly names and tightens the coherent behavior already
released in 0.250.1. It does not require a new planner route, storage format,
cursor form, mutation mode or capability configuration.

The accepted no-build outcome is to publish the contract and modeling guidance,
retain the current implementation, and add no nested feature. The Toko Miner
evidence does not demonstrate a need for list-element queries or partial
document mutation. Landing Slice 3 adds the separately measured
generated structural-input adapter at the authoring boundary without widening
the mutation contract.

The separately authorized 0.252.1 addendum subsequently completed the one
remaining scalar record-path query cell: accepted groupable paths may now be
declared in `GROUP BY` and referenced as exact raw grouped keys. It preserved
the relational single-valued boundary and did not admit repeated traversal or
partial mutation. Sections 4.2 and 11 retain the explicit `v0.250.1` baseline
that motivated that addendum; the maintained current contract is recorded in
the [scalar-path grouping design](0.252.1-scalar-record-path-parity-design.md)
and [Nested Storage Contract](../../contracts/NESTED_STORAGE.md).

## 2. Why A Decision Is Needed

The released system supports several nested behaviors that can be mistaken for
one larger promise:

- exact nominal records, tuples, newtypes and collections persist through
  accepted-schema admission;
- targeted durable rules visit finite direct and nested occurrences;
- SQL admits the exact scalar-path cells enumerated in Section 4.2 beneath a
  single-valued record;
- accepted field-path indexes can index an admitted single-valued scalar path;
- top-level collection predicates are limited to the exact root operators in
  Section 4.3;
  and
- structural writes can replace a complete composite or collection value.

Those facts do not establish semantics for a path through a repeated value.
For example, `profile.rank` identifies at most one value per row, while
`inventory.slot` may identify zero, one or many values. Admitting the latter
would require choices about existential versus expanded results, duplicate
matches, ordering, cursor boundaries, index fan-out, uniqueness, mutation
identity and resource bounds.

The current implementation already draws a real boundary:

- accepted nested-leaf metadata is derived only when the owning persisted field
  is a single composite record;
- a many-valued field lowers to a list kind and does not receive member-path
  leaf metadata;
- generated index authoring rejects a many-cardinality field;
- field-path index materialization walks map-shaped composite values rather
  than expanding lists; and
- nested expression execution uses one compiled map-key path, not a collection
  expansion program.

This is a sound fail-closed boundary. The design problem is that maintained
documentation does not yet present it as one deliberate product contract.

## 3. Vocabulary

This design uses the following terms narrowly:

| Term | Meaning |
| --- | --- |
| Scalar field | One accepted scalar at the entity-row root. |
| Single-valued composite | One required or optional nominal record, tuple or newtype stored in one root field. |
| Scalar member path | A rooted dotted path through named members of required/optional records that terminates at one accepted scalar. |
| Repeated aggregate | A list, set or map whose contents are owned and replaced as part of the containing row. |
| Repeated member path | A path that would have to traverse or expand a list, set or map before reaching its terminal. |
| Whole-field mutation | Omission, default, null or one complete authored value supplied for the owning persisted field. |
| Subpath mutation | A write that targets a composite member or collection element without supplying the complete owning field value. |

“Nested”, by itself, is not a capability. Every maintained statement should
name the shape, cardinality and operation it means.

## 4. Released 0.250.1 Capability Baseline

These tables record the exact released baseline and accepted direction. They do
not broaden a cell beyond behavior already maintained in 0.250.1.

### 4.1 Shape And Cardinality Matrix

| Persisted shape | Exact storage and decode | Query surface | Index surface | Mutation surface |
| --- | --- | --- | --- | --- |

| Tuple | Exact nominal positional list and arity. | Complete root value only; there is no maintained dotted positional-member path. | No tuple-member field-path index. | Complete root-field replacement only. |
| Newtype | Exact nominal wrapper and inner kind. | Existing root-field behavior for the accepted kind; no independently addressable wrapper-member path. | No wrapper-member field-path index. | Complete root-field replacement only. |
| Named list | Exact accepted item kind and list shape. | Complete root value and only the root predicates enumerated in Section 4.3. | No element traversal or multikey fan-out. | Complete aggregate replacement only. |
| Anonymous `value(many, ...)` | Exact accepted item kind and list shape. | Complete root value and only the root predicates enumerated in Section 4.3. | No element traversal or multikey fan-out. | Complete aggregate replacement only. |
| Set | Exact accepted item kind and canonical set shape. | Complete root value and only the root predicates enumerated in Section 4.3. | No element traversal or multikey fan-out. | Complete aggregate replacement only. |
| Map | Exact accepted key/value shape. | Storage and whole-field write only under the maintained query-practice contract. | No map-key or map-value path index. | Complete aggregate replacement only. |
| Opaque JSON/blob payload | One bounded `Blob` whose bytes and application encoding are opaque to IcyDB; there is no database JSON kind. | Complete root storage/projection and the maintained whole-blob scalar operations only; no JSON member expression. | No blob-member path or JSON/member index. | Complete blob replacement only; the application owns encoding and payload-version policy. |

Only named record members currently produce accepted dotted nested-leaf
metadata. “Single-valued composite” is the product category; it does not imply
that tuples or newtypes have an invented member-path syntax. Existing
top-level list/set predicates treat the collection as one value and do not
establish element traversal.

### 4.2 Scalar Member-Path Query And Index Matrix

This is the focused `v0.250.1` behavior audit for an admitted scalar path such
as `profile.score`. A supported cell remains subject to the terminal scalar
kind and to the ordinary clause-specific SQL contract; path admission does not
make an otherwise invalid scalar operation valid.

| Context | Exact `v0.250.1` contract | Accepted or rejected example |
| --- | --- | --- |
| Projection | Supported. | `SELECT profile.score FROM Player` |
| Filtering | Supported for the ordinary predicate/expression family accepted by the terminal kind. | `WHERE profile.score >= 10` |
| Ordering | Supported when the terminal kind is orderable. | `ORDER BY profile.score ASC` |
| Projection `DISTINCT` | Supported; the complete projected scalar result is the distinct key. | `SELECT DISTINCT profile.score FROM Player` |
| `GROUP BY` | Unsupported. The released grouped-key surface is direct-field-only and does not carry nested path identity. | `GROUP BY profile.score` rejects. |
| Aggregate input | Supported when that aggregate accepts the terminal kind, including `DISTINCT` aggregate inputs. | `SUM(profile.score)` and `COUNT(DISTINCT profile.score)` |
| `HAVING` | Supported only when the path is consumed inside an admitted aggregate expression. A raw path cannot become a grouped key through `HAVING`. | `HAVING SUM(profile.score) > 100` is accepted; `HAVING profile.score > 10` rejects. |
| `CASE`, arithmetic and scalar functions | Supported recursively wherever the selected function/operator and clause accept the terminal kind. | `CASE WHEN profile.score >= 10 THEN profile.score * 2 ELSE 0 END` |
| Prepared/cached execution | Supported. The internal schema-bound prepared plan and semantic cache key retain the rooted path. Public SQL placeholder parameters and a user-visible `PREPARE` statement are not part of the released SQL subset. | Re-executing `SELECT profile.score FROM Player WHERE profile.score >= 10` may use the normal prepared-plan cache. |
| Single and composite indexes | Supported when every key component is an accepted indexable scalar source. A member path may be one component of a composite key. | `CREATE INDEX player_tenant_score_idx ON Player (tenant_id, profile.score)` |

This matrix is the meaning of “first-class scalar member path” in this design.
It does not promise `GROUP BY`, raw-path `HAVING`, placeholder SQL or a new
prepared-statement surface.

### 4.3 Whole-List And Whole-Set Predicate Matrix

The maintained list/set predicate surface is the public structural/fluent
`FilterExpr` surface below. The examples are exact accepted authoring forms;
SQL does not gain a collection-literal, collection-member or path-through-many
syntax from them. Complete-value literals and `contains` elements must be
representable by `FilterValue` and admitted by the collection's accepted kind;
the examples deliberately use text elements rather than promising structural
record literals on this query DTO.

| Operator | List example | Set example | Meaning |
| --- | --- | --- | --- |
| `eq` | `FilterExpr::eq("tags", InputValue::list(vec!["mage".into(), "healer".into()]))` | `FilterExpr::eq("roles", InputValue::list(vec!["admin".into()]))` | Strict equality with one complete admitted collection value. |
| `ne` | `FilterExpr::ne("tags", InputValue::list(vec!["banned".into()]))` | `FilterExpr::ne("roles", InputValue::list(vec!["retired".into()]))` | Strict inequality with one complete admitted collection value. |
| `eq_field` | `FilterExpr::eq_field("tags", "required_tags")` | `FilterExpr::eq_field("roles", "effective_roles")` | Strict equality between compatible complete collection fields. |
| `ne_field` | `FilterExpr::ne_field("tags", "blocked_tags")` | `FilterExpr::ne_field("roles", "denied_roles")` | Strict inequality between compatible complete collection fields. |
| `in_list` | `FilterExpr::in_list("tags", [InputValue::list(vec!["mage".into()]), InputValue::list(vec!["healer".into()])])` | `FilterExpr::in_list("roles", [InputValue::list(vec!["admin".into()]), InputValue::list(vec!["operator".into()])])` | Test the complete collection against finite complete collection literals; this is not element membership. |
| `not_in` | `FilterExpr::not_in("tags", [InputValue::list(vec!["banned".into()])])` | `FilterExpr::not_in("roles", [InputValue::list(vec!["retired".into()])])` | Reject finite complete collection literals; this is not element non-membership. |
| `contains` | `FilterExpr::contains("tags", "mage")` | `FilterExpr::contains("roles", "admin")` | Test whether the top-level collection contains one admitted element. It does not traverse a record-valued element. |
| `is_empty` | `FilterExpr::is_empty("tags")` | `FilterExpr::is_empty("roles")` | Test whether the complete top-level collection has zero elements. |
| `is_not_empty` | `FilterExpr::is_not_empty("tags")` | `FilterExpr::is_not_empty("roles")` | Test whether the complete top-level collection has at least one element. |
| `is_null` | `FilterExpr::is_null("tags")` | `FilterExpr::is_null("roles")` | Test a nullable collection root for explicit `NULL`. |
| `is_not_null` | `FilterExpr::is_not_null("tags")` | `FilterExpr::is_not_null("roles")` | Test a nullable collection root for a present complete collection value. |

Ordered range operators, collection-member paths, existential/universal
predicates, collection-to-rows expansion and multikey behavior are not
supported. Accepted set inputs use the canonical admitted set identity; the
query contract does not expose list order as set semantics.

### 4.4 Bounds, Rules, Integrity And Recovery

| Capability | Accepted contract |
| --- | --- |
| Durable named-type rules | Applicable accepted rules visit finite direct, nested, repeated and recursive named-value occurrences. |
| Durable repeated-item count | A named collection owns `length_range_inclusive`; the rule is enforced by accepted write, activation, integrity and recovery authority. |
| Anonymous repeated-item count | `value(many, ...)` has no inline schema-owned item-count rule. General row, request and bounded-decode ceilings still apply, but they are not an application capacity promise. |
| Checks | Only shapes and paths admitted by the existing accepted check binder are supported. No repeated-member check, relation or uniqueness is inferred from structural nesting. |
| Relations and uniqueness | Existing explicitly accepted root relations and eligible scalar index contracts remain authoritative. Repeated members own neither relation identity nor uniqueness. |
| Write admission | The complete final row image and every applicable durable rule are validated before commit preparation. |
| Conflict and atomicity | The application may use its existing row revision plus IcyDB's existing atomic mutation-batch boundary. There is no field, member or element compare-and-swap identity. |
| Recovery and replay | Existing row and batch journal/recovery semantics apply to the complete replacement. There is no partial aggregate delta, element replay record or second recovery route. |
| Cost visibility | The optional entity-cost report, Canic endpoint evidence, row/request ceilings, and bounded recursive decode remain applicable. No repeated-path fan-out budget exists because repeated paths are unsupported. |

### 4.5 Optional Path Null, Missing, Distinct And Index Semantics

An explicit `NULL` terminal and a missing descendant are distinct for
predicate admission, but some result operators intentionally collapse them:

- `profile IS NULL` matches exactly a present root `NULL`, and
  `profile IS NOT NULL` matches exactly a present non-null root record;
- projection materializes `NULL` for a missing admitted descendant path;
- filtering treats a missing descendant as no match, including for `IS NULL`;
- an explicit accepted terminal `NULL` follows normal SQL null predicates and
  matches descendant `IS NULL`;
- an absent optional ancestor makes its descendant path missing rather than
  creating an independently addressable member value;
- ordering treats a missing descendant and an explicit terminal `NULL` as the
  same null key: they compare equal, sort first in ascending order and last in
  descending order, with the normal total-order tie-break deciding row order;
- projection `DISTINCT` likewise collapses missing descendants and explicit
  terminal `NULL` into one `NULL` result; scalar aggregates consume the
  materialized `NULL` under their ordinary null rules; descendant `GROUP BY`
  has no semantics because Section 4.2 rejects scalar member paths there;
- an already accepted omission-capable non-unique nested index contains no
  entry for a null/missing indexed terminal. A supported comparison against a
  non-null literal, such as `profile.score >= 10`, may use that index because
  the predicate excludes omitted rows. `IS NULL`, a missing-path test and a
  root-null test cannot use that index to recover omitted rows; and
- a unique index below a nullable ancestor rejects because the maintained
  physical resolver does not provide the required omission proof; an
  omit-capable nested terminal also rejects because the predicate binder does
  not accept the required dotted `IS NOT NULL` membership guard.

This does not create a new eligibility promise for paths below nullable
ancestors. It records use of an already accepted omission-capable index; the
accepted index contract remains the authority.

### 4.6 Surface Parity

| Surface | Admitted single-valued record path | Repeated or map traversal |
| --- | --- | --- |
| SQL projection/filter/order | Resolves through accepted nested-leaf metadata. | Reject before execution. |
| Generated fluent query | Generated record members have source `FieldRef` values, but rooted-path composition is not yet a maintained ergonomic promise. | No traversal reference is generated or accepted. |
| Dynamic query construction | Must resolve through the same accepted path classification as SQL. | Reject before planning; no scan fallback. |
| Generated index authoring | May describe only an already eligible accepted scalar source. | Many-cardinality sources reject. |
| SQL DDL index authoring | May bind only an accepted, indexable scalar field path. | Reject before catalog mutation; no multikey candidate. |
| `EXPLAIN` and diagnostics | Report the normal admitted route and residual work. | Return a typed pre-execution rejection; never report a successful fallback route. |
| Typed entity write | Authors a complete accepted typed field value. | Authors the complete aggregate, not an element operation. |
| Structural write | Replaces one complete root field through normal accepted write admission. | Member, positional, keyed and predicate-selected targets reject. |

The documentation/contract landing slice must audit these surfaces and use one
stable unsupported-path vocabulary without pretending their exact variants are
identical. Code and tests must not match error strings. The entry audit found
that unknown structural mutation field names reached an executor
invariant rather than a user-facing unsupported-field diagnostic. Landing
Slice 2 hard-cuts that lookup failure to the existing executor-origin
`RuntimeUnsupported` boundary without adding a diagnostic variant, payload, or
mutation route.

## 5. Candidate Directions

### A. Typed Values Only

All composites and collections are typed row values. Nested SQL is retained as
an administrative convenience with no broad optimization promise.

This is the smallest conceptual product, but it understates the accepted
single-valued field-path indexes and query behavior already maintained. It
would require describing those features as narrow exceptions, so it is not the
accepted direction.

### B. Single-Valued Composites, Repeated Aggregates

Single-valued scalar member paths carry exactly the audited query and index
cells in Section 4.2. Repeated collections remain whole-field aggregates.
Independently queried children become entities.

This is accepted because it matches the strongest coherent released subset
without adding collection expansion semantics.

### C. Document/Relational Hybrid

Repeated paths gain explicit element predicates, multikey indexes, keyed or
positional mutation and potentially nested relations or uniqueness.

This is an explicit pre-1.0 non-goal. No downstream evidence justifies its
planner, storage, cursor, constraint, mutation, recovery and cost surface.

### D. Author-Selected Capability Tiers

Schema authors opt nested values into aggregate-only, queryable, indexable or
repeated-query tiers.

This is also an explicit pre-1.0 non-goal. It introduces a configuration axis
despite the accepted product decision and multiplies combinations across schema
authoring, SQL, planning, mutation and recovery.

Selected future extensions and their mandatory pre-start, per-slice, and
rung-closeout evidence gates are recorded, without reserved syntax or
implementation authority, in the
[Future Path Capability Ladder Supplement](0.252-future-path-capability-ladder-supplement.md).
The supplement does not add to the 0.252 landing ledger or change Direction B.

## 6. Accepted Normative Contract

### 6.1 Product Identity

IcyDB is relational with exact typed values. Composite storage does not make a
row a general document, and the existence of dotted SQL does not promise
document-database mutation or indexing.

### 6.2 Path Admission

Accepted schema owns one classification for every rooted path:

1. direct root field;
2. scalar member path through required/optional named records; or
3. unsupported member traversal, including positional tuple, newtype-wrapper,
   repeated collection and map traversal.

Parser and fluent/generated construction remain schema-agnostic syntax owners.
Logical validation and index DDL consume the accepted classification, then the
planner carries the resolved path contract to execution. No layer independently
infers traversability from runtime `Value` shape.

An unsupported repeated path fails during schema/query validation with an
`Unsupported` diagnostic. It must not enter a scan fallback, because no result
semantics have been chosen for it.

### 6.3 Query And Index Boundary

One accepted scalar member path has exactly the projection, filtering,
ordering, `DISTINCT`, aggregate-expression, `HAVING`, scalar-expression,
prepared-plan and index cells in Section 4.2. `GROUP BY`, raw-path `HAVING` and
public SQL placeholder preparation remain unsupported. Every supported cell is
still conditional on the terminal kind and the ordinary clause contract.
Existing missing/null, coercion, ordering, admission and cursor contracts
remain unchanged.

A repeated member path is not a query term. In particular, the accepted pre-1.0
direction does not add:

- existential or universal collection predicates;
- row expansion or duplicate owning-row results;
- multikey index entries;
- collection-member grouping or ordering;
- nested joins, relations or uniqueness; or
- cursor boundaries over expanded elements.

Only the top-level list/set predicates enumerated in Section 4.3 remain
unchanged. They do not establish member-path traversal or index fan-out.

### 6.4 Mutation And Concurrency Boundary

The maintained nested write is whole-field mutation. Accepted write admission
validates the complete final row image and all applicable durable rules before
commit preparation.

There is no member patch, positional element patch, predicate-selected patch or
nested compare-and-swap. Applications needing those behaviors read a bounded
aggregate, validate and simulate the change, then replace the complete field
under their row-level revision and atomic-batch protocol.

This design does not add a database-owned application revision. The existing
application-owned row revision protocol and IcyDB atomic mutation-batch
authority remain the only conflict and commit boundaries.

### 6.5 Bounds And Aggregate Ownership

Every repeated value is physically bounded by the existing row, request and
fallible decode limits. Those operational ceilings are not schema-visible
application capacities.

Nominal named collection types are the accepted owner of durable collection
length rules. The shorter anonymous `value(many, ...)` spelling remains a
convenience for values whose product capacity is either intentionally
application-owned or adequately covered by the general row/request ceiling.

IcyDB does not add a second inline `max_items` spelling. A durable application
capacity uses one named collection type; anonymous `value(many, ...)` retains
only the existing general row/request bounds.

An application with a fixed safety capacity should use a named collection with
`length_range_inclusive`. A smaller dynamic capacity may remain an
application rule beneath that durable maximum.

Maintained source pattern:

```rust
use icydb_model::prelude::*;

#[record(fields(
    field(name = "slot", value(item(prim = "Nat16"))),
    field(name = "quantity", value(item(prim = "Nat64")))
))]
pub struct InventoryStack {}

#[list(
    item(is = "InventoryStack"),
    ty(rule(
        name = "capacity",
        length_range_inclusive(min = 0, max = 51)
    ))
)]
pub struct InventoryStacks {}
```

The accepted named-list rule is the durable database safety ceiling. A lower
or state-dependent capacity, slot uniqueness and cross-entity existence remain
application rules unless separately represented by an existing accepted
relational contract.

### 6.6 Generated And Structural Ergonomics

Generated record/list values duplicating accepted member names in
application-owned structural maps is a correctness smell at an atomic write
boundary. Removing that duplication is accepted only as a separate measured
candidate, and only through the existing accepted binding and typed input
conversion authority.

Any such adapter must:

- reuse `TypedInputValue` and accepted source bindings;
- produce one normal `InputValue`/write cell for the existing structural
  mutation pipeline;
- add no parallel encoder, runtime registry or schema fallback;
- retain accepted enum and exact-composite admission; and
- pass the established raw/code/function and reachable-entity Wasm gates in
  force when evaluated, including the gates retained by 0.251.

This is correctness work at an authoring boundary, not part of the nested query
contract. Wasm evidence may determine whether and how it lands. The candidate
must retain the closed 0.251 gates and must not introduce subpath mutation.

Landing Slice 3 retains `DbSession::bind_typed_input`: the session proves the
binding current, the binding resolves accepted source identities, and the
existing `TypedInputValue` implementation produces one normal `InputValue`.
No generated encoder family or binding-carrying mutation value was added. The
method-isolation probe measures only about 61 additional raw bytes per added
entity. The final representative generated record/list fixture measures 4,595
raw bytes per entity for the complete reachable adapter and retains the 8 KiB
gate.

Generated rooted-path ergonomics for single-valued records are deferred until
a demonstrated application requirement exists. Any future candidate is
separate from query semantics and must prove that it does not materially
restore generated or downstream monomorphization. Toko Miner does not currently
demonstrate a need for that API.

### 6.7 Modeling Guidance

The maintained guide should direct authors as follows:

| Need | Shape |
| --- | --- |
| One owner-local typed value, read and replaced with its row | Record/newtype/tuple field |
| Small bounded owner-local sequence, not independently queried | Named list with a durable maximum |
| Repeated child queried, indexed, related or mutated independently | Entity with an owner key/relation and accepted indexes |
| Opaque application payload with no member-level database contract | Bounded blob, with application-owned encoding and version policy |

Do not maintain both an aggregate and shadow child entities solely to recover
queryability. Choose one authoritative model.

## 7. No-Build And State-Space Assessment

### Demonstrated need

Toko Miner needed a safe model for 24-cell Core and 21–51-cell Rocket
inventories. Typed repeated records plus whole replacement work. Direction B
resolves the upstream capability ambiguity; awkward structural input remains a
separate candidate, not evidence for a missing list query.

### Smallest outcome

Publish the single-versus-many contract and modeling matrix. Improve authoring
or generated input only where the existing authority can be reused.

### Simpler alternatives

- Per-cell entities are available when independent query/index semantics are
  needed.
- Named lists already own durable maximum length.
- Whole-field structural mutation already owns atomic aggregate replacement.

### Canonical owners

- accepted schema: path and value capability;
- logical query validation: user-visible supported/unsupported operations;
- accepted write admission: complete field and row admission;
- generated binding: source-name and typed input ergonomics; and
- application: domain-specific capacity below the durable database maximum.

### State-space delta

The accepted contract adds no runtime mode, planner route, index kind,
cursor format, mutation variant, persisted state or capability configuration.
It narrows the documented promise around existing behavior.

A generated input adapter would add one public authoring route that converges
before normal structural admission. It is acceptable only if it removes manual
shape duplication without retaining a second encoder or material Wasm growth.

### External Design And Platform Evidence

- [PostgreSQL composite types](https://www.postgresql.org/docs/current/rowtypes.html)
  and [JSON design guidance](https://www.postgresql.org/docs/current/datatype-json.html#JSON-DOC-DESIGN)
  support treating a value as one atomic datum when its parts are not naturally
  modified independently.
- [MongoDB embedding guidance](https://www.mongodb.com/docs/manual/data-modeling/embedding/)
  supports embedding bounded owner-local values read and updated with their
  owner, while retaining separate documents when children are naturally
  independent or commonly read alone.
- The [official IC resource limits](https://docs.internetcomputer.org/references/resource-limits/)
  cap a canister Wasm code section at 12 MiB and reject modules with more than
  50,000 declared functions. Those limits reinforce the requirement to avoid
  speculative planner, cursor, mutation and multikey machinery in both IcyDB
  and downstream Toko actors.

## 8. Compatibility And Format Impact

Accepting the narrow contract alone changes no:

- Candid method or payload;
- public recursive value representation;
- proposal or accepted-schema encoding;
- persisted row, index, relation, marker, journal or cursor format;
- query result or missing/null semantics; or
- atomicity, recovery or replay contract.

Before 1.0, any diagnostic or authoring correction is a hard cut to the current
version-1 form. No legacy nested spelling, predecessor path interpretation,
dual decoder or compatibility fallback is added.

## 11. ICYDB-018 Audit Corrections

The accepted contract incorporates all five downstream closeout corrections
and the final exactness audit:

1. Sections 4.1 and 4.4 publish exact record, tuple, newtype, optional, list,
   set and map capability boundaries rather than treating every
   “single-valued composite” as query-path equivalent.
2. Section 4.5 records optional null-versus-missing behavior, nullable index
   membership and the existing omission limit on nested unique indexes.
3. Section 6.5 gives a maintained named-list
   `length_range_inclusive` authoring pattern and distinguishes the durable
   maximum from dynamic application rules.
4. Section 4.6 requires one accepted classification and typed rejection
   vocabulary across SQL, generated fluent, dynamic, DDL, `EXPLAIN` and
   structural mutation surfaces, with no scan fallback; Landing Slice 2 routes
   the structural diagnostic-classification defect through the existing
   `RuntimeUnsupported` boundary.
5. Section 6.6 treats the generated structural-input adapter as correctness
   work but isolates it as a measured candidate converging into the existing
   `TypedInputValue`/accepted-binding/write-admission path.

The final `v0.250.1` behavior audit additionally:

- enumerates every requested scalar-path query/index cell in Section 4.2,
  including the direct-field-only `GROUP BY` rejection and aggregate-only
  `HAVING` admission;
- names every maintained whole-list and whole-set predicate, with an accepted
  authoring example for each, in Section 4.3;
- completes root-null, missing/null ordering, `DISTINCT`, grouping and
  omission-index semantics in Section 4.5;
- gives opaque JSON/blob payloads an explicit shape-matrix row with no member
  paths, member indexes or database-owned JSON encoding; and
- distinguishes universal physical row/request/decode bounds from the durable
  item-count bound that only a named collection may own.

The active 0.252 line authorizes the bounded delivery plan above. It does not
authorize multikey indexes, repeated-member predicates, expansion semantics,
new cursor rules, positional or keyed element updates, nested relations or
uniqueness, partial mutation, capability tiers, rooted generated-query-path
ergonomics. The completed generated structural-input adapter changes only
whole-field input authoring and does not authorize any excluded path feature.
