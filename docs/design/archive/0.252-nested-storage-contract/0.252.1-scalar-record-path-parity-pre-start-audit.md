# IcyDB 0.252.1 Scalar Record-Path Parity Pre-Start Audit

Status: COMPLETE — ELIGIBLE FOR A SEPARATE DESIGN; NO IMPLEMENTATION AUTHORITY

Date: 2026-09-01

Candidate target: `0.252.1`

Immutable predecessor: annotated tag `v0.252.0`

Parent contract: [0.252 Nested Storage Contract](0.252-design.md)

Evidence contract:
[Future Path Capability Ladder Supplement](0.252-future-path-capability-ladder-supplement.md)

## 1. Verdict

The first ladder rung, complete scalar record-path parity, is **eligible for a
separate design**. This verdict does not authorize production implementation.

The narrow candidate is scalar record-path grouping, chiefly
`GROUP BY profile.rank`, plus raw-path `HAVING` only when that exact accepted
path is already a grouped key. It does not include repeated traversal,
subpath mutation, multikey indexes, row expansion, joins, a document mode, a
capability tier, or any persisted/catalog/public format change.

The implementation must not be treated as a parser-only admission. Direct
grouping identity is represented by `FieldSlot` throughout planning,
fingerprinting, prepared residents, ordered/hash execution, grouped projection,
`HAVING`, `EXPLAIN`, and cursor validation. A repository scan finds the current
group-field family in 49 Rust files, including tests. The smallest semantic
owner is therefore one accepted-schema-bound **group-key source** consumed by
the existing grouped execution flow.

Eligibility rests on four facts:

- accepted schema already classifies every permitted scalar record path;
- the scalar expression compiler already resolves an accepted root slot and a
  bounded compiled path, and its evaluator can borrow the terminal value;
- grouped cursors already persist materialized key values rather than runtime
  row references; and
- no persistence, recovery, mutation, generated entity, Candid, or endpoint
  representation needs to change.

The strongest remaining risks are the broad direct-slot assumption, path-aware
ordered-index completeness, and protecting the borrowed direct-key hot path.
Those risks require a separate design and measured landing slices rather than
one broad implementation diff.

## 2. Demonstrated Need And No-Build Alternative

The maintained 0.252 contract exposes one ordinary-scalar exception: accepted
record paths work in projection, filtering, ordering, `DISTINCT`, aggregate
inputs, scalar expressions, aggregate-owned `HAVING`, prepared plans, and
eligible indexes, but not as grouping keys. The maintainer explicitly requested
the 0.252.1 addendum after publishing 0.252.0. The benefit is semantic and
authoring parity: an application should not need a duplicate root scalar solely
to group a value that IcyDB already admits everywhere else as a single-valued
scalar source.

No current Toko Miner query demonstrates that need. Its accepted Direction B
model keeps embedded collections owner-local and performs no nested database
query. The simplest no-build alternative therefore remains valid:

- keep nested grouping unsupported;
- copy a frequently grouped scalar to an authoritative direct field; or
- model independently queried children as entities.

Deferral costs one explicit capability exception and can require denormalizing a
single-valued record member. It does not block Toko Miner and creates no data
correctness defect. The separate design may therefore still choose no-build if
the candidate exceeds any predeclared gate below.

## 4. Exact Current Capability Matrix

All accepted cells remain conditional on the scalar terminal kind and ordinary
clause rules.

| Scalar record-path cell | 0.252.0 | Candidate parity contract |
| --- | --- | --- |
| Projection | Accepted | Unchanged |
| Filtering | Accepted | Unchanged |
| Ordering | Accepted when orderable | Unchanged |
| Projection `DISTINCT` | Accepted | Unchanged |
| Aggregate input | Accepted where the aggregate admits the kind | Unchanged |
| Aggregate `DISTINCT` | Accepted | Unchanged |
| `CASE`, arithmetic, scalar functions | Accepted recursively | Unchanged |
| Aggregate-owned `HAVING` | Accepted | Unchanged |
| Internal prepared/cache execution | Accepted | Unchanged |
| Eligible single/composite path indexes | Accepted | Unchanged |
| `GROUP BY profile.rank` | Rejected before planning | Admit as one zero-or-one-valued scalar key |
| Raw `HAVING profile.rank ...` | Rejected | Admit only when the canonical path is a declared group key |
| Repeated/map member traversal | Rejected | Rejected |

Required and optional records use the existing scalar-path value contract. A
missing descendant and an explicit terminal `NULL` materialize as the same null
group key, so they collapse into one group. Filtering continues to distinguish
missing from explicit `NULL` under its existing predicate rules.

An omission-capable nested index is not automatically a complete grouped
source: it may omit both missing and null terminals. Ordered grouping may use
such an index only when the existing accepted access proof establishes that
omitted rows cannot contribute. Otherwise the planner must choose complete hash
grouping. No scan fallback may be disguised as an index-complete route.

## 5. Current Owners And Execution Flow

The parser currently stores `GROUP BY` as a `Vec<String>` produced by an
identifier-list parser. SQL normalization deliberately classifies grouping as a
string-only surface without nested semantics. SQL capability validation calls
top-level `SchemaInfo::sql_capabilities`, and query intent resolves each name to
one `FieldSlot`.

That `FieldSlot` then remains the group-key identity across:

1. grouped policy and projection validation;
2. semantic cache keys and fingerprints;
3. ordered-strategy and accepted-index order proofs;
4. prepared grouped runtime residents and retained-slot layout;
5. hash and ordered key read/hash/compare operations;
6. grouped projection and raw-key `HAVING` offsets;
7. `EXPLAIN` labels; and
8. grouped continuation validation and signature construction.

The canonical existing path authority is
`SchemaInfo::nested_sql_capabilities`. The reusable evaluation spine is
`compile_scalar_projection_expr_with_schema` into `CompiledExpr::FieldPath`,
which carries an accepted root slot and bounded path segments. A separate path
walker, callback, trait object, registry, or runtime shape guess would create a
second authority and is rejected.

The candidate design should bind a group key once into an internal shape
conceptually equivalent to:

```text
GroupKeySource
  Direct(FieldSlot)
  ScalarPath(AcceptedRootSlot, CompiledPath, CanonicalPathIdentity)
```

The exact type is intentionally left to the separate design. The important
boundary is one group-key source, with a direct branch that retains current
borrowed slot operations and a scalar-path branch that reuses the compiled path
reader. Runtime execution must not inspect schema shape or split into a second
grouped executor.

## 8. Direct Grouping Runtime Baseline

The focused `sql_perf` integration control installs 2,048 rows and executes one
accepted direct-field ordered group and one complete hash group. It passed with:

| Route | Instructions | Rows scanned | Peak live groups | Peak estimated bytes |
| --- | ---: | ---: | ---: | ---: |
| Ordered indexed `group_key`, first 10 groups | 61,472,675 | 1,329 | 1 | 496 |
| Complete hash `label`, 3 groups | 69,659,195 | 2,048 | 3 | 5,740 |

The ordered query proves its accepted index and returns only closed groups with
a continuation. The hash query proves finite planner-owned group/byte limits,
complete scan work, and no continuation. The existing rejection of unbounded
aggregate-driven Top-K grouping also remains closed.

This is a deterministic single-run entry baseline, not a post-candidate noise
band. The separate design must freeze three identical-baseline repetitions and
add distinct cold-plan and prepared-plan measurements before changing runtime
behavior. The candidate must also cover one group, many groups, maximum
supported groups, required/optional/missing/null paths, eligible index and scan
routes, positive and negative predicates, and bounded pagination.

Persistence, journal, stable-write, index-write, recovery, and rebuild cost are
not applicable: a read-only scalar grouping feature must create exactly zero of
that work. The unaffected write control must retain its exact existing physical
work and remain within the instruction noise gate selected by the separate
design.

## 9. Prospective Gates

These are rejection ceilings, not size targets or permission to spend the full
amount.

### Whole rung

- `default_empty`: byte-identical raw/code/data, function, indirect, export,
  and Candid evidence;
- SQL-off one-to-ten reachable pair: no raw/code or nine-entity-slope growth;
- frozen SQL-off Toko: no raw/code, function, indirect, export, or Candid growth;
- `one_entity_sql_query`: no more than 32 KiB cumulative final raw growth and
  no more than 32 KiB code growth;
- `sql_perf`: no more than 32 KiB cumulative final raw growth, no more than
  32 KiB code growth, no more than 4 KiB data growth, and no more than 64
  defined functions;
- all actors: zero new `call_indirect`, exported methods, or Candid bytes;
- generated scale: zero per-entity, per-record-type, and per-binding growth;
  and
- every additional nested grouping use after the first: no generated helper or
  per-entity function family.

### Runtime and resources

- current direct ordered/hash routes: exact rows, groups, cursor, and physical
  work, with no more than 1% median instruction regression over three runs;
- nested versus equivalent direct key after prepared-plan reuse: no more than
  15% ordered-route and 20% hash-route instruction overhead;
- cold planning: no more than 20% overhead versus the equivalent direct query;
- path work: at most one bounded traversal per accepted segment per examined
  row, with no repeated-element work;
- retained group state: no per-row retained allocation; only a newly admitted
  group may own its materialized key, under the existing group/byte limits;
- ordered grouping: one live group and early-stop behavior remain available
  only where accepted index completeness is proven;
- optional/missing/null: exact result parity with a denormalized direct scalar,
  including one collapsed null group; and
- unaffected query and write controls: exact physical work and no more than 1%
  median instruction regression.

Any exceeded gate stops the candidate. The response is to remove, narrow, or
return the tradeoff to the maintainer, not to weaken a threshold after seeing
the result.

## 10. Forecast And Candidate Decomposition

This audit does not assign implementation landing slices. It forecasts the
smallest reviewable decomposition for the separate design required by the
supplement:

| Candidate handoff | Outcome | Forecast | Stop gate |
| --- | --- | --- | --- |
| Design | Freeze exact semantics, owners, workloads, Toko source, and per-slice gates | 2–4 documentation/fixture-definition files; no Wasm | Any unresolved null/index/cursor authority |
| Internal group-key authority | Replace direct-slot identity with one source while retaining direct-only admission and behavior | roughly 20–30 production/test files; 600–1,000 changed lines; enabling cost only | more than 12 KiB raw/code, any indirect call, or >1% direct regression |
| Scalar-path admission | Bind/evaluate accepted paths end-to-end in SQL and structural grouping, including raw-key `HAVING`, ordered completeness, cursor, explain, and diagnostics | roughly 15–25 production/test/docs files; 500–900 changed lines | 32 KiB cumulative raw/code ceiling or any semantic/resource gate failure |
| Cumulative closeout | Rebuild all exact actors and downstream controls and update maintained contract/status/changelog | tests/docs/receipts only unless a measured correction is required | any cumulative gate or incomplete matrix |

The estimates overlap because group-key identity is cross-cutting; file count is
a review signal, not a work limit. The separate design must not combine the two
implementation outcomes into one multi-hour handoff. The internal-authority
handoff is explicitly an enabling-cost slice with zero user-visible benefit and
must stand on its own measured receipt.

The forecast is moderately more complex: one internal source variant and one
branch enter the existing grouping flow, while no new mode, executor, registry,
feature combination, public/generated/persisted shape, or semantic authority is
added. Reusing accepted path metadata and the compiled scalar reader prevents
the larger state-space increase of a parallel nested-group engine.

## 11. Rejected Alternatives

- **Parser-only dotted-name admission:** rejected because planning and runtime
  still assume direct slots and SQL qualification must distinguish
  `Entity.field` from `record.member` through accepted scope.
- **Compile every group key as a generic scalar expression:** rejected as the
  default shape because it would tax direct borrowed grouping and would admit a
  wider expression surface than the requested scalar path.
- **Second nested grouping executor:** rejected because it duplicates hash,
  ordered, cursor, limit, resource, and diagnostics semantics.
- **Runtime schema/value walking:** rejected because accepted schema and the
  compiled path are already the authorities.
- **Trait objects, callbacks, function-pointer tables, or a runtime registry:**
  rejected because they add indirect machinery without semantic benefit.
- **Automatic use of omission-capable path indexes:** rejected unless the
  access proof establishes result completeness.
- **Generated path-specific grouping code:** rejected because it would restore
  downstream monomorphization and per-entity growth.
- **Compatibility alias or fallback:** rejected under the pre-1.0 hard-cut
  contract. The candidate changes only current version-1 internal shape if a
  representation change proves necessary.

## 12. Gate-1 Closeout

The immutable IcyDB source/toolchain and controlled raw-Wasm actors are frozen;
the current capability gaps and cross-cutting direct-slot ownership are mapped;
direct ordered/hash runtime controls are numeric; Toko's SQL-off reachability
and lack of demonstrated downstream need are explicit; whole-rung and
prospective per-handoff stop gates are declared; and the no-build alternative
remains acceptable.

The rung may now seek a separate 0.252.1 design and explicit implementation
authorization. No parser, planner, executor, cursor, public API, test fixture,
changelog, or runtime code changed in this audit.
