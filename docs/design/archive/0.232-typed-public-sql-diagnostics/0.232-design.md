# IcyDB 0.232 Typed Public SQL Diagnostics

Status: approved; both planned patches implemented; focused closeout passed

Design cut: 2026-08-19

## Decision Summary

0.232 adds one narrow exception to the compact numeric diagnostic contract:
an error caused by a rejected query field reference may carry one optional,
bounded, typed `query_field` context containing the exact post-normalization
field reference presented to the resolver and its semantic role.

The intended public shape is:

```text
Error {
    code: u16,
    class: u8,
    origin: u8,
    facts: Vec<DiagnosticFact>,
    query_field: Option<QueryFieldDiagnostic>,
}

QueryFieldDiagnostic {
    role: u8,
    field: String,
}
```

`role` is interpreted through one production-safe `QueryFieldRole` registry:

```text
Predicate | Projection | GroupBy | Having | OrderBy | AggregateTarget
```

The leaf E-code remains the error reason. Existing numeric facts remain the
only owner of positions such as `TermIndex`, `ProjectionIndex`, `GroupIndex`,
`ClauseIndex`, and `AggregateIndex`. The new record supplies only the rejected
field and its role; it does not duplicate those positions or create a second
error taxonomy.

The field is retained exactly only when its UTF-8 encoding is at most 256
bytes. It is never truncated. An oversized, unavailable, ambiguous, or
invalid context is omitted and the existing E-code plus numeric facts remain
authoritative.

0.232 does not add arbitrary string facts, rendered messages, SQL excerpts,
schema suggestions, accepted-schema names, a diagnostic mode, persisted
state, or a second parser/planner/CLI error model. It changes only failed-query
diagnostic projection. SQL is the motivating public surface, but the canonical
planner context also reaches dynamic/fluent/generated query APIs that return
the same `icydb::Error`. Successful result rendering, including enum-path
shortening, is outside this line.

## Promotion Findings

The current implementation proves a maintained gap and also narrows the
solution:

- `validate_order_term` in
  `crates/icydb-core/src/db/query/plan/validate/order.rs` sees the rejected
  direct field, but constructs `OrderPlanError::UnknownField` with only the
  term index.
- `ExprPlanError::{UnknownField, UnknownExprField}` and several
  `GroupPlanError` variants in
  `crates/icydb-core/src/db/query/plan/validate/errors.rs` retain a `String`,
  but `diagnostic_facts` deliberately discards it.
- `SqlLoweringError::UnknownField` in
  `crates/icydb-core/src/db/sql/lowering/mod.rs` retains a field, but has no
  clause/role identity and is reduced through `QueryError` to E3.
- `QueryError::diagnostic_facts` in
  `crates/icydb-core/src/db/query/intent/errors/mod.rs` carries only numeric
  facts to the facade.
- `icydb::Error` in `crates/icydb/src/error.rs` contains only code, class,
  origin, and numeric facts.
- `render_error` in `crates/icydb-cli/src/diagnostic.rs` can therefore render
  only `E_QUERY_PLAN: query planning failed` plus numeric positions.
- The SQL parser does not resolve schema fields. It is not an unknown-field
  diagnostic owner and gains no parallel context path.

The reproduced production query ordered `PokemonCardMetadata` by `hp DESC, id
DESC`; the accepted field is `pokemon_card_id`. The planner knew both the
failing second term and `id`, while the public result retained only E3 and the
term position. Numeric positions alone are insufficient because operators
must inspect or guess the authored query to discover the rejected identity.

The audit also disproves the need to combine successful enum rendering with
this work. Enum shortening changes successful result presentation and has a
different owner, test matrix, and compatibility surface. It is deferred rather
than hidden inside a diagnostic slice.

## No-Build Gate

### Demonstrated need

The reference failure is actionable, deterministic, and already known at the
canonical semantic owner. Losing it forces operators to reparse the query or
inspect accepted schema despite the rejected name having originated in their
own request.

### Smallest sufficient outcome

Extend the existing owner-carried error flow with exactly one optional bounded
field-reference record. Reuse the E-code, numeric fact schema, planner error
taxonomy, public `Error`, generated endpoint result, and shared CLI renderer.

### Simpler alternatives

- **Keep only `TermIndex`:** insufficient when a generated query, log, or
  client abstraction hides the original term.
- **Render internal error text into Candid:** rejected because strings and
  formatting would become authority and clients would have to parse prose.
- **Add a numeric field ID:** impossible for an unknown field and unsafe to
  infer from a similar accepted name.
- **Return the whole SQL input or source span:** unnecessary and much less
  bounded; it can expose literals and unrelated request data.
- **Add schema-name suggestions:** requires accepted-schema search, ranking,
  privacy policy, and a second correctness surface.
- **Add string-valued diagnostic facts:** turns the globally numeric fact
  registry into an open payload channel and weakens every error family's
  privacy contract.
- **No build:** preserves a demonstrated operational defect for ordinary
  mistyped SQL. The bounded owner-carried record is proportionate to the gap.

## Goals

- Preserve the exact post-normalization rejected field identity and semantic
  role for every maintained field-reference failure listed below.
- Keep E-codes and numeric facts authoritative for reason, classification, and
  position.
- Bound user-controlled text before public construction and never truncate it.
- Use one internal context type, one schema validator, one facade field, and
  one shared CLI rendering path.
- Keep successful query planning, execution, and result rendering free of new
  diagnostic allocation.
- Make malformed or mismatched public context unavailable rather than trusted
  or guessed.
- Measure the public ABI, raw Wasm, error-path instructions, successful-query
  overhead, and complexity delta.

## Non-Goals

- No new E-code or changed error class/origin.
- No parser spans, raw SQL, literals, values, rows, keys, principals, schema
  candidates, or accepted-name suggestions.
- No arbitrary diagnostic message, string-fact vector, localization system,
  or production prose table.
- No change to query semantics, planner eligibility, execution, caching,
  cursor identity, authorization, mutation, or SQL DDL.
- No human shortening of successful enum or other output values.
- No new endpoint, method mode, setting, feature flag, public diagnostic mode,
  scheduler, timer, stable allocation, persisted flag, or format version.
- No compatibility decoder, alias, legacy field, or dual Candid error shape.
- No generic typed refactor of unrelated internal errors.

## Canonical Authority And Flow

```text
query field resolver at the failing clause/role
    -> existing typed planner/lowering/validation error
       + optional bounded QueryFieldContext
    -> QueryError (same E-code and numeric facts)
    -> icydb::Error.query_field
    -> generated Candid Result error
    -> shared CLI validator and renderer
```

| Concern | Canonical owner |
| --- | --- |
| Whether a field reference is valid | Existing accepted-schema-backed resolver at the clause validator |
| Rejected field identity | The post-normalization resolver input at the failure point |
| Field semantic role | The enclosing clause/lowering/planner validator |
| Error reason and classification | Existing E-code and `Diagnostic` registry |
| Numeric position | Existing per-code numeric fact schema |
| Field-context bound and role registry | `icydb-diagnostic-code` production-safe contract |
| Candid projection | `icydb::Error` facade |
| Human prose and escaping | Shared host/CLI renderer |

No consumer reparses SQL, matches an error string, consults generated models,
or searches accepted schema to reconstruct the context.

## Exact Context Contract

### Exact post-normalization identity

`field` is exact with respect to the semantic resolver input, not the original
SQL source spelling. It is the complete normalized field or field path passed
to the accepted-schema-backed resolver that rejects it. It is not:

- the whole SQL token slice;
- a rendered Rust error;
- an accepted field selected by similarity;
- a generated model name reconstructed later;
- an expression label when no singular field reference exists; or
- necessarily the exact characters authored before SQL normalization.

The current exact cases are:

| Input form | Public `field` on rejection |
| --- | --- |
| Bare SQL identifier | The parser-preserved identifier presented to the resolver; 0.232 adds no case folding |
| Quoted SQL identifier | No context: the maintained reduced parser rejects quoted identifiers as `UnsupportedFeature` before field resolution |
| Matching entity/table-qualified identifier | The local field or nested path after the existing longest matching scope qualifier is removed |
| Nonmatching qualified identifier | The unresolved canonical dotted reference that reaches the resolver |
| Nested field | The complete canonical dotted `root.segment...` path after scope normalization |
| Resolved ORDER BY or HAVING projection alias | The underlying normalized field reference selected by existing alias resolution, not the authored alias token |
| Unresolved alias-like token | The token as presented to the field resolver |
| Fluent/dynamic/generated structural field | The identifier or dotted path stored in the structural query and presented to the same resolver; there is no SQL spelling to preserve |

ORDER BY and HAVING alias resolution remains case-insensitive and uses the
existing first matching projection alias. If an alias collides with a field or
another alias, existing normalization precedence decides which expression
reaches the resolver. 0.232 neither diagnoses that collision nor preserves the
pre-rewrite alias as a second identity. Tests freeze that the diagnostic always
reports the resolver input selected by current normalization.

### Semantic role

The exact version-1 role registry is:

| Raw | Role | Meaning |
| ---: | --- | --- |
| 1 | `Predicate` | WHERE, filter, or predicate validation |
| 2 | `Projection` | selected scalar/grouped projection input |
| 3 | `GroupBy` | GROUP BY declaration |
| 4 | `Having` | HAVING field reference |
| 5 | `OrderBy` | ORDER BY direct field or expression input |
| 6 | `AggregateTarget` | aggregate target or aggregate input expression |

The registry is not a release counter and has no predecessor decoder. Unknown
raw roles fail context validation. A later role requires an explicit current
contract change; callers cannot supply their own role number.

### Bound

`MAX_PUBLIC_QUERY_FIELD_BYTES` is exactly 256 UTF-8 bytes.

This is twice the maintained 128-byte schema/source-name bound, so it covers a
normal qualified or shallow nested reference while remaining tiny relative to
the approximately 2 MiB admitted SQL input. It does not attempt to mirror the
maximum possible SQL token or a deeply authored invalid path.

The constructor accepts a non-empty string of at most 256 bytes. At 256 bytes
the value is preserved exactly. At 257 bytes it is unavailable. It does not
truncate, add an ellipsis, replace invalid context with an accepted name, or
split a UTF-8 code point. The error itself and all numeric facts remain
unchanged when context is unavailable.

Only one `QueryFieldDiagnostic` may exist on one error. There is no vector and
therefore no caller-controlled context count.

### Internal producer matrix

The maintained producer set is closed to the following existing failures:

| Existing owner/failure | Role | Existing numeric position retained |
| --- | --- | --- |
| `ValidateError::UnknownField` under planner predicate validation | `Predicate` | none |
| `SqlLoweringError::UnknownField` from projection admission | `Projection` | none |
| `SqlLoweringError::UnknownField` from GROUP BY admission | `GroupBy` | none |
| `SqlLoweringError::UnknownField` from aggregate input | `AggregateTarget` | none |
| outward `SqlLoweringError::UnknownField` from aggregate FILTER/predicate admission | `Predicate` | none |
| `OrderPlanError::UnknownField` | `OrderBy` | `TermIndex` |
| `ExprPlanError::UnknownExprField` caught at ORDER BY validation | `OrderBy` | none |
| `ExprPlanError::UnknownExprField` caught at projection validation | `Projection` | none |
| `GroupPlanError::UnknownGroupField` | `GroupBy` | `GroupIndex` when owned |
| `GroupPlanError::HavingNonGroupFieldReference` | `Having` | `ClauseIndex` |
| `GroupPlanError::UnknownAggregateTargetField` | `AggregateTarget` | `AggregateIndex` |

Existing structural-invariant paths remain invariants. A context is not added
where the current layer cannot prove both a singular rejected field and its
role. Duplicate fields, unsupported operators, type mismatches, missing
tie-breakers, and non-field expression failures keep their existing code and
facts without `query_field`.

0.232 does not opportunistically add numeric position facts to failures that
are currently fact-free. An aggregate FILTER duplicate-validation path that
currently classifies an impossible unknown field as an invariant remains an
invariant; only an outward user-field failure receives context.

Shared expression inference may identify the rejected field, but the enclosing
clause validator owns the role. It attaches that role while propagating the
existing error; expression inference does not guess its caller.

This matrix is an internal constructor and test invariant. Producer identity
does not cross `QueryError`, is not encoded in `QueryFieldDiagnostic`, and is
not reconstructed by the facade or client. After projection, public validation
can prove only the `(ErrorCode, QueryFieldRole)` allowlist and the field bound.

## API Boundary

The context applies to every maintained public query API that returns the
shared `icydb::Error` from the same canonical query validation/planning flow:

- trusted/generated SQL query, explain, and SQL mutation-selection planning;
- public and trusted dynamic live/grouped query execution; and
- typed/generated fluent query adapters whose database failure is
  `TypedQueryError::Database(icydb::Error)`.

SQL-lowering-only failures naturally occur only for SQL callers. Planner-owned
predicate, projection, grouping, aggregate, and ORDER BY failures can surface
for SQL or structural/fluent callers, and carry the same role and
post-normalization resolver field. The facade does not suppress otherwise
valid context based on frontend provenance; doing so would add a second query
error path and make equivalent planner failures diverge.

The context does not apply to schema DDL, mutation validation unrelated to a
query selector, row decoding, generated binding/adapter errors, or any error
that does not pass through the shared `QueryError` boundary. The 0.232 title
retains the production SQL incident that motivated the slice; it is not a
promise of SQL-only internal semantics.

## Internal Ownership

`icydb-diagnostic-code` gains only:

- the compact `QueryFieldRole` registry;
- `MAX_PUBLIC_QUERY_FIELD_BYTES`; and
- schema validation for `(ErrorCode, optional role, field byte length)`.

It remains free of Candid, CLI prose, schema lookup, and arbitrary strings as
authority. The existing numeric fact registry is unchanged.

Core owns one internal bounded `QueryFieldContext` and one fallible constructor
from `(QueryFieldRole, &str)`. That constructor is the sole byte-bound owner.
It returns `None` for empty or over-bound user input without changing the
underlying query error.

`PlanError` becomes the sole planner propagation carrier: its existing root
kind is paired with `Option<QueryFieldContext>`, all ordinary `From`
conversions default to `None`, and one private attachment adapter adds context
at a clause-owner boundary. The adapter extracts a field only from the closed
internal producer matrix. `ValidateError`, `ExprPlanError`, and
`GroupPlanError` do not gain role fields or a generalized context framework.
`OrderPlanError::UnknownField` is the one leaf correction required because it
currently discards the resolver field before the root adapter can attach it.

`SqlLoweringError::UnknownField` is the only pre-planner carrier. Its existing
constructor takes the role at the lowering resolver, and conversion into
`QueryError` transfers the same `QueryFieldContext` to the `PlanError` root.
No other SQL error gains diagnostic context.

The exact attachment points are:

| Attachment seam | Role |
| --- | --- |
| `validate_scalar_plan_semantic_gates` around `validate_predicate` | `Predicate` |
| `validate_order` around each direct or expression order term | `OrderBy` |
| `validate_projection_expr_types` around each projection expression | `Projection` |
| `resolve_group_field_slot_with_schema` and grouped declaration validation | `GroupBy` |
| grouped HAVING structure validation | `Having` |
| grouped/global aggregate target resolution | `AggregateTarget` |
| SQL projection capability and grouped projection resolver failures | `Projection` |
| SQL GROUP BY capability resolver failures | `GroupBy` |
| SQL aggregate input resolver failures | `AggregateTarget` |
| outward SQL WHERE/FILTER resolver failures | `Predicate` |

There is no attachment in `QueryError`, the facade, generated wiring, or the
CLI. Those layers only carry, validate, or render existing context.

`QueryError` exposes the already-owned optional context in parallel with
`diagnostic()` and `diagnostic_facts()`. Before serialization, the facade
validates the public E-code/role allowlist and the bound. An internally
constructed invalid combination becomes the maintained runtime invariant error
and the invalid query context is not serialized. Ordinary missing/oversized
context retains the original query error.

## Public Wire Contract

`icydb::Error` hard-cuts in place to the current version-1 shape with:

```rust
pub struct QueryFieldDiagnostic {
    role: u8,
    field: String,
}

pub struct Error {
    code: u16,
    class: u8,
    origin: u8,
    facts: Vec<DiagnosticFact>,
    query_field: Option<QueryFieldDiagnostic>,
}
```

Public accessors expose the raw role, its known typed interpretation, the
borrowed field, and one validated view. Fields remain private so production
constructors enforce the bound. A structured client still treats decoded raw
context as untrusted until the shared schema validator succeeds.

The complete public allowlist is:

| Error code | Allowed roles |
| --- | --- |
| `ErrorCode::QUERY_PLAN` | `Predicate`, `Projection`, `GroupBy`, `Having`, `OrderBy`, `AggregateTarget` |

`ErrorCode::QUERY_VALIDATE` and every other code remain context-free. A
`ValidateError::UnknownField` receives `Predicate` context only when the
planner semantic gate wraps it in `PlanError`; direct validation errors do not
gain a second attachment path.

No public validation step claims which internal producer created the record.
That proof ends at the internal constructor matrix. A valid public context
never changes code, class, origin, or facts. Every generated endpoint already
returns the shared `icydb::Error`; generated wiring does not implement another
projection.

This is the one documented Candid ABI change. Successful result records,
endpoint names, method modes, exports, and authorization remain unchanged. The
maintained current Candid foundation and downstream fixtures are replaced in
place. No old `Error` decoder or dual encoder remains before 1.0.

## Consumer And CLI Contract

The CLI first validates the existing numeric fact schema and the optional
query-field schema. On valid context it renders the stable E-code summary,
role, escaped field, and existing numeric positions. A representative result
is:

```text
E_QUERY_PLAN: query planning failed; order_by field `id`; term_index=1
```

The exact prose is host-owned and may evolve without becoming protocol
authority. Structured consumers read `query_field`; they never parse that
sentence.

Control characters, backticks, quotes, and terminal escape characters are
escaped into a single-line representation. The structured field remains exact.
An unknown role, invalid field bound, disallowed E-code/context combination,
or numeric-fact mismatch received from Candid causes the CLI to omit the
untrusted field and report a context mismatch alongside the generic
diagnostic. It never guesses a role or accepted field.

The existing `icydb diagnostic` numeric lookup remains valid without a field
context. No schema artifact is consulted to resolve an unknown field.

## Privacy And Trust Boundaries

The only admitted string is a field reference derived from the same caller's
failed query and returned in that query's error. A producer must omit context
if it has only an accepted-schema name, generated-model label, reconstructed
display string, or other identity that cannot be proven to be the rejected
query input. The canister does not log, persist, cache, broadcast, or suggest
from this value. Host rendering escapes it before terminal output.

This narrow caller-echo exception explicitly supersedes only 0.219's ban on
projecting query field names. Its ban on names in generic facts, SQL text,
values, keys, rows, principals, and arbitrary prose remains authoritative.

Server construction and client consumption are deliberately separate trust
boundaries:

1. **Server/internal:** the context constructor and public projection validate
   the field bound and explicit E-code/role allowlist before Candid encoding.
   A non-empty, within-bound field attached to a disallowed E-code/role pair is
   an internal contract defect and becomes the maintained runtime invariant
   error before serialization. It is not silently omitted as ordinary user
   input.
2. **Client/decoded Candid:** a client may receive malformed bytes from a
   nonconforming canister. The shared validator treats an unknown role,
   disallowed E-code/role pair, empty/over-bound field, or fact mismatch as
   untrusted optional context. The CLI retains the base E-code/facts, omits the
   field from normal rendering, and reports a context mismatch.

An oversized field encountered while constructing an ordinary user error is
not an invalid internal pair: bounded context construction returns `None` and
the original E-code/facts are serialized unchanged.

## Invariants

1. The E-code remains the sole error-reason and classification authority.
2. Numeric facts remain the sole position/count/bound authority and retain
   their exact per-code schemas.
3. One error carries at most one query-field context.
4. A context is created only by the resolver boundary that owns the rejected
   field; the facade and CLI never reconstruct it.
5. A role is attached only by the enclosing clause/semantic validator; shared
   expression inference never guesses it.
6. The field is exact, non-empty, valid UTF-8, and at most 256 bytes, or absent.
7. No accepted-name suggestion, whole SQL input, literal, value, row, key, or
   arbitrary prose enters the context.
8. Missing context never becomes an empty string, a numeric field ID, zero, or
   an inferred accepted field.
9. A server-side disallowed E-code/role construction becomes a maintained
   invariant error before serialization; malformed client-side context is
   omitted and reported as a context mismatch.
10. Successful planning and execution construct no query diagnostic context.
11. Equivalent planner failures use the same context across SQL and
    dynamic/fluent/generated query APIs that return `icydb::Error`.
12. All generated SQL endpoints consume the shared facade error; none has a
    private diagnostic route.
13. No persisted or configurable diagnostic mode is added.

## Persisted, Runtime, And Compatibility Impact

0.232 changes no accepted schema, row, index, journal, cursor, cache, stable
memory, cardinality generation, migration, or recovery representation. Stable
bytes and memory IDs must remain identical.

The public error record changes in place. Before 1.0, only the new current
version-1 Candid form is maintained. Generated clients and other structured
consumers must regenerate and rebuild against it; there is no legacy response
field, adapter, feature gate, or compatibility decoder. Canister data needs no
reinstall or migration because no persisted representation changes.

The new state-space axis is one optional error-only record with six closed
roles. It combines only with `ErrorCode::QUERY_PLAN`. The canonical schema
validator rejects every other E-code/role combination. No runtime or persisted
state combination is added.

## Validation Strategy

### Contract and owner tests

- Assert every known role's exact raw identity and reject zero/unknown roles.
- Assert empty, 256-byte, 257-byte, and multibyte UTF-8 field boundaries.
- Assert context is absent rather than truncated when over bound.
- Assert every producer in the exact matrix retains its field, role, and
  existing numeric position.
- Assert every non-field and invariant control carries no context.
- Assert shared expression inference is assigned the caller's role at ORDER BY
  and projection boundaries.
- Assert no producer can attach a query field to an unrelated E-code.
- Assert qualified, nonmatching-qualified, nested, resolved-alias,
  unresolved-alias, alias/field collision, and duplicate-alias cases expose
  exactly the post-normalization resolver identity.
- Assert matching SQL and structural/fluent planner failures produce the same
  role and field, while SQL-lowering-only failures remain SQL-only.

### Facade and Candid

- Round-trip the current `Error` and `QueryFieldDiagnostic` Candid shape.
- Verify a server-side invalid E-code/role combination becomes the maintained
  runtime invariant error before serialization.
- Verify malformed client-side raw role/context combinations preserve the base
  error while the validated context reports mismatch.
- Update all maintained ABI foundation and generated endpoint fixtures.
- Prove successful result types, method names, method modes, and exports are
  byte-for-byte or structurally unchanged except for the shared error record.
- Verify no audit-only endpoint enters production Candid or exports.

### CLI and integration

- Render every role with the exact escaped field and existing numeric facts.
- Include newline, control-character, backtick, quote, and terminal-escape
  inputs; output must remain one line and non-injectable.
- Force invalid-role, over-bound, wrong-E-code, and fact-schema mismatches; the
  renderer must not print untrusted field context.
- Reproduce `ORDER BY hp DESC, id DESC` against the reference-shaped accepted
  schema and assert E3, `OrderBy`, `id`, and term index 1 through a real
  generated canister response.
- Compare structured Candid decoding and CLI rendering so neither test can pass
  by matching only a hard-coded sentence.
- Cover SQL query, explain, prepared/cached compile, generated dispatch,
  dynamic query, and typed/fluent database-error routes that share the
  maintained error boundary.

### Negative-space guards

- No string-valued `DiagnosticFact` or generic text-fact registry exists.
- No raw SQL, schema suggestion, accepted-name lookup, or generated-model
  fallback enters production projection.
- No successful enum/output renderer changes in this line.
- No new public endpoint, mode, setting, feature, timer, persisted work flag,
  stable allocation, or format discriminator exists.
- Production code does not match rendered error strings.

Every implementation patch records:

- compiler-emitted Wasm, final raw Wasm, and deterministic gzip;
- Candid bytes and SHA-256;
- export count, endpoint names, and method modes;
- unknown-field failure instructions for the reference query;
- representative successful compile/execute instructions to detect hot-path
  overhead;
- stable-memory extent and stable-byte controls proving no format change; and

Raw non-gzipped Wasm remains authoritative. Existing instruction and Wasm

string retention/copy and no successful-path allocation; measurements must
confirm rather than assume that expectation.

## Rejected Alternatives

- A generic `DiagnosticText { tag, value }` vector: creates a second open fact
  schema and count bound.
- A public variant per E-code: duplicates the numeric E-code taxonomy.
- A public Candid variant for roles: Patch 1 must measure it against `nat8`, but
  raw `nat8` remains the selected contract even if byte savings are small. It
  follows the compact registry and, more importantly, lets a client decode the
  base error and isolate an unknown role as a context mismatch. A derived
  closed Candid variant can make an unknown tag fail the whole reply decode.
  Typed accessors and the shared validator provide downstream type safety
  without sacrificing that containment. The prototype is measurement evidence
  only; the implementation must not ship both forms.
- Storing source spans or original SQL: exposes much more caller data than the
  correction requires.
- Truncating long fields: can identify a different field and is therefore
  misleading.
