## Planning Status And Authorization

This line makes generated read authority separable from canister
controllership. It adds one application-supplied authorization choice to the
opt-in generated SQL and schema read surfaces while preserving their read-only
execution rules and existing controller/public forms.

The declaration structure is established precedent, not a new configuration
axis. IcyDB 0.224 already accepts `authorization = public | controller` on
`icydb_metrics`, `icydb_metrics_extended`, and `icydb_schema`. This line adds
the one current `guard(path)` value to the same field for SQL and schema read
surfaces. That narrow extension, not a policy framework, is the core change;
Patch 1 accepts it over a hand-written endpoint for the standard-name tooling
reason recorded below.

Patch 1 inventoried and measured maintained IcyDB surfaces without runtime
change. Patch 2 implemented the Rust-only guard contract, guarded SQL wrapper,
bounded allowlist and E281 after the user approved that baseline. Patch 3 adds
the guarded accepted-schema wrapper, E282 and exact scope/discovery guidance.
Their evidence is in the status tracker. Each later patch still requires review
of the preceding handoff and explicit user continuation; this document does
not authorize version or release work.

## Cross-Repository Independence

IcyDB 0.226 has no Canic, Explorer, reference application, fleet coordinator, authentication
framework, or desktop-tool dependency. None is a predecessor, release gate,
runtime dependency, canonical authority, or lifecycle owner for this line.

The framework/application fleet is retained as production incident evidence because it
made the controller-only failure concrete. It is not acceptance authority.
IcyDB closeout can be proved with a framework-neutral canister whose controller
is another canister and whose application guard authorizes a distinct human
principal.

This design does not specify or constrain any external token, proof,
`requested_scopes` field, session/receipt DTO, Candid method, capacity, expiry,
revocation, audit API, lifecycle macro, timer provider, or release. Canic may
independently improve its local application authorization so a consuming
application can write a small safe IcyDB guard. Explorer may independently
establish whatever authority that application requires. Those improvements are
downstream interoperability work, not IcyDB implementation or release gates.

## Production Evidence And Demonstrated Gap

The Explorer production report establishes two concrete failures in the
maintained controller-only SQL boundary:

1. a principal allowed to read generated SQL is necessarily able to exercise
   canister lifecycle authority outside IcyDB; and
2. when another canister is the controller, a human principal may have no way
   to call an otherwise-present generated SQL surface.

The reproduced application/framework 0.101.45 fleet contained six canisters exporting the
surface. Both available human identities received the SQL
controller-required diagnostic on every canister. The coordinator remained the
controller and exposed no external controller-bootstrap path.

The general requirement does not depend on how that fleet authenticates
people. An application must be able to replace controller authorization for an
opted-in read surface with its own local, fail-closed decision. IcyDB must not
add a competing reader registry or treat controller lists as application
policy.

## Decision Summary

IcyDB extends the existing authorization field for the two generated read
surfaces:

```rust
icydb::endpoints! {
    icydb_sql_query(
        introspection = true,
        authorization = guard(my_app::may_read_sql),
    );
    icydb_schema(authorization = guard(my_app::may_read_schema));
}
```

The existing SQL declaration without an authorization field remains exactly
controller-gated. Existing schema `public` and `controller` declarations
remain exact. A guarded declaration replaces controller authority for that
surface; it never means `controller OR guard`.

No controller escape hatch is needed. An application that deliberately wants
controllers included expresses that policy inside its guard, for example by
returning `Allow` when
`ic_cdk::api::is_controller(&context.caller)` is true. That is an explicit
application decision and does not create an IcyDB fallback authority.

The guarded SQL and schema endpoints retain their maintained public Candid
signatures. The exact Rust-only public contract is passed by value:

```rust
#[derive(Clone, Copy, Debug, Eq, PartialEq)]
pub enum ReadAuthorizationSurface {
    Sql,
    Schema,
}

#[derive(Clone, Copy, Debug, Eq, PartialEq)]
pub struct ReadAuthorizationContext {
    pub caller: candid::Principal,
    pub surface: ReadAuthorizationSurface,
}

#[derive(Clone, Copy, Debug, Eq, PartialEq)]
pub enum ReadAuthorizationDecision {
    Allow,
    Deny,
}

pub type ReadAuthorizationGuard =
    fn(ReadAuthorizationContext) -> ReadAuthorizationDecision;
```

`introspection_enabled` is deliberately absent. It is static declaration
configuration, not request context, and the guard cannot inspect the submitted
statement. `ReadAuthorizationSurface` remains useful when one function is
shared deliberately between SQL and schema declarations.

These types are exported from the `icydb` facade root. They do not derive
`CandidType`, `Serialize`, or `Deserialize` and do not become endpoint payload
types.

The declaration grammar inside `guard(...)` accepts exactly one standard Rust
macro `path` fragment, such as `my_app::may_read_sql` or
`MyPolicy::may_read_sql`. The captured value must then coerce to the exact safe
Rust `ReadAuthorizationGuard` function-pointer type. IcyDB does not parse,
normalize, qualify, or rewrite that path. Module and associated-function paths,
re-exports, named function-pointer constants, inferred generics, and explicit
turbofish are permitted when Rust resolves them to the exact type. Unsafe,
async, argument-by-reference, richer-result, and ABI-mismatched functions fail
coercion. Qualified-self paths, expressions, inline closures, blocks, literals,
calls, and multiple arguments fail the standard macro grammar.

Patch 1 froze the complete path-resolution matrix. Bare paths, ordinary module
paths, `crate::`, `self::`, resolvable leading `::` absolute paths,
raw-identifier segments, associated functions, named function-pointer
constants, re-exports, inferred generics, and explicit turbofish compiled.
`super::` is context-invalid at the required crate-root declaration site;
qualified-self, closure, block, literal, call, and multi-argument forms fail
grammar matching; unsafe, async, reference-argument, richer-result, and
ABI-mismatched functions fail exact coercion. These outcomes are compiler
authority, not a custom IcyDB path language.

The IC/CDK Candid boundary necessarily decodes the existing SQL `text` argument
before the Rust wrapper begins. The wrapper then rejects anonymous callers.
After successful Candid decoding, every non-anonymous guarded invocation calls
the declared synchronous guard exactly once before creating an IcyDB request
root, database session, readiness observer, SQL parser, schema observer, or
request executor. `Allow` continues into the existing wrapper. `Deny` maps to
the fixed surface-specific policy diagnostic. Decode failure never reaches the
wrapper or guard.

`Allow` establishes authorization only. It does not assert database readiness
or suppress normal IcyDB admission: the existing 0.225 check may still return
its typed startup-not-ready, recovering, or terminal-failure result after an
allowed guard. The guard never observes, translates, or drives that state.

The guard receives no SQL text, parsed statement, entity, field, row value,
continuation, token, proof, or mutable database handle. This line authorizes a
whole declared read surface, not row-level or statement-sensitive policy.

## SQL Introspection And Schema Scope

The SQL and schema guards protect distinct exported methods, not statement
classes within `icydb_query`:

- the SQL guard protects every statement admitted by `icydb_query`;
- when SQL introspection is enabled, that includes `SHOW`, `DESCRIBE`, and
  `EXPLAIN` as well as admitted `SELECT`;
- the schema guard protects only the dedicated `icydb_schema` method; and
- exporting `icydb_schema` does not replace SQL introspection for clients that
  issue those statements through `icydb_query`.

Explorer currently sends `SELECT`, `SHOW`, `DESCRIBE`, and `EXPLAIN` through
`icydb_query`. A compatible deployment therefore enables SQL introspection and
accepts that one SQL guard authorizes the complete admitted SQL read lane. An
application may separately guard `icydb_schema` for clients that use that
method, but the design does not claim this separates Explorer row reads from
Explorer introspection. Per-statement or within-SQL scope separation remains an
explicit non-goal.

## Maintained Allowlist Helper

The common static-reader case must not require applications to reimplement
principal matching. IcyDB owns one maintained helper:

```rust
pub const MAX_READ_AUTHORIZATION_ALLOWLIST_PRINCIPALS: usize = 64;

pub fn allowlist(
    context: ReadAuthorizationContext,
    readers: &[candid::Principal],
) -> ReadAuthorizationDecision;
```

It is exported as `icydb::guards::allowlist`. It performs no allocation,
logging, mutation, IcyDB entry, timer work, or call. It denies anonymous,
denies when `readers.len()` exceeds the fixed maximum, and otherwise performs
one bounded exact-principal scan. Empty, missing, and over-capacity lists deny;
duplicates are harmless and do not change authority.

A helper cannot capture a reader slice and return the frozen plain function
pointer. The smallest compatible application adapter is therefore one line:

```rust
fn may_read_sql(context: icydb::ReadAuthorizationContext)
    -> icydb::ReadAuthorizationDecision
{
    icydb::guards::allowlist(context, SQL_READERS)
}
```

This retains one guard execution model and removes application-owned matching
logic. Dynamic roles, sessions, revocation, and audit remain application or
independent-framework authority.

## Non-Normative Canic Adapter

A Canic application can map one local application scope onto the complete SQL
read lane without an IcyDB dependency on Canic. The following is illustrative
pseudocode; exact Canic names remain Canic authority:

```rust
fn may_read_sql(context: icydb::ReadAuthorizationContext)
    -> icydb::ReadAuthorizationDecision
{
    match canic::local_application_authorization(
        canic::LocalApplicationAuthorizationContext {
            observed_transport_caller: context.caller,
            required_scope: ICYDB_SQL_READ_SCOPE,
        },
    ) {
        canic::LocalApplicationAuthorizationDecision::Allow(_) => {
            icydb::ReadAuthorizationDecision::Allow
        }
        canic::LocalApplicationAuthorizationDecision::Deny(_) => {
            icydb::ReadAuthorizationDecision::Deny
        }
    }
}
```

`ICYDB_SQL_READ_SCOPE` authorizes the whole generated `icydb_query` lane,
including admitted `SELECT`, `SHOW`, `DESCRIBE`, and `EXPLAIN`. It is not four
statement-class scopes. Every denial or locally unavailable Canic authority
maps to IcyDB `Deny`; the adapter performs no remote call, shared grant lookup,
controller fallback, or policy reconstruction.

## User Outcome

- A reader can query an opted-in canister without becoming its controller.
- A canister controlled by another canister can authorize a human through
  application policy without changing controllers.
- Runtime-managed application policy can revoke access without an IcyDB
  upgrade; a deliberately source-fixed allowlist still requires an application
  upgrade.
- SQL and dedicated schema reads can use separate application guards and
  distinct policy-denial diagnostics.
- Anonymous remains denied unless the application deliberately exports the
  existing public schema mode; this line adds no public SQL mode.
- SQL mutation rejection remains unconditional.
- Generic tools retain one `icydb_query` method name, signature, and diagnostic
  vocabulary instead of discovering application-specific wrappers.

## Canonical Ownership

1. The application owns the decision to export each generated surface and the
   guard path attached to it.
2. IcyDB owns authorization grammar, guard types, maintained allowlist matching,
   wrapper ordering, anonymous rejection, fixed policy-denial mapping,
   read-only SQL dispatch, startup admission, and response bounds.
3. The application or independent framework owns identities, authentication,
   roles/scopes, local policy evidence, expiry, revocation, capacity, and audit.
4. Clients own authority establishment and human-facing explanation beyond the
   fixed IcyDB denial categories.

The canonical guarded-call order is:

```text
method present and selected by IC dispatch
  -> IC Candid decode of maintained arguments
  -> reject anonymous in guarded mode
  -> application guard over caller + declared surface
  -> existing 0.225 startup admission
  -> existing SQL/schema handler and request budgets
  -> existing bounded response
```

## Guard Contract

### Enforced By Generated Code

- standard Rust macro `path` grammar and exact function-pointer coercion;
- anonymous rejection before application code;
- exactly one invocation after successful Candid decoding for each
  non-anonymous guarded invocation;
- invocation before request-root, parser, readiness, schema, database, or
  handler construction;
- caller and declared surface as the only supplied context;
- fixed mapping of returned `Deny`; and
- no controller fallback or bypass in guarded mode.

There is no dynamic registration, string lookup, optional runtime guard, guard
chain, fallback guard, cached result, or controller union.

### Required Of Application Code

An application guard is required to be synchronous, local, bounded,
side-effect-free, and total over untrusted principals. It must not mutate heap
or stable state, log caller data, schedule work, enter IcyDB, call `db!()`,
observe readiness, drive recovery, recurse, panic, trap, or allocate from an
unbounded caller-controlled input. A synchronous local IC system predicate such
as `is_controller` is allowed; an inter-canister/management call or `await` is
not. The Rust signature alone cannot enforce these behavioral requirements.

IcyDB proves generated ordering and its maintained helper. A consuming
application or framework proves its own adapter. A guard panic or trap aborts
the call and releases no SQL or schema data, but is not caught and is not
guaranteed to return the typed policy-denied diagnostic. Compile tests must not
claim to prove purity, bounded cost, or panic behavior.

## Diagnostics And Empirical Surface Discovery

The two new leaves are reserved exactly:

| Condition | Symbol | Wire code | Class | Origin | Retry classification |
| --- | --- | --- | --- | --- | --- |
| guarded SQL caller denied | `RUNTIME_BOUNDARY_SQL_SURFACE_POLICY_DENIED` / `SqlSurfacePolicyDenied` | E281 | `Unsupported` | `Interface` | non-retryable for this request |
| guarded schema caller denied | `RUNTIME_BOUNDARY_SCHEMA_SURFACE_POLICY_DENIED` / `SchemaSurfacePolicyDenied` | E282 | `Unsupported` | `Interface` | non-retryable for this request |

The maintained taxonomy has no authorization/access-denied class. E25 and E26
currently use `Unsupported` with `Interface` origin for the same generated
access boundary. E281 and E282 retain that taxonomy so the line adds precise
policy-denial leaves rather than a new widely consumed class. Here
`Unsupported` means unavailable to this caller under the declared boundary,
not that SQL/schema reading is absent. Patch 1 rechecked the exact predecessor
before freezing this choice.

Anonymous and returned `Deny` use the relevant policy code. Application detail
is not placed in the public IcyDB error. Guard panic/trap is not translated.
Method absence remains the IC method-not-found result.

`Unsupported` and the non-retryable classification describe this request under
the authority observed now. They do not claim the surface is permanently
unsupported: a caller may establish or refresh application authority and issue
a later request, which evaluates current local policy again.

## Authorization Metrics And Audit Ownership

E281/E282 attempts, including anonymous guarded attempts, are intentionally
excluded from IcyDB database request metrics because rejection occurs before
request-root construction. IcyDB adds no denial counter or security log in this
line. The application or independent authorization framework owns bounded
security-audit evidence and any allow/deny aggregation; platform-level IC
method accounting remains independent. An allowed request joins the maintained
database metrics path only when the existing request root is constructed after
authorization.

0.226 emits no endpoint manifest, sidecar, digest, custom section, or second
discovery artifact. Tools discover practical availability by calling the
standard method and distinguishing success, E25 or E281 for SQL, E26 or E282
for schema, and method-not-found. Authorization mode that cannot be established
from that result remains unknown. Metadata is deferred until a demonstrated
consumer cannot use empirical discovery and supplies a concrete authenticated
deployment-evidence requirement.

## Persisted And Public Hard Cuts

- `guard(path)` is the sole new authorization spelling. No second attribute,
  registry, environment toggle, or controller-union mode is added.
- Existing SQL declarations remain controller-only; existing schema
  public/controller modes retain exact meaning.
- Guarded mode retains existing SQL/schema Candid signatures and adds no auth
  blob, token, proof, or continuation field.
- A declared guard is sole read authority for its surface. Controllers receive
  access only if application guard logic explicitly grants it.
- IcyDB persists and caches no reader authority or decision.
- SQL guard covers the complete admitted SQL lane; `icydb_schema` is not a
  substitute for SQL introspection.
- Lifecycle participation moves wholly to 0.227 and is not a 0.226 gate.
- Empirical calls to the standard methods are the only 0.226 discovery
  contract; this line emits no metadata artifact.

1. Read permission never grants controller/lifecycle authority.
2. Missing or unavailable application authority fails closed.
3. Anonymous never reaches application code on a guarded surface.
4. Guard replaces controller authority without implicit union.
5. After successful Candid decoding, guard runs before request-root, parser,

6. SQL mutation rejection is independent of authorization mode.
7. SQL and dedicated schema guards are independently declarable and have

8. SQL guard context does not imply per-statement authorization.

10. IcyDB owns no external identity, proof, session, expiry, or revocation

    decision is cached.
12. Method absence, controller denial, and policy denial remain distinguishable.
13. 0.225 readiness cannot be bypassed or driven by an allowed guard.
14. Denial creates no IcyDB request root, session, readiness observer, schema

15. The maintained allowlist helper is bounded, allocation-free, non-panicking,

18. No compatibility alias, shim, fallback authority, or dual format exists.

## Complexity And Maintenance Gate

Demonstrated need: controller-only generated reads grant excessive lifecycle
authority and cannot serve a human reader when another canister controls the
target.

The hand-written endpoint alternative already calls the trusted SQL facade,
but its application-chosen method name prevents generic discovery. Explorer
probes the standard `icydb_query` method and reports no SQL surface when it is
absent. Ten bespoke wrapper names require ten integrations; one generated name,
signature, mutation policy, and diagnostic vocabulary creates one ecosystem
surface. This tooling contract is the decisive justification.

Canonical owner: IcyDB owns only the generated guard, maintained matching
helper, diagnostic, and standard-method boundaries. Application policy stays
outside.

State-space delta: one new value in an established authorization field and one
two-way decision per declared read surface. IcyDB adds no persistence, auth
registry, credential format, grant lifecycle, remote cache, row policy,
lifecycle mode, or continuation authority.

Promotion fails if implementation adds a reader store, generic policy engine,
auth blob, async/remote guard, implicit controller union, statement parsing
before authorization, within-SQL scopes, cached decisions, lifecycle work,
deployment attestation, or another SQL route. Every handoff reports semantic
owners, duplicate flows, instruction/stable/raw-Wasm effects, file/line delta,
and whether structure became simpler, neutral, or more complex.
