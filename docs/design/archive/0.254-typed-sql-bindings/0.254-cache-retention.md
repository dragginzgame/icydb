# 0.254 — Shared-Plan Retention Prerequisite

Status: landing slice 2 implemented and verified in the worktree. See the
[implementation and measurement receipt](0.254-cache-retention-receipt.md).
Bindings remain landing slice 1 and do not start in this handoff.

## Decision Boundary

The baseline defect was a shared concrete-plan insertion charged zero bytes.
Strong cached plans also retain schema references, operands, ten top-level lazy
preparation residents and deferred raw index-bound buffers below those residents.
A shallow initial charge cannot bound later growth. The existing 4-MiB weight
and 1,024-entry limits remain the starting
policy, not permission to claim all allocator memory is bounded by 4 MiB.

The user selected preserving strong-cache behavior after reviewing the weak
prototype's native slowdown. The weak prototype was removed; it is not a
maintained mode. The alternatives considered were:

- Keep strong concrete plans and account their complete initial and lazy-owned
  graph, enforcing reservations before each retained attachment. This preserves
  repeat-read optimization but spreads accounting across many executor owners.
- Keep concrete-plan cache references weak, with the existing prepared-plan
  owner defining downgrade/upgrade. Cache keys and immutable value-independent
  template metadata remain strong and must be charged by capacity. Weak
  allocations/control blocks must also be charged. A weak reference does not
  retain the plan's operands, authority or lazy children after the last active
  strong owner drops; an already-live plan remains reusable under the existing
  current-authority/cache-key and cardinality checks.

The second alternative changes retention, not query execution semantics, but
may materially increase repeated structural-query cost once prior plans expire.
SQL compiled-command retention is a separate existing owner, not covered by a
shared-cache byte claim. Future bound SQL still bypasses that command cache.
Do not disguise this trade-off as free accounting or introduce configurable
strong/weak modes, a second executor, persisted state or a new cache registry.

Canonical owners: the existing shared cache admits/evicts entries; each immutable
key/template component supplies its own retained allocation accounting; the
prepared-plan owner controls plan lifetime. New internal lifetime handles, if
selected, add no public API, encoding or independent configuration axis.

## Selected Contract

Preserve strong plan and recent-bound memo reuse. Account initial owned
allocations and later lazy retention at their owners, using capacity rather
than wire size or a shallow shell charge. Admission/replacement must fit before
retention. Cache misses or declined retention must not reject otherwise valid
queries. The fix must not replace strong residents with weak references or
eagerly compile every unused execution route simply to obtain a size.

The native control measured repeat/changing/scan/literal-SQL at
14,967/25,613/9,684/6,872 ns per fresh-session call; the weak prototype measured
27,033/25,148/18,163/6,779 ns. These small host samples motivated rejection of
the weak policy; they are not Wasm evidence or numerical release ceilings.

## Ownership Trace And Scope Finding

The selected policy is sound, but treating its implementation as a local cache
weight correction understated the work. The retained graph crosses these
existing owners:

| Owner | Retention that an enforced byte contract must cover |
| --- | --- |
| `session/bounded_cache.rs` | Hash-map entry and FIFO key copies; weighted admission, replacement and eviction; mutable values currently have no reweighting boundary |
| `session/query/cache/{identity,template}.rs` | Recursive structural keys, candidate-index metadata, and the strong recent-bound memo; current 8-KiB/24-KiB base estimates do not measure that graph |
| `executor/prepared_execution_plan/{shared_plan,core}.rs` | Authority, logical/static plans, continuation copies, lowered specs and ten top-level lazy cells |
| `query/plan`, `predicate`, `index/predicate` | Original and compiled expressions, operand copies, projection/order/grouping contracts and encoded literals |
| `access/lowering.rs` | Encoded prefix components and deferred raw-bound cells, potentially one per multi-lookup prefix |
| `executor/authority`, `data/structural_row.rs`, `schema` | Accepted row/decode/schema contracts, defaults, relation metadata and shared enum/composite catalogs |
| `value` and schema numeric atoms | Recursive values and external arbitrary-precision storage whose retained capacity is not exposed by the current wrapper API |

A temporary syntax-only Rust scan starting from `SharedPreparedExecutionPlan`,
`QueryPlanCacheKey` and `PreparedQueryTemplate` found 150 potentially reachable
non-`Copy` declarations/aliases across 53 core source files. This is a scope
screen, not an exact type-resolved count, file-edit forecast or Wasm reachability
measurement: it over-approximates same-named types and does not resolve feature
configuration, generic substitutions or external implementations. The concrete
owner paths above were inspected separately.

### Deferred bounds are a separate lazy boundary

`LoweredIndexPrefixRawBounds::DeferredComponentPrefix` contains another
`OnceLock`, outside the ten cells on `PreparedExecutionPlanResidents`.
`raw_bounds()` materializes two owned raw-key buffers and returns references
into the cell. Therefore the simple policy "compute, try to reserve, return the
uncached owned result on failure" cannot be applied unchanged here: this API
returns borrowed results and needs the backing buffers to remain alive.

Resolve this at the access-lowering owner: either prove and reserve a
capacity-based upper bound for the future buffers during cache admission, or
explicitly change the ownership handoff and its direct consumers. Do not turn
budget exhaustion into a query error, silently retain the buffers without a
charge, or eagerly build every unused route. A reservation for only the ten
top-level cells is insufficient.

### Shared authority cannot simply be excluded

`EntityAuthority` holds an `Arc<SchemaInfo>` and a row-layout contract. Both reach
accepted value catalogs. `invalidate_accepted_schema_runtime_root()` removes
the current root-cache entry; it does not remove shared query-cache entries.
An old prepared plan can consequently prolong the life of accepted schema
allocations even though current-authority checks prevent executing that old
plan. Correct execution authority and bounded retention are separate proofs.

Count these retained allocations, conservatively allowing duplicate charges,
or first establish an explicit lifetime/invalidation contract that makes an
exclusion true. Do not assume that another owner permanently retains them.

### Accounting must not guess opaque capacity

`Vec`/`String` capacities are available at their owners. The existing big-integer
wrappers expose conversions and logical digits/encoding, not underlying retained
capacity; accepted catalogs use `BTreeMap`, whose node allocation is not exposed
through collection length. Logical payload limits alone do not establish either
allocation bound. Any representation change, supported conservative bound or
cache-ineligibility policy needs an explicit decision and workload evidence.

### Implementation decision

The user explicitly accepted the expanded accounting work: this is internal
implementation complexity, not another operational mode or user-facing choice.
Preserve strong reuse and proceed in slice 2; bindings remain unstarted.

The existing bounded cache owns a shared byte budget and entry-lifetime charges.
Prepared residents may borrow an entry's accounting handle without keeping the
entry alive. Admission measures owned capacity at the existing type owners;
later lazy attachments reserve their charge before the cache retains them.
Eviction/replacement releases entry charges. Declining retention never rejects
an otherwise valid execution. No endpoint, configuration, persisted state,
query route, registry or alternate strong/weak policy is added.

Use a private retained-allocation visitor with exhaustive owner-local field
coverage. Count owned buffer capacities and conservatively count shared graphs;
allocation metadata is an explicitly separate overhead, not a claim that the
whole process fits in 4 MiB. Opaque allocations must have a supported bound or
make that artifact cache-ineligible, never receive a guessed zero charge.
Deferred borrowed raw bounds reserve their encoder-owned maximum before entry
admission, preserving their existing borrowed execution API.

## Historical Ownership Probe Receipt

This section records the earlier investigation, before the now-completed
implementation. Its restored-baseline and validation statements are historical;
the linked implementation receipt above describes the current handoff.

A temporary native test constructed deferred prefix bounds behind two shared
owners, confirmed the cell was initially empty, materialized the bounds through
the execution owner and dropped that owner. The retained owner still held the
same lower-buffer pointer and both populated bounds. The empty-prefix fixture
retained 4,209 logical raw-key bytes; buffer capacities and allocator overhead
were not measured. This proves the extra lazy lifetime boundary, not its total
memory cost or a production-cache weight correction.

The probe passed and was removed, as was the temporary native policy timing
test. Reproduction patches and the syntax-screening tool remain only under
`/tmp/icydb-0254-retention-graph.RaJetG/`. Production code is restored to the
strong-cache baseline; no temporary instrumentation is part of the handoff.

After probe removal, all 15 focused session-ordering tests passed. Formatting
and tracked-diff whitespace validation also passed. The SQL-only build emitted
the same 64 existing dead-code compiler warnings; no clippy gate was run.

This follow-up changes three design documents (approximately 110 added lines)
and removes the pending timing probe; executable complexity is unchanged from
HEAD. No candidate Wasm or
instruction delta is available because no accounting implementation exists.
No package version, release note, endpoint, persisted representation or local
network lifecycle changed. Full suites remain user-owned.

## Required Proof

Run identical baseline/candidate workloads for repeated and changing structural
bindings, filterless scans and warm literal SQL. Report raw Wasm and function
count when building candidate actors; native timings alone are not a Wasm gate.
Verify A/B/A, schema/visibility changes and cardinality lifecycle behavior.

Memory tests must exercise nonzero insertion, capacity rather than logical
length, FIFO key copies, oversize admission, replacement/eviction, and plan
payload lifetime including lazy residents. Unknown allocation sizes cannot
silently receive a zero or guessed fixed charge. Any conservative cache
ineligibility must leave ordinary execution available and be documented.

Complete this bounded outcome, focused validation, release notes and its cost
receipt before handing off. Do not start SQL placeholder implementation here.
