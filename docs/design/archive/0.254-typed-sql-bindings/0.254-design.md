- **Status:** Implementation and approved corrections handed off; final read-only closeout next (see tracker)

- **Source baseline:** `v0.253.3`, observed at `07f14d9f1`; clean worktree before authoring
- **Tracker:** [0.254 status](0.254-status.md)
- **Pre-implementation evidence:** [Decoder probes and source findings](0.254-preflight.md)
- **Predecessor:** 0.253's reported ready/complete closeout and explicit authorization

  evidence of user-owned full-suite validation. Current delivery status belongs
  to the tracker; this document specifies the maintained contract.

## 1. Decision

Provide an optional ecosystem SQL frontend for edge cases, with typed values
and reusable syntax. The user's production applications will rarely use SQL;
typed/structural Rust queries remain their default. Reduce string construction
and repeated parsing for applications that choose SQL, not by migrating
structural callers. SQL text belongs to application code; changing
values use existing `InputValue` bindings. Reuse the existing parsed dispatch
artifact and converge on accepted-schema preparation and ordinary execution.
This is not a short-term SQL endpoint feature.

The desired user outcome is a repeated query such as:

```sql
SELECT id, amount FROM Transfer
WHERE owner = ? AND amount >= ?
ORDER BY id LIMIT 50
```

An application-owned endpoint accepts domain arguments such as account and
minimum amount, authorizes the operation, and supplies those values to its fixed
query. Its clients do not supply SQL or a generic bindings vector. Application
code can parse the fixed statement once and retain that immutable syntax for
repeated executions with different values. Parameterization does not grant read
access or change query consistency.

There are no endpoint/Candid/CLI binding changes, named statement services,
remote prepare/execute handles, new registries, binding modes or execution
routes. Application-owned parsed syntax contains no accepted authority or bound
operands. Every execution still resolves current authority. Plan reuse remains
an optimization, never a correctness or authorization dependency.

Success means a familiar SQL surface can accept typed changing values without
string interpolation or reparsing retained syntax, while using the existing
query engine. It need not beat structural queries in brevity or speed, and
production SQL adoption in the user's projects is not a release prerequisite.
Measure optional SQL costs separately from changes to shared owners that also
affect structural callers. Broader ecosystem reach is the capability benefit;
this is not a claim that the whole implementation becomes smaller or faster.

## 2. Rationale And Alternatives

The production-ledger intake motivates changing account, amount, block-range
and time-window operands. The existing parsed dispatch, typed `InputValue`, SQL
value nodes and shared planner provide the needed ownership boundaries without
a separate prepared-statement subsystem. Original source observations and
superseded endpoint experiments remain in the [preflight](0.254-preflight.md);
they are historical evidence, not a second current API specification.

The maintained `canisters/audit/sql_perf/src/lib.rs::query_entity_with_perf_loop`
calls the text facade inside its loop, so it reparses even on concrete-command
cache hits. It is a real parse-reuse control, not evidence that bindings are
necessary: the existing parsed path already avoids those repeated parses.
The changing-key control is
`canisters/audit/one_entity_dynamic_query/src/lib.rs::measure_parameterized_point_queries`,
which already constructs typed structural predicates without SQL interpolation.
Preserve that comparator rather than migrate it to SQL. These are maintained
audit workloads, not evidence of downstream production adoption.

Alternatives:

- Existing typed/structural queries already avoid SQL interpolation and parsing.
  Keep them idiomatic first-class APIs; do not move their callers to SQL to
  manufacture adoption. Compare a real repeated SQL call site with that option.
- Binding typed values removes value rendering/parsing, but a text-plus-bindings
  call still parses its SQL on every invocation. It alone does not satisfy the
  reduced-parsing objective.
- Reuse the existing immutable parsed-dispatch boundary for repeated statements.
  A second AST, global parse cache or server-side statement registry is not needed.
- Endpoint expansion does not justify this line. The earlier wire-decoder probe
  remains evidence for a separate future endpoint decision, not a current gate.

## 3. Library Invocation And Compatibility

Use the existing `SqlStatementDispatch` ownership model: the AST is coupled to
the exact borrowed source text, and its fields cannot be independently replaced
by callers. Make the needed facade access intentional and documented rather
than adding a parallel `PreparedSql` object or serialized `SqlQueryRequest`.
The parsed execution boundary accepts a bounded slice of `InputValue` bindings.
The maintained signatures are:

```rust,ignore
// Existing parser and type, intentionally exposed through icydb::db.
// The parser keeps its existing core QueryError return type.
pub fn sql_statement_dispatch(sql: &str) -> Result<SqlStatementDispatch<'_>, QueryError>;

// Existing DbSession method, changed in place.
pub fn execute_trusted_sql_query_dispatch(
    &self,
    dispatch: &SqlStatementDispatch<'_>,
    bindings: &[InputValue],
) -> Result<SqlQueryResult, icydb::Error>;

// Existing ad-hoc convenience, unchanged; parses and forwards with &[].
pub fn execute_trusted_sql_query(&self, sql: &str) -> Result<SqlQueryResult, icydb::Error>;
```

Document the existing parser, dispatch type and parsed-query method as intended
library surfaces; add the existing type's facade re-export. Keep unrelated
generated routing helpers hidden. Do not add a text-plus-bindings overload,
another prepared type, constructor wrapper, generic binding builder or old-arity
alias. Borrowing the syntax and a slice permits stack-allocated binding arrays.
Core parsed-query execution receives the same slice; callers of the changed
method propagate it directly.

- Parsing happens when application code constructs the dispatch, under the
  existing SQL input/token/depth limits. Repeated execution of that dispatch
  must not reparse its source, even when bindings change.
- Bind into per-execution owned operands; never mutate the reusable AST or retain
  current bindings/accepted authority in it. Its lifetime is application-owned,
  not an unbounded framework registry of caller-created statements.
- The existing text convenience boundary may parse once per call and converge
  on this same dispatch execution path. It is not the parse-reuse path.
- Literal-only queries and maintained introspection use empty bindings. Preserve
  existing capability checks and results. SQL mutations and DDL gain no bindings.
- Existing generated SQL endpoint exports, access policy, text arguments, Candid
  fixtures and CLI transport remain unchanged. If a Rust signature changes,
  generated handlers mechanically supply empty bindings to the current library
  path; they do not receive bindings from the wire. This is not a compatibility
  decoder or a second maintained wire form.
- Do not enable SQL exports in additional actors. Do not add generic binding
  endpoints, Candid request derives, new CLI syntax or secure SQL endpoint work
  to this line. Application endpoints retain domain-specific typed arguments.

Any changed Rust surface follows the pre-1.0 hard-cut rules with direct
call-site propagation and no aliases or legacy wrappers. No client wire
regeneration, persisted-format change, cursor change or format discriminator
is required by this scope.

### Application lifetime and structural comparison

The maintained implementation now uses the one-entity audit schema in
`canisters/audit/one_entity_sql_query/src/lib.rs`. Its `OnceCell` is initialized
only by init/post-upgrade, and its unchanged exported handler calls a private
`get_row(Ulid)` helper with the same immutable parsed dispatch. The focused
PocketIC test passed three separate query messages before and after upgrade.
Changing bindings and an accepted field rename are covered by native session
tests. This is lifecycle evidence, not a production adoption claim.
The following sketch illustrates where an application's authorization belongs;
the public empty audit fixture does not implement a production access policy.
`authorize_row_read` is application-owned policy and must run before entering
the trusted lane; it is not a new IcyDB helper. Return-domain mapping is omitted.

```rust,ignore
use std::cell::LazyCell;
use icydb::{
    db::{SqlStatementDispatch, sql::SqlQueryResult, sql_statement_dispatch},
    types::Ulid,
    value::InputValue,
    Error,
};

thread_local! {
    static ROW_QUERY: LazyCell<Result<SqlStatementDispatch<'static>, Error>> =
        LazyCell::new(|| {
            sql_statement_dispatch(
                "SELECT id FROM OneSimpleEntity01 WHERE id = ?"
            ).map_err(Error::from)
        });
}

// Call from the application's existing init and post_upgrade hooks.
// Force initialization in a committed lifecycle call, not the first query.
// A parse error is retained and returned by the handler, never unwrapped.
fn initialize_application_queries() {
    ROW_QUERY.with(|query| { let _ = LazyCell::force(query); });
}

// Application-owned domain handler; clients supply an id, never SQL/bindings.
fn get_row(id: Ulid) -> Result<SqlQueryResult, Error> {
    authorize_row_read(id)?;
    icydb::db::with_request_execution(|| {
        let database = icydb::db!()?;
        ROW_QUERY.with(|query| {
            let dispatch = query.as_ref().map_err(Clone::clone)?;
            let bindings = [InputValue::ulid(id)];
            database.execute_trusted_sql_query_dispatch(dispatch, &bindings)
        })
    })
}
```

The retained object borrows only a static SQL literal. It owns no session,
binding vector, accepted schema or caller permission. Each invocation creates
its session inside the request scope and borrows the same immutable syntax.
The closure is synchronous; no thread-local/session borrow crosses an await.
Schema changes require current-authority validation, not reparsing that syntax.

For the canister example, connect initialization to the existing application
hooks (the maintained `sql_perf` actor uses `icydb::start!` init/post-upgrade
hooks); do not add framework registration or another exported endpoint.
Initialize again after code replacement, rebuilding syntax rather than
persisting an AST format. Lazy initialization performed only in a query cannot
establish across-query reuse: query state changes are discarded. See the
[IC query semantics](https://docs.internetcomputer.org/references/ic-interface-spec/abstract-behavior/).
Require a multi-message test after lifecycle initialization, not just a loop
inside one message; also exercise syntax rebuild after upgrade.

The equivalent maintained structural construction is shorter for this point
lookup and needs neither parsing nor retained application syntax:

```rust,ignore
let request = DynamicQuery::new("OneSimpleEntity01")
    .filter(FieldRef::new("id").eq(id))
    .select(["id"]);
let output = database.execute_trusted_live_page(&request, None)?;
```

Compare projected ids, errors and authority behavior, not the different wrapper
types. This example establishes an ownership model, **not a SQL ergonomics win**.
The ecosystem-first scope does not require replacing a production structural
query to justify the extension. Do not count lifecycle boilerplate as complexity
removed. The
maintained SQL loop supplies a parsing baseline, while the structural actor
supplies an alternative that already handles changing values.

The [follow-up host controls](0.254-preflight.md#construction-cost-control)
measured parsing at 1,167–1,198 ns/op, AST cloning at 259–291 ns/op and matching
two-condition structural construction at 299–315 ns/op. These are two native
construction-only samples, not execution or Wasm results. AST cloning is not
free; the measurements do not establish an overall bound-SQL benefit.

## 4. Binding Semantics

### Supported statements and positions

Admit bindings for existing scalar, global-aggregate and grouped `SELECT`
queries, restricted to expression-operand positions in `WHERE` already
represented by the maintained scalar AST, plus individual values in an `IN`
list. Literal-only grammar slots such as LIKE patterns and numeric rounding
scales are not widened by this slice. Existing literal
`HAVING` remains supported, but placeholders in `HAVING` are excluded from this
release.
Parameter support never makes an otherwise unsupported expression executable.

- Each lexical `?` consumes exactly one zero-based slot. Quoted question marks
  are not slots. Comment syntax is not added; the existing grammar rejects
  block comments. Preserve slot order before normalization.
- The binding count must exactly equal the slot count; missing and extra values
  reject. Repeated values require repeated slots; named and numbered syntax is
  not added.
- `IN (?, ?, ?)` accepts three scalar bindings. `IN (?)` does not expand one
  list into multiple terms. Dynamic collection expansion is out of scope.
- Reject placeholders in projection, `HAVING`, `GROUP BY`, `ORDER BY`, `LIMIT`, `OFFSET`,
  entity/field names, operator names, and every schema or mutation statement.
- Nonempty bindings on introspection or `EXPLAIN` reject. Bound `EXPLAIN` is
  deferred; internal plan inspection supplies the required planner tests.

### Values and typing

Reuse existing scalar `InputValue` families admitted by the corresponding
accepted query position, including exact integers, big integers, U256,
decimals, finite floats, text, blobs, accounts, principals and temporal values.
`Null` uses existing SQL null semantics. Recursive list/map/record values and
enum inputs are outside this first contract, even where their public carrier
can represent them.

Input tags are authoritative; a textual numeric value is not guessed to be a
number. Reuse the existing accepted-field and expression normalization rules
for permitted conversions and comparison compatibility.
Do not introduce SQL-binding-specific casts, lossy BigInt/Decimal conversion,
implicit null-to-default behavior, or different arithmetic semantics.

Binding `Null` does not rewrite `field = ?` into `IS NULL`. It behaves like the
same concrete null operand under the maintained SQL contract. Impossible or
ambiguous type contexts reject through the existing semantic owner.

### Typed handoff and validation before simplification

The handoff is the existing `SqlStatement` containing `SqlExpr::Literal(Value)`,
not SQL literal strings or a second binding AST. After rejecting non-scalar
families, `InputValue::try_into_runtime_non_enum` transfers the typed payload
without textual conversion. `lower_sql_expr` in `db/sql/lowering/expr.rs` maps
that node directly to `Expr::Literal(Value)`. Accounts, principals, U256 and
decimals therefore keep their runtime representation through lowering.

For field comparisons and individual membership operands, reuse query operand
normalization and validation, not stored-field admission. The user explicitly
selected this policy after the slice-1 probe: a negative comparison boundary
for a Nat64 field is query-valid even though it cannot be stored in that field.
In `db/predicate/normalize.rs`, `normalize_enum_literals` routes non-enum operands
through `normalize_compare_value_for_accepted_kind`; only enum-bearing contracts
use `AcceptedValueAdmissionContract::normalize_input_to_runtime`. Follow with
`db/query/predicate::validate_predicate` before any simplification. Do not impose
write-time field range, precision, size or nullability constraints on query
operands unless the existing query owner requires them.
`normalize_query_predicate` in `db/query/plan/access_planner.rs` calls it before
predicate simplification. Reuse or narrowly expose this owner; do not copy its
conversion rules into SQL preparation.

Preparation must validate **every original slot in its unsimplified context**:
resolve placement and accepted operand contract, perform its permitted
normalization, and validate the containing expression before any SQL or
predicate fold can discard it. Retain lexical slot identity until this pass
finishes. Put the accepted normalizer's returned `Value` into the corresponding
typed operand node; do not stringify it or reconstruct it from the generated
model. Validate all membership elements before deduplication. For example,
an incompatible account bound to a numeric comparison rejects even beneath
`FALSE AND ...` or `TRUE OR ...`; valid neighbors cannot short-circuit admission.
Only then may ordinary preparation, lowering and planning simplify the query.
Execution artifacts contain no unresolved placeholders. Counting lexical slots
and validating only surviving predicates does not satisfy this contract.

The worktree implementation lives in `db/sql/lowering/bindings.rs`.
`prepare_statement` normalizes identifiers into an execution-owned AST, then
the binding visitor visits every original operand before ordinary lowering.
`compile_bool_compare_expr`, query normalization and `validate_predicate` admit
field/literal leaves; `infer_expr_type` admits other scalar expressions. Boolean
wrappers retain the existing WHERE truth-shape rules rather than imposing broad
expression inference on maintained SQL-null predicates. Membership uses one
literal-or-parameter leaf representation, not a general expression list.

Count, placement, depth and scalar-payload preflight run once at query ingress,
before cache eligibility is selected. Bound preparation requires that preflight;
it does not repeat it. An enclosing typed expression checks nested scalar
wrappers/arithmetic as one subtree. Nested comparisons still run their existing
query normalization before that enclosing check, and every IN element is
admitted separately. This scheduling cannot defer checks until after folding,
skip sibling operands or bypass current authority. Shared arithmetic typing
propagates known NULL only after validating both operand families; unresolved
types and incompatible non-NULL siblings still reject.

### Aggregate boundary

Bound `HAVING` is deferred. `WHERE` bindings still filter the input rows of
maintained scalar/global/grouped aggregate queries. Existing literal aggregate
behavior must remain unchanged.

The preflight's input-derived aggregate typing finding is addressed by the
separately approved aggregate-contract correction (status slice 7). Shared
inference now describes the existing Decimal or U256 reducer result without
changing numeric precision or input admission. This does not authorize bound
HAVING: its full result-normalization and pre-fold binding contract still needs
a separate decision. No SQL-local SUM classifier or source-field narrowing is
acceptable.

### Admission matrix

This matrix routes to existing semantics, not a new casting specification.
Each row requires an accepted/rejected fixture against the maintained owner.

| Original family | Valid context | Allowed conversion | Rejection example |
| --- | --- | --- | --- |
| Fixed signed/unsigned integers, IntBig, NatBig | Compatible accepted numeric comparison or `IN` element | Existing query comparison/coercion rules; negative comparison boundaries for unsigned fields can be valid | Unsupported comparison family/coercion, not merely a value outside the field's stored range |
| U256 | Accepted U256 field/expression comparison | Existing exact U256 admission/comparison only | Overflow or unsupported mixed arithmetic |
| Decimal, Float32, Float64 | Compatible numeric field/expression | Existing query normalization and comparison rules; no binding-specific conversion | Nonfinite float rejected by existing scalar construction; incompatible query operand family |
| Account, Principal, Subaccount, Ulid | Corresponding accepted field comparison or `IN` element | Preserve typed identity; no parsing display text into these types | Account in an amount comparison |
| Date, Timestamp, Duration | Corresponding accepted temporal comparison | Existing accepted temporal contract only | Wrong temporal family where the owner disallows it |
| Text, Blob, Bool, Unit | Corresponding maintained scalar predicate context | Existing operator/type contract only | Numeric-looking Text in a numeric-only comparison |
| Null | Nullable/SQL-null operand context admitted by the existing owner | No defaulting or equality-to-`IS NULL` rewrite | Null in a context the owner requires to be non-null |
| Any binding in `HAVING` | None in this release | None | `HAVING SUM(amount) >= ?` rejects placement, independently of the supplied family |
| Enum or recursive containers | None in this release | None; reject before recursive runtime conversion | List supplied for `IN (?)`, including an empty list |

Use equivalent literal SQL as the oracle only where its literal representation
is exact. Otherwise compare rows, order, aggregate values and typed rejection
against the maintained typed/structural query surface, including accounts,
large numerics and aggregates over rows filtered by bound WHERE operands.

## 5. Admission, Bounds And Errors

Library binding limits are 64 values and 64 KiB of aggregate logical value
payload. Scalar sizing and checked aggregate accounting precede cloning caller
data. These are admission limits, not caller configuration or cache
eligibility limits. Existing accepted-value, SQL syntax, IN, request execution
and output limits remain independently enforced.

The application authorizes its domain operation before entering the trusted SQL
library lane. Library admission then:

1. Uses the immutable parsed dispatch (or constructs it once for a text call).
   Validate static statement family and placeholder placement without reparsing.
2. Checks binding count before cloning or walking values; rejects container/enum
   tags without recursive runtime conversion; enforces scalar payload bounds.
3. Resolves current accepted authority. Every bound invocation validates every
   original slot/context before any fold can erase it; SQL concrete-command
   cache lookup and insertion are both bypassed. Literal-only cache eligibility
   remains unchanged after count/placement admission.
4. Executes through the maintained query pipeline and request budget owner.

A reusable syntax artifact is not authorization, accepted-schema proof or a
compiled executable plan. Current authority and access gates always run.
Bounds on Rust inputs do not claim to bound a caller's earlier construction or
decoding; the application owns its domain-specific wire contract. This line
adds no generic SQL/bindings decoder.

Errors distinguish count, unsupported statement/placement/family, accepted-type
mismatch and binding-bound exhaustion. Reuse existing typed diagnostics; add
only missing reasons at their owner. Bounded slot/type/limit facts are acceptable;
binding payloads and echoed SQL are not. Preserve authorization precedence.

The earlier Candid/recursive-decoder experiments are retained in the
[preflight report](0.254-preflight.md) as evidence for deferred endpoint work.
They neither authorize endpoint expansion nor block this internal-library
scope. Do not fix that wire path opportunistically in 0.254.

## 6. Fixed Cache Policy And Reuse

**Bound invocations bypass both lookup and insertion in the SQL concrete-command
cache.** Parsing once does not require a concrete command per binding vector.
There is no option to enable bound-command caching and no original-binding
digest in 0.254. The earlier digest specification and known-answer vectors are
historical evidence, not required implementation work.

Classify eligibility from the original dispatch and supplied inputs, before
simplification: a statement with any placeholder never enters this cache, even
if all bound branches later disappear. Missing bindings reject; supplied
bindings for a zero-slot statement reject. Only admitted zero-slot/empty-input
calls retain the existing literal-only cache policy and key. Do not classify
eligibility by whether the lowered command still contains a bound operand.

Resolve current catalog authority through the existing compile shell. For
bound calls, run the same semantic compiler with fully admitted per-execution
operands, then construct the same execution context without SQL cache access.
This is one fixed cache eligibility rule, not a new executor, runtime mode or
alternative normalization owner. No bound command may be cached under the
original SQL text or a synthesized SQL string.

| Work | Reused dispatch with bindings | Literal-only invocation |
| --- | --- | --- |
| Parsing | Once at syntax construction, never on rebinding | Once at construction; text convenience constructs per call |
| Current authority / application policy / request gates | Every invocation | Every invocation, including hits |
| Count, placement and scalar bounds | Every invocation | Empty input/zero-slot admission before cache access |
| Whole-slot context validation and normalization | Every invocation, before simplification | Existing semantic compilation on miss |
| AST cloning and operand allocation | Per-execution costs, measured separately | Existing hit/miss behavior |
| SQL lowering and concrete compilation | Every invocation, even identical bindings | Avoided on valid concrete-command hit |
| SQL concrete-command lookup / insertion | Neither | Existing policy and key |
| Shared planning and execution | Existing eligible plan/template reuse; current values required | Existing pipeline |

A/B/A tests must prove both SQL-cache bypass and correct current results through
downstream plan reuse. Include branches simplified to constants, changed
accepted schemas, invalid B after valid A, large operands and different IN
arities. No previous caller's authorization is reusable.

### Downstream retained values — prerequisite completed

Skipping SQL command retention does not eliminate downstream value retention.
Both ordinary shared plans and parameterized templates (including their single
replaceable recent-bound memo) use capacity-based admission. Replacing a memo
reweights its complete entry; lazy residents reserve capacity before attachment.
Separately retained copies are charged separately, conservatively. Repeated
accounting visits for those copies are not redundant admission checks.

The existing per-registry 4-MiB payload budget is not a whole-process heap limit.
Opaque big-integer limb capacity or excessive accounting depth declines cache
admission, not valid execution. Initial measurements, lazy-reservation proofs
and exclusions are in the [retention receipt](0.254-cache-retention-receipt.md).
This shared-owner cost also applies to structural queries. Do not introduce a
SQL-specific shared-cache mode or remove planning safeguards to improve a sample.

Measure original AST retention, temporary AST cloning, normalized operands,
returned-command/plan clones and cache-resident copies separately. Library
input limits alone do not prove a cache-memory bound. The original vector need
not be retained after admission. Existing literal-specific and parameterized
shared planning remain the only planning paths; no second SQL template cache,
universal aggregate template promise or new cursor identity is introduced.

The performance trade-off is explicit: identical bindings repeat semantic
compilation. Changing bindings would usually miss a per-vector SQL command
cache anyway. Reconsider that policy only with measured maintained-workload
evidence and separate authorization, not an optional feature in this slice.

## 7. Canonical Owners And Complexity

| Concern | Canonical owner and downstream boundary |
| --- | --- |
| Reusable syntax/source identity | Existing parser and immutable SqlStatementDispatch; application-owned lifetime |
| Library invocation/value inputs | Existing parsed-dispatch facade and InputValue |
| Placement, count and binding | Existing SQL preparation owner |
| Operand meaning | Accepted-schema value normalization and shared planner expression typing; no new aggregate-result contract |
| Concrete command cache eligibility | Existing SQL compile shell; bound invocations never look up or insert |
| Value-independent plan reuse | Existing shared parameter contract and template cache |
| Execution, current authority and budgets | Existing session/query pipeline |

State-space delta: bindings extend the existing parsed execution boundary with
one fixed cache-eligibility rule derived from original slot presence, not a
configuration axis. No digest or bound SQL cache resident is added. Reusing the
existing AST avoids a new prepared-statement type, registry or parse-cache owner. No Candid
request, endpoint route, configuration mode, persistence or cursor format is
added. Existing text and parsed entrypoints converge on the same execution flow.

Binding/context validation and any necessary downstream retention correction
still add implementation complexity. A smaller public API alone is not proof of lower total complexity.
Compare the maintained repeated SQL controls with parse-once typed binding and
the existing structural API. Record the eliminated string construction/parsing,
added owner-local code and retained memory. Do not invent an application
migration just to claim a reduction. The additional code is a capability cost,
not operational complexity or a demonstrated reduction in total engine code.
