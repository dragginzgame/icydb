# 0.254 — Binding Cost And Parity Controls

Date: 2026-09-06. Continuing landing slice 1; not a release/closeout verdict.

## Semantic Finding And Correction

The new parity check reproduced an admission mismatch: a bound null comparison
inside CASE was rejected by broad expression inference, while the concrete SQL
control executed successfully. Direct WHERE comparisons already worked.

The correction belongs to the existing expression type-inference owner:
comparisons with explicit null produce a boolean/UNKNOWN result, and explicit
null is admitted in boolean conditions. Both operands are inferred before the
comparison result is admitted. CASE result branches still undergo ordinary
type unification; this does not allow a discarded incompatible result binding
or an invalid arithmetic operand to escape validation. There is no new casting
rule, binding-specific expression representation or type-inference mode.

Stored-value parity now covers 20 non-null scalar families against the public
structural query surface, using accepted catalogs and typed writes rather than
SQL literal rendering as the oracle. This includes accounts with subaccounts,
principals, fixed/wide integers, decimals, floats, U256, blobs and temporal values.
Each control must actually match one stored row, not merely agree on an empty
result. Unit handoff and SQL-null behavior remain covered separately.

The first version of this test reused a thread-local registry after replacing
its storage, which correctly failed accepted-root publication. Cases now use
fresh thread-local registries rather than rebuilding storage beneath a retained
runtime root. The fix is confined to the test fixture.

## Matched Native Controls

Two independent optimized native test-process samples, Rust 1.97.1, all features,
same source and fixture. The fixture stores one row with a Unit primary key,
indexed label and U256 amount. The query selects id/label with a label equality,
amount threshold, primary-key ordering and limit 1. Repeated calls match the
row; changing calls use distinct absent account-like labels and thresholds.
Every frontend uses the same values and projection for its workload.

There are 20 warm-up calls followed by 500 measured fresh-session executions per
shape. Changing SQL text mostly misses the concrete-command cache; repeating
SQL text hits it. Bindings always bypass that cache. All controls retain the
shared-cache accounting from slice 2. These compare frontend choices on the
current code, **not** release-over-release regressions or production traffic.

| Execution shape | Host ns/call, two samples | Allocation requests/call | Requested bytes/call |
| --- | ---: | ---: | ---: |
| Warm literal SQL text | 9,334–9,791 | 96 | 15,793 |
| Warm retained literal dispatch | 7,754–7,789 | 67 | 13,884 |
| Retained bindings, identical values | 22,646–23,302 | 490 | 33,812 |
| Retained bindings, changing values | 44,906–45,354 | 731 | 43,460 |

| Structural, changing values | 39,109–39,875 | 551 | 37,921 |
| Rebuilt SQL text, changing values | 70,201–71,833 | 716 | 45,253 |

Interpretation: changing bindings reduce elapsed time about 36–37% versus
rebuilding SQL text in these samples, but cost about 13–15% more than structural
queries. Repeated bindings cost about 2.3–2.5 times warm literal text. Binding
allocation count is not lower than rebuilt SQL, although requested bytes are
about 4% lower for changing values. These timings are allocator-instrumented,
small host samples; neither timing nor allocation counts imply an IC speedup.

## Wasm Control Method

Temporary variants reuse the existing one-entity dynamic audit actor's methods,
arguments, return envelopes, schema and empty data. Repeated and changing point
methods each execute 200 reads in one query message; the scan remains an
unchanged structural control. The variants differ only in their frontend:
structural construction, rendered SQL text, or lifecycle-retained fixed SQL
with typed bindings. SQL variants enable the existing SQL library dependency;
neither exposes InputValue through Candid. The actor source and dependency
settings were restored after measurement. Both SQL variants use the same SQL
dependency feature; the structural-only control does not enable that frontend.
Repeated controls construct their request/render their SQL inside the loop;
this is not a comparison against every possible retained structural-query
optimization. All calls share one session within the measured query message.

These compare current-code frontend choices. They are not an exact 0.253.3
release baseline, a many-entity application workload, or multi-message cache
performance. The separate maintained lifecycle test proves syntax retention
across messages. Reports and exact temporary sources are saved under
`/tmp/icydb-0254-costs.wzVd0B`.

## Ecosystem Scope And Non-SQL Release Controls

The user clarified that SQL is primarily optional ecosystem/edge-case support,
not the intended production query API for their projects. Structural Rust stays
the default. The design therefore no longer requires a production SQL migration
or a SQL brevity/performance win over structural queries. The existing lifecycle
fixture and the public facade compile example establish the intended ownership
and invocation surface without manufacturing adoption.

This changes the product criterion, not the measurements or cost approval.
Shared-cache accounting still affects structural callers. To cover that boundary,
the unchanged empty and ten-entity reachable-operation actors were rebuilt with

## Verdict And Accepted Trade-Offs

The evidence supports typed bindings as an optional ecosystem capability for
application-owned SQL with changing values. It does not support
replacing structural queries for simplicity or speed, or promising a blanket
SQL performance improvement. Keep the no-bound-command-cache policy; adding a
cache mode or digest to improve the identical-value sample would introduce a
different complexity trade-off without a demonstrated application requirement.

The user accepted the measured trade-offs before authorizing read-only closeout;
slice 1 is handed off. The original pre-implementation numerical-ceiling gate
was missed and cannot pass retrospectively. The revised non-SQL exact-release/
many-entity controls are recorded above. Production SQL adoption is not a
prerequisite; a many-entity bound-SQL workload remains unmeasured, not evidence
of a universal adoption budget. The subsequent production NULL-typing finding
and approved correction are tracked as slice 3, not an endpoint or cache project.
That correction is now handed off; its
