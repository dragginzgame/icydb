# IcyDB 0.256 — Application API Friction

Status: authorized after the reported 0.255 closeout and user confirmation that
0.255.3 is live. Delivery state belongs to [the tracker](0.256-status.md).

## Outcome and scope

Make ordinary typed/structural application code easier to maintain by removing
demonstrably redundant preparation, conversion or result handling. Prefer using
the existing API correctly, improving an example, or narrowing its existing owner
before adding a public surface. A finding that needs no library change is valid.

This is not a facade rewrite, SQL endpoint feature, new batch system, transaction
API, generated projection framework or general clone-removal campaign. No new
runtime state, cache, configuration, persisted format or execution route is
currently proposed. Application authorization and business rules stay explicit.

## Slice 3: owned generated decoding

The user accepted the IcyDB-owned finding: generated `decode_row` receives an
owned row but borrows each output value, forcing heap-bearing scalar copies.
Replace that existing handoff and its recursive adapters with ownership transfer;
do not retain a borrowed compatibility path. Keep field/source resolution,
binding/entity checks, shape rejection and generated field evaluation order.
Records still reject duplicate/missing/unknown members before member decoding;
tuples retain exact arity and enum payloads retain source-bound selection.

Canonical owners remain the facade's accepted binding and the model's generated
adapters. The simplest alternative is retaining the copies. No cache, stored
format, configuration or execution route is added. Row extraction may leave a
NULL placeholder in the consumed scratch row, rather than allocate a second
optional-value vector; this is not a persisted state or an admission bypass.
Ordinary generated query/write callers remain unchanged. Handwritten low-level
adapter/context implementations must adopt owned arguments in this hard cut.

Baseline production source is published `v0.255.3`; the preceding 0.256 changes
only affect documentation and an enrollment compile fixture. Before runtime
edits, set gates at fewer allocation requests/bytes for heap-bearing generated
row decoding, at most +1 KiB final raw Wasm and +4 defined functions per measured
actor, and at most +1% cycles per measured control. Measure matched scalar and
nested outputs plus existing exact-key missing/duplicate controls. Retain raw
bytes as primary, gzip as secondary, and report any ceiling miss explicitly.
The measured source/toolchain/features and validation limits belong in the
slice receipt; full suites remain user-owned.

The [completed receipt](0.256-owned-decoding-receipt.md) records the final
in-place record permutation, removal of temporary member-validation buffers,
unchanged numerical gates and measured trade-offs. Raw Wasm and allocations
decrease; end-to-end cycle results are mixed, within the +1% ceiling.

## Slice 4: owned blob input

Slice 4 was explicitly accepted following the read-only closeout finding:
`TypedEntityBinding::input_scalar` owns its blob but copies it with `to_vec`.
Use the atom's existing `into_bytes` instead. This changes ownership only;
accepted binding freshness and subsequent structural admission stay unchanged.
The simpler canonical handoff adds no behavior axis or independent flow.
Baseline is the complete unpushed slice 3, not the published 0.255.3 source.
Before editing runtime code, retain gates of one fewer allocation and exactly
the blob length fewer requested bytes per nonempty blob at this boundary, no
change for empty blobs, at most +1 KiB final raw Wasm/+4 defined functions and
at most +1% cycles per measured control. Measure the actual typed-input boundary
through a current generated entity binding; this is not a full write benchmark.
The [completed receipt](0.256-blob-input-receipt.md) records exact per-blob
allocation savings, mixed artifact-size deltas and passing cycle controls.

## Slice 5: strict downstream SQL-handler linting

Slice 5 was accepted after the initial closeout. Toko Miner's saved strict
Clippy failures identify five generated SQL handlers; the generator is unchanged
between its pinned `v0.255.1` and IcyDB `v0.256.0`. IcyDB's workspace allowance
hid the consumer-policy mismatch. Keep owned endpoint-shaped handler signatures
and scope the intentional allowance to those five functions, rather than change
public ownership or require application-wide suppression. Two existing consuming
canisters deny this lint at crate scope and exercise SQL with and without SQL
endpoint exports in the maintained lint gates. No behavior axis is added.
Typed explain (ICYDB-021) is a separate candidate, not part of this repair.

## Application evidence gate

For each of the three workflows, record the repository, commit, relevant dirty
diff if any, endpoint/helper and schema files, IcyDB dependency revision and
features, authorization boundary, and smallest complete current call sequence.
Trace binding, conversion, database admission, execution, decoding, errors and
continuation to their existing owners. Classify steps as required database work,
application policy, avoidable ceremony or a demonstrated API gap.

Compare the existing specialized terminal first. Then show a before/after using
the maintained API; only then consider changing a library signature. Seek a
second independent call site before generalizing an application-specific helper
into a public API. Keep missing evidence explicit rather than inventing examples
and calling them application proof.

For each proposed library correction, the IcyDB-owned qualification record must
name exact source identity, locked build inputs/toolchain/features, focused
test or build command, artifact being checked and expected result. Slice 2's
source inspection proves only an audit finding. Its proposed test commands are
not passing evidence until run. Downstream full CI and deployment remain
downstream/user-owned; no external writes are authorized by this design.

## Single-write decision to investigate

The current `TypedWriteAdapter` already associates an input with its entity;
the concrete write-row terminal already owns execution and output projection.
If application evidence warrants simplifying orchestration, reuse those owners
and keep only unavoidable generated encoding/decoding generic. Do not duplicate
admission, result-cardinality checks or commit execution in a new generic path.

Compare retaining the explicit sequence, using the existing batch builder for
a genuine batch, and changing an existing surface. A one-item batch is not
assumed to have identical cost or bounds to a single write. No new signature,
compatibility wrapper, result mode or no-return execution lane is chosen here.

## Contracts and acceptance

- Accepted schema remains runtime authority; generated descriptors only bind
  and convert. Do not remove freshness or binding/entity-mismatch checks merely
  because one example uses a generated adapter.
- Preserve typed errors, caller ordering, missing rows, budgets, managed fields,
  write intent and the selected continuation/proof contract. Nested helpers
  reuse the current request scope rather than resetting accounting.
- [Write admission](../../contracts/WRITE_ADMISSION.md) and
  [transaction semantics](../../contracts/TRANSACTION_SEMANTICS.md) remain the
  semantic owners. Authorization and the final read/calculate/batch sequence
  stay application-owned; reread after asynchronous work. Atomicity does not
  imply rollback on an endpoint's later `Err`.
- Saved-row decoding is after publication. Optional decoding may be omitted
  when the application does not need the values; this does not skip database
  validation, response bounds or result preparation. Dedicated current-surface
  tests retain coverage of one-time result consumption and wrong-owner handles.
- Before runtime implementation, freeze workload-specific numerical cost gates
  and a matched baseline. Measure native allocation separately from IC cycles;
  report raw Wasm, defined functions and gzip with source/feature/toolchain
  identity. Include unique/missing or duplicate controls where relevant. No
  numerical performance claim follows from shorter application code alone.
- Report application versus library line changes and new/removed behavior axes.
  The example correction removes three Rust lines, adds no production flow and
  makes no cycle/Wasm claim. Full suites remain user-owned.
