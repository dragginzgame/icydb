## Actionable findings

1. **Use existing exact-key APIs at application call sites.** Toko Miner's
   `read_user_for_id` can retain its session/error mapping and replace its
   filter/order/limit/page/cardinality sequence with
   `database.get::<User>(Id::from_key(user_id)).map_err(operation_error)`.
   The membership helper has the same opportunity using its principal key.
   This is proposed source simplification, not compiled application evidence.
   Both methods exist in the application's pinned IcyDB 0.255.1 already; the
   later clone improvement is not a prerequisite. Keep the secondary-key query.
2. **Delete repeated result-shape checks at the downstream owner.** Toko's
   `execute_holding_mutation_batch` checks `rows.len() != row_count` immediately
   after `execute_trusted_structural_mutation_batch_rows`. The current
   [IcyDB terminal](../../../crates/icydb/src/db/session/write.rs) already owns
   exact result count and single-row projection. After qualifying the intended
   dependency, the downstream check is redundant; business row caps and ordered
   decoding remain necessary. Do not change the engine to remove this check.
3. **Do not yet add a single-write convenience API.** Toko's `insert_entity`
   and `update_entity` centralise binding/encoding/execution/decoding, but also
   run application-model preparation and advance an application data revision.
   Its whole-entity `TypedEntityMutation` is not IcyDB's generated input trait.
   Toko Miner instead uses generated batch inputs or explicit structural writes.
   The second application does not establish the same repeated generated-input
   single-write problem. Preserve those distinct needs rather than create a
   second facade or route every single write through a one-item batch.
4. **Document and qualify post-publication failures.** Toko's single-write
   helper advances its application revision only after decoding; a decoder
   failure after commit would skip that advancement. This is a conditional
   downstream failure-window concern, not a reproduced production failure.
   Likewise do not infer rollback from errors after Toko Miner's action batch.
   Review these application policies before simplifying result handling.

The scoped stale-path scan also found a comment in Toko's persistence trait
claiming durable installation is blocked pending versioned migration support.
That is not a current IcyDB release requirement and must not justify adding a
predecessor reader or compatibility API. No such mechanism is introduced here.
