# IcyDB 0.214 Final Closeout Audit

Date: 2026-07-29

## Verdict

**Ready to push.**

The tagged 0.214.0 implementation had one release-blocking defect: the
65,536-record Identity lifetime ceiling was enforced independently by each
schema store during publication even though the accepted contract defines one
combined database-wide ceiling. Quick integrity would have detected an
over-cap multi-store database only after publication. The closeout worktree
now performs a complete projected-inventory check across every registered
store before publishing any schema candidate or application receipt.

Two evidence gaps and two release-record inaccuracies were also corrected:

- a direct stale-two-cursor proof now demonstrates conflict, non-consumption
  and exact advance-identity replay;
- a direct multi-owner preflight proof now demonstrates that one stale owner
  rejects the complete set without changing any owner;
- final Wasm measurements and hashes were rebuilt after the correction;
- the detailed changelog no longer claims that release tooling made no
  dependency-version changes.

No open blocker or unresolved design decision remains.

## Accepted authority and exact-width enforcement

`Identity` is not a scalar or Serial type. It is represented as
`FieldInsertGeneration::Identity` on an accepted field. Proposal validation,
macro validation and accepted snapshot validation independently require:

- exactly `Nat8`, `Nat16`, `Nat32`, `Nat64` or `Nat128`;
- one required, non-null, scalar field;
- the sole primary-key field;
- no default, managed policy, competing generator, repetition, relation or
  composite-key position.

The accepted field kind is carried into the state owner and statement cursor.
`identity_kind_maximum` supplies the exact lifetime maximum. Values for Nat8
through Nat64 materialize through the maintained `Nat64` runtime value and are
checked against their narrower accepted maximum; Nat128 materializes through
the maintained `Nat128` value. There is no Nat64 inference or fallback.

Generated typed insert inputs omit the database-owned field. The generated
Rust `Default` implementation uses only a placeholder and never invokes
`Identity::next`. Direct proposal lowering uses the same accepted eligibility
checks as generated fragments. The current accepted schema codec and
fingerprint bind the Identity variant exactly. Ordinary reconciliation rejects
policy addition, removal, relocation, kind change and generator change;
explicit migration remains required.

Accepted schema is the runtime authority throughout allocation, inspection and
description. Generated `EntityModel` data is used only to compose/lower
proposals and typed adapters; no runtime reconstruction fallback was found.

## Shared pre-key allocation and frontend convergence

`AcceptedPreKeyInsert` carries accepted entity identity, unresolved field
intent and a bounded `u32` input ordinal but no caller-authored `DataKey`.
`execute_accepted_structural_save_batch_inner` opens at most one cursor per
participating owner, assigns values in admitted input order, derives the
storage key from the final row, and proves equality among:

- accepted owner/entity;
- generated field ID and row slot;
- exact scalar primary-key value;
- storage key;
- input ordinal and contiguous allocation position.

The same path is reached by generated typed inserts, dynamic structural
inserts, typed and structural batches, SQL omission, explicit SQL `DEFAULT`
and multi-row SQL `RETURNING`. The maintained lifecycle test commits these
frontends against one owner and observes one monotonically increasing
high-water.

Caller-authored typed, structural and SQL numeric values reject. Updates do
not allocate. Existing-row replacement preserves the current Identity;
absent-row replacement rejects rather than becoming an insert. Deletes do not
allocate or permit reuse. Recovery and derived index/relation rebuild use
separate commit-preparation modes and never enter the cursor path. SQL and
structural database writes do not call application normalizers or validators.

No authored-field bypass, keyed insert proxy, save-as-insert route,
frontend-specific generator or duplicate exact-width allocator was found.

## Non-consumption and stale publication

Tentative allocation remains statement-local until all final-row, accepted
constraint, uniqueness, relation/index preflight, resource admission,
precommit callback and commit preparation checks succeed. A rejected
precommit callback leaves both rows and high-water unchanged; the next
accepted statement reuses the first uncommitted candidate.

The write path is synchronous between recovered-state inspection and marker
publication. There is no await, yield, re-entrant application call or
externally visible state mutation in that interval.

Immediately before marker publication,
`preflight_identity_range_applies` re-reads every participating owner and
compares its complete expected high-water. The preflight is a read-only pass
over the entire set; application occurs only after every comparison succeeds.
A stale member returns typed `Conflict/Identity`, performs no invisible retry
and leaves every owner untouched. The new direct multi-owner regression is at
`crates/icydb-core/src/db/executor/mutation/commit_window.rs:1530`.

## Durable state and lifecycle

The durable owner tuple uses accepted database incarnation, entity tag and
field ID. Schema publication validates physical store placement and creates
one explicit active zero-state record atomically with the accepted candidate.
Missing active state never means zero.

The canonical high-water is `u128` for all widths. Removing a declaration
converts its active record to a retained retired record. Candidate cleanup,
snapshot replacement, live checkpoint recovery, journal replay and canonical
fold retain retired entries. An active/retired collision or any attempt to
reuse a retired owner fails closed.

The combined active-plus-retired database lifetime bound is exactly 65,536.
The original HEAD checked this only against each store-local projected
inventory. The correction now:

1. asks every affected store for its complete projected retained inventory;
2. reads the validated retained inventory for every unaffected store;
3. checked-adds those counts against the database limit;
4. rejects before application-receipt or candidate publication.

The exact combined boundary succeeds; the next cross-store owner returns
`Unsupported/Identity`. Per-store decoding bounds remain as defense in depth.
The corrected publication boundary is
`crates/icydb-core/src/db/schema/application.rs:603-752`; the exact boundary
test is at `crates/icydb-core/src/db/schema/application.rs:1583`.

Full destructive recreation is the only V1 reset and establishes a new
database incarnation. Restore/import remains outside 0.214; no existing path
silently omits or reconstructs Identity state.

## State, marker, journal and replay proof

The current Identity state record is exactly 104 bytes:

- magic `ICYIDST!`;
- version `1`;
- database incarnation, entity tag, field ID and exact kind;
- lifecycle;
- `u128` high-water;
- explicit absent/present last-applied advance identity;
- CRC32C.

The decoder requires exact length before decoding, validates checksum and
every enum/tag/canonical absent field, and bounds inventory growth before
insertion. Malformed or future records fail closed.

The current journal range record is exactly 65 bytes:

- record tag;
- database incarnation;
- entity tag and field ID;
- expected and new `u128` high-water;
- nonzero redundant `u32` count.

Journal batch validation requires one exact ordered row-put set per owner and
proves the sequence equals
`expected_high_water + 1 ..= new_high_water`. It rejects duplicates, gaps,
deletes, wrong key shapes, wrong entity/owner, row/key divergence, ordering
drift and count drift. Duplicate owner ranges across batches reject.

Replay identity is `(commit marker, journal batch, journal sequence, record
ordinal)`. `current == new` is idempotent only when the persisted
last-applied identity exactly matches. A different or older advance at the
same numeric high-water is corruption. The stale-two-cursor regression at
`crates/icydb-core/src/db/schema/store/tests.rs:789` proves both stale
conflict and exact-identity replay.

## Recovery and interruption matrix

The four maintained interruption cases are sufficient because they represent
the four materially distinct durable observations:

1. marker persisted, journal absent;
2. journal published, rows absent;
3. rows published, Identity state not materialized;
4. Identity state materialized, fold/cleanup incomplete.

Journal append, each live projection apply and the database-control writes are
atomic at the represented boundaries. Later canonical row fold, canonical
Identity fold, fold-watermark update, marker clearing and readiness rebuild
all move the same exact marker-authorized evidence forward and expose no new
allocator decision. The recovery scenario interrupts at every listed state,
then enters through a new guarded mutation, proves the next exact value,
forces a final recovery/rebuild and verifies clean Quick and Deep row
inspection.

The implementation distinguishes committed high-water proven by marker and
journal evidence from materialized high-water in the live state record.
Guarded re-entry finishes authoritative recovery and makes stores quiescent
before opening another cursor. No regeneration, `MAX(id)` reconstruction,
numeric-only replay, rewind, duplicate allocation or derived-work allocation
was found.

## Integrity and corruption precedence

Quick integrity runs after guarded recovery and enumerates every active and
retired record in every registered store. It validates database incarnation,
owner/key equality, exact accepted kind and lifecycle, active store placement,
accepted-declaration closure, duplicate/collision absence and the combined
database cap before generic store/index reporting.

Deep integrity uses the accepted Identity inspection plan. Identity key and
row-slot/primary-key/storage-key checks precede row-envelope, ordinary primary
key, constraint, index and relation findings. It classifies zero, wrong
unsigned shape, exact-domain overflow and values beyond committed high-water
without repairing or inferring state. The existing bounded continuation and
revision-invalidation contract remains intact.

The current tests cover malformed magic/version/length/checksum, wrong owner
components and kind, invalid lifecycle/high-water/last-applied combinations,
missing and duplicate state, active/retired collision, retired reuse,
candidate collision above state, invalid row/key identity, divergent range
evidence and mismatched advance identity. Identity corruption is selected
before generic uniqueness or row diagnostics where the contract requires it.

## Persisted and public format inventory

0.214 intentionally changes these current-form persisted formats:

- accepted schema V1 gains the exact `Identity` insert-generation variant and
  includes it in the accepted fingerprint;
- schema control state gains the fixed 104-byte active/retired Identity record;
- live-only schema checkpoints include the complete retained Identity
  inventory;
- journal batch V1 gains the fixed 65-byte Identity range record, including
  persisted count.

Ordinary Nat row and key encodings are unchanged. There is no old decoder,
dual-read, dual-write or compatibility alias.

The public description response changes as follows:

- `EntitySchemaDescription` gains
  `identity: Option<Box<EntityIdentityDescription>>`; `Box` does not add a
  Candid wrapper, and ordinary entities return `None`;
- `EntityIdentityDescription` exposes field, `Identity::next`, exact unsigned
  kind, minimum, maximum, committed high-water, remaining capacity and
  exhaustion;
- integrity adds finding kinds `InvalidIdentityValue` and
  `IdentityHighWaterExceeded`, plus verifier family `IdentityState`.

No unrelated response variant or endpoint signature was changed.

## Findings and corrections

### Release blocker — corrected

**Database lifetime capacity could be exceeded across stores.**

At audited HEAD,
`crates/icydb-core/src/db/schema/identity_state.rs:608` bounded only one
store-local projected map, while
`crates/icydb-core/src/db/integrity.rs:153` later summed the database-wide
inventory. Two individually valid stores could therefore publish more than
65,536 retained owners and turn the database corrupt after publication.

Correction: database-wide projected preflight, exact cross-store boundary
test and typed failure, before any schema/application publication.

### Test-evidence gaps — corrected

- The stale-state test used a constructed range rather than two cursors.
  It now opens two cursors at the same state, tentatively allocates the same
  range, commits one, rejects the stale one and requires exact replay identity.
- Multi-owner stale comparison had architectural coverage but no direct
  regression. A two-store test now proves the whole set is read-only when one
  owner is stale.

### Release-record inaccuracies — corrected

- Wasm sizes and hashes were rebuilt after the production correction.
- The detailed changelog now distinguishes “Identity adds no dependency” from
  the release tooling's updates of existing `http`, `rustls` and
  `tokio-macros` lockfile packages.

No uncorrected finding remains.

## Documentation and release readiness

The root and detailed changelogs, README/rustdoc, active Identity,
write-admission, atomicity, durability, SQL-subset and persisted-format
contracts agree on:

- five exact unsigned widths, with Nat64 as ordinary guidance rather than an
  exclusive implementation;
- start at one, step one, no cycle or caller override;
- generated-always insert ownership;
- no consumption by rejected writes and no reuse after deletion;
- possible gaps after committed deletion;
- entity/store-local allocation;
- no smaller-physical-storage promise for narrow kinds;
- SQL omission, `DEFAULT` and `RETURNING`;
- deferred SQL DDL authoring;
- ordinary Nat primary keys remaining caller-authored;
- ULID as the decentralized/cross-system alternative;
- retained retirement history;
- Toko as a separate post-closeout project, not a release gate.

Active docs contain no stale Sequence or Nat64-only authority. The changelog
covers all six slices without a duplicate patch entry or compatibility claim.
