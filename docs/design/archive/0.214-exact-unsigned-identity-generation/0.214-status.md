## Slice 1 — Accepted Policy And Owner Identity

Status: complete.

The source macro now admits:

```rust
field(
    name = "id",
    value(item(prim = "Nat64")),
    generated(insert = "Identity::next")
)
```

The same declaration is valid for `Nat8`, `Nat16`, `Nat32`, `Nat64`, and
`Nat128` only when the field is the sole non-null scalar primary key. The
macro rejects other primitive kinds, nullable or repeated fields, non-primary
placement, composite primary keys, database defaults, managed fields, and
unknown generator paths. Generated typed insert inputs omit the identity field;
decoded rows retain its exact Rust integer type. Full entity `Default` uses
only the ordinary zero-valued Rust placeholder and never calls the declarative
generator token.

The public proposal contract continues to use its existing
`FieldInsertPolicy::Generated` and `SchemaCapability::GENERATED_VALUES`
vocabulary. Exact scalar kind resolves the generator: unsigned bounded Nat
kinds lower to `FieldInsertGeneration::Identity`, while `Ulid` and `Timestamp`
retain their existing variants. Directly constructed proposal fragments enforce
the same eligibility rules as the source macro.

Accepted snapshots now:

- persist and decode the `Identity` enum variant in the current version-1
  accepted-schema format;
- validate the complete exact-kind, origin, nullability, default, management,
  and sole-primary-key contract before becoming runtime authority;
- include the policy in accepted schema bytes and therefore in semantic
  fingerprints; and
- reject policy drift through the typed field-write-policy transition detail,
  so adding, removing, or changing Identity requires an explicit migration.

Durable allocation ownership is frozen as
`(DatabaseIncarnationId, EntityTag, FieldId)` inside the selected physical
store namespace. Proposal source keys resolve those accepted IDs but are not
operational identity. Slice 2 introduces the persisted state record that
materializes this owner contract.

This slice does not implement allocation. If an accepted identity reaches the
ordinary write generator before Slice 3, execution fails closed at the
unsupported boundary. Only compile fixtures declare Identity in this slice;
deployed maintained canister schemas do not.

## Slice 2 — Bounded Operational State Lifecycle

Status: complete.

Each accepted Identity owner now has one explicit current-form operational
record. The fixed-width, checksummed record binds the database incarnation,
accepted entity and field IDs, exact unsigned kind, active/retired lifecycle,
u128 materialized high-water, and optional last-applied marker/batch/sequence
identity. Every newly accepted owner starts at explicit zero. Missing,
malformed, wrongly owned, wrong-kind, or duplicate active state is corruption.

Schema publication owns the lifecycle transition. Adding an owner creates its
zero record under the same marker boundary; allowed removal changes it to a
retained retired record; and any later reuse of that accepted owner rejects.
The schema-store control namespace never deletes identity history during
candidate cleanup. Journaled stores derive and apply the same transition during
live replay and canonical fold.

Live-only schema stores retain the complete bounded inventory beside their
accepted candidate in the existing durable schema checkpoint. Upgrade rebuild
therefore restores active and retired history rather than reconstructing zero
from the accepted model. Marker replay derives the checkpoint and heap-store
transition from the same current-form transition function.

The combined active-and-retired inventory is bounded at 65,536 records per
database. The exact boundary remains readable; the next new owner fails with
the typed unsupported Identity classification. This slice still does not
allocate values or advance high-water state; Slice 3 introduces pre-key
allocation and Slice 4 owns committed range advancement.

### Format And Compatibility

- Identity state uses one 104-byte fixed-width, checksummed current-form record
  in schema-store control namespace 4.
- The live-only accepted-schema checkpoint now includes the canonical sorted
  identity inventory under its existing bounded checksum envelope.
- No experimental Sequence state, decoder, alias, reconstruction path, or
  compatibility fallback is retained.
- This is a deliberate pre-1.0 persistence hard cut; incompatible development
  state must be recreated.

## Slice 3 — Accepted Pre-Key Allocation

Status: complete.

Keyless inserts now enter one accepted pre-key candidate carrying the selected
entity, exact unresolved field intent, and stable `u32` input ordinal. The
candidate has no caller-authored data key. One statement-local cursor reads the
active accepted Identity owner once, allocates from its materialized u128
high-water mark in input order, and converts through one exact unsigned helper:
`Nat8` through `Nat64` materialize as bounded `Value::Nat64`, while `Nat128`
materializes as `Value::Nat128`. Addition, width, and statement-count overflow
reject before durable preparation.

The shared accepted insert resolver consumes the tentative allocation for the
Identity slot. After canonical row materialization, execution proves that the
accepted owner, field slot, input ordinal, row-slot value, and final scalar
primary key all identify the same allocation before constraint and commit
preparation continue. No typed, SQL, or structural frontend owns a second
generator.

Typed insert patches omit the database-owned field. SQL omission and explicit
`DEFAULT`, including `RETURNING`, reach the same accepted generation path;
explicit numeric SQL values still reject at SQL authorship admission.
Structural omission follows the same path. An absent-row replace with a chosen
identity rejects rather than becoming save-as-insert, while existing replace
and update retain their pre-existing keyed semantics and allocate nothing.

Slice 4 still owns range aggregation, stale-state comparison, commit-marker and
journal encoding, and durable high-water advancement. Therefore Slice 3
deliberately stops an identity-bearing batch after complete row/precommit
materialization but before marker publication. The temporary typed Identity
boundary is unsupported/Identity: it publishes no row, advances no state, and
retries from the same value. Maintained deployed canister schemas still do not
declare Identity, so ordinary writes are unchanged.

### Format And Compatibility

- No new persisted record, marker field, journal record, or compatibility

- The existing current-form 104-byte Identity state remains unchanged and

- Candidate count is checked into `u32` before allocation, matching the range

## Slice 4 — Stale-Safe Range Commit And Replay

Status: complete.

Every successful identity-bearing statement now aggregates its tentative
allocations into one contiguous range per accepted owner. The range binds the
immutable owner, expected and new u128 high-water values, and a redundant
nonzero `u32` allocation count. Commit preparation proves that the marker batch
contains the exact ordered row-key set
`expected_high_water + 1..=new_high_water`; duplicates, gaps, deletes,
out-of-order values, count drift, and non-scalar unsigned keys fail closed.

Immediately before marker publication, every participating store re-reads its
active identity record and compares the complete expected high-water set.
Live-only stores compare the matching durable checkpoint as well. A stale
comparison returns typed `Conflict`/`Identity` before a marker or row is
published. Rejection after tentative materialization still consumes nothing,
and the next admitted statement reuses the first uncommitted candidate.

Each range is a current-form journal record in the same marker-owned batch as
its rows. Its exact `IdentityAdvanceId` is derived from commit-marker ID,
journal-batch ID, journal sequence, and canonical record ordinal rather than
duplicated in the record. First materialization requires the recorded expected
high-water. Repeated replay or fold accepts the new value only when the
persisted last-applied identity matches that exact tuple; numeric equality
alone is Identity corruption.

Journaled stores append the range with their row records, update the live
projection, fold it into canonical schema state, and rebuild without calling
the allocator. Heap stores use a sequence-zero marker batch with the same row
and range proof, and durably advance the accepted live-schema checkpoint before
materializing the volatile state. Guarded recovery synchronizes that checkpoint
and replays the exact marker, so interruption cannot expose a reusable
committed value.

Typed, SQL, and structural omission now complete real commits and return the
generated values. Explicit identity authorship, regeneration, and absent-row
replace remain rejected. Update and replacement of existing rows allocate no
range. Replay and derived rebuild continue to use the existing
`CommitPrepareMode` authority and never allocate.

### Format And Compatibility

- Journal batch format version 1 gains one current Identity range record
  carrying owner identity, expected/new u128 high-water values, and the
  redundant `u32` count.
- The existing fixed-width Identity state record now materializes the range's
  exact journal-envelope advance identity; its byte format and size do not
  change.
- Live-only checkpoints update the existing current-form identity inventory
  under the marker boundary.
- No Sequence decoder, prior range record, numeric-only idempotence fallback,
  state reconstruction, or compatibility alias is retained.
- This is a deliberate pre-1.0 persistence hard cut; incompatible development
  state must be recreated.

## Slice 5 — Recovery, Corruption, And Integrity

Status: complete.

Marker recovery now models committed and materialized high-water as distinct
facts. The persisted Identity record remains the materialized view; while a
marker is authoritative, its exact range supplies the committed value. A
pending record may equal the marker's expected value, and an already applied
record is idempotent only when its numeric high-water and complete
`IdentityAdvanceId` both match. Materialized state can never exceed committed
state, and zero versus nonzero high-water must agree with absent versus present
last-applied evidence.

The journaled commit path has test-only interruption boundaries after marker
persistence, journal publication, row publication, and state materialization.
Each boundary leaves the marker authoritative without running the in-process
rollback guard. The next ordinary mutation enters guarded recovery first,
folds and rebuilds forward, verifies the exact row/range effect, and only then
opens a new statement cursor. The four-boundary scenario produces the exact
sequence 1 through 8 without gaps, reuse, or extra allocation.

Quick integrity now enumerates every registered store's complete active and
retired Identity inventory after guarded recovery. It validates current-form
records, accepted closure, database incarnation, physical store placement,
database-wide owner uniqueness, and the combined 65,536-record lifetime bound.
An active/retired owner collision is Identity corruption before any generic
store diagnostic.

Deep row integrity carries the accepted Identity field ID, name, and exact Nat
kind in its compiled inspection plan. Its new Identity-state verifier runs
after data-key decoding but before row-envelope, primary-key, constraint,
index, or relation checks. Zero, wrong unsigned key shape, accepted-width
overflow, and any live key above committed high-water are therefore reported
as typed Identity corruption rather than hidden by generic uniqueness. Normal
generated insertion likewise classifies an already occupied generated key as
state-behind-row corruption before the ordinary key-exists error.

The recovery fixture now includes a real derived index. Final recovery clears
and rebuilds its witnesses from authoritative rows while high-water remains
eight, then passes both Quick control inspection and the bounded Deep row page.
Recovery and derived work never call the statement allocator. No prototype
runtime instrumentation remains; interruption controls exist only under
`cfg(test)`.

### Format And Compatibility

- Identity state and journal byte layouts remain the current Slice 4 formats.
- Current-form state now rejects a nonzero high-water without last-applied
  evidence and zero high-water with such evidence.
- Integrity Candid vocabulary gains `InvalidIdentityValue`,
  `IdentityHighWaterExceeded`, and the `IdentityState` verifier family.
- There is no persisted committed-state duplicate, recovery inference,
  MAX-row reconstruction, compatibility fallback, or disabled repair lane.

- Warnings-denied `icydb-core` Clippy passes across all targets and features.
- `icydb-core` checking passes without default features.

## Slice 6 — Frontend Parity, Introspection, And Closeout

Status: complete.

Accepted schema description now carries one optional boxed Identity descriptor.
It exposes the field, fixed `Identity::next` generator, exact unsigned kind,
minimum and maximum lifetime values, committed high-water, remaining capacity,
and exhaustion state. The descriptor is assembled only from the accepted
inspection plan and recovered quiescent control state. Ordinary entities retain
`None`, and boxing keeps unrelated `SqlStatementResult` variants from paying
the descriptor's in-memory size while preserving the Candid shape.

The maintained frontend lifecycle proves structural batch, dynamic structural,
typed adapter, SQL omission, SQL `DEFAULT`, multi-row `RETURNING`, explicit
authorship rejection, update rejection, and absent-row replacement rejection
against one accepted Nat64 owner. The same test observes description at zero
and after the shared committed range. Exact Nat8 exhaustion description and
out-of-domain rejection are covered separately.

The README and Identity, write-admission, atomicity, durability, SQL-subset,
and persisted-format contracts now document all five exact widths, Nat64
guidance, GENERATED ALWAYS semantics, non-consumption on rejection,
non-reuse after deletion, entity/store locality, ULID guidance, SQL DML parity,
SQL DDL deferral, marker recovery, and current-form persisted owners. No active
Sequence alias, Serial type, `auto_increment` surface, or Nat64-only Identity
example remains.

## Final Closeout Audit

The adversarial closeout found and corrected one release blocker: publication
bounded retained Identity owners per store while the contract requires one
combined database-wide 65,536-record limit. Schema application now checks the
complete projected inventory across every registered store before publishing
any candidate or receipt. Direct stale-two-cursor and stale multi-owner
regressions were also added.

The final verdict is **ready to push**. The complete evidence, corrections,
validation and remaining user-owned checks are recorded in
