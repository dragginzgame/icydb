# IcyDB 0.242 Exact Indexed Range Cardinality

Status: CLOSED — PATCH 2 MEASURED NO-BUILD — KEEP PUSHED 0.242.0 RUNTIME

Last updated: 2026-08-26

Exact released predecessor:
`v0.241.0` at `2dea44c7547cbdc98e1bf2f9fab45dd3da915894`.

## Outcome

Let one planner-proved, row-equivalent SQL `COUNT` consume exact synchronized
leading-index multiplicities over one canonical range. Equivalent SQL syntax
must converge on one immutable exact-cardinality target; no query spelling,
comparison operator or aggregate adapter may acquire its own execution branch.

The slice extends the existing exact-or-prepared global-count owner. It adds
no public SQL syntax, accepted-schema authority, index-selection authority,
cache slot, persisted state, background work, compatibility path or execution
mode. If exact range evidence is unavailable, the existing prepared executor
remains the only fallback.

## Current Baseline

PocketIC 15.0.0 and one production-profile SQL performance Wasm. The artifact
is 4,607,414 raw bytes with SHA-256
`01dddf8800aa25ff74e2c4320f6771556db24ed64d7842b2f99c550774b66242`.

Every ranged form uses one selected accepted-index range. The five equivalent
512-row forms differ by at most 239,658 cold instructions while retaining
identical physical work. True warming removes only 0.47M–0.74M instructions.
The dominant work remains approximately 15.8M store instructions and
6.6M–6.7M executor instructions attached to 512 row and index reads.

The exact controls establish an observed sub-1M metadata-only floor, not a
promise that range summation will have identical cost. The realistic release
target allows 2M cold instructions, leaving more than 21M absolute saving for
the principal case. The one-sided full-range observation establishes a second
hostile slope rather than authorization to optimize a separate query.

## Comparable Engine Structure

SQLite handles a ranged `COUNT(*)` through a generic covering-index range scan:
seek to the lower edge, test the upper edge, invoke the aggregate step for each
matching index entry and advance. Its special bare `COUNT(*)` and indexed
`MIN`/`MAX` operations are physical primitives selected after semantic
analysis, not branches keyed to SQL strings. See SQLite's
[query planner](https://www.sqlite.org/queryplanner.html),
[optimizer overview](https://www.sqlite.org/optoverview.html) and
[bytecode reference](https://www.sqlite.org/opcode.html).

IcyDB should follow the same ownership principle while using a capability
SQLite does not have: exact generation-matched per-leading-component
multiplicity metadata. The optimization belongs at the exact-cardinality
physical boundary, not in parsing, result projection or the generic range
scanner.

## Frozen Admission Contract

Patch 1 may admit a query only when all facts below are already proven before
exact execution:

1. The command contains exactly one global aggregate terminal and no grouping,
   `HAVING`, aggregate `FILTER`, `DISTINCT`, ordering, limit, offset or cursor.
2. The aggregate is row-equivalent: `COUNT(*)`, a provably non-null literal
   such as `COUNT(1)`, or `COUNT` of a direct non-nullable field. Nullable or
   expression arguments remain prepared.
3. The normalized predicate produces exactly one planner-selected
   `IndexRange` access path and no residual predicate, union, intersection or
   additional access child.
4. The range field is a direct non-nullable `Int32` field and the first key
   component of the selected accepted user index.
5. The accepted index is complete: it is not filtered and every admitted
   logical row contributes exactly one key under all suffix omission rules.
6. The range has at least one bound. Inclusive, exclusive and unbounded outer
   bounds are represented by the existing canonical bound model.
7. Every bound has already been normalized, type-checked and encoded by the
   existing planner/lowering authority. Execution performs no coercion or
   encoding.
8. The selected accepted index and its physical generation are carried in the
   target. Execution cannot reselect another compatible index.

`BETWEEN`, reversed operands, `>`, `>=`, `<` and `<=` are not separate
admission cases. They qualify only when existing normalization and range
planning produce the same canonical contract. Both-unbounded counts continue
to use the existing exact entity target. Equality and finite `IN` continue to
use the existing exact prefix targets.

Text, nullable fields, non-leading range components, equality-prefix plus
range, expression indexes, filtered indexes, disjoint ranges, residual
predicates and compound logical predicates are outside Patch 1. The internal
target shape may remain type-neutral, but no unmeasured scalar kind may be
admitted.

## Singular Target And Authority Chain

The intended shape is illustrative:

```rust
struct UserIndexFirstComponentCardinalityRange {
    index_id: IndexId,
    lower: Bound<Vec<u8>>,
    upper: Bound<Vec<u8>>,
}

enum ExactCardinalityTarget<'a> {
    Entity,
    UserIndexPrefixes(&'a [UserIndexPrefixCardinalityKey]),
    UserIndexFirstComponentDistinct(IndexId),
    UserIndexFirstComponentRange(&'a UserIndexFirstComponentCardinalityRange),
}
```

Names and borrowing may change during implementation, but ownership may not:

```text
normalized query facts
  -> structural planner selects one accepted IndexRange
  -> existing access lowering encodes its canonical bounds
  -> fingerprint-bound compiled command retains one exact-or-prepared target
  -> exact-cardinality executor validates target identity/readiness
  -> StoreHandle asks IndexStore for generation-matched range multiplicity
  -> one canonical COUNT result or existing prepared fallback
```

The range contract belongs beside `UserIndexPrefixCardinalityKey`, because it
is an immutable lookup into index-owned exact metadata. It may contain only the
accepted physical index identity and already encoded component bounds. It may
not contain schema references, generated models, SQL expressions, a store
handle, mutable state or freshness claims.

The existing compiled global-aggregate slot remains singular. Its cached plan
may be exact entity cardinality, exact prefix cardinality, exact first-component
distinct cardinality, exact first-component range cardinality, or the existing
prepared plan. No nested fallback cache or neighboring range cache is allowed.

Every cache entry remains bound to `SqlCompiledSchemaFingerprint`. Publication
creates a new outer compiled command under the existing cache lifecycle. A
retained old command cannot refresh its target, prove current schema or select
a replacement index.

## Exact Metadata Operation

For one pinned accepted root, complete accepted user index and synchronized
row/index generation, the existing invariant remains authoritative:

> Every present `first_component_counts` key represents exactly one canonical
> non-empty leading value present in the logical row set; its stored count is
> that value's exact logical-row multiplicity; every admitted logical row
> contributes exactly one physical key; and no key or metadata contribution
> exists without its logical row.

The new operation iterates only keys belonging to
`(IndexKeyKind::User, IndexId)` whose encoded first component lies within the
carried bounds. It sums stored multiplicities, not metadata-key count.

It must:

- reject a non-user or authority-mismatched target as an invariant failure;
- return unavailable when metadata is absent, undecodable, unsynchronized or
  the accepted index is not Ready;
- distinguish inclusive, exclusive and unbounded edges exactly;
- stop at the first different index identity or first key above the upper edge;
- reject zero multiplicity and arithmetic overflow as store invariants;
- return exact zero only from a positively initialized, decodable,
  generation-matched map after a complete bounded inspection;
- report both the multiplicity sum and metadata entries examined; and
- expose no map, iterator, raw metadata key or mutable reference above
  `IndexStore`.

Work scales with distinct leading components inside the range rather than
matching rows. A duplicate-heavy 512-row range may inspect only a few metadata
keys; the hostile all-unique fixture may inspect 512. A full-range all-unique
fixture may inspect 2,048. All three shapes require explicit measurement.

## Resource And Failure Semantics

The metadata probe is speculative until it proves the complete range.
`stop_after` derives from currently remaining canonical metadata-work capacity,
not configured maxima. The operation must distinguish complete from truncated
inspection without guessing from the accumulated row count.

| Outcome | Required action |
| --- | --- |
| Complete exact sum within budgets | Atomically charge metadata work plus one canonical result row/32-byte result, then project `Value::Nat64` |
| Metadata unavailable or bounded probe incomplete | Retain only real diagnostic probe work and enter the existing prepared fallback |
| Accepted target/index identity mismatch, impossible bound shape, zero multiplicity or checked overflow | Return the existing invariant/corruption error; never hide it with fallback |
| SQL shape ineligible | Cache and execute only the prepared plan; no exact probe |

No partial semantic charge may leak into prepared fallback. Exact success must
preflight and commit its complete charge bundle atomically through the existing
execution/request budget owner. A failed multi-category charge cannot consume
one category before another fails. The exact attempt may record real local
instructions and metadata entries examined, but it may not consume row-scan or
aggregate-ingestion work that did not occur.

The completed sum is converted to the canonical SQL `COUNT` result with checked
arithmetic. Saturation, wrapping and platform-width-dependent casts are
forbidden.

## Corruption And Lifecycle Outcomes

The range operation inherits, and may not weaken, the exact prefix/distinct
metadata authority established in `v0.240.1`:

| State | Required outcome |
| --- | --- |
| Logical row removed while index/metadata remains | Generation mismatch makes exact evidence unavailable; prepared execution supplies its existing result/error |
| Physical index entry removed while row remains | Synchronization is cleared; prepared fallback runs |
| Orphan index entry inserted | Synchronization is cleared; no exact overcount |
| Malformed component or optional metadata decode | Exact evidence unavailable; prepared fallback runs |
| Forged root, entity, index or generation identity | Typed invariant/corruption failure |
| Journal metadata not materialized after reopen | Prepared fallback; no startup scan or repair |
| Publication or recovery | Existing owner installs/reconstructs one complete authority state; no derivative cache repair |

Successful insert, update, delete, rollback, replay and fold must preserve the
row/index/metadata invariant atomically or make exact evidence unavailable.
Patch 1 adds no persisted range count, recovery job, timer or prewarm path.

## Alternatives

| Option | Decision |
| --- | --- |
| Keep prepared row/index traversal | Correct fallback, but retains 23.4M for the measured 512-row family and 92.4M for the full one-sided range |
| SQLite-style covering index count | Reject for Patch 1: removes row gets but still visits every index entry and requires a separate accessed-corruption proof |
| One exact target per SQL spelling/operator | Reject: duplicates normalization and creates planner/executor disagreement risk |
| One canonical first-component range target | Selected: reuses existing range lowering, exact metadata authority and singular command slot |
| Generic exact aggregate framework | Reject: current metadata proves counts only; `SUM`, `AVG` and arbitrary aggregates need different correctness state |
| Persisted cumulative/range counts | Reject: adds stable format, mutation fanout, recovery and authority state without evidence |

## Required Proof Matrix

Admission and equivalence:

- the five measured equivalent forms select one exact target class;
- inclusive/exclusive lower and upper edges, one-sided ranges, `BETWEEN` and
  reversed operands;
- negative, zero, positive, `Int32::MIN` and `Int32::MAX` edges;
- empty input, no matches, one match, duplicate-heavy and all-unique data;
- single-field and complete compound indexes with the range field first;
- a second compatible index proves no runtime reselection;
- nullable counted expression, nullable range field, Text, expression,
  non-leading component, equality-prefix range, partial index, residual,
  `OR`, grouped, ordered, windowed, `FILTER` and `DISTINCT` shapes fallback;
- SQLite result equality, alias/column metadata and `Nat64` result equality.

Authority and lifecycle:

- cold miss and true-warm compiled-command hit;
- selected metadata unavailable while another compatible index is available:
  prepared fallback without reselection;
- metadata becoming available later through the existing lifecycle;
- target publication, unrelated publication, old retained request and new
  request after publication;
- fingerprint mismatch, missing/mismatched root and accepted index generation;
- heap and journaled stores, journal replay, fold, projection reset, same-Wasm
  upgrade, reinstall and unmaterialized journal metadata;
- successful and rolled-back insert/update/delete, including transitions across
  both range edges and deletion of the final value.

Budgets and corruption:

- complete and truncated metadata probes at exact remaining-budget boundaries;
- atomic success charge and no semantic charge surviving fallback;
- checked multiplicity, examined-count, total-count and result conversion;
- zero multiplicity, malformed component, missing row, missing index entry,
  orphan index entry, borrow conflict and forged target identity;
- cached success followed by publication and cached prepared fallback followed
  by metadata availability.

Regression and delivery:

- existing exact entity, prefix, indexed distinct and prepared aggregate
  controls retain result, physical work and instruction ceilings;
- ordered scalar DISTINCT group seek and indexed extrema remain unchanged;
- focused no-default, SQL-only, diagnostics and maintained all-feature checks;
- raw/gzip Wasm, Candid, exports, generated API, stable extent and package
  version evidence;
- `cargo fmt`, diff checks and architecture invariants.

## Implementation Verdict

`DESIGN VIABLE — PATCH 1 IMPLEMENTED WITHIN FROZEN GATES`

The released cost is current, absolute and physical-work-driven; five SQL
spellings already converge on one access shape; existing exact multiplicity
metadata is the identified removable owner; and one conservative target can
reuse the singular authority, cache and fallback chain. The design is rejected
if implementation cannot stay inside that shape.

## Implementation Closeout

Patch 1 uses the conservative shape above with one simplification: no new
range-target type was necessary. The existing cached-plan enum directly owns
the accepted `IndexId` and two encoded component bounds. Target construction
reads those bytes once from the canonical already-lowered raw range keys while
using the normalized semantic bounds only to retain inclusive, exclusive or
unbounded shape. It performs no second encoding or index selection.

Exact indexed DISTINCT and exact indexed range count share one bounded walk of
the existing `first_component_counts` authority. Range execution returns the
checked multiplicity sum; DISTINCT returns the checked examined-key count.
Both remain generation-matched and use the same accepted-index identity,
budget owner, compiled-command slot and prepared fallback.

## Patch 2 Cleanup Audit Closeout

The cleanup audit tested the exact source seams that appeared repetitive after
Patch 1: fingerprint-bound entry construction, prepared-plan ownership and the
cached-plan-to-executor projection. The authoritative comparison used two
separate clean source exports of pushed `0.242.0` at
`32750aeb570c8a6e7599ff5eb175f33d10242ed9`, Rust 1.97.1, locked dependencies,
separate target directories, the same production SQL audit canister and the
same post-link pipeline.

| Subject | Production Rust delta | Raw Wasm | Gzip Wasm |
| --- | ---: | ---: | ---: |
| Exact pushed source | baseline | 4,610,621 | 1,785,620 |
| Shared entry constructor plus borrowed prepared projection | -13 | 4,610,771 | 1,785,679 |
| Candidate delta | -13 | +150 | +59 |

The historical Patch 1 artifact was 4,610,196 raw bytes, but rebuilding the
exact pushed source in the paired audit produced 4,610,621 bytes. Reused-target
experiments were therefore discarded as non-authoritative; only the isolated
same-input pair above decides Patch 2.

The candidate failed the frozen zero-growth gate and was reverted. The
apparently duplicated cached and executable target shapes are an intentional
owned/borrowed boundary, while the small per-shape constructors compile more
compactly than the shared enum-taking wrapper in the measured production
subject.

The matched symbol-bearing predecessor audit further reduced the original
concern: `0.242.0` added three net symbols, and 2,734 of its 2,775 stripped code
bytes were attributable to the range metadata operation and atomic budget
handling. It did not add a second cache, planner, executor or fallback flow.

Verdict: `CLOSED — MEASURED NO-BUILD — KEEP PUSHED 0.242.0 RUNTIME`.
