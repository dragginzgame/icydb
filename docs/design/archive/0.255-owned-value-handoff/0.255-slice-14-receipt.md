# 0.255 slice 14 — Owned batch-input lowering

Date: 2026-09-07. Explicitly authorized after the owned-input audit. Baseline is
the complete unpushed slice 13, not published 0.255.1. Both slices belong to the
active 0.255.2 notes; Cargo versions and published notes are unchanged.

## Decision and boundaries

The four owned dynamic/typed batch loops consume requests through the existing
lowerers. Patches yield owned field intents in their admitted order; one shared
cell lowerer moves authored InputValue payloads. Owned keys enter the existing
runtime conversion without a preliminary clone. Accepted schema remains the only
runtime authority. Catalog selection, bounded counts, key-before-patch failures,
typed binding checks before field lowering, defaults, Identity, result bounds
and atomic staging are unchanged.

The hidden core typed single-write entry point now consumes its request. Direct
callers must pass it by value; there is no compatibility shim. Application-facing
typed methods already own requests and retain their signatures. The genuinely
borrowed dynamic singleton retains its existing boundary copy, then uses the
same consuming lowerer. No second lowering flow, ownership flag, cache, format,
runtime authority or execution mode is introduced.

## Native allocation evidence

A frozen copy of the baseline lowerers and the actual candidate lowerers run in
one native binary. Request construction and typed patch binding are outside the
allocation window; the complete mutation-intent lowering is inside it. Each
subject executes insert/update/replace through both dynamic and typed lowering
with scalar-only, one-blob and 128-blob inputs. Blobs contain 1,024 bytes. Three
samples of 20 invocations per cell give 2,160 checked lowerings; all 108 sample
records are stable. Output intents are checked outside the allocation window.

The two frontends have identical measured allocation counts:

| Input | Operation | Allocation requests before → after | Requested bytes before → after |
| --- | --- | --- | --- |
| Scalar only | Insert | 1 → 1 | 384 → 384 |
| Scalar only | Update / replace | 2 → 2 | 688 → 688 |
| One blob | Insert | 3 → 1 | 1,472 → 384 |
| One blob | Update / replace | 4 → 2 | 1,776 → 688 |
| 128 blobs | Insert | 130 → 1 | 139,648 → 384 |
| 128 blobs | Update / replace | 131 → 2 | 139,952 → 688 |

These are lowering allocation requests, not live-heap peaks or endpoint latency.
The 128-blob cases each save 139,264 requested bytes. Existing patch-vector and
key-target allocations remain; no capacity policy was changed to improve these
numbers artificially.

After normalizing crate hashes and compiler numeric symbol suffixes, seven cleanup
functions appear and one cleanup symbol disappears. New symbols cover owned
DynamicMutation, DynamicWriteCell, the field-name/cell tuple, its Vec and IntoIter,

destruction functions, not new semantic routes. The existing patch destructor

lowerer and unchanged dynamic/typed routing.

Attribution is explanatory, not deploy-size evidence. An initial parallel
attribution attempt reused a host helper rooted in the other temporary tree;
that comparison was discarded. Only the sequential same-path builds are used.
This does not affect the original same-path production/cycle artifacts. On
2026-09-07 the user accepted the six-function result provided the code is cleaner.
That condition is supported by the source and attribution: existing lowerers
consume owned inputs without payload clones or another execution route, while
the additional functions implement ownership cleanup. Slice 14 is ready with
this explicit exception; the original +4 numeric gate remains documented and
