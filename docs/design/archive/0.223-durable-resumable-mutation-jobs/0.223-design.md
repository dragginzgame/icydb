# 0.223 Durable Resumable Mutation Jobs

Status: accepted design authority; Patch 1 contract and baseline complete;
runtime implementation pending

Design cut: 2026-08-08

Predecessor: `v0.222.4` at commit
`2a18f0aa3aade9cd209e8cec9e040d732e35b7af`

Primary foundations:

- [0.210 Exact And Resumable Bulk UPDATE](../archive/0.210-exact-and-resumable-bulk-update/0.210-design.md)
- [0.221 Request-Bounded Query Reliability And Resumable Reads](../0.221-request-bounded-query-reliability-and-resumable-reads/0.221-design.md)

## Decision Summary

0.223 makes complete collection-wide fixed updates durable and replay-safe
without requiring an application to custody an opaque engine continuation.
IcyDB persists one canonical mutation intent, its bounded Forward/Verify
continuation, sequence, totals, and last replay receipt in the existing
excluded progress allocation.

The trusted application surface becomes:

```text
start(job_id, fixed_update_intent) -> state
state(job_id) -> state
advance(job_id, expected_sequence, idempotency_key) -> receipt
acknowledge(job_id, terminal_sequence) -> ()
```

SQL is an initial frontend for constructing the accepted fixed-update intent;
it is not persisted runtime authority. Start lowers SQL immediately into a
bounded catalog-native intent. Every later call needs only the job identity,
expected sequence, and idempotency key.

One advance performs exactly one bounded engine step. A mutating Forward step
commits the target-row batch and next progress record as one recoverable
transition. Verify is read-only with respect to target rows and can report
completion only after a full clean sweep at one unchanged durable target-store
revision.

The existing revision-strict generic `ResumableJob` remains a read and
validation protocol. It is not relaxed to permit mutations of its protected
stores. Mutation jobs use a separate type family, persisted record domain, and
advance coordinator because changing the target store is expected progress,
not proof invalidation.

IcyDB owns one-entity mutation execution and durable job correctness. It does
not own application authorization, business phases, timers, or multi-entity
workflow meaning. A rarity change may compose token-tier and scoring-state jobs
in application state, but that orchestration is outside IcyDB.

## Incident And User Outcome

The motivating collection flow currently performs eager fan-out:

1. load every vendor in the collection;
2. mutate every vendor object and call one atomic batch update;
3. load every token in the collection;
4. set every token tier and call one atomic batch update; and
5. separately load tokens and scoring rows before marking scores stale.

The token path therefore makes retained rows, staged mutations, and request
work proportional to complete collection size. A collection above roughly
10,000 tokens reaches the hard execution envelope and returns E273 instead of
durable progress.

The application also records effects one at a time immediately before
execution. If the first rarity effect fails, a later scoring effect may never
be persisted. A pending effect currently records only an effect name; it does
not identify a phase, engine job, sequence, or committed progress.

The required user outcome is:

- changing rarity commits or returns a typed durable job rather than attempting
  one unbounded fan-out;
- every call performs bounded work and returns a replayable state or receipt;
- progress survives later calls, lost responses, and ordinary canister
  upgrades that retain the current record format;
- collections larger than 10,000 tokens converge without treating a bounded
  page or E273 as completion;
- tier reset and score invalidation cannot be lost because an earlier phase
  failed; and
- applications supply no batch-size tuning or continuation-storage code.

## Current IcyDB Reality

0.210 already provides the correct row-level convergence engine:

- one journaled target entity;
- deterministic fixed authored assignments;
- authoritative primary-key traversal;
- at most 256 scanned keys and 64 staged updates per Forward call;
- one operation timestamp retained across the whole operation;
- a bounded opaque continuation binding operation, target, accepted schema,
  scope, patch, checkpoint, and batch-policy identity; and
- a stable-revision Verify phase that restarts Forward on revision drift or
  residual work.

Its public custody contract is intentionally incomplete for the new outcome.
The application must persist the prepared continuation outside the target store
before the first mutation, supply the same SQL and operation identity on every
resume, and safely replace the continuation after each call. A lost response
between a committed row batch and application custody can leave the application
without the returned next continuation.

0.221 provides a durable generic progress store with:

- nonzero 32-byte job identities;
- bounded idempotency keys;
- sequence-checked advancement;
- exact lost-response receipt replay;
- terminal acknowledgement; and
- a physically separate stable-memory allocation excluded from source proofs.

That coordinator verifies the same read-set proof both before and after its
operation closure. If the closure mutates a protected target store, the second
comparison correctly invalidates the job. Treating that invalidation as
mutation progress would weaken exhaustive-read correctness and is prohibited.

0.223 composes the 0.210 convergence state machine with 0.221's durable
identity/replay lessons, but it does not wrap mutation inside
`compare_proof_and_advance` and does not introduce a flag that disables its
post-page proof check.

## Non-Negotiable Invariants

1. The initial job record commits before the first target-row mutation.
2. One mutating advance commits one complete atomic target batch and its exact
   next job record, or neither becomes durable.
3. Replaying the same job sequence and idempotency key returns the persisted
   receipt without executing target work again.
4. A different idempotency key at an old sequence returns a typed stale-sequence
   error and performs no work.
5. The job cannot change target entity, accepted schema identity, scope, fixed
   patch, operation timestamp, or engine batch-policy identity after start.
6. `Completed` requires clean Verify exhaustion at one unchanged durable target
   revision. Forward exhaustion, 10,000 processed rows, or a full bounded page
   is never completion.
7. E273 and every other pre-commit failure leave both target data and retained
   job sequence unchanged.
8. Application authorization is checked outside IcyDB on every start, state,
   advance, and acknowledgement endpoint. A job id is not bearer authority.
9. Persisted decoding is bounded and fallible. Unknown current-format tags or
   unsupported versions never reconstruct or translate an older job.
10. Production execution contains no panicking recovery or job-transition path.

## Scope

0.223 adds:

- a separate typed durable mutation-job lifecycle;
- one current bounded persisted record family in the existing excluded
  progress allocation;
- catalog-native custody of fixed update meaning and engine continuation;
- idempotent start, state, advance, terminal receipt replay, and
  acknowledgement;
- commit-marker ownership for atomic target-batch plus progress advancement;
- stable-revision Forward/Verify completion across arbitrary collection size;
- typed restart-required outcomes for accepted-authority or engine-policy
  changes;
- focused collection-scale evidence above 10,000 rows; and
- diagnostics, raw Wasm, instruction, stable-byte, and complexity evidence.

0.223 does not add:

- background execution, timers, heartbeats, async calls, or automatic retries;
- caller-selected batch sizes or instruction limits;
- multi-entity atomicity or a generic business-workflow engine;
- resumable `INSERT`, `DELETE`, `UPSERT`, schema mutation, or row `RETURNING`;
- row-relative arithmetic, append, random, time-varying, or external-call
  patches;
- mutation of primary-key, generated, managed, relation-owned, unique, or
  otherwise non-batch-safe fields;
- public bearer continuations or automatic generated canister endpoints;
- a target-store snapshot promise while other writes continue; or
- legacy decoders, application-continuation import, aliases, or dual public
  custody paths.

Vendor-specific nested sale-policy rewriting is not generalized into an
arbitrary persisted closure. The reference application must keep that phase
independently bounded or design a later catalog-native fixed mutation that
passes the same eligibility rules. The 0.223 acceptance requirement is the
large token-tier and scoring-state fan-out that causes the reported failure.

## Authority And Ownership

The authority order is:

1. the accepted schema snapshot owns entity, field, layout, constraints,
   indexes, and field-ownership semantics;
2. lowering owns conversion from SQL or a future typed frontend into one
   canonical accepted fixed mutation intent;
3. the persisted mutation intent owns immutable target, scope, patch,
   timestamp, and policy meaning after start;
4. authoritative primary-key traversal owns Forward and Verify progression;
5. the target store's durable mutation revision owns stable Verify evidence;
6. the commit marker owns atomic target journal publication plus mutation-job
   progress replacement; and
7. the excluded progress record owns public sequence, lifecycle, totals, and
   replay receipt.

Generated `EntityModel` and `IndexModel` remain proposal and convenience
surfaces. Mutation-job resume never reconstructs runtime authority from a
generated model. SQL is parsed only at start and lowers into the same canonical
intent a future typed frontend must produce.

The application owns:

- caller authorization and tenancy;
- generation and business association of job identities;
- collection configuration and business fences;
- ordering of vendor, token-tier, scoring, and other semantic phases;
- when clients poll or advance work; and
- composition of IcyDB receipts into application response DTOs.

## Public Trusted Contract

The exact Rust names may move mechanically during implementation, but the
surface must preserve this semantic shape:

```text
start_trusted_sql_mutation_job(
    job_id: MutationJobId,
    sql: &str,
) -> Result<MutationJobState, MutationJobError>

mutation_job_state(
    job_id: MutationJobId,
) -> Result<MutationJobState, MutationJobError>

advance_trusted_mutation_job(
    request: &MutationJobAdvanceRequest,
) -> Result<MutationJobAdvanceReceipt, MutationJobError>

acknowledge_mutation_job(
    job_id: MutationJobId,
    expected_terminal_sequence: u64,
) -> Result<(), MutationJobError>
```

`start_trusted_sql_mutation_job` parses and admits SQL once, freezes the
catalog-native intent, prepares the initial engine continuation, and persists
the record before returning. Starting an absent id creates sequence zero.
Repeating start with the same id and exact canonical intent returns the existing
state. Equality ignores the server-generated operation timestamp and compares
the immutable target/scope/patch request fingerprint instead. Reusing an id for
different meaning returns a typed identity conflict.

`advance_trusted_mutation_job` takes no SQL and no opaque continuation. It loads
both from IcyDB custody, validates current authority, executes at most one
bounded Forward or Verify step, and persists one next sequence and replay
receipt.

State and receipt types are Candid/Serde-compatible so an application may embed
them in its own authorized API, but IcyDB does not export a public canister
method automatically.

### Identity And Request

```text
MutationJobId([u8; 32])

MutationJobAdvanceRequest {
    job_id,
    expected_sequence,
    idempotency_key,
}
```

The id must be nonzero. The application may deterministically derive it from a
business operation, but IcyDB does not generate randomness or infer caller
identity. The idempotency key is nonempty, bounded to 256 UTF-8 bytes, and must
be reused exactly after a lost response.

### Lifecycle And Phase

```text
MutationJobStatus {
    Active,
    Completed,
    RestartRequired(MutationJobRestartReason),
}

MutationJobPhase {
    Forward,
    Verify,
}
```

`RestartRequired` is terminal for the retained job. It reports authority or
policy drift that cannot safely continue the frozen intent. It is not used for
ordinary concurrent target writes: those restart Forward inside the same
active convergence job.

Initial restart reasons are:

- accepted schema identity changed;
- target allocation/incarnation changed;
- canonical intent is no longer eligible;
- engine batch-policy identity changed; and
- the valid job record contains an unsupported internal continuation identity.

An unsupported record that cannot be safely decoded returns a typed format
error without mutation. It is never silently converted into a fabricated
`RestartRequired` record.

### State

```text
MutationJobState {
    job_id,
    sequence,
    status,
    phase,
    keys_scanned_total,
    rows_updated_total,
    verify_restarts_total,
}
```

Opaque continuation bytes, canonical scope/patch bytes, operation timestamp,
and fingerprints remain private engine custody. Totals use checked `u64`
arithmetic. A counter overflow fails before transition and cannot wrap.

### Receipt

```text
MutationJobAdvanceReceipt {
    request_sequence,
    committed_sequence,
    status,
    phase,
    keys_scanned,
    rows_updated,
    keys_scanned_total,
    rows_updated_total,
    verify_restarts_total,
}
```

The retained receipt also binds the idempotency key. Exact replay returns the
same receipt bytes and never re-enters planning, traversal, mutation, or
accounting.

## Canonical Persisted Intent

The job does not persist raw SQL as execution authority. Start lowers the
statement through accepted schema and structural mutation admission into:

```text
CanonicalMutationIntent {
    database_incarnation,
    target_store_identity,
    target_entity_identity,
    accepted_schema_revision,
    accepted_schema_fingerprint_method,
    accepted_schema_fingerprint,
    canonical_scope,
    canonical_fixed_patch,
    start_request_fingerprint,
    scope_fingerprint,
    patch_fingerprint,
    operation_timestamp,
    batch_policy_identity,
}
```

All variable-length components are bounded before persistence. Canonical scope
and patch decoding is current-form, accepted-schema-checked, and independent of
generated models. Start rejects unknown dependencies, unsupported values, or
an intent that would require current-row-relative computation.

The start-request fingerprint binds the admitted target, scope, fixed patch,
accepted authority, and batch policy, but not the operation timestamp generated
by IcyDB. A repeated start re-lowers the supplied statement and compares this
fingerprint before returning the retained state; it never replaces the original
timestamp or resets progress.

The existing trusted resumable-update continuation may remain the internal
checkpoint encoding if it stays bounded and current. Public APIs stop exposing
its bytes. Resume reconstructs the executable accepted plan from the persisted
canonical intent and current accepted runtime authority, then verifies every
stored identity before row access.

The initial frontend continues to admit only 0.210's fixed resumable SQL
`UPDATE` subset. A future typed frontend is additive only if it produces the
same `CanonicalMutationIntent`; it may not introduce a second executor or a
separate persisted plan representation.

## Persisted Job Record

Mutation jobs receive their own record magic, version, and key domain within
the existing integrity-progress memory allocation. They do not reuse the
generic proof-job codec or key prefix.

```text
MutationJobRecordV1 {
    job_id,
    sequence,
    status,
    phase,
    canonical_intent,
    engine_continuation,
    totals,
    last_receipt,
}
```

Initial hard bounds are:

| Item | Bound |
| --- | ---: |
| Job id | exactly 32 bytes, nonzero |
| Idempotency key | 256 UTF-8 bytes |
| Engine continuation | 2 KiB |
| Canonical intent | 16 KiB |
| Replay receipt | 8 KiB |
| Complete encoded mutation-job record | 64 KiB |
| Retained progress records across all job families | existing global cap of 64 |

Patch 1 verifies these values against the published 0.222.4 continuation,
progress-store, marker, stable-memory, and response limits before Patch 2
freezes them. Limits are engine-owned; callers cannot raise or tune them.

The record header includes magic, current version, bounded payload length, and
checksum. Decode validates the envelope before allocating nested state. Length
arithmetic is checked, collection counts are capped, trailing bytes reject,
and corrupt or future versions return typed errors.

No new stable-memory id or user configuration is introduced. Generated IcyDB
memory declarations already reserve the excluded progress allocation.

## State Machine

```text
                     bounded batch + progress commit
                  +-----------------------------------+
                  |                                   |
                  v                                   |
Start(seq=0) --> Forward ------------------------> Forward
                  |
                  | authoritative keyspace exhausted
                  v
             Verify(revision, start)
                  |
                  | clean bounded page
                  v
             Verify(revision, next_pk)
                  |
                  +-- revision drift --------> Forward(start)
                  |
                  +-- residual row ----------> Forward(start)
                  |
                  +-- clean exhaustion at
                      same revision ----------> Completed

authority/policy incompatibility -------------> RestartRequired
```

Only `Active` accepts a new non-replay advance. `Completed` and
`RestartRequired` retain their terminal receipt until sequence-checked
acknowledgement. An exact replay remains available in every lifecycle until
acknowledgement removes the record.

Acknowledgement is idempotent after a lost response: an already absent job id
succeeds. It rejects an active job and rejects a terminal job when the supplied
sequence differs.

## Forward Semantics

Forward uses the maintained 0.210 eligibility and traversal contract:

1. validate job envelope, sequence, idempotency, current accepted authority,
   target identity, intent fingerprints, and batch-policy identity;
2. exact-replay the retained receipt if request identity matches;
3. scan at most 256 authoritative primary keys after the retained checkpoint;
4. evaluate the stable scope and fixed-patch necessity;
5. stage at most 64 accepted structural updates using the retained operation
   timestamp;
6. derive the exact next checkpoint/phase and checked totals;
7. prepare the next job record and replay receipt; and
8. commit target journal work and progress replacement as one transition.

Already converged rows are scanned but not rewritten. This makes recovery from
an old checkpoint semantically idempotent, but atomic progress publication is
still required; idempotent values are not a substitute for an exactly replayed
sequence and receipt.

When the Forward scan exhausts, the same advance persists `Verify`, a null
checkpoint, and the durable target revision observed after its own last target
commit. It does not report `Completed`.

## Verify Semantics

Verify is read-only with respect to target rows:

1. compare the retained Verify revision before scanning;
2. scan one bounded authoritative primary-key page;
3. if any scoped row still needs the fixed patch, persist a Forward restart;
4. if the durable target revision changes during the page, discard its
   checkpoint and persist a Forward restart;
5. otherwise persist the next Verify checkpoint; and
6. only clean exhaustion at the same revision persists `Completed`.

The job's own Forward writes are not treated as external invalidation. Verify
captures its baseline only after Forward target mutation and progress commit
have converged to the retained transition.

Concurrent application writes remain allowed. They can cause additional
Forward/Verify passes, but cannot produce false completion. Applications that
require eventual completion under continuous conflicting writes must enforce a
business fence; IcyDB does not infer or persist one.

## Atomicity, Recovery, And Lost Responses

### Start

Start fully validates and encodes the initial intent and record before writing
the excluded progress store. No target row changes during start. A storage or
budget failure leaves no job.

### Mutating Forward advance

The commit marker gains one bounded mutation-job progress operation containing:

- progress key;
- expected current sequence and digest;
- complete bounded replacement record bytes; and
- enough identity to replay or verify the replacement during recovery.

The marker is persisted only after target mutations, journal entries, result
accounting, next record, and receipt are completely staged. Recovery applies
the target journal batch and progress replacement idempotently before clearing
the marker. A mismatch against neither the expected before-state nor exact
after-state is typed corruption and blocks reads; recovery never guesses which
side won.

The current commit-marker format moves directly to the new current form. There
is no legacy marker decoder. Normal upgrades must begin without a pending
marker; an unexpected incompatible marker fails typed recovery.

### Read-only progress advance

A Verify page, Forward page with no required mutations, terminal transition,
or acknowledgement changes only one bounded progress record. It uses a
sequence/digest-checked replace or remove under the serialized request. It does
not construct an empty target commit marker merely for uniformity.

### Response loss

Canister message commitment includes both target and progress state. If the
response is lost after commitment, retrying the exact request returns the
retained receipt. If the message traps, the platform rolls back the message;
if recovery-visible marker work was committed before a later controlled
failure, normal IcyDB recovery finishes the exact marker transition before any
database access.

No application can observe a committed target batch paired with an older
durable job sequence after recovery completes.

## Budget And E273 Contract

Mutation jobs are the completion protocol; E273 is not converted into a
successful progress response.

- Each advance inherits the caller's one non-resettable request execution
  scope.
- Job load, intent validation, traversal, row decode, staging, marker bytes,
  target apply, progress encoding, stable writes, receipt construction, and
  response bytes are charged.
- The engine-owned 256-key/64-row limits stop a normal step before it consumes
  an unbounded collection-sized amount of work.
- If earlier work in the same request consumed the shared budget, advance may
  still return E273 before commitment. The retained sequence and target remain
  unchanged and the application may retry in a fresh request.
- Every charged or fallible post-marker requirement is preflighted before
  marker publication. E273 cannot become a controlled post-marker outcome;
  marker-owned apply is mechanical and recovery-completable.
- A row, intent, marker, or progress record too large for one indivisible unit
  returns a typed terminal size/admission error, not an unchanged successful
  receipt.
- No API accepts a caller batch size, scan size, or instruction allowance.

Metrics distinguish request budget failure, ordinary bounded advancement,
Forward-to-Verify transition, Verify restart, completion, replay, and
acknowledgement.

## Error Contract

`MutationJobError` is a closed typed protocol at the IcyDB Rust boundary. Its
initial semantic families are:

- invalid job or idempotency identity;
- already exists with different intent;
- not found;
- stale sequence;
- active/terminal lifecycle mismatch;
- accepted-authority or intent mismatch;
- unsupported or corrupt persisted format;
- ineligible mutation intent;
- progress-store capacity or record-size limit;
- commit/recovery corruption;
- target mutation/query failure; and
- request execution budget exhaustion with the maintained E273 facts.

Errors do not match or expose strings internally. Compact public IcyDB
projection may retain E24/E273-style codes, but logs and trusted diagnostics
must preserve the typed source before projection.

A transient pre-commit error does not advance sequence. An authority or policy
change that is safely identifiable from a valid record commits one replayable
`RestartRequired` terminal transition. Corrupt or undecodable records never
execute and cannot be acknowledged through a fabricated state.

## Application Rarity Integration Contract

The reference application is reference evidence, not an IcyDB dependency. IcyDB must not import its
types, phases, errors, or authorization model.

The application-level rarity operation should persist its complete phase plan
before executing the first fan-out:

```text
RarityChangeOperation {
    collection_id,
    requested_config_identity,
    status,
    phase,
    vendor_phase_state,
    token_tier_job_id,
    scoring_stale_job_id,
    sequence,
    last_receipt,
}

phase:
    VendorPolicyReset
    -> TokenTierReset
    -> ScoringStateInvalidation
    -> Completed
```

The collection configuration update and complete pending phase plan must share
one application-owned durable transition. The application must not enqueue
`ScoringStateInvalidation` only after `TokenTierReset` succeeds.

The large fixed phases lower to canonical IcyDB mutation intents equivalent to:

```sql
UPDATE Token
SET tier = <default-tier>
WHERE collection_id = <collection>
```

and:

```sql
UPDATE TokenScoringState
SET score_stale = true
WHERE collection_id = <collection>
```

Exact syntax and value admission follow accepted schema; these examples state
meaning, not a new SQL grammar promise.

One application call advances at most one bounded phase step and returns a
typed application receipt carrying the current phase plus the embedded IcyDB
job state/receipt facts needed by the client. Polling state is read-only;
advancing is an authorized update.

The vendor phase remains application-owned because its current nested
sale-policy rewrite depends on each row's variant and contents. It must have an
independent bounded proof before the application claims the complete rarity
operation is scalable. This design does not falsely classify it as a fixed
IcyDB patch.

## Security And Operational Boundaries

- Mutation job APIs are trusted Rust APIs. Generated public endpoints are not
  added automatically.
- Job identities and idempotency keys prevent ambiguity and replay duplication;
  they do not authorize a caller.
- Public state and receipts omit raw SQL, canonical scope bytes, patch bytes,
  primary keys, row values, and opaque continuations.
- Diagnostics use bounded fingerprints, counts, phases, and reason codes rather
  than stored values or query literals.
- Capacity is bounded globally and per record. Start rejects before persistence
  when capacity is exhausted.
- A client cannot select engine limits or force an arbitrary persisted closure.
- A target job cannot call external services or await between validation and
  commit.

## Breaking And Migration Contract

0.223 is a pre-1.0 hard cut of application-custodied resumable update progress.
When the durable job surface is complete:

- public `prepare_trusted_sql_resumable_update` and
  `resume_trusted_sql_resumable_update` custody methods are removed from the
  façade;
- their continuation remains internal only if it is still the canonical engine
  checkpoint;
- no alias, wrapper, feature flag, or dual dispatch preserves the old public
  path;
- application-held continuation bytes cannot be imported into mutation jobs;
  callers start a new current job; and
- tests that exist only to preserve the removed public custody path are
  replaced by current durable-job tests.

The revision-strict generic `ResumableJob` and exhaustive-read APIs remain
unchanged. They solve a different problem and retain their pre/post proof
validation.

No source row, accepted schema, index, or target journal format changes solely
because a job is introduced. The progress allocation gains a current mutation
record family, and commit markers gain a current progress-replacement
operation. No old mutation-job record exists to migrate.

## Diagnostics And Observability

Focused diagnostics report bounded facts for:

- start, state, advance, replay, restart, completion, and acknowledgement;
- current phase and sequence;
- keys scanned and rows updated in the step and in checked totals;
- Verify restart reason and count;
- progress record bytes and marker contribution;
- request execution budget usage; and
- target entity shape fingerprint, never raw scope values.

Diagnostics do not change mutation eligibility or result. Their own retained
and response bytes are charged. Public application progress should be
constructible from typed state/receipt without parsing diagnostic text.

## Measurement And Validation Authority

Patch 1 freezes the exact `v0.222.4` predecessor and records:

- raw final Wasm for the maintained dynamic-query and typed canisters;
- current instruction cost for prepare, one 256-key/64-update Forward step,
  and one Verify step, plus fixed first-measurement identities and ceilings for
  mutation-job state load, exact replay, and acknowledgement when Patch 2 owns
  those operations;
- the current generic progress-record envelope and the proposed mutation-job
  record/receipt limits; exact new-format initial, maximum active, terminal,
  and replay sizes become measurable only when Patch 2 owns that codec;
- the current marker's zero mutation-progress contribution and the proposed
  maximum progress replacement; exact marker contribution becomes measurable
  only when Patch 4 owns that current format;
- fixed stable-memory measurement points for 1, 8, and maximum active mutation
  jobs; exact growth becomes measurable when Patch 2 owns the record; and
- a collection-scale eager control demonstrating E273 or bounded admission failure
  above 10,000 tokens without relying on a trap.

Final evidence must include:

- a collection with at least 10,001 matching tokens;
- more than one Forward call and more than one Verify call;
- exact total rows converged and no stale scoped row after completion;
- response-loss replay at start, mutating Forward, Verify, completion, and
  acknowledgement;
- interruption/recovery before and after target apply and progress replace;
- concurrent target mutation during Verify causing a deterministic Forward
  restart rather than false completion;
- heap and journaled-store rejection/acceptance parity required by policy;
- corruption, future version, maximum, max-plus-one, and checked-overflow cases;
- no raw SQL/keys/values in public state or diagnostics;
- raw non-gzipped Wasm delta as primary size evidence and deterministic gzip as
  secondary context; and
- complexity delta by files, approximate lines, and implementation shape.

Patch 1 sets numeric performance and Wasm review gates from the published
baseline before behavior lands. Later patches may not replace a failed named
fixture with a friendlier workload or weaken a gate after seeing results.

## Cross-Patch Acceptance Matrix

| Concern | Required proof |
| --- | --- |
| Initial durability | Job record exists and is decodable before any target mutation can execute |
| Mutating atomicity | Target journal batch and exact next sequence/receipt recover together across every failpoint |
| Replay | Same sequence/key returns byte-equivalent receipt without planning, scanning, or mutation |
| Stale request | Old sequence with different key returns typed stale sequence and changes nothing |
| Bounded work | No advance scans more than 256 keys or stages more than 64 updates; caller cannot tune limits |
| Complete meaning | Only clean stable-revision Verify exhaustion returns `Completed` |
| Concurrent writes | Target drift restarts convergence and never produces false completion |
| Budget exhaustion | E273 before commit leaves target and job sequence unchanged |
| Record safety | Every decode is bounded/fallible; corrupt/future records and arithmetic overflow fail typed |
| Authority | Accepted schema and persisted canonical intent bind every resume; generated models never reconstruct runtime meaning |
| Security | No automatic public endpoint, bearer authorization, raw SQL, row values, keys, or continuation leakage |
| Scale | A fixed collection above 10,000 rows finishes through multiple calls with exact final values |
| Application composition | All rarity phases are durable before the first phase runs; a failed phase cannot erase a later phase |
| Compatibility | Generic proof jobs remain revision-strict; old public mutation continuation custody is removed without aliases |
| Cost | Named instruction, stable-byte, raw Wasm, gzip, Candid, and complexity gates are reported without substitution |

## Exit Criteria

0.223 is complete only when:

- the public trusted mutation surface requires no application continuation or
  batch-size custody;
- start, Forward, Verify, completion, replay, and acknowledgement have durable
  typed contracts;
- marker recovery proves target/progress atomicity at every mutation failpoint;
- the existing generic read job still self-invalidates on protected mutation;
- the old public resumable-update custody surface and its compatibility tests
  are deleted;
- the fixed >10,000-token incident fixture completes with exact tier and score
  invalidation results across multiple calls;
- downstream phase persistence proves scoring work cannot be skipped after an
  earlier rarity phase failure;
- focused native, wasm-target, compile-surface, lint, corruption, recovery, and
  PocketIC checks pass;
- raw final Wasm, instruction, stable-byte, Candid, and complexity evidence is
  recorded against the frozen 0.222.4 baseline; and
- no unresolved correctness, persistence, public-surface, or recovery finding
  remains hidden behind a performance or application follow-up.
