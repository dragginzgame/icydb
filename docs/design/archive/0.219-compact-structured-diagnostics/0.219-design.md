# 0.219 Compact Structured Diagnostics

Status: proposed; implementation not started

Design cut: 2026-08-03

Implementation order: after 0.218 closeout

## Decision Summary

0.219 completes the compact-diagnostic direction established in 0.180.

The stable error code remains the categorical authority. Every public error may
add one bounded, production-safe sequence of numeric facts that identifies the
failing object, position, operation, bound, version, or compact kind without
embedding diagnostic prose, schema names, values, rows, keys, SQL text, or
debug output in the public error.

The final public shape is:

```text
Error {
    code: u16,
    class: u8,
    origin: u8,
    facts: Vec<DiagnosticFact>,
}

DiagnosticFact {
    tag: u8,
    value: u64,
}
```

The fact sequence is interpreted together with the leaf error code. The code
defines the error reason; facts contain only parameters of that reason. The
same fact representation is used for query, cursor, mutation, constraint,
schema, recovery, codec, index, and relation errors.

For example:

```text
E236 MutationBatchTooManyItems
facts:
    ActualCount = 5000
    Limit = 4096
```

Host tooling renders:

```text
E236 MutationBatchTooManyItems: batch contains 5000 operations; maximum 4096
```

The canister carries the numeric code and facts only. It does not carry that
sentence.

0.219 also hard-cuts the immediate-error use of `ConstraintDiagnostic`. E223
and E225 use the common fact channel:

```text
E223 ConstraintViolation
facts:
    AcceptedSchemaFingerprintMethod = 1
    AcceptedSchemaFingerprintHigh = ...
    AcceptedSchemaFingerprintLow = ...
    EntityTag = 17
    ConstraintId = 4
    ConstraintKind = Unique
    ConstraintContext = WriteAdmission
    MutationOperation = Insert
    BatchPosition = 0
```

Tooling may resolve the accepted fingerprint, entity tag, constraint ID, and
field IDs to current names. Resolution never makes generated/source metadata a
runtime authority.

Historical constraint activation findings remain a distinct operational
payload. Their durable primary-key locator is required for bounded validation,
acknowledgement, recovery, and repair. An ordinary `Error` never includes a
primary key, conflicting value, row, or arbitrary byte payload.

## Motivation

IcyDB currently has two different diagnostic shapes.

Most errors cross the public Candid boundary as:

```text
code + class + origin
```

The leaf code often identifies a precise categorical reason, but useful
parameters are lost. Examples include:

- a cursor's invalid character position, expected offset, actual offset, and
  signature prefixes;
- found and required database-format versions;
- expected and current accepted-schema revisions;
- actual and maximum mutation-batch counts or byte sizes;
- ORDER BY term indexes and duplicate-term pairs;
- function codes, argument indexes, inferred type classes, and expected and
  actual arity;
- row-layout stamps and expected and actual slot counts; and
- index, relation, field, entity, and constraint numeric identities.

E223 and E225 are the exception. Public `Error` has a dedicated optional
`ConstraintDiagnostic` carrying accepted names, entity strings, field-path
strings, and primary-key bytes. This is informative but contradicts the
code/detail-first direction, couples immediate errors to historical validation
findings, and makes one error family structurally special.

The internal implementation already preserves much of the desired compact
context:

- `OrderPlanError` retains term and primary-key-component indexes;
- `ExprPlanError` retains function/operator codes, argument and branch indexes,
  compact type classes, and arity;
- `CursorPlanError` retains decode reasons, positions, length bounds, signature
  prefixes, and offsets;
- `RecoveryErrorDetail` retains found and required versions and marker
  subreasons; and
- accepted schema and constraint runtime paths already have stable IDs and
  fingerprints.

The missing boundary is a single public representation for those parameters.
0.219 adds that boundary without restoring text-first errors.

## Design Dependencies

0.219 consumes rather than reopens:

- [0.180 compact diagnostic
  codes](../archive/0.180-compact-diagnostic-codes/0.180-design.md), especially
  stable leaf codes, CLI-owned prose, compact indexes/counts/IDs, and the rule
  that an error remains code-only only when additional context is not
  actionable;
- [0.211 accepted catalog
  constraints](../0.211-accepted-catalog-constraints/0.211-design.md), especially
  stable entity-local constraint IDs, accepted constraint kinds, activation
  findings, and accepted-schema ownership;
- [0.213 schema authority and application-model
  separation](../0.213-schema-authority-and-application-model-separation/0.213-design.md),
  especially accepted schema as runtime authority and generated models as
  proposal/adapter owners only;
- [0.215 SQL structural coverage and range
  remediation](../0.215-sql-structural-coverage-and-range-remediation/0.215-design.md),
  especially mixed structural mutation ordering and atomicity; and
- [0.218 explicit versioned schema
  migrations](../0.218-explicit-versioned-schema-migrations/0.218-design.md),
  especially accepted fingerprints, revisions, migration phases, findings,
  and tooling operations.

0.219 does not change the semantic classification, transactional behavior, or
recovery behavior established by those lines.

## Goals

- Preserve every existing stable E-code identity.
- Add useful compact context to errors whose failing position or expected and
  actual facts are already known.
- Use one public representation for every error family.
- Keep rich prose, labels, hints, and schema-name resolution outside production
  canister code.
- Remove schema names, field names, constraint names, field-path strings, and
  primary-key bytes from immediate constraint errors.
- Retain enough stable accepted identity for host tooling to resolve names
  exactly when metadata is available.
- Keep successful execution paths free of context construction and allocation.
- Bound context before it crosses the public response boundary.
- Avoid adding a feature-dependent public error ABI.
- Measure raw non-gzipped Wasm after every implementation patch.

## Non-Goals

- Do not make every internal invariant publicly diagnosable.
- Do not expose caller principals, controller identities, SQL text, values,
  rows, primary keys, stable-memory bytes, or formatted Rust values/types.
- Do not make a public error sufficient to reproduce a failed operation.
- Do not turn generated model metadata into accepted runtime authority.
- Do not introduce a production diagnostic-name table.
- Do not add a `diagnostic-text` or similarly feature-dependent wire shape.
- Diagnostic projection does not require changes to persisted rows, indexes,
  journals, markers, accepted schemas, migrations, or cursors. Any co-shipped
  pre-1.0 codec hard cut must be explicit, bounded, current-only, and documented
  without a compatibility decoder.
- Do not change error class, origin, uniqueness semantics, query semantics, or
  mutation atomicity.
- Do not add compatibility decoding for the retired public error shape.

## Current Architecture

### Categorical identity

`icydb-diagnostic-code` owns one contiguous registry of public numeric leaf
codes. A leaf code reconstructs its broad category and categorical detail for
host rendering. That registry intentionally contains no long prose and no
Candid types.

### Internal typed errors

Core subsystems retain varying amounts of typed context:

```text
planner/cursor/schema/store/runtime error
    -> typed internal variant and parameters
    -> Diagnostic { code, origin, categorical detail }
```

Some conversions preserve the typed variant only until the public facade.
Others deliberately reduce it earlier to an `InternalError` unit detail.

### Public facade

The current public facade maps most errors to:

```text
Error { code, class, origin, constraint: None }
```

Only accepted constraint errors clone a rich `ConstraintDiagnostic` into the
public error.

### CLI

The CLI reconstructs categorical prose from the E-code registry. For
constraint errors it currently renders the name/path/key strings supplied by
the canister. It has no general parameter channel and no schema-artifact
resolver.

## Final Authority And Flow

```text
subsystem-owned typed failure
    -> stable E-code
    -> subsystem-owned compact typed parameters
    -> canonical DiagnosticFact projection
    -> public Error { code, class, origin, facts }
    -> host-side fact validation and interpretation
    -> optional exact accepted-schema resolution
    -> CLI/application rendering
```

The public fact sequence is evidence, not authority. Accepted schema remains
the sole owner of entity, field, constraint, index, relation, and layout
meaning.

Generated metadata may assist host rendering only when it proves an exact
accepted-fingerprint match. It never changes the error, planner, executor,
constraint evaluator, or recovery result.

## Public Wire Contract

### Error

`icydb::Error` hard-cuts to:

```rust
pub struct Error {
    code: u16,
    class: u8,
    origin: u8,
    facts: Vec<DiagnosticFact>,
}
```

The current `constraint: Option<ConstraintDiagnostic>` field is removed. No
alias or dual decoder remains.

`code`, `class`, and `origin` retain their current meaning. Facts never change
classification or recovery policy.

### DiagnosticFact

```rust
pub struct DiagnosticFact {
    tag: u8,
    value: u64,
}
```

The raw representation is deliberately generic and numeric. It avoids a large
public Candid variant whose labels and exhaustive conversion logic would be
linked into every canister.

The production-safe diagnostic-code registry owns each numeric fact-tag
assignment. Public consumers may inspect raw facts. Host tooling exposes typed
views and labels.

### Why one numeric fact representation

Alternatives were rejected:

1. **One optional field for every possible parameter**
   - produces a wide Candid record;
   - repeats absent-option encoding;
   - makes every error carry every family's vocabulary; and
   - grows every consumer when a new parameter is added.
2. **A public enum with one variant per error family**
   - duplicates categorical identity already owned by the E-code;
   - retains public variant labels and conversion arms in production Wasm; and
   - encourages a second error taxonomy beside the E-code registry.
3. **Arbitrary strings or bytes**
   - reintroduces text-first diagnostics;
   - permits values, keys, and prose to leak accidentally; and
   - lacks a stable machine-readable contract.

`tag + u64` carries IDs, indexes, counts, bounds, offsets, versions, compact
enums, fingerprint halves, and packed ID pairs without those problems.

## Fact Registry

Fact tags are global semantic labels. The implementation inventory freezes the
complete numeric table before the public hard cut. Required tag families are:

- accepted authority:
  - fingerprint method version;
  - fingerprint high and low halves;
  - entity tag;
  - constraint, field, index, and relation ID;
- operation location:
  - mutation operation;
  - batch position;
  - clause, term, projection, aggregate, argument, branch, component, and
    parameter index;
  - source-span start and end where the parser already preserves them;
- expected/actual facts:
  - expected, actual, minimum, maximum, limit, and count;
  - expected and actual revisions, versions, offsets, arity, lengths, and slot
    counts;
- compact kinds:
  - constraint and context kind;
  - field/value/type family;
  - function, operator, aggregate, mutation, row-op, key-namespace, component,
    and mismatch kind;
- packed constraint-value path components:
  - root field;
  - record member;
  - tuple element;
  - newtype;
  - enum variant;
  - list/set element; and
  - map key/value entry.

Two accepted `u32` identities may be packed into one `u64` fact value only
through one registry-owned big-endian helper. This covers composite/member,
composite/tuple-ordinal, and enum/variant pairs without lossy narrowing.

No tag has an open-ended meaning such as `DebugValue`, `Message`, `Name`,
`Payload`, or `Bytes`.

## Per-Code Fact Schemas

The leaf-code registry also owns the permitted fact schema for each E-code:

- allowed tags;
- required tags;
- canonical ordering;
- whether a tag may repeat;
- packed-value interpretation; and
- the maximum number of facts for that code.

The E-code remains enough to classify an error. An empty fact sequence remains
valid for deliberately code-only errors.

Known malformed fact sequences are never reinterpreted heuristically. Host
tooling prints the stable E-code plus raw `tag=value` facts and reports the
context mismatch. It does not panic or silently attach the wrong labels.

Unknown tags are rendered numerically. They are not treated as legacy aliases
or translated into another current tag.

## Bounds

`MAX_PUBLIC_DIAGNOSTIC_FACTS` is 80.

The bound covers:

- at most 64 existing accepted targeted-value path components; and
- at most 16 common identity, classification, operation, position, and
  fingerprint facts.

Every non-constraint error has a materially smaller per-code bound. The
registry records that tighter bound and tests it.

Fact construction uses already bounded internal domains. It never reserves
capacity from an untrusted caller-provided count. Numeric conversion is
checked and non-lossy. On Wasm and supported native targets, `usize` positions
fit `u64`; the conversion remains explicit.

The public projection is infallible only after the internal typed context has
passed its subsystem bound. An impossible projection-bound violation becomes a
compact internal error rather than panicking, truncating, or publishing a
partial fact sequence.

## Internal Ownership

0.219 does not replace every subsystem error with `Vec<DiagnosticFact>`.

Subsystems retain typed variants using their natural types:

- `usize` for indexes into existing vectors/slices;
- `u16` for bounded field slots and compact component counts;
- `u32` for versions, offsets, byte lengths, and accepted local IDs;
- `u64` for entity tags, revisions, and counters; and
- compact enums for operations and kinds.

Each subsystem owns one projection from its typed error into canonical facts.
There is no second projection in SQL, structural, typed, CLI, or endpoint code.

The public facade calls that projection exactly once:

```text
InternalError / QueryError
    -> diagnostic()
    -> diagnostic_facts()
    -> icydb::Error
```

`QueryError::diagnostic_facts()` must cover validation, intent, planning,
cursor, and execution errors. Non-execution query errors must not bypass the
fact boundary merely because they have not become `InternalError`.

Fact construction occurs only after an operation has failed. Successful
planning, execution, mutation, recovery, and persistence do not allocate a
fact vector.

## Diagnostic Family Contracts

### Query validation and planning

Eligible context includes:

- order term index;
- first and duplicate term indexes;
- missing primary-key component index;
- group key and aggregate indexes;
- aggregate count;
- HAVING expression index;
- function code and argument index;
- expected and actual arity;
- unary/binary operator code;
- CASE arm/branch indexes;
- compact expected and actual type families; and
- projection index.

Unknown fields use a query/source position, projection position, or already
resolved accepted field ID where available. They do not return the field-name
string. Tooling already has the authored query/request and can label the
position.

### Cursor and continuation

E6 gains:

- decode-reason code;
- actual and maximum token length;
- invalid character position;
- payload component and component index;
- expected and actual signature prefix;
- expected and actual offset;
- expected and actual arity; and
- order or primary-key-component index where available.

The complete cursor token and complete signature are never returned.

### SQL frontend and write boundary

Existing leaf codes continue to identify unsupported features, lowering
reasons, surface mismatches, and write boundaries. Facts add only parameters:

- clause/item/parameter position;
- expected and actual projection width;
- expected and actual affected-row count;
- requested and maximum returning rows/bytes;
- scan or staged-row limit and actual usage; and
- compact operation and value/type-family codes.

SQL text and literal values are never returned.

### Mutation admission

Eligible E196 and E233-E240 facts include:

- accepted schema fingerprint and entity tag;
- field ID for required/database-owned/managed fields;
- mutation operation;
- batch position;
- first and duplicate batch positions;
- expected and offending entity tags;
- actual operation count and operation limit;
- actual staged bytes and staged-byte limit; and
- actual result bytes and result-byte limit.

Duplicate-key diagnostics never contain the key. The mixed-mutation scheduler
must retain the first input ordinal beside each staged key so it can report the
two positions without exposing the key itself.

### Accepted constraints

E223 and E225 carry:

- accepted schema fingerprint method and fingerprint;
- entity tag;
- entity-local constraint ID;
- constraint kind;
- constraint context;
- mutation operation when applicable;
- batch position when applicable; and
- a bounded packed accepted value path for targeted rules.

Constraint ID is never interpreted without entity tag and exact accepted
fingerprint.

The immediate error omits:

- constraint name;
- entity name/path;
- field names/paths;
- index/relation names;
- primary key;
- conflicting key/value; and
- attempted row.

Unique violations remain E223 with `ConstraintKind = Unique`. They do not
receive a second uniqueness-specific public error code merely to carry
parameters.

The canonical origin remains `Executor` for accepted write-admission
constraint failures, including unique-index detection. The detecting physical
subsystem does not replace the unified mutation-enforcement boundary.

### Historical activation findings

Historical findings are not ordinary errors. Their primary-key locator and
field IDs are durable evidence used by bounded validation and acknowledgement.

0.219 separates the public finding DTO from immediate error facts:

```text
ConstraintValidationFindingOutput {
    accepted_schema_fingerprint: [u8; 16],
    entity_tag: u64,
    constraint_id: u32,
    primary_key: Vec<u8>,
    field_ids: Vec<u32>,
    value_path: Option<...>,
    error_code: u16,
}
```

The exact DTO spelling may follow the maintained public naming convention, but
its lifecycle is fixed:

- it appears only in explicit validation/integrity operations;
- it is not embedded in `Error`;
- it preserves the current bounded row locator required for repair; and
- its names are resolved by host tooling rather than carried beside every
  finding.

The durable validation-job payload hard-cuts from private Candid/Serde encoding
to the bounded checksummed `ICYCVJOB` version-1 codec shipped in 0.219.0. It
stores compact IDs, primary-key bytes, value paths, and error codes separately
from immediate public diagnostics. No decoder for the predecessor payload is
retained; affected pre-1.0 development state is recreated.

### Schema DDL and migration

Eligible facts include:

- expected, current, and requested schema/entity versions;
- expected and actual revision;
- fingerprint method, expected fingerprint prefix, and actual fingerprint
  prefix where full binding is unnecessary;
- entity tag and accepted object ID;
- migration phase and bounded finding position; and
- budget resource, actual usage, and limit.

Facts do not duplicate migration receipts, plans, or complete fingerprints when
the public operation already returns those values in a typed success/progress
payload.

### Recovery and database format

E19 and recovery-origin corruption errors may carry:

- found and required format version;
- control/marker component code;
- malformed-marker reason;
- expected and actual length;
- expected and actual state code; and
- database-control record kind.

No stable-memory payload, marker bytes, key, journal row, or schema name is
returned.

### Persisted row and codec

E197/E198 and selected corruption codes may carry:

- entity tag where already available;
- row-layout stamp;
- accepted history floor and current layout;
- field ID or physical slot;
- expected and actual slot count;
- codec/component kind;
- expected and actual payload length; and
- compact expected and actual value/type family.

Call sites move from field names to accepted field IDs or slots before adding
public context. A name is never retained solely for an error.

### Commit, index, and relation

Eligible facts include:

- commit/control/journal component kind;
- memory ID expected and actual;
- entity tag;
- index or relation ID;
- physical generation;
- key component index;
- expected and actual arity; and
- compact row-op, key-namespace, or value-kind code.

Stable keys, entity/store paths, index keys, primary keys, and row bytes are not
public facts.

### Code-only errors

The following remain code-only unless a later call site proves safe actionable
context:

- controller/authorization failures;
- generic internal/executor/store invariants;
- ordinary not-found errors where the only locator is a key or value;
- corruption where only raw bytes identify the failure;
- exact unsupported-feature leaf codes that already tell the caller what to
  change; and
- failures whose context exists only as formatted debug text.

Controller principals and other caller identities are never diagnostic facts.

## Tooling And Humanization

### CLI rendering

The CLI owns:

- E-code labels and prose;
- fact-tag labels;
- per-code fact interpretation;
- hints and examples;
- schema artifact loading;
- live introspection lookup; and
- numeric fallback.

The CLI does not mutate or reinterpret the engine error. It renders facts.

Examples:

```text
E6 QueryInvalidContinuationCursor:
invalid hex character at position 12
```

```text
E198 PersistedRowSlotCountMismatch:
layout 7 requires 14 slots; row contains 13
```

```text
E223 ConstraintViolation:
entity User [17]
constraint User.pid [4]
kind unique
operation insert
batch position 0
```

### Schema resolution order

Tooling resolves accepted IDs in this order:

1. an exact accepted-schema diagnostic artifact keyed by fingerprint method,
   accepted fingerprint, and entity tag;
2. explicit live schema introspection when the deployed canister publishes it;
3. generated/source metadata only when it proves the same exact accepted
   fingerprint and complete ID mapping; and
4. numeric IDs when no exact resolver is available.

Generated metadata is never consulted merely because its names or shape appear
similar.

### Diagnostic schema artifact

The CLI may export and consume a host-only artifact containing:

- fingerprint method and exact accepted entity-schema fingerprint;
- entity tag and current entity name/path;
- field IDs and current names;
- constraint IDs, kinds, current names, and implicated field IDs;
- index/relation IDs and current names where required for rendering; and
- artifact provenance sufficient to reject a mismatched deployment/schema.

The artifact:

- is produced from accepted-schema introspection, not source declaration alone;
- is bounded using maintained accepted-schema limits before allocation;
- is never compiled into a production canister;
- is not a persistence, recovery, schema-application, or runtime authority;
- cannot authorize a mutation; and
- fails closed on fingerprint mismatch.

Host tooling may bind that exact accepted artifact to generated/source
metadata. The binding retains the artifact's numeric mapping and exact accepted
identity unchanged, replaces deployment provenance with one bounded source
label, and is stored as a distinct provenance kind. `icydb diagnostic` consults
it only after an exact deployment artifact and explicit live introspection have
failed to resolve the same fingerprint method, all fingerprint bits, entity
tag, and requested constraint ID. A deployment artifact cannot be supplied as
source metadata or vice versa.

0.219 adds no compatibility decoder for an older artifact shape. Before 1.0,
the current artifact shape is the only accepted shape.

### Introspection identity

Current entity/constraint description payloads expose names and constraint IDs
but do not expose enough identity to match an E223 numeric payload exactly.
The explicit introspection surface must add:

- entity tag;
- accepted schema fingerprint method version; and
- accepted entity-schema fingerprint.

These fields are available only through the existing deliberately enabled
introspection capability. They do not make introspection implicitly available
on production deployments.

If introspection is disabled and no exact artifact exists, tooling prints the
numeric fingerprint, entity tag, constraint ID, kind, operation, and batch
position with instructions to obtain or supply an artifact.

## Wasm And Runtime Cost Contract

### Production Wasm

0.219 must not add a name table, prose table, schema strings, or renderer to
production canister dependencies.

The production-safe pieces are:

- numeric E-code mapping;
- numeric fact-tag constants;
- cold typed-to-fact projections; and
- the two-field Candid fact record.

Host prose and context schemas that are not called by canister code must remain
dead-strippable. No Cargo feature changes the public error Candid shape.

Every implementation patch records raw non-gzipped Wasm bytes for maintained
SQL, typed-query, dynamic-query, and mutation-capable subjects. Gzip is
secondary context only.

No fixed byte threshold is assumed before measurement. Any surprising growth
must be attributed by section/symbol evidence before the patch is considered
ready. The design target is no meaningful increase across production subjects;
removing E223 name/path/key construction may offset some common fact machinery.

### Runtime performance

Facts are constructed only on an error path. Successful query planning,
execution, writes, commit, and recovery perform no fact-vector allocation.

Error-path work is bounded and linear in fact count. There is no schema graph
walk, name lookup, string formatting, row clone, or key encoding merely to
construct public facts.

## Security And Privacy

The public fact registry is an allowlist, not an open telemetry channel.

Allowed:

- immutable accepted IDs;
- compact operation/kind codes;
- positions into caller-known requests;
- counts and limits;
- versions/revisions;
- bounded fingerprint prefixes or exact schema fingerprints when required for
  identity resolution; and
- packed numeric targeted-value path coordinates.

Forbidden:

- names and paths;
- principals;
- SQL/query text;
- literal, conflicting, attempted, or stored values;
- primary/index/relation keys;
- row bytes;
- cursor/token bytes;
- stable-memory bytes;
- arbitrary hashes of values or rows; and
- arbitrary text/debug payloads.

The CLI may combine numeric facts with metadata supplied separately by the
operator. The canister error itself remains safe if copied into logs.

## Compatibility And Format Impact

This is a pre-1.0 hard cut.

Public Candid changes:

- `Error.constraint` is removed;
- `Error.facts` is added;
- `DiagnosticFact` is added; and
- constraint validation finding output receives its own operational DTO.

No compatibility alias, dual Candid shape, legacy constraint decoder, or
fallback reader is added.

Unchanged:

- numeric E-code assignments;
- error class and origin semantics;
- accepted schema and source binding formats;
- row, index, relation, journal, commit-marker, cursor, and migration formats;
- SQL/query/mutation response success shapes; and
- query, mutation, constraint, atomicity, recovery, and authorization
  semantics.

Current-only persisted hard cuts shipped beside the diagnostic work:

- constraint-validation jobs use checksummed `ICYCVJOB` version 1; and
- schema-application records retain their `ICYSAR01` version-1 envelope while
  replacing its payload with the direct bounded mapping.

Neither format has a predecessor decoder or translation path.

The diagnostic schema artifact is a tooling format, not an IcyDB persisted
database format.

## Public API

The maintained public facade exposes:

- `Error::code()`;
- `Error::class()`;
- `Error::origin()`;
- `Error::facts()`;
- `DiagnosticFact::tag()`;
- `DiagnosticFact::value()`; and
- production-safe numeric fact-tag identities.

Typed host interpretation belongs in tooling-facing APIs. The production
facade does not grow one accessor for every possible E-code/fact combination.

The existing `constraint_diagnostic()` accessor is removed. Tooling uses the
common facts plus its resolver.

## Testing Strategy

### Registry and public wire

- fixed Candid shape for `Error` and `DiagnosticFact`;
- contiguous E-code registry remains unchanged;
- fact-tag numeric assignments are unique and fixed;
- per-code required/allowed/repeated/canonical-order contracts;
- maximum fact count and non-lossy conversions;
- malformed known context produces numeric mismatch output, never panic;
- unknown tags remain numeric; and
- no compatibility decoder for the old constraint field.

### Family propagation

- cursor empty/too-long/odd/invalid-hex, payload, signature, and offset cases;
- found/required database-format version and malformed-marker reason;
- mutation counts/bytes/limits and duplicate input ordinals;
- stale expected/current accepted revision;
- order, group, expression, function, CASE, and projection indexes;
- SQL width/count/limit/parameter facts;
- row layout-window and slot-count facts;
- commit/index/relation component/identity facts; and
- code-only families remain fact-free.

### Constraints

- E223 unique, not-null, check, relation, and targeted-rule facts;
- E225 activation-blocked facts;
- exact accepted fingerprint/entity/constraint binding;
- operation and deterministic batch position;
- bounded packed targeted value paths;
- no primary key, value, row, or schema-name fact;
- renamed accepted names resolve through the same stable IDs;
- wrong-fingerprint artifact fails closed; and
- numeric fallback remains complete without introspection.

### Operational findings

- durable activation codec bytes remain unchanged;
- public finding output retains the required row locator and numeric IDs;
- error output never inherits the finding's primary key;
- acknowledgement and replay semantics remain unchanged; and
- SQL and structural validation rendering use the same host resolver.

### Negative-space and source guards

- public error constructors accept no `String`, `&str`, arbitrary `Vec<u8>`,
  value, key, or row context;
- no renderer or diagnostic prose enters core error construction;
- unique-violation construction does not clone names, field paths, or primary
  keys for `Error`;
- generated model metadata is not consulted by runtime errors;
- no feature changes the public error Candid shape; and
- production canister dependency trees do not acquire a host renderer or
  artifact parser.

### Wasm

Measure at least:

- one-entity typed-query canister;
- one-entity dynamic-query canister;
- maintained SQL performance canister; and
- one mutation-capable canister exercising structural errors.

Report raw byte deltas, hashes, export counts, and attributable section/symbol
changes. Do not infer a size win merely from removing Rust source lines or
strings.

- the detailed changelog when the user names a release target.

Documentation must say that IcyDB avoids schema-specific names and prose in
ordinary error payloads. It must not claim that production Wasm contains no
schema names anywhere: SQL, dynamic APIs, accepted catalogs, and explicit
introspection remain name-driven by design.

## Rejected Alternatives

### Keep E223 special

Rejected because it leaves two public diagnostic systems and keeps immediate
errors coupled to migration findings.

### Add more strings to selected errors

Rejected because it restores text-first construction, increases Wasm and
response size, and risks values or schema details leaking into logs.

### Add one E-code for every parameter combination

Rejected because a code identifies the categorical reason, not runtime values
such as positions, counts, revisions, or limits. Encoding parameters in the
leaf-code space would cause unbounded registry growth.

### Put rich names behind a canister feature

Rejected because feature-dependent public error ABIs are difficult for clients
to decode and are easy to enable accidentally. Rich rendering is host-side.

### Resolve IDs inside the engine before returning

Rejected because it performs accepted-name lookup and string construction in
the production error path and gives the runtime a second diagnostic rendering
responsibility.

### Use generated source metadata without fingerprint proof

Rejected because accepted renames, SQL DDL, reconciliation, and existing-store
identity can make source metadata differ from runtime authority.

## Completion Criteria

0.219 is complete when:

- one bounded common fact representation is the only immediate public
  diagnostic context;
- all current E-code assignments remain stable;
- E223/E225 contain compact accepted identities and no names/keys/values;
- the highest-value cursor, recovery, mutation, planner, SQL, schema, row,
  index, and relation contexts reach the public boundary;
- code-only families are explicitly justified;
- historical findings are separate from immediate error context and preserve
  their durable lifecycle;
- CLI prose and schema humanization are host-only;
- exact artifact/introspection resolution fails closed on fingerprint
  mismatch;
- numeric fallback is useful without introspection;
- persisted changes are limited to the two documented current-only codec hard
  cuts, with no compatibility decoder or runtime semantic change;
- focused tests and warnings-denied Clippy pass for affected packages;
- raw production Wasm deltas are measured and explained; and
- a final source/construction/dependency audit finds no alternate rich-error
  path or feature-dependent public ABI.
