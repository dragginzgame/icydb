# IcyDB 0.240.1 Exact Indexed `COUNT(DISTINCT)` Cardinality

Status: IMPLEMENTED — RELEASED AS `v0.240.1`

Last updated: 2026-08-25

Exact released predecessor:
`v0.240.0` at `9fa9eecdec30b686ca327e7b39fce33c43b70854`.

Exact released target:
`v0.240.1` at `1cf73c9346595b4d6a6a7845cb2297df1dba44d5`.

## Outcome

Allow one evidence-bounded SQL global aggregate,
`COUNT(DISTINCT direct_non_nullable_int32_field)`, to return the exact number
of non-empty leading-component keys already maintained by one complete
accepted user index.

This is an index-only aggregate over exact synchronized metadata. It is not a
row scan, index-entry scan, group seek, estimate, result cache, materialized
view, statistics mode or new aggregate implementation. Incompatible shapes
and unavailable evidence retain the current prepared aggregate route before
that route performs any store work.

The line is a hard cut onto one generalized exact-global-count owner. It may
not retain separate direct-row-count and distinct-count cache slots,
classifiers, fallback caches or diagnostics branch trees. It adds no public
SQL syntax, compatibility alias, feature flag, persisted format, stable-memory
state, accepted-schema authority, Candid method or export.

## Demonstrated Need

The exact 0.240 predecessor measures the production-shaped 2,048-row query:

```sql
SELECT COUNT(DISTINCT age) FROM PerfAuditUser
```

| Observation | Exact 0.240 value |
| --- | ---: |
| Cold instructions | 120,671,186 |
| True-warm instructions | 120,426,858 |
| Rows fetched | 2,048 |
| Result | 5 |

The fixture's accepted `age` index has five non-empty leading-component
groups. Current execution nevertheless fetches every row, canonicalizes every
value, maintains a distinct hash set and reduces the five admitted values.
The 0.237 audit measured the same shape at 104,380,904 instructions before
later runtime changes; the 0.240 pair is the sole release gate because it is
the exact predecessor.

The maintained `IndexPrefixCardinality` owner already stores one
`first_component_counts` entry for every non-empty canonical leading
component of each user-index generation. Insert, update and delete transitions
maintain those entries and remove zero counts. The map is usable only when its
decode state is valid and its recorded data generation equals the
authoritative row-store generation.

The removable work is therefore identified, not inferred: 2,048 row fetches,
2,048 distinct-key canonicalizations and the corresponding distinct-state
allocation are unnecessary when an already accepted complete index has exact
synchronized first-component metadata. The candidate still performs work
proportional to the number of distinct values, not the number of rows.

## Database Design Rationale

Using exact index-maintained cardinality for an index-only aggregate follows
the same database principle as an index-only count: a transactionally
maintained complete access structure may answer a query when its key
equivalence, coverage and freshness are proven. Three boundaries keep that
principle safe here:

1. **Exact, never estimated.** The result is the count of non-empty canonical
   first-component keys from a generation-matched map. Histograms, sampling
   and cost estimates cannot produce a result.
2. **One semantic and selection owner.** SQL lowering proves the aggregate
   shape and the accepted-schema planner helper selects one compatible index.
   The executor receives an immutable target and cannot reclassify the query
   or search for a different index.
3. **Optional evidence changes cost only.** Missing, stale or undecodable
   metadata returns unavailable. SQL then uses the current prepared aggregate
   plan and produces the same result or typed failure it does today.

This is deliberately narrower than a general aggregate optimizer. No adaptive
execution is needed because the decision is made before store work. No
cost-based threshold is needed because an admitted exact target either has
usable metadata or takes the predecessor fallback.

## Frozen Initial Admission

The `v0.240.1` exact target is constructed only when every condition below is
true:

1. The statement is one SQL global aggregate over one accepted entity.
2. Its complete projection is exactly one direct
   `COUNT(DISTINCT field)` terminal, with no additional output expression.
3. `field` resolves to one direct top-level accepted row slot and its accepted
   scalar kind is exactly `Int32`.
4. The field is non-nullable. Nullable `COUNT(DISTINCT ...)`, including any
   physical NULL-omission contract, remains on the predecessor route.
5. There is no `WHERE`, aggregate `FILTER`, `GROUP BY`, `HAVING`, cursor,
   `ORDER BY`, `LIMIT` or `OFFSET`.
6. One planner-visible accepted field-path user index has this exact field as
   component zero.
7. That index is complete: it has no predicate, no expression key item and no
   conditional omission contract, and its first field path is exactly the
   single segment `field`. Primary access, nested field paths, expression
   indexes and filtered/partial indexes are excluded.
8. A compound index is eligible only when accepted schema proves every
   admitted row contributes exactly one complete index key. Every suffix
   component must therefore be total, canonically indexable and incapable of
   NULL, optional-path or other omission. It is not enough for only the
   leading target field to be non-nullable.
9. Index visibility is `StoreReady`, the physical `IndexId` belongs to the
   pinned accepted entity authority, and the accepted schema proves canonical
   `Int32` index equality is exactly SQL DISTINCT equality.
10. The exact metadata owner can prove decodability and current row/index data
    generation before returning a value.

Multiple compatible indexes are resolved by the existing deterministic
accepted-field-path selection rule already used by exact prefix cardinality:
shortest key arity first, then stable index name. The rule is generalized in
place and remains the only special exact-cardinality index selector. A second
selector in the SQL adapter or executor is forbidden.

The selected `IndexId` is immutable command preparation. If that compatible
index's metadata is unavailable while a second compatible index happens to be
available, execution takes the prepared fallback. It must not search for or
switch to the second index at runtime.

The `Int32` restriction is evidence-led, not a statement that other scalar
types are impossible. It covers the measured `age` hotspot and reuses the
0.238 proof that canonical accepted-index component equality agrees with
projected SQL equality. Text and other scalar kinds remain fallback until
their value-size budget equivalence and canonical equality are separately
measured. Widening the type cohort is outside this patch.

## Selected Structure

The retained compiled command continues to own the one 0.240
fingerprint-bound exact-or-prepared cache slot. Conceptually its exact target
vocabulary gains one payload:

```rust
enum SqlGlobalAggregateCachedPlan {
    ExactEntityCardinality,
    ExactUserIndexPrefixes(Rc<[UserIndexPrefixCardinalityKey]>),
    ExactUserIndexFirstComponentDistinct(IndexId),
    Prepared(SharedPreparedExecutionPlan),
}
```

The name is illustrative. The implementation must reuse the existing enum,
fingerprint wrapper and slot. It may not add a neighboring slot, nested
`OnceLock`, cached result count or second fingerprint type.

The current `DirectCountCardinalityTarget`/`direct_count` owner no longer
describes the complete maintained responsibility once distinct count is
admitted. It may be renamed in place to an exact-global-count owner, but the
old module, type names and wrappers must be removed in the same patch. No
aliases, forwarding module or dual dispatch remain after the hard cut.

Execution is a straight-line authority chain:

```text
pinned accepted catalogue and entity authority
  -> lowering-owned exact COUNT shape fact
  -> one deterministic accepted-index target selection
  -> one fingerprint-bound compiled exact target
  -> canonical exact-cardinality executor
  -> StoreHandle freshness/proof boundary
  -> IndexStore generation-matched first-component metadata
  -> existing SQL scalar result projection
```

On metadata unavailability the existing `QUERY_PLAN_CACHES` owner supplies the
prepared fallback exactly as in 0.240. The exact compiled target stays in the
sole command slot and may become usable on a later request. A fallback plan is
never retained beside or inside it. Publication continues to create a new
compiled command through `SQL_COMPILED_COMMAND_CACHES`; a populated `OnceLock`
is not replaced.

## Exact Metadata Contract

`v0.240.1` formally promotes synchronized first-component metadata from advisory
planning evidence to result correctness authority for this one admitted
aggregate. The promotion is valid only under this invariant:

> For one pinned accepted root, one complete accepted user index and one
> synchronized row/index data generation, every present
> `first_component_counts` key represents exactly one canonical non-empty
> leading-component value present in the logical row set. Its stored count is
> exactly that value's current logical-row multiplicity. Every logical row
> contributes exactly one physical key to the accepted index, and no key or
> metadata entry exists without its logical row.

Row mutation, user-index mutation, metadata mutation and synchronized
generation publication must preserve that invariant atomically. Generation
publication is the final authority step: no partially applied transition may
publish synchronized metadata. Rollback must restore the preceding complete
row/index/metadata state or leave the new evidence unavailable. This proof
must cover failed inserts, updates and deletes at every preflight/publication
boundary, not only successful mutations.

`Exact(0)` requires positive evidence: an initialized, decodable empty map
whose generation matches the pinned authoritative row store and whose
accepted complete index is Ready. An absent, unmaterialized, undecodable or
generation-unbound map is `Unavailable`, never zero. Empty heap and initialized
empty journaled stores may use their existing positive empty proof; reopening
a populated journaled store without materialized metadata may not.

Patch 1 must establish this invariant from the current mutation and generation
publication architecture without adding a second authority, repair pass or
persisted count. If it cannot, this slice closes as a no-build.

`IndexPrefixCardinality` may add one bounded operation that iterates the
ordered `first_component_counts` range for exactly
`(IndexKeyKind::User, IndexId)` and counts keys, not stored row counts. Each
present key represents one non-empty leading component because the existing
mutation owner removes entries whose count reaches zero.

The operation must:

- reject a non-user key kind or mismatched index generation;
- return unavailable when metadata is undecodable or the data generation does
  not match;
- use the ordered identity range and stop at the first different identity;
- use checked count arithmetic and fail closed on impossible overflow;
- accept a caller-owned stop-after bound so over-budget cardinality can be
  detected without unbounded work; and
- expose no map, raw key or mutable metadata reference above `IndexStore`.

The stop-after value is the largest cardinality the canonical grouped policy
can definitely admit, plus one. Exhaustion below that sentinel is an exact
result. Reaching the sentinel is only an over-budget witness and is never
returned as the SQL count; it selects the predecessor fallback so the existing
typed error and its ordering remain authoritative.

`StoreHandle` remains the only session/executor proof boundary. The executor
derives the accepted-root identity from its pinned `EntityAuthority`, as the
current exact-cardinality tie-break path does, and asks `StoreHandle` for the
result. Session code must not borrow `IndexStore` or inspect
`first_component_counts` directly.

The completed metadata-key count is converted with checked arithmetic into
the canonical SQL `COUNT` result representation, `Value::Nat64`. Saturation,
wrapping and platform-width-dependent casts are forbidden.

For a populated journaled store reopened without materializing prefix
metadata, the exact result is unavailable by design. The existing prepared
scan runs. `v0.240.1` does not scan stable entries at startup, add a persisted
per-index distinct count, enumerate durable prefix digests, create a recovery
job or prewarm metadata. An empty journaled index may retain its existing
exact-zero proof. Fold and recovery may make the existing in-memory metadata
available only through their current lifecycle; this slice adds no repair path.

## Resource And Failure Semantics

The predecessor global DISTINCT executor has finite distinct-value and
retained-state budgets. A faster physical plan may do less work, but it may
not turn a query that currently fails its semantic admission limits into a
successful result accidentally.

For the fixed-width `Int32` cohort, the exact count is sufficient to prove a
conservative bound for the existing per-group distinct-value count and
retained key-state bytes. The exact executor must use the canonical grouped
and hard-request budget owners, not duplicate numeric constants in SQL code.
The metadata stop-after sentinel is derived from the currently remaining
canonical budgets after prior request work, not from their configured maxima.
Its decision is:

| Exact evidence | Budget proof | Action |
| --- | --- | --- |
| Unavailable | any | Prepared predecessor fallback |
| Available and success is conservatively proven | within all currently remaining caps | Atomically commit the complete logical charge bundle, then return the exact count |
| Available but a cap would be crossed or cannot be proven | uncertain/over cap | Prepared predecessor fallback, preserving current typed error and ordering |

Metadata probing records diagnostic/test evidence for keys examined and real
instruction work, but it does not consume logical distinct-entry or
retained-state budgets. On exact success, the canonical budget owner must
preflight the complete logical bundle against both execution-local and request
remaining capacity, then commit every category atomically before result
projection. A failed batch may not consume one category before another fails.

On unavailable, uncertain or over-budget evidence, no logical budget mutation
survives into prepared fallback. The fallback begins with the same semantic
budget state it would have had without the exact attempt; only the real bounded
probe instructions and diagnostic metadata-work observation remain. The
shortcut never fabricates a distinct hash set merely to reproduce allocation.
Any inability to implement this transactionally through the existing budget
authority closes the line as a no-build.

## Unavailability Versus Invariant Failure

These outcomes are distinct and must not share a catch-all `None` path:

| Class | Examples | Required action |
| --- | --- | --- |
| Ordinary unavailability | metadata not materialized, stale data generation, optional metadata undecodable, store/index not Ready, or budget success uncertain/over cap | Perform no semantic charge and enter the single prepared fallback |
| Structural invariant failure | non-user exact target, target from another accepted root/entity, impossible accepted `IndexId` generation mismatch, compiled fingerprint/target disagreement, checked-count overflow or internal borrow conflict | Return the existing exact-count invariant/corruption failure; never hide the defect with fallback |
| SQL shape ineligible at preparation | nullable/wrong-kind target, incomplete index, predicate, additional terminal or other frozen-admission failure | Cache/execute only the ordinary prepared plan; no exact probe occurs |

The owner call retains no index borrow across result projection or prepared
fallback. A structurally invalid compiled target is a programming or authority
error, not an optional evidence miss.

## Corruption Outcomes

The metadata invariant defines explicit outcomes for the focused corruption
fixtures:

| Injected state | Required outcome before exact result |
| --- | --- |
| Logical row removed while its index/metadata contribution remains | The row-generation mismatch makes exact authority unavailable and prepared fallback returns its existing result/error; attempting to republish the mismatched generation is an invariant failure |
| Physical user-index entry removed while its logical row remains | Index mutation clears synchronization, so prepared fallback runs; no synchronized undercount may be returned |
| Orphan user-index entry inserted without a logical row | Index mutation clears synchronization, so prepared fallback runs and retains the predecessor result/error; no synchronized overcount may be returned |
| Malformed index component invalidates optional decoding | Evidence is unavailable and prepared fallback runs with predecessor semantics |
| Target/root/index identity is forged or mismatched | Existing invariant/corruption error, never prepared fallback |

In particular, an orphan key plus apparently matching metadata may not
silently increase the SQL result when the predecessor logical-row scan would
exclude it. Supported mutation, rollback and corruption-injection APIs must be
unable to publish that state as synchronized. If the current architecture can
produce or accept it, the design is a no-build; adding an ad hoc row probe is
not an authorized repair.

Arbitrary memory modification that bypasses all Rust visibility and store
mutation boundaries remains outside IcyDB's supported detection model, exactly
as for existing exact index-prefix cardinality. This limitation does not relax
the required proofs over every maintained mutation and corruption-injection
surface.

## Rejected Alternatives

### Reuse 0.238 group seek

Rejected for this query. Group seek would visit representative physical index
entries and needs traversal, boundary and corruption handling. Exact
first-component metadata already contains the smaller sufficient fact. A
group-seek fallback after metadata failure would add a third physical choice
and adaptive state; the current prepared path remains the only fallback.

### Add an O(1) per-index distinct-count cache

Rejected. It would duplicate a value derivable from
`first_component_counts`, add mutation and recovery obligations, and create a
new independently synchronized state solely to avoid an O(distinct values)
metadata walk. The initial evidence has five distinct values.

### Persist or rebuild distinct metadata on startup

Rejected. That introduces stable format, upgrade, rebuild and corruption
state without evidence that journaled fallback frequency dominates supported
workloads. Cache absence affects performance only.

### Support Text or every scalar kind immediately

Rejected. Text requires an exact or conservative retained-byte proof using
variable payload lengths, while every additional scalar kind expands equality
and resource tests. The measured hotspot is `Int32`; breadth is not required
to prove the physical design.

### Support predicates, aggregate FILTER or nullable fields

Rejected. These require subset coverage, NULL omission or filtered-index
proofs and could make the number of index groups differ from the SQL input
set. They remain on the current general executor.

### Cache the returned count in the compiled command

Rejected. A count is data-generation state, not compiled schema state. Caching
it would add stale-result invalidation and make a command cache an alternative
data authority.

### Add a generic aggregate metadata framework

Rejected. No second aggregate has demonstrated the same sufficient metadata.
`SUM` and `AVG` require values, while `MIN`/`MAX` already have bounded indexed
routes. One owner-local target is the smallest design.

## Frozen Gates

All comparisons use clean `v0.240.0` and candidate trees, the same locked
dependencies, Rust toolchain, feature set, production profile and final Wasm
pipeline. Raw non-gzipped Wasm is authoritative; gzip is secondary.

| Dimension | Required result |
| --- | --- |
| 2,048 rows / 5 distinct cold query | at most 5,000,000 instructions and at least 110,000,000 saved |
| True-warm query | at most 4,000,000 instructions and no compiled-cache regression |
| Physical row/index work | 0 row gets and 0 physical index entries read |
| Metadata work | exactly the target identity's distinct keys plus at most one range-boundary probe; measured separately from physical index reads |
| 100% distinct at 2,048 rows | at least 75% faster than predecessor or close as no-build; result remains exact |
| Metadata unavailable | same predecessor result/error and row/index work, plus only the bounded metadata probe; no more than 2% instruction regression |
| Stop-after/over-budget fallback | no semantic budget residue, same predecessor result/error and row/index work, metadata keys examined bounded by the derived sentinel, and no more than 5% instruction regression |
| Incompatible shapes | exact predecessor route and result; no more than 1% regression |
| Mutation/lifecycle | exact after insert/update/delete and when current metadata is available; otherwise predecessor fallback |
| Raw Wasm | growth no greater than 8 KiB |
| Maintained runtime | report production files and net runtime lines against the six-file/~300-line design forecast; no hidden state or owner may be used to reduce the reported footprint |
| Production types/cache state | no net type increase, no cache slot, mutable owner, persisted state or invalidation edge |
| Public/stable surfaces | Candid, exports, generated API, stable extent and package versions unchanged |

The 5M gate is an acceptance boundary, not an aspiration. The 100%-distinct
case prevents optimizing only the friendly five-group fixture while moving
unbounded work into metadata traversal. If either performance gate fails, the
implementation and measurement fixtures are reverted and this slice closes as a
measured no-build. Gates are not weakened and the cohort is not redefined
after measurement.

Current repository governance treats file and delivery-domain counts as
review signals rather than execution limits. The original six-file/~300-line
forecast is therefore retained for honest comparison, while the hard
complexity gate remains zero new production types, cache slots, mutable owners,
persisted states or invalidation edges. The status document records the actual
footprint and explains every required authority seam.

## Required Proof Matrix

Semantic admission and equality:

- 0, 1, 5, 100 and 2,048 distinct `Int32` values;
- negative, zero, positive, minimum and maximum `Int32` edges;
- one single-field and one compound accepted index with the target first;
- compound suffix nullable/optional/omitting cases remain fallback, while an
  admitted compound proof establishes one key contribution for every row;
- two compatible indexes proving deterministic shortest-arity/name choice;
- selected compatible metadata unavailable while the second compatible index
  is available: prepared fallback without runtime reselection;
- duplicate-heavy and all-unique distributions;
- SQLite result equality for every performance fixture;
- `COUNT(DISTINCT age) AS ages` preserves the existing alias, column metadata,
  fixed-scale metadata and `Nat64` result shape;
- checked metadata-key-count conversion, including its impossible-overflow
  invariant failure;
- nullable target, Text target, expression target and unindexed target remain
  prepared fallback;
- filtered/expression index, target in a non-leading component and
  store-not-ready state remain fallback;
- predicates, aggregate `FILTER`, `HAVING`, additional projections, ordering,
  windows and grouped queries remain fallback.

Authority, cache and lifecycle:

- cold compiled-command miss and true-warm hit use the same exact target;
- metadata unavailable uses `QUERY_PLAN_CACHES` without a second command slot;
- unavailable metadata becoming available needs no command replacement;
- accepted publication creates a new outer compiled command and old requests
  remain bound to their old immutable authority;
- fingerprint mismatch cannot authorize or populate the occupied old slot;
- empty heap, initialized empty journaled and unmaterialized populated
  journaled stores distinguish `Exact(0)` from `Unavailable`;
- heap and journaled stores, journal replay, fold, projection reset,
  same-Wasm upgrade, reinstall and empty-store recovery;
- insert of an existing/new distinct value, update within/across groups and
  deletion of the last/non-last group member, including deletion of the final
  logical value back to positively proven `Exact(0)`;
- failed/rolled-back insert, update and delete at every mutation/publication
  seam preserve the prior exact state or leave evidence unavailable.

Budgets and corruption:

- exact success below all grouped limits;
- stop-after derives from currently remaining budgets; value-count boundary,
  retained-byte boundary and conservative uncertainty select fallback and
  reproduce the predecessor typed error/order;
- probe-only fallback leaves logical distinct/state counters unchanged, and
  successful multi-category batch charging is all-or-nothing;
- missing root, mismatched root, data-generation mismatch and borrow conflict;
- malformed metadata/index component makes exact evidence unavailable;
- injected missing row, missing index entry and orphan index entry produce the
  exact outcomes frozen in the corruption table, including no orphan overcount;
- no partial result or late fallback after exact output begins.

Build and regression:

- focused no-default, SQL-only, SQL+diagnostics and all-feature warning-denied
  package checks;
- the exact-count, aggregate `FILTER`, `AVG`, ordered DISTINCT group-seek and
  direct `COUNT(*)` sentinels retain their frozen ceilings;
- final raw/gzip Wasm, stable extent, Candid and exports;
- one diagnostics-enabled metadata-work counter or equivalent owner-level
  proof makes map entries examined unambiguous without adding a public metric;
- a focused stop-after/over-budget performance fixture locks the bounded probe,
  predecessor physical work and 5% double-work regression ceiling.

## Promotion And Closeout

Design review approved implementation after the result-authority,
atomic-budget, corruption-outcome and unavailability/invariant contracts above
were made explicit. Patch 1 established executable proof that:

1. maintained mutation and generation publication invalidate optional
   metadata before unsupported raw changes and publish synchronization only
   after complete transitions;
2. canonical budget ownership derives stop-after from both remaining scopes
   and atomically commits or rejects the complete semantic bundle;
3. unavailable, malformed or generation-mismatched evidence cannot return
   exact zero or a stale result;
4. the singular cache and planner selection owners require no second state;
   and
5. the frozen predecessor, hostile-cardinality, over-budget, fallback, Wasm
   and surface gates pass.

The measured implementation outcome and exact complexity delta are recorded
in [the 0.240.1 status](./0.240-status.md). There is no compatibility phase,
feature flag, partial landing or fallback mode to retain. Complete repository
and release validation remains user-owned.
