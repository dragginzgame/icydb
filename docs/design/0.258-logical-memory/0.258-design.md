## Outcome and scope

Applications name a durable canister namespace and store key instead of choosing
four physical IDs per journaled store and three control IDs. IcyDB derives role
keys; `ic-memory` resolves and persists physical placement. Host allocation
policy remains explicit at the integration boundary, not repeated in each store.

This is an ergonomics and ownership change, not memory compaction. It does not
reduce buckets, move existing data, reclaim retired slots, change memory profiles,
or add a second allocator. Accepted schema remains database semantic authority.
Heap stores do not acquire stable allocations.

### IcyDB integration and the lifecycle distinction

- [Canister model](../../../crates/icydb-model/src/node/canister.rs) owns the
  explicit namespace, memory profile, range and three control IDs today.
  [Store model](../../../crates/icydb-model/src/node/store.rs) derives store keys
  from physical ID and role. Replace the ID-derived portion with a durable store
  key; retain profiles and database roles.
- [Generated wiring](../../../crates/icydb-model/src/build/actor/db/store.rs)
  registers explicit ranges and key/ID pairs. Replace this mechanical plumbing
  with logical requests and committed resolutions. Remove the corresponding
  physical-ID fields and checks from the
  [canister](../../../crates/icydb-model-macros/src/node/canister.rs) and
  [store](../../../crates/icydb-model-macros/src/node/store.rs) macros in the same
  hard-cut landing, including fixtures and documentation.
- [Bootstrap integration](../../../crates/icydb/src/db/bootstrap.rs) already
  adopts a host's committed runtime without replacing its policy/profile, and
  verifies this database's declarations are present. Preserve that protection,
  comparing logical requests to their committed resolutions rather than
  reconstructing physical authority from generated constants.
- [Commit control](../../../crates/icydb-core/src/db/commit/store/control_slot.rs)
  retains at most 16 active-plus-retired store quartets. This is database
  incarnation/recovery state, not an allocator to delete automatically.
  [Convergence](../../../crates/icydb-core/src/db/database_format/convergence.rs)
  `reconcile_current_registry` retires an omitted store after checking its journal
  tail; it rejects a reintroduced retired quartet and changes with a pending
  marker. Generic allocation absence and database-store retirement are **not the
  same contract**. Preserve database safety and current retirement behavior in
  0.258 unless a separately reviewed lifecycle change is necessary.

Omitted store journal checks need historical memory access, while
`CommittedAllocations` contains current declarations only. The admission contract
below completes those declarations before commitment; L3 must prove that path
through generated production bootstrap, without a raw-memory bypass.

## Dependency contract (supplied by 0.14.1)

Logical requests feed the existing allocation validation/commit flow alongside
fixed host/library claims. The following requirements motivated the upstream
work; IcyDB consumes the released API rather than implementing another allocator.

1. Recover the existing ledger from its fixed root. Resolve known keys first;
   require their committed slots still satisfy current authority policy. Reject
   retired keys and conflicting fixed claims with typed errors.
2. For genuinely new keys, select only from the host-granted eligible pool.
   Exclude every historical claim, reservation and current fixed declaration.
   Assign new keys in a canonical order using the lowest eligible free IDs;
   never recompute existing assignments. Reject exhaustion before commitment.
3. Commit the complete resolved snapshot through the existing persistence owner,
   then expose key-based opens and resolved IDs through committed authority.
   Default and explicitly owned runtimes must share this flow. IcyDB must not
   choose an ID, recover another ledger, or cache an independent mapping.
4. Define the standalone host's pool and composed-host grants in the dependency
   contract. Removing per-database ranges must not silently authorize IcyDB to
   consume another library's address space. Raw unregistered manager users are
   not safely discoverable; hosts must declare their reservations/claims.
5. Establish numerical bounds at existing owners for requests, physical search,
   serialized ledger bytes, generation history and decoding before allocation.
   The finite 0–254 ID space bounds slot search, not all serialized history.
   Preserve fail-closed recovery and typed rejection without per-step budget
   machinery in IcyDB. Provide interrupted-write and oversized-input evidence.

The dependency's mechanism is qualified separately from generated IcyDB adoption.
Do not interpret upstream tests as proof of IcyDB lifecycle integration.

## Identity and admission decisions

### Key grammar and scope

Use an explicit namespace `N` and store key `S`, independent of Rust type names,
package paths and principals. Both are single segments matching
`[a-z][a-z0-9_]*`; each complete key must meet `StableKey`'s 128-byte limit.
Do not normalize case, truncate, hash or infer either identity. Keep version 1.

| Allocation | Exact key |
| --- | --- |
| Commit control | `icydb.N.commit.control.v1` |
| Startup control | `icydb.N.startup.control.v1` |
| Integrity progress | `icydb.N.integrity.progress.v1` |
| Store quartet | `icydb.N.store.S.{data,index,schema,journal}.v1` |

These retain the current control-key spelling; the older idea's added `canister`
segment is not adopted. The derived request authority remains `icydb.N`.
Match complete segments and exact roles, never substring/suffix guesses. Reserve
the `icydb.` domain for these allocations; unrelated library domains are ignored.
Unsupported keys within that domain reject rather than become invisible history.
No predecessor-key decoder is introduced.

### Preparation and host composition

The shared `icydb::db::prepare_memory_bootstrap` function operates on
`BootstrapAdmission` for the whole sealed host snapshot, not only the namespace
whose session starts first:

1. Validate current IcyDB logical declarations and their namespace authorities.
   Every namespace has its three controls; every current journaled store has its
   quartet. Generated declarations are proposals, not accepted-schema authority.
2. Inspect all recovered IcyDB-domain records, across the whole ledger rather
   than only currently granted ranges. Require every historical namespace to
   retain its three control requests in the original sealed input. Do not repair
   an omitted control using `include_historical`. Thus replacing/removing a
   namespace rejects even if a new authority has a different, valid grant.
   Adding another namespace while retaining existing ones is allowed.
3. For retained namespaces, select only omitted exact journal-role keys using
   `include_historical("icydb.N", key)`. Include journals for stores already
   retired by IcyDB: convergence still checks them. Do not select omitted data,
   index or schema allocations. A generically retired journal rejects through
   the dependency; it is not skipped. Current requests and all selections remain
   subject to current grants and final host policy.
4. Return to the existing resolve/validate/persist/publish flow. Only then open
   control/journal memory and run existing database convergence. Allocation
   commitment does not mean schema or store-lifecycle admission has succeeded.

The host owns grants. Move ranges out of database schema declarations; do not
infer ownership of free IDs. A standalone host explicitly grants its chosen pool
to `icydb.N` using the existing range registration (for example, 100–254 when it
owns that pool). A composed host supplies disjoint grants alongside other library
claims/reservations. No grant means rejection, not an automatic fallback pool.

IcyDB-owned cold bootstrap uses a policy calling this shared preparation function.
A host-owned policy calls the same function once in its `prepare_bootstrap` hook,
alongside other consumers, and includes its semantics in the policy identity.
This is a required host integration contract, not protection against a host that
bypasses it. Warm adoption checks current logical requests against committed
resolutions without replaying preparation or replacing policy/profile. Missing
historical access fails through normal committed opens; there is no late second
commit. A warm capability alone cannot prove that a custom host ran admission.

### Store identity: accepted lifecycle

Preserve current database removal/addition semantics, as confirmed by the user on
2026-09-17. Store keys are permanent identities: changing one is removal plus a
new store, never a rename or data migration.
`reconcile_current_registry` already allows that operation after checking the old
journal is empty, new roots are fresh, the registry limit is respected and no
pending marker blocks the change. An empty journal does **not** establish that
the old store has no rows; its data remains allocated and is not copied into the
new store. Reintroducing its retired identity remains rejected.

This cannot detect a mistyped store key while allowing the identical intentional
remove/add operation. Rejecting all combined remove/add changes would be a new
lifecycle restriction, not a deduction from allocation metadata; it would also
not solve a replacement split over two deployments. Do not add a rename detector,
another identity ledger or an intent flag without a separately approved need.
Application documentation and examples must describe keys as permanent identities.

Required integration matrix (execution evidence is recorded in the status tracker):

| Change or failure | Required outcome |
| --- | --- |
| Reorder declarations or rename Rust types only | Existing keys/slots unchanged. |
| Add store or namespace, keeping historical namespaces | New placement only; existing assignments unchanged. |
| Remove/replace a namespace, including into a newly granted pool | Reject during preparation; existing allocation generation unchanged. |
| Omit a store with empty journal | Select old journal, then existing convergence may retire the store. |
| Omit store with debt, or change registry with pending marker | Database convergence rejects; no database retirement/publication. Allocation commit may already have succeeded. |
| Change a store key | Same checks as remove/add; no data transfer or typo-detection claim. |
| Reintroduce database-retired store | Existing database convergence rejects. |
| Revoke grant or select generically retired journal | Dependency rejects before publishing an allocation capability. |
| Two namespaces, overlapping-looking names, foreign library journal | Exact scoped selection; no foreign journal capability. |
| Host already committed without required historical journal | Normal open fails; no policy replacement, retry commit or bypass. |

Include malformed IcyDB roles, incomplete current role sets and simultaneous
multi-namespace bootstrap in L3's direct tests. Use the production memory runtime,
not convergence's test-only memory lookup, for omission/debt coverage.

Initial adoption is a pre-1.0 hard cut: recreate/reinstall affected databases.
No ID-derived-key aliases, old-key adoption, dual formats or migration bridge.
Export/import would be separately authorized work, not an implicit prerequisite.

## Need, alternative and complexity control

- Need: manual coordination of four IDs per store, three controls and ranges.
- Simplest alternative: one starting ID per store. It shortens attributes but
  leaves the physical coordination problem with applications.
- Canonical owners: applications name identity; IcyDB defines database roles and
  lifecycle; hosts grant space; `ic-memory` alone allocates, persists and opens.
- State-space delta: IcyDB replaces explicit placement with one logical path;
  no explicit/automatic mode, new allocator ledger, inference mode or reclamation
  state. The dependency gains request resolution before its existing commit.
- Retain database recovery checks and memory profiles. Delete obsolete ID fields,
  role-key construction and generated fixed placement, not unrelated code.

Host admission is a stateless facade-owned function, not generated policy copies.
Its typed errors distinguish unsupported roles, invalid declarations, incomplete
role groups, removed namespaces and dependency selection failures. The alternative
is duplicating IcyDB admission in each host; the shared function adds no persisted
state, mode or configuration. L3a qualifies this public host boundary separately
from L3's generated hard cut. Generated standalone bootstrap now invokes the
shared hook, and composed hosts must include it before committing allocations.

## Qualification and release boundary

Required tests: duplicate/oversized keys; deterministic fresh placement;
reordering and additions without relocation; host fixed claims/reservations;
range-policy change; exhaustion; dependency absence/reintroduction/retirement;
IcyDB omission with empty/nonempty journal and pending marker; accidental
namespace/key replacement; failed persistence and interrupted recovery; opens
before commitment; host-owned and standalone runtime bootstrap; profile mismatch.
Maintain current-format tests only, with no legacy decoding route.

Measure fresh bootstrap and warm opening in IC instructions/cycles, raw Wasm
bytes (gzip secondary), metadata bytes and allocated pages separately. Report
files/lines and removed versus introduced flows. No native timing. L3a's
allocation-admission tests exercise production recovery, not generated database
convergence. L4 now records a matched before/after actor measurement, including
the integration and dependency change together; it does not isolate hook cost.
Metadata bytes and isolated cold-bootstrap instructions remain unmeasured.

Verdict: L2/L3a and L3 are complete; L4 records the broader matrix and matched cost
qualification with explicit coverage limits. The line is ready for the user-owned
release gate; no further upstream mechanism is identified. Do not claim the namespace/journal rules
are implemented by the dependency update alone, or expand the line into storage
reclamation or another broad accounting cleanup.
