# IcyDB 0.253 — Nested Relations

- **Status:** Implementation in progress; Landing Slice 1 measurement contract
  and numerical relation-work limits are complete
- **Date:** 2026-09-04
- **Target line:** 0.253, after the 0.252 line has a ready/complete closeout
- **Current authority:** 0.252 closed at published `v0.252.11`; the user opened
  0.253 implementation on 2026-09-04. Landing Slice 1 is the current completed
  worktree handoff; later slices remain separately gated.
- **Compatibility posture:** Pre-1.0 recreation-only hard cut. A 0.253 binary
  must not upgrade a 0.252 database in place. Data that must survive is
  exported through the old binary, then imported through ordinary current-form
  writes into a fresh 0.253 installation. Every changed proposal,
  accepted-schema, reverse-key, migration and integrity representation remains
  current format version `1`; predecessor forms are not decoded or upgraded.
- **Primary downstream evidence:** Toko's relation annotations and remaining
  application-owned reference validation

## 1. Decision

IcyDB 0.253 should add referential integrity for scalar references located
inside accepted composite values and repeated aggregates.

This is a real missing database capability, not an authoring convenience. The
narrow feature is approved because it does not create a second relation
system. It adds one new way to extract target keys, then converges immediately
on the existing strong-relation machinery:

```text
direct scalar/tuple source slots ── direct fast path ─┐
                                                     ├─> sorted, deduplicated
accepted rooted nested path ── generic interpreter ──┘   RelationTargetKeys
                                                               │
                                                               v
                                            existing target validation,
                                            reverse maintenance, RESTRICT,
                                            batch overlay and integrity flow
```

That convergence is the architectural boundary of this minor. Nested
relations do not gain a separate enforcement mode, target-key encoding,
reverse-index implementation, transaction rule, recovery route or integrity
definition.

The capability remains deliberately relational:

- a nested target must exist for the whole lifetime of the source state in
  which the reference occurs;
- a reference may occur below an optional value, enum variant, list, set or
  map value and contributes no edge while that occurrence is absent;
- every accepted rooted occurrence is an independently identified relation;
  and
- the database enforces target existence and target-delete restriction for
  those extracted keys exactly as it does for a direct relation.

The feature does **not** add nested querying, joins, member indexes, collection
expansion or partial nested updates. A nested `asset_id` may prevent deletion
of the referenced asset, but it does not make
`WHERE storefront.pic_asset_id = ?` a supported query.

### 1.1 Review Closure

| Review issue | Frozen resolution |
| --- | --- |
| Upgrade boundary | Recreation only; old-binary export and fresh current-form import are the only row-retention route. |
| Aggregate work | Per-image limits plus four shared per-atomic-batch counters; exact numerical ceilings are frozen by Slice 1. |
| Relation identity | Existing durable `RelationId` is strengthened with a monotonic non-reuse high-water and a disjoint physical-generation lifecycle. |
| Optional/named traversal | Both are explicit, contract-bearing and charged path instructions. |
| Extractor scope | One implementation supports `All` and exact `Relation(RelationId)` projection. |

## 2. Demonstrated Need

The Toko audit found 18 intended relation annotations. Two are ordinary direct
oracle relations. The remaining 16 relation leaves occur inside 11 reusable
value types and cannot currently become accepted relation edges because model
lowering discovers relations only at entity-root fields.

This leaves applications to duplicate database semantics:

- decode the containing composite;
- find every nested reference;
- validate target existence on each write;
- account for same-batch creates and deletes;
- block target deletion or repair stale references;
- repeat the logic during migration and integrity work; and
- keep the manual walker synchronized with schema evolution.

The row is already an accepted typed value and the relation is already a
strong database invariant. Requiring each application to reproduce the
extractor and lifecycle rules is the wrong ownership boundary.

The audit also proves that not every identifier-looking leaf should become a
relation. Section 12 freezes the Toko classification rule before adoption.

## 3. Scope And Vocabulary

| Term | Meaning |
| --- | --- |
| Direct relation | The maintained relation whose source key is read from one or more entity-root slots. |
| Nested relation | A strong relation whose scalar source key is reached by interpreting an accepted rooted path below an entity field. |
| Rooted occurrence | One complete route from one entity field through accepted value shapes to one annotated scalar leaf. |
| Path program | The accepted, identity-based sequence of structural steps used to reach a nested scalar relation leaf. |
| Raw reference occurrence | One scalar value emitted by path traversal before sorting and duplicate removal. |
| Target keys | The maintained canonical relation-target key representation consumed by target and reverse enforcement. |
| Strong relation | A reference whose target must exist for the entire lifetime of every source state in which the reference occurs. |

“Nested” describes the source-key location only. It does not weaken the
relation contract or widen any query or mutation surface.

## 4. Accepted Capability Matrix

### 4.1 Admitted Source Shapes

| Source shape | 0.253 contract |
| --- | --- |
| Direct scalar or maintained direct composite source | Existing fast path and semantics remain. |
| Required/optional record member | Admitted when the rooted path ends in an accepted scalar key kind. Every optional boundary is an explicit path instruction; an absent optional ancestor contributes no target key. |
| Enum variant payload | Admitted for the explicitly identified variant. Other variants contribute no key. |
| List item | Admitted; every item is traversed in canonical stored order for charging purposes, then target keys are sorted and deduplicated. |
| Set item | Admitted; every canonical set item is traversed. |
| Map value | Admitted; every value is traversed in canonical map-key order. |
| Repeated combinations | Admitted subject to the fixed path, work and raw-reference limits in Section 10. |
| Map key | Rejected in 0.253. Map keys remain structural ownership keys, not relation-bearing value positions. |
| Tuple position | Rejected in 0.253; no new positional authoring or diagnostic path syntax is introduced. |
| Opaque blob or application JSON | Rejected; IcyDB has no accepted structure to traverse. |
| Recursive value cycle | Rejected for relation paths even when storage admits a separately bounded recursive value. |
| Composite target primary key assembled from multiple nested leaves | Rejected. A nested relation terminal produces one scalar through the maintained target-key conversion. |

Named collection aliases are traversable through an explicit accepted
named-value step followed by their list, set or map-value shape. Every optional
boundary is also explicit. Null or missing ancestors produce no edge, not a
null target key.

### 4.2 Target Contract

A nested relation may target exactly the entity/key combinations accepted by
the existing strong-relation binder when one scalar terminal can be converted
to that target's key. It must use the existing target-key conversion and
canonical encoding. ULIDs and other scalar keys do not receive a nested-only
encoding.

The extractor returns target keys in canonical sorted order with duplicates
removed. Ten occurrences of the same target under one relation create one
logical reverse edge. The raw occurrence count is nevertheless charged before
deduplication so repeated duplicates cannot bypass the admission budget.

### 4.3 Strong Semantics Only

There is one relation mode. Every accepted direct or nested relation means:

1. each extracted target exists in the final atomic-batch image;
2. the source-to-target reverse edge reflects the committed source image;
3. deletion of a referenced target is restricted in the final batch image;
4. activation, migration and integrity evaluate the same invariant; and
5. corruption or budget exhaustion fails closed through a typed boundary.

0.253 does not add weak, conditional, historical, external, cross-canister or
cross-shard relation modes.

## 5. Authoring And Proposal Lowering

### 5.1 Recursive Discovery

Model-only proposal lowering recursively discovers relation annotations in
accepted value definitions reachable from entity fields. Discovery is
performed per entity root, not once per reusable value type.

If the same `Storefront` value type occurs under `primary_storefront` and
`preview_storefront`, the same annotated `asset_id` leaf produces two proposed
rooted relations. They receive independent accepted `RelationId` values and
independent reverse domains. Neither value-type identity nor terminal field
identity collapses them.

Likewise, two annotated leaves below one root field are distinct relations even
when they target the same entity and scalar key kind.

### 5.2 Proposal Identity

Generated models remain proposal and reconciliation input only. Runtime code
must never reconstruct a nested relation by walking generated Rust metadata.

A proposed nested relation carries:

- its source entity key;
- its full rooted source-key path, including value-type, record-field and enum
  variant source identities where applicable;
- every collection traversal step;
- the terminal scalar contract; and
- the ordinary relation target path.

The proposal codec remains current format version `1` and changes in place.
A deterministic bounded diagnostic name may be derived from the rooted source
path, but neither that name nor a path hash is enforcement identity. If a
bounded derived source key is used for reconciliation, the complete structured
locator accompanies it and any collision is a typed schema rejection.

### 5.3 Reconciliation

The catalog reconciles each rooted occurrence independently. An accepted
rename that preserves the underlying accepted root/member/variant identities
preserves the relation's `RelationId`. Removing a rooted relation and later
adding one allocates a new relation ID; its initial physical generation is
assigned by the ordinary activation path.

Standalone reusable value types own no runtime relation. Only their rooted
occurrences under an accepted entity can instantiate relation identity.

## 6. Accepted-Schema Path Program

Every accepted relation has its own non-zero `RelationId`. Direct relations
retain that requirement; nested relations do not infer identity from a root
slot, terminal member, type, rendered name or hashed path.

The logical current-form accepted snapshot is:

```text
AcceptedRelation {
    id: RelationId,
    physical_generation,
    name,
    target_path,
    source: Direct { field_ids }
          | Nested { root_field_id, steps, terminal_scalar_contract },
}
```

The nested `steps` program contains the complete route. Its instructions are:

```text
EnterNamed {
    accepted_type_identity,
    expected_shape,
    expected_input_contract,
    expected_output_contract,
}
OptionalSome {
    expected_optional_contract,
    expected_inner_contract,
}
RecordMember {
    accepted_record_identity,
    accepted_field_identity,
    expected_input_contract,
    expected_output_contract,
}
EnumVariantPayload {
    accepted_enum_identity,
    accepted_variant_identity,
    expected_input_contract,
    expected_payload_contract,
}
ListItems { expected_input_contract, expected_item_contract }
SetItems { expected_input_contract, expected_item_contract }
MapValues {
    expected_input_contract,
    expected_key_contract,
    expected_value_contract,
}
```

There is no context-dependent rule for whether a wrapper is “semantically
relevant.” Every transition through a named accepted value emits
`EnterNamed`, including named wrappers around scalars and collections. A named
record therefore has `EnterNamed` followed by `RecordMember`; a named list has
`EnterNamed` followed by `ListItems`; and a named scalar wrapper has
`EnterNamed` before its terminal.

Every nullable boundary emits `OptionalSome`, including a nullable root,
nullable record member, optional collection item and nested optional. The step
costs one traversal work unit whether the value is absent or present. Absence
ends only that traversal branch; presence continues with the exact recorded
inner contract.

Every instruction records its expected accepted input and output contracts.
Binding rejects a mismatch between the program and accepted catalogs before
row execution. A current-form row whose runtime shape violates the bound
contract is typed corruption; it is never treated as an absent optional or
silently unwrapped.

The program obeys these rules:

- `root_field_id` is the accepted entity field identity, never its Rust name,
  display name or source declaration position;
- record and enum steps use accepted-schema identities, never Rust member
  names or ordinal source positions;
- named and optional transitions are explicit and deterministic rather than
  inferred by the walker;
- collection steps are explicit and cannot be inferred from a runtime value;
- the terminal contract is one accepted scalar kind compatible with the target
  primary key;
- path binding is completed when the schema is accepted, not during a write;
  and
- runtime authority is only this accepted snapshot plus the accepted value
  catalogs it references.

If current composite catalogs lack an identity required by this program, 0.253
adds that identity to the current version-1 accepted representation. It does
not substitute a source name or unstable ordinal.

The persisted relation snapshot, source-binding catalog, proposal codec,
fingerprint, corruption inspector and migration codec all move to this one
current version-1 shape. No predecessor decoder, translator or fallback is
retained.

## 7. Relation-Owned Reverse Identity

The maintained reverse index currently derives physical index identity from
the first local field slot. That is invalid for nested relations: two leaves
below the same root field would collide, and the root slot does not identify
the relation.

0.253 hard-cuts reverse identity to the accepted `RelationId`.

The current-form reverse key domain is logically:

```text
relation-system-domain
  / source EntityTag
  / relation physical_generation
  / exact big-endian RelationId (u32)
  / canonical target key
  / canonical source primary key
```

Implementation should use one reserved relation-system index domain rather
than widen every ordinary `IndexId`. The exact `RelationId` is an encoded key
component and therefore is neither narrowed to a field-slot `u16` nor replaced
by a hash. Target-delete bounds include the physical generation and exact
relation ID before the target key.

Consequences:

- two nested relations below one entity field cannot collide;
- two rooted occurrences of one reusable type cannot collide;
- direct and nested relations use the same reverse-key form;
- relation removal and generation changes prove or clear the exact relation
  domain; and
- each reverse entry contains a four-byte relation-ID payload component. Its
  net encoded-size delta must be measured because it replaces part of the
  existing field-slot/index-derived identity rather than only appending bytes.

### 7.1 `RelationId` Lifecycle

The current system already persists a non-zero `RelationId` in accepted
relation snapshots and source bindings and uses it during reconciliation. It
does **not** yet provide the complete 0.253 semantic identity contract: current
allocation is based on the maximum live relation ID, so removal of the highest
ID can permit later reuse, and reverse storage is still identified from a
field slot. 0.253 therefore strengthens an existing durable identifier rather
than merely renaming a new concept.

The exact lifecycle is:

- the `RelationId` namespace is local to one source `EntityTag`; the reverse
  key always carries both identities;
- a fresh catalog allocates IDs monotonically from `1` in canonical rooted
  relation proposal order;
- each source entity persists `relation_id_high_water`, the greatest ID ever
  allocated in that entity catalog lifetime;
- adding a relation computes `relation_id_high_water + 1` with checked
  arithmetic, allocates that value, then persists it as the new high-water;
- removed IDs are never reused during that entity catalog's lifetime, even if
  the removed relation had the greatest allocated ID;
- allocation past `u32::MAX` is a typed schema-admission failure before a
  candidate catalog is persisted; and
- recreation starts a new catalog lifetime and may assign a new deterministic
  ID set because no predecessor accepted or reverse state survives.

Semantic preservation and physical generation are disjoint:

| Change | `RelationId` | `physical_generation` |
| --- | --- | --- |
| Display/source rename that preserves every accepted root, path, terminal and target identity | Preserve | Preserve |
| Accepted entity, type, field or variant rename/reorder that preserves the identities referenced by the bound program | Preserve | Preserve |
| Physical reverse rebuild with no semantic relation change | Preserve | Advance to a fresh checked generation before writing the replacement domain. |
| Root field, path step, optional/wrapper contract, terminal scalar contract, target entity/key or enforcement semantics changes | Allocate a new ID | Start the new relation's generation through the ordinary activation path. |
| Remove relation | Retire permanently for this entity catalog lifetime. | Its physical domain is removed through the maintained bounded lifecycle. |

Generation `0` is reserved for the initial physical domain created in a fresh
catalog where no backfill is required. Any activation or physical rebuild over
existing current-form rows assigns an activation generation strictly greater
than the relation's preceding generation. A generation is never decremented
or reused for the same `RelationId`.

`physical_generation` identifies one physical materialization of an unchanged
semantic relation. It never decides whether two relation definitions are the
same. Generation exhaustion is a typed schema-transition failure; it cannot
wrap or force a new semantic `RelationId`.

### 7.2 Recreation-Only Boundary

The reverse key is derived state, but 0.253 does not use that fact to promise
an in-place rebuild from a 0.252 database. The accepted relation/source-binding
catalog and reverse-key form both change, so the upgrade contract is exactly:

1. while the old binary is installed, export any rows that must survive using
   its maintained public/application export path;
2. reinstall or recreate the database actor so no old accepted catalog, row
   store, journal, activation state or reverse/index state remains;
3. install the 0.253 binary, accept its compiled current-form proposal into a
   fresh catalog; and
4. import data through ordinary 0.253 writes, which validate and construct all
   current-form relation state.

A 0.253 binary must reject upgrade-mode startup over 0.252 stable state with a
typed incompatible-format failure. No old structure remains readable “long
enough” to locate rows, and there is no row-preserving regeneration path,
reverse-only rebuild path, predecessor catalog decoder or implicit upgrade.

Within a fresh 0.253 catalog lifetime, current-form activation, migration,
integrity and physical relation rebuild remain supported. Those operations do
not read or regenerate predecessor 0.252 state.

## 8. One Shared Extractor

There is one runtime relation projection API. Conceptually it is:

```text
extract_relation_target_keys(
    accepted relation projection plan,
    accepted structural row image,
    ProjectionScope::All | ProjectionScope::Relation(RelationId),
    budget: &mut RelationProjectionBudget,
) -> Result<RelationId -> RelationTargetKeys, TypedRelationProjectionError>
```

The plan is an ephemeral binding of the accepted snapshots; it is not a second
schema authority. It may group programs by root field and share materialized
root values, but such optimization cannot change results or budget charging.

“One extractor” means one implementation and one semantic authority, not that
every caller projects every relation:

- `ProjectionScope::All` projects every applicable direct and nested relation
  for source-row commit preparation, activation/backfill and whole-row
  integrity work; and
- `ProjectionScope::Relation(id)` uses the same binding, interpreter,
  conversion, sorting and deduplication logic for one exact accepted relation.

The scoped form rejects an ID not owned by the source entity. It touches only
the root/path required by that relation and charges only that projection.
Target-deletion verification already learns the exact `RelationId` from the
reverse domain and must use this scoped form when re-projecting a source row.
An unrelated nested relation in that row therefore cannot add work or cause a
budget failure during targeted verification.

The budget object owns per-image counters and may also borrow the caller's
cumulative operation budget. Commit preparation supplies the one shared atomic
batch budget defined in Section 10; activation, migration and integrity supply
their maintained bounded-job budgets. Budget plumbing does not create a second
walker or conversion path.

The extractor has two internal routes:

- a separate direct scalar/tuple-slot fast path that preserves existing
  direct-relation cost and permits the nested interpreter to dead-strip; and
- one generic accepted-value interpreter for every nested path.

The nested interpreter is data-driven. It does not generate recursive Rust
extraction functions per composite type, enum variant or relation path. That
rule protects Wasm size, monomorphisation and function count.

All extraction returns the maintained target-key type after the maintained
scalar-to-target-key conversion. Sorting and duplicate removal happen at this
shared boundary. Downstream target validation and reverse maintenance cannot
distinguish whether a key came from a direct slot or a nested path.

The same API is mandatory for:

- ordinary commit preparation, using `All`;
- insertion, replacement and removal of reverse entries;
- source removal and target-deletion verification, using the narrowest valid
  scope;
- candidate activation and backfill, using `All` for each admitted row image;
- current-form schema migration and relation rebuild;
- deep integrity checking and repair admission, using `All` or exact relation
  scope according to the bounded job; and
- recovery validation wherever a row image must be re-projected.

No consumer may carry its own composite walker. If a lifecycle operation needs
different reporting or continuation behavior, it wraps the same typed result;
it does not reimplement extraction.

## 9. Commit And Lifecycle Semantics

### 9.1 Source Transition

Commit preparation extracts the old and final new row images through the same
accepted relation projection plan. It computes reverse removals and additions
from their canonical target-key differences. Optional or variant transitions
naturally add or remove keys; complete aggregate replacement remains the only
write surface.

The containing root value should be structurally decoded/materialized once per
row image and reused by all paths rooted there. Repeated path interpretation is
bounded independently of this optimization by Section 10's logical work
definition.

### 9.2 Final Atomic-Batch Image

Nested relations preserve the maintained final-batch overlay exactly:

- creating a target and creating or updating a nested reference to it in the
  same atomic batch succeeds, independent of operation order;
- removing the last nested reference and deleting the target in the same
  atomic batch succeeds;
- deleting a target while any final direct or nested source reference remains
  fails with the ordinary relation restriction; and
- a source transition is validated against final target existence, not only
  the pre-batch snapshot.

There is no nested-specific transaction phase and no application-visible
ordering requirement.

### 9.3 Activation, Migration, Integrity And Recovery

Candidate activation binds current-form path programs, extracts candidate row
images within the same per-image limits, constructs current-form reverse
state, and promotes only after complete target validation.

Migration uses the accepted source/target catalogs and the same extractor. It
cannot reconstruct a missing path from generated models. Relation creation,
removal, path-preserving rename and generation changes remain catalog-native;
SQL DDL is only a frontend.

Deep integrity verifies that extracted canonical keys and stored reverse edges
agree in both directions. A malformed accepted value, invalid path terminal or
budget-exceeding persisted row is a bounded corruption finding, never a reason
to skip the relation or fall back to generated metadata.

Recovery replays only the current relation key shape and fails closed on an
invalid current-form relation projection. No old reverse-key inspector or
repair bridge remains.

## 10. Deterministic Limits

The 4 MiB row ceiling bounds bytes but does not adequately bound a value made
of many tiny nodes or repeated duplicate references. Per-image bounds alone
also do not bound an atomic batch containing many individually valid rows.
0.253 therefore has two cumulative budget layers.

### 10.1 Per-Image Limits

| Limit | Contract value | Charging rule |
| --- | ---: | --- |
| Maximum accepted nested relation path steps | **64, frozen** | Count every explicit `EnterNamed`, `OptionalSome`, record, enum or collection instruction after the root. |
| Maximum nested relation traversal work units per source row image | **349,440** | Charge one unit for each path-instruction evaluation against one frontier occurrence, aggregated across the projected nested relation programs for that scope and row image. Shared-prefix optimization does not reduce the logical charge. |
| Maximum raw nested reference occurrences per source row image | **5,460** | Charge every scalar terminal occurrence across the projected nested relations before sorting or deduplication. |

These are measured contract constants, not deployment defaults. The
3,276-row one-delta boundary comes from the existing 16,384-unit commit window
at five work units per direct-relation insert. The 2,730-row two-delta boundary
comes from the same window at six units per replacement; its old/new images
produce exactly 5,460 raw references and reverse deltas. Multiplying that
measured mixed boundary by the frozen 64-step path ceiling yields 349,440
traversal work units. The non-power-of-two limits therefore follow existing
commit admission and the measured stable-tree mix rather than convenience.

The limits apply separately to each old or new row image. A
`ProjectionScope::Relation(id)` charges only that relation; `All` aggregates
all applicable nested programs for the image. Direct relation slots do not
invoke or retain the nested walker merely to share these per-image counters.

### 10.2 Per-Atomic-Batch Limits

Commit preparation owns one `RelationCommitBudget` for the complete atomic
batch and passes it by mutable reference through every old/new projection and
relation enforcement action. It is not recreated per entity, operation, row,
relation or projection scope.

| Required batch counter | Contract value | Exact charging rule |
| --- | ---: | --- |
| Nested traversal work | **349,440** | Add every per-image nested traversal work unit across all old and final-new row images projected by the batch. |
| Raw relation references | **5,460** | Add every raw terminal occurrence emitted by direct and nested relations across old and final-new images, before per-relation deduplication. |
| Unique target lookups | **3,276** | Charge the first validation request for each distinct `(target EntityTag, canonical target key)` in the final-new reference set, whether final-batch overlay or stable state satisfies it. Reuse of that batch-wide result is not charged again. |
| Reverse deltas | **5,460** | Charge every distinct physical reverse-key insert or delete remaining after old/new relation-key difference and batch-wide coalescing. |

The fixed calibration harness measures high-cardinality stable-tree hits,
misses, inserts, deletes, source replacement, target `RESTRICT`, and both
one-delta and two-delta first-over-limit boundaries. Its worst admitted batch
uses 4,928,211,587 instructions against the applicable 40-billion-instruction
IC update ceiling. That leaves 35,071,788,413 instructions, including the
required 10-billion-instruction (25%) reserve for surrounding commit and
recovery work. The exact provenance, actor shapes, artifact baselines and path
fixtures are recorded in the
[Landing Slice 1 receipt](0.253-landing-slice-1-receipt.md).

The batch counters cover direct relation work where specified even though the
nested interpreter remains dead-stripped from a direct-only actor. Small fixed
counter operations are not a reason to link nested traversal code.

After Slice 1, these per-image and per-batch constants become schema/runtime
contract rather than deployment configuration. An actor cannot select private
limits. A later change requires an explicitly designed contract revision.

### 10.3 Failure Semantics

Failure behavior is deterministic:

- an overlong program is rejected during schema admission;
- an authored row that exceeds traversal or raw-reference limits fails with a
  typed admission error before journal or reverse mutation;
- a batch that exceeds traversal, raw-reference, unique-target-lookup or
  reverse-delta budget fails during commit preparation before any journal, row,
  index or reverse mutation;
- candidate activation records the bounded typed finding and cannot promote;
- migration stops or resumes through its existing bounded continuation model
  without partially accepting the offending row;
- integrity reports a bounded corruption finding for already persisted state;
  and
- the same input and accepted snapshot fail at the same logical unit regardless
  of map implementation, cache hits or shared-prefix optimization.

The pathological-collection proving actor must demonstrate this boundary; the
row-size ceiling alone is not acceptable evidence. The maximum-atomic-commit
actor must also prove that the exact admitted maxima complete with the required
instruction headroom and that the first over-limit unit fails deterministically.

## 11. Explicit Non-Goals

0.253 does not add:

- dotted SQL paths through lists, sets, maps or enum payloads;
- nested filtering, ordering, grouping, aggregate input or projection beyond
  the separately maintained nested-storage query contract;
- joins or relation traversal in queries;
- automatic indexes on relation-bearing members;
- multikey or collection-member indexes;
- uniqueness for nested occurrences;
- partial composite, member, variant, element or map-entry updates;
- a weak, optional-enforcement, conditional, historical, external,
  cross-canister or cross-shard relation mode;
- composite nested source assembly for a composite target primary key;
- runtime schema reconstruction from generated models;
- generated recursive extractor code per value type or path; or
- a generic predecessor export/import facility; applications that need to
  retain pre-0.253 data must use an already maintained application export path
  before recreation.

Relation introspection may render the accepted rooted path for diagnostics. It
does not expose that path as a queryable field-path promise.

## 12. Toko Classification And Adoption

Toko adoption must classify semantics before adding or retaining `rel`. The
test is not “does this identifier sometimes need to exist?” It is “must this
target exist for the entire lifetime of every source state in which this value
occurs?”

| Toko reference class | 0.253 treatment |
| --- | --- |
| Existing direct oracle relations | Remain ordinary strong relations and prove direct-path parity. |
| Storefront assets, `CustomSpec`, generator mapping/scoring references, and vendor/claim references | Adopt nested `rel` only where the lifetime test is proven. These are candidates, not blanket approvals based on their names. |
| Historical selected-part references and generator snapshot IDs | Keep as ordinary scalar IDs. A historical snapshot must not be invalidated when the live target disappears. |
| `Recipient::User`, friends-list references and workspace pins that identify another canister or shard | Keep as ordinary scalar IDs. Local strong relations cannot prove external existence or restrict external deletion. |
| `AssetSelection` references required only for live/active tokens | Keep explicit domain validation. Conditional existence is not a strong relation. |

0.253 will not add weak or conditional relations to make `AssetSelection` fit.
Toko may eventually remodel draft and active state so the strong reference is
present only in the active representation; until then, explicit domain
validation is the correct owner.

Toko adoption is complete only when:

- every added nested `rel` has a recorded lifetime justification;
- historical, external and conditional identifiers remain visibly ordinary;
- replaced manual target-existence and delete-restriction validation is
  deleted rather than retained as a second authority;
- application-only policy validation remains where it still owns distinct
  semantics; and
- the `project_instance` proving actor passes the net Wasm gate after those
  deletions.

## 13. Complexity And Performance Model

### 13.1 State-Space Delta

The conceptual state-space increase is controlled:

| Dimension | Delta |
| --- | --- |
| Relation enforcement mode | None; strong relations only. |
| Accepted source locator | One tagged source shape: direct slots or one rooted nested path program. |
| Relation identity | Strengthen the existing persisted/reconciled `RelationId` with a durable non-reuse high-water and exact reverse authority. |
| Extraction authority | One shared API with a direct fast path and one generic nested interpreter. |
| Reverse enforcement | Existing flow after target-key extraction. |
| Transaction semantics | Existing final-batch overlay. |
| Query/mutation surface | None. |
| Configurable behavior | None; limits are fixed contract constants. |

The implementation is moderately more complex inside schema lowering,
accepted codecs and relation projection. It should simplify Toko and other
applications by deleting duplicated validation and preventing lifecycle
walkers from diverging.

The initial audit estimated 25–40 files and 1,500–3,000 lines. That is plausible
for the central path but 3,000 lines is optimistic once current-form codecs,
corruption fixtures, activation, migration, recovery, final-batch coverage,
budget cases and Toko regressions are included. Planning should allow roughly
30–50 files and 2,000–4,000 net lines across the complete minor. These are
reporting estimates, not permission to combine independent work or omit direct
tests and documentation.

Every landing report must include files touched, approximate line delta, and a
judgment that the implementation shape became simpler, stayed neutral or
became more complex.

### 13.2 Time And Memory

For a row image, nested projection is bounded by:

```text
O(logical path work + R log R)
```

where `R` is raw terminal occurrences before canonical sorting and
deduplication and is bounded by the frozen per-image and batch constants.
Reverse writes remain proportional to changed unique target keys, not
duplicate occurrences. Runtime memory is bounded by the accepted row/decode
ceilings and the 349,440-work/5,460-reference budgets.

The root structural value should be decoded once and reused across its nested
relations. An ephemeral shared-prefix plan may avoid walking the same list or
record prefix repeatedly, but results and logical charging cannot depend on
that optimization.

Typical nested writes should target only a 10–20% relation-projection premium
over an equivalent direct relation workload. Whole-operation latency may hide
or amplify that cost, so measurement must report both isolated projection work
and end-to-end write work where the harness permits it.

The reverse-key hard cut places the exact four-byte `RelationId` component in
every direct and nested reverse entry while removing the old field-slot/index
identity from that role. Stable-memory measurements must report the net
encoded byte delta per edge and at representative cardinalities. Four bytes is
the new component's payload size, not a forecast of net growth.

### 13.3 Wasm Shape

The main Wasm risk is not the path data. It is retaining a generic interpreter
in actors with no nested relations, or generating recursive Rust functions for
each composite/path instantiation. The design prevents both:

- direct sources use a separate fast path;
- the nested interpreter is referenced only when an accepted nested relation
  is present in the generated proposal/runtime binding;
- all nested shapes use one data-driven walker; and
- no per-type or per-path recursive extraction code is generated.

A fixed 4–10 KiB cost paid by every actor is a design failure, not an acceptable
baseline tax.

## 14. Measurement Matrix And Gates

All Wasm comparisons use a frozen clean predecessor, identical lockfile,
toolchain, release profile, features and build command. Raw non-gzipped final
`.wasm` bytes are primary. Also report the code section, data section, defined
functions, `call_indirect`, exports, imports, Candid surface and gzip size.

Every instruction measurement reports absolute instructions for baseline and
candidate, the absolute delta and the percentage delta. A percentage alone is
not an acceptance argument when the baseline operation is tiny. Byte/function
ceilings and absence of nested-interpreter functions are hard gates;
instruction percentages labelled “target” require review together with the
absolute delta and profile.

| Proving actor | Required gate |
| --- | --- |
| No relations | **Hard:** zero retained nested-interpreter functions. Unavoidable generic current-format snapshot-codec movement is isolated and capped separately at 2 KiB raw, 2 KiB code section and 8 defined functions. It cannot contain traversal or relation-projection logic. |
| Direct relations only | The nested walker remains dead-stripped; direct relation instruction movement is at most 1%. Raw bytes, code bytes and function movement are still reported. |
| Controlled nested relation | At most 32 KiB raw-module growth, at most 32 KiB code-section growth and at most 64 defined functions versus its direct/no-nested control. Separate shallow and repeated builds identify retained shape. |
| Toko `project_instance` | At most 32 KiB net raw and code-section growth after deleting replaced manual validation. Function and `call_indirect` deltas are reported even when within the byte gate. |
| Shallow single-valued write | Target at most 20% relation-projection instruction premium over an equivalent direct relation case with the same target/reverse work. |
| Repeated list/set/map write | Target at most 40% relation-projection instruction premium over an equivalent direct relation case with the same raw and unique target cardinality. |
| Typical Toko calls | Target at most 5% whole-call instruction regression for the agreed representative read/write set after deleting replaced manual validation. Report each call, not only an average. |
| Cold first read after installation/recovery | No-relation actor targets at most 1% instruction movement and retains no nested interpreter. Report nested-schema first-bind work separately with absolute instructions and required message headroom. |
| Warm ordinary read | A read that does not enforce relations targets at most 1% instruction movement in an actor whose accepted schema contains nested relations. No row relation projection may occur. |
| Activation/backfill | Report absolute instructions per representative row and per bounded page for shallow and repeated paths. The calibrated maximum page must retain the Section 10 instruction headroom. |

| Maximum admitted atomic commit | Demonstrate success at all frozen batch maxima within the Section 10 instruction headroom, then deterministic pre-mutation failure at the first over-limit unit for each counter. |

The controlled actors collectively include an explicit optional path, an
explicit named wrapper, one enum variant payload and list, set and map-value

exercise insert, replace, source delete, target `RESTRICT` and same-batch
overlay so dead stripping is not obtained by failing to use relations.

Existing 0.252 nested scalar-path Wasm evidence may inform the forecast, but it
is not a substitute for these frozen 0.253 A/B measurements.

## 18. Rejected Alternatives

### 18.1 Generate Recursive Extractors Per Type Or Path

Rejected. It multiplies monomorphised functions, retains shape-specific code
and makes Toko's reusable value types a Wasm liability. One interpreted walker
is the accepted implementation.

### 18.2 Derive Reverse Identity From Root Slot Or Path Hash

Rejected. A root slot is shared by multiple nested leaves and occurrences. A
hash is not the accepted relation identity and adds collision policy. The exact
accepted `RelationId` owns the reverse domain.

### 18.3 Preserve Old And New Relation Formats

Rejected. The project is pre-1.0. Proposal, accepted snapshot and reverse state
move directly to one current version-1 form. Retained rows require old-binary
export followed by fresh 0.253 reinstall/recreation and ordinary import; there
is no in-place or row-preserving regeneration path.

### 18.4 Add Weak Or Conditional Relations

Rejected. That would introduce a new enforcement axis to solve application
states that do not satisfy the strong lifetime contract. Historical, external
and conditional identifiers remain ordinary IDs with domain validation where
needed.

### 18.5 Treat Nested Relations As Nested Query Support

Rejected. Referential extraction and query-path expansion have different
cardinality, indexing, planning, ordering and cursor contracts. This minor
admits only integrity extraction.
