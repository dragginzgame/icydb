## Audit Outcome

The provisional roadmap title, "Deterministic Planner Statistics And Plan
Observability", is too broad for the maintained implementation.

IcyDB already has:

- one exact durable entity and accepted user-index prefix cardinality authority
  from 0.230, including exact live-overlay deltas and conservative
  unavailable/Building behavior;
- deterministic structural index ranking, same-score residual-burden ranking,
  and lexicographic accepted-index tie-breaking;
- structured logical and verbose execution EXPLAIN output containing chosen,
  alternative, and rejected routes with typed reason codes;
- actual key, row, materialization, result, time, instruction, and response
  observations through the maintained diagnostics pipeline; and
- one accepted-schema-bound prepared-plan and parameterized-template cache.

The current gap is narrower and directly demonstrable. When two accepted
prefix-family indexes are equal under every maintained structural and residual
ranking dimension, the planner chooses by lexicographic index name even when
0.230 can prove that one candidate will visit far fewer entries for the exact
bound values. The selected route is semantically correct, but it can perform
materially unnecessary IC work.

0.236 therefore does not add a statistics subsystem. It consumes current exact
0.230 evidence only to replace the final lexicographic tie-break for eligible
non-grouped prefix, multi-lookup, and branch-set candidates. Range estimates,
histograms, sampling, null fractions, approximate distinct counts, physical
index payloads, and a general cost optimizer are rejected from this line.

The direct `#[newtype]` predicate-planning defect is not part of 0.236. It was
corrected separately in released `v0.235.1` by normalizing accepted query-value
kinds at the schema projection boundary. Patch 2 starts from that exact release
and may not alter newtype query normalization except for mechanical propagation
required by an existing type change. The production-shaped cardinality fixture
uses ordinary scalar fields so performance attribution cannot absorb that
correctness fix.

## No-Build Gate

The no-build outcome keeps lexicographic ties. It is deterministic and correct,
but leaves an avoidable population-dependent scan cost even though the exact
candidate entry counts are already maintained and bounded. A production-shaped
query with predicates `common = ? AND rare = ?` and equal structural indexes
on `(common, id)` and `(rare, id)` proves the gap: name order can select the
large `common` prefix while the exact `rare` prefix contains one entry.

The broad intake proposal would add persisted statistics, build lifecycle,
staleness policy, public warnings, and optimizer math. That duplicates 0.230
and creates several new authorities before a workload demonstrates their need.

The smallest justified outcome is:

1. enumerate only candidates already tied under the current planner policy;
2. ask the existing store/cardinality proof boundary for their exact current
   prefix counts;
3. choose the lowest exact count, retaining lexicographic order for equal
   counts or unavailable evidence; and
4. surface that exact decision through the existing explain and diagnostic
   owners.

## Decision Summary

The canonical planner remains the only access-selection authority. Its order
for one eligible single-index family becomes:

1. existing prefix length and exact-match policy;
2. existing filtered-index, range-bound, and required-order policy;
3. existing residual-burden class and term count;
4. lower exact candidate prefix-entry count at plan selection, only when every
   candidate in the remaining tie set has evidence from one accepted
   authority;
5. lexicographic accepted index name.

Cardinality never promotes an otherwise weaker route. It does not compare an
index against a primary-key route, full scan, intersection, union, range
family, or grouped route. It only resolves the final tie that would otherwise
be lexicographic.

The same concrete bound values produce the same decision from the same
accepted root and exact selection-time evidence. Missing, Building, malformed,
stale, overflowing, over-budget, or incomplete evidence keeps the complete tied
set on the current lexicographic outcome. It never partially ranks the
candidates whose counts happened to be available.

## Eligible Candidate Families

The line admits these existing access families:

| Family | Exact evidence |
| --- | --- |
| `IndexPrefix` | exact count for its complete equality prefix |
| `IndexMultiLookup` | checked sum of normalized, deduplicated, disjoint exact prefixes |
| `IndexBranchSet` | checked sum of normalized, deduplicated, disjoint exact branches |

The planner may compare candidates only within the same family and only after
their current structural score and residual burden are equal. A zero count is
valid exact evidence. Equal exact counts retain the current lexicographic
winner.

The following remain structural in 0.236:

- `IndexRange`, because a parent-prefix count is not the exact cardinality of
  its bounded range;
- grouped plans, whose grouping/order/materialization trade-offs cannot be
  represented by a prefix-entry count alone;
- exact intersections, unions, primary-key routes, and full scans;
- order-only index candidates; and
- any candidate whose physical prefix cannot be lowered through current
  accepted schema authority.

This exclusion is a correctness boundary, not a placeholder estimate of zero
or infinity.

## Canonical Evidence Owner

`StoreHandle` remains the only runtime proof boundary for exact cardinality.
0.236 adds one bounded planner-evidence operation over the existing 0.230
generation and live-delta machinery. It does not expose schema-map slots,
generation headers, fold watermarks, journal records, or raw count digests to
the planner.

The operation receives:

- the database incarnation and exact admitted accepted-root identity;
- the target entity and current accepted physical index identities; and
- a bounded set of already lowered user-index prefix keys.

One proof attempt returns exactly one of:

- all exact visible counts at selection time; or
- unavailable evidence plus one opaque comparable lifecycle stamp; or
- policy fallback when the optional probe envelope is exceeded.

The lifecycle stamp exists only to prevent an unavailable cached fallback from
remaining warm after evidence becomes usable. It is derived from existing
0.230 Absent, Building, Ready, generation, and source authority. Building
cursor progress does not change it; Ready publication, rotation, source drift,
or another availability transition does. Ordinary row mutations do not change
the lifecycle stamp. No stamp is persisted, and no mutation revision, new
counter, or fallback revision source is introduced.

Exact counts for a journaled store are the current 0.230 Ready base plus exact
live deltas at the synchronous proof call. The owner fails the complete proof
if its accepted source changes during collection. Planning performs no await or
mutation while evidence is collected. Once selected, the count is advisory
`exact_at_selection` evidence; it is not continuously refreshed as rows change.

Accepted schema snapshots remain runtime authority. Generated models cannot
reconstruct an index, prefix, count, lifecycle stamp, or fallback plan.

## Fixed Work And Memory Bounds

Existing accepted-schema and predicate limits already bound one request to at
most 64 visible indexes and one branch-set candidate to at most 16 normalized
prefixes. 0.236 additionally freezes the advisory evidence policy:

| Resource | Fixed maximum |
| --- | ---: |
| Tied candidates examined | 64 |
| Exact prefix probes | 256 |
| Cumulative lowered probe bytes | 4 MiB |
| Prefixes prepared at once | 16 |
| Transient lowered bytes prepared at once | 1 MiB |

One maximum valid four-component prefix candidate with all 16 branches fits
the per-candidate envelope including encoded components and both materialized
raw scan bounds. Candidate preparation is streamed one candidate at a time,
then transfers—not clones—its component buffers into the single complete
StoreHandle proof batch. The cache does not retain lowered keys or duplicate a
complete probe batch. Counts, candidate summaries, and checked totals are
retained; raw values and encoded prefixes are not copied into diagnostics.
The maximum preparation payload is therefore 5 MiB plus bounded candidate/key
metadata: at most 4 MiB of already admitted component buffers plus at most
1 MiB for the candidate whose components and raw lower/upper bounds are being
checked. No second 4 MiB component buffer is materialized.

If a tied set exceeds either advisory probe limit, its query remains admitted
and uses the current lexicographic decision. Evidence work is optional planner
work, so absence or policy exhaustion cannot turn a previously valid query
into an execution-budget error or deterministic retry failure. Malformed
optional cardinality evidence remains unavailable under the existing 0.230
contract and can never produce a numeric estimate. Corruption outside that
derived-evidence boundary retains its current typed behavior.

Before closeout, Patch 3 must measure the 64-candidate and 256-probe shapes on
the maintained IC harness. If the fixed envelope cannot remain materially
below the query-message instruction ceiling, the implementation must lower the
advisory probe cap and preserve fallback; it must not add caller-selected
budgets or unbounded work.

## Plan Cache And Parameterized Bindings

Exact counts are value-dependent. Reusing the index chosen for one set of
parameter values for another set would be incorrect planner policy even though
query results remain semantically correct.

The existing shared cache remains the sole cache. It changes as follows:

- a concrete plan selected with exact counts retains its bounded
  `exact_at_selection` candidate summary and is reused under the existing
  schema/visibility/cache-eviction rules;
- ordinary target or unrelated row mutations do not invalidate, re-probe, or
  re-rank that cached plan;
- a lexicographic fallback caused by Absent, Building, malformed, or otherwise
  unavailable evidence retains the opaque lifecycle stamp plus the selected
  route pin needed only if that plan emits a scalar cursor;
- an unavailable fallback cache hit compares that cheap lifecycle stamp and
  performs no prefix-count probes while it remains unchanged;
- a changed unavailable stamp retries the bounded proof and replaces the same
  structural cache entry if evidence has become usable; and
- a policy fallback is stable for that accepted query shape, retains the same
  bounded selected-route pin for cursor continuity, and does not poll lifecycle
  state, because the fixed probe envelope—not readiness—caused it.

No evidence state is added to the cache key and no plan history accumulates.
Exact cardinality is selection-time advisory evidence, not a cache-validity
condition. A successfully cardinality-ranked cached plan remains valid under
the ordinary plan-cache lifetime even if later row mutations would cause a
newly compiled query to choose another tied candidate. This can affect
performance but never query semantics. The next cold compilation, new bound
values, normal eviction, or accepted schema/visibility invalidation observes
current exact evidence again.

`PreparedQueryTemplate` becomes candidate-neutral for the affected family. It
retains bounded accepted semantic candidate authority rather than only the
index selected for the first values. Every new bound predicate performs the
same tied-candidate decision. Its existing one-entry recent-bound memo also
retains the selection outcome and is reused for the same bound predicate
fingerprint. An exact selection or policy fallback uses ordinary memo reuse; an
unavailable memo additionally compares its lifecycle stamp. Different bound
values always run the bounded tie decision against current evidence.

The template/cache retained-byte charge includes every retained semantic
candidate and the recent memo. An artifact that exceeds the existing weighted
cache envelope is executed without being cached; the estimate is not left at
the former fixed selected-index footprint.

This is one cache and one planner path for SQL, structural, dynamic, and typed
callers. There is no typed-only optimizer, executor-side reroute, or
value-dependent cache key proliferation.

## Scalar Continuation Stability

A live scalar cursor binds the finalized planned query through its continuation
signature. If fresh cardinality selected another index between pages, merely
replanning would reject a valid continuation or, worse, resume through a
different physical route.

The current authenticated scalar cursor therefore carries a bounded
planner-choice pin for a cardinality-ranked route. The canonical pin is:

```text
accepted physical IndexId
+ Prefix | MultiLookup | BranchSet
+ consumed prefix arity
```

Consumed prefix arity is the equality-prefix length for `IndexPrefix`, one for
`IndexMultiLookup`, and `fixed_values + branch slot` for `IndexBranchSet`. It
is bounded by the current four-item index-key limit. This discriminator is
deliberately included even though the current planner loops derive at most one
candidate per index and family: singleton branch canonicalization and future
candidate derivation must not make `(IndexId, family)` ambiguous. The pin
contains no predicate value, SQL, row key, branch value/count, cardinality,
lifecycle stamp, or caller-selected hint.

Continuation handling is:

1. decode and authenticate the scalar token through the existing cursor
   owner before access selection;
2. validate its database, accepted root, entity, and window authority as
   today;
3. enumerate through the ordinary planner and require exactly one currently
   accepted eligible candidate matching the pinned index, family, and consumed
   prefix arity; zero or multiple matches reject the cursor;
4. rebuild or reuse that exact candidate without consulting fresh cardinality;
5. validate the existing complete continuation signature; and
6. emit the same pin on the next page.

A cold initial query may choose a different index after target data changes;
an issued cursor remains on its original route. An ordinary warm initial query
continues using its cached advisory selection. The pin is not accepted as a
separate request field and cannot select an otherwise ineligible access path.
If a cached plan does not match the pin, the continuation compiles the pinned
plan without replacing the ordinary unpinned initial-request cache entry.

The scalar cursor is opaque, authenticated, bounded, and pre-1.0. 0.236 is an
intentional hard cut: it replaces the sole current version-1 encoder, decoder,
and maintained current-layout tests in place. Repository policy defines a
pre-1.0 format version as the discriminator for the sole current canonical
shape, not as a release-history counter, so incrementing this cursor to version
2 is forbidden.
There is no predecessor constant, decoder, inspection path, dual form, or
fallback. Strict payload length/layout, MAC, accepted-authority, exact-one pin
matching, and continuation-signature validation make previously issued
pre-0.236 scalar cursors fail closed after upgrade. Grouped cursor bytes are
unchanged because grouped selection is outside this line.

## Complexity, Instruction, And Wasm Gates

0.236 does increase local source complexity. It adds one bounded proof-outcome
DTO, one final tied-candidate comparison, one unavailable-fallback lifecycle
stamp, and one small authenticated route pin. Pretending that this is
complexity neutral would hide the work required to keep parameter binding,
Ready publication, and pagination correct.

The system-level state space remains bounded because the implementation must:

- extend `StoreHandle`, the current access-choice owner, the current shared
  cache artifact, and the current scalar token rather than add parallel owners;
- replace the template's selected-index retention with one candidate-neutral
  representation rather than retain both forms;
- freeze the tied candidate set once and reuse it for selection, fallback, and
  explain instead of adding another candidate-enumeration authority;
- retain no raw lowered probe keys in cache state;
- add no persisted state, background lifecycle, configuration, feature mode,
  executor branch, second cache, or public hint; and
- keep all new names on `cardinality_tiebreak`, `exact_prefix_entries`,
  `evidence_state`, and `route_pin` terminology. Production names using
  `cost`, `estimate`, `optimizer_score`, or `cheapest` for this decision are
  rejected because fewer exact matching index entries is the only proven fact.

Patch 2 must report the production files and approximate line delta and state
whether redundant ranking/cache logic was deleted or merely extended. If the
implementation requires a second planning flow, a second retained candidate
model, or a new independent state axis, the design no longer authorizes it and
must return to review.

The hot-path rules are:

- a query without a genuine final tied candidate set performs zero cardinality
  state reads and zero prefix-count probes;
- a warm plan previously selected from exact counts performs zero lifecycle
  reads and zero prefix-count probes, even after ordinary writes;
- only a warm unavailable fallback performs one cheap lifecycle-stamp
  comparison and zero prefix-count probes while the stamp is unchanged;
- a changed unavailable stamp retries only the bounded tied-candidate proof;
- a resumed pinned cursor performs zero cardinality state/count probes; and
- policy fallback preserves the predecessor execution route.

Patch 3 must capture focused predecessor and candidate instruction baselines
for a non-tied query, cold tied query, warm exact-selected hit, unchanged and
Ready-transition unavailable fallbacks, parameter rebind, and resumed cursor.
The non-tied and warm exact-selected routes must show no new stable cardinality
reads and no material instruction regression. The unavailable-stamp and cursor
overhead must each remain within the greater of 5% or 2 million instructions
against the matching predecessor fixture. The cold tie proof is not claimed to
make every small query faster; acceptance requires the production-shaped
selective fixture's reduction in entries visited and total instructions to
materially exceed its bounded planning overhead.

Raw non-gzipped Wasm is the artifact authority. Against a clean exact
`v0.235.1` build of the same representative query canister, Patch 2 performs a
preliminary stop-gate build and stops for attribution and reduction if raw
Wasm grows by more than the smaller of 96 KiB or 3%. The design does not
authorize waiving that gate with gzip results. Candid and exports must remain
unchanged. Patch 3 repeats the exact final artifact and instruction
measurements after all evidence corrections.

## Explain, Diagnostics, And Privacy

The existing planner-owned access-choice snapshot remains the source for all
renderers. For eligible candidates it gains:

- optional `exact_prefix_entries`;
- a closed evidence state: `exact_at_selection`, `unavailable`, or
  `policy_fallback`; and
- ranking reason `exact_cardinality_tiebreak`.

Compact explain remains compact. Structured and verbose explain display the
bounded candidate counts and reason beside the current structural and residual
facts. Existing actual execution counters remain the only source for keys
visited, base rows materialized, rows returned, instructions, and response
bytes. 0.236 does not estimate or duplicate those actuals.

`exact_at_selection` is deliberately historical plan evidence. A cached plan
does not claim that its displayed candidate counts still equal current data,
and 0.236 adds no stale-age calculation or automatic mutation-driven refresh.

Metrics may record only low-cardinality evidence outcomes and the new selected
reason. They must not label by index name, SQL, predicate value, encoded
prefix, count value, cursor material, or parameter fingerprint. Exact count
values appear only in an explicitly requested explain response under the same
read authority as the query; logs and aggregate metrics never contain them.

Unavailable evidence is not a warning that the query is incorrect. It is a
bounded explanation that the maintained structural fallback was used.

## Correctness Invariants

1. There is one planner and one executor; cardinality changes only the final
   choice among current eligible candidates.
2. A candidate that loses any existing structural or residual comparison can
   never win by cardinality.
3. Every compared count is exact visible cardinality from one admitted root at
   the synchronous selection call; cached evidence is labelled
   `exact_at_selection`.
4. Partial evidence never ranks a partial candidate set.
5. Checked sum overflow, malformed keys, or accepted-authority corruption
   cannot produce a numeric estimate.
6. Missing, Building, stale, or over-policy evidence preserves the exact
   maintained lexicographic result.
7. Query admission and execution semantics do not depend on evidence
   availability.
8. A parameterized template selects from current bound values, not the first
   values that populated the template.
9. Ordinary row mutations do not invalidate or re-rank a cached exact-selected
   plan; correctness remains independent of its advisory choice.
10. Every unavailable proof returns a lifecycle stamp, including Absent,
    Building, malformed, and unreadable evidence, so a Ready transition cannot
    remain hidden behind a warm fallback.
11. A changed unavailable lifecycle stamp retries the complete all-or-nothing
    proof; an unchanged stamp performs no prefix probes.
12. Every resumed scalar page uses the authenticated initial route pin and the
    existing complete continuation signature.
13. A cursor pin identifies one exact route by accepted `IndexId`, family, and
    consumed prefix arity; zero or multiple ordinary-planner matches reject it.
14. A cursor pin cannot introduce an index, family, or query authority the
    ordinary planner would reject.
15. No raw predicate, key, SQL, row, cursor, or parameter material reaches
    metrics or error facts.
16. No persisted statistics, second generation, generated-model fallback, or
    compatibility decoder is added.

## Recovery And Compatibility

0.236 adds no stable-memory allocation, persisted cardinality record, journal
record, recovery marker, schema snapshot field, generated model field, or
runtime fallback. Existing 0.230 Ready/Building state reopens through its
current version-1 codecs and is consumed through the same `StoreHandle` proof.

Plan cache state is heap-only and is rebuilt after upgrade. The first request
therefore chooses from current accepted authority and current cardinality
availability. A recovery transition that leaves cardinality unavailable uses
the structural fallback until the existing 0.230 driver publishes Ready.

The only representation hard cut is the opaque authenticated scalar cursor.
Rust explain DTOs gain the bounded optional evidence fields. No Candid method,
generated endpoint, canister export, or stable state shape changes.

## Rejected Scope

0.236 does not add:

- sampled, approximate, or caller-supplied statistics;
- histograms, null fractions, distinct sketches, range summaries, or cost
  formulas;
- statistics DDL, refresh commands, timers, jobs, or persisted epochs;
- a second plan cache, planner mode, feature flag, or caller-selected budget;
- range, grouping, union, intersection, or full-scan costing;
- physical index payloads, covering-index schema, write-amplification models,
  or DDL storage forecasts;
- new introspection commands or a parallel explain envelope;
- executor-time route switching;
- snapshot pagination, MVCC, caller-selected indexes, or compatibility cursor
  decoding; or
- generated-model reconstruction of accepted runtime authority.

The provisional 0.233 bound-SQL, 0.234 semi-join, and 0.235 covering-index
roadmap assignments were not the released contents of those versions and are
not absorbed here.

## Acceptance Evidence

Closeout must demonstrate all of the following rather than infer them from unit
shape alone:

- a later lexicographic index with a smaller exact prefix count wins and visits
  materially fewer keys than the predecessor route for equal results;
- missing/Building/over-policy evidence chooses the exact predecessor route;
- Prefix, normalized MultiLookup, and BranchSet counts are exact and checked;
- range and grouped plans remain byte-for-byte current in route choice;
- different values bound through one parameterized template can choose
  different indexes;
- a warm exact-selected plan performs no cardinality reads after target or
  unrelated writes, while an unavailable lifecycle stamp makes a Ready
  transition refresh only the fallback;
- a live cursor continues on its issued route across a target mutation while a
  subsequent cold compilation may select another route;
- same-index candidate depth/canonicalization fixtures prove the route pin's
  family and consumed-prefix discriminator; zero/multiple matches, cursor
  tampering, foreign root/entity/index, and unknown/current-layout mismatches
  fail closed;
- reopen and upgrade consume current 0.230 evidence without stable migration;
- structured/verbose explain shows exact candidate evidence while metrics and
  errors contain no semantic payload;
- the maximum admitted advisory shape remains below the frozen IC instruction
  ceiling and within its transient/cumulative byte envelope;
- non-tied, warm exact-selected, unavailable-fallback, and
  pinned-continuation overhead satisfies the focused instruction gates, while
  the selective fixture reduces total instructions;
- stable-state bytes are unchanged apart from ordinary fixture rows and
  existing 0.230 counts;
- Candid and exports are unchanged; and
- raw non-gzipped Wasm satisfies the 96 KiB/3% review gate, and its attribution
  plus the files/line/complexity delta are recorded. Gzip is secondary context.

The repository-wide suite and release workflow remain user-owned.
