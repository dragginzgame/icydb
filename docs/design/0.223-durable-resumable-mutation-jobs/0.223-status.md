## Design Reconciliation

The original design was cut against `0.222.2`. The implementation baseline is
the final published `0.222.4` tree because closeout corrections changed the
real predecessor's executor and Wasm shape. The durable mutation architecture
is otherwise unchanged.

Patch 1 confirms four distinct relationships:

- reuse the existing bounded Forward/Verify engine and aggregate request root;
- extend the excluded progress allocation with a separate mutation key/record;
- extend the current marker with one atomic progress replacement effect; and
- preserve generic revision-strict jobs unchanged rather than disabling their
  post-operation proof comparison.

The application-custodied prepare/resume API remains current only until Patch
5 lands its durable replacement. It will then be removed as a pre-1.0 hard cut,
without an alias or continuation importer.

## Patch 4 Evidence

  must begin without a pending marker, as required by the existing commit
  protocol.
- One canonical `MutationProgress` control effect binds the hashed progress
  key, job identity, expected sequence, domain-separated SHA-256 digest of the
  complete before record, and complete bounded before/after record envelopes.
  Decoding checks each nested record against the 64 KiB bound before allocation.
- Marker construction accepts at most one mutation-progress effect and proves
  that the after record is the next sequence for the same job and immutable
  canonical intent. Opening the commit window requires exact before bytes.
- Normal apply and recovery are idempotent over exactly two states: before is
  replaced with after, while after is retained as a lost-response replay. Any
  third state is typed commit/recovery corruption and leaves marker authority
  in place so reads remain blocked.

  target image and remains marker-recoverable until successful marker clear;
  no second WAL, transaction coordinator, or progress memory allocation exists.

  publication, target publication, and progress replacement. Every boundary
  recovers the exact target image and sequence-one record; clean completion
  clears the marker, while an injected neither-side record blocks repeated
  recovery.
- The maximum currently constructible replacement uses two 18,842-byte active

## 0.223.7 Release Gate Ordering Correction

- The 0.223.6 release attempt exposed a tooling defect: `release-commit`
  created the version commit before running the full gate. A test failure could
  therefore leave an untagged release commit even though the intended release
  had not passed validation.
- Patch, minor, and major preparation now run the full gate against the clean
  candidate before any version mutation and recheck that tracked state stayed
  clean. Only then may the existing bump owner change release surfaces.
- One bounded local receipt binds the tested commit, bump kind, exact version
  transition, and complete allowed diff hash. Staging and the resulting commit
  must reproduce that transition exactly before tagging; pre-push and publish
  reuse remain bound to the final annotated release commit.
- The simpler alternative of moving tests only before `git commit` was rejected
  because a failing gate would still leave version files mutated. The canonical
  candidate-receipt owner adds one ignored local evidence state and removes the
  post-commit test plus failed-release resume branch.
- A temporary Git fixture proves valid recording and verification plus staged
  tamper, dirty-state, and non-version-path rejection. Structural invariants
  freeze the required ordering and sequential one-shot release execution.
- This correction changes no runtime, API, Candid, persistence, mutation,
  instruction, stable-byte, raw Wasm, or gzip contract. Those measurements
  remain exactly the accepted 0.223.6 evidence.
- The handoff touches 11 release-tooling, governance, and documentation files
  by approximately `+647/-52` lines. Most growth belongs to one strict receipt
  verifier and one temporary-repository regression fixture. Delivery tooling
  becomes moderately more complex; runtime structure remains neutral.

## 0.223.8 Literal Command Boundaries

- Repository hooks made ordinary Git commands perform hidden formatting,
  staging, compilation, and test work. They and their installation paths are
  removed; commit and push now perform only the Git operations requested.
- `make test`, `make clippy`, `make check`, `make build`, and formatting targets
  now perform only their named operation and do not install hooks or invoke one
  another implicitly.
- One explicit `make validate` workflow composes formatting checks, structural
  invariants, feature checks, Clippy, and the complete test suite. Patch, minor,
  and major preparation invoke it once before version mutation.
- The change deletes an execution route and nested target dependencies. It adds
  no runtime, public, persisted, configuration, compatibility, Wasm, or Candid
  state; delivery structure becomes simpler.

  did not provide the explicit `POCKET_IC_BIN` required by every evidence
  target. All P1 and scale shards therefore stopped at Makefile preflight; P2

  same path.
- This changes workflow delivery only. It adds no runtime or public state,
  configuration, format, cursor, error, execution route, Wasm, or Candid
  surface, and avoids restoring the retired repository-level binary resolver.
