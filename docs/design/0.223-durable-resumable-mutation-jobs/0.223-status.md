## Design Reconciliation

The original design was cut against `0.222.2`. The implementation baseline is
the final published `0.222.4` tree because closeout corrections changed the
real predecessor's executor and Wasm shape. The durable mutation architecture
is otherwise unchanged.

Patch 1 confirms four distinct relationships:

- reuse the existing bounded Forward/Verify engine and aggregate request root;
- extend the excluded progress allocation with a separate mutation key/record;
- extend the current marker with one atomic progress replacement effect; and
- preserve generic revision-strict jobs unchanged rather than disabling their
  post-operation proof comparison.

The application-custodied prepare/resume API remains current only until Patch
5 lands its durable replacement. It will then be removed as a pre-1.0 hard cut,
without an alias or continuation importer.

## Patch 2 Evidence

- Mutation jobs now have a distinct Candid-compatible identity, idempotency
  key, lifecycle, Forward/Verify phase, public state, receipt, restart reason,
  and typed error family. Generic revision-strict jobs remain unchanged.
- The current mutation record uses its own hashed key domain, `ICYMJOB1`
  magic, version, bounded payload length, and checksum inside the existing
  excluded progress allocation. No memory id or user configuration was added.
- Exact complete record sizes are 97 bytes initially, 167 bytes for the
  current replay fixture, 165 bytes completed, and 166 bytes
  restart-required. Maximum admitted initial and active records are 18,524
  and 18,842 bytes, respectively, below the 64 KiB hard limit; the maximum
  current retained receipt is 319 bytes, below its 8 KiB limit.
- The existing global 64-record capacity is shared across integrity, generic,
  and mutation jobs. Isolated stable allocation measures 4,390,912 bytes at
  one and eight small mutation records and 38,993,920 bytes at 64 records.
- Exact replay is checked before stale-sequence or terminal rejection.
  Terminal acknowledgement is sequence-checked, rejects active jobs, removes
  one valid terminal record, and succeeds when repeated after response loss.
- Public state load and acknowledgement are available through the core and
  facade sessions. Start, SQL custody, marker replacement, target mutation,
  and Forward/Verify execution remain outside this patch.
- Host-side codec/store tests do not claim canister instruction counts. The
  named state, replay, and acknowledgement instruction evidence remains a
  required canister-level closeout measurement under the frozen 2M ceilings.
- The maintained dynamic-query subject is 2,612,975 raw bytes, up 5,594
  (`0.21%`) from the published baseline, while deterministic gzip falls 2,014
  bytes to 1,019,804. The typed-query subject is 1,799,937 raw bytes, up 7,280

  bytes with hashes `c973e18e...`/`1005c63f...`; no method, mode, or automatic
  endpoint was added.
- The patch changes 11 maintained files by approximately `+2,010/-20` lines,
  including focused tests. The implementation adds one necessary lifecycle
  state axis and a separate codec/coordinator owner, but reuses the existing
  allocation, capacity, budget, and facade patterns without adding a generic
  job framework, configuration, or compatibility path. Complexity therefore
  increases moderately and remains localized to the required mutation-job
  boundary.

## Patch 3 Evidence

- The trusted mutation-job start surface lowers the maintained fixed-update
  SQL subset through accepted runtime authority and persists sequence-zero
  progress before returning. Start performs no target-row read or mutation.
- Persisted custody contains no raw SQL. The bounded current intent binds the
  database incarnation, accepted root revision, method and fingerprint,
  target store and entity, canonical predicate and fixed patch, operation
  timestamp, internal continuation, and the fixed 256-key/64-update policy.
- Intent, predicate, and fixed-patch payloads use explicit current-version
  magics, bounded lengths, fallible decoding, and a checksum. Predicate depth
  is limited to 32 nodes deep and 256 total nodes; scope and patch payloads are
  each limited to 8 KiB and the complete intent to 16 KiB.
- Repeating a start with the same canonical meaning returns the retained
  sequence-zero state without replacing its timestamp or continuation.
  Formatting-only SQL differences replay identically; a changed patch returns
  `IdentityConflict`, accepted-authority drift returns `AuthorityMismatch`,
  and heap-store targets return `IneligibleIntent`.
- The start identity fingerprint deliberately excludes only the operation
  timestamp. All semantic and authority fields remain bound, and generated
  models never reconstruct runtime meaning.
- The named journaled-canister fixture measures 1,051,601 instructions for the
  first durable start and 1,161,322 for formatting-equivalent replay, both
  below the frozen 5M start and 2M replay ceilings. It proves sequence zero and
  zero changed target rows after first start, replay, conflict, and rejection.
- The existing application-custodied 512-row control remains behaviorally
  unchanged: prepare uses 434,549 instructions, Forward uses
  25.58M-27.16M per call, Verify uses 6.48M-6.49M per call, and all 512 rows
  still converge exactly.
- The maintained dynamic-query and typed-query subjects remain exactly at the
  Patch 2 sizes: 2,612,975 and 1,799,937 raw final Wasm bytes, respectively.
  Their extracted Candid remains 4,670/64 bytes with hashes
  `c973e18e...`/`1005c63f...`; Patch 3 adds no automatic endpoint or method.
- Patch 3 changes approximately 11 maintained source, test, and documentation
  files by `+1,300/-20` lines. Most of the growth is the bounded canonical
  intent codec and its exhaustive tests; the start path reuses accepted SQL
  lowering, current value encoding, progress storage, request budgeting, and
  the facade. Complexity increases moderately without a second mutation
  engine, compatibility decoder, or generated-model fallback.

## Patch 4 Evidence

- The commit-marker envelope hard-cuts directly from version 2 to the sole
  current version 3. There is no legacy decoder or dual dispatch; upgrades
  must begin without a pending marker, as required by the existing commit
  protocol.
- One canonical `MutationProgress` control effect binds the hashed progress
  key, job identity, expected sequence, domain-separated SHA-256 digest of the
  complete before record, and complete bounded before/after record envelopes.
  Decoding checks each nested record against the 64 KiB bound before allocation.
- Marker construction accepts at most one mutation-progress effect and proves
  that the after record is the next sequence for the same job and immutable
  canonical intent. Opening the commit window requires exact before bytes.
- Normal apply and recovery are idempotent over exactly two states: before is
  replaced with after, while after is retained as a lost-response replay. Any
  third state is typed commit/recovery corruption and leaves marker authority
  in place so reads remain blocked.
- Target rows, journal publication, identity state, and progress replacement
  share the existing mechanical commit window. Progress applies only after the
  target image and remains marker-recoverable until successful marker clear;
  no second WAL, transaction coordinator, or progress memory allocation exists.
- Focused journaled recovery interrupts after marker persistence, journal
  publication, target publication, and progress replacement. Every boundary
  recovers the exact target image and sequence-one record; clean completion
  clears the marker, while an injected neither-side record blocks repeated
  recovery.
- The maximum currently constructible replacement uses two 18,842-byte active
  records and contributes exactly 37,797 marker-payload bytes, below the 16 MiB
  commit ceiling. The established journal/identity interruption suite remains
  unchanged and passing.
- The maintained dynamic-query subject is 2,631,079 raw final Wasm bytes,
  18,104 above Patch 3 and 23,698 (`0.91%`) above the published baseline. The
  typed-query subject is 1,818,037 raw bytes, 18,100 above Patch 3 and 25,380
  (`1.42%`) above baseline. Both per-patch deltas remain below 64 KiB; gzip is
  1,024,796/688,585 bytes.
- Extracted Candid remains 4,670/64 bytes with hashes
  `c973e18e...`/`1005c63f...`. Patch 4 adds no automatic endpoint, public
  method, or method-mode change.
- Patch 4 changes approximately 15 maintained source, test, contract, and
  documentation files by `+950/-35` lines. Most growth is exact codec and
  interruption/corruption coverage; production behavior extends the existing
  control-op and commit-window owners. Complexity increases moderately but
  stays within one marker/recovery flow.

## Current Authorization

The next implementation handoff is Patch 5 only. It may execute one bounded
Forward step from IcyDB custody, commit mutating pages through the Patch 4
target/progress boundary, retain exact replay receipts, and hard-cut the old
public prepare/resume continuation facade. It may not implement stable Verify,
claim completion, relax generic proof jobs, add compatibility aliases, or
change the fixed 256-key/64-update policy.
