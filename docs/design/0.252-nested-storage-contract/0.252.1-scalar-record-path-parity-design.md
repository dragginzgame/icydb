# IcyDB 0.252.1 — Scalar Record-Path Grouping Parity

- **Status:** Complete; all five landing slices accepted
- **Date:** 2026-09-01
- **Target:** `0.252.1`
- **Immutable predecessor:** annotated tag `v0.252.0`
- **Parent contract:** [0.252 Nested Storage Contract](0.252-design.md)
- **Gate-1 evidence:**
  [Scalar Record-Path Parity Pre-Start Audit](0.252.1-scalar-record-path-parity-pre-start-audit.md)
- **Delivery tracker:** [0.252 Status](0.252-status.md)

## 1. Decision Summary

IcyDB will admit an accepted single-valued scalar record path as a grouping key.
The canonical example is:

```sql
SELECT profile.rank, COUNT(*)
FROM Player
GROUP BY profile.rank;
```

The feature completes the remaining scalar record-path query cell without
changing IcyDB's relational product boundary. A path still traverses only
required or optional named records and produces zero or one scalar value for
its owning row. Lists, sets, maps, tuples, newtypes, opaque blobs, repeated
members, positional access, row expansion, joins, member mutation, and multikey
indexes remain unsupported.

Accepted schema remains the only authority that decides whether the path
exists and whether its terminal scalar is groupable. SQL and structural/fluent
frontends lower into one group-key identity. Hash and ordered grouping continue
through the existing grouped executor; this design adds no nested-group
executor, fallback semantics, capability mode, registry, callback, or dynamic
dispatch boundary.

The direct grouping fast path is preserved structurally. A direct-only query
continues to carry and execute the existing direct `FieldSlot` list. A query
containing at least one scalar path uses one path-aware group-key set. This
single outer decision prevents a path branch from entering every row of every
existing direct grouping query.

## 2. Demonstrated Need And Accepted Scope

The 0.252 contract already admits scalar record paths for projection,
filtering, ordering, projection and aggregate `DISTINCT`, aggregate inputs,
scalar expressions, aggregate-owned `HAVING`, prepared execution, and eligible
indexes. Keeping `GROUP BY profile.rank` unsupported forces an otherwise
unnecessary duplicate root scalar when applications need grouped reporting.
The maintainer explicitly authorized this addendum after publishing 0.252.0.

Toko Miner does not currently require this feature. Its owner-local aggregate
model remains correct, and the no-build alternative remains denormalizing a
frequently grouped scalar or modeling independently queried children as
entities. That absence of downstream urgency is why every implementation slice
is reversible and evidence-gated rather than treated as correctness repair.

The accepted user-visible scope is:

- `GROUP BY` on one or more direct and accepted scalar record paths;
- grouped projection and scalar expressions that reference those exact keys;
- raw-path `HAVING` only when the exact canonical path is a declared group key;
- grouped `ORDER BY`, limits, offsets, and continuation behavior equivalent to
  the same direct scalar shape;
- complete hash grouping for every admitted path query; and
- ordered path-index grouping only when accepted index and predicate evidence
  proves that the access stream is complete and key-ordered.

The design does not admit arbitrary grouping expressions. A function,
arithmetic expression, aggregate, literal, or `CASE` expression cannot itself
be declared in `GROUP BY`. Existing post-group scalar expressions may consume a
declared group key under the same rules as a direct group key.

## 3. Exact Semantic Contract

### 3.1 Path cardinality and admission

One admitted group path has all of these properties:

1. its root is a field in the current accepted schema snapshot;
2. every intermediate segment is a named record member;
3. the path does not traverse a list, set, map, tuple, newtype, or blob;
4. the terminal is one accepted scalar;
5. the terminal has the ordinary accepted `groupable` capability; and
6. enum grouping remains rejected until the separate canonical-ID grouping
   contract admits enums for both direct fields and paths.

Generated models may propose the same path but are not runtime authority.
Runtime admission must not reconstruct nested metadata from a generated model
or inspect an example `Value` to guess shape.

### 3.2 Missing and null

Grouping uses the already maintained projection/order materialization rule:

- a present scalar terminal contributes its accepted runtime value;
- an explicitly null terminal contributes `Value::Null`;
- an absent optional ancestor or descendant contributes `Value::Null`; and
- all missing and explicit-null instances therefore form one null group.

This does not change predicate semantics. A missing descendant continues to be
different from explicit `NULL` for filters where the current contract makes
that distinction.

The path reader must return the owned null singleton without constructing an
intermediate map or allocating a per-row placeholder. Invalid root access or a
path that disagrees with the accepted compiled contract is an internal typed
error, not a null value.

### 3.3 Canonical identity

One group key has a structural identity:

```text
Direct(field)
ScalarPath(root, segment_1, ..., segment_n)
```

Presentation labels and SQL qualifiers are not identity. `profile.rank`,
`Player.profile.rank`, and `p.profile.rank` under `FROM Player p` lower to the
same accepted path identity. `rank` remains a different direct identity.

Duplicate group declarations compare this structural identity. Fingerprints,
prepared cache keys, grouped projection offsets, `HAVING`, `ORDER BY`,
`EXPLAIN`, and continuation signatures all consume it rather than reparsing a
dotted label.

### 3.4 Group value equality

After path extraction, the terminal uses the same canonical grouped value,
stable hash, equality, ordering, and byte-accounting contracts as the
equivalent direct scalar. A path does not introduce another numeric coercion,
text collation, null ordering, hash, or memory estimator.

## 4. Frontend And API Contract

### 4.1 SQL

The parser continues to accept a field-reference list after `GROUP BY`; it does
not widen the clause to arbitrary `SqlExpr`. Scope normalization distinguishes
qualification from path traversal before accepted-schema binding:

- `rank` is a direct field;
- `profile.rank` is a path unless `profile` is the current table alias or
  entity qualifier;
- `Player.profile.rank` strips the entity qualifier and becomes the path
  `profile.rank`; and
- `p.profile.rank` under `FROM Player p` strips the alias and becomes that same
  path.

Unknown roots, unknown members, unsupported traversal, non-scalar terminals,
non-groupable terminals, and ambiguous qualification reject during lowering or
logical validation before route planning.

The accepted grouped selection is:

```sql
SELECT profile.rank, COUNT(*)
FROM Player
GROUP BY profile.rank
HAVING profile.rank IS NOT NULL
ORDER BY profile.rank ASC;
```

A raw path in projection, `HAVING`, or grouped `ORDER BY` must match a declared
group-key identity exactly. A sibling or descendant path does not gain access
merely because the same root record is grouped.

### 4.2 Structural and typed query builders

The current hard-cut builder surface remains singular:

```rust
query.group_by("profile.rank")
```

One segment resolves as a direct field; multiple segments resolve through the
accepted scalar-path authority. No new alias, parallel path builder, generic
expression constructor, generated path registry, or predecessor adapter is
added. Generated record-member references are not expanded as part of this
slice; their absence is an authoring ergonomics question, not a second semantic
route.

SQL and structural strings converge into the same resolved group-key identity
after SQL-only qualifier normalization. They do not maintain separate path
classifiers.

## 5. Planner-Owned Group-Key Model

### 5.1 Direct-preserving set

The logical grouped plan replaces the assumption that every key is one
`FieldSlot` with one closed internal group-key set, conceptually:

```text
GroupKeySet
  Direct(Vec<FieldSlot>)
  PathAware(Vec<GroupKeySource>)

GroupKeySource
  Direct(FieldSlot)
  ScalarPath {
    identity: PathSpec,
    root_slot: usize,
    compiled_path: CompiledPath,
    terminal_group_contract: ...
  }
```

Names are illustrative; the accepted implementation may reuse an existing
owner-local type when that reduces code. The required shape is not optional:

- `Direct` preserves the exact current direct list for all-direct queries;
- `PathAware` exists only when at least one key is a path and permits mixed
  direct/path tuples;
- accepted root slot, compiled segments, structural identity, and terminal
  groupability are resolved once before execution; and
- there is no parallel `group_fields` list that can disagree with the group-key
  set.

This adds one internal source axis, not a public mode. It combines with the
existing hash and ordered strategies. Repeated/non-scalar paths are made
unrepresentable by the accepted resolver, and invalid combinations fail before
the route planner.

### 5.2 Accepted binding

The group-key resolver consumes `SchemaInfo` and the existing nested leaf
metadata. It may extend that owner with one bounded projection carrying the
terminal group contract, but it must not expose the complete persisted leaf or
create a grouping-specific schema catalogue.

Direct keys keep `FieldSlot` and its accepted kind. Scalar paths reuse
`PathSpec`, the resolved root slot, and the existing compiled path form. The
terminal kind/capability evidence must originate in the same accepted leaf
lookup; a second lookup by rendered label is not allowed after binding.

### 5.3 Prepared reader

Prepared grouped residents freeze one concrete key reader:

```text
PreparedGroupKeyReader
  Direct(...existing direct slot contract...)
  PathAware(...resolved direct/path sources...)
```

The direct variant delegates to the existing borrowed single-key and multi-key
hash/equality/materialization functions. It does not evaluate `CompiledExpr`,
allocate a per-row vector, or match on path variants inside its row loop.

The path-aware variant owns concrete methods for exactly three operations:

1. hash the row's canonical group tuple;
2. compare the row's borrowed tuple with an existing owned `GroupKey`; and
3. materialize the tuple only when a genuinely new group is inserted or an
   ordered group is opened.

Those methods evaluate each source on demand and do not build a temporary
`Vec<Value>` for every row. Existing `GroupKey` remains the only owner of
canonical owned keys, stable hashes, equality, order, and retained-byte work.

### 5.4 Shared path evaluation

The grouped row runtime already implements `CompiledExprValueReader` for slot
access, while scalar projection owns the maintained field-path resolver. The
implementation must expose that existing concrete resolver through the grouped
row reader or move it to the current shared projection-path owner. It must not
copy the map traversal into grouped code.

The retained-slot compiler marks each path's root slot exactly once. Decoding
still happens at the structural row boundary, and path evaluation borrows from
the decoded root value. Intermediate record maps are not cloned or
materialized.

## 6. Grouped Projection, HAVING, And Ordering

Grouped output is evaluated after row access, so a declared path reference must
compile to the existing grouped-key offset leaf:

```text
Expr::FieldPath(profile.rank)
  -> exact GroupKeyIdentity lookup
  -> CompiledExpr::GroupKey { offset, label }
```

It must not re-evaluate the row path after aggregation. This rule applies to:

- canonical grouped projection;
- functions, arithmetic, and `CASE` over declared grouped keys where the
  direct-key equivalent is already admitted;
- raw-key `HAVING` predicates; and
- grouped `ORDER BY` expressions.

Aggregate-owned path expressions such as `SUM(profile.score)` retain their
existing row-expression compilation and are not rewritten as group keys unless
that exact path is separately declared in `GROUP BY`.

Projection layout, `HAVING`, and Top-K classifiers replace direct-name matching
with structural group-key identity matching. Rendered labels remain
presentation-only diagnostics.

## 7. Hash And Ordered Execution

### 7.1 Complete hash grouping

Landing Slice 3 admits path grouping through the existing complete hash route.
A plan containing a path must use hash grouping until the ordered path proof in
Landing Slice 4 is accepted. This temporary implementation boundary is
semantically complete: grouped projection, `HAVING`, final ordering, limits,
offsets, and supported continuation behavior remain correct, but it does not
claim index-stream early stop.

The existing finite `max_groups` and `max_group_bytes` policy applies without a
new path budget. Path depth is already bounded by accepted recursive schema and
compiled path structure. Each examined row performs at most one traversal per
declared path segment per group-key hash/equality operation; repeated elements
are never visited.

### 7.2 Ordered path-index grouping

Landing Slice 4 may select the existing ordered grouped strategy for path-aware
keys only when all current proofs succeed and the accepted access contract
structurally matches the group-key prefix after any equality-bound index
prefix.

Completeness is mandatory. In particular:

- a complete required non-null path index may provide the stream;
- an omission-capable optional/null path index cannot provide an unfiltered
  full grouping because it omits the null group;
- such an index may become eligible only when the accepted predicate/access
  proof establishes that omitted rows cannot match;
- a filtered index requires the existing predicate-implication proof;
- mixed direct/path group keys require one matching ordered index prefix; and
- any gap, direction mismatch, expression key, or uncertain completeness falls
  back to complete hash grouping.

The route planner owns this decision. Execution must not rediscover index
completeness from runtime rows or silently switch strategies.

Ordered grouping retains one live group, closed-group emission, early scan
stop, and the current cursor boundary. It does not add a third grouping
strategy.

## 8. Fingerprints, Cache, EXPLAIN, And Cursors

The semantic fingerprint hashes a domain-separated direct/path tag plus the
canonical identity components in declaration order. It never hashes a SQL
alias or an unnormalized input spelling. Two different paths under one root
must not share a prepared plan.

`EXPLAIN` keeps the existing grouped field list and renders one canonical
dotted label for a path. It may report the existing ordered/hash strategy and
fallback reason; it does not add a path mode or a second explain schema.

Grouped continuation tokens continue to carry:

- the current version-1 token shape;
- the continuation signature;
- materialized group-key values;
- direction; and
- initial offset.

No field/path identity is added to the token payload. The signature already
binds query semantics and will now include structural group-key identity. Any
pre-0.252.1 cursor whose signature no longer matches fails with the current
typed signature error. There is no old-signature bridge, fallback decoder,
dual cursor form, or format-version increment.

Prepared caches are runtime-local and use only the new current semantic
fingerprint. No predecessor cache-key reader is retained.

## 9. Diagnostics And Fail-Closed Boundaries

The feature reuses current typed query/lowering diagnostics wherever their
meaning is exact:

- unknown direct root;
- unknown accepted member path;
- unsupported traversal/non-scalar path;
- non-groupable terminal;
- duplicate group key;
- raw projection/`HAVING`/order source not present in `GROUP BY`;
- grouped order prefix mismatch; and
- continuation signature mismatch.

A new public diagnostic code is allowed only if the current code cannot
truthfully distinguish unknown from structurally unsupported path admission.
Tests assert typed variants/codes, not rendered strings.

All path errors occur before execution except corruption or a compiled
accepted-path/read-layout disagreement, which returns a typed internal error.
There is no scan-as-success fallback for an unsupported semantic path.

## 10. Public, Generated, Persistence, And Recovery Effects

The completed feature changes no:

- public Candid request or response type;
- generated entity, record, query, mutation, or binding type;
- canister endpoint inventory;
- accepted schema/catalog/persisted snapshot representation;
- row, index, journal, recovery, rebuild, or migration representation;
- stable-memory state or memory ID;
- cursor wire encoding; or
- internal format discriminator, which remains exactly version `1` where one
  exists.

SQL and the existing string-based structural builder gain current hard-cut
semantics. No alias, deprecated constructor, compatibility shim, old-path
fixture, fallback, or dual API is retained.

## 12. Validation Matrix

Focused coverage must prove distinct risks, not every syntactic combination.

- accepted required and optional scalar paths;
- unknown root/member, repeated traversal, composite terminal, and enum
  rejection;
- duplicate canonical identity across differently qualified spellings;
- terminal accepted groupability from the accepted snapshot; and

### Grouped expression tests

- raw-path `HAVING` over the exact key;

- scalar expression over a grouped path key;
- aggregate-owned path input remains row-local;
- grouped `ORDER BY` and aggregate Top-K classification; and

### Runtime tests

- required values match a mirrored direct scalar;
- missing and explicit null collapse into one null group;
- one group, many groups, maximum groups, and group-byte rejection;
- mixed direct/path tuple hashing, equality, ordering, and output;
- path values are borrowed for probes and owned only for a new group;
- hash pagination/cursor resume returns no duplicate or split group;
- complete path index selects ordered grouping;
- omission-capable index without excluding predicate falls back to hash;
- an accepted excluding predicate permits the index only when completeness is
  proven; and

### Unaffected controls

- existing direct ordered and hash grouping;
- one scalar non-grouped query that cannot select the feature;
- one accepted write with exact physical work;

## 13. Complexity And State-Space Delta

### Added axis

One internal group-key source axis is added:

- all-direct key set; or
- path-aware key set containing direct/path sources.

It combines with current hash grouping in Slice 3 and current ordered grouping
only after Slice 4 proves accepted index completeness. Invalid repeated,
non-scalar, ungroupable, and unaccepted sources reject at the group-key resolver.
The group logical plan is the canonical decision owner.

### Retained specialization

The existing direct grouped hash/equality/materialization loops remain separate
from the path-aware reader. This is intentional measured hot-path
specialization, not duplicate semantics: both consume the same `GroupKey`
canonicalization and grouped executor, while the direct lane avoids per-row path
dispatch. The 1% direct control gate decides whether that retention succeeds.

### Not added

There is no new public mode, configuration, feature flag, planner strategy,
executor, cursor format, persisted state, recovery state, generated type,
runtime registry, trait object, callback, function-pointer table, or fallback.

Implementation structure becomes moderately more complex by one owner-local
source branch. That cost is proportionate only if path grouping passes the
declared semantics, raw-Wasm, runtime, and unaffected-control gates. Otherwise
the accepted outcome is removal and continued no-build.

No active technical-debt item is created. A rejected candidate is removed
rather than left behind as dormant infrastructure.

## 14. Rejected Designs

- **Universal scalar-expression grouping:** too broad and would add functions,
  arithmetic, literals, and `CASE` as declared keys without demonstrated need.
- **Every key represented as `CompiledExpr`:** loses the direct `FieldSlot`
  shape and taxes all current grouping for one new source kind.
- **Parallel direct and path lists:** creates two authorities that can disagree
  on arity, order, projection offsets, and fingerprints.
- **Path-specific executor:** duplicates grouped hash, order, cursor, limits,
  diagnostics, and output.
- **Per-row temporary key vector:** adds allocation before the executor knows
  whether the group is new.
- **Generated per-path readers:** restores downstream entity/type
  monomorphization.
- **Automatic omission-capable index use:** can silently drop the null group.
- **Path identity as a dotted string:** conflates SQL qualification,
  presentation, and semantic identity.
- **Compatibility decoding or aliases:** forbidden by the pre-1.0 hard-cut
  contract and unnecessary for a query-planning change.

## 16. Slice 1 Receipt

Landing Slice 1 is documentation-only. It converts the eligible audit into one
accepted semantic contract, selects the direct-preserving group-key set,
separates complete hash admission from ordered path-index optimization, freezes
five reviewable slices, and declares attributable/cumulative gates before code.

The split from the audit's four-handoff forecast is deliberate: deeper source
inspection showed that ordered path-index completeness is an independent
planner proof and measurable optimization. Keeping it out of semantic hash
admission avoids one cross-layer mega-slice and allows rejection without
removing correct path grouping.

No parser, lowering, planner, executor, cursor, public API, generated code,
fixture, persisted representation, Candid, changelog, or runtime path changed.

## 17. Slice 2 Receipt

## 18. Slice 3 Receipt

The complete-hash implementation and attributable feature gates pass. The
candidate retains borrowed probes, owns a key only for a new group, keeps the
direct representation, and adds no generated entity slope, indirect calls,
