## Assignment And Boundary

The accepted-schema 0.237 candidate closed as a measured, unreleased no-build
and remains an immutable historical record. Because no `v0.237.*` tag or
release exists, the user explicitly reassigned the 0.237 release number on
2026-08-22 to this separate SQL query-performance evidence line. This does not
reopen, retain, or authorize any accepted-schema runtime work.

This line answers a narrower question: which supported SQL query shapes are
currently expensive as rows, branch fanout, projection width, payload width,
result windows, aggregate work, and storage backends scale? It expands the
existing performance authority, measures it, and localizes removable phases.
It does not authorize a production optimization. Any runtime proposal needs
the evidence produced here and a separately accepted design.

SQLite remains the semantic reference for eligible reduced-SQL cases. It is
not an instruction-performance comparator: native SQLite host timing and IC
Wasm instruction counts do not share a meaningful unit or lifecycle. The
matrix therefore uses SQLite to reject semantic drift and uses IcyDB PocketIC
instruction and physical-work evidence to rank performance.

## Current Evidence Gap

The released predecessor already has a broad, deterministic P1 matrix of 1,787
SQL scenarios. It covers six data surfaces, every maintained route family,
scalar and grouped projections, aggregate forms, metadata statements, and
SQLite-eligible correctness cases. The existing exact-cardinality scale lane
is much narrower: 24 sentinel families at 16, 256, and 2,048 rows, or 72
measurements.

The scale lane already covers primary and secondary ordering, incompatible
filter/order, residual filtering, materialized ordering, sparse equality
prefixes, `COUNT`, blob payloads, heap and journaled primary reads, and ten
grouped ordered/hash cases. Its main gaps are interaction gaps rather than SQL
surface gaps:

| Dimension | Current scaled evidence | Missing comparison |
| --- | --- | --- |
| Projection width | one wide blob payload | metadata, derived length, one blob, and full payload under the same route |
| Covering work | one sparse token route | covering, non-covering, and full-entity projections at fixed branch fanout |
| Branch fanout | one sparse 250-prefix case | admitted two-branch, admitted nine-branch, and over-cap materialized routes |
| Pagination | windows 1/10/16/50/100 | `OFFSET` under an otherwise identical primary route |
| Scalar aggregation | `COUNT` | non-count reducer fold and aggregate `DISTINCT`/`FILTER` |
| Materialization | heap materialized narrow read | computed projection and full-entity heap/journaled pairs |
| Secondary projection | narrow indexed read | wide row-fetching projection under the same selectivity/order |

The old focused P2 hotspot list contains 15 token branch-family cases from a
previous investigation. Keeping it as a forced shortlist would bias a new
rediscovery pass. Patch 1 removes that forced list. P2 selection continues to
use complete P1 rankings, the existing promoted regression sentinels, the
grouped contract sentinels, and exact scale candidates.

## Measurement Authority

The existing harness remains the sole owner:

```text
deterministic P1 declarations
  -> SQLite/reference correctness confirmation where eligible
  -> PocketIC attributed IcyDB samples
  -> exact scale declarations and fixture facts
  -> P1 ranking and strict P2 selection
  -> repeated cold/warm P2 confirmation
  -> reviewed baseline comparison
```

No second generator, report format, benchmark runner, phase taxonomy, or
baseline store is added. The checked-in performance profile pins the exact P1
and scale scenario sets, sharding, measurement coverage, sample counts, and
thresholds. Its method identity hard-cuts to
`icydb-sql-performance/0.237/v1`; older identities remain historical and cannot
be decoded as current comparable evidence.

The profile format discriminator remains version 1. The `v1` suffix is the
current method identity, not a compatibility path. There is no old-profile
fallback.

## Ranking And Attribution Rules

The audit must report absolute instruction counts before percentages. It ranks:

1. total local instructions;
2. adjacent-cardinality instruction slopes;
3. normalized cost per fixture row, returned row, aggregate row ingested,
   data-store get, index entry, and output byte where that denominator exists;
4. raw compile, planner, store, executor, projection/grouped, and response
   phases; and
5. unaccounted or over-attributed residuals.

Paired comparisons are explanatory evidence, not proof of a removable phase.
Examples include narrow versus wide secondary projection, page-only versus
non-covered token projection, two versus nine branches, admitted versus
over-cap materialization, heap versus journaled full-entity reads, and `COUNT`
versus `SUM`. A hotspot becomes actionable only when its absolute cost grows,
the responsible phase is observed, and equivalent results/physical-work facts
exclude a semantic shortcut.

Cold and true warm evidence remain separate. A query-created heap cache cannot
survive an IC query message; warm-at-entry evidence requires the existing
update-warmed path and cache counters. Loop-local reuse is reported separately.

## No-Build And Scope Gates

This audit stops without a runtime design when any of these applies:

- no current supported query has a material absolute or slope hotspot;
- the expensive work is target-owned physical work required by the result;
- phase attribution cannot identify a removable owner;
- a smaller existing-owner change cannot be isolated;
- the likely saving is not proportionate to runtime lines, Wasm, tests, or new
  state; or
- the proposal needs a new route, cache, persisted state, mode, or parallel
  authority merely to produce a benchmark win.

No performance ceiling is raised and no semantic case is removed after seeing
results. SQLite/reference mismatches, result drift, route drift, physical-work
drift, dirty evidence, incomplete shards, or environment drift invalidate the
evidence rather than improving the score.

## Complexity Budget

Patch 1 adds no behavior axis, mutable owner, cache, format decoder, runtime
route, or production dependency. It extends one declarative test-owned profile
and deletes one historical forced-selection policy. The maintained method gets
broader but not architecturally deeper.

Patch 2 may add measurement declarations or report fields only when existing
typed evidence cannot answer a selected question. Temporary instrumentation
must be removed before handoff. Patch 3 may retain scale sentinels or reviewed
budgets when a bounded combination probe exposes a distinct current owner, but
cannot change production code.

Any future optimization must report files, line delta, raw and gzip Wasm,
absolute instructions, realistic savings, new state axes, invalidation edges,
failure states, and proof burden beside the simpler no-build alternative.

## Closeout

The final 58-family profile was calibrated three times at one clean committed
subject and passed an ordinary baseline comparison with no instruction,
semantic, route, or physical-work drift. Four separately designed
optimizations then passed their frozen instruction, physical-work, semantic,
lifecycle, feature and Wasm gates: exact entity counts save
96,075,607–125,950,053 instructions, indexed extrema save
100,826,309–133,049,153, secondary ordered endpoints save
54,047,414–54,150,094, and the measured 17-key exact-prefix count saves
40,459,476 at 2,048 rows.

Across Patches 4–7, raw Wasm grows by 6,440 bytes from 4,576,629 to 4,583,069.
The implementation adds no module, mutable owner, cache, invalidation edge,
persisted state, schema authority, endpoint or public behavior mode. Generated
code, public APIs, Candid, exports, stable formats and package versions remain
unchanged. The shared 16-branch page cap remains unchanged, and no blanket cap
increase is authorized. All planned 0.237 landing patches and the read-only
closeout audit are complete; full release validation and publication remain
user-owned.
