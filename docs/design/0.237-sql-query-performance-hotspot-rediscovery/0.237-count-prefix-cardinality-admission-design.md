# IcyDB 0.237 Count Prefix-Cardinality Admission

Status: COMPLETE — PATCH 7 GATES PASS

Date: 2026-08-22

Parent: [0.237 SQL performance design](./0.237-design.md)

## Outcome

Patch 7 evaluates one exact-cardinality discontinuity. A scalar `COUNT(*)`
whose complete predicate is represented by 16 accepted index prefixes reads
exact synchronized cardinality metadata, while the equivalent predicate with
one additional absent literal crosses the shared branch-plan cap and scans
rows and index entries.

The implementation may admit exactly one more distinct prefix for the existing
SQL direct-count target. It may not raise the shared row-producing branch cap,
broaden the public exact-count adapter, create a general large-membership
route, or change accepted-schema, cardinality-maintenance, cache, persistence,
query-result or public behavior.

## Accepted Evidence

The clean 0.237 calibration measured predicates with the same result. The
17th literal is absent from the fixture:

| Rows | 16 distinct values | 17 distinct values | Avoidable difference | Physical work: 16 / 17 |
| ---: | ---: | ---: | ---: | --- |
| 16 | 2,440,359 | 3,000,421 | 560,062 | 0 / 4 row gets and index entries |
| 256 | 2,527,427 | 7,447,688 | 4,920,261 | 0 / 64 row gets and index entries |
| 2,048 | 2,621,927 | 42,726,968 | 40,105,041 | 0 / 512 row gets and index entries |

The same cap must not be raised for ordinary pages. At 16 and 256 rows, the
admitted 16-branch page is respectively 1.6 million and 2.1 million
instructions slower than the 17-branch fallback. It becomes approximately
7.0 million instructions faster only at 2,048 rows. That crossover rejects a
static shared-cap increase and any cardinality-dependent page-planning mode in
this patch.

## Demonstrated Need And Simplest Alternative

The demonstrated need is limited to the measured 16/17 exact-count boundary.
The removable phase is the fallback's 512 accepted-index entries and 512 row
fetches at 2,048 rows. The existing exact-cardinality terminal already performs
zero such reads when given accepted prefix keys.

The simplest alternative is a count-owned admission bound of 17 distinct
canonical keys. The shared access-plan bound remains 16. A cap of 17 is
deliberately evidence-shaped: larger values are technically possible but have
not been measured for compilation cost, key-byte pressure or realistic use.
They therefore remain unsupported by the direct-count shortcut rather than
being inferred from the SQL input-size limit.

This introduces one bounded internal decision: exact count metadata may accept
17 distinct keys while row-producing branch execution accepts at most 16.
The canonical owner is the existing direct-count prefix-cardinality planner.
There is no new execution route or externally selectable mode.

## Frozen Admission

The count-only path is admitted only when all of these facts hold:

- the complete SQL query intent is the existing scalar direct-count metadata
  candidate: no order, grouping, `DISTINCT`, cursor, offset or finite limit;
- accepted schema and visible accepted indexes are pinned by the request's
  existing immutable entity authority;
- the predicate is either the already-supported strict leading-field equality
  or membership shape, or one conjunction exactly represented by fixed strict
  equality prefix components plus one strict membership component;
- canonicalization occurs before the count-specific cap is checked;
- there are between one and 17 distinct exact prefixes;
- the selected index is an accepted, unfiltered field-path index;
- the concrete access bounds prove the complete predicate, leaving no residual
  predicate or filtered-index guard;
- lowering produces one synchronized user-index cardinality key for every
  admitted prefix; and
- exact metadata is ready for the pinned data/index generation.

Any failed proof retains the current scan fallback for SQL. The explicit public
exact-count helper remains governed by the shared 16-key bound and retains its
current typed unsupported result above that bound because it has no scan
fallback.

Eighteen or more distinct keys remain over cap. Eighteen authored literals
that canonicalize to 17 distinct keys may be admitted; duplicate input must not
double-count cardinality.

## Ownership And Semantics

The accepted entity authority remains the only schema and freshness authority.
Visible accepted indexes remain the only index-selection input. The existing
prefix-cardinality metadata remains the only count data owner, and the existing
direct-count compiled entry remains the only memoized target.

The count-specific planner may construct derivative cardinality keys only from
that pinned authority and its selected accepted index. A key or cache hit may
not select a schema, prove freshness, reread stable roots, consult generated
models or survive authority replacement independently.

The shared `MAX_INDEX_BRANCH_SET_VALUES` constant remains 16 and continues to
govern pages, covering scans, branch merges, continuations and ordinary access
validation. Patch 7 does not make a 17-prefix access plan executable as a row
route. It only converts a fully covering proof into the existing count target.

Metadata absence, staleness, generation mismatch or malformed lowering remains
fail-closed. SQL falls back to its existing authoritative scan; the public
exact-count helper returns its existing typed unsupported or corruption error.
No delayed validation or changed corruption behavior is accepted.

## Required Proofs

Correctness and bounds:

- 0, 16, 256 and 2,048-row 17-key SQL counts match the predecessor result and
  SQLite reference while performing zero row and index-entry traversal;
- the 16-key count remains exact and unchanged;
- 18 distinct count keys remain on the scan fallback;
- 18 authored values canonicalized to 17 distinct keys use exact metadata
  without double counting;
- an ordinary 17-value page remains on the shared over-cap fallback;
- equality, one-field membership and composite fixed-prefix membership retain
  exact results;
- residual predicates, filtered indexes, incompatible literals and unready
  metadata cannot enter the direct terminal;
- the public exact-count adapter retains its existing 16-key bound;
- true-warm execution retains the same result, zero physical reads and compiled
  target reuse; and
- publication and same-Wasm recovery add no lifecycle state and preserve
  result and stable extent.

Build and surface controls:

- focused core direct-count/planner tests;
- one focused PocketIC ladder and fallback-control test;
- no-default, SQL-only and all-feature core checks where supported;
- raw Wasm comparison, with gzip secondary;
- stable extent, Candid, exports, generated files and package versions
  unchanged.

Failure of the instruction or physical-work gate closes Patch 7 as a no-build

are not broadened after measurement.

## Planned Landing Boundary

One reviewable patch may:

1. retain the shared 16-branch access-plan cap unchanged;
2. let the direct-count owner prove and lower up to 17 canonical exact prefixes;
3. add focused semantic, cap, fallback and physical-work tests;
4. measure the existing 16/17 scale families, true warm and raw Wasm; and
5. update the 0.237 status and active changelog notes.

Patch 7 stops after this outcome. It does not authorize a larger cap, a new
planner mode or another 0.237 implementation patch.

## Measured Outcome

The exact PocketIC ladder passes at 16, 256 and 2,048 rows. The 17-key SQL
count returns the predecessor/fixture result while performing zero row fetches
and zero index-entry reads:

| Rows | Candidate | Predecessor | Absolute saving |
| ---: | ---: | ---: | ---: |
| 16 | 2,075,520 | 3,000,421 | 924,901 |
| 256 | 2,167,004 | 7,447,688 | 5,280,684 |
| 2,048 | 2,267,492 | 42,726,968 | 40,459,476 |

The 2,048-row saving clears the frozen 35,000,000-instruction gate. True-warm
execution costs 1,238,845 instructions with one compiled-command cache hit and
zero physical reads. Sixteen distinct keys remain on their existing exact
route. Eighteen authored values canonicalized to 17 distinct keys use exact
metadata without double counting; 18 distinct keys retain the scan fallback.
The ordinary 17-value page continues to report a shared branch-cap rejection.

Focused native proof covers the same 17/18 boundary on a composite accepted
index. Same-Wasm recovery retains the exact metadata result and performs no
stable allocation at upgrade or query execution; ordinary recovery-owned
stable reconciliation remains unchanged.

Patch 7 changes four production files by approximately 150 net lines plus
focused tests. It adds one internal evidence-bounded constant and one owned
prefix representation, but no module, mutable owner, cache, invalidation edge,
persisted state, schema authority, endpoint or public behavior mode. Against
the isolated corrected Patch 6 snapshot, raw Wasm grows by 1,869 bytes to
4,583,069 bytes with SHA-256
`42b0896692f44e64f5694494095b88509b7b827a0bcf84371f863b9bcd9bc00d`,
within the 8 KiB gate. Final gzip is 1,782,329 bytes. Generated code, Candid,
exports, stable formats and package versions remain unchanged.
