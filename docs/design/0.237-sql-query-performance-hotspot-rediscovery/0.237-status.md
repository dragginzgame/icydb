## Long-Ladder Decision

No 8,192-row canary is added in Patch 2. The steep candidates are already
unambiguous over 16, 256, and 2,048 rows, while a fourth point would make the
largest single measurement hundreds of millions of instructions without
changing candidate order or identifying a removable owner. The blob and
admitted token cases are sufficiently flat that a longer ladder is also not
justified. If Patch 3 finds an unresolved nonlinear boundary, it must request
one narrowly named canary instead of broadening the profile speculatively.

### Exact Whole-Entity SQL Count Intake

`SELECT COUNT(*) FROM PerfAuditUser` scales almost entirely with avoidable row
execution:

| Fixture rows | Total | Compile | Planner | Store | Executor | Row gets |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 16 | 1,622,376 | 481,177 | 290,518 | 495,368 | 353,865 | 16 |

| 2,048 | 96,891,236 | 484,650 | 288,447 | 71,842,620 | 24,274,124 | 2,048 |

The 256-to-2,048 increase is 84,438,020 instructions. At 2,048 rows the scalar
base-row phase alone is 95,159,751 instructions; the reducer fold is only
878,592. The removable ceiling is therefore not an inferred parser or reducer
micro-cost: 96,116,744 store-plus-executor instructions are attached to reading
and ingesting every row.

The public exact-count path already represents `ExactCountPlan::Entity`, binds
it to the accepted `EntityAuthority`, and calls the shared exact-cardinality
executor. The store already owns exact entity cardinality. The SQL direct-count
path uses the same authority and executor for exact user-index prefixes, but its
compiled count entry can represent prefix keys only. With no predicate it gets
no prefix target and falls back to the measured row scan.

Existing exact-prefix SQL controls demonstrate the metadata execution shape:

| Control | Total | Store + executor | Row gets | Index entries | Sink |
| --- | ---: | ---: | ---: | ---: | --- |
| Account active/tier `IN` count | 1,572,282 | 510,778 | 0 | 0 | `IndexPrefixCardinality` |
| Token branch-set count | 1,497,188 | 537,992 | 0 | 0 | `IndexPrefixCardinality` |

These controls use the small main fixture, so they do not directly measure a
2,048-row whole-entity SQL terminal. They do prove that the current metadata
terminal performs no row or index traversal. Conservatively retaining the
2,048-row bare-count compile, planner, reconciliation remainder, and the larger
537,992-instruction metadata store/executor cost gives an estimated total of
1,312,484 and a realistic saving of 95,578,752 instructions. The theoretical
maximum removable store/executor cost is 96,116,744 instructions. Both figures
are absolute; the approximately 98.6% estimate is secondary context, not the
acceptance basis.

At the Patch 3 closeout this candidate did not authorize implementation. The
user subsequently continued the 0.237 line and Patch 4 froze a separate design
for the smallest existing-owner change: let the SQL direct-count plan
represent either whole-entity or user-index-prefix cardinality, reuse the pinned
accepted entity authority and shared exact-cardinality executor, and preserve
the current SQL scan fallback when metadata is unavailable. It must not add a
cache, persisted state, format, route, mode, public API, or schema authority.

The accepted Patch 4 budget is at most six production files, 250 net runtime
lines, one extension to the existing direct-count target/cache representation,
no new mutable owner, and no more than 8 KiB raw Wasm growth. Evidence must cover
0/16/256/2,048 rows, heap and journaled stores, insert/update/delete, journal
overlay and fold, upgrade/recovery, metadata ready/unready behavior, compiled
and shared-plan reuse, exact result equality, zero physical row/index traversal,
and unchanged non-count/predicate-count paths. Stable extent, Candid, exports,
and public behavior must remain unchanged. Exceeding this budget or discovering
another authority/failure axis returns the proposal to no-build review.
