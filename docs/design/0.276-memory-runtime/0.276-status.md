# Memory 0.44 integration repair

The maintainer requests repair of the current dependency graph's reported
compilation failures. One landing slice covers explicit runtime binding,
allocation-report projection, generated storage consumers, feature guards,
direct tests and retained-data documentation.

Memory 0.44 removes its global runtime and separates construction from
bootstrap errors. IcyDB therefore needs one binding to the host's committed
`MemoryRuntime`; storage, integrity, generated wiring and diagnostics must
observe that same instance. The simplest alternative, reverting the dependency,
would discard the maintainer's selected graph. Recreating the removed upstream
global API would duplicate its retired authority. Core owns the binding;
`ic-memory` retains bootstrap, allocation, persistence and open semantics.

The binding adds no durable state or alternative execution route. It replaces
the removed upstream process-local runtime location, accepts a bootstrapped
host instance, rejects replacement and permits repeated binding of that same
instance. Standalone generated wiring constructs and bootstraps the runtime;
composed hosts bind their already bootstrapped runtime before database startup.
Construction and binding failures remain typed at the facade boundary.
Cold startup rechecks the binding after the pool callback so a host-bound
runtime is adopted before another manager could be constructed for that backing.

`DatabaseBootstrapError::Construction` retains Memory's now-independent
construction cause, and `Binding` retains the binding refusal. Flattening both
to an internal error would lose the existing bucket-mismatch diagnostic and
typed host integration evidence. The facade owns this projection; the added
variants introduce no persisted state, mode or configuration.

Public allocation-report fields remain IcyDB-owned: use Memory's constants and
geometry-aware calculations, canonical ledger key/owner constants, and explicit
unavailable payload occupancy. The reserved ledger slot is not evidence of
validated payload contents. The checkpoint writer is unconditional; the
migration operation import is gated with its consumer.

Memory 0.44 retires earlier durable ledger images. Operators must retain the
old binary and backups for required recovery/export, then explicitly retire or
reset affected installations before adopting the new image. This source repair
performs no data reset and adds no old-format reader. Pending notes select
0.276.0; package versions and release execution remain maintainer-owned.
