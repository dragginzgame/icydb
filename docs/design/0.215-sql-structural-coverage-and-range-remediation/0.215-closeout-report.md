## Toko Conservation Flow

The maintained flow for one holdings entity is:

1. authorize the caller;
2. complete asynchronous work;
3. read current holdings;
4. calculate the complete split, merge, or transfer;
5. synchronously call
   `execute_trusted_structural_mutation_batch` without an intervening `await`;
6. consume the deterministic input-order result.

After any `await`, the application must re-read and recompute. Sequential
writes and compensation are not valid substitutes for the mixed batch.

| Scenario | Maintained request | Required outcome | Closeout evidence |
| --- | --- | --- | --- |
| Split | `Update(100 -> 60) + Insert(40)` | total remains 100 | successful mixed batch and exact after-images |
| Invalid split | `Update(60 -> 50) + invalid Insert` | source remains 60; output absent | required-field rejection before publication |
| Transfer | `Update(60 -> 70) + Update(40 -> 30)` | total remains 100 | distinct patches and exact after-images |
| Merge | `Delete(30) + Update(70 -> 100)` | one holding remains with 100 | delete before-image plus update after-image |
| Late merge failure | `Delete(40) + Update(missing)` | both original rows remain | late failure leaves staged delete unpublished |
| Duplicate target | `Update(key) + Delete(key)` | whole request rejects | typed duplicate-key rejection and unchanged row |
| Recovery | interrupted mixed journaled batch | exact admitted end state | marker, journal, row-prefix, and materialization recovery proof |
| Bounds | item, staging, row, and result limits | reject before publication | checked boundary tests and precommit result sizing |

This proves the Toko flow that motivated Slice 6 without broadening IcyDB into
application concurrency control. If application code reads, awaits, and then
submits an old calculation, that is outside this contract.

## Findings And Corrections

### P2 — Conservation test did not conserve its fixture total

The previous mixed-batch test started with quantities `100 + 40` and finished
with `60 + 20 + 20`. It proved mixed ordering, atomic failure, and Identity
ordinals, but its name overstated conservation evidence.

Correction: the fixture now exercises exact split, transfer, merge, invalid
split, late merge failure, and duplicate-target cases while checking the
maintained result and stored-row boundaries.

Consequence after correction: the existing production batch is directly
proven against the downstream conservation shape; no runtime change was
required.

### P3 — Application guidance omitted the canonical mixed batch

The public facade guide described only the insert-only convenience batch.

Correction: it now documents the heterogeneous batch with a holding split and
the required authorize/async/re-read/synchronous-submit ordering.

### P3 — Mixed-batch facade compilation was proved only by a SQL fixture

The public mixed batch itself is SQL-free, but the only compile fixture that
called it lived under `pass-sql`. That could allow a future accidental SQL
dependency to escape the ordinary structural facade contract.

Correction: the call now compiles in the base no-feature structural-write
fixture, and the duplicate SQL-only proof was removed.

### P4 — Active documentation retained two stale surface claims

The read-intent checklist referred to a maintained typed cursor even though
the same guide correctly states that scalar typed/dynamic continuation is not
exposed. The grouped contract also named the retired generic `Response<E>`
surface.

Correction: both now describe the maintained current surfaces without
compatibility terminology.

No P0 or P1 runtime finding was found during Slice 5.

## Remaining Risks

- Toko must use the documented no-interleaving sequence and must test its own
  authorization and endpoint response envelope. Those application policies do
  not belong to IcyDB's trusted mutation API.
- Scalar typed/dynamic continuation is not exposed. Applications needing
  multi-message paging require a separately designed public continuation
  surface.
- Durable general schema migration remains future 0.218 work. Existing
  production stores must not be upgraded through an unsupported transition.

These are explicit boundaries, not reachable duplicate 0.215 implementations.
