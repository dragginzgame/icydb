# IcyDB 0.244 Exact Indexed `Int32` Numeric Aggregates

Status: PATCH 1 COMPLETE — READY FOR USER VALIDATION

Last updated: 2026-08-26

Exact released predecessor:
`v0.243.1` at `859703e9fd409d8ddf6aaf567bd11e917c224d85`.

## Outcome

Allow one evidence-bounded SQL global aggregate over a direct, non-nullable
accepted `Int32` field to derive exact `SUM`, `AVG`, or both from one complete
accepted user index's synchronized leading-component multiplicities.

The path is an exact metadata fold, not an estimate, aggregate-result cache,
materialized view, index-entry scan or persisted sum. It derives one `(count,
sum)` fact in work proportional to distinct leading values and projects all
admitted outputs from that fact. Missing or stale optional evidence and every
excluded shape retain the existing prepared aggregate executor before it does
store work.

This line adds no SQL syntax, public method, generated surface, accepted-schema
authority, persisted state, stable format, cache slot, feature flag or
compatibility path.

## Demonstrated Need

The exact predecessor measures these production-shaped 2,048-row queries:

| Query | Cold instructions | True warm | Rows fetched |
| --- | ---: | ---: | ---: |
| `SELECT SUM(age) ...` | 98,081,958 | 97,717,969 | 2,048 |
| `SELECT AVG(age) ...` | 98,067,171 | 97,703,437 | 2,048 |
| Exact five-value metadata reference | 591,864 | 369,948 | 0 |

The indexed and unindexed `SUM` controls differ by only 1,257 cold
instructions. Current aggregate execution does not inspect the user index; it
loads and decodes every row. Attribution assigns 94,977,950 instructions to
base-row work and about 2.2M to reducer work, identifying more than 97.1M
removable instructions for each target.

`IndexPrefixCardinality` already retains one canonical non-empty first
component and exact row multiplicity for every leading value of a synchronized
user-index generation. Five metadata entries therefore contain the sufficient
facts for the measured queries:

```text
count = sum(multiplicity)
sum   = sum(decoded_int32_value * multiplicity)
avg   = sum / count
```

No reducer-only cleanup can remove the dominant row-load cost. The no-build
alternative is insufficient because an existing correctness authority already
holds the smaller exact input and the demonstrated saving exceeds 96M
instructions even under the conservative release ceiling.

## Frozen Admission

The exact target is prepared only when every condition below holds:

1. The statement is one global aggregate over one accepted entity.
2. There is no `WHERE`, aggregate `FILTER`, `DISTINCT`, `GROUP BY`, `HAVING`,
   cursor, authored `ORDER BY`, `LIMIT` or `OFFSET`.
3. Every output field is a direct `SUM(field)` or `AVG(field)` aggregate. Output
   expressions such as `ROUND(AVG(field), 2)` and arithmetic remain prepared.
4. Every unique terminal targets the same direct top-level accepted field.
   Either terminal may appear alone, together, in either output order, with an
   alias, or as a repeated direct output.
5. The accepted field kind is exactly `Int32` and is non-nullable.
6. One planner-visible accepted field-path user index has that field as
   component zero.
7. The index is complete: no predicate or expression key, and every compound
   suffix is direct, total, canonically indexable and non-nullable so every
   logical row contributes exactly one key.
8. Visibility is `StoreReady`, the physical `IndexId` belongs to the pinned
   accepted entity authority, and canonical index `Int64` payloads are proven
   to represent the accepted `Int32` field exactly.
9. Metadata is decodable and synchronized to the authoritative row generation
   before it may return a result.

Multiple compatible indexes use the existing deterministic exact-metadata
selection rule: shortest arity first, then stable index name. The selected
`IndexId` is immutable compiled preparation. If its metadata is unavailable
while another compatible index is usable, execution falls back; it never
reselects at runtime.

## Singular Authority And Execution Chain

```text
pinned accepted catalogue/entity authority
  -> lowering-owned exact numeric shape fact
  -> one deterministic accepted-index selection
  -> existing fingerprint-bound exact-or-prepared command slot
  -> exact aggregate executor
  -> StoreHandle recovery/freshness boundary
  -> IndexStore synchronized leading-component fold
  -> canonical SUM/AVG finalization and SQL projection
```

The existing `SqlGlobalAggregateCachedPlan` gains one exact numeric target.
The exact-terminal and session module boundaries are generalized in place;
established target orchestration remains the singular exact-or-prepared owner.
There is still one `OnceLock`, one fingerprint wrapper and one fallback-plan
owner.

When an exact target's optional metadata is unavailable, the existing
registry-scoped `QUERY_PLAN_CACHES` owner supplies the prepared fallback. The
exact command target remains cached and may become usable later. No fallback
plan is retained beside or inside it.

Publication continues to install a new outer compiled command under the new
accepted-catalogue key. Old requests may retain their old immutable command and
authority. A populated old slot is never replaced, repaired or promoted to
authority for a new snapshot.

## Metadata And Numeric Contract

The existing synchronized cardinality invariant remains authoritative:

> For one pinned accepted root, complete accepted user index and synchronized
> row/index generation, every first-component key represents exactly one
> canonical non-empty leading value in the logical row set, its multiplicity
> equals the number of logical rows carrying that value, every logical row
> contributes exactly one accepted index key, and no key or metadata entry
> exists without its logical row.

0.244 does not maintain another sum. `IndexPrefixCardinality` gains one bounded
read operation over that map. For each target-identity entry it:

- validates nonzero multiplicity;
- decodes the canonical `Int64` component through the index-key owner;
- proves the decoded value fits accepted `Int32`;
- accumulates multiplicity in checked `u64` arithmetic;
- accumulates `value * multiplicity` in checked `i128` arithmetic; and
- stops before exceeding the caller-owned metadata-entry bound.

The `i128` accumulator is sufficient by construction: one accepted value is
bounded by `i32`, total multiplicity is bounded by `u64`, and therefore the
largest possible absolute sum is below `2^95`. Checked operations remain in
place so corruption or a violated invariant fails closed rather than wrapping.

An initialized, decodable, generation-matched empty map returns exact
`(0, 0)`, which projects SQL `NULL` for both `SUM` and `AVG`. An absent,
unmaterialized, undecodable or generation-mismatched map is unavailable and
must never be interpreted as empty.

The executor converts the exact integer sum to the existing scale-zero Decimal
representation. `AVG` delegates to the existing checked decimal-average owner.
Aliases, output order and duplicate direct projections are shaped by the
existing SQL projection contract. Exact output is charged through the same
active request execution budget before response conversion.

Canonical signed-integer decoding moves below covering execution into the
index-key owner. Covering projection and the metadata fold call that one
decoder. Duplicating the sign-bit transform or allowing session code to inspect
raw components is forbidden.

## Resource And Failure Semantics

The metadata stop-after bound is derived from the currently remaining
`KeyIndexEntriesVisited` budget. The fold reports exact examined work and never
walks beyond that bound. Exact success charges its complete materialized
result row through the canonical runtime-value budget owner before returning.

An incomplete or unavailable fold enters prepared execution after charging
only the real bounded metadata probe. It does not fabricate row, decoded-value,
distinct-state or result charges. No partial exact output is observable.

| Outcome | Action |
| --- | --- |
| Synchronized complete fold | Atomically finalize and charge one exact output row |
| Metadata absent, stale, undecodable or not materialized | Prepared fallback |
| Work bound reached before completion | Prepared fallback |
| Wrong entity/index generation, impossible component kind/value, zero multiplicity, overflow or borrow conflict | Existing invariant/corruption failure; never hidden by fallback |

Supported row/index/metadata mutation invalidates synchronization before
changing projections and publishes it only after the complete authoritative
transition. Insert, update, delete, rollback, journal replay, fold and recovery
must therefore leave either the previous exact state, the complete next exact
state, or unavailable evidence.

## Rejected Alternatives

- **Reducer micro-optimization:** rejected because reducer work is only about
  2.2M of the 98M-instruction query.
- **Persisted per-index sums:** rejected because it adds correctness state,
  write amplification, recovery and a format boundary when multiplicities are
  already sufficient.
- **Aggregate result cache:** rejected because it adds data-generation keying,
  invalidation and snapshot consistency to avoid a bounded metadata fold.
- **Runtime index reselection:** rejected because the planner-selected target
  must remain the sole immutable execution contract.
- **Nullable, filtered, DISTINCT, expression or arbitrary numeric inputs:**
  rejected because current metadata does not prove those semantics and the
  measured `Int32` target needs none of them.
- **A separate exact-numeric cache/executor lifecycle:** rejected because it
  would duplicate the singular exact-or-prepared owner established in 0.240.

## Required Proof

- `SUM`, `AVG`, both orders, aliases and repeated direct outputs;
- empty initialized state, deletion of the final value, one duplicate group,
  five groups, all-unique values, negative/zero/positive values and `Int32`
  extrema;
- single-field and complete compound indexes, deterministic multi-index choice,
  and selected-unavailable without runtime reselection;
- wrong type, nullable, unindexed, non-leading, partial/expression index,
  filtered, DISTINCT, aggregate `FILTER`, output expression, `HAVING`, authored
  ordering, limit/offset and grouped controls retaining prepared execution;
- insert, update, delete, rollback, journal replay/fold, projection reset,
  publication, same-Wasm recovery and reinstall;
- old request retained across publication and new request bound to the new
  accepted command;
- missing/stale/unmaterialized metadata, bound exhaustion, missing root,
  mismatched target, borrow conflict and malformed component behavior;
- injected missing row, missing index entry and orphan index entry cannot
  publish a synchronized incorrect sum;
- cold miss, true-warm hit and unavailable-to-available transition;
- zero rows and physical index entries on success, exact metadata work,
  deterministic SQLite equality, Candid/export/stable equality, no-default,
  SQL-only and all-feature builds; and
- paired final raw/gzip Wasm plus production/test line deltas.
