## Current Internal-Library Findings

- The existing parser plus `SqlStatementDispatch` can own immutable syntax
  without a session or accepted authority. The proposed API adds a bindings
  slice to the existing parsed-query method and intentionally exposes the
  existing dispatch type; it adds no prepared-query carrier.
- The maintained `sql_perf` repeated SQL loop currently reparses each time.
  The existing parsed path already avoids this; bindings are not necessary for
  that isolated gain. The dynamic-query actor's changing-key loop already
  avoids value rendering and parsing. Neither observation demonstrates a
  maintainability advantage for SQL over structural queries.
- The design's application example initializes thread-local syntax in existing
  init/post-upgrade hooks and creates a fresh session per invocation. A
  query-only lazy initializer cannot persist its newly parsed syntax for the
  next query because query mutations are discarded. See the
  [IC query semantics](https://docs.internetcomputer.org/references/ic-interface-spec/abstract-behavior/).
  Multi-message reuse and upgrade rebuild still need integration evidence;
  the proposed example has not been compiled.
- Skipping SQL command caching removes a new binding digest and per-vector SQL
  residents, but shared `PreparedQueryTemplate::recent_bound` still retains a
  concrete plan. Its estimate uses a 24-KiB base plus index estimates without
  traversing memo allocations; replacement does not reweight. The shared
  cache's 4-MiB configured estimate is therefore not an actual-byte proof.
  Ordinary shared `PreparedPlan` insertion calls `BoundedCache::insert`, whose
  retained weight is zero. Current-value identity and reachable operand-copy
  accounting remain a focused gate at this existing owner, not permission for
  a broader cache redesign.
- All 15 existing `db::session::tests::unit_ordering` tests passed on the source
  baseline with the SQL feature: parsed routing, structural/SQL parameterized
  plan reuse, wrong-type range rejection and aggregate parity are covered.
  This does not test new placeholder binding, prove absence of other aggregate
  bugs, or measure execution cost. The build emitted 64 existing dead-code
  warnings; no clippy failure occurred. Full suites were not run.

The proposed bound-HAVING aggregate mismatch has not been tied to an observed
wrong-result query in this review. Bound HAVING is deferred rather than making
aggregate-result changes a prerequisite for WHERE bindings. Measure AST clone
and operand allocation costs separately from parser work before claiming an
overall performance improvement. No network lifecycle action was taken for
these current source checks and host tests.

## Follow-Up: Executed Ownership And Retention Probes

Source baseline: `07f14d9f12bbaf2f37a32815651043a657fb6197`. Three temporary
native probes ran with SQL enabled, Rust 1.97.1, the optimized test profile and
one test thread. All three passed on the final run. No runtime fix or binding
implementation is implied by these results.

### Retained syntax and current authority

A thread-local `LazyCell<SqlStatementDispatch<'static>>` initialized
`SELECT label FROM Singleton ORDER BY id LIMIT 1` before any session or accepted
schema existed. After startup and insertion, the startup session was dropped.
Three fresh request sessions executed the same dispatch and returned the
expected label. A subsequent accepted revision renamed `label` and its index
field path to `renamed_label`. Another fresh session using the retained dispatch
returned the typed missing-field context for projection `label`. The counted
dispatch initializer ran once.

This validates the core Rust ownership/current-authority pattern, not the
proposed bound facade, canister lifecycle hooks or upgrade behavior. The first
probe run failed during test schema construction because the renamed field's
index path had not also been renamed. Correcting that fixture made the test
pass; this was not a discovered runtime failure.

### Construction cost control

The control query was `SELECT id, label FROM Singleton WHERE label = 'singleton'
AND amount >= U256 '2' ORDER BY id LIMIT 50`. Each sample performed 10,000
operations through `black_box`, including disposal of the constructed object.

| Operation | Sample 1, ns/op | Sample 2, ns/op |
| --- | ---: | ---: |
| Parse SQL into AST | 1,198 | 1,167 |
| Clone already-parsed AST | 291 | 259 |
| Construct matching DynamicQuery predicates/projection/order/limit | 299 | 315 |

These are two host construction-only samples, not full-query latency, Wasm
instruction counts or a stable distribution. Ordinary allocations contribute
to these timings, but allocation counts/bytes were not instrumented. Binding,
normalization, planning and execution were not measured. AST cloning is
material relative to structural construction; avoiding parsing does not prove
that bound SQL is cheaper or simpler overall. These samples do not justify
numerical release ceilings.

### Reproduced uncharged shared resident

A structural read selected `id` and `label`, ordered by `label`, with limit 3,
and returned the seeded row. Shared-cache `(entry_count, retained_weight)`
changed from `(0, 0)` to `(1, 0)`: a concrete shared plan was retained with no
byte charge. This is not a measurement of its actual heap size or evidence of
exhausting the separate entry-count bound.

Changing that insert call alone cannot fix the bound. Cached
`PreparedExecutionPlanResidents` also contains ten lazy residents for projection,
covering reads, grouped preparation, scalar/aggregate preparation, initial
routing and slot layouts. Allocations can attach after insertion through shared
ownership. The template's recent-bound memo retains this same graph. Correct
accounting must cover initial keys/plans and future retained allocations, not
only original binding bytes or shallow memo size.

This is an independently reviewable shared-plan accounting outcome affecting
structural callers as well as future SQL bindings. The current binding slice
excludes a broad cache project. A separate prerequisite landing slice was
proposed to the user; it is not yet authorized or added to the tracker. Do not
substitute a guessed fixed charge, silently disable shared-plan reuse, or mark
the gate passed.

Temporary instrumentation was removed. Its reproduction patch remains at
`/tmp/icydb-0254-internal-preflight.V921sh/probe.patch`; source files match their
pre-probe contents. Only documentation remains changed by this follow-up. The
build emitted the same 64 existing dead-code warnings. Full suites, binding
execution, allocation instrumentation and Wasm/PocketIC measurements were not
run. No network lifecycle action occurred.

## 1. Whole-Slot Validation: The Actual Ordering Hazard

`prepare_sql_statement` currently does identifier/scope normalization before
parameter rejection. That normalization is not itself the demonstrated
constant-folding hazard: `normalize_select_statement_to_expected_entity` and
`SqlIdentifierNormalizer` preserve the typed literal/parameter nodes.

The destructive seam is `lower_sql_bool_expr_internal` in
`db/sql/lowering/predicate/mod.rs`: it calls `lower_sql_expr`, then clause-shape
validation, then `normalize_where_bool_expr` or
`normalize_scalar_where_bool_expr`. Those routines fold literal-only terms and
simplify Boolean constants before downstream accepted-field normalization.
`validate_where_bool_expr` only delegates to clause-shape admission; it does not
prove every field operand's accepted type.

The binding validation pass must complete before that seam, after non-folding
identifier/alias resolution. For direct field comparisons and IN elements,
reuse the accepted predicate admission contract and write its normalized `Value`
back to the typed operand. Scalar-expression admission must traverse every
unsimplified child through the planner's type owner; a scalar projection compiler
alone is insufficient. `compile_scalar_projection_expr_with_schema` resolves
slots/compiles expressions, but does not call `infer_expr_type` to validate all
operand combinations. It also rejects aggregate nodes, so it cannot serve as
the HAVING validator.

`infer_sum_aggregate_type` currently returns the input-derived type. The maintained
reducer returns Decimal for admitted non-U256 SUM and AVG, U256 for U256 SUM,
and Null for empty SUM/AVG. Resolve this at the existing planner type owner,
including nullable-result behavior, not by narrowing a HAVING binding using
the source field's bounds. Existing expression comparisons have their own
numeric/opaque/null admission rules; do not apply broad expression inference
to every field predicate and accidentally narrow maintained field semantics.

These findings pin the seam and rule out two false proofs. The complete
owner-local integration and aggregate-result parity fixtures remain gates.

## 2. Native Candid Probe

An isolated Rust probe outside the workspace exercised the actual `InputValue`
decoder from this source, with Candid 0.10.35, serde 1.0.229 and CDK 0.20.2.
It used the proposed request fields and `decode_args_with_config_debug`.
Exploratory settings were decoding quota **1,000,000**, skipping quota **10,000**,
type-table maximum **256**, and abbreviated errors. These are **probe settings,
not frozen endpoint limits**. In particular, they have not been qualified
against the existing maximum SQL text size or all scalar families.

The second variant changes only deserialization of the bindings vector: check
the sequence length hint before allocating, and use a per-element seed that
rejects slot 65 before deserializing it even if the hint is absent. Both variants
have the same Candid record/vector/InputValue type. No scalar wire enum or
alternate public carrier was introduced.

| Wire case | Ordinary Vec decoding | Bounded-vector prototype |
| --- | --- | --- |
| 64 Nat64 values; 830 wire bytes | Decodes; 2,231 decoding work units | Same result and work units |
| 65 Nat64 values; 839 wire bytes | Decodes all 65 | Rejects before element allocation |
| 65,536 Null values; 65,792 wire bytes | Decodes; 852,919 work units; 10,501,923 cumulative allocation-request bytes; largest allocation 4,194,304 bytes | Rejects; 16,498 cumulative allocation-request bytes; largest allocation 1,536 bytes |
| One 65,536-byte Blob | Decodes; 263,110 work units | Same result and work units |
| One 65,536-byte Text | Decodes; 66,501 work units | Same result and work units |
| Nested List at depths 16 / 64 / 128 | Decodes | Still decodes: the vector visitor is not a recursive/scalar admission guard |
| Extra record field / extra argument containing 2,048 32-byte strings | Rejects under quotas | Rejects under quotas |
| Ordinary request with decoding quota 100 | Not the control case | Rejects |
| Extra 1,000-element Nat64 vector with skipping quota 100 | Not the control case | Rejects |

Allocation figures are cumulative allocator request sizes, including reallocations,
not peak live heap, resident memory or Wasm allocation measurements. The first
case also initializes Candid type metadata; do not use its cold allocation count
as a warm-path regression. No native timing is used as an instruction gate.

Conclusion: a request-local bounded vector visitor is required; choosing a
decoding quota that admits the largest legitimate scalar does not enforce the
64-slot policy before allocations. The vector visitor preserves the proposed
wire shape, but does not yet establish scalar/container safety or failure privacy.

A malformed 20-byte header containing a synthetic private sentinel also caused
abbreviated Candid Debug output to contain that sentinel's hex encoding. Both
vector-decoder variants exhibited it. The previously specified constant
payload-free public failure is necessary; `set_full_error_message(false)` is
not a sanitization boundary.

## 3. Wasm Decoder Gate

The locked Candid `src/utils.rs::check_recursion_depth` uses remaining-stack
checks on native targets but is a no-op on Wasm. Its u16 depth-counter overflow
check is not an adequate canister stack bound. Native deeply nested decoding
results therefore cannot be promoted to a Wasm safety verdict.

A standalone CDK query probe checked the proposed full-InputValue decoder under
PocketIC 16.0.0, independently of database execution. It used the same
1,000,000/10,000/256 quota/type-table settings, a 128-KiB exploratory wire cap,
and a custom decoder that maps errors to a fixed trap message. This deliberately
tests the generic InputValue decoding path; it does not implement the proposed
vector visitor or scalar-family gate. A vector visitor would not prevent the
single-slot recursive cases below.

| Case | Wire bytes | Result / instructions through handler entry |
| --- | ---: | --- |
| Empty bindings, empty SQL | 225 | Decoded; 772,547 instructions |
| 64 Nat64 bindings, empty SQL | 801 | Decoded; 1,099,018 instructions |
| One List binding, depth 128 | 295 | Decoded; 2,005,724 instructions |
| One List binding, depth 512 | 1,063 | Decoded; 6,470,428 instructions |
| One List binding, depth 1,024 | 2,087 | Engine `CanisterTrapped`, heap out of bounds |
| One List binding, depth 2,048 / 4,096 | 4,135 / 8,231 | Same engine trap |
| Extra skipped recursive argument, depth 128 | 499 | Decoded; 2,702,532 instructions |
| Extra skipped recursive argument, depth 512 / 1,024 | 1,267 / 2,291 | Controlled `CanisterCalledTrap` from the fixed decoder-error boundary |

The engine traps are observably different from the controlled decoder rejection.
This establishes failure of the proposed generic decoding path for small deep
inputs; it does not establish a precise stack-byte limit or peak heap usage.
The skipped-argument cases passed their rejection boundary, but do not prove
all skipped field/optional/type-table shapes safe.

Probe artifact: `target/icydb/wasm32-unknown-unknown/release/icydb_0254_decoder_preflight.wasm`,
SHA-256 `3626df16f4fa7f6fdd25ef6c5cd4f26566f977e413a29361118c39bc981e880f`.
It is compiler-emitted opt-z/fat-LTO/one-codegen-unit/panic-abort/stripped Wasm,
not a maintained post-link actor comparison. Its raw size is 529,879 bytes,
with 1,216 defined functions and 465,500 code-section bytes. Do not attribute
these totals to incremental binding overhead or use them as a release ceiling.

**Disposition under the original scope:** stop before exposing the new request. The next bounded design
correction is early scalar-family rejection during deserialization, alongside
the proven bounded-vector approach, while retaining the same `InputValue`
Candid type and canonical scalar decoders. Investigate a request-local Serde
enum-access guard that rejects Enum/List/Map before their payloads are decoded,
not a parallel scalar casting table or a new public wire enum. Re-run the deep
binding and skipped-data cases on that shape before treating this gate as passed.
If this requires changing Candid itself or introducing a separate wire value
surface, revise the design explicitly rather than silently expanding the slice.

Remaining endpoint proof includes oversized declared vectors, recursive rejected
values, large scalar families, malformed type tables, and recursively expensive
skipped fields/arguments/optional values. Public failure and log inspection must
check encoded as well as plain-text payload sentinels; absence of the original
ASCII string alone is not a privacy proof.

## 4. Cache Retention Finding

`CompiledSqlCommand::Select` and `GlobalAggregate` retain their command through
Arc and an additional plan through `Rc<OnceLock<...>>`. The plan is populated
later by `set_cached_select_plan` / `set_cached_global_aggregate_plan`, after
initial compiled-command insertion. Charging only initial command size would
undercharge later retained plan/operand allocations even with a weighted cache.

The existing SQL cache owner must reserve a conservative full weight before
insertion or enforce an updated weight before attaching the lazy plan. Pin that
choice and bound with the retained-allocation inventory before implementation.
Do not add an unaccounted post-insert mutation or another cache owner. Arc/Rc
command clones are shared retention, not automatically independent payload
copies; charge actual owned copies and document conservative shared accounting.

budget are not frozen. This preflight has not established the three-actor matrix,
