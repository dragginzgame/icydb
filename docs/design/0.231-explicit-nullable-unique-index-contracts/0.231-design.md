## Planning Status And Authorization

The user explicitly authorized this design document before predecessor
closeout as a documentation-only exception to normal minor-line sequencing.
That exception does not authorize implementation, change the numeric
dependency order, or promote this document over unfinished 0.229 or 0.230
work.

0.231 narrows the accepted unique-index contract. A unique index whose key can
omit an entry because one or more key sources are nullable is valid only when
its existing filtered-index predicate explicitly requires every such source to
be non-null. The line does not encode `NULL`, change physical uniqueness, add a
second index representation, or create a new planner route.

Implementation requires completed 0.229 and 0.230 closeouts, Patch 1
reconciliation against that exact predecessor, review of the three-patch
tracker and hard-cut impact, and explicit user authorization for 0.231
implementation.

## Current-Surface Reconciliation

| Concern | Maintained authority | Concrete remaining gap |
| --- | --- | --- |
| Accepted schema | `AcceptedSchemaSnapshot` wraps only snapshots that pass structural integrity | Index integrity confirms key/path metadata but does not reject an implicit nullable unique key |
| Physical index membership | Canonical index-key encoding returns no entry when any required component is `NULL` | Correct omission is easy to mistake for complete natural-identity enforcement |
| Unique enforcement | Accepted `PersistedIndexSnapshot::unique` plus the accepted constraint catalog and unique-index plan own enforcement | A row with any null key source has no index membership and therefore no uniqueness probe |
| Filtered indexes | Accepted `predicate_sql`, predicate compilation, row evaluation, physical rebuild, and planner guard implication own partial membership | No accepted-contract rule requires the predicate to expose nullable unique-key omission explicitly |
| Generated proposals | `IndexFragment` and catalog-native lowering produce the same persisted index snapshot used at runtime | A generated unique index can lower with a nullable key and no explicit non-null guard |
| SQL DDL | `CREATE UNIQUE INDEX ... WHERE ...` already lowers into catalog-native candidate publication and bounded activation | Binding accepts the same ambiguous nullable unique shape |
| Nullability transitions | Accepted-after schema derivation owns `SET/DROP NOT NULL` and generated reconciliation | Making a unique-key source nullable can leave an ambiguous accepted index behind |
| Planner eligibility | The filtered-index implication owner proves a bounded comparison subset | It does not prove an `IS NOT NULL` guard from an exact matching guard or a non-null comparison |
| Cardinality | 0.230 counts only entries actually present in accepted user indexes | 0.231 must preserve that omission and must not reinterpret existing counts as rows with null components |
| Diagnostics | Proposal and SQL DDL paths already have typed admission errors that converge on standard error projection | No exact failure reason identifies a nullable unique index missing explicit guards |

The production intake provides a concrete workload: natural identities for
sets, items, and variants included optional release, collector, or edition
components. Rows with a null component were intentionally absent from the
physical index, so the apparent unique natural identity was neither complete
nor safely discoverable through that index.

Patch 1 must re-run this audit after 0.230. It removes or contracts 0.231 if the
accepted predecessor already owns the exact rule, if maintained proposal
syntax cannot express the required guard, or if the workload no longer
demonstrates an ambiguous accepted contract. No implementation patch may use
the provisional `v0.229.0` inspection identity as its comparison baseline.

The current evidence for the gap is concrete:

- `PersistedSchemaSnapshot::has_valid_integrity` and
  `schema_snapshot_index_integrity_detail` validate active and candidate key
  structure, but do not relate `unique`, source nullability, and
  `predicate_sql`;
- `build_accepted_field_path_index_key_from_components` and
  `build_accepted_expression_index_key_from_components` return no complete key
  as soon as one component returns `None`;
- every maintained expression-index operation has one accepted source path,
  propagates a `NULL` source to no component, and returns a value for an
  admitted non-null source;
- accepted unique-index enforcement consumes those physically present keys, so
  a row with no complete key reaches no collision probe; and
- generated lowering, SQL candidate construction, candidate activation,
  current-format decode, and nullability mutation all converge on existing
  structural integrity without the proposed relationship check.

Thus current accepted metadata can expose a unique natural-identity contract
whose physical membership silently omits null-bearing rows. This is the gap
Patch 1 must either reproduce against the accepted 0.230 predecessor or use as
the reason to cancel the line if the predecessor has already closed it.

## Decision Summary

For one accepted index `I`, let a canonical source identity be the accepted
root field identity plus its exact relative nested path. The current root label
is retained only for deterministic diagnostics. Renames and frontend aliases
must bind to this identity before comparison; raw SQL spelling is not path
identity.

Define `N(I)` as the distinct canonical source identities whose resolution can
omit that key item under the accepted row contract:

- `PersistedIndexKeySnapshot::FieldPath` contributes each exact field path;
- `PersistedIndexKeySnapshot::Items` contributes the path from every
  `FieldPath` item and the sole `source()` path from every `Expression` item;
- mixed field/expression keys take the union in key-item order; and
- repeated identities are retained once at their first key-item occurrence.

The maintained expression representation admits exactly one source path per
item. It has no zero-source or multi-source expression form. `LOWER`, `UPPER`,
`TRIM`, `LOWER(TRIM(...))`, `DATE`, `YEAR`, `MONTH`, and `DAY` all omit their
component for a `NULL` source and produce a non-null result for an admitted
non-null source. Therefore 0.231 derives expression omission from that one
source contract; it does not infer arbitrary function nullability. If Patch 1
finds a maintained zero-source, multi-source, null-recovering, or
non-null-to-null expression form in the accepted 0.230 representation, this
definition is incomplete and Patch 1 must contract or redesign the line before
implementation.

The implementation owner must classify expression null propagation with an
exhaustive match and no wildcard arm. The current proof has this bounded
shape:

```text
match operation {
    Lower | Upper | Trim | LowerTrim
    | Date | Year | Month | Day
        => SourceNullOmitsComponentAndNonNullSourceProducesComponent,
}
```

Adding an operation therefore requires an explicit decision about source
count, source-null behavior, and non-null-source result behavior. It cannot
inherit the current proof accidentally.

For a nested path, "can omit" follows the maintained physical resolver, not a
display-only notion of nullability. The current terminal
`PersistedIndexFieldPathSnapshot::nullable()` bit is not proved
ancestor-closed: Patch 1 must trace a nullable top-level field and every
nullable nested prefix through accepted row decode and key construction. A
nullable ancestor or absent member contributes the exact terminal source to
`N(I)` only when that state is valid under the accepted row contract and the
physical builder maps it to no component. A non-map ancestor, malformed value,
type error, or other failed path resolution remains a typed integrity or row
decode failure and must not be reclassified or repaired by 0.231. If the
accepted 0.230 resolver admits an ancestor-null shape but cannot classify it
consistently, Patch 1 blocks this line and records that predecessor defect
separately.

Physical path resolution receives the same exhaustive treatment, with no
catch-all that turns failed resolution into nullability:

```text
valid present value        -> component
valid nullable/absent path -> omitted component
malformed or type mismatch -> typed failure
```

Patch 1 must identify the exact accepted 0.230 resolver result type and map
every maintained variant into one of those three outcomes. A future resolver
variant must require an explicit classification.

Define `G(I)` as the distinct canonical source identities bound from exact
top-level conjunctive `IS NOT NULL` leaves in the normalized accepted
filtered-index predicate.

The accepted contract is:

```text
valid(I) = !I.unique || N(I).is_empty() || N(I) is a subset of G(I)
```

For a unique index with nullable key sources:

- a predicate is required;
- every nullable source requires its own exact `path IS NOT NULL` conjunct;
- additional admitted predicate conjuncts remain allowed; and
- `OR`, `NOT`, ordinary comparisons, function inference, or coincidental
  three-valued-logic exclusion do not substitute for the explicit guard at
  schema admission.

Parentheses and normalization that preserve a conjunction are not separate
forms. The contract is proved from the already admitted predicate structure,
not by matching rendered SQL strings.

### Guard Extraction Contract

Accepted index metadata continues to persist only `predicate_sql`; there is no
persisted predicate AST today and 0.231 does not add one. The validator uses
the existing `parse_sql_predicate` and `normalize` authorities transiently,
then walks only the normalized root:

- a root `Predicate::IsNotNull { field }` contributes its bound canonical
  source identity;
- a root `Predicate::And(children)` recursively contributes only such direct
  conjunct leaves;
- normalization-flattened parentheses, reordered conjunctions, duplicate
  guards, repeated key sources, unrelated guards, and additional admitted
  conjuncts are deterministic and allowed; and
- `OR`, `NOT`, comparisons, `IS NULL`, casts, functions, expression-to-source
  reasoning, and any other leaf contribute no guard.

Generated and SQL authoring paths retain their existing predicate admission
checks. Raw snapshot integrity has no persisted AST to trust, so an affected
nullable unique index must successfully parse, normalize, and bind its stored
predicate before it can produce `G(I)`. A parse/bind failure contributes no
guard and fails through the maintained malformed-predicate or raw-corruption
classification; it is not reported as a missing nullable guard. This line does
not add a general second integrity pass for unaffected predicates.

Generated `SourceCheckExpr` lowering and SQL DDL must both reach the same
transient parse, normalize, accepted-row binding, and guard-extraction path.
Neither frontend may compare authored or rendered SQL text. Because current
normalization flattens `AND`, removes only neutral structure, sorts children,
and preserves `NOT` and null-test leaves, equivalent accepted conjunctions do
not acquire different `G(I)` values.

Examples:

| Index shape | Outcome |
| --- | --- |
| `UNIQUE (account_id)` where `account_id` is non-null | Accepted; no new predicate requirement |
| `UNIQUE (release_date)` where `release_date` is nullable | Rejected without a predicate |
| `UNIQUE (release_date) WHERE release_date IS NOT NULL` | Accepted |
| `UNIQUE (set_id, edition_code)` where only `edition_code` is nullable, guarded by `edition_code IS NOT NULL` | Accepted |
| Same composite key guarded only by `set_id IS NOT NULL` | Rejected; the nullable source remains unguarded |
| Nullable unique key with `WHERE active = TRUE` | Rejected; partial membership is explicit but nullable omission is not |
| Nullable unique key with `WHERE field > 0` | Rejected at schema admission; logical non-null inference is deliberately outside this contract |
| Non-unique nullable index with no predicate | Unchanged; null components still omit the complete entry |

## User Outcome

After 0.231:

- an accepted unique index cannot silently look like a complete natural
  identity while omitting rows with null key components;
- generated proposals and SQL DDL reject the ambiguous shape before durable
  candidate publication or stable allocation;
- the rejection identifies the index and missing canonical non-null guards
  through the existing typed error families;
- authors can deliberately request partial uniqueness by providing the exact
  guards; and
- equality/range queries that prove those guards can use the existing filtered
  index route without adding the guards redundantly to ordinary application
  SQL.

Documentation states the resulting semantics directly: uniqueness applies
only to rows satisfying the accepted predicate, and every row with a null key
source is outside a compliant nullable unique index because the predicate must
exclude it.

## Canonical Ownership And Converged Flow

Accepted schema remains runtime authority. The index-integrity owner derives
one bounded nullable-unique proof from:

- accepted `unique`;
- accepted ordered key items and their source nullability; and
- a transient parse and normalization of accepted filtered-index
  `predicate_sql` through the existing predicate authority.

### Accepted-Snapshot Construction Boundary

Patch 1 must name the exact accepted 0.230 predicate binder signature and prove
that nullable-unique validation does not depend on an
`AcceptedSchemaSnapshot` that is still being constructed. The frozen
construction order is:

1. validate the candidate snapshot's bounded base structure, including key and
   path shape;
2. construct or borrow the smallest read-only binding context from that
   structurally valid candidate snapshot, reusing the maintained context type
   when one exists;
3. parse, normalize, and bind `predicate_sql` through the existing predicate
   authority using that context;
4. run the sole nullable-unique semantic validator over the bound candidate;
   and
5. construct `AcceptedSchemaSnapshot` only after all structural and semantic
   checks succeed.

That staged construction is one validation boundary, not a second semantic
owner or predicate representation. Any new binding-context type is ephemeral,
borrowed, bounded by maintained schema limits, and stores no accepted proof.
If the accepted 0.230 binder can operate only on an already accepted wrapper
and cannot be narrowed without duplicating predicate semantics, Patch 1 blocks
implementation and records the circularity explicitly.

The current `schema_snapshot_index_integrity_detail` and
`PersistedSchemaSnapshot::has_valid_integrity` APIs return only `Option<()>`
and `bool`. Patch 2 must make one canonical detailed integrity path return a
typed result, with the exact maintained receiver and arguments frozen by Patch
1. The intended relationship is:

```text
schema_snapshot_integrity_detail(candidate)
    -> Result<(), SchemaSnapshotIntegrityError>

has_valid_integrity(candidate)
    -> schema_snapshot_integrity_detail(candidate).is_ok()
```

The Boolean method remains only a mechanical convenience wrapper for callers
that need no detail. Accepted wrapping, raw decode/reopen, generated
application, SQL DDL, and candidate promotion consume the detailed result when
they must project a specific typed boundary; they do not rerun or locally
reconstruct `N(I)` or `G(I)`.

The intended flow is:

```text
generated proposal ----\
                        -> lower candidate index
SQL DDL ---------------/          |
                                   v
                     accepted index-contract validator
                          | accepted          | typed rejection
                          v                   v
                candidate/publication     frontend projection
                          |
                          v
              physical index + constraint owners
                          |
                          v
             existing filtered-index planner proof
```

After the existing predicate parser/binder succeeds, one core
`validate_nullable_unique_index_contract`-shaped function returns either an
ephemeral proof or one typed `NullableUniqueIndexContractError`. Predicate
parse/bind failures retain their existing error and are never converted into
that nullable-contract error. The semantic call edge belongs beneath the
canonical detailed schema-integrity path and its index-specific owner, so the
`PersistedSchemaSnapshot::has_valid_integrity` Boolean wrapper covers both
active and candidate index collections and `AcceptedSchemaSnapshot::try_new`
cannot bypass it. The raw codec must consume the detailed owner and map its
typed result, not call a Boolean and invent a decoder-local classification.

Ownership is fixed as follows:

| Class | Maintained path | 0.231 responsibility |
| --- | --- | --- |
| Canonical validator owner | Typed `schema_snapshot_index_integrity_detail`, composed by the typed whole-snapshot integrity path beneath the Boolean `PersistedSchemaSnapshot::has_valid_integrity` wrapper | Derive `N(I)` and `G(I)` and return the sole semantic violation |
| Mechanical accepted wrapper | `AcceptedSchemaSnapshot::try_new` | Consume canonical detailed integrity; no nullable-unique logic |
| Mechanical raw ingress/egress | `decode_persisted_schema_snapshot`, `encode_persisted_schema_snapshot`, schema-store reopen/cache decode | Consume the same detailed integrity result and map failure at the maintained persisted-state boundary |
| Generated frontend | initial lowering and generated reconciliation/application | Build the final candidate and project the shared typed violation; no generated-model runtime fallback |
| SQL frontend | `bind_create_index_statement` and schema DDL admission | Bind author intent, then project the shared violation through `SqlDdlBindError` and `SchemaDdlAdmissionError` |
| Candidate lifecycle | SQL unique candidate construction, validation/promotion, and abort | Candidate creation and promotion consume canonical integrity; abort removes state and adds no semantic admission rule |
| Nullability/path transition | accepted-after field, nested-path, rename, migration, and generated reconciliation derivation | Validate the complete final candidate snapshot once |
| Physical consumers | accepted/rebuild key builders, unique probe, staged generation, and constraint catalog | Preserve omission, bytes, and present-entry uniqueness; consume no guard metadata |
| Planner consumer | `predicate_implies_predicate_for_planner` through filtered-index eligibility | Extend the existing full-predicate implication owner only in Patch 3 |

Direct callers of `has_valid_integrity`, raw codec ingress, candidate promotion,
and accepted-after derivation are explicit bypass-audit targets because not all
of them call `AcceptedSchemaSnapshot::try_new` first. The test-only unchecked
`AcceptedSchemaSnapshot::new` remains fixture-only and cannot gain a production
call edge. A frontend may project the typed error earlier, but it must delegate
the complete accepted inputs to the canonical validator rather than
reimplement `N(I)`, `G(I)`, or their subset check.

Candidate proof is revision-local and ephemeral. Successful candidate creation
never stores or implies a permanently valid nullable-unique proof. Promotion
must either:

- re-run the canonical validator against the exact final accepted-after schema
  revision; or
- consume the existing 0.230 revision/invalidation authority only after Patch
  1 proves that it invalidates the candidate for every relevant source, nested
  path, key item, expression operation/source, predicate, and nullability
  change.

For example, a candidate created while its source is non-null cannot promote
from that old proof after the source becomes nullable. It must be invalidated
or revalidated against the now-required guard. Patch 1 maps this invariant to
the exact accepted 0.230 candidate revision and invalidation symbols. 0.231
adds no persisted `validated`, nullable-unique, or guard-proof bit.

The accepted constraint catalog continues to reference the unique index by
identity. It does not duplicate nullable paths, guard paths, or predicate
semantics. Physical key construction, unique probing, staged generation,
publication, and 0.230 cardinality continue to consume only the accepted index
contract.

## Admission And Publication Boundary

Every nullable-unique decision is fallible input-dependent work and therefore
occurs before schema-marker or candidate-generation publication, stable-memory
allocation, constraint-identity advancement, index activation, new-write-gate
publication, or journal publication.

The following accepted-after changes must all satisfy the same rule:

- initial generated schema publication;
- generated index addition or predicate/key change;
- SQL DDL unique-index creation;
- promotion of a candidate unique index;
- a field or nested source becoming nullable;
- a field-path or expression source changing; and
- current-format accepted snapshot decode or reopen.

Candidate promotion validates the exact final accepted-after snapshot, not
the candidate's creation-time schema. Any use of 0.230 freshness in place of
revalidation must prove the exhaustive invalidation coverage above.

Rejection leaves accepted schema, candidate catalogs, constraint identity
allocators, physical index generations, stable allocators, markers, new-write
gates, and journal state byte-for-byte unchanged. Previewed identities may be
computed but are not consumed. No repair, automatic predicate injection, or
post-marker rollback path is added.

Making every nullable key source non-null may make an unfiltered unique index
valid. Making one source nullable requires an explicit guard in the complete
accepted-after candidate; publication order cannot expose an intermediate
ambiguous shape. Where generated reconciliation can carry predicate and
nullability changes together, it validates that final snapshot once. SQL DDL
does not gain an `ALTER INDEX` or multi-statement transaction for this line:
an operator must establish a guarded replacement while the source is still
non-null, complete its unique activation, and only then drop the not-null
contract. An existing explicit predicate is never removed automatically when
nullability tightens.

`CREATE INDEX IF NOT EXISTS` retains its maintained classification. An exact
same-name active or live-candidate contract is a true no-op because that object
has already passed accepted/candidate integrity. A same-name non-exact contract
is a conflict, not a no-op; an absent name builds and validates the complete
new candidate. `IF NOT EXISTS` must not become a frontend exemption from the
shared rule. Candidate abort remains a removal-only transition and leaves no
new accepted shape.

## Planner Guard Implication

The admitted predicate remains the sole filtered-index membership contract.
0.231 extends the existing bounded implication owner only enough to make the
new explicit contract usable:

- an exact query `path IS NOT NULL` implies the matching required guard;
- an already supported strict equality or ordered comparison of the same bound
  canonical field path to a non-null bound value implies the matching guard;
- an unsatisfiable query continues to imply every guard; and
- conjunction combines those facts.

Unsupported `OR`, `NOT`, cross-field comparison, expression-to-source
inference, nullable parameter uncertainty, and broader SQL theorem proving
remain conservative. A query must prove every predicate conjunct before the
filtered index becomes eligible. In particular, a composite prefix query that
does not constrain a later nullable key source cannot use the index if doing so
would omit matching null-bearing rows.

An equality or ordered comparison proves a non-null guard only when its bound
value is already proven non-null by maintained binding. A nullable or unknown
parameter does not. Predicates with additional conjuncts remain eligible only
when the query implies those conjuncts too; proving every nullable guard is
necessary but never sufficient on its own. Every newly eligible case requires
indexed-route versus forced full-scan result parity.

This is an extension of the existing filtered-index implication function, not
a new access path, optimizer, nullability lattice, or planner artifact. Query
and index predicate clauses are compared structurally after the existing index
plan compilation parses and normalizes the accepted predicate. 0.231 adds no
second parser or rendered-string matching path.

## Diagnostics

The canonical violation carries bounded accepted facts:

- accepted index identity/name;
- ordered nullable source paths; and
- the subset missing exact guards.

Both path lists use accepted key-item order with first-occurrence
deduplication; the missing list preserves that same relative order. Their
length is bounded by the maintained maximum key-item count, and every path is
bounded by the maintained accepted path depth/name limits. The error stores no
predicate AST, rendered predicate, row value, or unbounded explanation text.

Diagnostic precedence is deterministic:

1. key and path structural validity;
2. predicate parse validity;
3. predicate binding validity;
4. source omission and effective-nullability derivation; and
5. missing exact nullable-source guards.

An invalid key path cannot be concealed by a predicate error. A malformed or
unbound predicate cannot become `MissingNullableUniqueGuards`, and a failed
physical path resolution cannot be reported as nullable omission.

Generated-schema application maps it to one specific typed schema-application
reason. An earlier authoring-time diagnostic is allowed only when it delegates
to the same shared contract input and is never the runtime enforcement owner.
SQL DDL binding maps the violation to one specific `SqlDdlBindError` and the
existing `SchemaDdlAdmissionError` projection. Raw accepted-state ingress maps
well-formed semantic noncompliance to the existing incompatible
persisted-format boundary rather than pretending it is new author intent;
malformed predicate SQL or structurally invalid bytes remain corruption.

Patch 1 must name the exact accepted 0.230 error type, constructor, class, and
origin used for that incompatible-current-form boundary. The current raw codec
collapses failed semantic integrity through a Boolean corruption path, so
Patch 2 may not preserve that flattening for this case. If no existing typed
incompatible boundary can distinguish a well-formed current-format semantic
hard cut from malformed bytes, Patch 1 blocks authorization and records the
missing boundary for reconciliation within the existing error envelope; it
must not invent a second public envelope or silently reuse generic
`store_corruption`.

0.231 does not create a second public error envelope or implement the general
typed SQL diagnostic programme reserved for 0.232. Any public reason added here
is limited to this new semantic rejection. Code and tests do not match error
strings.

## No-Build And Alternatives Gate

No build would preserve physically coherent omission but retain a demonstrated
schema-safety ambiguity: accepted metadata can claim uniqueness without making
its incomplete membership apparent. Documentation alone is insufficient
because proposal publication would continue accepting the ambiguous contract.

Rejected alternatives:

- **Encode `NULL` as an index component.** This changes physical keys,
  uniqueness, ordering, prefix counts, rebuilds, stable bytes, and query
  semantics. No workload or storage evidence justifies that state-space
  expansion.
- **Add `NULLS DISTINCT` / `NULLS NOT DISTINCT`.** This introduces a public
  mode and a second uniqueness policy where one explicit partial-index
  contract is sufficient.
- **Inject guards automatically.** This silently changes authored membership,
  hides the important partial-uniqueness contract, and creates divergent
  generated/DDL behavior.
- **Accept any predicate that happens to reject null.** A general implication
  theorem expands semantic and test state far beyond the demonstrated need.
- **Warn but publish.** Accepted schema would remain ambiguous and warnings
  could be missed or unavailable during later recovery.
- **Store a new nullable-unique flag or guard list.** Accepted key nullability
  and the existing predicate already contain the complete decision inputs.
- **Move the rule into generated models or SQL DDL.** Either choice would leave
  another frontend and raw accepted-state ingress able to bypass runtime
  authority.

## Scope

0.231 includes:

- one accepted-schema-owned nullable unique-index validator;
- exact guard extraction from normalized accepted predicates;
- current-format accepted and candidate snapshot integrity;
- initial/generated proposal, reconciliation, migration, SQL DDL, unique
  activation, and field-nullability propagation;
- one exact typed rejection mapped through existing error families;
- narrow filtered-index implication for exact non-null guards;
- maintained SQL/schema documentation and focused generated/DDL/runtime tests;
  and
- acceptance, planner, performance, Candid, raw-Wasm, and complexity evidence.

## Non-Goals

0.231 excludes:

- encoded-null index keys;
- `NULLS DISTINCT`, `NULLS NOT DISTINCT`, or configurable null uniqueness;
- changing non-unique nullable index membership;
- changing primary-key nullability;
- treating omitted rows as index members for lookup or cardinality;
- automatic predicate synthesis, rewriting, or removal;
- general predicate implication, SAT solving, or arbitrary expression
  null-propagation proofs;
- new index formats, stores, generations, cursors, jobs, timers, or recovery
  phases;
- planner statistics, cost comparison, or observability beyond the existing
  filtered-index route;
- general public SQL diagnostic expansion reserved for 0.232;
- startup repair, generated-model reconstruction, compatibility aliases, or
  predecessor decoders; and
- unrelated schema DDL or relation work.

## Persisted And Public Hard Cuts

0.231 does not change accepted-schema, index-key, index-entry, constraint,
predicate, cursor, or 0.230 cardinality bytes. It adds a stricter validity rule
for the sole current accepted-schema form.

Before 1.0, a current installation carrying an implicit nullable unique index
must publish a compliant current schema before adopting 0.231 or be
reinstalled/recreated. On reopen, a noncompliant accepted or candidate snapshot
fails closed. There is no automatic predicate injection, compatibility reader,
upgrade bridge, repair shim, or generated-model fallback. No format version is
incremented; every genuine current format discriminator remains version 1.

Patch 1 must first prove inventory completeness. Maintained operator surfaces
must expose enough bounded identity to reconstruct, without display-label
guessing:

- active key items, including nested paths and expression source paths;
- active predicates;
- candidate key items and ownership;
- candidate activation identity and state; and
- the accepted field and nested-ancestor nullability needed to derive `N(I)`.

If `SHOW INDEXES`, `SHOW CONSTRAINTS`, and maintained schema inspection do not
provide that information, Patch 1 must require either a bounded offline
inspection procedure over the current codec or reinstall/recreation. It must
not infer nested or expression identity from rendered labels. Candidate
predicates that remain unobservable require conservative replacement, but
that replacement must still preserve enforcement as described below.

The required operator sequence is:

1. while still running the accepted pre-0.231 binary, inventory every active
   and pending unique index and classify its owner, exact key sources,
   ancestor-aware omission, predicate, activation state, and accepted
   constraint references;
2. choose and prove one uniqueness-preserving replacement route for each
   noncompliant active index:
   - **shadow replacement**, only if accepted 0.230 proves that the old and
     guarded physical indexes may coexist under distinct identities, the old
     index remains enforcing while the guarded candidate validates and
     promotes, and any accepted constraint/reference can be redirected
     atomically before the old index is retired; or
   - **quiesced replacement**, by blocking every mutation that can touch the
     indexed entity, dropping the old index, creating and fully promoting the
     guarded replacement, verifying the accepted contract, and only then
     re-enabling writes;
3. treat pending candidates with the same discipline. Do not abort a candidate
   whose new-write gate contributes enforcement and then leave writes enabled
   while recreating it. Use a proved shadow transition or quiesce affected
   writes through abort, recreation, validation, and promotion;
4. for generated-owned indexes, deploy an intermediate application on the
   accepted pre-0.231 runtime only after Patch 1 proves that reconciliation
   retains old enforcement until the guarded accepted replacement is
   authoritative. Otherwise use the quiesced route. Generated ownership does
   not excuse an intermediate enforcement gap;
5. when a source is still non-null, establish and promote its guarded
   replacement before dropping the not-null contract. Validate the final
   accepted-after schema revision rather than relying on the replacement's
   creation-time proof; and
6. verify that active and candidate inventories are compliant and that no old
   constraint/reference remains before installing the 0.231 binary.

Patch 1 must name the exact 0.230 coexistence, constraint-reference transfer,
write-quiescence, candidate-gate, generated-reconciliation, and promotion
authorities used by the chosen routes. If neither shadow nor quiesced
replacement is executable for SQL-owned, generated-owned, or pending
candidates, the hard cut has no safe operator path and implementation remains
blocked. 0.231 does not add an upgrade bridge merely to make the sequence
convenient.

A well-formed version-1 snapshot that violates only the new semantic contract
is an incompatible current-form installation, not evidence of malformed
bytes. Reopen maps it through the exact existing typed incompatible
persisted-format boundary named by Patch 1. Malformed bytes or predicate SQL,
invalid path metadata, checksum/codec failure, or other structural failures
remain corruption and retain distinct detailed causes. Retaining version 1 is
honest because this is the mandated pre-1.0 replacement of the sole current
semantic form, not support for two coexisting formats.

The public Rust/schema and compact SQL error surfaces may gain only the exact
semantic rejection required above. Candid changes are not assumed: Patch 2
must prove whether the existing error projection changes and report the result.
`SHOW INDEXES` retains its existing shape and displays the accepted predicate;
documentation supplies the clarified contract.

## Frozen Physical And Cardinality Semantics

0.231 is admission and planning work only. For every schema that remains
valid, before/after evidence must prove identical index-key bytes, index-entry
bytes, null-entry omission, unique collision probing for present entries,
non-unique nullable membership, accepted constraint identity, rebuild versus
incremental-write membership, and `SHOW INDEXES` shape. Duplicate key values on
rows outside the accepted filtered predicate remain outside uniqueness
enforcement.

0.230 entry and prefix cardinality continue to count only physically present
accepted entries. A row omitted because any key component is null contributes
neither an entry nor any prefix, even when earlier composite components are
non-null. No diagnostic or planner proof may reinterpret those counts as row
population.

## Non-Negotiable Invariants

1. Accepted schema is the sole runtime authority for nullable unique-index
   validity.
2. Every nullable key source in a unique index has one exact explicit non-null
   guard in the accepted predicate.
3. A null key component still omits the complete physical index entry.
4. Unique enforcement applies only to entries actually present in the accepted
   filtered index.
5. Non-unique nullable index behavior is unchanged.
6. Field-path and expression items derive effective omission from accepted
   path metadata plus the maintained physical resolver; generated models never
   reconstruct it at runtime and resolver failures never become nullable
   omission.
7. Expression null propagation and physical resolver outcomes are classified
   exhaustively without wildcard fallthrough.
8. Candidate and accepted indexes satisfy the same rule, and candidate proof
   is revalidated at promotion or protected by proved exhaustive 0.230
   invalidation.
9. All fallible validation occurs before durable marker, activation,
   allocation, or publication work.
10. Rejection leaves no candidate, constraint, physical, journal, or allocator
   residue.
11. Predicate structure, not rendered-string matching, proves required guards.
12. Planner eligibility remains conservative unless the query proves every
    accepted predicate conjunct.
13. 0.230 cardinality continues to count only physically present entries and
    prefixes.
14. No new persisted state, format version, compatibility path, configuration,
    or execution route is introduced.
15. Diagnostics are typed, ordered by the frozen precedence, and bounded; code
    and tests do not match strings.
16. Production executor code gains no panic, assertion, unwrap, or expect path.

## Complexity And Maintenance Gate

Demonstrated need: accepted schema can currently present partial nullable
uniqueness as if it were a complete natural identity.

Simplest outcome: reject only the ambiguous unique-index combination and reuse
the existing filtered predicate to state partial membership.

Canonical owner: accepted index integrity, consumed by every proposal and
publication frontend.

State-space delta:

- no new persisted or public behavior axis is added;
- the existing `unique × nullable key × predicate` space is narrowed;
- `unique + nullable source + missing exact guard` becomes unrepresentable;
- non-unique indexes and all existing physical membership states remain
  unchanged; and
- one owner-local ephemeral proof and typed rejection are derived, not stored.

Duplicated-flow delta: neutral-to-lower. Generated, SQL DDL, candidate,
nullability, and raw accepted-state paths converge on one validator. The
planner extends its existing implication owner rather than introducing a
parallel classifier.

Maintenance cost is proportionate only if implementation preserves the one
validator, one existing predicate representation, and one existing planner
route. A new persisted flag, general theorem engine, frontend-specific rule,
or compatibility path fails this gate and requires redesign.
