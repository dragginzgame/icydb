# IcyDB 0.247 Measured Wasm Footprint Reduction

Status: ACTIVE — PATCHES 1-3 COMPLETE, PATCH 4 NEXT

Last updated: 2026-08-28

Exact released predecessor: tag `v0.246.1`, revision

## Outcome

Reduce IcyDB's executable contribution to generated Wasm without adding a
feature profile, engine, compatibility route, configuration axis or runtime
authority. The realistic source-level objective is 30–80 KiB of release code
section reduction. Canic remains the only owner of final Binaryen
optimisation; IcyDB must improve the input and the final output of that
pipeline.

Toko Miner is the read-only proving application. Candidate measurements use a
disposable copy or supplied artifacts and never edit its repository, build
state or persisted state.

## Hard Scope And Authorities

0.247 is internal footprint work only. It adds no public API, Candid method,
SQL syntax, schema behavior, persisted format, query engine, configuration,
feature-profile variant or compatibility path. It does not add `wasm-opt` to
IcyDB.

The maintained authorities remain:

- accepted schema snapshots are runtime authority;
- generated models propose or reconcile schema but never reconstruct runtime
  authority;
- the existing planner and prepared query own bounds, ordering and execution
  eligibility;
- the existing executor owns row reads, retained ownership, logical work and
  typed errors;
- persisted schema and journal decoders remain bounded and fail closed; and
- Canic alone finalises IC release artifacts.

Drop-glue or generic-family work is admissible only when it simplifies an
existing ownership boundary. It is not authority for type erasure, boxing or
dynamic dispatch across unrelated hot paths.

## Candidate Measurement Contract

Every source-changing candidate records one exact predecessor and candidate
from the same source fixture, Rust toolchain, Canic version, feature set and
build profile. The record includes:

1. raw non-gzipped release bytes, code-section bytes and defined functions both
   before and after Canic's final optimiser;
2. named Twiggy family counts, total bytes and approximate bloat;
3. representative affected query instructions, results and physical work;
4. cold and populated startup/recovery instructions, callback counts, stable
   writes and cycle balance where the harness exposes it;
5. exact export names/kinds and public Candid metadata parity;
6. focused schema, canonical-order, query, persistence and upgrade tests; and
7. files changed, approximate line delta and state-space/complexity delta.

A query regression is material when it adds both more than 250,000
instructions and more than 3% to any frozen affected control. Such a candidate
is rejected unless its trade-off is explicitly measured, justified and
accepted before it is retained. Result bytes, typed-error identity, cursor
identity, logical work, physical visits and deterministic persisted bytes may
not regress. Final closeout requires the complete downstream gate; IcyDB's full
repository suite remains the user-owned validation workflow required by local
governance.

## Patch 1 — Baseline And Candidate Ledger

Patch 1 is measurement and documentation only. It freezes the supplied Toko
Miner release artifacts, verifies their code sections and Candid parity,
records the named monomorphisation families and inspects each requested owner.
It changes no Rust, fixture, public surface or artifact.

The source inspection establishes:

- `compact_sort_unstable_by` shares its public shell but still instantiates the
  complete `sift_down<T, F>` heap kernel for each retained type/comparator;
- retained full-row and slot-only scans select four semantic lanes before
  entering a generic closure shell, while their row-read and borrowed-primary
  instrumentation helpers instantiate again per reader;
- repeated stable sort bodies include canonical IcyDB keys, predicates,
  expressions and kernel-row payloads, and some `BTreeMap::from_iter` paths
  invoke stable bulk sorting despite an ordered semantic owner;
- the five named large functions are attribution roots containing or retaining
  ordinary success work as well as diagnostics and typed-error branches; their
  shallow named sizes alone do not prove that outlining reduces final code; and
- initial generated schema still reaches the general proposal-to-accepted
  lowering compiler, so an embedded canonical representation is feasible to
  measure but is not yet safe to ship.

## Patch 2 — One Compact Sort Kernel

Replace type/comparator-specific heap traversal with one non-generic internal
position or sort-key kernel. The generic boundary may project comparisons and
apply a permutation, but must not instantiate the heap algorithm for nearly
every element type. Avoid unsafe erased storage unless a safe index-based
experiment cannot meet the size and instruction gates.

Required proof:

- `sift_down` falls from 43 retained instances to one or disappears, and its
  approximate bloat falls by at least 75%;
- all current empty, duplicate, projected-key and bounded-length tests match
  the predecessor ordering contract;
- schema fingerprints, proposal lowering, migration planning, accepted
  snapshots and persisted bytes remain deterministic;
- any allocation or comparison increase is recorded against startup,
  recovery and representative query controls; and
- both pre- and post-Binaryen code sections shrink. A sub-4-KiB pre-Binaryen
  saving does not justify a more complex implementation.

The existing API remains private and unstable-order only. This patch does not
convert stable semantic sorts or claim interchangeable ties elsewhere.

## Patch 3 — One Retained Scan Kernel

Move retained full-row, slot-only, filtered and unfiltered execution behind one
concrete internal scan request and one non-generic read loop. Lane selection
must remain outside the per-row hot loop unless measurement proves that a
single concrete mode dispatch is cheaper. Row ownership remains borrowed where
the primary-map visitor already owns the row and owned everywhere else.

Required proof:

- retained scan instances converge from `4/6/3` toward `1/1/1`, with the exact
  residual explained;
- row bounds, scan budgets, ordering windows, continuation anchors, errors,
  physical visits and retained backing bytes remain identical;
- the three 2,048-row controls remain within the material-regression gate; and
- a final code-section reduction remains after Binaryen.

## Patch 4 — Canonical Sorting Owners

Audit repeated sorts of the same canonical types and call-site closures. Reuse
named comparators when that actually converges code, insert directly into
already ordered owners, and let semantic owners emit canonical order instead
of collect-then-sort where possible.

Stable sorting remains required whenever equal-key input order can affect
schema bytes, predicate evaluation, index traversal, cursors, query results or
persisted output. Unstable sorting is allowed only when the comparator is a
total order or ties are proven interchangeable by tests and owner invariants.
Each changed sort is measured separately so one improvement cannot hide a hot
path regression.

Patch 5 performs isolated A/B builds for recovery failures, diagnostics and

only if the complete release code section falls by at least 4 KiB before
Binaryen and does not grow afterward. Attribute motion from a caller into a
helper is not a saving. Hot success work, generic ownership and error identity
remain unchanged.

## Patch 6 — Canonical Pre-lowered Initial Schema

Measure a generated, canonical pre-lowered initial-schema representation whose
digest is bound to the authored canonical proposal. Runtime must verify the
digest and all accepted-schema invariants before publication, use the ordinary
accepted snapshot as authority afterward, and keep general-purpose lowering
for non-generated proposal and upgrade/reconciliation work.

This is build/no-build work. Continue only if a representative generated actor
stops retaining the general initial compiler and saves at least 32 KiB in the
final raw artifact with a net code-section reduction. Any current version-1
encoding is replaced in place; no predecessor decoder, fallback compiler,
alternate generated mode or public configuration is allowed. Fresh install,
same-Wasm upgrade, persisted-schema digest rejection and accepted-schema
verification must all pass.

## Patch 7 — Downstream Qualification And Closeout

Rebuild the frozen Toko Miner release subject from a disposable read-only
mirror against the final IcyDB candidate. Record cumulative pre- and
post-Binaryen raw/code/function deltas, final monomorphisation counts, query and
startup/recovery costs, Candid parity and the complete Toko Miner downstream
gate. Remove any candidate that does not retain a measured net saving or meet
its semantic/cost gates.

No patch may commit, tag, publish, push or deploy either repository.
