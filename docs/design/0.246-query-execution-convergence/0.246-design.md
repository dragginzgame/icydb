## Outcome

Reduce broad prepared-query cost and maintenance duplication without adding
another query-shape fast path, cache, authority or execution mode.

The line has one production opportunity: let the existing primary-map visitor
deliver borrowed rows through retained-slot scans without a second tree lookup,
then order large retained payloads by compact positions instead of repeatedly
moving complete `KernelRow` values.

Patch 1 produced the required clean complete P1, scale and P2 baseline. Only
the bounded Patch 2 attempt is now authorized.

## Demonstrated Need

Patch 1's exact clean released-source evidence records these 2,048-row costs:

| Prepared family | Instructions | Physical observation |
| --- | ---: | --- |
| Aggregate `DISTINCT` plus `FILTER` | 109,234,618 | 2,048 rows ingested and 2,048 row gets |
| Nullable expression `DISTINCT` control | 118,738,995 | 2,048 candidates and 2,048 row gets |
| Expression-order `DISTINCT` control | 109,375,905 | 2,048 candidates and 2,048 row gets |

By contrast, exact synchronized-metadata aggregates complete below 1.4M
instructions. That comparison establishes a large ceiling but does not treat
all row work as removable. The clean aggregate attribution assigns 71,852,668
instructions to the store phase and 13,127,318 to required reducer work. The
candidate may remove per-key lookup and complete source-row retention; it must
still visit and decode every required value and must measure the actual saving.

## Hard Scope

0.246 is internal cleanup and optimization only. It adds no SQL syntax, public
API, Candid or export, schema behavior, stable format, generated surface,
persisted state, configurable mode or compatibility path.

The maintained authorities remain:

- accepted schema snapshots select runtime schema;
- the planner selects one prepared access and execution contract;
- the existing request pins that contract and authority for its execution;
- the executor owns physical access, residual retry, corruption and
  physical-work semantics;
- the prepared contract fixes ordering and window requirements once;
- aggregate reducers own aggregate projection, folding, `NULL` and filter
  semantics; and
- scalar `DISTINCT` consumers own projection tuple identity, canonical
  equality, projection-order application, pagination and output-budget
  semantics under that prepared contract.

No candidate may add a process-, database-, schema- or publication-lifetime
query artifact. No candidate may reconstruct planner eligibility at runtime.
Unsupported or unproven cases continue through the existing canonical prepared
flow.

## Patch 2 — Borrowed Row Delivery And Compact Ordering

Patch 1 identified repeated primary-row lookup and large-payload ordering before
aggregate and scalar `DISTINCT` consumers. Implementation evidence narrowed the
acceptable seam: carrying evaluated order tuples on each retained row added
per-row state and made the measured path materially slower, while the existing
borrowed primary-row visitor and canonical ordering helper already owned all
required semantics.

Patch 2 therefore extends those two existing owners rather than creating a
consumer cache or another execution route. Aggregate folding and scalar
`DISTINCT` admission remain separate consumers.

Conceptually:

```text
existing prepared key/row execution
  -> eligible primary-map visitor supplies the already-open raw row
  -> canonical retained-slot decode and residual predicate
  -> aggregate or scalar DISTINCT consumer remains unchanged

expression-backed ordering
  -> cache canonical order values once
  -> sort compact source positions
  -> move each retained row into final order once
```

Direct visitation is admitted only by the existing primary-map leaf and only
for unpaged retained-slot scans or the pre-existing bounded-order window. A
`DISTINCT` stream adapter may forward that capability only while the same leaf
still owns monotonic unique physical keys. Every other stream, paginated scan,
residual-retry shape and unsupported payload stays on the predecessor path.

Ordering continues to use the planner-resolved order and the existing cached
order-value comparator. Only the sorted payload changes: compact source
positions are sorted and the fallible reorder pass moves selected rows once.
No projected value, order tuple or eligibility result is cached on a row.

### Required semantic proofs

- `NULL`, numeric coercion and expression-error behavior are byte-for-byte or
  typed-error identical to the predecessor;
- multi-expression `DISTINCT` retains complete tuple identity;
- authored ordering, stable tie behavior, offset, limit and cursor semantics
  are unchanged;
- logical work, retained-state and nested-value budgets are charged at the same
  semantic boundaries, with no partial charge surviving fallback;
- corruption, missing-row, invalid-slot, borrow-conflict and residual-retry
  behavior remains fail-closed and equivalent;
- borrowed and lookup-backed consumers return identical result bytes and
  logical-work counters; reviewed physical changes must be limited to replacing
  per-key gets or source-row retention, with no added row or index visits; and
- exact routes and every unsupported prepared shape remain unchanged.

### Frozen performance and complexity gates

- prepared aggregate and scalar projection `DISTINCT` controls each save at
  least 25,000,000 instructions and 25% at 2,048 rows under repeated clean
  current-source measurement;
- the complete P2 profile confirms every selected affected matrix row and
  preserves all result and cursor signatures;
- no confirmed matrix row regresses by both more than 250,000 instructions and
  more than 3%;
- no result, error, logical row/index work or stable extent changes, and no
  physical row/index visits increase;
- final raw production SQL Wasm grows by at most 4,096 bytes against the exact
  predecessor subject; gzip is secondary context;
- at most one new private contract type, no new module, cache, mutable owner or
  behavior axis; and
- maintained production Rust grows by at most 120 net lines, with deleted
  intermediate-materialization code reported separately.

Missing either consumer-family gate closes Patch 2 as no-build. A large saving
for only aggregates, only scalar `DISTINCT`, one field type or one SQL spelling
does not qualify.

## Closeout

0.246 succeeds only if retained production work is broad, attributable and
proportionate. Closeout must run the complete frozen matrix against the exact
candidate, compare final raw Wasm with the same toolchain/profile/features,
report complexity and state-space deltas, and prove unchanged Candid, exports,
stable formats and public behavior.

The valid line verdicts are:

- `BUILD GATES PASSED` for each retained patch;
- `MEASURED NO-BUILD` for an individually rejected patch; or
- `CLOSED — NO RETAINED PRODUCTION CHANGE` if all candidates fail.
