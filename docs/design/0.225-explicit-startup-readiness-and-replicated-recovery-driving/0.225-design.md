## Decision Summary

0.225 introduces exactly one successful startup state type and one typed
terminal failure result:

```rust
pub enum DatabaseStartupState {
    Ready,
    Recovering,
}

pub enum StartupFailureKind {
    DatabaseControl,
    JournalRecovery,
    SchemaReconciliation,
}

pub struct StartupFailure {
    kind: StartupFailureKind,
    diagnostic: Diagnostic,
}

pub fn startup_state() -> Result<DatabaseStartupState, StartupFailure>;
```

`StartupFailure` is a bounded typed error, not a third successful state. It
classifies database-control, journal-recovery, and generated-schema
reconciliation failure without retaining unbounded strings; public accessors
return its kind and compact diagnostic. The generated
root-level `startup_state()` function is the exact ungated application control
surface. It performs memory bootstrap and pure bounded observation directly
over the generated database domain; it does not call `db!()`, require a request
root, construct an ordinary session, schedule work, or export a Candid method.

Ordinary `db!()` construction and ordinary query, mutation, schema, integrity,
and diagnostic entrypoints observe the state. Apart from the existing explicit
migration-control exception defined below, they do not execute startup work.
While the state is `Recovering`, ordinary database work returns one
dedicated retryable recovery-pending error that is distinct from corruption,
schema conflict, optimistic mutation conflict, and generic storage failure.
`db!()` remains fallible with its existing `Result<DbSession<_>, icydb::Error>`
shape and performs this admission before returning the session; the hard cut is
behavioral, not a new macro signature. There is no fallback that waits until
the first database operation to reject the session. `Recovering` maps to the
dedicated retryable pending error; `Err(StartupFailure)` maps to its terminal
startup diagnostic rather than being rewritten as pending or generic conflict.

Only a dedicated replicated update driver advances recovery. Generated
startup wiring registers a dedicated recurring watchdog independently of
application callbacks. The driver is single-flight, re-entry safe, and trap
aware. Durable recovery controls are authority; volatile registration and
active flags are optimizations only. The watchdog's next invocation is queued
by the timer library before the current callback self-call executes, so a trap
or instruction exhaustion in that callback cannot consume the only future
wake-up. Patch 1 verified this statement against the pinned CDK and IC
execution model before promoting the design.

Generated schema application remains gated behind complete recovery. The
application contract is explicit: inspect readiness, restore application
timers or caches only at `Ready`, retry bounded readiness observation while
`Recovering`, inspect the existing migration status when reconciliation reports
that explicit migration control is required, and stop blind retries on typed
failure. IcyDB does not persist application callbacks or own application
scheduler policy.

This line deliberately uses the predecessor's current recovery cursor and page
engine. It does not add Validate/Apply, continuous online folding, backlog
admission, tail aggregate metadata, or durable cardinality.

## User Outcome

- A readiness check is bounded control work and does not decode a journal batch.
- A query never spends instructions on recovery mutations that the query call
  cannot commit.
- An ordinary `db!()` call cannot incidentally advance a recovery page.
- Recovery callbacks and application callbacks have separate instruction
  envelopes.
- Applications can restore schedulers without a guessed delay or matching a
  generic conflict.
- A trapped driver remains retryable and cannot create false `Ready` state.
- Empty and populated installs/upgrades preserve resulting accepted-schema and
  atomicity semantics. Fresh-install readiness timing intentionally changes:
  generated schema application moves to the first watchdog invocation instead
  of completing through incidental `db!()` startup work.

## Canonical Ownership

Ownership is singular:

1. accepted schema snapshots remain runtime semantic authority;
2. the commit marker, journal, current fold cursor, canonical stores, and fold
   watermark remain recovery authority;
3. the startup coordinator derives `Ready` or `Recovering` from bounded current
   recovery controls plus generated-schema reconciliation state and owns the
   sole durable terminal-failure receipt;
4. the replicated recovery driver owns page invocation and failure
   publication;
5. generated canister wiring owns recurring-watchdog lifecycle registration
   only; and
6. applications own authorization, readiness exposure, callbacks, timers, and
   scheduler restoration.

The startup coordinator does not decode records or apply them. The generated
driver does not implement journal semantics. Ordinary sessions do not acquire
an alternate recovery route.

`Ready` requires all current recovery controls to prove completion and the
generated schema fragment to be reconciled. `Recovering` means startup is
incomplete: either the dedicated driver can advance it, or an
already-authoritative migration-control operation is required. It never means
ordinary operations may opportunistically help.

## Startup State Priority And Ungated Control Surface

The coordinator applies this complete priority order. A lower row is considered
only when every higher row is absent.

| Current authoritative evidence | Result |
| --- | --- |
| One current deterministic startup failure, derived directly from bounded control evidence or retained in a matching durable failure receipt | `Err(StartupFailure)` |
| A commit marker, fold cursor, startup-actionable journal tail, incomplete recovery epoch, or generated-schema reconciliation remains | `Ok(DatabaseStartupState::Recovering)` |
| Recovery is complete and the generated schema identity is reconciled | `Ok(DatabaseStartupState::Ready)` |

Observation reads one fixed, deployment-bounded set of controls: the failure
receipt, database control frame and marker-presence field, recovery-domain
witness, fold watermark/cursor controls for the statically generated journaled
stores, and generated-schema reconciliation receipt/state. It performs no row,
index, journal-record, or retained-history scan and decodes no journal record
envelope. A malformed bounded control may therefore return `StartupFailure`
directly; corruption discovered only while decoding a recovery page is surfaced
through the durable receipt below.

Generated reconciliation is bound to the database incarnation and the exact
generated submission key, which is derived from the complete generated
fragment and migration plan. A terminal `NoOp` or `Applied` receipt for that
submission remains reconciled when a later accepted, catalog-native SQL DDL
operation advances the accepted head. This is required because exact submission
replay returns the original immutable receipt, while maintained DDL deliberately
preserves generated-owned identities and semantics and may add or modify
DDL-owned state. A missing or different submission, or a `Pending` or `Aborted`
outcome, remains unreconciled. Failure receipts remain bound to the accepted
head at which the failure was observed so a later authoritative change can make
the failure stale.

For 0.225, a retained tail is startup-actionable exactly when the current Wasm
instance lacks a completed recovery-domain witness or when a marker/fold cursor
already proves interrupted recovery. A nonempty tail appended by a successful
commit after that witness was established is not actionable in the current
epoch because its live projections were synchronously applied; tail nonemptiness
alone cannot flip `Ready` to `Recovering`. Patch 1 proved this rule against
every 0.224 commit path and retained the normally returned-error scheduling
correction below.

While the result is not `Ready`, the complete executable allowlist is:

1. generated root-level `startup_state()` observation, including its bounded
   `StartupFailure` payload;
2. the hidden replicated startup driver and its watchdog callback; and
3. existing authorized generated schema-migration control operations, only
   after journal recovery is complete and only when the maintained migration
   authority reports that reconciliation needs that explicit resumable lane.

There is no separate startup-diagnostics endpoint in 0.225. Applications may
expose the bounded `StartupFailure` returned by `startup_state()` through their
own authorized surface. Ordinary database diagnostics remain gated with
queries, mutations, catalog operations, and integrity work.

## Durable Startup Failure Authority

0.225 adds one fixed-size current-format `StartupFailureReceipt` in one
startup-coordinator-owned stable allocation per generated database domain. It
is not a journal cursor, recovery checkpoint, compatibility record, or source
of recovery semantics. Its only purpose is to preserve a deterministic failure
first discovered by the timer driver so later bounded observations cannot
misreport `Recovering` forever.

The receipt contains:

- one bounded `StartupFailureKind` for database control/format, journal or
  existing fold-cursor recovery, or generated-schema reconciliation;
- the existing compact diagnostic identity and bounded numeric facts, never an
  error string or copied record envelope; and
- exactly one binding assembled from maintained identities:
  `database_control_proof_identity` for readable database control,
  `DatabaseIncarnationId`, the affected `StoreAllocationIdentity` plus
  `JournalTailProofIdentity`, the existing `FoldRecordCursor` fields when one
  exists, or the generated submission key and accepted schema head/fingerprint
  for reconciliation. If corruption prevents reading database-control
  identity, the receipt is terminally bound to that commit allocation until a
  fresh database incarnation is initialized.

No receipt field introduces the digest/sequence/count/phase/ordinal cursor
owned by 0.228. Existing sequence, batch ID, count, and ordinal fields may
appear only when they already exist in `FoldRecordCursor` or maintained proof
identity.

Publication, replacement, and clearing rules are exact:

1. A deterministic failure already re-derived by bounded observation remains
   owned by its existing persisted bytes and needs no duplicate receipt. The
   driver records a receipt only when a returned persisted-corruption,
   current-format-incompatibility, or deterministic generated-schema error
   cannot be re-derived by that observation.
2. Immediately before publication, the coordinator re-captures the current
   binding so any durable progress made earlier in the callback is included.
   The receipt write and successful callback outcome commit together.
3. A trap, panic, instruction exhaustion, transient timer/self-call failure,
   insufficient cycles, or other retryable execution failure never creates or
   replaces a receipt.
4. Re-publishing the same failure for the same binding is idempotent. A
   deterministic failure at a different current binding replaces the old
   receipt; two receipts never coexist.
5. A matching receipt has priority over all pending evidence and suppresses
   blind driver retries. Ordinary work cannot clear it.
6. A receipt is cleared only when a supported authoritative transition makes
   its binding stale—a fresh database incarnation or changed generated-schema
   identity—or when recovery and schema reconciliation for the new current
   binding complete successfully. A schema/code change alone cannot clear a
   database-control or journal-corruption receipt whose durable binding still
   matches.
7. The all-zero uninitialized allocation is the canonical absent receipt for
   upgraded and fresh stores; it is not a legacy format or fallback decoder.
   Any other malformed receipt is fail-closed startup-control corruption. There
   is one current format, with no decoder alias, translation, or fallback
   inference.

The existing recovery engine must retain the exact durable owner alongside
every returned page failure: database format, commit marker, live-schema
checkpoint, and database-control effects are `DatabaseControl`; journal
publication, projection reset, cursor, watermark, batch, and record failures
name the exact affected journal store. The coordinator classifies and binds
that owner directly. It must not infer ownership from store presence, select a
first active journal, or require a journal allocation before recording a
database-control failure. This is error provenance only, not a second recovery
route or persisted format.

The allocation is the generated canister's required `startup_memory_id`, with
stable key `icydb.<memory_namespace>.startup.control.v1`. It is a distinct
compile-time stable-memory identity, not a caller-selected runtime policy. The
one current receipt envelope is at most 2,048 encoded bytes; its first write may
grow that virtual memory by one 65,536-byte Wasm page. The maximum includes the
fixed header/checksum, one closed failure kind, one compact diagnostic identity,
at most `MAX_PUBLIC_DIAGNOSTIC_FACTS` (80) `(u8, u64)` numeric facts, and one
closed binding whose only variable input is an already-bounded canonical stable
key (128 bytes) or schema submission key (128 bytes). Patch 1 confirmed the
predecessor has no equivalent persisted failure authority.

## Superseded Direct-Provider Watchdog Protocol

This section records the protocol against which the original 0.225 line was
accepted. It is retained as review history only. The hard-cut
`ic-timers 0.3.1` protocol in the next section supersedes its direct provider,
`TimerId`, serial-interval, cadence-guard, and deferred-clear authority in full.
None of those old implementation details remains an allowed fallback.

The timer protocol uses three volatile facts with deliberately weak meaning:

- `watchdog_timer: Option<TimerId>` contains the exact current registration.
  `Some(id)` deduplicates registration and allows terminal `clear_timer(id)`;
  it is never readiness or progress authority; and
- `driver_active` means one callback message has entered the synchronous
  driver. It rejects re-entry within that message. Because the flag is set and
  cleared inside the driver message, a trap rolls it back to inactive; and
- `driver_cadence_time: Option<u64>` records the IC time of the most recent
  normally completed driver attempt. A callback at the same IC time is a
  bounded no-op. The value is set before the synchronous driver runs, so a trap
  or instruction exhaustion rolls it back and leaves another same-time or
  later callback eligible. It is reset on upgrade and is neither progress nor
  readiness authority.

The watchdog uses
`set_timer_interval_serial(Duration::from_secs(1), ...)`, not
`set_timer_interval`. The exact interval is one second and is engine-owned,
not caller-selectable. Serial execution admits at most one active driver
future; a tick that arrives while it is active is skipped and rescheduled by
the timer library instead of starting an overlapping invocation. The driver
performs no `await`, so overlap is defensive rather than part of normal
progress. One logical recurring task owns one next deadline. The pinned global
dispatcher may dispatch overdue ticks before the first executor self-call has
marked the serial task busy, but it caps all outstanding timer self-calls at
250 canister-wide and then defers the remaining deadline. Patch 1 measured the
full cap after a 300-second jump with simultaneous watchdog/application timers:
125 callbacks for each logical timer were delivered at one IC timestamp. That
burst is excessive for a recovery page that may consume 20 billion
instructions. Therefore `driver_cadence_time` is mandatory: at most one
normally completing recovery attempt runs at one observed IC time, and every
remaining same-time watchdog callback performs only the fixed cadence,
active-state, receipt, and readiness checks. The shared callback queue remains
bounded by the pinned 250-call cap, and delayed or duplicate callbacks remain
idempotent.

The maximum IcyDB-added delay between an eligible completed callback and the
next requested callback is one second. The maximum end-to-end wall-clock
recovery latency is explicitly unbounded by the protocol: the IC gives timers
best-effort minimum delays, not a delivery SLA, and subnet/input-queue delay or
periods without enough liquid cycles have no finite maximum. The operational
contract is therefore: one recovery page per successfully delivered serial
tick, with a one-second requested cadence and no guaranteed wall-clock
completion time. Patch 1 measures initial fresh-install delay and first,
representative, catch-up, and terminal inter-page delays rather than claiming
a platform maximum that the IC does not provide.

`init` and `post_upgrade` register the watchdog once only for
`Ok(Recovering)`; neither `Ready` nor a typed terminal failure registers
recovery work. Upgrades discard heap timers and the old `TimerId`, so
`post_upgrade` resets `watchdog_timer`, `driver_active`, and
`driver_cadence_time` before reconstructing registration from durable
observation. Recovery and application tasks may share the CDK's
platform global timer, but they use distinct logical timer registrations and
distinct self-call callback messages; no application callback executes in the
recovery callback's instruction envelope.

For the pinned `ic-cdk-timers` 1.0.0 implementation, the global-timer message
reschedules a recurring task before dispatching its callback self-call. The
already-surviving wake-up after a callback trap or instruction exhaustion is
therefore the next recurring timer invocation, whose scheduling state was
committed by the parent global-timer message. The design depends only on that
verified property and the IC rule that the callback's uncommitted heap/stable
changes roll back. Patch 1 captured executable real-canister evidence and the
exact pinned-source/IC references in `0.225-status.md`; a future timer-library
change reopens the promotion gate.

Every invocation re-derives authority from durable controls. A duplicate or
delayed callback sees `driver_active`, the same `driver_cadence_time`, a
matching failure receipt, completed state, or the next durable recovery
position and is harmless. On `Ready` or any typed terminal failure, a
successful callback takes the stored `TimerId` and leaves `watchdog_timer =
None`. The pinned serial executor restores its busy task from a completion
guard after the callback future returns, so calling `clear_timer(id)` inside
that same future would remove the guard's slot and make normal completion trap.
The callback therefore schedules one zero-delay, engine-owned cleanup message
that calls `clear_timer(id)` only after serial completion. Already-dispatched
duplicates observe the retired logical registration and are bounded no-ops.
This cleanup never drives recovery, invokes application work, or becomes
readiness authority. On upgrade, the old timer and ID are assumed lost and
registration is reconstructed. Autonomous retry is guaranteed only while the
canister is running with enough cycles for timer self-calls; insufficient
cycles is an operational inability to execute any driver and must never be
misclassified as corruption.

The callback uses the timer library's self-call executor, which authenticates
`msg_caller() == id()` before invoking the stored future. The IcyDB driver is a
private Rust function captured by that future, not a generated Candid or IC-CDK
endpoint. If implementation requires any separately exported driver wrapper,
that wrapper must enforce the same self-caller check before observing or
advancing recovery. Patch 3 owns a real-canister security test that invokes the
timer executor and every generated driver-like method from external ingress,
expects rejection, and proves marker/cursor/watermark/failure-receipt state did
not change.

Patch 1 proved that the pinned recurring task survives its callback's
trap/instruction exhaustion exactly as described. A timer-library change must
reopen that proof and replace the mechanism or narrow the autonomous retry
contract if it no longer holds. A one-shot timer plus a `scheduled = true`
heap flag is explicitly rejected.

### Superseded Timer Provider And Canic Integration Boundary

The accepted 0.225 watchdog is registered directly through pinned
`ic-cdk-timers 1.0.0`; it is not registered through Canic's application timer
facade. This is a deliberate semantic boundary, not an interchangeable import
choice. IcyDB has no Canic manifest dependency, and generated database recovery
must remain usable by both plain IC-CDK canisters and applications that use a
different endpoint framework.

A replacement timer provider is eligible only if maintained source and real-
canister evidence prove all of the following as one contract:

1. the next watchdog wake-up is committed at an earlier replicated call
   boundary before the current recovery callback begins, so a callback trap or
   instruction exhaustion cannot strand pending durable recovery;
2. one logical registration is serial and non-overlapping, with duplicate and
   late callbacks harmless and overdue work bounded or coalesced;
3. registration is idempotent, its handle has one owner, and terminal
   cancellation is safe when requested by the running callback rather than
   invalidating a completion guard;
4. init and post-upgrade reconstruct volatile registration from IcyDB's durable
   readiness authority before ordinary database admission or application
   restoration;
5. the callback runs in a distinct replicated update message, is not charged to
   an application callback, and any executor ingress authenticates self-caller;
6. insufficient cycles, delivery delay, timer loss on upgrade, traps, and
   instruction exhaustion remain retryable operational conditions rather than
   typed database corruption; and
7. the provider exposes no caller-selected cadence, second executor, persisted
   timer policy, query-side driving path, or automatic public endpoint.

Canic 0.101.53 does not yet satisfy this substitution gate. Its maintained
public `timer_interval!` / `TimerApi::set_interval` contract intentionally arms
one one-shot timer after the preceding future completes. That gives application
tasks non-overlap and prevents missed-interval catch-up, but a trapping or
instruction-exhausted callback cannot reach the rearm step. Its public opaque
`TimerHandle` also represents an application timer; Canic's built-in timer keys
and workflow registration are private. Therefore using the current facade for
the IcyDB watchdog would remove the already-proved surviving-next-wake-up
invariant.

Lifecycle ownership is a second integration gate. Both `canic::start!` and
`icydb::start!` currently own the canister `init` and `post_upgrade` exports,
while Canic defers its optional user block through a zero-delay application
timer. Nesting IcyDB registration in that deferred block would not provide an
atomic engine-first lifecycle boundary: a later trap in the same deferred
message could roll back IcyDB's registration, and two start macros cannot be
emitted together. A future Canic integration must instead provide a synchronous
post-runtime-restore framework-participant hook on both lifecycle paths, before
deferred user work, or another single-owner composition mechanism with the same
ordering.

Canic adoption is consequently a reviewed provider transition, not a 0.225
cleanup. It requires a public framework/system watchdog surface with pre-armed
trap-safe recurrence and lifecycle composition, followed by the complete timer
source, PocketIC trap/exhaustion, upgrade, method-mode, raw-Wasm, and populated
recovery gates. Until then the direct pinned timer dependency remains the one
canonical watchdog owner; an optional Canic timer mode or dual registration is
forbidden.

## Current `ic-timers` 0.3.1 Watchdog Protocol

IcyDB depends directly and exactly on `ic-timers 0.3.1`. It has no direct
`ic-cdk-timers` dependency, call, handle, or re-export. `ic-cdk-timers` remains
only the private transitive platform provider used by `ic-timers`; that is not
a second IcyDB authority or compatibility path.

The generated canister owns one volatile
`Option<ic_timers::WatchdogRegistration>` under the fixed logical identity
`("icydb", "startup", "recovery")`. Durable readiness, recovery controls, and
the startup-failure receipt remain the only demand authority. The registration
claim, shared bounded registry, provider handles, callback generations,
single-flight state, counters, and terminal cancellation are owned by
`ic-timers`.

`init` and `post_upgrade` synchronously call the idempotent
`ic_timers::initialize_runtime()` before application hooks, derive desired
state from IcyDB's durable startup observer, and call `reconcile_watchdog` with
a one-second `TimerCadence`, `DeclarationLifetime::Retained`, and either
`Scheduled` or no registration. A fresh Wasm heap reconstructs the claim; a
duplicate lifecycle invocation reuses the exact claim and cannot register a
second watchdog. Initialization, identity construction, claim borrowing, or
reconciliation failure traps the lifecycle message. It cannot commit startup
work without a wake-up.

The watchdog scheduler runs in one replicated message, atomically pre-arms the
next one-second successor, and dispatches the synchronous IcyDB work in a
separate message. A work-message trap or instruction exhaustion therefore
rolls back that attempt while leaving the earlier successor committed. The
shared runtime admits one work attempt per logical identity; it coalesces
duplicate ensure requests and does not replay one callback for every missed
interval. IcyDB no longer owns a re-entry flag, same-timestamp cadence guard,
raw `TimerId`, or zero-delay cleanup callback.

Every returned callback classifies its result explicitly:

- `Ready` returns `no_work + Stop`;
- a durable terminal `StartupFailure` returns `invariant_failure + Stop`;
- one recovering page that reaches terminal state returns `success + Stop`;
- one recovering page that remains pending returns `success + Continue`; and
- a retryable page error returns `retryable_failure + Continue` after logging
  only its stable IcyDB diagnostic code.

`Stop` safely clears the pre-armed successor through the runtime's watchdog
completion transition while retaining the logical declaration for a later
atomic ensure. `timer_snapshot(identity).next_deadline_ns()` is the bounded
observation used by tests and application lifecycle evidence; retained claim
presence alone does not mean a wake-up exists.

The post-`Ready` commit guard invokes the generated synchronous ensure seam
when a normally returned error retains actionable recovery work. Any runtime
initialization or ensure failure traps, rolling back that execution rather
than committing a marker without a future wake-up. There is no query-side
scheduling, alternative provider, persisted timer policy, caller-selected
cadence, automatic public driver endpoint, or fallback to the former direct
provider.

IcyDB and Canic may share the one resolved `ic-timers 0.3.1` registry in a
final canister, but IcyDB remains framework-independent and owns its lifecycle
participant ordering. Canic is neither a dependency nor release authority for
this protocol. Any future timer-provider substitution must independently
re-prove the complete pre-arm, trap/exhaustion, coalescing, terminal-stop,
upgrade-reconstruction, atomic-ensure, executor-authentication, and bounded
registry gates.

## Post-Ready Execution Liveness And Schema Handoff

0.229 owns normal post-commit convergence scheduling. Patch 1 proved the
promotion invariant that lets 0.225 remain independent:

> No normally committed post-`Ready` execution—successful or failed—may leave
> a marker, fold cursor, startup-actionable tail, or incomplete recovery epoch
> without atomically ensuring that a watchdog wake-up exists.

This includes three exhaustive exit classes for every maintained mutation,
schema-publication, migration-control, and generated update path:

| Exit class | Required final state |
| --- | --- |
| Trap or instruction exhaustion before a normal return | The current message's uncommitted database and watchdog changes roll back together. Any recovery control committed at an earlier IC call boundary must already have atomically registered the watchdog before that boundary; maintained IcyDB database paths currently make no such outgoing call while opening a commit window. |
| Returned success | No marker, fold cursor, startup-actionable tail, or incomplete recovery epoch remains unless the fixed watchdog identity has a live next deadline. |
| Returned error | Either no startup-actionable recovery control remains, or `ic-timers` reconciliation has completed and the error returns with a live next deadline in the same normally committed message. |

Patch 1 inventoried all awaits/outgoing calls and normal return sites in the
covered paths. Introducing a call boundary inside a commit window reopens this
gate because later trapping execution may roll back only to that boundary.

The 0.224 candidate behavior is that a successful durable mutation appends a
marker-bound tail batch, synchronously applies live row/index/schema effects,
and clears the marker. Such a retained tail is historical durability input for
the next startup epoch, not automatically a startup-actionable tail in the
already-recovered current epoch. On upgrade the volatile recovered witness is
absent, the same tail becomes startup-actionable, and generated
`post_upgrade` registration drives it. Patch 1 proved that distinction for
every successful mutation and schema-publication commit path. It also
classified every returned-error path because the maintained commit guard may
intentionally preserve a marker after a normal error. No normally returned
execution may transition the current epoch back to `Recovering` after the
watchdog stopped unless that same message synchronously ensures its retained
`ic-timers` declaration is scheduled.

The minimal exceptional transition-to-pending registration required by a
normally returned error belongs to 0.225 because it preserves recovery
liveness; it does not authorize successful post-commit folding or continuous
online convergence. If successful normal execution also leaves current-epoch
actionable work, this design cannot promote unchanged: either the smallest
successful transition registration moves into 0.225, or 0.229 must precede
activation of the 0.225 gate. The issue may not be deferred to implementation
or hidden as a query-side recovery fallback.

The terminal generated-schema phases are:

1. Fresh installation with no marker, cursor, or tail begins `Recovering`
   because no generated-schema reconciliation receipt exists. The watchdog
   performs the existing bounded synchronous fragment application on its first
   delivered watchdog attempt and then publishes `Ready`. This intentionally changes
   readiness timing, not the resulting schema or atomicity semantics; Patch 1
   freezes the initial delay.
2. After the final recovery page, the same driver synchronously invokes the
   existing generated-schema reconciliation boundary. A successful idempotent
   application completes the terminal handoff in that callback. If the exact
   application instead returns a durable `Pending` row-local validation job,
   later watchdog invocations select that exact job from the generated
   submission receipt and advance at most one page through the canonical
   schema-application continuation executor. Clean `Started`, `Advanced`, and
   `Restarted` results remain `Recovering`; only `Applied` publishes `Ready`.
   A retained generated check or targeted-rule finding publishes its canonical
   typed E223 startup failure, while an exact `Aborted` outcome publishes the
   existing typed schema-application conflict. The driver never acknowledges
   or discards a finding page and never creates another cursor or executor.
3. If maintained schema-migration authority reports an exact prepared or
   running resumable migration, 0.225 does not duplicate or automatically
   execute it. State remains `Recovering`; the existing authorized migration
   control lane advances it, while the watchdog performs only bounded
   observation until reconciliation can complete.
4. A retryable execution failure leaves state pending for the next watchdog
   invocation. A returned deterministic reconciliation rejection publishes
   the bound startup failure receipt. A trap or instruction exhaustion
   publishes neither failure nor readiness.

Schema reconciliation is therefore synchronous and fallible when direct
application completes within one call, watchdog-resumable through the existing
canonical schema-application executor when it returns `Pending`, delegates
already-resumable migration work to its existing authority, and is never
scheduled through an application timer.

## No-Build And Alternatives Gate

- Raising an IC instruction limit does not remove history-sized work from
  queries or timer collisions.
- Keeping `db!()` as a recovery driver makes cost depend on whichever endpoint
  happens to run first and preserves rollback-prone query work.
- Returning generic conflict leaves application retry policy coupled to an
  unrelated broad error class.
- A fixed application grace period cannot prove database readiness.
- A user-selectable startup mode or recovery batch size adds policy states
  without a demonstrated deployment-specific semantic need.
- Restoring whole-store rebuild duplicates canonical recovery authority and is
  outside this line.

Patch 1 confirmed that the accepted predecessor does not provide equivalent
explicit state, a dedicated error, or independently driven replicated recovery.

## Scope

0.225 includes:

- `DatabaseStartupState::{Ready, Recovering}` on the trusted Rust surface;
- generated ungated `startup_state() -> Result<DatabaseStartupState,
  StartupFailure>` observation;
- one dedicated retryable recovery-pending error identity;
- one bounded durable startup-failure receipt when no existing authority can
  preserve timer-discovered deterministic failure;
- removal of recovery-page execution from ordinary queries, mutations, and
  `db!()` construction;
- one dedicated replicated recovery driver over the current recovery engine;
- generated lifecycle wiring for recurring-watchdog registration and terminal
  schema application;
- atomic transition-to-pending watchdog registration before any normally
  returned error can leave actionable recovery controls;
- single-flight scheduling, re-entry rejection, timer separation, and trap
  recovery;
- the application readiness contract and focused operational guidance; and
- owner-local plus real-canister evidence for empty and populated startup.

## 0.225.2 Physical DDL Recovery Correction

Accepted SQL DDL that changes a journaled store's physical user-index domain
must persist that exact staged deletion and insertion set under the same marker
and journal batch as the accepted-schema publication. The schema record remains
first. Domain records are ordered by entity, deletion before insertion, and
carry the accepted-after entity fingerprint. Each record contains at most 64
strictly ordered keys, so the existing record cursor remains the only recovery
continuation and instruction checks remain effective between chunks.

The existing journal-record-count, journal-byte, and 16-MiB marker ceilings
apply before any target mutation. A staged DDL transition that cannot fit those
durable limits fails precommit; it may not publish schema metadata while
leaving its physical domain volatile. Recovery folds the recorded chunks into
the canonical index before marking startup ready. Query fallback, lazy rebuild,
a second executor, a new memory allocation, a new cursor, and a compatibility
decoder remain forbidden.

## Non-Goals

0.225 excludes:

- a new journal cursor, batch envelope, or general journal redesign;
- read-only Validate followed by canonical Apply;
- raw-envelope, digest, sequence, byte, record, fanout, or overshoot redesign;
- continuous folding or routine scheduling after successful normal commits;
- live-overlay convergence semantics;
- tail aggregate metadata, a backlog ceiling, or convergence-pressure
  admission;
- exact durable entity or index-prefix cardinality;
- application callbacks, persisted hooks, or automatic endpoint exports;
- a second schema-migration runner or automatic migration policy;
- caller-selected recovery policy; and
- general ingestion, aggregate-job, rollup, partition, or planner work.

## Persisted And Public Hard Cuts

- Ordinary operations move directly from incidental recovery to state-only
  admission. No legacy helper retains the old side effect.
- The public error taxonomy gains one current recovery-pending identity rather
  than an alias for generic conflict.
- `DatabaseStartupState` is the sole successful readiness representation; no
  Boolean alias or string status is added.
- `StartupFailureReceipt` has one bounded current format and one coordinator
  owner. It is not embedded in the journal or decoded as an old/new dual form.
- Generated timer wiring moves directly to the dedicated driver. There is no
  dual generated path.
- The 0.225.2 correction adds only the accepted-schema index delete/put record
  tags to the current batch envelope and exhaustive decoder. It does not add a
  cursor version, compatibility decoder, alternate batch format, or dual path.
- No compatibility decoder, alias, shim, dual dispatch, fallback readiness
  inference, or generated-model recovery authority is permitted.

No canister endpoint is automatically exported. Applications may embed the
trusted Rust state and error in their own authorized surface.

## Non-Negotiable Invariants

1. Accepted schema snapshots remain runtime authority.
2. `Ready` is impossible while a marker, fold cursor, startup-actionable tail,
   incomplete recovery epoch, or exact generated submission remains
   unreconciled; a later compatible DDL-owned accepted-head revision does not
   invalidate an already-terminal generated submission.
3. `Recovering` is observable without decoding a journal batch or mutating
   stable state.
4. Ordinary queries, mutations, diagnostics, schema operations, and `db!()` do
   not advance recovery or a pending generated-schema application. The hidden
   startup driver advances the latter through its canonical executor; only the
   explicitly allowed existing migration-control lane may externally advance
   its separately owned migration job.
5. Recovery advances only in replicated update execution.
6. Pending recovery has one dedicated retryable typed error.
7. Deterministic corruption and incompatible state never collapse into
   `Recovering`; timer-discovered failure remains observable through one
   binding-checked durable receipt.
8. At most one driver callback is logically active for one database domain.
9. A recurring watchdog wake-up already survives before driver execution;
   trap, instruction exhaustion, and duplicate scheduling cannot strand the
   driver or publish false readiness.
10. Application callbacks never execute inside a recovery-page callback.
11. Generated schema reconciliation occurs only after recovery completion.
12. Generated models never reconstruct missing runtime authority.
13. Maintained production startup and timer paths use no explicit `panic!`,
    `unwrap`, or `expect`, and no recoverable failure is left unhandled.
14. Raw non-gzipped Wasm is the authoritative footprint measure.
15. No normally committed post-`Ready` execution, successful or failed, leaves
    actionable recovery controls without atomically ensuring a watchdog
    wake-up. Trap/instruction exits roll back uncommitted control and scheduling
    changes together.
16. One timer provider owns the watchdog. Provider substitution is allowed only
    after proving the complete pre-armed successor, lifecycle reconstruction,
    cancellation, self-caller, trap/exhaustion, overdue-delivery, and populated
    recovery contract; optional or dual provider modes are forbidden.
17. Journaled accepted DDL cannot advertise a ready user index whose exact
    physical deletion/insertion domain is absent from durable recovery
    authority; startup remains gated until both schema and domain converge.

## Complexity And Maintenance Gate

Demonstrated need: startup currently has no explicit public state, ordinary
operations can invoke recovery, and generated scheduling can couple recovery
and application work.

Simplest alternative rejected: a broad conflict plus application delay does
not prove readiness and leaves engine cost on arbitrary callers.

Canonical owners: startup coordinator for state, current recovery engine for
semantics, replicated driver for progress, generated wiring for lifecycle, and
application for its own scheduler.

State-space delta: one two-value readiness result, one dedicated pending error,
one bounded terminal `StartupFailure`, one durable failure receipt, and three
non-authoritative volatile watchdog conditions. It adds no persisted policy
mode, recovery cursor format,
journal format, backlog state, or cardinality generation. The receipt removes
the otherwise unbounded observable state in which a timer has found terminal
corruption but all later callers can see only `Recovering`.

Promotion fails if implementation requires a second recovery engine, a second
timer policy beyond the one fixed watchdog, persisted application callbacks,
query-side fallback driving, an independent schema-migration runner, an early
0.228 cursor, or compatibility paths. Every handoff reports files and
approximate line delta, delivery domains, instruction/stable/raw-Wasm changes,
states added or removed, duplicate flows, and whether the implementation became
simpler, stayed neutral, or became more complex.
