Audit date: 2026-08-18

`make patch` version transition)

## Findings

### Critical, resolved: `v0.230.2` identifies the preceding candidate

The annotated `v0.230.2` tag already exists at commit
`ded57cffdf12a2e273746179113014cd18dcc090`, tree
`9d8db4be342dd32c31d5f9d1be346a22420068f3`. Audited `HEAD` is later commit
`06863b6f870f1f88795ec4c109216d532ed66da2`, tree
`d72a4226a60855f5abe9de6721a87f2875cc9324`, and no tag contains it. The only
committed difference after the tag is a retroactive `CHANGELOG.md` rewrite.

The correctness corrections below exist only as uncommitted worktree changes,
so the existing tag cannot identify them. The user selected `0.230.3` for the
complete corrected bundle on 2026-08-18. The audit therefore leaves
`v0.230.2` immutable and treats it as preceding release history. Version bump,
commit, tag, push, and publication remain user-owned and were not attempted.

### High: journaled consumers accepted volatile counts as authority

Pre-audit `StoreHandle::exact_entity_count` and
`StoreHandle::exact_user_index_prefix_count` returned populated volatile
full-count caches before reading or validating the durable generation. This
bypassed generation state, source identity, watermark, accepted index identity,
full digest, and build-cursor validation. It contradicted the one-authority
contract even when the volatile value happened to agree.

The correction is in `crates/icydb-core/src/db/registry/handle.rs` at
`StoreHandle::exact_entity_count`, `exact_user_index_prefix_counts`, and
`ready_cardinality_counts`. Heap stores retain their volatile exact-count
convenience. Journaled stores require one validated `Ready` base plus the exact
signed post-watermark delta.

### High: partial accepted user-index prefixes were rejected

The consumer predicate required prefix component count to equal full index
arity. A `k`-component accepted index persists all nonempty prefixes `1..=k`, so
the predicate incorrectly made shorter valid prefixes unavailable.

`CardinalityBuildAuthority::accepts_user_index_prefix` in
`crates/icydb-core/src/db/schema/cardinality_build.rs` now admits precisely
`1..=accepted_arity`. The regression
`accepted_user_index_authority_covers_every_non_empty_component_prefix` covers
zero, every valid prefix, over-arity, and unknown identity.

### High: a newly accepted live root did not invalidate consumers immediately

Consumer authority was derived only from the folded canonical accepted root.
After a successor root published into the positioned live overlay but before
its batch folded, the preceding canonical root and old cardinality header could
still validate together.

`CardinalityBuildAuthority::derive_for_current_consumer` now compares the
effective accepted authority with the canonical accepted-root selection and
makes evidence unavailable on drift. The journaled regression in
`crates/icydb-core/src/db/session/write.rs` proves immediate invalidation and
proves that populated volatile entity and prefix caches cannot rescue the stale
evidence.

### High: bounded child enumeration bypassed the proof boundary

`expand_index_prefix_family_with_exact_child_prefixes` called `IndexStore`
directly. That made a volatile-only child set planner-visible without durable
source or count proof. It now calls
`StoreHandle::exact_user_index_child_prefixes_for_parent_set`. For journaled
stores the volatile structure may propose a bounded set, but synchronized
durable parent and child totals must prove the proposal complete before use.

Same-index prefix families are validated in one batch through
`StoreHandle::exact_user_index_prefix_counts`; direct `COUNT`, empty pruning,
prefix sums, covering execution, and bounded child enumeration therefore share
the same proof boundary.

### High, corrected: consumer proof redundantly decoded the accepted bundle

The first correctness-only correction made each exact consumer reread and
decode the complete canonical accepted bundle. The maintained
`sql_perf_token_branch_set_limit50_pressure_beats_overcap_fallback` regression
therefore measured 125,867,260 execute instructions for the exact wide branch
against 16,474,822 for the conservative fallback. Batching same-index proofs
reduced that to 17,413,664 versus 16,402,920 but still failed the contract.

The final correction adds `SchemaStore::current_accepted_schema_authority_ref`.
It borrows the existing root-keyed verified effective bundle only after an
independent canonical root read proves the effective and canonical selections
identical. It adds no cardinality cache, proof lifetime, persisted state, or
alternate authority and avoids cloning the bundle. The exact rerun passes at
5,357,533 execute instructions versus 10,379,743 for fallback, about 48 percent
lower. The complete durability slice then passes all 88 tests.

### High: required whole-repository gates remain unexecuted

Repository instructions explicitly prohibit agents from running `make test`,
`make validate`, `cargo test --workspace`, `cargo test --all`, or equivalents.
Those instructions take precedence over the request to run full repository and
release suites. The commands were not run. Because the requested gate requires
that evidence, this audit cannot return a ready verdict.

Release mutation commands (`make patch`, `make release-stage`,
`make release-commit`, `make release-push`, and `cargo publish`) were also not
run, as required by both the request and repository rules.

### Medium: the 0.230.3 source candidate remains uncommitted and pre-bump

The audit began with a user-owned `Cargo.lock` change updating `h2`,
`quinn-proto`, and `zerovec-derive`. The user subsequently directed that all
current work be bundled into `0.230.3`, so those compatible dependency
resolutions are now part of the intended candidate. The production artifact

The artifact is valid evidence for this exact source candidate, but the
workspace still reports version `0.230.2`; repository policy requires the
user-owned `make patch` flow to validate first and perform the mechanical

## Core Correctness Reconstruction

### Authority and persisted identity

`CardinalitySourceIdentity` binds database incarnation, the fingerprint of all
four store allocations, accepted root revision and fingerprint, accepted index
count and canonical set fingerprint, and complete fold watermark. The current
version-1 header adds generation ID, `Building`/`Ready`, and slot. Header,
cursor, and count codecs accept only their single exact length/magic/version
and validate fingerprints. `CardinalityCountRecord::validate_identity` checks
both generation and the full 32-byte stored digest after the 15-byte physical
key selection, closing physical digest collisions.

Zero is represented by record absence. All generation, count, signed-delta,
page-total, entry, byte, and prefix arithmetic relevant to authority uses
checked operations. Saturation found in the diff is confined to diagnostic
instruction measurement or pre-existing bounded executor helpers, not count or
generation authority.

No legacy decoder, predecessor inspector, migration translator, generated-model
fallback, estimate, alternate statistics epoch, or compatibility path exists.
Malformed, unsupported, incomplete, contradictory, identity-mismatched,
collision-affected, and stale evidence returns a typed error or unavailable
proof.

### Exact count semantics

Rows contribute one entity presence transition only when their decoded entity
is accepted by the bound snapshot. Present entries from the exact accepted
physical user-index set contribute every nonempty component prefix. `Missing`,
nullable omission, system indexes, candidate/rejected indexes, retired
identities, malformed keys, and nonaccepted generations cannot contribute.

Recovery derives changes from final prepared raw-key transitions, validates row
and entry witnesses, coalesces duplicate digests, and preflights checked add or
subtract. Insert, delete, replacement, same-key repetition, nullable
transition, index membership change, hidden older fold, overflow, underflow,
unknown identity, arity mismatch, and collision controls are covered by the
focused cardinality, schema-store, commit, convergence, and trap tests.

### Bounded construction and publication

The frozen page limits remain constants in
`crates/icydb-core/src/db/schema/cardinality_build.rs`:

- 4,096 source entries;
- 16,777,216 source key/value bytes;
- 16,384 prefix updates.

`BuildPageBudget::admit` computes the next totals with checked arithmetic and
declines before consuming the first entry that would exceed any dimension.
Row and index collectors resume exclusively after a validated raw checkpoint,
including maximum-sized keys and the row-to-index transition. Each page is
fully decoded, validated, sorted/coalesced, arithmetically preflighted, and
encoded before `apply_prepared_cardinality_build_page` begins stable mutation.
After that point only stable-map insert/remove operations occur. Ordinary
errors are returned before mutation; backend contradictions in complete fold
application trap and rely on IC whole-message rollback.

Empty canonical row and accepted-index domains publish exact zero without a
row or index scan. No startup, query, repair, or alternative scan builder was
found.

Publication requires complete row and index phases, a matching complete
cursor, unchanged source identity, `Building` state, and an isolated slot.
Publication removes the cursor. `Ready` with a cursor is rejected everywhere.
Source drift during clear/build/completion/publication starts a checked next
generation in the alternate slot; it does not merge prior candidate counts.
Repeated maximum-shape use reaches both slots and then remains at fixed
physical high-water.

### Fold maintenance and live visibility

`prepare_folded_cardinality_maintenance` runs only after complete journal-batch
validation and before `apply_preflighted_fold`. Schema/index mutations
invalidate rather than reinterpret the source. `SchemaStore` preflights every
coalesced physical key, detects same-page shortened-key collision, validates
the current `Ready` header and absent cursor, computes every count, encodes the
next source-bound header, and reserves output before the first canonical row or
index write. Count records and the next watermark therefore describe the same
completed transition; partial batches cannot publish a new boundary.

The maintained derivation bound remains
`D <= R_insert_delete + 4I_user_actual`. Positioned overlay maps carry exact
signed deltas relative to canonical state and account for insert, replace,
delete, same-key newer effects, hidden older folds, pressure, quiescence, and
reopen. A journaled visible count now has only one derivation: validated
durable `Ready` base plus exact post-watermark delta.

### Scheduling, safety, and scope

The generated startup watchdog remains the sole timer/driver. It tries normal
recovery first, advances at most the first nonquiescent store-local cardinality
action, self-chains while work remains, and stops when all stores quiesce.
Optional cardinality failure terminates optional work without changing row or
index authority or ordinary database readiness. Generated init and
post-upgrade paths initialize/arm runtime state and do not scan canonical
domains.

Contextual review of added `unwrap`, `expect`, `panic`, assertion,
`unreachable`, unsafe, conversion, indexing, saturation, allocation, and clone
sites found no new production panic or unsafe path. Matches were tests,
diagnostic measurement, `debug_assert`, or already bounded executor code.
Stable decoding is length-bounded and fallible. No unbounded collection clone
or ordinary fallible work after page mutation was found.

The line adds no fifth store allocation; the deployment bound remains 38. It
adds no second row/index lifecycle, second statistics epoch, public policy,
setting, endpoint, method mode, export, persisted work flag, timer, scheduler,
or instruction-ceiling increase. The audit-only
`mutate_cardinality_closeout_index` endpoint remains behind `test-admin-api`
and is absent from production Candid and Wasm exports.

## Baseline-To-Final Scope And Complexity

Before audit corrections, `v0.229.1..HEAD` contained 36 files excluding the
lockfile, with 6,191 insertions and 173 deletions. The line introduces one
durable version-1 generation lifecycle, one cursor, and two reusable physical
count namespaces inside the existing schema allocation. It does not add a
second semantic authority, allocation, timer, public policy, or endpoint.

The audit correction adds a batched proof-bound consumer path, borrowed reuse
of the existing accepted-bundle cache, focused regressions, and the complete
`0.230.3` release notes. Excluding the adopted `Cargo.lock`, it touches 15
files including this report. The final correction delta is 930 insertions and
120 deletions. The complete predecessor-to-audited-worktree diff excluding
`Cargo.lock` is 38 files, 7,027 insertions, and 199 deletions; including the
adopted lockfile it is 39 files, 7,070 insertions, and 242 deletions. The
persisted and public state-space delta remains zero.

The correction increases local implementation complexity because stable
generation proof is now explicit for journaled prefix families and bounded
child proposals, but it reduces semantic complexity by removing two divergent
volatile-authority bypasses. Persisted/public state-space delta is zero for the
correction.

Performance and Wasm deltas are reported above. The maintained wide branch is
now about 48 percent cheaper than its conservative fallback; no assertion or
threshold was weakened.

## Verdict

**NOT READY**.

The core durable-generation design, construction, fold atomicity, slot reuse,
instruction ceilings, post-upgrade behavior, direct-count storage-read
contract, raw-Wasm allowance, Candid, and exports are supported by independent
evidence after the worktree corrections. Release readiness is nevertheless
blocked by the uncommitted source candidate, pending user-owned `0.230.3`
version transition, and mandatory unexecuted whole-repository gates.
