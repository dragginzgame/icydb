## Planning Status And Authorization

This line makes exact entity and accepted user-index prefix cardinality durable,
generation-bound derived evidence. It owns bounded construction for populated
predecessor stores, publication, invalidation, and incremental maintenance.

Release `v0.229.1` is the accepted predecessor. Patch 1 reconciled that exact
release, froze the generation/build/storage shape and acceptance gates in the
[implementation status](0.230-status.md), and the user explicitly authorized
0.230 on 2026-08-17. Each later patch remains separately bounded by the landing
tracker.

## Decision Summary

0.230 introduces one durable exact-cardinality generation per journaled store.
It contains entity counts and all accepted user-index component-prefix counts
for the exact accepted identity set. It is derived evidence, never row, index,
schema, or optimizer authority.

Every generation binds:

- cardinality format version;
- database incarnation;
- store allocation identity;
- accepted schema root/revision;
- exact accepted user-index identity set;
- canonical fold watermark/epoch; and
- generation identity and lifecycle state.

The only persisted lifecycle states are:

```text
CardinalityGenerationState {
    Building,
    Ready,
}
```

Missing, malformed, unsupported, identity-mismatched, fold-stale, or incomplete
evidence is unavailable to planning. It is not translated, inferred, or
reconstructed from generated models.

`Ready` evidence describes the canonical state at its bound watermark. The
planner may derive exact visible cardinality only by combining that Ready base
with the exact bounded live-overlay delta guaranteed by 0.229. If either base
or delta is unavailable or mismatched, planning uses its maintained
deterministic conservative path.

Empty accepted stores publish exact zero without a scan. A populated predecessor
without current evidence starts an explicit bounded initial build outside
`post_upgrade`. It scans canonical accepted rows and accepted user-index entries
in stable key order into isolated candidate storage, checkpoints physical
progress, binds to the source revision/watermark, and publishes only after one
complete clean pass.

Once Ready, canonical convergence transitions update exact counts
incrementally. During a partially applied batch, evidence is not newly
published as Ready. Batch completion binds the updated counts to the new fold
watermark. Accepted schema or index identity changes invalidate the generation
and start a new isolated current build; old counts never leak across identities.

## User Outcome

- Populated stores regain exact entity and accepted index-prefix counts without
  a startup scan.
- Planning never consumes a count from the wrong database, store, schema,
  index set, or fold boundary.
- Empty stores have exact zero immediately.
- A bounded build survives calls and upgrades and publishes only complete
  evidence.
- Writes and online fold preserve exact counts incrementally after publication.
- Missing or stale evidence retains deterministic conservative planning.
- Future statistics work extends this generation authority rather than adding
  a second statistics epoch or store.

## Canonical Ownership

1. accepted schema snapshots own entity and index meaning;
2. canonical row and accepted user-index stores own the facts counted;
3. the accepted 0.228/0.229 watermark owns the canonical boundary;
4. one store-local cardinality generation owns exact derived counts for that
   bound identity and boundary;
5. one bounded build cursor owns isolated candidate construction;
6. the 0.229 live overlay owns exact post-watermark visibility deltas; and
7. the planner owns conservative route selection when exact evidence cannot be
   proved.

The cardinality store is the sole durable generation authority for exact counts.
0.236 may extend its generation identity/lifecycle with advisory statistics,
but may not create a parallel cardinality generation, epoch, build, or stale
policy.

Durable cardinality records use reserved namespaces in the existing store-local
schema allocation. They do not add a fifth store allocation, reduce the
38-store deployment bound, or add a public memory-ID setting. One control
namespace plus two isolated count namespaces provide a single header/build
cursor and Ready/Building slot separation without retaining generation history.

## Exact Count Contract

Entity cardinality counts every canonical accepted row for one accepted entity
tag in the store.

Index-prefix cardinality counts only present entries of accepted user indexes.
For an index with `k` ordered key components, every non-empty accepted prefix
length from `1..=k` is counted under the exact accepted index identity. System,
candidate, rebuilding, missing, or rejected index generations do not contribute.
An omitted nullable key contributes no index entry and therefore no prefix
count; 0.230 does not redefine nullable index membership.

Counts are exact `u64` values. Overflow is typed invalid evidence, not
saturation. Duplicate/malformed raw keys, impossible removals, unknown index
identity, or count underflow make the current candidate unavailable and produce
owner-local integrity evidence.

## Generation And Build Lifecycle

### Building

A `Building` header binds the target identities, source watermark/revisions,
current scan domain, last completed physical key, isolated candidate
generation, and bounded progress counters. Build pages:

- scan canonical rows/index entries in stable physical order;
- decode keys fallibly and charge bytes, entries, prefixes, and instructions;
- write counts only into the isolated candidate generation;
- checkpoint after bounded work;
- restart from a fresh empty candidate if the bound canonical or accepted
  identity changes; and
- remain optional for query correctness.

No page scans live overlays as canonical input. Writes may continue, but a
revision change invalidates that pass rather than attempting an unproved merge.

### Ready

Publication verifies complete row and index phases, exact accepted identity
coverage, unchanged source revision/watermark, and a current candidate header.
One current publication transition makes the candidate Ready; incomplete
counts are never planner-visible.

After publication, each prepared canonical row/index transition carries its
exact count delta. Count update and convergence progress are reconciled through
the existing digest-bound complete-batch fold watermark and exact positioned
overlay evidence. No convergence cursor is introduced. The generation is Ready
only at a complete watermark boundary. Overlay deltas preserve exact current
visibility between normal commit and canonical fold.

### Unavailable And Stale

Absence, Building state, identity mismatch, stale watermark, unsupported
version, malformed bytes, overflow, underflow, or incomplete prefix coverage
returns no cardinality evidence to the planner. Integrity inspection may report
the typed reason. Ordinary query correctness continues through the maintained
deterministic conservative plan; it never substitutes zero, a generated count,
or an estimate.

## No-Build And Alternatives Gate

- Startup scanning violates the bounded readiness contract and grows with
  database history.
- Generated models know declarations, not stored rows or accepted physical
  indexes.
- Rebuilding counts on every query is an unbounded scan and duplicates planner
  work.
- An advisory approximate estimate cannot replace the exact counts already
  used for correctness-preserving bounded route decisions.
- A separate entity generation and index generation would multiply publication
  and staleness states; one store generation keeps them synchronized.
- Folding old counts into a new accepted index identity is a compatibility
  translation and is prohibited.

Patch 1 must stop or narrow this line if the accepted predecessor already has a
durable exact generation with equivalent database/store/schema/index/watermark
binding.

## Scope

0.230 includes:

- exact entity cardinality;
- exact accepted user-index prefix cardinality;
- database, store, accepted schema, accepted index-set, and fold-progress
  generation binding;
- `Building`, `Ready`, unavailable, and stale behavior;
- exact empty-store zero publication;
- a bounded initial populated-store build;
- revision/index invalidation and isolated candidate restart;
- atomic publication at a clean current boundary;
- incremental maintenance with canonical convergence and bounded overlay
  deltas; and
- deterministic conservative planner behavior without evidence.

## Non-Goals

0.230 excludes:

- approximate distinct counts, null fractions, samples, histograms, sketches,
  selectivity ranges, or correlations;
- general cost-based optimizer work;
- plan comparison, rejected-route, estimate/actual, warning, or observability
  surfaces;
- changes to nullable unique-index semantics;
- full integrity repair or startup reconstruction;
- generated-model fallback;
- caller-configurable build/cardinality policy; and
- compatibility decoders or migration of nonexistent legacy cardinality state.

## Persisted And Public Hard Cuts

- One current durable generation/header/count-key/build-cursor format is added;
  no legacy format exists or is inferred.
- Populated stores without current evidence are explicitly unavailable and
  build a new current generation; they are not decoded through a fallback.
- Accepted schema/index changes create a new current generation and retire the
  old candidate directly.
- Planner count access moves to the one proof-bound source plus exact overlay
  delta; no volatile-only or generated fallback remains as competing authority.
- For journaled stores, `StoreHandle` either validates the live accepted root
  against canonical authority itself or consumes the exact root/incarnation
  already admitted by the current `EntityAuthority`. It then reads one
  source-matching `Ready` generation. Volatile full-count caches may remain
  heap-store conveniences, but journaled consumers use only durable bases plus
  exact overlay deltas.
- The positioned index delta carries the exact canonical fold watermark from
  which it was derived. Recovery binds that watermark without scanning; every
  complete fold preflights it before canonical mutation and advances it with
  the same transition. An unbound, stale, or impossible delta is unavailable.
- Once the effective and canonical root selections agree, consumers may borrow
  the existing root-keyed verified accepted bundle. They do not reread, clone,
  or decode that immutable bundle, and no cardinality-specific proof cache is
  introduced.
- Bounded child-prefix enumeration may use the volatile index structure only
  to propose children. `StoreHandle` proves the proposal complete by comparing
  source-validated exact parent and child totals before a planner consumes it.
- Malformed or stale cardinality is rejected as evidence without changing row
  or index authority.
- No public endpoint, successful query-result shape, or accepted schema meaning
  changes in this line.

## Non-Negotiable Invariants

1. Cardinality is derived evidence; rows, indexes, and accepted schema remain
   authority.
2. Every generation binds database, store, accepted schema, accepted index set,
   and canonical fold progress.
3. Planner-visible evidence is either completely Ready and synchronized or
   absent.
4. Building counts remain isolated from planning.
5. Empty accepted stores may publish exact zero without scanning.
6. Populated initial construction is bounded, checkpointed, fallible, and
   outside startup readiness.
7. Revision or identity drift invalidates and restarts the candidate; it never
   merges unproved counts.
8. Entity and accepted user-index prefix counts publish as one generation.
9. System, candidate, missing, and non-accepted index entries are excluded.
10. Count arithmetic never silently saturates, underflows, or guesses.
11. Incremental count deltas correspond to the exact prepared canonical
    transition and complete-batch journal position.
12. A Ready canonical generation plus exact post-watermark overlay delta is the
    only exact visible-count derivation.
13. Missing, stale, malformed, or incompatible evidence produces deterministic
    conservative planning.
14. Generated models never reconstruct counts or accepted index identities.
15. 0.236 must extend, not duplicate, this generation authority.
16. Production build/maintenance paths contain no panicking operations.
17. Raw non-gzipped Wasm is the authoritative footprint measure.

## Baseline And Acceptance Measurements

Patch 1 records entity and prefix count availability, planner route/entry/row
effects with and without counts, cardinality lookup instructions, initial build
entries/bytes/prefixes/instructions per page, publication and incremental write
cost, stable bytes per entity/index/prefix, candidate peak storage, startup
instructions, final raw Wasm, deterministic gzip secondary, Candid/method modes,
and complexity signals.

Acceptance requires no row/index scan in `post_upgrade`; exact zero for empty
stores; bounded populated build pages; publication only at an unchanged exact
boundary; exact incremental counts across all current record families that
affect them; deterministic conservative planning whenever proof is absent; no
duplicate statistics generation; and raw-Wasm/storage/write amplification
within frozen review gates.

Measurements distinguish rows `N`, accepted index entries `E`, prefix updates
`K`, build pages `P`, candidate bytes `C`, steady cardinality bytes `S`, planner
row loads `B`, and instructions `I`. Planner benefit must be reported beside
stable and write amplification.

## Complexity And Maintenance Gate

Demonstrated need: exact cardinality already influences maintained planning but
is intentionally lost on populated reopen and cannot recover without an
unbounded scan.

Simplest alternative rejected: permanent conservative fallback preserves
correctness but discards a maintained exact planning capability after every
upgrade.

Canonical owner: one store-local durable exact generation synchronized to
accepted identities and fold progress, with one isolated build cursor.

State-space delta: Building/Ready plus unavailability derived from absence or
failed proof. One generation owns both entity and prefix counts. No statistics
epoch, estimator, histogram, optimizer mode, startup repair, or user setting is
added.

Promotion fails if implementation creates separate entity/index publication
lifecycles, scans during startup, guesses stale counts, duplicates 0.229
revision/overlay authority, or pre-builds 0.236 statistics abstractions. Every
handoff reports files/line delta, domains, states, duplicate flows,
instruction/stable/raw-Wasm effects, and complexity direction.
