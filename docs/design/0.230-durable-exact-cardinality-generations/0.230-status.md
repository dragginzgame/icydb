## Frozen Durable Shape

### Storage owner and key space

Cardinality uses the existing store-local schema `StableBTreeMap`; it adds no
stable-memory ID and does not change the four-role registry or `S_max = 38`.
`RawSchemaKey` remains exactly 16 bytes. The currently unused namespaces are
reserved as follows:

| Namespace | Purpose |
| ---: | --- |
| `0x05` | One generation header and one bounded build-cursor control record |
| `0x06` | Count slot A |
| `0x07` | Count slot B |

Count keys are `slot namespace || digest[0..15]`. The complete 32-byte digest
is stored in the value and must match on every read/write; a truncated-key
collision makes the candidate unavailable rather than selecting another
logical count. The domain-separated SHA-256 preimage is:

```text
"icydb.cardinality-count-key.v1"
|| kind
|| entity_tag_be
|| [index_id_bytes || component_count || (component_len_be || component_bytes)*]
```

`kind = 0` identifies an entity count and omits the bracketed suffix.
`kind = 1` identifies an accepted user-index prefix and includes the fixed
`IndexId` bytes plus one to four canonical encoded components. This is the
durable form of the existing `UserIndexPrefixCardinalityKey`; system,
candidate, Missing, and rejected generations have no count key.

The two count slots are isolated candidate/Ready buffers, not two semantic
owners. Before reuse, the inactive slot is cleared through bounded pages. At
most one Ready and one Building slot exist, and retired generations are not
retained as history.

### Generation identity

Every header binds all of the following current authority:

- format version `1`;
- database incarnation;
- a domain-separated fingerprint of the active data/index/schema/journal
  allocation quartet, including each memory ID and stable key in role order;
- accepted store-root presence, revision, and 32-byte fingerprint;
- the count and domain-separated fingerprint of canonical sorted accepted
  user `IndexId` values;
- `FoldWatermark::{highest_folded_journal_sequence, fold_epoch}`;
- checked monotonic generation ID;
- active slot and `Building` or `Ready` state.

The accepted root already commits to the accepted bundle, but the explicit
index-set digest keeps the counted physical generations reviewable and
independently checkable. Missing, malformed, unsupported, mismatched, or stale
identity is unavailable evidence. No predecessor decoder or generated-model
reconstruction is permitted.

### Build cursor

The cardinality build cursor is unrelated to the removed convergence cursor.
It is a bounded scalar checkpoint for optional derived-evidence construction
and uses only the current version-1 form. It binds the candidate generation and
all source identities above, then stores:

- phase `Rows` or `Indexes`;
- the last completed physical row or index key, resumed exclusively;
- checked source-entry, source-byte, prefix-update, and distinct-count-key
  totals.

The row key is bounded by `RawDataStoreKey` at 262 bytes. The index key is
bounded by `IndexKey` at 16,668 bytes, so the complete cursor record must remain
within 20 KiB. A page admits at most 4,096 source entries, 16,777,216 source
key/value bytes, and 16,384 prefix updates, stopping before the first exceeded
dimension. The page must also remain below the inherited 30-billion
instruction policy and the IC 40-billion message limit. These are fixed
internal limits, not caller configuration.

Rows are scanned first in canonical physical-key order, followed by index
entries in canonical physical-key order. Index build input must decode to a
present accepted user-index entry in the bound set; every non-empty component
prefix contributes exactly once. A changed root, index set, watermark, store
identity, or database incarnation discards the candidate and starts a fresh
inactive slot. No page scans live overlays as canonical input.

### Frozen lifecycle transitions

| From | Event | To and required behavior |
| --- | --- | --- |
| Absent/unavailable | Empty canonical row and accepted-index domains | Publish Ready exact zero at the current identity/watermark without a scan |
| Absent/unavailable | Populated current store | Clear the inactive slot and enter Building; ordinary planning remains conservative |
| Building | Bounded page, source unchanged | Advance the exclusive physical cursor in the same candidate |
| Building | Source identity or watermark drift | Discard/clear the candidate and restart from the new exact source |
| Building | Rows and indexes complete, source unchanged | Atomically publish the candidate slot as Ready |
| Ready | Prepared canonical batch | Preflight checked count deltas and target generation before canonical mutation; publish the new complete watermark with the exact counts |
| Ready | Accepted root/index-set drift | Make old evidence unavailable and begin a fresh isolated build |
| Ready | Live debt after its bound watermark | Derive exact visible counts only from the Ready base plus exact positioned-overlay deltas; otherwise fall back |

The existing 0.225 replicated driver owns optional build wake-ups, duplicate
coalescing, and self-chaining. Startup never scans rows or indexes and may
reach ordinary `Ready` while cardinality is Building/unavailable because the
planner fallback is correctness-preserving. No timer, scheduler, persisted
`work_pending` flag, public mode, or configuration axis is added.

## Frozen Resource And Acceptance Gates

Let `G` be the number of nonzero entity keys plus distinct accepted user-index
prefix keys in one complete generation. A count record uses one 16-byte key and
a fixed value containing magic/version, generation ID, full 32-byte logical-key
digest, and exact `u64` count. Patch 2 must keep that value at or below 64 bytes
and the fixed generation header at or below 256 bytes.

- Logical steady count payload is bounded by `80G + 256` bytes.
- Physical candidate high-water, measured on an isolated store, must remain at
  or below `256G + 262,144` bytes above the pre-build baseline.
- Repeated clear/build/publish/clear/build cycles must reuse the two namespaces
  and stop increasing physical high-water after both slots have reached the
  maintained maximum shape.
- One row insertion/deletion contributes at most one entity delta. Each actual
  accepted user-index put/delete contributes at most four prefix deltas.
  Same-key deltas are coalesced before stable writes, so prepared delta events
  satisfy `D <= R_insert_delete + 4I_user_actual`.
- Patch 5 must retain the 0.229 30-billion fold-callback ceiling, including the
  65,536-key accepted-index shape. A ceiling increase is not authorized. If
  exact maintenance cannot fit, Patch 5 stops for a design decision rather
  than weakening exactness or adding paged convergence.
- Ready direct COUNT must retain zero row-store gets and zero index-entry reads.
  Missing/Building/stale/malformed evidence must return the maintained result
  through conservative execution, never through an estimate or guessed zero.
- `post_upgrade` must perform no canonical row/index scan and remain under the
  maintained 25-million startup-observation ceiling.
- The complete 0.230 line may add no Candid method/mode or export and may not
  grow the final raw `sql_perf` Wasm by more than 131,072 bytes without a
  reviewed simplification or scope decision. Raw Wasm is authoritative; gzip
  remains secondary.

These gates deliberately make maximum accepted-index maintenance and physical
slot reuse blocking evidence. They are not permission to raise an inherited
ceiling or add a second admission/scheduling route.

## Patch 2 Durable Generation Identity And Codec Results

### Current persisted forms

- `db/schema/cardinality_generation.rs` owns one current version-1 codec set.
  There is no predecessor constant, decoder, inspector, translation, or
  fallback form.
- The generation header is exactly 192 bytes: a 160-byte fixed body plus a
  domain-separated 32-byte SHA-256 fingerprint. Its source identity occupies
  141 fixed bytes and binds every frozen database/store/schema/index/watermark
  dimension.
- A count record is exactly 57 bytes and the schema key remains exactly 16
  bytes, for 73 logical bytes per stored nonzero count. The value retains the
  complete 32-byte digest, so the 15-byte physical digest prefix cannot become
  an alternate authority after a collision.
- The build cursor has a 197-byte fixed body, an optional bounded physical key,
  and a 32-byte fingerprint. Its maximum index-checkpoint form is 16,897 bytes
  (16,913 logical bytes with its schema key), below the frozen 20-KiB limit;
  the maximum row-checkpoint form is 491 bytes.
- `RawSchemaKey` now reserves exact control keys in namespace `0x05` and
  digest-prefixed count keys in slots `0x06` and `0x07`. A focused stable-map
  reopen proves all three record families remain decodable from the existing
  schema allocation.
- Generation increment, encoded-length arithmetic, cursor bounds, and all
  reader offsets are checked; the exact count form accepts through `u64::MAX`
  while zero remains absence. Zero generation/count values,
  unknown versions, malformed lengths, trailing data, fingerprint corruption,
  invalid source closure, phase/checkpoint mismatch, and typed source or count
  identity mismatches fail closed.

Patch 2 defines persisted authority but has no production writer or consumer.
